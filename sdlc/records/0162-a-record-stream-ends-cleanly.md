# 0162: A record stream ends cleanly

Status: Built on `ticket/0162-a-record-stream-ends-cleanly`, awaiting fresh read-only code review and landing gates.

The batch reader now polls standard output between requests and stops when the platform reports a closed downstream pipe. A real-pipe compiled-binary test reads the first kept `filter` row and closes its reader. At `--batch 1` and `--batch 10`, the command exits 0, stays quiet and sends at most 12 of 301 possible requests with `--jobs 4`. The test failed before the change because the command sent all 301. Existing closed-pipe tests still cover commands that write each result and quiet termination after a concurrent backend failure.

The line reader now skips empty, white-space and CRLF blank lines before a request or batch, while carrying original input line numbers. The first compiled-binary regression failed before the change and now sends exactly three requests for three text lines separated by blanks, prints three rows and exits 0. A second boundary table adds the case the first test does not cover: a failed line after a skipped blank reports input line 3 with one finished record. It also pins that blank JSONL still fails at line 2. Both cases count one request and pin the complete stop message and exit code. The two tests share one loopback answer builder.

The command now carries a numbered failure through the existing scheduler and takes the stop line number from that failure. The engine drops its unused `at` field; its finished count and ordering stay unchanged. No public API or library binding changed. The record specification now states the blank-line rule, its stop numbering, the platform-dependent closed-pipe check, and the derived reply time behind the old `--jobs 3` rate. It states that no requests-per-minute setting exists.
