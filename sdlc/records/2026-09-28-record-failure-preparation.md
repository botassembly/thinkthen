[Roadmap](../../specification/roadmap.md) holds `--on-error continue` because it needs an error-row shape, count and distinct exit. The 2026-09-27 [work plan](https://github.com/botassembly/thinkthen/blob/eafcd3f26/sdlc/planning/work-plan-2026-09-27.md) later directs one I1 design after 0162 and B5. Both prerequisites have landed: [0162](../records/0162-a-record-stream-ends-cleanly.md) and ticket 0170's B5 run facts. No `--on-error` parser or policy exists on this revision.
- [The grouped scheduler](../../crates/thinkthen/src/engine/annotate_schedule.rs) stops on an input, preparation, group-answer, or aggregation failure. Its `drain` prints completed rows in input order. [The command bridge](../../crates/thinkthen/src/cli/annotate_schedule.rs) maps a completed run with partial logical failures to exit 6; a later whole-run failure keeps its own exit code and stop position. [The aggregation](../../crates/thinkthen/src/cli/annotate/aggregation.rs) prints a completed row with good answers and failed-question markers. [The reply adapter](../../crates/thinkthen/src/core/adapters/systemone/response.rs) and [facade assembly](../../crates/thinkthen/src/engine/facade/annotate.rs) distinguish failed logical members from a wholly unusable reply. The current [partial-failure CLI tests](../../crates/thinkthen/tests/backend/annotate/partial_failure.rs) pin exit 6 with two printed rows and two sends, then exit 4 with one printed prefix row and two sends after a later status 401.
- [The annotate command](../../crates/thinkthen/src/cli/annotate.rs) rejects any question name already held by an input record before considering `--details`. Its dry run makes the same check in [plan.rs](../../crates/thinkthen/src/cli/annotate/plan.rs). [The spec](../../specification/annotate.md) explicitly promises this exit-2 refusal. A missing `on` pointer reaches `QuestionSet::group_evidence` in [question_set.rs](../../crates/thinkthen/src/core/question_set.rs), then `Reading::part` in [records.rs](../../crates/thinkthen/src/core/records.rs); it reports that the record holds nothing at the named pointer and stops. A failed record sends no request for itself if preparation fails. Already dispatched independent work may still finish; a proof of exact sends should use `--jobs 1` and `--batch 1` where compatible.
- B5's [run-facts carrier](../../crates/thinkthen/src/cli/facts.rs) already emits `thinkthen.run/1` with finished-record and actual-send counts; [stop facts](../../crates/thinkthen/src/cli/failure/facts.rs) include `at`, cause and retryability. A new continuation policy must define whether those fields count attempted, skipped, and error-row records. Do not infer a zero token count when a failed reply reports no usage.

## Proposed design for review

Keep the current stop policy as the default. The smallest coherent explicit continuation is `--on-error continue` for record streams: a failed record emits one structured error row containing its input position, safe failure kind and cause, and no fabricated answer. Processing resumes where it is safe. A completed run that emitted error rows returns a new distinct nonzero exit status and reports the count once on standard error. A later terminal failure keeps its terminal status and stop boundary. Avoid a silent skip option unless a worked demo needs it; it would hide which records were lost. Codes 7 and 8 are reserved by [channels](../../specification/channels.md), but choosing one and fixing the schema require contract review.

Classify refusal by boundary before changing the scheduler. Per-record parse, collision in bare mode, and missing pointer are candidates for continuation with zero sends for that record. Failed logical questions inside an otherwise usable annotate reply already yield answer markers and exit 6; preserve them rather than relabeling the whole row. A whole failed request has no usable answers for its affected records. An error row per affected record is honest and requires no new send, but it does not meet register 43's literal one-poison-record isolation when several records share a batch. Isolating one bad member would require a bounded split/retry design, altered request identity and extra attempts. Treat that as an explicit design choice, not a promise in the first ticket. Cancellation, deadline, defect, output failure, and failures that prevent trustworthy accounting need an explicit terminal rule. Do not silently continue after them. For multi-group annotate rows, decide whether an already answered group survives beside a failed group in a complete error row; current assembly cannot produce such a row after a whole group failure.

The details collision exemption can be resolved at the command's output-mode boundary without changing the input data or bare append refusal. The fresh design review should verify it against the accepted detailed carrier and then amend the spec and the exact negative test. It must not turn a name collision into an implicit overwrite.

## Small outside-in proof and file map

Use fixed loopback replies, `--no-cache --max-retries 0 --jobs 1 --batch 1` where supported, and independently pinned request bodies. Reuse [annotate partial-failure tests](../../crates/thinkthen/tests/backend/annotate/partial_failure.rs), [annotate collision test](../../crates/thinkthen/tests/backend/annotate.rs), [scheduler tests](../../crates/thinkthen/tests/backend/annotate/scheduling.rs), and [batch failure tests](../../crates/thinkthen/tests/backend/batching.rs). Each new case should assert complete stdout rows, exact stderr, exit status and listener send count, not a substring or dry-run-only absence. A useful compact table is:

1. Good JSONL row, row missing `/body`, good JSONL row under a set whose `on` is `/body`: default prints only the first row, reports the pointer and stop at record 2, exits 2, and sends exactly one request. The candidate continuation prints answer, pointer error row, answer in that order, reports one skipped record, takes the chosen distinct exit, and sends exactly two requests. Verify full request bodies and no request for the bad row.
2. A record member shadows the question name: bare mode still exits 2 before any send. With `--details`, the original member remains under `input`, the named answer is separate, stdout is one full detailed row, stderr empty, exit 0 and exactly one send. Pin the same details behavior in dry run with zero sends, if the new contract gives it that exemption.
3. Two questions sharing an `on` pointer get one reply with one valid and one failed logical answer: preserve one completed row, its failed marker, exit 6, empty stderr and one send. A lone group with no usable answer currently prints no row, exits 4 and sends once. Under continuation, pin the selected error-row rule with a later good row and exactly two sends. One two-group row with a good group and a wholly failed group distinguishes whether completed sibling answers survive; pin its exact request bodies and send count separately.
4. For a failed multi-record batch, pin the chosen rule with exact affected rows and actual sends. A status 503 after retries zero must never be represented as one isolated poison member without proof. Reuse the first-record stop and partial-reply boundaries already in `backend/batching.rs`; keep `rank`'s held-output behavior distinct from streaming stdout.

Likely files after review: `cli/args` and command help for the option; `cli/annotate.rs`, `annotate/plan.rs`, `annotate_schedule.rs` and `engine/annotate_schedule.rs` for grouped policy; `cli/asking/batched.rs`, `cli/schedule.rs` and `engine/schedule.rs` only for verbs the ticket actually admits; `cli/failure.rs` and its facts, `cli/facts.rs`, `core/result` or a narrow result carrier for the safe error row; `specification/{channels,records,annotate,result,roadmap}.md`, exact CLI tests and measured ratchet. ## Review risks

- The accepted specification explicitly refuses collisions under `--details`; the original register asks the reverse. Review that contract change instead of calling the criterion a duplicate.
- The plan's “one ticket settles four” shorthand could hide register 68's page criterion or register 43's batch isolation. The whole-batch choice affects paid attempts and cannot be inferred from the existing one-split-on-413 rule.
- A new error row must never contain backend response or evidence text in a diagnostic, and must never print a key. Name only safe user-supplied pointer syntax, record position and fixed failure metadata. A zero-send assertion needs the loopback listener count.
- The failed request may have consumed tokens that the backend did not report. Keep run facts and per-row metadata truthful. Existing partial exit 6 and a later terminal exit 4 retain their precedence until a reviewed contract changes it.
