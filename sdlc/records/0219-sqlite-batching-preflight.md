## Small proof and dependencies

The smallest new boundary case uses four distinct short warm records, fixed visit order, batch cap 2 and cache off. An unlimited-total run pins two independent packed bodies and digests; a fresh total-one run accepts either one as the sole transport arrival, exact one attempt and spent-total Usage, with no aggregate count returned by `fetchall()`. The existing 503 retry-denial case remains distinct. A compact duplicate/`NULL`/two-question table pins warm count and cache reuse; a four-argument table pins each eligible result type, literal context identity and deadline-slot validation. The table above gives the existing 256-row deadline, cancellation, replay and max-record proofs their correct batch settings or changed fixed oracle. A late error can leave prior sends/cache effects; the SQL query reports an error rather than a partial aggregate value. Do not add a test-only hook, another loopback server or a planner matrix.

Build readiness requires B12a's final source, final 0157 SQLite size source and precise runtime claims. The 0216 metadata choice and 0217 PostgreSQL source are separate; neither grants SQLite runtime support. Proposed shared docs (`databases/sqlite/README.md`, `specification/settings.md`, batching issue) merge second. Only the three claimed 0219 note files change in this design pass.

## What preparation taught us

Inspecting every SQLite registration exposed the deadline/context position that the PostgreSQL brief cannot supply. Inspecting `WarmState::step` and `settings::remaining` exposed both the prior-send effect and the invalid row-equals-attempt shortcut. The existing helper proves a failed aggregate has no returned count through `fetchall()`; it does not establish transaction rollback or prevent earlier scalar rows from being observed by a stepping host. Fresh review of `c2c5b0f4` exposed a second proof-preparation miss: retaining a test name did not preserve its expected send count under a new default. The inventory now assigns all affected warm count assertions to explicit batch `1`, unchanged distinct-group/singleton counts, or independently pinned packed bodies. These exact boundaries will make the later build comparison useful if the final B12a scheduler or 0157 setter differs.
