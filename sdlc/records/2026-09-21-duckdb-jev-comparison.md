# duckdb-jev (colliber) vs our DuckDB surface — comparison

Snapshot: `colliber/duckdb-jev` at `fad67eb` (2026-09-18, cloned by Ian today; 3 C++ sources, ~0.9k lines, plus tests and CI) against our surface at `worktrees/thinkthen-surfaces/databases/duckdb` (Rust, ~2.8k lines with tools). ## 1. Extension configuration
**Theirs:** C++ API via the official template. `Makefile:9` includes the ci-tools makefiles; `CMakeLists.txt` builds static + loadable and links OpenSSL via vcpkg (`vcpkg.json`). Pins live in CI: duckdb `v1.5.4`, ci_tools `v1.5-variegata`, `VCPKG_COMMIT 84bab45` (`.github/workflows/ci.yml`). PR gate is format only; main and tags run the twelve-platform distribution plus clang-tidy (`MainDistributionPipeline.yml`); `scripts/extension-upload.sh` is the community-S3 upload. `.gitmodules` floats duckdb on `branch=main` for local clones.
**Ours:** Rust over DuckDB's unstable C API (`Cargo.toml`: `duckdb ~1.10505.0`, `loadable-extension`, `vscalar`, `vscalar-arrow`); `Makefile` pins `TARGET_DUCKDB_VERSION=v1.5.5` with `USE_UNSTABLE_C_API=1` — the recorded version-pin trap; ci-tools vendored; `package.sh` zigbuilds at glibc 2.28, appends metadata, loads in the official `duckdb:1.5.5` container, removes it. No CI; the rung exists on the branch; signing path unchecked.
**ADOPT:** when we publish, copy their pipeline shape — pinned ci-tools refs, format-on-PR / distribution-on-main, and the upload script's metadata steps. **KEEP OURS:** the glibc-pinned artifact proven in a clean official container (their repo shows no equivalent install-and-run evidence) and our explicit version pin over their floating submodule.

## 2. API shape
**Theirs:** four scalars plus one table function — `jev_choice`→ENUM, `jev_score`→DOUBLE, `jev_noul`→DOUBLE, `jev_ask`→STRUCT, `jev_usage` (`src/jev_extension.cpp`). The criteria must be a constant literal, and the **return type is derived from it at bind** (`EnumOf`, STRUCT fields); every malformed input fails at plan time — empty map, duplicates, over 255 options, one-level rubric, NULL, non-constant criteria, missing secret (`ResolveJevSettings` throws `BinderException`). Per-row dynamic questions are impossible by design.
**Ours:** nine fixed-registration functions; the question rides as text, `'@file'`, or JSON per row; the question check runs at the first row because the stable C API's bind surface is broken (our open issue `2026-09-21-the-scalar-bind-surface-is-unusable-on-duckdbs-stable-c-api.md`); plus `details`, the warm aggregate, the recognize pair, and `relate` as a query-string table function.
**EQUIVALENT:** the usage table function, the 255 ceiling, and the fail-before-any-request property (theirs at bind, ours at first row — both cost zero requests). **ADOPT:** nothing structural; their constants-only design cannot express our per-row questions and question files. Their binder errors name the fault precisely, which ours already do inside chunks.

## 3. Performance
**Theirs:** their code states "One POST per row is the API's floor: a request carries exactly one state" (`src/jev_client.cpp`) — a second independent implementation **corroborating our one-state ceiling issue**. Per-chunk thread pool capped at 16, calling thread included (`jev_extension.cpp:280,337`); no process-wide cap, and the comment admits chunks on several threads. A **new httplib client per POST** (`jev_client.cpp:138`) — a fresh connect and TLS handshake per request, no reuse. Timeouts 10 s connect / 30 s read; follows redirects. Cache: process-wide mutex map keyed endpoint+body, cleared wholesale at 100k entries (`:22,:80`). Retries: 4 attempts, 200 ms doubling, only 429/5xx/transport; no Retry-After. Functions marked VOLATILE so DuckDB folds nothing (`jev_extension.cpp:465`). Usage counts requests, cache hits, **and both token counts** from every reply.
**Ours:** each chunk's distinct (question, text) pairs group and go through the batch door into the process-wide gate (`src/lib.rs`, `distinct_of`/`judged_rows` → up to 32 in flight; measured 33 pooled connections per 1,000 requests); retries honor Retry-After and split retryable from final; deadline and cancel token, with the SIGINT chain measured (0.11 s stop, wire frozen); cache at the engine (memory now, XDG disk planned); usage counts requests and cache answers — tokens are the recorded gap.
**ADOPT:** the token counters — our vendor returns the same usage block, and their tolerant four-counter parse is the shape to copy. **KEEP OURS:** connection reuse (they pay a handshake per request), the process gate (our 207 measured exactly their exposure class: 85-wide on 101 connections), Retry-After honoring, and the cancel/deadline path they do not carry. **EQUIVALENT:** per-chunk concurrency, ours through the batch door and theirs at 16 — ours stays bounded process-wide, the ruled stance.

## 4. Security
**Theirs:** DuckDB's SecretManager — `CREATE SECRET (TYPE jev, API_KEY ...)` with `redact_keys` on the key (`src/jev_secret.cpp:21`), so it is redacted from `duckdb_secrets()` output and never enters SQL text or logs; a missing secret fails at bind (`:39`). Their mock asserts the Authorization header on the wire. Risks: `client.set_follow_location(true)` with a bearer header on every request (`jev_client.cpp:141`) — whether httplib re-sends Authorization across redirects is **unverified here** (the submodule vendoring httplib is absent) — and errors embed the full response body.
**Ours:** the key never touches the surface; the engine reads it from its own settings. The recorded gap is exactly what they solved: the stable C API registers no secret type, and our PostgreSQL channel's reload-log leak is on record. No redirects — the engine's client policy.
**ADOPT:** the secret-manager model as the target for our key story — secret type, redaction, plan-time absence failure — pending the C++-API-or-upstream decision already tracked in the scalar-bind issue. **KEEP OURS:** the no-redirect policy.

## 5. Testing
**Theirs:** sqllogictests for bind behavior with no network, using `DESCRIBE` to prove return types (`test/sql/jev.test`); a 430-line mock over stdlib http.server with fail-on-demand knobs — `FAIL_FIRST`, `ALWAYS_FAIL`, `DROP_NEXT`, `DELAY` — covering one-POST-per-row, WHERE+SELECT cache dedupe, concurrent chunk rows, 429 backoff, dropped-connection retry, 400 no-retry, `on_error`, one-request `jev_ask`, and usage tokens (`test/python/test_http.py`); a pure-SQL live suite skipped without a key, with the empty-variable guard (`Makefile` `test_live`); everything wired into CI.
**Ours:** the 17-check null suite, the 102-check conformance driver (replay, per-case offsets, the join-sends-no-request proof), the wire suite against the stub with counter assertions, the slide extracted and run as drawn, and the defect-mapping unit test; no failure injection at the wire seam; no CI, but the rung is on the branch.
**ADOPT:** failure injection at the wire seam for retry, backoff, and on-error paths (our retry semantics are proven at the engine, not through SQL); sqllogictest as the portable public-repo format, including its `DESCRIBE` type assertions; the live contract-not-numbers suite shape. **KEEP OURS:** the replay conformance file and the cross-surface matrix — their suite has no cross-surface story.

## 6. Hygiene
**Theirs:** clean layout and real-output demo tooling (`docs/capture.py` … `togif.sh` record the GIF from live queries). Lapses: `LICENSE` is the template's MIT text with "Stichting DuckDB Foundation" as the copyright holder (unchanged template); `test/README.md` is untouched boilerplate still mentioning "the quack extension"; `.gitmodules` floats duckdb on main; no running-notes equivalent.
**Ours:** NOTES.md and README are thorough; ci-tools is vendored with a dangling `.git` pointer, documented and resolved from the review; no LICENSE file inside the surface folder (the root repo has one; `Cargo.toml` says MIT).
**KEEP OURS:** the notes discipline and the exact documentation of divergences. **EQUIVALENT:** size and structure otherwise.

## Five most valuable learnings
1. **The secret manager is the working model for our key story** — redaction, plan-time failure, per-connection settings (`jev_secret.cpp`). It is the concrete motivation for the scalar-bind issue; put it in front of the build team.
2. **Token counters from the reply's usage block** — data we already receive, a gap we already recorded; copy their tolerant four-counter parse.
3. **Failure injection at the wire seam** — their mock's knobs exercise retry paths through SQL, which our fixed stub cannot.
4. **Their distribution machinery** — the community-repo path to copy at publication time, with pinned refs and the upload script.
5. **Confirmations with teeth** — their code independently states the one-state-per-request floor (corroborating the ceiling issue), and our pooled connections, process-wide gate, and no-redirect policy each close a cost or risk their implementation pays.

**Unchecked:** their duckdb submodule (httplib source) not initialized; nothing built or run on either side; the redirect-header question is code-evidence only; their live suite not run.
