`catch_unwind` invokes the hook before it returns. The existing C/SQLite/old DuckDB guard messages independently copy payloads. Fix both channels. Host hook state is process-global within a Rust runtime; a once-installed wrapper can delegate for unrelated threads, but a later host `set_hook` or concurrent registration can replace or race it. A per-call `take_hook`/`set_hook` would interfere with other host threads and is rejected. Preserve nesting depth through unwind and payload disposal; install before owned work begins, not after a first panic. The hook also holds an instruction pointer into its binding: SQLite's current `ffi.rs::pin` runs only after registration, so a failed load can leave a newly installed hook pointing into an unloadable extension. Move a fallible pin before hook installation. The C door ships both static and dynamic libraries but has no dynamic self-retain; a host `dlclose` after installing its hook could unload that code. Require a verified process-lifetime self-reference for the dynamic form, while the static form resides in the host image. Pinned DuckDB v1.5.5 `extension_load.cpp:531` uses `dlopen` for old C API packages and has no `dlclose` call in that source tree; validate this lifetime on each actual packaged host. Current C has no Rust callback from the host; SQLite polls a C interrupt predicate; the old DuckDB worker polls its own atomic SIGINT predicate. A new host callback must be reviewed before extending a marked region across it. C++ exceptions stay on the C++ side.

## Small proof and bounded other-binding scan

Use the existing `public/options.rs` selected child-test pattern. Set a prior hook inside the child and write a distinct harmless host marker through it. Trigger one synthetic string panic in each affected binding's own guard; for SQLite and old DuckDB, also trigger one on its binding worker thread. Assert fixed Defect, false retryability, exact returned error without the synthetic secret marker, and a later success. The parent captures both streams and asserts the synthetic marker absent, while an unrelated thread's host marker reached the prior hook. Add a bounded dynamic-C load/release witness and SQLite success/failed-load pin witness; a callback-only marker test cannot establish that a global hook's code remains mapped. No production fault switch, repeated campaign or network request is needed. Existing C, SQLite and old DuckDB payload-copy assertions must be replaced by this stronger boundary proof rather than retained as stale expectations. A separate normal installed smoke case checks each available packaged artifact without pretending ordinary input can force the panic.

A bounded scan of other binding guards found R `thinkthen/src/rust/src/calls.rs::on_worker` still uses `words(&*panic)` in a returned defect and lacks local hook suppression. Python `src/lib.rs::caught`, Ruby `src/lib.rs::guarded`, and TypeScript `src/door.rs::guarded` return fixed messages but do not locally mask a default hook before catch; their current tests do not establish stderr secrecy. These paths need explicit follow-on routing and evidence before an all-bindings claim. They do not justify silently widening 0226's three named issue rows.

## Preparation lesson and refresh trigger

The 2026-09-27 issue predates the landed Linux C++ package, so its DuckDB row must be read as the retained C API route. Tracing only callback guards would miss the detached old DuckDB worker and SQLite's separate load entry; the pinned rusqlite helper confirms the latter has no catch. Tracing only returned error text would miss the pre-catch process hook. Tracing only call return would miss the hook's lifetime after a failed load or `dlclose`. Before implementation, refresh main ancestry, exact file claims and package targets; after High review, compare the built child and package evidence with this inventory. Preparation helped only if it prevents a second payload route, dangling hook or false Linux-C++ proof for old packages.
