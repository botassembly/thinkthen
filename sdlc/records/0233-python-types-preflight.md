## Settled contracts and routine choices

ADR 0082 and the [type-contract issue](../issues/closed/2026-09-27-one-type-contract-for-every-surface.md) approve Enum/Literal, per-label override precedence and unknown-label usage error, typed rows/kinds, and the optional Pydantic extra. J1 `0204` owns the shared schema; J2 `0209` owns stable frame columns; 0214 owns facts/receipt and direct Call migration. None duplicates J5. `specification/question-file.md` accepts ordered list or map labels and string/object/list/null descriptions; `{what, not_for, examples}` is a conventional object, not a new mandatory Python schema. `score` remains numeric. A `failed` marker is distinct from null.

The proposed routine choice is a string Enum value when present, otherwise the member name, in canonical iteration order. It supports ordinary Enum and string Enum while never stringifying an integer into a label. Member `description` precedes a distinct member docstring, and an inherited enum/class docstring is ignored. A single new `descriptions=` mapping replaces just the named default; unknown names fail before worker start. Direct `Literal[...]` arguments preserve the spelling and order still visible to `typing.get_args()`. Python canonicalizes `Literal["a", "a"]` to one argument before runtime inspection, so reject only duplicates that remain observable, never promise to detect erased source repetition or inspect source text. A collapsed one-label choose set must reach the native label-count refusal. Enum aliases remain observable through `__members__` and must be refused separately. Do not accept a nested union whose argument order can be changed by typing caches; [Python's typing documentation](https://docs.python.org/3/library/typing.html) warns that `get_args()` order may differ for nested Literal or union forms. [Python's Enum reference](https://docs.python.org/3/library/enum.html) confirms canonical iteration order and alias behavior. A list/map remains unchanged, and equivalent lowerings must produce identical request bytes/digests. The design reviewer should inspect the string-value/name fallback, alias refusal and `descriptions=` spelling as public API choices within the accepted outcome.

The recognize keyword route needs its own existing JSON bridge, rather than the question-file bridge used by `question`. `Engine.recognize` currently turns a `kinds` mapping or list into `(name, meaning)` pairs and `_rules(relations, either)` turns an ordered relation map/list into `(name, source, target, either)` tuples; its module function delegates these same keywords. `_Recognize._build` in `src/asked.rs` accepts only `Option<String>` meanings and calls `Description::text`, so structured Enum or override meanings would be lost. `_Recognize._from_json` already calls `Recognize::from_json`; `core/recognize_file.rs` accepts the closed version-one `recognize.kinds` object and applies `Description::of_json` to string/object/list/null values. Lower keyword kinds to that ordered object and keyword rules to `recognize.relations` entries with `name`, `source`, `target` and `either`; the parser supplies default `reads`, `0.5` cuts, `ENTITY` for no kinds, and wildcard normalization. Keep supplied `ask=` dict/file on `_spec`, omit absent threshold keys, preserve `on=` as the Python frame-column selector with the current no-relations guard, and leave `relate` on its separate builder. Pin request identity against equivalent version-one `ask` objects for existing list/map/relations/default forms and structured kinds; do not create another Rust parser or widen the narrow `_build`.

Pydantic v2 exposes `model_fields` as ordered field definitions with `FieldInfo.description`; [official field documentation](https://pydantic.dev/docs/validation/latest/concepts/fields/) also covers `Annotated[..., Field(...)]`. Its [dynamic-model documentation](https://pydantic.dev/docs/validation/latest/concepts/models/#dynamic-model-creation) documents `create_model` and notes that a single annotated field definition is supported from v2.11. Therefore the proposed extra is `pydantic>=2.11,<3`, with one exact tested v2 pin plus hashes for the optional development proof. No Pydantic import occurs on ordinary `import thinkthen`; a Pydantic-only form triggers the lazy adapter. Label model fields supply names/descriptions. Question-set model fields supply kind from type and question text from `Field.description`; `json_schema_extra` carries only existing question-file keys, then the native parser validates the lowered set. For a direct annotated Literal, one Field description applies to each member because the question grammar has no set-level description. A tuple of annotated singleton Literals supplies per-member meanings. `row_model` uses strict `create_model` fields; it validates existing dict rows without changing `Call.value`.

## Design review corrections

Fresh review of proposed `b7262133` caught two observable-contract mistakes before implementation. The recognition keyword constructor is text-only even though the existing version-one JSON constructor supports structured descriptions; the ticket now specifies that reused parser and captured equivalence for old and new keyword forms. Python erases repeated equal Literal arguments before `get_args()`, so the ticket promises only observable duplicate refusal and native label-count validation for a collapsed one-label choose set. These are preparation learnings; no product implementation or build was performed.
