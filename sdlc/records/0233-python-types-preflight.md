## Settled contracts and routine choices

ADR 0082 and the [type-contract issue](../issues/2026-09-27-one-type-contract-for-every-surface.md) approve Enum/Literal, per-label override precedence and unknown-label usage error, typed rows/kinds, and the optional Pydantic extra. J1 `0204` owns the shared schema; J2 `0209` owns stable frame columns; 0214 owns facts/receipt and direct Call migration. None duplicates J5. `specification/question-file.md` accepts ordered list or map labels and string/object/list/null descriptions; `{what, not_for, examples}` is a conventional object, not a new mandatory Python schema. `score` remains numeric. A `failed` marker is distinct from null.

The proposed routine choice is a string Enum value when present, otherwise the member name, in canonical iteration order. It supports ordinary Enum and string Enum while never stringifying an integer into a label. Member `description` precedes a distinct member docstring, and an inherited enum/class docstring is ignored. A single new `descriptions=` mapping replaces just the named default; unknown names fail before worker start. Direct `Literal[...]` arguments preserve the caller's spelling and order. Do not accept a nested union whose argument order can be changed by typing caches; [Python's typing documentation](https://docs.python.org/3/library/typing.html) warns that `get_args()` order may differ for nested Literal or union forms. [Python's Enum reference](https://docs.python.org/3/library/enum.html) confirms canonical iteration order and alias behavior. A list/map remains unchanged, and equivalent lowerings must produce identical request bytes/digests. The design reviewer should inspect the string-value/name fallback, alias refusal and `descriptions=` spelling as public API choices within the accepted outcome.

Pydantic v2 exposes `model_fields` as ordered field definitions with `FieldInfo.description`; [official field documentation](https://pydantic.dev/docs/validation/latest/concepts/fields/) also covers `Annotated[..., Field(...)]`. Its [dynamic-model documentation](https://pydantic.dev/docs/validation/latest/concepts/models/#dynamic-model-creation) documents `create_model` and notes that a single annotated field definition is supported from v2.11. Therefore the proposed extra is `pydantic>=2.11,<3`, with one exact tested v2 pin plus hashes for the optional development proof. No Pydantic import occurs on ordinary `import thinkthen`; a Pydantic-only form triggers the lazy adapter. Label model fields supply names/descriptions. Question-set model fields supply kind from type and question text from `Field.description`; `json_schema_extra` carries only existing question-file keys, then the native parser validates the lowered set. For a direct annotated Literal, one Field description applies to each member because the question grammar has no set-level description. A tuple of annotated singleton Literals supplies per-member meanings. `row_model` uses strict `create_model` fields; it validates existing dict rows without changing `Call.value`.

## Focused proof and review risks

- Reuse the existing offline child/listener helpers in `tests/conftest.py` and `tests/test_call.py`. A single table compares captured request bodies and digests for equivalent list/map/Enum/Literal forms, then one described Enum/map pair and one explicit one-label override. Verify observed send count zero for an unknown override. Check one engine route, module delegate and many route rather than multiplying fixtures.
- Reuse existing partial `annotate` and frame cases to pin `bool`, chosen label, numeric score, tag list, `None`, the exact `{"failed":{"kind":"backend","cause":...}}` marker, and the separate typed frame column. The existing 0214 listener already pins suppressed-output accounting, receipt failure identity and singleton batch-one bytes; retain it instead of duplicating that proof.
- Add one optional installed case for `BaseModel.model_fields`, one `Annotated[..., Field]` route and `row_model(...).model_validate` on answered/unresolved/failed data, plus a plain installed import with Pydantic absent. The tests must actually run, not count a skipped optional case as green. Pin development-only `mypy` with hashes and run one `tests/type_contract.py` fixture under the Python check rung; a runtime `assert_type` alone would not prove stub behavior. The design reviewer should inspect the new checker pin and its run from `check.sh` before implementation claims.

No test-only native hook is justified.
