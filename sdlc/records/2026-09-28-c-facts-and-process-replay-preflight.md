# Typed C facts and process replay preflight

Source pin: main `e8789b76`. This is a notes-only refresh of the original every-surface-facts issue, ADR 0089, ticket 0230, register 103 in local experiment 284, and the accepted 0148 replay settings. It makes no new API decision or issue closure. No build, provider call or new measurement was run.

## Typed C calls: facts already captured, then lost on success

The original issue requires facts on every library call without a second asking call. `0230` completed the JSON door: successful `thinkthen_call[_opts]` returns `{"value":...,"facts":...}`; a started failure may be read through borrowed `thinkthen_error_facts_json` on the same calling thread and engine. `{"usage":true}` is a process counter, not that call's facts. `Call<T>` and final `Batch::facts()` from ADR 0089 are the reusable Rust carriers. Cost at a user-provided price, provider timing and request ID remain distinct open criteria; this preflight invents none of them.

| Exported C family | Current successful path | Facts fate and retained boundary |
| --- | --- | --- |
| `thinkthen_decide` and `_opts` | The plain macro forwards to `_opts`; `ffi.rs::typed` calls `door.rs::decide`, which invokes `Engine::details_with` and immediately takes `into_value()`. The writer fills the fixed `thinkthen_answer` outcome and probability. | The returned `Call` facts are dropped. The existing two-field answer struct and success/error code are retained. |
| `thinkthen_decide_many` and `_opts` | The plain macro forwards; `door.rs::decide_many` consumes the `Batch` into `Vec<Reply>` in input order; `ffi.rs` copies rows to the caller's array after all rows succeed. | Final `Batch::facts()` is never read. The no-partial-output rule and caller-owned array remain. Default packing means rows are not transport attempts. |
| `thinkthen_recognize` and `_opts` | The plain macro forwards; `door.rs::recognize` returns `(JSON, Facts)` from `recognize_with`; `ffi.rs` hands the JSON to the caller. | The writer explicitly discards `_facts`. The returned string is owned and freed through `thinkthen_free_string`; its existing JSON shape has no facts. |
| `thinkthen_relate` and `_opts` | The plain macro forwards; `door.rs::relate` returns `(JSON, Facts)` from `relate_with`; `ffi.rs` hands the JSON to the caller. | The writer explicitly discards `_facts`. The same owned-string and no-partial-output rules remain. |

All eight names have a working failure route through `ffi.rs::typed` and `Held::settle`. A started Rust error becomes a `Failure` with frozen facts; `failures.rs` keeps its CString in an engine/thread slot until that thread records another failure or frees the engine. An argument refusal before a call starts has no facts. The success paths neither stash facts nor give a borrowed success-facts pointer. A subsequent `thinkthen_call` or `usage` query would be a different call or process total and cannot reconstruct the typed call under concurrency. Current `libraries/c/examples/functions.c` and the retained experimental Zig C-ABI consumer under experiment 273 call typed symbols, so a JSON-door-only answer would require caller migrations rather than transparently satisfy them.

**Unmatched criterion and choice for review.** Ian's original outcome says “library results carry facts on every call, with no setting and no second call.” The typed C success results remain bare. ADR 0089 rejected leaving old bare Rust methods beside opt-in fact methods; it did not decide how to evolve the stable C ABI. Extending `thinkthen_answer` or changing existing exported signatures would break compiled callers. One additive route gives new suffixed typed exports a caller-owned JSON facts output in the same asking call. It preserves the old ABI and yields immutable per-call bytes, but leaves the old eight names as a literal exception unless the owner accepts a compatibility interpretation. Another route adds a borrowed success-facts accessor after each old typed call. It makes no second asking or provider call, yet it is a second C function call and an engine/thread “last result” slot rather than facts owned by the returned result. That slot would need clear until-next-operation lifetime rules and must clear or replace stale success facts on a new failed or pre-start call; it must not disturb `thinkthen_error_facts_json`'s existing until-next-failure promise. A caller-owned output parameter on the current exports and a larger answer struct both break the existing ABI. The accepted 0230 JSON door already gives callers facts in one call, but its use does not prove the typed exports meet the criterion. Recommend a bounded design review compare the owned-output route with the accessor and explicitly rule on the legacy exception; this preflight does not choose an API or mark the criterion done. Exact prospective source claim: `libraries/c/include/thinkthen.h`, `libraries/c/src/{ffi,door,failures}.rs`, the nearest private FFI child if needed, `libraries/c/tests/c/{opts,threads,driver}.c`, and C installed driver registration. Keep the existing six error codes, pointer ownership and no-partial-output rule.

The smallest outside-in proof uses the existing installed C header and loopback driver. Exercise each of the four plain and four `_opts` paths against fixed replies, including batch one for a three-record `decide_many` request-count assertion. Compare one call's facts with actual listener arrivals and reported usage; an omitted usage field stays absent. Exercise a started error and a pre-call Usage refusal, two threads on one engine, a later success on the same thread, and string disposal or copied facts ownership. For an accessor option, also prove a failed and a pre-start call cannot expose stale success facts. Preserve the already-passing `opts.c` plain/options parity, `threads.c` failure-slot isolation, header/exported-symbol check and 0230 JSON-door wrapper proof. Captured requests and complete call facts are stronger evidence than a header or inventory citation alone. The accepted 0230 C installed proof establishes the JSON door, not these typed success facts. `specification/settings.md`'s C run-facts cell still describes an older state and needs a separately claimed page correction when the C boundary is decided.

## Register 103: one process policy, distinct from per-engine replay

The original local `284-issue-register/103-no-process-wide-strict-replay.md` re-triaged this to low-priority severity 4 after review severity 3. Its exact success criterion is one environment variable that makes a whole embedded process strictly offline, with a loud live-send refusal naming the call site. `0148` supplies an explicit replay folder to `EngineBuilder` and host constructors. The SQL replay remainder is tracked under its own settings row. `public/settings.rs::EngineBuilder::from_env` reads cache, URL, key, certificate, batch and request-size variables, but no replay variable. `Engine::builder()` starts from `new()`, so adding a default only to `from_env` would leave that public path outside the process policy. C `settings.rs::build`, SQLite `settings.rs`, PostgreSQL `call.rs`, and DuckDB `engines.rs` use `from_env` before their own settings; default Rust engines and host module engines are constructed lazily. No current `THINKTHEN_REPLAY` variable appears in product source or the settings table.

**Bounded design choices.** The smallest credible process force is a replay-folder environment value captured at `EngineBuilder::build` for every newly built engine, including `Engine::builder()` and `from_env` paths. A process guard checked only by host wrappers would miss native and direct Rust callers. A read on every send would react to mid-run environment mutation but creates a process-global race and can change behavior during one call; do not infer that requirement from the original criterion. State that the variable must be set before engine construction, that an already-built or lazily cached default engine keeps its construction snapshot, and what a child after `fork` inherits. The existing `storage()` rules refuse mismatched record/replay folders and preserve the selected folder's safe marker/read policy. Because this variable is a *force* policy, decide whether it overrides or refuses conflicting explicit cache, record and replay settings. Ordinary `settings.md` precedence puts typed settings above environment, so an exception requires a reviewed row; merely treating the new variable as a lower-priority default would not satisfy “whole process offline.” Recommend fail-closed refusal for conflicting explicit folders before any send, while matching replay and unrelated model/deadline settings remain usable. Choose safe fixed error wording that names the host operation or verb as the call site; the core cannot know a Python stack frame or SQL query text, and errors must not echo paths, keys or evidence. No new public call stack is required.

The smallest boundary table runs with an isolated environment and two construction paths: `Engine::builder()` with explicit cache, and a C or SQL constructor that starts from `from_env`. Supply one pinned recorded hit and one absent digest under the forced folder; assert the hit's saved answer, Local replay miss, named operation, zero listener arrivals, and unchanged fixture bytes. Then check a conflicting explicit record/replay folder refuses before a send, with the existing no-key path unable to escape the force. Use the existing 0148 strict hit/miss, marker and host settings cases as retained proof; count actual transport starts, not logical rows. A selected loaded-host case is needed before claiming coverage for that host or package. Tests should set the environment before construction and restore it without sharing mutable process environment across parallel cases. This is preparation for a settings/API review, not implementation or a completed process-wide guarantee.

## What this refresh learned

The last C operation's process counters, a failure-only thread slot and a successful call's immutable `Facts` are different carriers. A source call to `into_value()` or a tuple pattern that ignores `_facts` can erase an otherwise complete report at an FFI boundary. A replay folder on one engine does not force another engine offline. The 284 criterion includes a call-site diagnostic and a precedence decision, so proving one `from_env` miss alone would be incomplete. This refresh claims no additional completed issue or reviewed ticket.
