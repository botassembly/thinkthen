The [open issue](../issues/2026-09-29-systemone-adapter-sends-null-criteria-liquid-d1-refuses.md) came from experiment 413, whose available `RESULTS.md` says `thinkthen check` at source `2c5ac772b` made four requests and Liquid `d1:free` returned status 422 for `questions.q1.criteria.false`. ## Diagnosis and decision

The filing overstates the **missing-side** case. In `crates/thinkthen/src/core/adapters/systemone/request.rs`, `NoulCriteria.yes/no` already skip `Option::None`, and `RequestQuestion::asking` emits `criteria` only when at least one side is present. A CLI `--true` without `--false` therefore has no null-false member. The failing fixed `check` probe in `crates/thinkthen/src/core/check.rs` explicitly parses `"false":null`. `question_file/fields.rs::meaning` keeps that as `Some(Meaning(Json::Null))`; the serializer writes the present null. The same construction at experiment commit `2c5ac772b` matches current source. `specification/question-file.md` deliberately treats explicit null as a present input, and `specification/backends.md` currently promises to send it. This is a real conflict with the reported Liquid schema, not a regression from an absent-side encoder.

Recommend the bounded wire revision in [0301](../tickets/0301-noul-criteria-compatibility.md): omit a `noul` side whose description is `Json::Null`, and omit the whole `criteria` object when neither side has a non-null description. Preserve the internal question, explicit-null input acceptance and canonical digest; this avoids equating a null file key with an absent file key. A null description supplies no positive or negative meaning, but equivalence of old and new hosted answers is **not measured**. Choice null means an option still exists and must retain its key; score null already becomes `{}` in its ordered array. The issue's broader phrase “omit null criteria entries” must not be applied to those shapes.

## Exact proof and identity effects

The affected checked-in exact bytes are `specification/fixtures/check/requests.jsonl` row 1, `specification/check.md`'s first request and probe table, `spec/decide.md`'s structured-null dry run, `crates/thinkthen/src/core/adapters/systemone/request.rs`'s structured assertion, and `crates/thinkthen/tests/question_file/structured.rs`. `spec/check.md` and `crates/thinkthen/tests/backend/check.rs` compare emitted check bodies to the fixture; keep those routes. The latter already has `Listener::serving` and `Listener::requests()` for a captured live body. The other three check bodies remain identical. The shared `conformance/cases.json` has no exchanged `noul` request with a null criterion at this pin; its two-sided decide case 05 and existing choice/score null cases remain useful unchanged. The question-file corpus may still parse explicit null and needs no grammar rewrite. A local exact-body/listener test proves construction and send count; it cannot establish Liquid acceptance. Use one mirror for false-only, no-criteria and both-described as a small edge table, not a new field-by-surface matrix.

`core/digest.rs` hashes the canonical `Question`, so unchanged parsed values keep `meta.question_sha256` and `meta.questions_sha256`. `core/recording.rs::Exchange::digest` hashes adapter name, URL and **exact request bytes**. Only affected null-criterion requests therefore get new cache keys and `meta.requests` values. Old strict replay or default-cache lookup of such a question can miss even while the old entry remains readable; there is no evidence for a fallback or for rewriting captured recordings. `check` itself uses no cache or recording. Existing captured no-criteria and both-described receipts keep their input identity; they do not prove the new omitted-null request. The experiment's 422 is retained reported evidence, while a reviewed, authorized hosted check after implementation remains necessary for the issue's remote done condition.
