## Diagnosis and decision

The filing overstates the **missing-side** case. In `crates/thinkthen/src/core/adapters/systemone/request.rs`, `NoulCriteria.yes/no` already skip `Option::None`, and `RequestQuestion::asking` emits `criteria` only when at least one side is present. A CLI `--true` without `--false` therefore has no null-false member. The failing fixed `check` probe in `crates/thinkthen/src/core/check.rs` explicitly parses `"false":null`. `question_file/fields.rs::meaning` keeps that as `Some(Meaning(Json::Null))`; the serializer writes the present null. The same construction at experiment commit `2c5ac772b` matches current source. `specification/question-file.md` deliberately treats explicit null as a present input, and `specification/backends.md` currently promises to send it. This is a real conflict with the reported Liquid schema, not a regression from an absent-side encoder.

Recommend the bounded wire revision in [0301](../tickets/0301-noul-criteria-compatibility.md) and accepted [ADR 0110](../planning/adr/0110-noul-null-criteria-wire-omission.md): omit a `noul` side whose description is `Json::Null`, and omit the whole `criteria` object when neither side has a non-null description. Preserve the internal question, explicit-null input acceptance and canonical digest; this avoids equating a null file key with an absent file key. A null description supplies no positive or negative meaning under the proposed wire rule, but equivalence of old and new hosted answers is **not measured**. Choice null means an option still exists and must retain its key; score null already becomes `{}` in its ordered array. The issue's broader phrase “omit null criteria entries” must not be applied to those shapes. `specification/README.md` requires an ADR to change these Settled wire sections; Fresh High review accepted the corrected design at `46925b681`, and the coordinator approves ADR 0110.

Keep the input assertion and update the body and digest together. `libraries/typescript/tests/verbs.test.mjs:219,240–241` keeps `true:null` and a structured false description, then currently expects the true wire member to be null; change only that member expectation while retaining the false object and its choice/score null checks. A read-only search across `libraries/` found no other serialized-noul-null expectation; PHP/Go accepted-request null entries are `choice` and stay. The shared `conformance/cases.json` has no exchanged `noul` request with a null criterion at this pin; its two-sided decide case 05 and choice/score null cases remain useful unchanged. The question-file corpus may still parse explicit null and needs no grammar rewrite. A local exact-body/listener test proves construction and send count; it cannot establish Liquid acceptance. Use one mirror for false-only, no-criteria and both-described as a small edge table, not a new field-by-surface matrix.

`core/digest.rs` hashes the canonical `Question`, so unchanged parsed values keep `meta.question_sha256` and `meta.questions_sha256`. An explicit-null and an absent-side question can have distinct canonical digests. `core/recording.rs::Exchange::digest` instead hashes adapter name, URL and **exact request bytes**. The new explicit-null body changes its old cache key and `meta.requests` value. At one URL, model, evidence and otherwise identical question, it can become byte-identical to the previously absent-side body and use that existing cache/recording entry. This is the current exchange contract, not a claim of provider-answer equivalence. Old strict replay may therefore miss its old null-body entry **or hit** an existing absent-side entry; the old captured file remains readable, and neither fallback nor rewriting is justified. A small core identity regression should assert distinct canonical question digests and the same final wire and exchange digest for that pair. `check` itself uses no cache or recording. Existing captured no-criteria and both-described receipts keep their input identity; they do not prove the new omitted-null request. The experiment's 422 is retained reported evidence, while a reviewed, authorized hosted check after implementation remains necessary for the issue's remote done condition.
