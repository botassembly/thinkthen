# 0260 design: portable content-batch identity

Status: accepted by fresh read-only design review of `f68d9496`; the coordinator approved the retained contract and claimed the first proof slice at main `94bdf96d`. This records a proof plan, not a closed register item. Ian may overturn the record-spelling and proof scope. ADR 0048 already fixes the cut and exact-request cache rule; this design does not amend them.

## Identity rule and supported domains

The selected **value** that reaches `core::BatchRecord` is serialized as one compact JSON value with no trailing newline. Hash its UTF-8 bytes with SHA-256. Read the first eight hash bytes as an unsigned big-endian integer; a remainder of zero modulo 4,096 closes the current batch **after** that member. This is the source path in `core/batch/questions.rs::push_slice` through `core/render.rs::json_line`, using pinned `serde_json` 1.0.151. Duplicate detection also keys the record's serialized value and complete question. Profile/size/member caps, explicit batch size, input end, and a live CLI pause may close a batch for separate reasons. A controlled fixture therefore fixes Max, one question, model, address and limits, sends a complete finite input without a pause, and disables cache/retry.

For this contract, compact spelling means JSON punctuation without insignificant spaces; JSON escapes for quote, backslash and control characters; ordinary valid non-ASCII characters in UTF-8, including `é`, rather than an optional `\u` spelling; arrays in element order; objects in received member order including nested objects. JSONL selected structured values keep the core's parsed number kind: integer `1` and floating `1.0` remain distinct, as does finite `-0.0`. The parser converts finite exponents to its floating representation, then the current serializer gives its shortest round-tripping spelling, which can include `e+20`; the fixture pins examples rather than promising preservation of arbitrary numeric source lexemes. Whitespace around parsed JSON tokens is not retained. Invalid/duplicate-member and nonfinite inputs keep current refusals. Text entrypoints turn text into a JSON string first; a literal text `{"n":1}` is a string value, not a structured object.

The command's JSONL/pointer route can select structured values. CLI lines, CSV/TSV cells, public Rust, C, Python/Polars, TypeScript, R and SQL bulk routes supply text strings to the same Rust batcher. Ruby accepts other Ruby values but `JSON.generate` converts them to text before the native Rust route. Do not infer structured-value parity from that Ruby convenience or widen another host's domain. The 11 C-door packages (PHP, C#, JVM's Java/Kotlin/Scala, Dart, Swift, Zig, Go, C++, Ada, GNU Objective-C and COBOL) route through the C library; Java/Kotlin/Scala share one package but remain separate language callers. A shared C corpus validates the native core path once. Each wrapper still needs a real public entrypoint call with the five Unicode texts in order and Max selected; its counted listener and returned request identities must match the three fixed bodies/digests, so host re-encoding or truncation cannot pass unnoticed. The wrapper may read the one C corpus rather than copy its literal bodies. Existing installed package and platform checks retain their separate ownership.

The request digest remains SHA-256 over `systemone`, LF, resolved URL including `/systemone`, LF, and the **actual** request body bytes (`core/recording.rs::Exchange`). It is not a digest of record bytes alone. A changed member can move a content cut and thereby change bodies and cache entries on the whole affected stretch. Preserve existing singleton body bytes and cache/replay lookup. The record rule belongs beside batching in `specification/records.md`; link it from `specification/fixtures/batching/README.md`. `question-file.md`'s question canonical form is a distinct identity and its float rule must not be copied over the record's integer/float distinction.

## Literal shared corpus

Use `alpha`, `café-5544`, `omega`, `line 2907`, `tail` in that order. Independently calculated compact record byte spellings are `"alpha"`, `"café-5544"`, `"omega"`, `"line 2907"`, `"tail"` without newline; the second contains literal UTF-8 `c3 a9`. Their first eight SHA-256 bytes in hex are `902cf2b465fb0762`, `3db0138d194cf000`, `00b22856036ff398`, `ee04192375591000`, `0c3f5e9d2376aedc`. The second and fourth heads end in `000`, yielding `[1,2]` content, `[3,4]` content, `[5]` end. An escaped `"caf\u00e9-5544"` instead has head `72afc19814d82dd9` and moves the first cut, so the corpus distinguishes spelling from digest-only parity. The preflight records the narrow observation from the checked-out command. The implementation must confirm every literal against the newly built core before accepting the fixture.

Store the five input texts and literal per-record expected UTF-8 bytes/heads/cut flags in one batching fixture. Store three complete exact System One request bodies as raw UTF-8 fixtures, with separately calculated full lowercase digest strings for one fixed canonical URL. The runner may substitute only the listener's actual URL in the digest prefix, then hash the **fixed fixture body**, while separately comparing the listener's actual bytes to that fixture. Do not derive expected bytes from the production encoder, parse-and-reserialize a captured body, or compute both expected and observed digests from the same capture. Assert the five logical rows, group membership and close reasons before comparing three sends; compare detail `meta.requests` and, where exposed, batch metadata against the three independently fixed digests. The listener counts attempted sends, including any unexpected ones. Preserve the existing `grouping.txt`, singleton fixture and case corpus instead of copying them into a new framework.

Run a separate CLI JSONL arm with an ordered nested object, non-ASCII text, a quotation/backslash/control escape, integer and float variants, negative zero and an exponent. Pin its literal compact selected bytes and the resulting cut decisions; choose at least one numeric pair whose cut changes only after verifying the actual core encoding. Keep this arm out of text-only host parity. Do not let a pretty-printed input fixture stand in for the selected value after parse.

## Incremental proof and closure

The first slice is the compiled CLI over complete `--lines` input and the compiled C door over a JSON array of the same five strings. These are distinct host encodings and real entrypoints into the shared batcher. Use the existing CLI backend listener and C driver/conformance backend to capture exact bodies and count sends, with fixed Max/no-context/no-cache/retry settings. The fixture's URL is a fixed reference for its committed digest; the listener's ephemeral port changes the digest prefix only. A single CLI dry run shows only the first batch and is corroboration, not completion proof.

Then consume the same five-text corpus through public Rust, Python and its frame/column adapter, TypeScript, Ruby, R, SQLite, PostgreSQL, DuckDB and every wrapper exposed through C. Each runner needs an invocation from its existing check route and assertions for its supported call shape: ordered five-row acceptance, three actual sends and the same literal bodies/digests at its listener URL. A wrapper may reuse the C corpus for body and cut expectations when its public forwarding test proves exactly the string list, settings, three counted requests and returned digest identities that the C corpus exercises; it need not replicate a Rust hasher or duplicate three body fixtures. SQL hosts keep their own NULL and aggregate ordering constraints and must use a deterministic ordered five-text input. Record an explicit not-applicable reason for any claimed surface without a five-record route. The existing `conformance/cases.json` forces batch 1 in several runners, so merely adding one case there would not prove Max content cuts; wire this corpus through the actual host routes. The full functional and release/platform matrices remain separate gates.

Do not close register 64 when only CLI and C pass. The build record keeps a finite table of every advertised host and wrapper, its invoked proof or supported reuse, and missing target proof. Register 19 concerns answer/settings parity, and the separate wire-duplication issue concerns repeated text in requests. Neither is an alias of this byte identity criterion. The fixture says nothing about answer accuracy or provider cost.
