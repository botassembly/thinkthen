## Findings

1. `crates/thinkthen/src/engine/http.rs:115-118`: a slow accounting step lets a request go out after the deadline. `post_observed` reads the remaining budget and sets `limit` first. Only then does it call `before_attempt()`, which is `Counters::request_sent`. That call takes the in-process usage mutex, a blocking `File::lock` on the usage `.lock` file, and fsyncs (`engine/usage.rs:110`, `:183`). None of these waits observes the deadline. After it returns, `send` runs with the old `limit`. Another thinkthen process holding the usage lock, or a sibling worker fsyncing, is enough to trigger it. A scratch probe gave a 200 ms budget and made `before_attempt` take 500 ms. The loopback listener accepted the connection at 500.8 ms, and the call returned `Deadline` at 706 ms. So the request went out 300 ms after the deadline, and the call returned 506 ms late. This breaks the ticket's rule that a spent deadline sends nothing and that the remaining budget caps each blocking send. It also breaks ADR 0017's rule that a past deadline sends nothing.
   Fix: after `before_attempt()`, call `cancel.stop_or_remaining()?` again and compute `limit` from that second reading. Add a red-green test like the probe. `before_attempt` sleeps past a 200 ms budget, and the test asserts `Deadline`, zero accepted connections, and a return well before the send limit. Record one consequence in the ticket and the build record. In that window, `requests_sent` can count one attempt that never started. Counting one extra request costs less than sending one after the deadline. The other fix is to make the usage lock observe the deadline, but that is larger than this ticket allows. The width gate of 0077 is the right place to revisit it.
