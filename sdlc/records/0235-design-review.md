# 0235 design review and correction

Status: first fresh High review rejected design `2ebd20b3`; corrected ticket and preflight await the same reviewer's recheck. This record reports the reviewer finding and builder correction. It does not accept the revised design or authorize runtime edits.

The first design used a synced intent file and wrote a tagged retry sidecar before the legacy monthly file. Review found one blocking case: after the sidecar sync but before the legacy rename, the process can die; an immutable old writer can then add the exact same four-counter delta to the legacy file. The next new writer sees the proposed legacy totals and tagged sidecar, deletes the intent as if its own base write completed, and loses its original base delta. The sidecar identifier cannot identify who wrote the legacy file. The proposed state table incorrectly labeled that pair safe.

The corrected ticket keeps the sidecar-first **migration** of an already contaminated five-field month. Its sidecar and original retry field must match, so a crash before projecting the legacy file is recognizable without adding the two values. For **ordinary new deltas**, it syncs the four-field legacy base first and the retry sidecar second under the stable lock. A crash between them may undercount advisory retries; a detected sidecar failure keeps the existing warning and failure latch. Previously durable base totals remain. The next writer rereads both files and adds only its own delta. An old writer may interleave after lock release and advances only the base. There is no intent, transaction identifier, or indefinite manual-recovery state. Status stays read-only, and the paid ledger remains separate.

The recheck should verify that the ticket and preflight consistently use this ordering; that migration scans every recognized month and refuses malformed, foreign or future input; that ordinary crash behavior is described as possible retry undercount rather than exact atomic totals; and that the old pinned executable's own parser and diagnostic are not claimed repaired before migration. It should also check the bounded 520–524 classification and timeout-only advice against the existing 429/503 and transport rules. Return ACCEPT or findings to fix. No product source, provider call, real usage file, or broad gate ran during this correction.
