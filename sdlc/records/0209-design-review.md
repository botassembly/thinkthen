## Response to first review

The reviewer at `6f030e14626d0c2e008ed7a990c009f9c9562119` confirmed the widening defect and requested three corrections. The ticket now shows a two-row pandas/Polars example. pandas's `failed` dictionary contains only failed names; a Polars fixed-key Struct row exposes a null sibling for a question that did not fail. Recommend the native Struct because the pinned Polars API lacks a public Map dtype and this keeps typed Arrow and Rust frame schemas. The extra sibling key is observable, so Ian must explicitly accept this interpretation before runtime claims. JSON text is not a fallback.

Each Polars question field now nests `failed: Struct<kind: String, cause: String>`, so the full existing `{"failed":{"kind","cause"}}` marker remains under that name. The outer Struct needs an explicit validity bitmap. Pinned `polars-core` 0.55.2 `StructChunked::from_series` constructs parent arrays with no validity, while its public `with_outer_validity(Some(bitmap))` sets parent nulls. The Python Arrow writer already owns array buffers and validity; the new nested Struct needs its own outer bitmap. Both doors must prove actual null success cells and typed zero-row schemas. Pinned `polars` 0.55.2 names the optional feature `dtype-struct`. The proposed writer extraction moves existing schema/metadata logic to one private sibling before adding the nested cell shape, with exact source growth measured at implementation. This is a source-cap plan, not a measured budget amendment.
