## What changed

- The PostgreSQL extension now exposes defaulted named `settings json` and judgment conveniences, four keyed `jsonb` `_many` tables, native `jsonb` `thinkthen_plan`, and settings on find and annotate. The old warm, probability, decide-array, positional-context, and find-none signatures give plain migration refusals. The old array/context/warm implementation files and their now-obsolete internal tests were removed; installed SQL/API cases below replace the useful packing, cache, refusal, and context witnesses. Recognize, relations, and relate retain their existing row/query contracts.
- `json` settings retain their original bytes through one pgrx datum bridge so the shared core parser sees duplicate names before a `serde_json::Value` conversion. `jsonb` keyed input has already normalized repeated keys in PostgreSQL; this host cannot claim to reject those duplicates. The host refuses a wrong judgment kind before transport. Contextual scalar details use the one-record public many path, because the public scalar path correctly refuses shared context.
- The actual send reservation enforces `thinkthen.max_requests_total`, including later packed requests, while cache/replay reads that need no send remain available. A nonempty interactive `SET thinkthen.api_key` warns; the next call refuses with 22023 until reset, and the value never enters the engine. PostgreSQL's live SQL `SET` reached the GUC hook as `PGC_S_SESSION` on the pinned host; checking only `PGC_S_INTERACTIVE` missed it. The warning never repeats the supplied value. Default logging fixture checks the sentinel is absent from output/log and pins four SET warnings versus five call refusals; `log_statement=all` and `pg_stat_statements` can still capture a caller's SET text.
- The engine constructor now accepts the 0299 key `max_estimated_input_tokens_total`, while the separate portable `Settings::parse` still calls it unknown. On the merged source, the original host guard after `Settings::parse` was unreachable and the installed check observed generic unknown-key Usage. The host now maps that one `UnknownKey` to explicit unsupported-host Usage, without accepting an inert reservation. The same duplicate-aware parser still refuses repeated names before the host maps the key; a selected repeated-0299-key check proves this boundary.

## What the build taught us

The preparation correctly identified pgrx named defaults, tuplestore rows and raw settings JSON as the narrow path. It missed that a SQL `SET` reaches the warning hook as session source, that the public scalar details path rejects context and needs one-record many dispatch, and that the old tests/docs still presented removed forms as successful calls. The first installed wrong-kind file test found a request was sent before a Usage refusal; preflighting the loaded question kind replaced that false zero-send claim. A final ADR reread corrected the WIP assumption that the key warning allowed a call: the settled contract requires a subsequent 22023 refusal until RESET. The NULL-input try-details path still skips call settings, while the SET itself warns. E1's exact body can be proven with the existing generic loopback and a literal fixture without claiming the later shared semantic replay corpus is complete. The integration run caught a second preparation miss: engine-constructor validity and portable call-settings validity are distinct, so a guard after `Settings::parse` can be unreachable. The selected installed table now tests that seam, including duplicate-key preservation. The host's selected archive, installed server proof and eventual release-runner qualification remain separate receipts.
