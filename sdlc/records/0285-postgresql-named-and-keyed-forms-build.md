## What the build taught us

The preparation correctly identified pgrx named defaults, tuplestore rows and raw settings JSON as the narrow path. It missed that a SQL `SET` reaches the warning hook as session source, that the public scalar details path rejects context and needs one-record many dispatch, and that the old tests/docs still presented removed forms as successful calls. The first installed wrong-kind file test found a request was sent before a Usage refusal; preflighting the loaded question kind replaced that false zero-send claim. A final ADR reread corrected the WIP assumption that the key warning allowed a call: the settled contract requires a subsequent 22023 refusal until RESET. The NULL-input try-details path still skips call settings, while the SET itself warns. E1's exact body can be proven with the existing generic loopback and a literal fixture without claiming the later shared semantic replay corpus is complete. The integration run caught a second preparation miss: engine-constructor validity and portable call-settings validity are distinct, so a guard after `Settings::parse` can be unreachable. Fresh review found the analogous question boundary: a settings-parser proof cannot establish question parsing when an earlier host conversion erased repeated fields. The selected installed cases now pin both seams. The host's selected archive, installed server proof and eventual release-runner qualification remain separate receipts.
