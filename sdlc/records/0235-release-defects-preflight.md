# 0235 release-defects source preflight

Status: read-only design preparation on main `faa9e7b8`; corrected design accepted by fresh High review at `55137d08`. This preflight changed no runtime, specification, live usage file or paid ledger. The local experiment 345 report was read; its raw credential-bearing outputs and real usage cache were not opened.

Experiment 345 reproduced the usage failure in pinned binaries `02dc0b96` and `72d60786` after a newer binary wrote `retries`. Historical `engine/usage.rs` at each pin has `#[serde(deny_unknown_fields)]`, schema `thinkthen.usage/1` and only requests, input/output tokens and cache answers. Current `engine/usage/counts.rs` adds defaulted `retries` under the same identifier. Its old-row unit test proves only old-to-new reading. `engine/usage.rs::read` scans all recognized monthly files under the shared `.lock`, so an older contaminated month breaks `status` even if the current month is clean. `update` holds the exclusive stable lock, checked-adds, writes a 0600 temporary file, syncs it, renames and syncs the directory. The writer latches failure, and `cli/mod.rs` warns after the answer. Ticket 0225 already bounded the writer's finalization lock acquisition; do not undo it. `config.rs::usage_path` selects the platform cache-adjacent usage directory independently of answer cache selection. The paid ledger has separate authority.

The minimal old-reader-compatible shape is a four-counter `/1` monthly row plus an old-reader-ignored retry sidecar. A current writer must migrate all recognized retry-extended months before its next durable update; a current status reads them without mutation. A sidecar-first projection survives an interruption because a matching contaminated row and sidecar describe the same retry total and are never summed. An ordinary write takes the opposite order: legacy base first, retry sidecar second. Each file becomes durable after its file sync, rename **and directory sync**. A crash after a rename but before its directory sync may retain the prior durable file. An interruption after the base directory sync and before the sidecar directory sync can leave retry statistics low while preserving the committed base. The first High review rejected an intent protocol because an immutable old writer can add the same base delta after a crash, making the alleged transaction state indistinguishable. The corrected design removes the intent and manual recovery dependency. No new reader can change an immutable old binary, and no two-file protocol can promise atomicity to a binary that knows only the legacy file. Ticket 0235 states that boundary and gives an upgrade route for a user who cannot wait for a later compatible usage write.

`cli/status.rs` currently maps cache and usage read errors to the same `Failure::StatusState`; `cli/failure.rs` gives a generic pathless sentence. The new code may name a generated month basename and the fixed usage directory label, not raw JSON, OS/parser text, arbitrary path bytes, evidence, URL or key. An old binary's generic sentence cannot be changed. The existing `tests/status.rs` checks exact output shape; any status diagnostic or count change needs its exact fixture adjusted. `specification/recording.md:33–35` currently promises one retry-extended file and needs an explicit contract update after design acceptance.

The retry list is `engine/error.rs::RETRIED = [429, 500, 502, 503, 504, 529]`. `engine/http.rs::post_observed_with_retry` applies that one classification to the shared exact-URL gate and per-call resends, with a maximum retry count, exponential wait, `Retry-After` floor, deadline/cancellation stops and attempt marking before transport. A transport failure remains one send because it may have been billed. The current fixed status table omits 520–524. Cloudflare's [structured 5xx notice](https://developers.cloudflare.com/changelog/post/2026-04-27-structured-responses-for-5xx-errors/) calls 520–524 retryable; its [5xx reference](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/) describes the gateway/origin failure family. This supports a bounded status-list correction, not transport resends or a backend availability guarantee.

`cli/failure/stopped.rs` gives multi-record timeout size advice while `cli/failure.rs` gives a singleton timeout duration advice. `specification/backends.md:88` states both. ## Preparation lessons

The historical source check changed the design: removing `deny_unknown_fields` in current code cannot help old binaries. The `status` directory scan means repairing only the active month is insufficient. The stable `.lock` lets a new writer migrate beside an old writer without concurrent mutation, but a crash releases that lock and makes later old-writer changes possible. The first intent proposal could not identify the legacy writer after that crash; the corrected order preserves durable base totals and openly permits advisory retry undercount. The D18 closure must be read by criterion: its 429 correction survives, while the live timeout exposed a bad new phrase. Preparation produced no runtime proof; the builder must prove the real executable boundary and record any correction in the ticket's build lessons.

The later reported zero-byte canonical month is confirmed malformed input, but its crash origin is unverified. Historical `02dc0b96` and current writers create and truncate `.update.tmp`, sync it, rename it to the canonical month, and sync the directory; neither creates a zero-byte canonical placeholder on first write. A build regression should prove valid-or-absent first-write publication and refuse an existing zero-byte file without changing its bytes or manufacturing lost totals.
