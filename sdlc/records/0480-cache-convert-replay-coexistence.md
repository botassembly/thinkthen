# 0480: Cache conversion and replay coexistence

Replay now waits for a committed SQLite snapshot within the existing lock limit and call cancellation. It reads and validates the snapshot once. Conversion syncs the containing folder after removing the live SQLite file. On Windows, conversion takes a file handle that excludes writers before reading or publishing. If an open reader prevents removal, it restores the previous fixture bytes or removes the new fixture while the guard remains held. Restoration failure surfaces a recovery error. Replay still refuses a folder that holds both live and fixture files.

## What the build taught us

SQLite's moved-file protection refused the pending Linux write after conversion removed the pathname. The original lost-write claim needed a two-process proof before changing the write path. A deferred SQLite `BEGIN` also needs an actual read before it has a committed snapshot; waiting around that first read preserves the existing deadline and cancellation behavior. Windows file sharing requires a separate guard and a recovery path when an existing reader prevents deletion.
