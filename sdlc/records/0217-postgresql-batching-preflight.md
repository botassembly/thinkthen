## Retained test assets and focused next proof

`databases/postgresql/check.sh` already checks a two-item array, array deadline/cancel, `thinkthen_warm` filling cache for later scalar reads, banded question parity, missing/broken named files, request-limit refusal, one backend's request total, strict replay miss, retry-total refusal, six-kind SQLSTATE mapping, and privilege/grant behavior. `tests/runner.py` maps shared `conformance/cases.json` to SQL and already hashes canonical request bytes; its `many` adapter reads array results in `ORDER BY i`. `tests/settings_cases.py` records the PostgreSQL-specific zero-send prevalidation of `max_requests`; do not copy another host's partial-send expectation. Reuse these checks. They do not pin a packed full body/digest, first-occurrence batch order after current sorting, context identity, or the deadline of a later packed request. A new listener table for those boundaries earns its place; do not add a second broad conformance matrix or a test-only hook. The PostgreSQL checker packages normal and panic-probe extensions unless a verified unchanged artifact is supplied; select focused steps, but do not call an old artifact proof of new source.

The native aggregate reads input in PostgreSQL's delivered order; an explicit aggregate `ORDER BY` is the caller's replay control. `Array<'_, &str>` and pgrx aggregate state cannot cross a detached worker. Own validated strings and context first, keep outputs owned until the backend materializes them, and join or detach with current cancellation semantics. A 20,000-row warm input can yield many core batches, but its single aggregate deadline must not reset between them. A finite array has no 50 ms input pause. With `max_requests_total = 1`, two packed requests may send the first and refuse the second; `max_requests` remains a separate pre-send distinct-record cap for arrays and per-question/context warm groups. The SQL error aborts the materialized result, while sends and cache entries already completed remain real.

## Unresolved before runtime

The accepted issue's PostgreSQL “final context argument” does not enumerate singleton scalar overloads. This design proposes context on the array and warm forms, where it is shared across records. A one-text scalar context overload would quote even one record and change its body/digest; it would not solve register 73's serial scalar calls. The independent reviewer should judge whether B0 requires that broader outward reach; route a material public extension to the coordinator and Ian rather than silently adding it. Refresh B12a's actual final `Call<T>` and options source, 0157's plan/size source, exact overlapping file claims and PostgreSQL's generated SQL/package before writing runtime code. No new ADR is filed for a design-only question.
