## Proposed release order for the coordinator

1. **Bounded SQL fixes under current contracts.** Correct the PostgreSQL README choose example now. Add plain judgment text in PostgreSQL under its existing signatures and yes probability in SQLite under its existing arguments. Give each an installed-host request/NULL/refusal proof. 2. **Column results and facts.** Add Python threshold/probability and the chosen pandas/Polars/R idioms after agreeing how a plain column exposes mandatory call facts. Preserve existing module `Call` APIs. This carries criteria 3's frame part, 5 and the frame portion of 6. The accepted run-facts issue is a dependency, not a duplicate of the whole usability issue.
3. **Reviewed shared syntax, examples and measurable counts.** Decide whether the common third slot and native named syntax earn their API cost before implementing them. Keep old NULL, deadline, context and file semantics in the design review. Repair the SQLite site example under Marketing; the database builder owns both database README examples. Publish a cross-host spelling table, run selected SQL and frame examples from actual installed packages, and state exact listener counts for scalar versus batched forms. This carries criteria 1, 4, 6-7 and 11 without assuming all optional row-source or settings redesigns. The new six-surface demonstration may reuse completed conformance proof.

Review separately after these: criterion 8's row-source parity; criterion 9's one-row SQL usage shape; criterion 10's exact retry text; criterion 12's ADR for all decisions. Their distinct acceptance criteria must remain visible if the issue is split. A 0.1 cut can document native dialect limits rather than add row sources, hot SQLite engine replacement, a per-call model, `rows_judged` usage, short aliases, packaging a SQLite pip helper, or several-column records. These are unaccepted additions with larger surface area and no demonstrated release blocker in the present source. The issue's own out-of-scope list remains a guard.
