# SQL usability preparation at `42b45db6`

This is a source check and batching recommendation for [the open issue](../issues/2026-09-28-sql-interface-usability-before-0-1.md), not approval of its proposed API. The source reference and `origin/main` both resolved to `42b45db612e47836ab98fb33614eecc7f272a0d8` when checked. The issue's survey was taken at `8033eeac`. DuckDB `cpp/src/thinkthen.cpp:408-440` uses deadline for decide/probability and a `LIST` of labels for choose/score/tag. SQLite can encode descriptions in a JSON question; DuckDB and PostgreSQL's native lists carry labels, not descriptions. | A shared JSON settings slot, native named syntax, changing existing slots, and per-call model are **unapproved alternatives**. Preserve old valid two-argument calls, complete JSON/file questions, SQL NULL behavior, context request identity, per-call deadline/connection budget semantics, and native label order. The approved batching and settings contracts are ADRs 0048/0051/0053/0055/0087 and tickets 0149, 0217, 0219, 0222. A new common grammar must have one independent corpus of valid/invalid settings and expected wire bodies, exercised through all three installed hosts. | Probability without a JSON path | **Small real gap and broader proposal.** PostgreSQL registers decide probability in `src/lib.rs:141-150`; DuckDB registers it in `cpp/src/thinkthen.cpp:408-420`; SQLite's registration at `src/scalars.rs:359-370` omits it. ## Proposed release order for the coordinator

1. **Correctness and usable scalar path.** Decide the smallest plain-text rule for PostgreSQL and the common third-slot contract. Include SQLite decide probability and a portable choose/options example only if the reviewed grammar keeps each host's current NULL, deadline, context and file semantics. This addresses acceptance criteria 2, 3's SQLite part, 4 and the SQL portion of 6. The first dependency is a reviewed API record, followed by native installed-host tests. A correction limited to PostgreSQL's broken README example can happen earlier under the site owner, but does not settle the plain-text defect.
2. **Column results and facts.** Add Python threshold/probability and the chosen pandas/Polars/R idioms after agreeing how a plain column exposes mandatory call facts. Preserve existing module `Call` APIs. This carries criteria 3's frame part, 5 and the frame portion of 6. The accepted run-facts issue is a dependency, not a duplicate of the whole usability issue.
3. **Examples and measurable counts.** Repair the three wrong samples, publish one cross-host spelling table, run the selected SQL and frame examples from the actual installed packages, and state exact listener counts for scalar versus batched forms. Route edits through the site-samples owner. This carries criteria 1, 6-7 and 11 without waiting for all optional row-source or settings redesigns.

Review separately after these: criterion 8's row-source parity; criterion 9's one-row SQL usage shape; criterion 10's exact retry text; criterion 12's ADR for all decisions. Their distinct acceptance criteria must remain visible if the issue is split. A 0.1 cut can document native dialect limits rather than add row sources, hot SQLite engine replacement, a per-call model, `rows_judged` usage, short aliases, packaging a SQLite pip helper, or several-column records. These are unaccepted additions with larger surface area and no demonstrated release blocker in the present source. The issue's own out-of-scope list remains a guard.

## Aliases and checks before ticket writing

- Tickets 0149/0157 and `specification/settings.md` already own settings reachability. The new hot SQLite setting and per-call model are distinct proposed behavior.
- Tickets 0217/0219/0222 and the batching issue already own packed array/warm/vector calls. Register 73 still owns scalar per-row throughput; this issue adds a reader-facing count and possible design choice, not another implementation of B13.
- Ticket 0224 and ADR 0096 own ordered group `find`, its typed result, request capture and target qualification. Do not replace it with probability sorting.
- ADR 0082 owns plain SQL output types; the run-facts issue owns per-call facts and cost. This issue's companion probability and usage-display asks must retain their distinct criteria.
- The site-samples issue owns regeneration; this issue supplies the broken SQL examples and the desired parity checks. The shared-conformance issue owns question-file proof. The issue's SQLite relations sample can be corrected even if row-source parity is deferred.

The issue proposes named `:=` calls in DuckDB/PostgreSQL and JSON settings in SQLite, but neither syntax is approved or proved here. PostgreSQL `:=` may resolve differently once overloads and defaults coexist; DuckDB's scalar registration at `cpp/src/thinkthen.cpp:408-440` uses positional parameter vectors. A named-argument or macro claim needs an installed v1.5.5 bind/host probe before ticket acceptance. No test should derive the expected body from the implementation's own parser. Capture the complete observed request and compare with a separate fixed fixture, including question digest and actual served URL where applicable. Keep host value domains separate: SQLite's total cannot be zero, while a zero connection budget is valid and spent (`databases/sqlite/README.md:87,93`).
