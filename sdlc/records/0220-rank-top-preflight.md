# 0220 rank top retention preflight

Status: read-only design preparation at main `ebc80d88`; no runtime, page, broad test or provider change. The [ticket](../tickets/0220-bound-rank-top-retention.md) is proposed, not accepted by this note. Register 45 guidance has a separate owner and a shared `specification/rank.md` claim.

| Live layer | Current behavior and implication |
| --- | --- |
| CLI rank sink | `cli/judge.rs::rank` parses `--top` as a positive `usize` and passes it to `Output::ordered`. `cli/schedule.rs::Output::take` pushes every `Judged` into `Mode::Ordered.held`. At successful end it allocates `odds: Vec<f64>`, calls `core::order::ranking`, then writes the selected rows. The row vector, odds and place vector all scale with total records today. `ranking` uses stable sort with `f64::total_cmp`, so exact ties preserve input order. |
| Scheduler completed results | `cli/schedule.rs::over_records` and `cli/asking/batched.rs::run` pass `output.holds() == true` to `Engine::records` for rank, with or without top. `engine/schedule.rs::Run::waiting(true)` is `in_flight`; streaming uses `dispatched - next`. A stalled earliest result plus later fast completions can keep `in_flight` below `jobs` while `pending: BTreeMap` grows with file length. The same `held` bit enters `RunOutcome::Stopped` and `Failure::Stopped`, which prints rank's no-output sentence. Simply passing `false` for top would bound the pending window but misreport that stopped run. |
| Input and batch staging | Unbatched line/JSONL and CSV/TSV readers advance on scheduler asks. The batched feeder uses `sync_channel(AHEAD)` with `AHEAD=64`. `Former` holds an open batch and a queue of closed batches/refusals; `core/batch.rs` caps a batch at `MEMBERS=4,096` as well as request-size/profile limits. `answered` temporarily returns `Vec<Judged>` for one batch and split halves can hold their own bounded values. This staging is bounded in *row count* independent of total file length once scheduler dispatch is windowed, but individual raw input rows and selected output rows can be large. No second batch planner is needed. |
| Side effects and failures | `Output::take` records a done row after successful receipt even when rank holds it until end. `Output::ended` runs only on `RunOutcome::Complete`; a stopped rank run prints no rows, and `Failure::Stopped.held` names that. A bounded pending window can send fewer speculative requests before a failure/cancel, and a timed input pause can close a batch at a different place; accurate stopped metadata and error forms must remain, but old speculative sends are not a parity target. `--details` builds a whole original-input result per row; warnings print only for ranked rows actually written. Recording/cache and usage are per request/record side effects and are not output-memory buffers to delete. |

Existing literal command tests in `tests/backend/keeping.rs` pin no-top order, exact tie order, top-two output and four requests, detailed top membership, failed rank empty stdout/stopped sentence, dry-run and invalid `--top`. `core/order.rs` pins the stable order and top prefix, including property cases. These tests do not fail if a top-N run still holds every row; the new private row-count invariant must. A finite held-first listener case proves the selected scheduler mode is exercised by the command, while source review establishes the bound for arbitrary file length. Neither is a claim of measured RSS.

Nonblank counts at this main: `cli/schedule.rs` 284, `engine/schedule.rs` 459, `engine/facade.rs` 401, `cli/asking/batched.rs` 488, `tests/backend/keeping.rs` 496, `tests/backend/batching.rs` 466, `core/order.rs` 81. The 500-line policy makes a `keeping/rank_top.rs` child preferable to expanding its parent, and leaves little room in `asking/batched.rs` for a new retention mechanism. The flow value belongs in the scheduler, while winner selection belongs in the existing output sink. Check all `Engine::records` bool callers when replacing the private parameter; five other callers currently pass `false`. Direct `run_cancelled(false)` tests occur twice in `engine/schedule.rs` and three times in `engine/deadline_tests/schedule.rs:59,126,183`. `core/order.rs` and `cli/asking.rs` are source evidence, not expected edit paths. `cli/args/command.rs` help and `specification/rank.md` both promise that rank holds every record, so they need scoped wording after implementation; `cli/failure/tests.rs` contains the same premise in a comment.

The key review question is the small private mode's separation of output-held metadata from admission backpressure. It must leave streaming and uncut rank unchanged, choose held-windowed only for rank top, and never allow a later exact tie to replace an earlier winner. A held first result also tests that retaining N winners in the sink alone would leave the engine's completed-results map unbounded. Completed finite input with stable batch boundaries supports exact request/output parity; interrupted or timed input may expose less speculative work or another pause cut, so no parity promise covers those counts. No unresolved external product choice or new flag was found.

## What the build taught us

This is a preflight record, not a build record. The first source read found the obvious all-row `Output.held`; tracing the scheduler mode found an independent unbounded pending map under a stalled earliest batch. The existing source cap and tests favor one private flow mode, a child command table, and a focused internal row-count assertion. Fresh design review corrected the proof scope for bounded speculation and found three missed direct deadline-scheduler callers. The later builder and reviewer must report whether this inventory was sufficient and which proof actually caught a regression.
