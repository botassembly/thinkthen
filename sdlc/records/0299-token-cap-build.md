# 0299 estimated-input admission: core, command and C source build

Status: focused source candidate for independent High code review. Design `f49eaccf2` and accepted branch metadata `ee55bd6f4` were merged normally with main `4f8acbca8` before code. The issue remains open for other host conversions and release qualification.

## Changed

`SendBudget` remains the single process reservation owner and now retains an atomic estimated-input sum. Each engine selects its optional finite estimate limit at admission. The exact final encoded `Exchange.body` charges `ceil(bytes × 908 / 1000)` for every live attempt, including retry and split child. The checked reservation drops without charge before transport if a later gate refuses or marking fails; a started send commits even if its reply, decode, timeout or cancellation fails. Unset engines still count. Fork resets both sums. Neither reported usage nor the plan preview settles the admission sum.

Rust `EngineBuilder`, the asking CLI including find, and the C closed JSON constructor actively select the new limit. Core JSON validation rejects wrong types and repeated keys; C retains null as unset. `EstimatedInputDenial` has separate InitialRequest, AdditionalRequest and Retry statuses. Public errors expose that typed reason and safe message; CLI prints the reviewed exact `thinkthen usage:` sentence with exit 2; native batch treats the refusal as a recoverable Usage failure. The C header and specification settings, backend and preview pages describe the source behavior and its limits. No C symbol or result shape changed.

## Focused proof

- The new `public_estimated` source listener case calculates a charge from the observed final body. It pins initial and later ordinary denials, selected lower/raised limits, a held concurrent request with exactly one arrival, a retry denied after one observed 503, identical cache and replay answers at a spent limit, and final facts. A narrow reservation-boundary test drops an unstarted attempt, proves the same estimated body can reserve again, then proves a denied estimate refunds its request slot. A reply reporting 312 input and 48,000 output tokens after a smaller admitted estimate proves the limit is not a provider or bill cap. Listener receipts are consumed once; the first version of the test incorrectly indexed a drained receipt and was corrected before the passing run.
- The existing compiled backend's new split-child case first captures the actual 5/3/2 bodies without a limit, then gives a separate process only the parent body's measured charge. Its 400 `max_tokens_exceeded` parent arrives once, and the child is denied as AdditionalRequest before a second arrival. The ordinary split test remains in place.
- The compiled command's zero-limit case pins exit 2 and the exact safe sentence. Its first run showed a missing `usage:` prefix, fixed in the typed failure route. The C constructor zero-limit test pins an accepted JSON setting, refusal and zero backend arrivals. The existing C negative-settings table was extended for negative, fractional, string and overflowing values, plus null-unset acceptance.
- Focused root and C all-target Clippy, format, policy, public inventory, pages, tickets, ratchets and diff checks are required before handoff. Record their final outputs below.

No existing test was removed or replaced because the request-cap, cache, retry and split regressions prove distinct behavior.

## What the build taught us

The 0289 preparation lesson about a process counter versus a process-wide setting applies to estimates too: a limit belongs to the attempt, and the retained sum belongs to the shared owner. A final body, rather than planned bytes or observed usage, is the only safe admission input. The separate public, CLI and native-batch error conversions were all material. The C header had an older incomplete constructor-key list and was brought into agreement with the closed parser. The host-by-host setting rollout remains explicit; this source candidate does not close the 0299 issue, qualify an archive or claim a provider-side cap.
