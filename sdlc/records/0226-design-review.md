# 0226 native panic diagnostics design review handoff

Status: proposed at main `cd395d3f`, awaiting a fresh independent High security/technical review. Owner: Codex. Review the [ticket](../tickets/0226-native-panic-diagnostics.md), [preflight](0226-panic-preflight.md), proposed [ADR 0098](../planning/adr/0098-native-panic-diagnostics.md), issue and accepted ADR 0081. This handoff authorizes no runtime edit or issue closure.

Check the two independent leaks. `catch_unwind` catches only after the process hook runs. C `failures.rs::guard`, SQLite `lib.rs::guard`, and retained DuckDB C API `src/errors.rs::guarded` also copy `&str`/`String` payloads into returned defects. Old DuckDB's detached `src/worker.rs::run_typed` has no binding guard on that thread. Confirm the proposed local once-installed delegating hook and thread-local depth cover each owned callback and worker, include error conversion and payload drop, restore through unwind, and leave unrelated host threads on the previous hook. Probe nesting with the landed engine hook. Review later host replacement and simultaneous registration as explicit limitations, never as guarantees. Hook code must remain mapped: SQLite moves its fallible `ffi.rs::pin` before registration/hook installation; the dynamic C door retains itself before installation while the static archive resides in the host; pinned DuckDB v1.5.5 loader source shows `dlopen` with no `dlclose` in its extension tree, to be checked on target packages. Host callbacks retain their policy; no per-call global hook swap is allowed.

Check the conversion boundary: C retains `DEFECT`, false retry and last-error lifetime; constructor `built` stays fixed. SQLite keeps `SQLITE_ERROR`, `thinkthen defect: ` and no Defect failed JSON; its detached worker gets its own marker. Its exported load entry currently calls `rusqlite::Connection::extension_init2` without a catch; pinned rusqlite 0.40.2 source confirms this. The proposal wraps that entry in the same `lib.rs::guard`, maps only unexpected panic to fixed safe `SQLITE_ERROR`, and preserves ordinary load errors, with an exact host mapping check before claiming load containment. Old DuckDB keeps its callback name, fixed defect, closed-channel/cancel behavior, engine error mapping and exactly one `catch_unwind` in `src`. Its worker should use that existing guard through a nested result, not create a second catch. The Linux x86-64 C++ bridge and root worker guard already landed and must remain untouched.

The focused child proof must use a synthetic marker, capture whole stdout and stderr, inspect the actual returned C/SQLite/old DuckDB error, classify Defect and non-retryable, make a next successful call, and show an unrelated host-thread panic reached the previous hook. Cover worker threads for SQLite and old DuckDB, plus a bounded C dynamic unload and SQLite failed-load residency witness. The current payload-copy unit tests must change; do not add a public fault switch, another HTTP harness or repeated panic matrix. Check that the selected C and SQLite routine tests execute those children. A local old-C-API unit child is not an installed Linux x86-64 DuckDB check: `check.sh` there builds the C++ extension, while release-pack still ships C API on Linux ARM64 and both macOS targets. Require real matching stock hosts and archive ABI checks before claiming those packages. Review a direct C `libc` dependency, already present transitively in its lock graph, if the self-retain uses `dladdr`/`dlopen`.

The bounded other-binding scan found a separate R returned-payload copy and fixed-return Python, Ruby and TypeScript guards whose default hooks may still print. Review whether those need an explicit follow-on claim; do not describe 0226 as a universal all-bindings solution. Public names, SQL forms and ordinary six-kind behavior do not change. The architectural question for review is whether three small private hook scopes safely coexist with host and engine hooks under the stated limits, including SQLite's load wrapper; no new outward choice is proposed to Ian.

## What preparation taught us

The old issue is correct for three named payload-copy guards but stale for the landed Linux C++ bridge. A source-only `catch_unwind` count also misses the hook's earlier diagnostic and the worker's separate thread. The proposed proof is therefore a child process that reads both streams and the returned error. A process-global hook also survives the call, so the C shared library and SQLite failed-load teardown need explicit residency checks. C's `ffi.rs` has 42 nonblank lines of file headroom; its scope belongs beside the existing guard, while a small self-retain may fit in the FFI module. Review should decide whether this inventory gives the builder a complete narrow start and identify any unclaimed ABI path before code begins.
