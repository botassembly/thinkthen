# 0257 audit case evidence preflight

Status: proposed design at clean main `23371cc9`; runtime, public pages and original issue remain read-only. The [filed issue](../issues/2026-09-27-audit-shows-group-counts-and-no-per-case-evidence.md) asks for one row per case with identity, input, said, truth, outcome, probabilities and available tokens, plus miss shape, sent option order, case kind and suitable top-two evidence. The reviewed [four-row refresh](2026-09-28-tuning-evidence-refresh.md) accepted at `fa512f45` keeps per-case audit separate from uncertain-case selection, repeated runs and chained-call guidance. Ticket 0256 and ADR 0102 have since landed: the tuned-output route is independent and must stay unchanged. [Proposed ADR 0103](../planning/adr/0103-audit-case-evidence.md) chooses a case-only JSONL contract.

## Actual source path and saved carriers

`cli/audit.rs::grade_all` validates current options, reads numbered result/key lines, calls `answer::read(..., Identity::Question)` and `Key::read`, builds a `Settings` rule, then calls `grade::audit`. It refuses a nonempty key with no labeled unfailed answer and calls `write::bars` only when `--write` is present. `cli/audit.rs::run` prints aggregate rows and an optional pooled line. `core/measure/answer.rs` expands `answers` members and `tag` labels, refuses repeats by `(name, id, question text, label)`, marks failures, and applies the selected rule through `Answer::said`. `key.rs::Key::want` joins by id then answer name; `key::outcome` distinguishes right/wrong/unsure/tied. `rows.rs::row/count` excludes failed and unlabeled answers; `items.rs::tally` counts matched, extra and missed names/edges. These functions already own grading. `cli/diff.rs` reports changed cases only, so it is not this view.

The saved `Json` object preserves member order. `Answer` retains line, id, member name, text, label, verb, probability and parsed top, but not raw input, all ordered question options, raw distribution or usage. Access the raw result by its existing one-based line, then select `answers[name]` for an annotated criterion; never independently rebuild identity. `question.options` is the sent-order carrier for choose; `question.labels` and `question.levels` carry tag/score order. A distribution's object order is not proof of the question's sent order. A suitable choose `top_two` requires both carriers. The saved root `meta.usage` is optional. The current packed CLI may share a backend usage total into a saved row, and `annotate`'s root metadata aggregates its named questions; the case view must copy and label the saved result-line scope, not allocate it again. `--facts` is a separate whole-run counter and supplies no case tokens. `filter --details` omits filtered-out records, so it cannot create evidence for misses that were never saved.

## Precise small proof to build

Create one generic saved `results.jsonl` and `key.jsonl` under `tests/fixtures/measure/cases/`, with each input and expected member written literally. The shortest choice row can use `{"input":{"id":"c1"},"value":"red","question":{"verb":"choose","text":"Which colour?","options":["red","green","blue"]},"answer":{"probabilities":{"red":0.8,"green":0.1,"blue":0.1}}}` and key `{"id":"c1","value":"red"}`. The case projection must include `id:"c1"`, `question:"Which colour?"`, `verb:"choose"`, `options:["red","green","blue"]`, `said:"red"`, `truth:"red"`, `outcome:"right"`, the exact saved probability map, `top_two:[{"option":"red","probability":0.8},{"option":"green","probability":0.1}]`, and `usage:null`. A second choice line has a tied top; the tie stays `tied` even if its key is one of the holders. Use a separate option-order fixture where distribution member order differs from `question.options`, so the top-two tie break proves sent order rather than JSON map order. Pin the entire output object, not only these fields.

The same small table needs a yes/no false positive and false negative, a score one level away from truth, an annotated record with two distinct named criteria and one root `meta.usage:{input_tokens:7,output_tokens:2}`, a failed criterion, an unlabeled row, a null-usage row, one unresolved answer, and a recognize or relate partial set whose existing `tally` returns `matched:1,extra:1,missed:1`. An annotated criterion must say `usage_scope:"result_line"`, so two criterion rows do not claim two separate token charges. Keep a valid nonempty key with at least one label to avoid the earlier `NoneLabeled` refusal masking the test. For missing input on supported set/find output, pin line-number fallback id and `input:null`. Compare the **same** fixture's ordinary aggregate output and `--cases` output under `--threshold` where meaningful: scalar outcome totals equal aggregate right/wrong/unsure/tied/failed/unlabeled, and set item counts equal aggregate item directions. The default aggregate output must remain byte identical to the existing golden. Do not expect a scalar right/wrong total to equal the set's item count.

Append a duplicate case identity to otherwise valid saved input and assert exit 2, empty stdout and `thinkthen: audit: results line N repeats a record for one question\n`. Show a second question member under one id succeeds. Pin one conflict such as `--cases --table` as usage exit 2 before any input read, and exercise the other conflict names through a small table. A configured loopback listener and canary `THINKTHEN_API_KEY` around the compiled audit child must count zero sends and show no canary in stdout/stderr. Reuse `tests/support/measure.rs` and exact existing fixture input; do not create a new request or grade framework. Retain selected `audit.rs`, `audit_refusals.rs` and `audit_output.rs` cases for aggregate, refusal and 0256 publication behavior. No provider, stress, broad suite or source experiment is needed in design.

## Preparation lesson and implementation handoff

The hard part is not serializing an `Answer`: that parsed type has intentionally shed raw saved carriers, while the original criterion needs input and sent options. Attach those fields by the answer's already parsed line/member identity, and let `Key::want`, `Answer::said`, `key::outcome` and `items::tally` remain the sole grader. Failed answers may have unusable keyed values that aggregate audit never validates; retain raw key evidence separately if desired, but do not introduce a new refusal or report it as graded truth. The case-only choice avoids an aggregate/case mixed stream; explicit conflicts keep aggregate-only flags from being silently ignored. The normative audit page and command help must land with source because the existing page is Settled. The ticket lists precise source files and current ceilings. Build lessons and any changed file claim belong in a build record after approval, not this design note.
