# 0257 audit case evidence preflight

Status: proposed design at clean main `23371cc9`; runtime, public pages and original issue remain read-only. The [filed issue](../issues/2026-09-27-audit-shows-group-counts-and-no-per-case-evidence.md) asks for one row per case with identity, input, said, truth, outcome, probabilities and available tokens, plus miss shape, sent option order, case kind and suitable top-two evidence. The reviewed [four-row refresh](2026-09-28-tuning-evidence-refresh.md) accepted at `fa512f45` keeps per-case audit separate from uncertain-case selection, repeated runs and chained-call guidance. Ticket 0256 and ADR 0102 have since landed: the tuned-output route is independent and must stay unchanged. [Proposed ADR 0103](../planning/adr/0103-audit-case-evidence.md) chooses a case-only JSONL contract.

## Actual source path and saved carriers

`cli/audit.rs::grade_all` validates current options, reads numbered result/key lines, calls `answer::read(..., Identity::Question)` and `Key::read`, builds a `Settings` rule, then calls `grade::audit`. It refuses a nonempty key with no labeled unfailed answer and calls `write::bars` only when `--write` is present. `cli/audit.rs::run` prints aggregate rows and an optional pooled line. `core/measure/answer.rs` expands `answers` members and `tag` labels, refuses repeats by `(name, id, question text, label)`, marks failures, and applies the selected rule through `Answer::said`. `key.rs::Key::want` joins by id then answer name; `key::outcome` distinguishes right/wrong/unsure/tied. `rows.rs::row/count` excludes failed and unlabeled answers; `items.rs::tally` counts matched, extra and missed names/edges. These functions already own grading. `cli/diff.rs` reports changed cases only, so it is not this view.

The saved `Json` object preserves member order. `Answer` retains line, id, member name, text, label, verb, probability and parsed top, but not raw input, all ordered question options, raw distribution or usage. Access the raw result by its existing one-based line, then select `answers[name]` for an annotated criterion; never independently rebuild identity. `question.options` is the sent-order carrier for choose; `question.labels` and `question.levels` carry tag/score option order. A distribution's object order is not proof of the question's sent order. **Tag row order differs:** `core/measure/verbs.rs::labels` expands in `answer.probabilities` member order when present, falling back to `question.labels` only without a distribution. The view must preserve that parsed row order even when it prints `options` in a different question order. A suitable choose `top_two` requires both carriers. The saved root `meta.usage` is optional. The current packed CLI may share a backend usage total into a saved row, and `annotate`'s root metadata aggregates its named questions; the case view must copy and label the saved result-line scope, not allocate it again. `--facts` is a separate whole-run counter and supplies no case tokens. `filter --details` omits filtered-out records, so it cannot create evidence for misses that were never saved.

## Precise small proof to build

Create one generic saved `results.jsonl` and `key.jsonl` under `tests/fixtures/measure/cases/`, with each input and expected member written literally. The complete row oracle below includes a tied `choose` case whose distribution member order differs from `question.options`, so its top-two tie break proves the saved sent order rather than map order. The tie stays `tied` even though its key names one of the holders. Pin the entire output objects, not selected fields.

The same small table needs a yes/no false positive and false negative, a score one level away from truth, an annotated record with two distinct named criteria and one root `meta.usage:{input_tokens:7,output_tokens:2}`, a failed criterion, an unlabeled row, a null-usage row, one unresolved answer, and a recognize or relate partial set whose existing `tally` returns `matched:1,extra:1,missed:1`. An annotated criterion must say `usage_scope:"result_line"`, so two criterion rows do not claim two separate token charges. Keep a valid nonempty key with at least one label to avoid the earlier `NoneLabeled` refusal masking the test. For missing input on supported set/find output, pin line-number fallback id and `input:null`. Compare the **same** fixture's ordinary aggregate output and `--cases` output as run; use a separate threshold-compatible subset for rescore parity because `score` refuses `--threshold`. For each non-tag scalar group, the matching cases reproduce `right`, `wrong`, `unsure`, `tied`, `failed`, `unlabeled`, `true_yes`, `false_yes`, `true_no` and `false_no` when applicable. For tag, compare the pooled group with all expanded label cases and each label group with only that label's unfailed cases plus the one shared failed entry; never sum pooled and label rows together or multiply the failed case across labels. For a set group, sum `matched`, `extra`, `missed` into aggregate `true_yes`, `false_yes`, `false_no` respectively, and do not assert a scalar right/wrong total. The default aggregate output must remain byte identical to the existing golden.

## Preparation lesson and implementation handoff

The hard part is not serializing an `Answer`: that parsed type has intentionally shed raw saved carriers, while the original criterion needs input and sent options. Attach those fields by the answer's already parsed line/member identity, and let `Key::want`, `Answer::said`, `key::outcome` and `items::tally` remain the sole grader. Fresh review caught two missed distinctions: the internal `Said` and `Want` enums need a concrete JSON contract, and `tag` row expansion follows saved probability member order before it falls back to question labels. The first design also tested only right/wrong totals; the build must pin both yes/no error directions against the correct aggregate tag groups. Failed answers may have unusable keyed values that aggregate audit never validates; retain raw key evidence only in the failed row, without a new refusal or a graded truth claim. The case-only choice avoids an aggregate/case mixed stream; explicit conflicts keep aggregate-only flags from being silently ignored. The normative audit page and command help must land with source because the existing page is Settled. The ticket lists precise source files and current ceilings. Build lessons and any changed file claim belong in a build record after approval, not this design note.
