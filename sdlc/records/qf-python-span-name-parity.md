## Decision and retained behavior

Local experiment 284, register 114 asks Python frames to rename a recognized span from `text` to `name`. Its claim that every other recognition surface uses `name` is false against the current accepted contract. [ADR 0082](../planning/adr/0082-one-type-contract-for-every-surface.md) keeps existing span field names. [types.md](../../specification/types.md) and [result.schema.json](../../specification/result.schema.json) require recognized entity `text`; [recognize.md](../../specification/recognize.md) shows that shape. [relate.md](../../specification/relate.md) gives the separate entity input `name` and explicitly accepts a recognized `text` when `name` is absent. `libraries/python/src/frame/names.rs` emits Polars `text`; `libraries/python/src/frame.rs` emits pandas nested `text`; `libraries/python/src/input.rs` already reads `name` first and falls back to `text`. C/command JSON, Rust, TypeScript, Ruby, R, SQLite, PostgreSQL and DuckDB recognition use `text` in their current source or public pages. Renaming Python alone would create a divergent public frame shape and break current consumers. Propose treating the demanded rename as a **non-issue under the later accepted ADR**, while preserving the separately valid field/unit documentation and handoff proof. Root owns the register disposition after review.

`specification/recognize.md` now states the actual recognized field and offset convention per surface. It distinguishes zero-based Unicode scalar offsets, TypeScript UTF-16 units, and R one-based inclusive positions. It names Python Polars and pandas frame layouts and the `text`-to-`relate` fallback. No output schema or JSON fixture changed.

## What the build taught us

Preparation repeated the register's shorthand without comparing it to the later normative type schema and actual consumers. The accepted schema and `relate` fallback resolve the supposed field mismatch: a recognition span is `text`, while a relation entity is `name`.
