# 0224 SQL group find design review handoff

Status: corrected after the first independent review of `a43f9541`; the same reviewer should check the capture route and budget clarification. Owner: Codex. Read the [ticket](../tickets/0224-sql-group-find.md), [preflight](0224-sql-find-preflight.md), proposed [ADR 0096](../planning/adr/0096-sql-group-find-contract.md), SQL-find [issue](../issues/2026-09-27-sql-find-is-missing-from-three-databases.md), and settled [find specification](../../specification/find.md). This is a design review. No SQL function, installed artifact or paid proof exists.

Check the recommendation as an outward contract, not as implemented source. Each host receives an ordered collection in one scalar call and delegates once to public `Engine::find_with`. SQLite takes JSON text, PostgreSQL `text[]`, DuckDB `VARCHAR[]`; their proposed result types are JSON text, `jsonb`, and a typed `STRUCT`. All report zero-based selected index, original value, selected probability and ordered per-candidate probabilities, including a null-index none candidate. The result itself stays non-null when the model selects none; a top-level SQL NULL or valid empty set returns SQL NULL. Verify duplicate values cannot lose the selected original index: the private `Indexed` type implements `Evidence`, so public `Found::selected()` returns that index and `candidates()` supplies every probability. No new public Rust accessor or second request is needed.

Check source-known limitations before recommending the syntax. `Question::from_json` has no find verb, so the proposed argument is plain question text and `none` is a separate boolean (SQLite integer 0/1); `@` is literal, with no new file read or per-question model/profile promise. The conformance case JSON is runner input, not a legal SQL question argument. Inspect the three existing question constructors and worker paths; top-level NULL short-circuits before transport, inner NULL refuses, and wrong types fail at the appropriate bind or dynamic edge. The caller must explicitly order `json_group_array`, `array_agg` or `list`; no warm or aggregate-combine encounter order is accepted. Confirm the pinned SQLite 3.50.0 ordered JSON aggregate spelling with the installed host during implementation; the pinned DuckDB v1.5.5 read-only query and PostgreSQL repository example already support their stated ordered constructors. Review one-unit/over-cap and 16 MiB byte handling, real tie and none tie mapping, and no partial winner on error.

Trace authority and lifetime: SQLite `worker::run` checks process total, connection `thinkthen_budget_ms`, optional fourth-argument deadline and interrupt; PostgreSQL `call::read/run` fixes backend settings and `thinkthen.deadline_ms`, then polls statement cancellation on its backend thread; DuckDB C++ `StatementOwner::Remaining`, caller-session settings and folder probes feed one bridge worker with `StopFor`. The three older DuckDB C API packages require their own implementation and installed proof; Linux C++ alone is a stage. No B12a/0222 proposed method is a dependency. Host error-kind tables, cache/replay identities and actual attempt reservations remain unchanged.

Inspect the installed proof route: shared cases 18/19 currently skip in SQLite `tests/conformance.py`, PostgreSQL `tests/runner.py`, and DuckDB `tools/conformance.py`. The shared loopback backend already accepts `capture`, returns exact UTF-8 bodies and keeps at most three bodies of 96,000 bytes; `arms.rs::capturing` currently permits only relation cases 42–50, so extend it to 18/19. Use `/case/ID/capture/v1` in each selected host. SQLite's runner can reuse `tests/helper.py::Backend.capture`; PostgreSQL needs a bounded fd-7 capture reader beside `runtime.sh::bcount` and selected verification through `check.sh`/`tests/runner.py`; DuckDB needs a small `tools/harness.py::Backend.capture` using `_say/_line` and a selected assertion in installed `tools/conformance.py`. These helpers observe the backend; no product test hook or second listener is needed. Each host must check the one **observed** complete body against the independent corpus request, calculate its digest from captured bytes and actual served URL, and compare with the digest independently expected from the corpus body and served URL. SQL result fields cannot observe a request digest. Also assert one listener send, selected original value/index, and candidate probabilities. An empty/duplicate/tie/invalid table adds only distinct boundaries and counts zero sends where required. The installed PostgreSQL package must contain generated overload SQL; DuckDB installed mode invokes conformance but not the full verbs suite, so a new extra case needs explicit selected installed routing. Reuse existing held-cancel and expired-budget helpers; no broad matrix, stress, load or provider run.

The first review's positive-budget sleep suggestion rested on a mistaken rejection premise. `databases/sqlite/src/budget.rs::register` accepts `thinkthen_budget_ms(0)` and makes the connection deadline immediate; `tests/test_try_budget.py::test_zero_budget_sends_nothing_and_is_connection_owned` observes its no-send result. `thinkthen_max_requests_total(0)` is a different, refused request-total control. The corrected proof retains the direct zero-budget case; please withdraw the positive-sleep requirement. This preserves existing setting semantics and avoids timing sensitivity.

Review questions: Is the proposed native result shape and optional `none` position faithful and practical for all three hosts? Does SQLite's pinned aggregate syntax preserve array order in the installed binary? Can every adapter retain an inner NULL to reject it rather than dropping that unit? Are the default/explicit deadline signatures unambiguous at binding? Does the private indexed wrapper really avoid an unnecessary public Rust change? Flag any new outward choice for Ian **after** technical review. If the proposed signatures survive review, Ian may approve or overturn them. The review does not authorize runtime, close the issue or claim three-platform DuckDB completion.

## What preparation taught us

A source-level parser trace changed the design from a tempting JSON find question to plain text plus `none`: the public question-file parser cannot construct find. The public `Found` type also lacks an index getter, but generic `Evidence` can carry a position, so an additive Rust API is unnecessary. The existing DuckDB warm set sorts, PostgreSQL array bulk deduplicates, and the older DuckDB C API list reader treats NULL children specially. The implementation brief must keep those paths separate from find's ordered, duplicate-preserving input. First review caught an omitted observation path: pinned corpus bytes are an expectation, while actual sent bytes require the shared backend capture and host runner plumbing. It also exposed ambiguous budget wording; source and an existing no-send test establish that SQLite's connection budget accepts zero. The next build/review should check whether this avoided parser, ordering and proof-route rework.
