## Register 45: ordered-output stall

Local register `experiments/284-issue-register/45-d10-ordered-output-stalls.md` cites the pre-0155 architectural experiment's 3-second retry hold and 4-second reply hold. The ordering mechanism remains: `engine/schedule.rs::Run::{waiting,drain}` emits only the next ordered completion. Current batching makes an ordered window hold batches, potentially many records each. `specification/records.md` already promised a bounded buffer and `rank.md` already said rank waits for all input, but neither told a reader that a slow earliest request can stop visible output. For streaming output, `Run::waiting(false)` counts dispatched work not yet emitted, so a full `jobs` window also stops dispatch. `rank` uses the held-output mode from `cli/schedule.rs`; `Run::waiting(true)` counts only in-flight work and later completions can free dispatch slots. The corrected page separates these modes. The first draft overlooked this scheduler distinction; that was a guidance mistake, not a runtime defect.

Do not copy the old experiment's 93/150-second arithmetic. It assumed two retries and independent per-record waits. Current `specification/backends.md` and `engine/http.rs` have a default of three retries, a process gate for an exact posting URL, a minimum one-second wait for zero retry headers, a per-attempt timeout, and no whole-command deadline. An arbitrary finite wall bound would also miss waiting on a pre-existing process gate or a held output/usage path. The page names the actual boundary without promising a single worst-case run duration. Current `--facts` in `specification/result.md` contains final totals and stopped metadata; it has no live waiting-record identity. Register 45's separate success criterion that facts name the record being waited on remains outstanding. **Disposition proposed: partial; leave row 45 open for that requirement or explicitly narrow its criterion after review.**
