## Handoff constraints and lessons

- `requests_sent` is actual transport attempts including retries; it is not provider usage or completion count. `SendBudget` reservations can refund before marking. `Facts.records` counts finished ordered input, including filtered rows; optional token fields mean *unknown* when absent, not zero. A failure remains a failure, never `false` or `null`.
- Keep lifetimes explicit: `--jobs` and backoff are in-process; SQL totals are SQLite/DuckDB process or PostgreSQL backend; `Call.facts` is one call; CLI `--facts` is one run; `status` reads a durable command usage store. Neither a session setting nor a per-call budget implies an account-wide ceiling.
- The first useful build slice is a bounded carrier/criterion decision for register 61, 45 and the facts issue's remaining ask 1, then durable `status` accounting if root selects Option 1. Backend timing, price, dry-run estimate and shared pacing need their distinct prerequisites. No new design is made in this note.
- Preparation friction to avoid: read the final transport ordering before naming a send exact; inspect each host's input domain and public carrier rather than cloning another host's test; compare current source and accepted branch before repeating an old issue's negative claim; map every original acceptance clause to a real proof. This note specifically corrects the old facts audit's claims that DuckDB details and conformance fields are still missing, and the old status issue's assertion of three active SQL cap leaks.
