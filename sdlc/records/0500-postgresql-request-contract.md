# PostgreSQL request conversion

The adapter starts from `ee9b233f8`. PostgreSQL reads saved questions on the backend thread through its existing role, descriptor, regular-file, link, size and confinement checks. A typed Request receives the admitted definition and caller-owned evidence. PostgreSQL keeps its SQL key, row-id and NULL projections. Evidence paths remain the native client-reader workaround.

## Complete bridge

The PostgreSQL complete adapter includes the reviewed shared SQL Request bridge and calls its admission and execution functions directly. Backend-thread saved-question checks remain before worker execution. The existing `Inputs::parse(inputs, false)` authority guard refuses server evidence and image paths before `Inputs::parse_request` enables deferred native readers; this reuses the existing rule and performs an extra parse without widening file access. A future shared parser parameter can remove that extra parse after review.

The installed PostgreSQL cases extend the existing complete-call boundary with eager declaration failure at record two, incremental malformed-image prefixes, annotation selection before schema checks, retained false filter observations and original ordinals, and zero-send descriptor and server-file refusals. They reuse the installed typed SQL child checks and counted owned loopback helper. The full shared parity and owning-facts checks remain in the same gate.

## Shared legacy result conversion

Complete atomic results retain `core::result::complete::Atomic::legacy`, a native `DecisionResult`. That carrier owns the question, threshold, primitive value, probabilities, nearest level and metadata. `public/complete/records.rs` deliberately supplies no input when it constructs the atomic carrier; the enclosing `CompleteRecord` owns the original. Converting only the atomic result cannot reproduce a legacy record document.

Keep `CompleteDecision`, `CompleteChoice`, `CompleteTags` and `CompleteScore::legacy_details(&self) -> Result<Details, Error>` for the input-free projection. Add `CompleteRecord<T, R>::legacy_details(&self) -> Result<Details, Error>` for each of those four result types with `T: Serialize`. The record method serializes its actual original using the same native JSON materialization as `Details::of_member`, inserts the retained record into a clone of the existing `DecisionResult`, and invokes that carrier's result/1 serializer. It also keeps the input-free serialized carrier in `Details::scalar_json`, so `to_json()` retains the original and `to_scalar_json()` omits it. Neither method reexecutes the judgment or changes its identity.

One private Details constructor consumes the complete atomic carrier plus its existing metadata and identity views, with an optional serialized original. It derives the question, threshold, profile warning and nearest level from the retained native fields. It fills sources and observations from the existing identity and uses one narrow internal `DecisionResult::cached(&self) -> bool` accessor in `core/result.rs` for the actual legacy flag. The accessor lives beside the DecisionResult carrier, where the private metadata field is reachable; it does not expose a Meta field through the public metadata view. It must not infer that flag from result/2 provenance, because a result with no question sources can still retain its actual legacy cache state. Existing `Written` wrappers hold both serialized documents and retain their withheld Debug behavior. `Details` Debug in `public/results/member.rs` currently prints authored choice, tag and score replacement labels through value, probabilities and nearest. The same implementation must withhold those three fields for both existing and converted Details. Keep count and identity diagnostics and the existing withheld JSON and URL fields. PostgreSQL adds no result/1 serializer.

`CompleteAnnotated::value_json(&self) -> Result<String, Error>` borrows `canonical.legacy` through a narrow internal `AnnotateResult::value()` accessor and serializes that existing `NamedValues` carrier. The returned String owns its bytes. The existing serializer preserves authored member order, primitive successful values, primitive abstention null and failed-member markers. The complete annotation legacy carrier stores primitive `answer.read()` values. Its projection preserves exact current `annotate_with().value_json()` semantics and does not apply authored structured readings or treat an authored null reading as a new annotation result meaning. Broader authored annotation meanings require a separate reviewed outcome. Recognition and relation complete carriers already expose their native actionable values.

### Scalar metadata contract

Request executes atomic inputs through native record batching. Its scalar projection retains the resulting `batch_setting`, any `batch_warning` and any `context_sha256`; it does not erase actual execution metadata to imitate ordinary `details_with`. Therefore the equivalence oracle is the corresponding native batch member, including its scalar projection, rather than the non-batch `details_with` document.

For PostgreSQL details and try-details, context-free single-text calls use the atomic input-free conversion. This keeps their input-free result/1 shape while adding actual native batch metadata. Calls with shared context retain the existing record document shape through the record-aware conversion, including their original input and actual context metadata. Images use the input-free scalar projection. The SQL primitive values, NULL behavior, probability tables, request keys, question content, errors and model selection remain unchanged. Fresh review must accept this explicit metadata change; the design makes no promise of identical JSON to a non-batch scalar call.

### Proposed source claim

The shared implementation claim is limited to `crates/thinkthen/src/public/results.rs` for registering the conversion module, `crates/thinkthen/src/public/results/legacy.rs` for the private constructor and four atomic and four record methods, `crates/thinkthen/src/public/results/complete_annotation.rs` for the annotation projection, `crates/thinkthen/src/public/results/member.rs` for withholding sensitive Details Debug fields, and `crates/thinkthen/src/core/result.rs` for the internal DecisionResult cached and annotation-value accessors. Regression cases belong in `crates/thinkthen/tests/request_legacy_projection.rs`, using the existing isolated engine and counted loopback helpers; `sdlc/ratchet.json` records the resulting measured source ceiling. No executor, admission, scheduler, schema or generated binding implementation changes belong to this seam. PostgreSQL changes remain in `databases/postgresql/**`; this record remains the sole design and lessons document.

### Exact regression cases

For each of decide, choose, tag and score, compare Request's atomic conversion with the input-free projection of the corresponding native batch member. Compare the record-aware conversion's `to_json()` with that member's full record document and compare its `to_scalar_json()` with the member's scalar document. Retain identical fake route, model, batch and recorded responses. The record table includes a string original, an object original selected through authored `on`, two identical evidence texts with different originals, and a JSON original containing false and null. Verify the original survives full conversion and is absent from scalar conversion.

Additional atomic cases cover described true/false readings with explicit authored null, a banded decision, unsure decide and choose null, shared context, a profile warning, absent usage and partial reported usage, live/cache/replay metadata, sources and observations. Pin batch and context fields to the matching native batch projection, including context-free calls, rather than normalizing them away. Compare actual cached flags, including a native carrier with no question sources. Serialization of a caller original retains `Details::of_member`'s error classification; internal carrier serialization remains Defect and never produces a successful value.

Annotation cases compare existing `annotate_with().value_json()` with the new complete projection for successful primitive members, primitive abstention null, failed named members and authored member order. Include described decide members with authored structured and null readings and pin their existing primitive annotation output; the conversion must not introduce authored meaning semantics. Debug regressions test both existing and converted Details with sensitive replacement labels for choose, tag and score. Assert that value, probability names and nearest never expose those labels. Also test sensitive originals, source URLs and both serialized documents through the existing withheld wrappers. Installed PostgreSQL cases retain scalar, table, details and try-details outputs and count exact loopback sends, including zero-send refusals and cache/replay reuse.

## Diagnostic planning

The coordinator ruled that `thinkthen_plan` retains the existing shared `Engine::plan_with` diagnostic implementation. Planning makes no judgment and sends nothing. Its existing admission, saved-file authority and estimate output remain the contract. The adapter adds no planner or copied estimate logic. Existing planning checks count loopback requests to retain zero sends.

## Lessons

Native batch equivalence needs matching execution controls. Complete carriers retain opt-in attempt receipts; the old `Details::of_batch_member` document omits them. Exact document fixtures use ordinary attempt controls and retain actual batch/context metadata. The conversion preserves any attempts already present in its retained native carrier.

The default max-batch tag fixture exposed another native difference: the legacy batch details emit a `batch_warning` tuned for one record, while the complete-record carrier omits that warning. The conversion must not invent a warning. The exact four-function equivalence fixture explicitly selects batch one; the max-batch discrepancy needs a shared native ruling or fix. Its source is `public/complete/records.rs` passing the composed question into `batch_run` rather than rebuilding metadata in the compatibility adapter.

Annotation input framing remains native. Valid JSON documents must use `QuestionInput::annotation_document` before typed Request composition, so authored member selectors operate on structured originals. A literal-text Request item would lose that behavior. The existing installed missing-member case exercises the retained distinction.

The new native fixture initially used invalid tag grammar and a non-RFC-6901 selector; native admission refused both. A score fixture also assumed object wire criteria, but the native score route sends an array. The loopback response now handles both criteria shapes. The first unit fixture attempted private probability and identity construction from the result adapter; the core result test uses the existing identity constructor in its permitted scope. These setup failures supplied no product parity evidence.

Complete find originals are `QuestionInput`, which implements `InputEvidence` rather than `Evidence`. Typed composition retains supplied literal text in `RecordEvidence::original()`. The installed duplicate/tie find cases caught a projection that assumed the original remained the bare Text variant. The SQL text-array projection must read the retained literal and use the typed selection index; it must not restore a separate index-bearing evidence wrapper.

The installed rank refusal case caught an error-wording difference before sending: shared Request admission says `the evidence is empty or blank`, while the SQL legacy contract says `evidence is text, not white space`. The coordinator ruled that PostgreSQL adopts the shared Request sentence as the intentional 0.2 migration. The SQL assertion retains Usage classification, zero sends and secrecy. PostgreSQL adds no whitespace validator.

PostgreSQL imports SQLite source through `#[path]`, so Cargo formatting follows those shared modules. Formatting a PostgreSQL file can dirty shared SQLite source, and restoring that incidental diff exposes baseline formatting drift in the PostgreSQL gate. The reviewed SQLite dependency owns that correction. Keep the existing formatter and rerun the affected installed cases after integration; changing a running shell script invalidates that run.
