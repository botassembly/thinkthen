## Questions for the reviewer

1. **Public shape.** Ian ruled that every library result carries facts without another request. Is proposed ADR 0089's `Call<T>` for eager calls plus final `Batch::facts()` for lazy calls a coherent narrow amendment to ADR 0017? Does `Error::facts()` for post-start failures preserve the six exhaustive error kinds and usable failure data? A public `Call<T>` changes existing Rust signatures and downstream adapter compilation; an additive optional method on old bare values cannot satisfy the ruling. If the proposed shape is wrong, name one concrete replacement before runtime work. ADR 0089 must not restate ADR 0048/0056/0083.
2. **Details and bounded streaming.** The run-facts issue also asks for probabilities, confidence and request digests on every verb. `Details` currently covers single decide/choose/tag/score, while `filter` suppresses rows and `Batch` streams. Decide whether per-row details ride emitted rows, a bounded side channel, or another reviewed shape. No design should claim full gap closure while holding an unbounded hidden-row history or making a second paid call.
3. **Real batch adapter.** `core::Batcher` already owns the exact body and digest, while `public/bulk.rs` presently calls `judge` per record and `public/batch.rs` schedules one item at a time. Does the proposed bridge through `facade::ask_batch` retain lazy input, ordered rows, duplicate sharing, partial answers, cancellation and a joined worker on error/drop? `rank` may keep its whole input; `annotate` must keep `on` groups and partial failures. Do not conflate a copied 0172 command test with a Rust consumer proof.
4. **Scope and dependencies.** Confirm that the 0172 context parent and public result files, 0149/0157 facade/usage/settings files, and all root free-function and adapter consumers are in the prospective claim inventory. Runtime edits to held files wait final landed source or exact released claims; a nonoverlapping first Rust slice need not wait on 0201/0149/0157 as new semantic prerequisites. The plan's statement that B12a “closes” register 19/78 is shorthand for the Rust piece: those findings describe other languages too, so item closure needs the later B12b–B13e evidence or an explicit coordinator scope ruling.
5. **Identity and proof.** Is the pinned compact JSON/SHA-256/first-eight-big-endian/mod-4096 statement precise enough for register 64 and a future cross-language fixture? Does the proposed public loopback table distinguish one full batch, `batch 1` byte compatibility, typed choose null vs Backend failure, per-call facts under retry and a later context overflow, with no paid or load run?

The coordinator can settle routine implementation ordering, whether the first red case is `decide_many` or `filter`, and a measured source-growth amendment after exact claims. A new public return representation, an unbounded detail store, a different first-error rule or a changed register-closure meaning needs a reviewed design decision. The user may overturn the recorded batching and facts rulings through their owning records. This draft asks no new configuration question and changes no accepted ticket.

## What this preparation changed

The source map found that current Rust `Question::from_json` drops `batch`, the public bulk adapter never calls `core::Batcher`, and the command's facts snapshot belongs to process counters. It also exposed tight parent headroom before proposing a source claim. These findings should save the builder from adding a second planner, estimating from aggregate space alone, or reporting concurrent process deltas as exact call facts. Evaluate them after the eventual build: count which paths needed no rediscovery and record any missed constructor, copied adapter or boundary proof in the ticket's final lessons.
