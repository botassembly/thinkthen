## Findings

1. **Batch interrupts are not prompt on main's engine.** 0073 says a cancelled call "lets already-started work finish" and "returns only after every engine-owned worker joins". 0085 keeps that rule. 0095's interrupt check fires the call's token, and "sent attempts finish". A SIGINT during a held `decide_many_with`, `annotate_with`, or `relate_with` call therefore returns only after release, or after the 30 s attempt timeout. Several claims fail as written. R4-22 says four held queries each stop "within 100 ms of the signal". R5-23 says a SIGINT stops a held batch within 100 ms. Case 23 uses the held arm and a SIGINT. The rule "every held test releases or cancels" cannot end a held batch by cancel alone. At the tag, R4-22 closed at 20 of 20. Keeping the batch path as designed reopens it.
   Fix, recommended: extend decision 5 to every engine call. Batch, annotate, and relate calls run on a spawned worker that owns the distinct texts as `Vec<String>`, a clone of the question, and an internal `CancelToken`. The worker builds its `Batch` there, since `Batch` is not `Send`. The DuckDB thread waits in 50 ms ticks on the decision 6 predicate. On a stop it cancels the token, detaches the worker, and raises `cancelled`. Test and plant: hold a 64-text batch at width 8, send SIGINT once `count` reads 8, and assert `cancelled` within 100 ms. Then release and assert the count stays at 8. Plant: call the engine on the DuckDB thread. The 100 ms assertion turns red. Every held test then ends with an explicit release.
   Fallback: keep the engine call on the DuckDB thread. Each 100 ms assertion is then measured from release. The table marks R4-22 and R5-23 as changed, states the 30 s worst case, and names the worker as Ian's lever.
2. **Split the ticket in two.** It carries 49 rows, 4,300 production lines, and 26 test files. 0105 split at about 1,200 lines "for review size". `connections.rs` and `relate.rs` hold 2,138 of the tag's 4,457 production lines. Relate forms a clean seam.
   - 0110, the extension core: scalars, questions and `@file`, SIGINT and the predicate, warm, usage, details, recognize, relations, errors and guard, `check.sh`, deny, lints, and conformance. It carries R1-1, R1-15, R2-3, R2-18, R1-21, R2-14, R3-13, R6-6, R5-21, R7-7, R2-22, R3-11, R4-16, R5-23, R5-24, R5-25, and every cross-surface and engine half.
   - 0111, relate on the caller's database: connections, registry, identity probe, reaper, relate guard, relate from rows, the queue-wait message, and cases 51 and 52. It carries R1-16, R2-13, R2-2, R3-7, R2-6, R3-1, R3-6, R4-3, R4-4, R4-5, R5-26, R3-23, R3-12, R5-22, and R6-5.
   - R4-22 splits: the scalar half stays in 0110, and the relate half moves to 0111. The bridge thread that interrupts relate connections moves to 0111.
   Each ticket gets its own budget and red-green record.
3. **The deny plant turns red for the wrong reason.** Observed: a crate with a `file://` git dependency fails under `--offline` inside `cargo metadata` ("can't checkout … you are in the offline mode"). cargo-deny never reaches `[sources] unknown-git`. Any broken manifest would give the same red. Fix: plant the removal of one license exception. `licenses` then fails and names `foldhash`, and the test pins that diagnostic. If a sources plant stays, pin deny's own `sources` message so a metadata failure cannot pass as red. The accepted 0105 has the same plant. Give its builder a note.
4. **The license exception reasoning needs correcting.** `arrow` and `hashlink` are unconditional dependencies of `duckdb` 1.10505.0, so dropping `vscalar-arrow` removes none of the three crates. Also, `recognize.rs` and `relations.rs` use `duckdb::vtab::arrow::WritableVector`. `tiny-keccak` arrives through `ahash`, `const-random`, and the proc macro `const-random-macro`, under `arrow-array`, not `arrow-select`. It runs only at build time. `zlib-rs` arrives through `flate2` and `zip` in `libduckdb-sys`'s build dependencies, also build time only. Only `foldhash` links into the shipped extension. Fix: say that all three exceptions are forced by `duckdb` and `libduckdb-sys` 1.10505.0. Name the two build-time-only crates. State that Zlib requires no notice in a binary. Drop the `vscalar-arrow` lever.
5. **Some plants cannot turn red or cover only part of a row.**
   - R6-7: the check runs `cd "$HERE"` first, so reading `tools/version.env` by a relative path afterwards still works from `/`. Plant a relative read before the `cd`, or a second read of `$0` after it, as at the tag's bug.
   - R3-29: "Add an unpinned `packaging` line. Setup still passes, and its refusal test turns red" contradicts itself. Plant: drop the `==` check. Setup then accepts an unpinned line, and the refusal test turns red. Name the requirements file setup reads.
   - R5-31: the lookup-miss refusal has no plant. Add one: fall through on a lookup miss, and the case runs.
   - R6-2: add a row. Point `THINKTHEN_DUCKDB_CLI` at a missing file, and the rung prints "not run". Plant: report "pass" on a missing CLI.
   - R2-22 and R4-16 each join several assertions under one plant. Give each assertion its own plant or mark it as covered elsewhere. R4-16's logical-type grep may not fit typed wrappers. Say what replaces it.
6. **The library name, the artifact, and the entry point are unnamed.** The tag's package is `thinkthen`, and it builds `libthinkthen.so`. A crate `thinkthen-duckdb` that depends on `thinkthen` cannot keep a lib named `thinkthen`. ADR 0047 item 6 renamed the C lib for the same reason. The tag's entry point is a hand-written `#[unsafe(no_mangle)] thinkthen_init_c_api`, not the macro the ticket names. Fix: name the lib `thinkthen_duckdb`. Keep the hand-written entry point in `src/ffi/`. State the metadata call that replaces the Makefile: `-n thinkthen`, `-dv v1.5.5`, and `--abi-type C_STRUCT_UNSTABLE`. It must give `thinkthen.duckdb_extension` from `libthinkthen_duckdb.so`. Cite the 2026-09-21 stable-C-API issue for the unstable ABI.
7. **Test-only builds need a shipped-build check.** R7-7 adds a `test-hooks` feature. R4-5's retire hook and R3-1's forced reaper pass also need hooks. R1-10 needs `test-panic`. The ticket checks only the `ENGINE_TEST_PANIC` string. Fix: put every hook behind one test feature. `check.sh` proves the shipped extension has no hook symbol or string. Plant: enable the feature by default.
