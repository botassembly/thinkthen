## Findings

1. **The cross-surface count is wrong, one row is missing, and one row lacks its own plant.** The ticket says "fourteen cross-surface rows". The table carries halves of 19 distinct rows from other surfaces: R2-24, R2-10, R1-10, R1-31, R2-31, R2-32, R3-29, R4-19, R5-34, R3-30, R5-29, R5-30, R5-32, R1-28, R3-28, R1-30, R3-31, R3-32 and R4-10. It also retires R1-29 and R5-36, sends R1-11 to 0086, and answers R2-29 in prose. R5-37 (Mac recipe, `sed -i`, Linux-only tools) shares probe `t7d/R3-32_R4-10_R5-37.sh` with R3-32 and is not named. R5-30 (case 17 excused by a note substring) has no plant of its own. "Skip case 40 silently" tests the sum check. It does not test an excuse that matches note text. Fix: state the real count. Name R5-37 beside "the `package.sh` halves move with `package.sh`". Add a plant for R5-30: excuse a wrong answer whose note matches a substring, and the fail count turns red. In the R3-32 row, say that the Linux-only guard allows bare `timeout`, because the wave-7 probe named bare `timeout` in `check.sh`.

2. **The relate row cap departs from ADR 0047 item 9 without saying so.** ADR 0047 item 9 and 0095 Q14 say the 255 cap counts unique pairs. Decision 10 refuses a 256th row. Ticket 0110 makes the same choice and states it: "This row cap is stricter than the engine's unique-pair cap, and the README says so." Fix: add that sentence and the README line, or count unique pairs after the dedupe.

3. **The key refusal must happen at call time.** Other Settings acceptance says "`SET thinkthen.api_key` gives 22023". The tag lets the `SET` succeed and refuses on the next call (`unwired_key_refusal`). A refusal inside `SET` would be an ERROR on that statement. PostgreSQL then writes `STATEMENT: SET thinkthen.api_key = '…'` to the server log under the default `log_min_error_statement`. That line leaks the key the secrecy test checks for. A string check hook without its own `GUC_check_errmsg` also echoes the value. Fix: acceptance reads "a call after `SET thinkthen.api_key` gives 22023". Keep the tag's call-time rule, and have the log test assert that no `STATEMENT:` line carries the value.

4. **The ADR 0043 amendment is sound in mechanism and keeps the ADR's intent. It needs four additions.**
   - Sound: the worker never calls into PostgreSQL. It owns a copy of every input, and a cancelled internal token stops retries. The deadline stays the budget. Blocking signals before the spawn keeps PostgreSQL's handlers on the backend thread. `postgres.md` line 84 asks for this behavior. ADR 0043 does not record the rule as Ian's (record 0070 names no ruling by him), and its text says Ian can overturn it. The owner may therefore amend it and say Ian can overturn the amendment.
   - (a) The mask covers single rows only. Array decide, warm and relate run on the backend thread with its signals unblocked, so any worker the engine spawns during those calls inherits an open mask. The same happens when `default_engine()` is first built on the backend thread. A process-directed SIGINT or SIGALRM can then run PostgreSQL's handler on an engine thread. Fix: pick one rule and record it. Either route every engine call through the masked spawn, or write down why PostgreSQL 16's cancel, alarm and procsignal handlers are safe on another thread. Name the test that covers the rule.
   - (b) pgrx `GucSetting::get` panics off the backend thread, as the tag's comment at `lib.rs` around line 220 says. State that the deadline and every other setting are read before the spawn.
   - (c) Carry ADR 0043's honesty sentence into the amendment. A cancel returns control, but a send already on the wire still completes and is billed. Its answer lands in the cache. Each detached send holds one width permit until the request timeout at most, so repeated cancels can fill the width. Give that bound.
   - (d) The ADR's title and decision say "not cancel" and "stays deadline-only". Update the status line so a reader sees the amendment first.

5. **pgrx lint variances will predictably stop the build.** The root table forbids `unexpected_cfgs` with only `thinkthen_internal_doctest` allowed. It also forbids `unreachable_pub` and `missing_debug_implementations`. `pgrx_embed!` needs `cfg(pgrx_embed)`, and `#[pg_extern]` and `pg_module_magic!` emit `pub` wrappers. A local `allow` cannot lift a forbid. Fix: before code, run the root lint table against the tag's crate as a design probe on Beelink, since that crate already checks in 69 s. Put any needed ADR 0047 variance, such as extra check-cfg names, into this ticket's ADR 0047 section, with a `policy.py` accepted copy. This avoids a mid-build stop.

6. **The check plan is sound and safe. Four gaps remain.** It starts no visible service: no TCP port, a 0700 `mktemp` socket folder, no root, no systemd, no container, and a stop trap. No written rule requires authorization for the one-time fetch. The workspace `CLAUDE.md` names production or licensed data, paid services, visible services, external state and deletions. The repo's `AGENTS.md` bars network in a gate, and `runtime.sh` never fetches; it reports "not run" with the command. The deb comes through apt's signed metadata with a pinned SHA256. Fixes:
   - (a) Pin the version in the command: `apt-get download postgresql-16=16.15-0ubuntu0.24.04.1`. Without it, a later security release fetches 16.16 and fails the hash.
   - (b) An unattended upgrade can move `postgresql-server-dev-16` past 16.15. Have `runtime.sh` compare `pg_config --version` with `postgres -V`. Then either report "not run" on a mismatch, or accept minor drift in writing (PostgreSQL's magic block checks the major version only).
   - (c) The tag's `.gitignore` lacks `.runtime/`. List `/.runtime/` among the files the ticket changes. `ratchet.mjs` walks every folder with no ignore list, so `ratchet.py.json` rooted at the binding would also count `.runtime/` and `target/`. Point each config at folders the extraction and build never write, or prove the extracted tree holds no `.py`.
   - (d) A SIGKILL skips the trap and leaves a postmaster and the 0092 backends running. Use `timeout -k 10 900`, trap `EXIT INT TERM`, have the trap stop the 0092 backends too, and state the `initdb` auth method (trust behind the 0700 socket folder).

7. **The script budget does not add up.** The ticket's own numbers give 841 − 110 + 150 = 881, over the 850 cap. Fix: name what else leaves (the `saved_answer_kb` steps, and the 21 lines that drive the stub, `ENGINE_NULL` and `synthetic-partial`) with a count, or set the cap at 900. The other budgets are realistic. Production Rust at 1,450 compares with a measured 1,461. Rust tests at 450 compare with 366. `runner.py` at 330 compares with 329 and is tight, given a restart per case. Say it may shrink when rewritten onto `cases.json`.

8. **Two tests can end but may not turn red cleanly.**
   - R2-19 asserts 20,000 warm rows within 30 s under a `psql` `timeout 30`. A slow run then ends as a kill and never reaches the assertion. Give that step `timeout 60`.
   - The preload plant claims the server fails to start. Against the loopback backend, a decide in `_PG_init` may answer, and the server may then start. Make the preload test also assert exactly two counted sends after the two sessions, so it turns red either way. `pg_ctl -t 10` still bounds it.
   - Every other test ends: held tests end by a release, a cancel or a deadline, each `psql` call has a timeout, the whole check runs under `timeout 900`, and each held test gets its own backend.

9. **Smaller design gaps.**
   - Decision 9 does not say how scalar `choose` and `tag` get their answer. Following 0095 G5 and 0105 decision 8, they call `details` and read `value()` with no added send. Add that.
   - Decision 3 says environment-only "as ADR 0017 section 5 rules for databases". ADR 0017's table gives databases "the engine value's setting, then the same variable". Environment-only is this ticket's decision. Reword the sentence to say so.
   - Decision 4's README tells a reader to raise the 100 MB cap, but the binding has no setting for it. Name the way: the configuration file of the server's operating-system user (ADR 0017 section 5), or `thinkthen cache prune`.
   - The R2-19 row's "20,001st refuses naming the cap" refers to a warm cap no decision defines once the answer map leaves. Name that cap and its reason in decision 4.

10. **Writing.** Trailing "which" clauses: decision 6 ("`check_for_interrupts!()`, which raises…"), decision 9 ("Unicode scalar values, which PostgreSQL counts…"), option (b) ("`~/.pgrx/config.toml`, which other worktrees read"), and the `lint` line ("a git-sourced dependency, which `[sources] unknown-git = "deny"` refuses"). The R5-15 row has a contrastive appositive ("gives the one refusal, never the cap sentence"). Fix: split each into two sentences. Also correct "fourteen" per finding 1.

### Blocking

C1. **Settings at their defaults override the environment seed.**
- The problem: 0086 line 83 says `from_env` reads `cache_bytes` from the configuration file in the server user's XDG folder. Decision 3 gives `thinkthen.cache_bytes` a default of `100MB` and applies all four settings after the seed. An unset `cache_bytes` therefore overrides the configuration file that decision 4's old lever named.
- A second mismatch: PostgreSQL's `MB` is 1,048,576 bytes, so the default becomes 104,857,600. The engine's ruled default is 100,000,000 (`DEFAULT_CACHE_BYTES` in `cli/config.rs` on main). The ticket's own unit test (`'1MB'` → 1,048,576) fixes that unit.
- Fix: give `cache_bytes` and `max_requests` a default of -1, meaning "keep the seed", and call the setter only when the value is not -1. Add a test: with the setting unset and `cache_bytes` in a fixture configuration file under the server's `XDG_CONFIG_HOME`, the built engine carries the file's value. Width may stay an explicit 4, because the configuration file holds no width.

### Non-blocking

- The two writing slips that appeared since the review are contrastive appositives: ", never a hidden hook" in decision 1 and ", never the engine's address" in change 15. Split each into two sentences.
- **Exact header and server match, or "not run".** This is right. PostgreSQL 17.1 did break an extension-facing struct inside a major version, and a wrong-minor build could corrupt memory without any error. The cost is real, though. Beelink has `APT::Periodic::Unattended-Upgrade "1"` (observed; package lists do not refresh on their own). The 0093 rung reports "not run" without failing. So one `apt update` plus upgrade quietly turns a landed surface into "not run". Lever for the builder: also fetch `postgresql-server-dev-16` 16.15 into the toolchain folder with its own pinned hash, and build with that `pg_config`. Both halves would then be pinned and immune to system upgrades.
- **`unexpected_cfgs` at deny for `pg_module_magic!`.** This is right. pgrx 0.17.0's `pg_magic_func!` (`src/lib.rs`, around line 231 in the cargo registry) expands `#[allow(non_snake_case, unexpected_cfgs)]` inside the user crate, and a forbid refuses any such `allow` with E0453. Declaring the `pg13` to `pg18` features would not remove the attribute. Deny gives up one guarantee: a hand-written `#[allow(unexpected_cfgs)]` in `src` would now compile. Restore that guarantee mechanically with a `policy.py` step that refuses `unexpected_cfgs` inside any `allow` or `expect` in `databases/postgresql/src`.
- **The script cap, now 1,040.** It is realistic. The tag measures 841. The ticket claims 101 wire-suite lines and 31 `saved_answer_kb` lines. The review confirmed the 31 and found about 100 lines in the wire block. The itemized additions reach about 1,010. The soft spot is "line for line" for container calls. The stop-and-re-score rule covers an overrun. Production Rust at 1,500 is also realistic.
- **Superuser only.** This is right for `cache` and `cache_bytes`, because they choose where and how much the server's operating-system user writes. `file_directory` already follows that rule. It is right for `width`, because width sets the pace at the paid vendor for the whole server. For `max_requests`, it stops an ordinary role from tightening its own spend guard. That is acceptable at 0.1: `ALTER ROLE … SET` gives an administrator a per-role limit, and a session change would need an engine rebuild. Record the lever: a user-settable value that may only lower the limit, checked per call in the binding.
- **`SuBackend` and a lazily loaded library.** A value set in `postgresql.conf` at server start reaches a lazily loaded library. A value changed later by `pg_reload_conf()` does not. PostgreSQL ignores a SIGHUP-sourced `PGC_SU_BACKEND` value when `define_custom_variable` reapplies it in a running backend (`set_config_option_ext`, `IsUnderPostmaster && !is_reload`). The README should tell an administrator to restart the server, or to use `shared_preload_libraries`, after changing these settings. The tests restart the server per test and are unaffected.
- State what `thinkthen.max_requests = 0` does.

Checked against `2894e6bc`, the branch tip after `git fetch`. The reviewer is the same fresh, read-only session.

1. **The blocker C1 is fixed.** `cache_bytes` and `max_requests` now default to -1, and `cache` defaults to empty. Each of these defaults means "unset", and the binding calls no setter for an unset value. So `from_env`'s seed stands, including the configuration file's `cache_bytes` or the ruled 100,000,000 bytes. The ticket names the 104,857,600-byte trap.
2. **The test on the plan of setter calls can fail.**
   - The plant registers `cache_bytes` with a default of `100MB` and always applies it. The plan then holds `cache_bytes(104857600)`, and the test asserts no such call, so the test turns red.
   - Changing only the default, without the "always apply" part, also turns it red, because 104,857,600 is not -1.
   - `_PG_init` and the test read the same default constants, so a plant cannot move one without the other.
   - A gap remains, and it does not block. A bug in the function that applies the plan, such as one that ignores the plan and always calls `cache_bytes`, would pass this test. The environment-seed test of change 15 covers only the cache folder. A unit test could feed the apply function an empty plan and check that it calls no setter, through a fake or a counting stand-in for the builder. It would cost a few lines.
   - The reason for testing the plan holds. 0084's `EngineBuilder` has no getters, and 0086's settings seam is private (`cfg(test)`).
3. **`max_requests = 0` matches 0084 and ADR 0017.**
   - 0084 declares `max_requests(self, value: Option<usize>)` with no stated floor.
   - ADR 0017 section 5 says the limit "refuses a run before its first request when the input holds more than `N` records". So `Some(0)` refuses any call with one record or more, and nothing is sent.
   - The ticket also covers a possible 0086 refusal of `Some(0)` as `usage`, which maps to 22023 with zero sends. The two readings give the same outcome.
   - Main's engine has no `max_requests` code yet, so no code contradicts either reading.
4. **An explicit width of 4 still lets the environment be read, and it breaks no 0077 rule.**
   - `from_env` seeds only the address, key, cache folder, and configuration fields. 0062 line 31 says the configuration file carries no width, and 0086 line 88 says the seed leaves width omitted. So `width(4)` replaces nothing that the seed read.
   - 0086 line 94 describes the one 0077 conflict: two different explicit widths in one process. Each PostgreSQL backend is its own process and builds one engine for its whole life. A second copy of the library loaded through PL/Python has its own static values (ADR 0047 item 5).
   - Non-blocking: the port guide's type-map row (main, `surfaces-port-guide.md` line 181) says "Omitted width stays omitted (0077)". 0084 line 26 says an implicit engine never turns the command default into an explicit width. An explicit 4 departs from both, harmlessly. Record the departure in decision 3, or give `thinkthen.width` the same -1-means-unset default as its siblings. The second option also keeps the four settings to one rule.

### Notes (non-blocking)

State the 0 case, as the ticket now does for `max_requests`. Alternatively, set the setting's minimum so 0 cannot be chosen, with -1 still meaning unset.
