## Current route and observed gap

`.github/workflows/release.yml` still has only `workflow_dispatch`. `resolve` pins one checkout SHA. `build` has four native targets: Linux x86-64, Linux ARM64, Darwin ARM64 and Darwin x86-64. Both Linux jobs call `release-container` for C, SQLite, DuckDB, PostgreSQL, Python, TypeScript and Ruby inside digest-pinned manylinux 2.28 images, then pack command and first-run on the outer host. Both Darwin jobs run the old default `release-pack`. Later jobs verify four wheels/gems, assemble npm, and run installed `release-smoke` on four target hosts before `draft`. The draft job collects all platform files; release-mode outward jobs still require the `release` environment and first-step `RELEASE_ARMED=true`. The workflow does not request any of the eleven 0261–0265 source/managed wrapper parts. Current `release-smoke` already selects their installed checks if their files happen to be present, but its historical required-presence loop still requires only the original nine families. No missing wrapper currently fails that loop.

The Linux container source is `git archive HEAD` unpacked at `/work/src`. It has no `.git`. `release-pack` now assigns `source_commit=$(git -C "$REPO" rev-parse HEAD)` unconditionally near the top, before selecting parts. The current Linux container route therefore cannot reach even its old pack list from that archive. Its source-wrapper guard also calls `git status --porcelain`, so adding wrapper names alone would fail separately. This is a source-traced defect introduced after the accepted 0128 Phase 3a local route; no container reproduction or runner failure is claimed. A minimal legacy correction reads Git identity only for source wrappers. A controlled archive-source handoff is needed for any wrapper packaged in the container.

The C provenance cannot be repaired by packing new wrappers on the outer Ubuntu host with a second `release-pack c ...`: its C archive would be built outside the manylinux image and might require newer glibc symbols. The accepted local 0261–0266 wrapper manifests name the exact outer C archive hash, source SHA, target and version, and their pair preflight verifies that fixed data. They do not make a host C equal the container C. The container currently takes a single digest-pinned image for each Linux target, checksums fetched Rust/Node/Python/PG/OpenSSL inputs and builds with a pinned Rust toolchain. New SDK download/setup or an archive identity override is a real supply-chain and permission-sensitive boundary for High review.

## Smallest proof and risk

The first useful workflow slice repairs the gitless legacy route and adds Go/C++ only to the Linux x86 container invocation. `release-container` can create the tar once, compare Git's embedded tar commit identifier with its checkout HEAD, and pass that 40-hex value to `release-pack` only in an explicit archived-source mode. The ordinary checkout mode keeps its clean-tree rule. The new mode must not accept an arbitrary mismatched environment value or a reused/preexisting C. Both wrappers must name the container's C outer SHA and remain source-only. The x86 smoke setup needs Go, CMake, GCC/C++, Clang++, linker/ABI tools, Node/Python and offline Rust; the local 0261 versions are receipts, not a promise that `ubuntu-24.04` currently supplies them. Check or pin each runner prerequisite before adding a consumer that otherwise exits 77. Preserve the four-target old family rule and require the exact selected Go/C++ pair only on x86. Existing `release-go-cpp-pair`, installed selectors and `release-smoke` routing supply the behavioral oracle; no new language fixture framework is needed.

Because `draft` automatically collects every platform file after smoke, adding Go/C++ to the x86 platform artifact changes what a manual rehearsal draft and later release may expose. It is still governed by the current manual trigger and outward approvals, but fresh High release-safety review must inspect the exact source provenance, glibc floor, tool downloads, artifact presence rule, permissions and environment guards. No request here authorizes workflow dispatch, public draft creation, tag, registry upload or publication. If runner toolchain pins or the archive-source proof are not yet reviewable, land only a focused legacy gitless repair and return the unmet facts instead of weakening the release claim.
