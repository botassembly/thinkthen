## Current code and the first integration seam

At the initial `5261cb93` snapshot, `public/settings.rs::{from_env,max_request_bytes,build}` carried a positive request-byte setting into `Backend::with_request_size`; `engine/facade.rs::with_model` preserved it when a question selected a different model. `public/results.rs::Counters::retries` had landed. `public/options.rs::CallOptions` had the 0149 `SendBudget`, cancellation, deadline and interrupt controls, but no batch, context or observer. Main's `public/question.rs::Question::from_json` bound `(file, _batch)` and discarded the parsed question-file batch tier. Ticket 0203 had landed: `Question` carried `profile: Option<ProfileName>`, `from_json` copied `resolved.profile()`, and programmatic constructors left it absent. `public/set.rs::QuestionSetBuilder::question` refused a profiled member with the exact Usage sentence `a question set member takes no profile; name it on the set`. `Details::of` compared saved and running names, used the shared result writer's one digest for typed/JSON details, and exposed `profile_warning()`. Keep the saved name, warning, digest, `SendBudget` reservation, profile ceiling and retry count through the new return and batch paths. Ticket 0210 held `public/settings.rs` and `public/results.rs` then; it has landed, and the current handoff is below.

`public/bulk.rs::decisions` still forms one `worker.judge` closure per text and `public/batch.rs::start` schedules those records lazily through `facade::records`. `rank` collects before that path and sorts only after completion; `annotate` uses grouped work. `facade::ask_batch` already sends a `core::Batch` body/digest through recording, replay, cache, retry and transport. The missing bridge is mapping closed core batches and their member outcomes into the lazy ordered public stream without losing closed work on a later planner refusal. Reuse `core/batch.rs::{Batcher,Setting}` for fixed typed questions. Landed `core/batch/questions.rs::push_with_question` and `halves_with_questions` preserve complete per-row question identity for command choose/tag/score; they are not a new library parser or permission to deduplicate unlike options. Keep the record-byte content cut and B9's exact question identity separate. `cli/asking/batched.rs` is a near-cap command adapter, not a library adapter.

0220 added `engine/schedule.rs::RecordFlow::{Streaming,HeldAll,HeldWindowed}`. `public/batch.rs::schedule` explicitly passes `Streaming`, preserving the accepted lazy library boundary. For Streaming, `Run::waiting` counts dispatched minus ordered `next`. At worker completion, `Run::accept` halts further admission for an outer `Err` or a completed value with `stop: Some`; `Run::drain` then delivers pending results in order and records the first terminal cause. A recoverable 413 can be handled inside a split-aware worker adapter, but a fatal failure must remain an outer worker `Err`. Wrapping every result in `Ok` would let out-of-order fatal work appear successful for admission until ordered delivery catches up. Preserve the first-error stopping stream and joined final facts. This is an implementation boundary, not a change to the accepted contract.

`facade::ask_batch` sends one batch and does not perform 413 halving. The current split/halves path is `cli/asking/batched.rs::split_answered`, with `core/batch/questions.rs::halves_with_questions`; the library must share or provide a private split-aware adapter rather than assume `ask_batch` supplies it. One eligible refusal counts the refused send and the two half sends; it does not resend an isolation probe. Keep an actual fatal result visible to the scheduler while preserving ordered emission. The 0222 design's proposed dependency on such a shared adapter is not existing source behavior.

Attempt accounting has a precise seam. `engine/http.rs` acquires an open-gate permit, runs the host-aware stop check, prepares potentially blocking usage bookkeeping, checks the deadline without a host callback, reserves the send budget, then `PreparedAttempt::mark`s immediately before transport. A proposed per-call send observer belongs at that actual mark, after the final checks and reservation. It must see transport failures, 413 and retry attempts, while keeping the process counter and budget order. `engine/request.rs::ask_sent` handles replay/cache and live reply receipt; it calls `usage.cache_answer`, `usage.live_reply`, and `usage.answered_by` before returning success-only `Answered`. A call-scoped receipt observer there must also see received usage on a response that later fails decoding. `engine/usage/facts.rs::run_snapshot` is process-wide, so concurrent-call subtraction cannot provide 0212 facts. `engine/schedule.rs::Completed` counts ordered row completion; it cannot count sends. The accepted design's joined-later-reply facts need a call-scoped state shared by request workers and frozen only after their join and `Stop::finish`. This maps the existing boundaries; it does not claim the hook already exists.
