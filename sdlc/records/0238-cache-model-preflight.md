# 0238 cache model preflight

Status: design-only candidate from main `2b388453`, rechecked against main `299df9ef` after fresh High review of `4177184d`, 2026-09-28. No provider, broad build, runtime change, production cache edit or outcome closure. Ticket [0238](../tickets/0238-cache-model-freshness-and-refresh.md) and proposed ADR [0100](../planning/adr/0100-cache-model-freshness.md) are the review set. The reviewer found three missing boundaries: independent half replies inside one completion, a per-question public model override sharing the recorder, and a replacement failure after a complete live reply. This revision makes all three explicit; it does not claim design acceptance.

The current default is `jev-1.13.0` in `core/adapters/systemone.rs:35`; `jev-latest` remains an accepted explicit name. `core/recording.rs::Exchange::digest` hashes adapter, URL and exact request bytes; `Entry::replayed` checks the stored exchange, not today's alias target. `engine/recorder.rs::prepare_in` returns a valid answer-cache hit without a send. `engine/request.rs::ask_prepared` reads the key only for live work, decodes complete replies, counts actual live replies and avoids caching failed answers. The recorder already has a per-digest lock for misses or damaged entries and an atomic temporary-write path; valid hits currently bypass that lock and explicit record writes compare rather than replace. ADR 0020 makes explicit recordings immutable. A refresh implementation must deliberately add a cache-only valid-entry lock/replacement path; a generic record overwrite would violate that ruling.

`core/recording_identity.rs::Document` has only `schema` and `backend_sha256`. The pinned `02dc0b96` and `72d60786` readers deny unknown marker members, and the old writer creates its marker before an entry. The version-one entry envelope is shared by cache, record and replay. Thus a marker field or in-place schema bump is not a compatible freshness shortcut. No metadata-format change is proposed. Old executables can read the complete replacement entry but keep their old freshness behavior. Shared writable folders cannot promise a cross-process model snapshot.

`engine/facade/annotate.rs::check_model` already refuses differing models within one record. `crates/thinkthen/tests/backend/annotate/cache_versions.rs` supplies an old cached group and an edited live group; today it exits 4 with no stdout and three sends, proving the old/new artifact. Keep its true mixed-live refusal while changing the cache case. `cli/asking/batched.rs::split_answered` sends two half requests after a parent 413, then extends both `Judged` vectors into one `Completed<Vec<Judged>>`. A single model per completion would miss a left/right difference. `answer_rows` receives each actual `Answered.reply.model`; `row_of` can carry that model into each row. `schedule::Output::take` streams filter rows and buffers ranked rows in input order. Compare each row model there before using it; checking worker completion order would make the anchor nondeterministic. A parent 413 has no answer model but still counts as a send. `--top` does not make earlier model checks optional. Any already dispatched request remains counted, and previously printed filter rows cannot be retracted.

`public/engine.rs::for_model` may override one question's model; `engine/facade.rs::with_model` shares the recorder with the original engine. A recorder-wide alias bit captured at build time would be wrong in both directions. `PreparedRequest` stores exact body and digest, while the adjacent `Plan::model()` supplies that request's effective model at `engine/request.rs::ask_prepared`; select automatic alias refresh there and pass the decision into recorder preparation. A pinned engine with an alias question refreshes; an alias engine with a pinned question replays a valid pinned hit. This is a source-level finding, not a claim that the current code already refreshes either path.

The choice is a live requested exchange on every known-alias cache use, with a one-time pre-send cost warning. The effective model can come from `--model`, a question file or configuration; it is not identified by looking only at the raw CLI option. The explicit force-refresh flag must reject a disabled cache and must reach every CLI consumer of shared cache options. It is the smallest rule that does not pretend an offline entry reveals today's alias target. A first-live-then-matching-cache policy saves calls but adds an alias epoch and falsely assumes a stable target during the remainder of the run. A standalone probe adds an unrequested paid call and still cannot guarantee later target stability. A blanket alias-hit refusal leaves no refresh workflow. `--refresh-cache` is a narrow explicit control over the same path for pinned caches; it is not a new command. Offline replay never contacts the provider.

Small proof after acceptance: an isolated loopback fixture seeds a version-one alias entry, then sends the same requested group and an edited group under a new reported model. Check exact bodies, two planned sends, one warning, no old answer used, atomic replacement and unchanged marker. In a focused request/recorder test, inject `StorageStage::Install` **after** a complete live reply and file sync but **before** rename, then compare exact old entry bytes and the returned storage refusal. Reuse the real pinned old reader against a temporary successfully refreshed entry. In one small listener table, ordinary two replies test the run check, and a parent 413 plus left/right replies naming distinct models tests the split; assert three actual attempts with no retries, the filter's left prefix, the rank's empty output and exit 4. Preserve one truly mixed-live annotate refusal. In a public API test, override pinned engine to alias question and alias engine to pinned question; assert the refresh/send and hit counts respectively. This is not a provider or stress campaign.

Known limits: a live reply is the only observation of the alias target and may itself be misleading or change before another send. A crash between rename and directory sync leaves old-or-new complete durability uncertain. The writer cannot retroactively change an immutable old executable's behavior. Register 40's writable named-folder warning and register 105's recording vintage and refresh cadence remain separate. The older report's tuned-profile warning is already partly addressed by 0159 and is not redefined here. No separate material decision remains outside the delegated cache policy; fresh design review must still accept or return findings.
