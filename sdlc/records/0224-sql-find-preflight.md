## Current contract and reachable Rust path

`specification/find.md` requires one ordered set, 2–255 units (254 when offering none), generated IDs `u001` onward, original selected unit, no deduplication, first real unit on a real-only top tie, and none on a strict lead or any top tie with none. Empty CLI input is successful with no send. `conformance/cases.json` 18 has three units, selects index 1 at 0.8, and records body digest `6fda9be83c82dff3ec9e6f74a817e418e23c1dd9f76daa77a7ed180460b74654`; 19 has two units, selects none at 0.7, and records `910893767d4e6027d815c8a3b57eb4566015e0327b65ec2b0bb626ade3a280a5`. Both use one synthetic recorded exchange. At a loopback URL the digest changes; recompute it from the **pinned full body** and actual served URL, as the existing conformance runners do. Neither case can be represented by a per-row probability sort.

| `public/options.rs::CallOptions` and each binding's worker | A find uses one deadline/cancel/send-budget scope and actual attempt accounting. An empty SQL set short-circuits at its binding before `find_with`, because the public call itself rejects zero units. A failed call has no partial winner. |

The suggested SQL result preserves both selected probability and every candidate probability. `none` selected is a **non-null** SQL value with null index/value and a trailing candidate of null index; SQL NULL is reserved for a NULL top-level argument or valid empty set. `Found::selected()` on the index-bearing wrapper gives the chosen position directly. The count and combined text-byte caps must be checked before transport; whitespace-only evidence also follows `public::evidence`'s existing Usage rule. `Question::find` reads plain question text. `@` stays literal rather than opening a file; this follows CLI `find`, which takes a text question and has no file-question grammar. The model/profile come from the existing engine settings.

The proposal uses ordered collection constructors, not a custom `thinkthen_find(question, unit)` aggregate. SQLite warm already deduplicates by pair; PostgreSQL warm deduplicates and uses a text transition state; DuckDB warm sorts and combines. None is an index-preserving find planner. A new custom aggregate would need an explicit ordinal and merge semantics in every host; the scalar collection boundary keeps one public `find` call and makes ordering the caller's visible choice. PostgreSQL/DuckDB reject wrong SQL argument types at bind; SQLite's function checks dynamic types. Top-level SQL NULLs short-circuit; inner NULLs refuse before send.

## Preparation lessons and refresh trigger

The public results wrapper solves the duplicate-index gap without a new Rust surface. The file parser cannot parse find, so the SQL question is deliberately plain text and none is explicit; a future file feature would need its own accepted grammar. The DuckDB C API list reader's NULL-child behavior and PostgreSQL's existing array deduplication are reasons to trace adapters rather than infer order from an array type. Before runtime, refresh current main, the three accepted SQL batching branches and the 0222 decision; recheck host versions, generated SQL registration, source headroom and the exact installed case selector.
