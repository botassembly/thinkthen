# 0225 usage-lock source preflight

Status: read-only proposal on main `4e0505a9`; no runtime or settled page edited. The source still confirms register 31 in `$HOME/workspace/experiments/284-issue-register/31-unbounded-exit-wait-usage-lock.md`: `engine/usage.rs:235` takes the exclusive usage lock with blocking `File::lock`; `Counters::finish` at lines 93–99 waits on `Shared.changed` while the writer has pending or active work, and `Drop` at lines 140–152 joins the writer. A timeout only in finish would not free exit. The already closed 0163 page issue fixed documentation, not this runtime wait. `specification/recording.md:37` and accepted ADR 0049 item 3 explicitly describe the unlimited wait, so [proposed ADR 0097](../planning/adr/0097-bound-advisory-usage-lock-acquisition.md) is needed before changing the Settled page.

The queue's `pending` holds `(month, Counts)` deltas. `write_behind` takes all pending deltas, sets `writing`, calls `update` for each month, then clears `writing`, sets `failed` on any error, drops later pending deltas and notifies `finish`. `Counters::add` and `PreparedAttempt::mark` stop queuing new persistent counts once `failed` is set. `cli/mod.rs:111–114` already prints one fixed warning when `finish` reports failure, after the command result and before its final facts. `engine/usage.rs::read` has a separate shared lock for status; the proposed writer correction does not alter it. The paid live ledger is another subsystem and is out of scope.

A bounded design must let the **writer** abandon a contended lock so its join can complete. It can retain the current queue and `update` error path: poll `File::try_lock` at a short interval, and set one `Instant` deadline when finish begins; drop sets one when no finish occurred. Every remaining month acquisition sees that same deadline, then returns a local write error when it expires. `write_behind` already turns a failed update into `failed` and a cleared queue. A deadline in `finish` with no writer cooperation, or one new full allowance for every month, misses the outcome. Other filesystem calls may still block; this design bounds only foreign lock acquisition after finalization starts.

The 500-nonblank-line headrooms on this main are `engine/usage.rs` 483/17, `engine/usage/tests.rs` 295/205, `cli/mod.rs` 248/252, and `tests/backend/facts.rs` 431/69. A coherent `engine/usage/lock.rs` child keeps the near-full parent small. Existing `engine/usage/tests.rs::every_update_stage_warns_once_and_disables_later_persistence` pins failure suppression; the compiled `tests/backend/facts.rs` cases pin warning-before-facts and count-only status. One new held-lock command case should use a scratch `XDG_CACHE_HOME`, one loopback request and a holder that keeps `.lock` owned until the command exits. It should assert answer, exit, warning, facts, absent new month count, and zero paid-ledger interaction. A generous watchdog distinguishes the old indefinite wait without repeated timing or saturation. No runtime proof was run in this preflight.

## What the build taught us

Tracing cleanup was decisive: `Drop` joins the same writer after finish. The deadline must be visible to that writer and shared across its remaining month updates. Existing `failed` and `pending.clear` provide the count-loss and warning behavior; a second warning or detached background thread would complicate the contract. The later builder should check whether filesystem setup before `try_lock` alters the observed held-lock case and document the exact limit rather than claiming a total exit bound.
