## Current call path and authority

`libraries/typescript/index.js` builds a question JSON string with `specOf`/`specFrom`, separates the final options object in `splitLast`, and calls `native.call` through `invoke`. Its `CALL_KEYS` contain only `signal` and `deadlineMs`. `splitLast` treats `null` as an absent whole options object; explicit values for an allowed key remain present until `callOptions`, but `recognizeSpec` uses `inputs.kinds ?? []`, `relateSpec` uses `inputs[key] ?? []`, and `JSON.stringify` drops supplied `undefined` object fields. These are the actual missing-versus-null places to audit before extending options. A question created with `question(spec)` freezes a callable carrying serialized JSON; existing overloads accept strings, that question, or a spec object. Bare choose/tag/score text requires a last-object list; supplied specs carry their own labels. `index.d.ts` currently declares label fields as `readonly string[]`, so it rejects map descriptions even though the native version-one parser can accept maps. `RecognizeOptions.kinds` already allows a string-to-string-or-null object, but not structured descriptions. `QuestionSet` and annotate output unions already distinguish `null` and `FailedField`; score is numeric and `ThinkThenError.kind` has all six names.

`index.js` installs each `verbs` entry on `Engine.prototype` and on the module-level export. `index.mjs` explicitly reexports names. The asking routes are scalar `decide`, `choose`, `score`, `tag`, `details`; many-record `decide_many`, `filter`, `rank`, `annotate`; bounded `find`; and `recognize`, `relate`. `usage` is a counter read and `question` a local constructor. That is 12 asking method names for the ten semantic verbs; new `choose_many`, `score_many`, `tag_many` require additions to `verbs`, CJS/ESM exports, `Verbs`/`Engine`/module declarations and the export-name test. Their concrete argument order and result types are fixed in ticket 0236. `rank.top`, `find.none`, recognition kind/relation inputs and the last-object grammar must survive result wrapping. JavaScript retains original record arrays and remaps Rust indexes for `filter`, `rank` and `find`; the result wrapper must not replace those values with serialized Rust records.

`src/node.rs::call` clones the engine, owns `Call {op,spec,payload,deadline_ms}`, starts one worker and gives its envelope to a Node threadsafe callback. `src/door.rs::answer` creates only cancel and optional deadline call options; `run` currently unwraps eager `Call<T>` with `into_value`, drains lazy rows to bare arrays and discards `Batch::facts`. Its `engine` builder starts with `EngineBuilder::from_env`, so `decide_many_with`, `filter_with`, `rank_with` and `annotate_with` already inherit 0212's selected engine/question/default batch. The explicit setting is missing, not the Max route. `src/door.rs::Failure` stores only kind, retryable and safe message. Its panic guard intentionally cannot promise facts after losing the payload. Current `src/node.rs::CallHandle.detach` cancels, aborts the only TSFN and drops late completion. `index.js::invoke` races `AbortSignal`, rejects immediately and detaches on every settle. This gives prompt stop and Node exit, but cannot expose final joined facts on early abort. Worker creation precedes Rust validation/accounting and is not proof of account start. `public/bulk.rs::rank_with` can reject before `Stop::begin`; `Error::facts` may then be absent. A spent deadline after account start has final zero-send facts. The pinned `napi 2.16.17` source exposes `ThreadsafeFunction::unref(&Env)` and `refer(&Env)`; `CallHandle` already holds the TSFN behind a `Mutex<Option<Held>>`, and the worker holds its clone. Ticket 0236 fixes the early-abort path as cancel-plus-unref, observed `completion.wait()` as refer, and the one final callback as release. The callback caches the final envelope before resolving a waiter. A plain pending Promise cannot keep Node alive, so an observed receipt needs the refer call.

The shared Rust authority is landed: `CallOptions::{batch,context,observe}`, `EngineBuilder::batch`, `BatchSetting::{Max,Records}`, `Call<T>::facts`, `Batch::facts`, `Error::facts`, and `Engine::details_many_with`. The last takes a runtime `DetailQuestion` with `Evidence + Serialize` input and yields stopping ordered `Row<input,Details>`; it is the route for dynamic JavaScript choose/score/tag arrays. `CallOptions::without_context` and the public method routing decide eligibility; `annotate_with` accepts batch and refuses context, while `find`, recognize and relate do not consume a shared context. The C 0230 bridge demonstrated the same dynamic detail and per-row metadata writer, but its JSON ABI and last-failure accessor are not TypeScript API shapes. DuckDB's recoverable member policy must not leak into this stopping library route: a terminal failed row rejects and joins, preserving fatal tagged send-budget denials.

## Label order, consumers and focused checks

The native question-file parser uses `core::Json` objects as ordered member vectors, and `labels_in` retains those entries. The accepted TypeScript forms are arrays/readonly tuples and JSON object maps, with no added `Map` API. `Object.entries` gives the observable JavaScript own-property order, including integer-like keys, and `JSON.stringify` carries that order to the native parser; no unobservable insertion history is promised or used to reject a valid object. Native grammar distinguishes choose/tag list and null-map equivalence from score list and explicit-null map identity: `specification/question-file.md` lines 65–71 and 142 define the difference. Python 0233's fresh review caught a mixed bare/described score map that turned a bare label into explicit null; its corrected listener pins the two different bodies and digests. TypeScript must prove the same boundary and reject a supplied invalid optional before `JSON.stringify` erases it. Ruby 0234's fresh preparation/build likewise proved that a host worker may start before Rust facts exist and that explicit batch one is interactive under a held reply.

The direct library consumers are `tests/cases.mjs` and `tests/conformance.test.mjs` for shared cases; `tests/verbs.test.mjs`, `tests/shapes.test.mjs`, `tests/types.test.ts` and `tests/examples.test.mjs` for values, exports, typing and sample output; `tests/abort.test.mjs`, `tests/throttle.test.mjs`, `tests/settings.test.mjs`, `tests/settings_cases.test.mjs`, `tests/calibration.test.mjs`, `tests/deadline.test.mjs`, `tests/fork.test.mjs`, `tests/fork_child.mjs` and `tests/fork_worker.mjs` for timing/count/worker claims; plus `examples.json`, `README.md` and `NOTES.md`. `tests/backend.mjs` already starts scrubbed child Node processes with a fake key and loopback-only backend, so a new listener case can capture actual request bytes and digests. `cases.mjs` currently compares bare results and exact one-record fixture bodies. Shared cases 13–16, 27–28 and 34–35 need case-local `batch: 1` after result unwrap; keep their existing result/digest assertions. `verbs.test.mjs` asserts 27 sends for the shape table and direct bare values; classify its count rather than blindly rewriting it. `abort.test.mjs` waits for four held sends from one 200-record call; `throttle.test.mjs` separately waits for four across five scalar calls, then expects five, and has a 96-record event-loop case. ## Preparation lesson

The old TypeScript `AbortSignal` test proves prompt rejection and exit, but its deliberate callback abort means it cannot also prove final facts. The new completion design needs one held worker proof that checks pending versus joined accounting while preserving that old exit property. The inherited Max default is already real, so shared fixture failures are an expected environment difference, not missing Rust batching. A copied batch-one setup would invalidate four-held-send assertions because the scheduler waits for the first row. The label inventory also must separate a supplied `null`, a supplied `undefined` and a missing key before serialization; Python's score-map correction is evidence of a real identity error, while Ruby's invalid UTF-8 conversion bug has no direct JavaScript-string analogue. These lessons narrow the future build; they do not establish implementation or provider accuracy.
