The proposed code claim covers the 26 reported library files and one adjacent Go parent launcher, `libraries/go/fixtures/installed_release.py`, whose copied `abi_env` would otherwise reach the reported `abi.py` child. This is a bounded 27-file proposal; the 45 baseline count does not include every copied map in `checks/` or `fixtures/`. The non-SQL locations divide by process role, not by one universal list of variables:

- `nm`, `readelf`, Git, `ldd`, `pkg-config`, CMake, GNAT, COBOL, GNU Objective-C, C++, Swift, Zig, Go, Java/Kotlin/Scala and .NET launchers need selected toolchain paths and only the required host inputs. `libraries/jvm/tests/types.py` currently launches `javac`, `kotlinc` and `scalac` without `env=`. The [landed 0273 design](0273-linux-language-runner-design-review.md) shows Kotlin and Scala select Java transitively through `JAVACMD`, then `JAVA_HOME`, then `PATH`; pass the selected JDK into those children rather than keeping an inherited Java setting.
- Loopback backends in Ada, COBOL, C++, Objective-C, PHP and Go are launched without `env=`. Their consumer processes need test-owned fake keys paired with loopback addresses, fresh homes/cache, relevant `TT_*` fixture settings and explicit native loader paths. The five portable texts yield three exact bodies/counts; passing that assertion after isolation protects the behavior, while the plant checks that the backend and consumer never see an unrelated parent secret.
- Installed checks pass extracted wrapper and C artifact paths into checkout-owned Python scripts. For example `libraries/ada/check.sh` extracts into scratch then invokes `checks/portable_batch.py` from the checkout with `THINKTHEN_PORTABLE_PACKAGE` and `THINKTHEN_PORTABLE_NATIVE`; `libraries/cpp/check.sh` similarly invokes `fixtures/installed_release.py` with wrapper/native arguments. Those scripts can import `conformance/children/children.py` by their checkout root, but an extracted consumer package must not be assumed to contain that helper. Retain source and installed receipt identity separately.
- Nested Python checkers in C++ and Dart have their own first child (`plant-check.py -> run.py`), before the latter starts a backend and consumer. Passing a clean map only to the deepest consumer leaves the parent helper exposed. The R helper already imports `clean_env` and uses it for its Rscript children; its two hash-tool calls in `libraries/r/tests/helper.R` are the new R findings. C# and JVM also have whole-map **reads** in type checks, so change those reads to named settings as well as isolating their subprocesses.

The accepted 0127 helpers are `conformance/children/children.py::child_env` and `conformance/children/children.R::clean_env`. Both start empty, add `PATH`, read kept names individually, and reject keeping `THINKTHEN_*` or secret-shaped names. The builder should use existing imports as a pattern, without changing the helpers or guard. In the affected files, `libraries/cpp/fixtures/installed_release.py` builds `abi_env = os.environ | ...`, and Go's installed release helper also passes a copied ABI map. These are adjacent maps that source inspection found even where the saved guard did not name that line; the builder must not leave them in the changed handoff. A top-level Rust or shell launcher that starts a Python checker also needs its own explicit environment if that launcher falls within the claim. A clean grandchild is no evidence that its parent checker was isolated.

## Limits and lessons for the builder

No library runtime check was run in preparation. `policy.py` passed with offline Cargo and cleared compiler wrappers, `pages` reported 1 coming and 23 green, `tickets` reported zero evidence failures, and `git diff --check` passed. The source map supports a design but does not prove a compiler, SDK, installed package or runner is present. A selected check that cannot run must be reported as unavailable, not passed or replaced with an unobserved mock. A subprocess timeout must kill and reap its child and close descriptors; environment isolation does not excuse a leftover process. This follows the new [ticket-preparation lesson](../planning/ticket-preparation.md) and keeps the implementation proportional to the accepted 0127 method.
