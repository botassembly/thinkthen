## Actual path and reuse

`crates/thinkthen/src/public/choice.rs` defines `Choice` and the exported `choices!` macro; today the macro accepts only `Variant => "label"`, generates ordered labels and a compile-time duplicate check. `crates/thinkthen/src/public/builders.rs::Listing::next` checks a typed member's place, then sends its optional description to `push`; `ChooseBuilder::option` and `TagBuilder::label` both use it. That is the one place to select metadata behind an existing `Some` override. `crates/thinkthen/src/public/question.rs::Description` already holds and validates string/object JSON via `text` and `builder`, and `public/question.rs::bound` already checks loaded label order. `core/question_file/fields.rs::described` and `core/question.rs::Labels::{described,tags}` already implement map descriptions and the choose/tag null rule. Reuse them; no parser, wire writer, question binding or shared scheduler change is proposed.

The file grammar at `specification/question-file.md:65,107,142` is important: a loaded map enumerates the whole ordered set, a present null means no description, and a list/map of nulls have one question identity for choose/tag. Binding a loaded question must not synthesize enum descriptions into that object. An explicit typed-builder `Some` overrides that one enum default; it need not alter other labels. A malformed description is checked only after it is selected, as existing builder precedence requires.

Design risks for review: a new trait requirement breaking manual implementations; macro expansion referring to an unexported/private name; a structured literal silently reserialized differently; an invalid default evaluated despite an explicit override; metadata applied to `Question::from_json` after its digest was fixed; accidental changes to old bare choices or typed outputs.
