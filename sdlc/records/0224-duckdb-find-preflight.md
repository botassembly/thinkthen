## Current target and call paths

The original ticket says both Macs retained the C API. That statement predates [0231's M5 migration proof](0231-macos-arm64-build.md). Current `sdlc/scripts/release-pack::part_duckdb` selects the C++ package for `x86_64-unknown-linux-gnu` and `aarch64-apple-darwin`; `cpp/build.sh`, `cpp/CMakeLists.txt`, `tools/setup.sh` and `check.sh` have pinned native inputs for Linux x86-64 and Darwin arm64. Linux ARM64 and Intel macOS still package `src/` through the C API. M5's prior archive loaded on actual macOS 26 with a `minos 15.0` field and official Rust 1.95 standard library; it proves neither changed 0224 source nor execution on macOS 15. Linux ARM64, Intel macOS and actual macOS 15 runner proof remain separate, as does the full 0128 rehearsal. The later [0240 safe-budget repair](0240-duckdb-try-budget-build.md) is integrated on Linux; its earlier loaded binary and the M5 0222 artifact are historical sources, not packages for find.

The accepted SQL call is `thinkthen_find(question VARCHAR, units VARCHAR[][, none BOOLEAN[, deadline_ms BIGINT]])`. `list(unit ORDER BY ordinal)` is the caller's ordered constructor; the pinned v1.5.5 CLI observation in ADR 0096 kept two equal texts in order. The result is `STRUCT(index BIGINT, value VARCHAR, probability DOUBLE, candidates LIST<STRUCT(index BIGINT, probability DOUBLE)>)`. Top-level NULL in any supplied argument and a valid empty list return SQL NULL without a send; selected none returns a **non-null** struct with null index and value. Nonempty input requires 2–255 units, or 2–254 with none, nonblank question and member text, no NULL child, and at most 16 MiB combined UTF-8 member text. Wrong SQL types fail binding. Validate the complete list in order with checked byte addition, then call `Question::find` on literal text, optionally `offering_none`, and `Engine::find_with` once. A private owned `Indexed { position, text }` implementing `Evidence` carries original zero-based positions through `Call<Found<Indexed>>::into_value`; `Found::selected` and `candidates` give the winner and every original-order probability. Equal text is not equivalent evidence here. `@` and JSON-looking question strings are literal question text; neither host's question-file resolver nor `Question::from_json` belongs in this route. No public Rust accessor or copied find planner is needed.

The C++ `thinkthen.cpp::Decide` and `Listed` paths group and deduplicate scalar rows. Pinned DuckDB v1.5.5 `Vector::GetValueInternal` follows dictionary selections and builds a LIST by calling each selected child vector's `GetValue`; its `ListValue::GetChildren` returns those `Value` children and refuses a top-level NULL (`source/src/common/types/{vector,value}.cpp`). `listed_result.cpp::Members` then returns `nullopt` both for a top-level NULL and a NULL child, so find needs its own ordered list reader that distinguishes those outcomes. A dedicated bind must avoid `ResolveQuestion` and early file reads, and runtime validation should follow the current chunk-before-send pattern so an invalid later row does not trigger a new send. `StatementOwner::Remaining` supplies the statement budget; combine it once with the optional fourth-slot deadline and use `StopFor` when calling the bridge. Copy question, list and settings before detach. `SessionSettings::Bridge` points into caller-owned strings only during the synchronous FFI call; `ffi.rs::asked` owns copied settings and `copied_texts` owns list strings before `run_detached`. The worker must retain only owned input, engine, deadline, `CancelToken` and `SendBudget` options. `RustReply` frees both success and error buffers through `thinkthen_cpp_free`, including a decoder throw. `nested_result.cpp` already demonstrates checked byte reads and DuckDB `Value::STRUCT`/`Value::LIST`, but decodes a list of structs, not the accepted one struct containing a list: a small checked find frame/decoder is appropriate. Reject truncated, extra, oversized or invalid frame data before publishing a partial SQL value. Ordinary find raises the existing typed SQL error; 0240's safe per-row `try_details` envelope and terminal-denial drain are separate and must remain intact.

The retained C API has another distinct hazard. `src/ffi.rs::read_column` currently maps a NULL list child to an absent whole row, and its `Column` has no boolean reader. Find needs a typed path that retains child NULL for Usage and reads `BOOLEAN` without treating it as text or BIGINT; `ffi::write` already handles nested `Value::Struct`, `Value::List`, nulls, BIGINT and DOUBLE. `src/scalars.rs::Groups` deduplicates texts and `on_worker` calls `engines::within_total` to truncate ordered rows. Neither may shorten a find set. Use one owned set in `worker::run` with the existing cancellation and `engines::options`/actual-attempt `SendBudget`, then map the complete `Found` into `Value::Struct`. The ordinary scalar init currently builds an engine before reading any row; check that lifecycle against ADR 0096's NULL/empty no-send outcome without adding an unapproved promise that NULL bypasses invalid settings. Keep settings, file probes, host error kinds and one call's deadline authority; do not borrow DuckDB vectors across the worker. A failed later chunk may follow earlier completed sends, but validation must not initiate new sends after detecting that chunk's refusal.

No sleep, provider, full port suite or stress. Check `list(unit ORDER BY ordinal)` and the exact return type in the stock host before claiming them. Repeat only affected selected proofs per target and record actual package hashes; compilation alone grants no platform support.

SQLite's accepted build found that a generic responder always favors its first option, so a counted fixed reply is needed to prove a second duplicate or none tie. The expected result must be literal, not derived from that reply. DuckDB preparation adds two host-specific traps that old generic prose missed: `Members` and the C API list reader conflate child NULL with top-level NULL, and C API `on_worker` truncates record groups under the process total. Neither behavior is permissible for one atomic find set. The staged claims above preserve the approved result while keeping these corrections inside private host adapters.
