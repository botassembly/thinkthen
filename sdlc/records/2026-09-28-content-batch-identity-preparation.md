# Register 64: content-batch identity preparation

Notes only, source `origin/main` `f1b0acac0d1df3d24bfa6ad0f4b584f3209e561d` (2026-09-28). Original criterion: `experiments/284-issue-register/64-cross-language-batch-identity.md` asks for record-spelling rules and a shared fixture hashed on every applicable surface, so two implementations agreeing on spelling yield the same digest. The hazard is **a moved content cut**: a different spelling of one record can change batch membership before request encoding and cache lookup. The accepted [remaining-queue reconciliation](2026-09-28-remaining-queue-reconciliation.md) corrected its earlier single-batch-digest mistake. This note changes no contract, source, page, issue or status. Codex-6 currently owns specification-page edits.

## Current path and actual input domains

| Entry at this revision | Conversion into the shared batcher; limit of parity claim |
| --- | --- |
| CLI text/JSONL/CSV/TSV | `cli/asking/batched.rs` and `core/records.rs::Reading::{record,batch_record}` select a `core::Json`. Text becomes `Json::String`; JSONL and selected structured values keep parsed numeric kind and **object member order** (`core/json.rs`); table cells are strings in header order. A pointer can select a number, array or object. Annotation groups also call `core::Reading`, while root-only public annotation is text. CLI timing can close an open batch on a 50 ms pause, so a file/fast complete input is the controlled comparison, not an interactive pipe. |
| Public Rust, C, Python/frames, TypeScript, Ruby, R | Public `Evidence` and `public/batch/planned/answer.rs::record` turn each bulk item into Rust text and `Json::String`; `public/native_batch.rs` does the same for recoverable native rows. C's `call/records.rs` parses `records` as `Vec<String>`; Python `input.rs::listed` requires `str`, including frame/column cells; TypeScript `index.js::checkRecords` requires strings before JSON transport, and `door/result.rs::records` decodes `Vec<String>`; R `ffi.rs::texts_of` requires a character vector. Ruby `lib/thinkthen.rb::texts` accepts other JSON values but first converts them with `JSON.generate` to **text**; `src/ffi.rs` then passes `Vec<String>`. Ruby's object is therefore not CLI's structured object record. These routes inherit the Rust cut and encoder; their host conversion can still alter the *text* (notably Ruby object serialization, R UTF-8 translation, and JS string validity). Preserve each host's accepted domain rather than expanding it to arbitrary JSON for a test. |
| SQLite, PostgreSQL, DuckDB | SQL scalar/contextual calls and array/vector/warm routes in `databases/{sqlite,postgresql,duckdb}` gather SQL text into Rust `Vec<String>`/`&str` and call public `*_many_with`/annotation; SQL NULL/refusal and host conversion precede it. A single scalar proves no content cut. Selected package proofs are target-specific; a source route or Linux installed case does not establish native Intel/macOS 15. |

The common implementation is real. `core/batch/questions.rs::Batcher::push_slice` writes `json_line(&record.value)` through `core/render.rs`/serde_json, hashes those UTF-8 bytes with SHA-256, reads the first eight bytes big-endian and closes after that record when the remainder is zero modulo **4,096**. It also uses the serialized record plus complete question as its duplicate key. `core/batch.rs::close/built` builds the request once with the System One encoder and obtains its digest from `core/recording.rs::Exchange` over adapter name, newline, resolved URL, newline and **actual request bytes**. Setting, profile/size limits, 4,096-member cap, optional context, source end and CLI pause can also close a batch. `public/bulk.rs::selected_batch` defaults to Max unless an explicit, engine or saved-file tier wins. Thus host parsers may change what *value reaches Rust*, but there is no separate Python/Node/Ruby/R/SQL content-hash implementation to fix by analogy. `question-file.md` specifies question-digest spelling, not this record-cut contract.

## Small distinguishing fixture and proof

Use one fixed `decide` question and a complete file/list under default Max, fixed model and resolved URL, no context, retries or cache, and generous identical size/profile limits. A **five-text** candidate is `alpha`, `café-5544`, `omega`, `line 2907`, `tail`. A small independent Python SHA-256 calculation over literal compact UTF-8 JSON strings gives first-eight-byte prefixes `902cf2b465fb0762`, `3db0138d194cf000`, `00b22856036ff398`, `ee04192375591000`, `0c3f5e9d2376aedc`: proposed cuts after records 2 and 4, hence membership `[1,2] [3,4] [5]`. The existing [batching fixture](../../specification/fixtures/batching/README.md) already pins `line 2907` as a cut. Encoding `é` as `\\u00e9` instead gives the second record prefix `72afc19814d82dd9`, **not** a cut; this makes a spelling error move membership, not merely a digest within one selected batch. These are candidate calculations, **not** an executed Rust or host result. Before using them as expected values, confirm `core::Json`'s actual compact output at this revision and pin each literal record byte string, the per-record cut decisions and all three complete request bodies/digests independently.

For CLI structured input only, a separate three-record arm can put `{"n":1,"tag":"cut-1530"}` between noncut object rows and compare its supported parsed numeric/object-order forms. The same independent calculation gives prefix `c92816a409748000` for that literal and `6f0630ef5ae370ca` for the complete UTF-8 object bytes `{"n":1.0,"tag":"cut-1530"}`; only the former is a proposed cut. First verify both forms through the current `core::Json` parser/serializer and preserve their distinct accepted values. Do **not** feed objects to text-only hosts, equate Ruby's JSON-generated text to a CLI object, or treat numeric spelling as universally cross-host. Keep the five-text arm as the all-eligible-host comparison.

The actual proof should reuse `core/batch/tests.rs` and `tests/backend/batching.rs` plus the existing conformance runner/listener. It must assert five accepted records, exact ordered group membership and closure reasons, each captured listener body byte-for-byte against independently written fixtures, observed send count, and each detail/request digest against SHA-256 of the independently fixed body at the listener's actual URL. A test hashing its own captured body for both expected and observed values would be vacuous. Compare CLI and each *supported* Rust/C/Python/Polars/TypeScript/Ruby/R/SQL bulk entry at the same question/model/address/setting, noting when a host lacks a bulk route or selected package. Reuse existing per-host batch and stopped-run tests; case-local `--batch 1` legacy fixtures remain valid but cannot prove content cuts. `conformance/cases.json` still describes per-record exchanges and `conformance/record-values.json` tests output serialization, so neither presently pins this multi-record identity. A shared new case must be consumed by each named runner, not merely copied into a registry.

## Scope and decision

Prepare a numbered design before changing record serialization or a public spec: define which accepted record types share an identity, canonical compact spelling (numbers, escapes/non-ASCII and object order), and the independent shared fixture/runner obligations. Likely design pages are `specification/records.md` or a canonical-form section linked from it; codex-6 owns public pages now. A build should first add the literal fixture and focused core/CLI/host boundary checks, then change `core/json.rs`, `core/render.rs`, `core/batch/questions.rs` or host conversion **only if** those checks expose a real disagreement under the accepted domain. Audit every consumer of a new conformance case and the measured ratchet/file caps before source growth. One selected Linux package or one host's digest is not all-platform proof; record missing installed targets separately.

Register 64 remains open pending that cross-surface spelling/cut/body/digest proof. Register 19's equal-*answer* outcome and the separate issue about duplicated record/question wire text are shared batching context, **not aliases** of this identity criterion. No answer accuracy, token-economy or cache-hit measurement is established by this note. Smallest later checks are the existing core batch test, one CLI loopback, and one invoked case per applicable host; no provider, stress, full suite or new benchmark is needed. The preparation lesson is to trace the public input domain and the cut before comparing request digests: a matching digest for one chosen batch says nothing about rows that another host placed in a different batch.
