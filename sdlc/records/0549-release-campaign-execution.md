## What the build taught us

Repeated Flutter test-runner startup consumed the execution budget before the cases asserted. Building the actual installed application once removed that repeated work. The first application proof failed because the child environment omitted display authorization; passing the existing authorization fixed the transport without changing fixtures or native behavior.

Process ownership must include reaping adopted children while the campaign runs. The campaign supervisor adopted orphaned grandchildren but deferred reaping until teardown. The unchanged R startup test could still see an exited child and failed. With a genuine installed package from the same commit, the test passed normally, failed under deferred reaping with an adopted R zombie, and passed under active adopted-child reaping. All three startup assertions and the zero-send assertion stayed unchanged. The diagnostic evidence is `target/0549-r-startup-evidence/` in the separate R assessment worktree; its normal, deferred and reaping receipts retain the child states and actual exits.

Preparation must use real existing cache directories and create output destinations before linking them. A dangling parity output link failed before consumers ran in an earlier attempt. Those failed and interrupted receipts remain separate from the completed canonical receipt.

Fixture transport repairs need a class-wide reader audit: a successful correction of two observed failures did not cover six custom readers. Binding source caps also need checking before another expensive campaign; one redundant fixture import stopped the next attempt before parity. Neither failure justifies relaxing a limit or deleting an assertion.

Privacy checks cover compiler paths in each installed artifact. Full-campaign remaps use a neutral build path while retaining each language's real package and native carrier. The focused database and Polars proofs retain both the initial failures and their corrected commands. A zero-case run cannot establish parity.

Passing installed consumers does not establish that their temporary artifacts satisfy a later package-reuse check. The Python wheel lived in consumer-owned scratch while release smoke expected a retained package path. The final smoke exposed that ownership mismatch after every local parity assertion passed.

Retained build output can contain an older package even after a successful build. Selecting every matching wheel joined two valid paths into one invalid argument. Replacing only the builder-owned retained wheels after fresh validation binds preparation and package reuse to the current checked artifact. Isolated focused checks also require the actual backend at the paths their installed fixtures use and a fresh preparation prefix; preserving those setup failures prevented them from being mistaken for product regressions.
