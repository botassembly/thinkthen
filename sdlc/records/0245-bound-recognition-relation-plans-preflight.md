# 0245 recognition relation bound preflight

Status: notes-only source snapshot of main `730c9145`, 2026-09-28. No product, specification or issue was edited; no compile, provider call, stress run or fixture mutation occurred. [Ticket 0245](../tickets/0245-bound-recognition-relation-plans.md) is proposed for fresh review.

Experiment 284 register 111 records severity 3 and requires a local entity-count refusal with a remedy before a name-dense relation plan spends. The open scale-and-shape issue and accepted ADR 0056 are related, but neither supplies that missing bound. Current `engine/facade/recognize.rs::relations` calls shared `core/relation/pairs.rs::plan_pairs` after stages 1 and 2; the planner materializes every allowed `Question` and `Pair` before `engine/prepared_request.rs::pair_chunks` applies 400-question and byte ceilings. The default 600,000-byte text guard may be raised and is not a bound on pair or rule multiplication. Standalone relate admits 255 entities and uses the same planner; a shared cap at its entry would change its accepted 254/255/256 behavior.

The proposed recognize-only preflight counts distinct rule-eligible `(name, kind)` identities exactly as the planner does. For each rule, with source count `A`, target count `B` and intersection count `I`, directed questions equal `A × B − I`; `either` questions equal that result minus `I × (I − 1) / 2`. Checked arithmetic and summing every rule, including repeated rules, protect the aggregate. A read-only enumeration of 11,648 small rule/name combinations matched the formula to the current `allowed` predicate; this sanity check is not compiled product proof. No-rule and zero-eligible-pair paths need explicit exemption even when there are many names. A 255 pair-forming-name limit plus 4,000 total allowed questions bounds the two vectors built before chunking; profile and byte splits prevent any claim that this is a ten-request or spend ceiling.

The existing fixture inventory is concrete: `specification/fixtures/recognize/relations.jsonl` has 30 rows, at most four expected names in a row, and its recorded replay uses four rules. The 200-row names key peaks at five names; the one long-text key has 65 names and its replay has no relation rule. The proposed bound preserves those recorded forms. A wildcard directed rule over 64 distinct names makes 4,032 prospective questions and exercises the question refusal; a 256-name pair-forming case exercises the count refusal. Neither calls for a saturation campaign.

Current `engine/error.rs` and `cli/failure/recognize.rs` can carry a narrow numeric Usage refusal through exit 2; `public/error.rs` must expose the same safe category. `public/options.rs::Stop::run_call` retains prior actual Facts on failure, and the stage observer has already reported any completed recognition sends. Refusal therefore means zero **relation** sends, not zero total sends or a fabricated zero-cost run. It emits no final refused record and leaves earlier record rows intact. One small backend loopback table and the existing core relation tests can pin those boundaries; no new result field, option or storage format is needed.

Prospective exact claims and retained/deferred outcomes are in the ticket. The design lesson is to place the guard before expensive whole-plan allocation, count both admitted identities and every rule's pair multiplication, and avoid rejecting zero-work recognition or accepted standalone relate. The original register criterion governs later closure; this preflight does not mark it done.
