## Existing proof and new assertions

The existing `core/relation/tests.rs::pair_questions_keep_rule_order_ids_and_wording` pins planner order, IDs, relevant-kind state and two-rule construction. The existing compiled `recognize/rules.rs` declined-name case pins a one-rule state and no irrelevant pair; `recognize/stores.rs::details_carry_every_probability_and_request_metadata` pins a **kept** 0.9 pair in the exact fixture. The one-question profile case pins split output equality. These did not show repeated equal name/kind mentions at the command boundary, a two-rule recognize request body, a sub-cut pair in details, or two distinct relation chunks admitted together.

One new counted-listener command case uses `Ada met Acme, then Ada met Acme in Town.` with two person-to-organization rules. It pins **three actual sends**, the literal relation request's complete state and both ordered question strings, and omission of `Town` from that state. There is one `Ada` and one `Acme` in the relation state despite two of each in the output. It compares all five literal output entities, their original offsets and strengths, and the kept edge's **first** endpoints. The scripted 0.9 and 0.2 relation answers produce one kept edge and two `answer.pairs` rows; the 0.2 row retains its original endpoints and is absent from `value.relations`. The expected request and results are fixed literals, not values derived from the implementation or the captured body. No test-only product hook is added.

A second command case uses one `--lines` text, two rules, a profile capped at one question per request, and `--jobs 2`. The existing `Gathering` listener holds both relation replies until both have entered. It pins `peak == 2`, exactly two one-question relation bodies with the literal rule wordings, two completed edges and nine actual sends (four boundary chunks, three label/edge chunks, two relation chunks). If the old rule-by-rule wait returns, the bounded listener fails to collect both before its existing failsafe; no wall-clock threshold or large repeated dataset is involved. A plain one-text invocation cannot carry `--jobs`, which is why this test uses the accepted framed-record route. The test shows overlap for **split chunks** of one shared plan. The accepted architecture intentionally combines rules that fit into one request, so the original wall-time wording is satisfied by avoiding sequential rule epochs and allowing split requests to overlap, not by manufacturing one request per rule.

These cases protect different regressions: changing dedup would multiply pair questions or change first endpoints; reintroducing rule-specific state would duplicate sends or include `Town`; dropping rejected odds would erase the 0.2 details row; serializing the split relation stage would prevent the second held request from arriving. Existing core/planner, one-rule, kept-pair and split-equivalence proofs remain. No test was deleted or consolidated because those cases protect distinct parser, storage and output behavior.

## Disposition for review

Recommend closure of that narrow criterion if review accepts this case. Its separate Problem/Fix observation that SQL flat edge rows cannot identify repeated mentions remains an explicitly recommended SQL-host follow-up; this proof does not close it.

- **113:** The 0.2 pair is in `answer.pairs` and absent from `value.relations`, with a 0.9 kept control in the same result. Recommend closure of the dropped-probability criterion after review.
- **Shared-rule issue:** The captured recognize body contains both rule questions and only relevant unique entities; existing 0167 relate proof covers its other host. Recommend review of the implemented shared-state outcome, retaining the separate long-text split-cost finding 115.

## What the build taught us

The existing automatic tag fixture is useful for normal short names but does not promise that every capitalized token after punctuation becomes a separate output name. A repeated-mention proof must pin its input and literal spans, not infer them from capitalization. The CLI's width control belongs to framed record mode; one framed record still exercises the same text's split relation chunks. The `Gathering` listener proves concurrent admission deterministically, while numeric wall time would depend on the host and would add no stronger correctness evidence here. SQL repeated-name edge identity remains outside this Rust relation proof.
