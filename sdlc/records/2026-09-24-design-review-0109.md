## Findings

1. **Width 8 cannot be reached, so case 18 cannot end.** `default_engine()` reads only what `Engine::from_env` reads. Main reads `THINKTHEN_API_KEY`, `THINKTHEN_BASE_URL`, and `THINKTHEN_CACHE`. ADR 0017's settings table puts width only on the engine value, and the default is 4 (`cli/schedule.rs:17`). The tag set width through the stand-in's `ENGINE_WIDTH=32`, in `two_connections.py`, `cancel_fast.py`, `wire_suite.py`, and `examples.py`. That variable retires. Case 18 waits for the count to read 8, and it will stop at 4, so the test waits for the 300 s timeout. ADR 0017 also says the request limit "earns its place in the databases", and SQL cannot reach it either. Fix: rewrite case 18 and the kept width tests at the default width, and state that width here. Record a decision that SQLite runs at the default width with no request limit and no cache cap. Name the lever: a setting function or environment reads in `thinkthen`, which this ticket may not touch. The README says it.

2. **The R2-24 deadline on the 503 arm returns `backend`.** The 503 arm answers with `retry-after-ms: 10` (`arms.rs:148-151`). The engine retries only up to `max_retries` (`http.rs:136`), and the command's default is 2. The call fails as `backend` after about 30 ms, well before a 150 ms deadline. Fix: drop the 503 clause, since R2-10's held-arm deadline covers it. Or assert the actual outcome there, `thinkthen backend (retryable)`, with three counted sends.

3. **The held arm's release is permanent, and only the process that started the backend can count.** `Backend::release` lets "every held reply go, now and from here on" (`arms.rs:110`). `count` and `release` are lines on that process's standard input. ADR 0047 has the rung hand `check.sh` one port. A shared backend stops holding after the first test that releases. Fix:
   - Every counted or held test starts its own `conformance-backend` process, reads its port, and drives `count` and `release` itself. The check section says so, and names the rung's port as the one used for unheld cases only.
   - Every wait for a count reading has a bound, such as 5 s.
   - Every held test arms a release timer, such as 2 s after the signal, so a planted run fails on its assertion and does not wait for `timeout 300`. This applies to R1-14, the R2-10 tick plant, R4-17, R4-21, and R6-9.

4. **The disk cache can answer across tests and runs.** Decision 2 moves warm onto the engine's disk cache. Its default is `THINKTHEN_CACHE` or the XDG cache home. A previous run, or the user's own cache, can then answer these claims: R2-22 "counts 2", R6-14, the slide's warm count, R3-22, and every "zero counted" claim. Fix: `check.sh` and each test child set `THINKTHEN_CACHE` to a fresh temporary folder. One test runs the cache-off path the README describes.

5. **Four plants cannot turn their tests red.**
   - R4-17, recognize half: recognize runs on the worker (decision 5). With empty `CallOptions`, the calling thread still detaches and returns `cancelled` within 100 ms. Plant instead: run recognize on the calling thread.
   - R4-17, relate half: it has no plant. Plant: pass no interrupt check to relate, with a relate that needs more sends than width. Release after the interrupt, and the count grows.
   - R6-14: if the test spells model A and model B, or fields `kind` and `topic`, in the question argument, the keys of a map keyed by question text differ. The planted map then serves nothing stale. Fix: use one `'@q.json'` argument and rewrite the file between calls. The question cache re-reads on a change to modified time or size, and the planted map keyed by argument text serves the stale answer.
   - R1-11: decision 7 refuses a value above 4,294,967,295,000 before any add. The plant "add the milliseconds to `Instant::now()`" then never runs on `9223372036854775807`. Fix: state where the tick's deadline instant is computed, and place the plant before the range check. Or plant the unchecked add in the tick's computation from the accepted value, using a value inside the range that overflows it.

6. **Relate and warm are not promptly interruptible during a send.** `specification/relate.md` says relate "sends its requests in order". The interrupt check does not run during one blocking send (0095). A `thinkthen_relate` held at a send therefore waits up to the 30 s request timeout. Warm waits for its in-flight sends the same way, which case 18 shows by ending only after the release. Decision 5 also says "No thread outlives its call". A detached worker does outlive its call until its send ends. ADR 0017 claims zero threads outlive a call. Fix: run `thinkthen_relate` on the worker as well. `Entity` is `Clone`, so the worker can own a `Vec<Entity>`. Or state the 30 s bound in decision 6 and the README, with Ian's lever. Reword the thread sentence, and record the detached worker as the known exception to ADR 0017, as 0105 does.

7. **`lint` does not run clippy or rustfmt on the binding.** Main's `lint` runs `cargo clippy --workspace … -D warnings` on the root workspace only (`sdlc/scripts/lint:22`). `databases` is excluded from that workspace. `unwrap_used`, `expect_used`, `indexing_slicing`, and `panic` are clippy lints, so the rewrites named under Lints would go unchecked. Fix: add `cargo clippy --locked --offline --manifest-path databases/sqlite/Cargo.toml --all-targets --all-features -- -D warnings` and `cargo fmt --check` for the binding, with a planted `unwrap` that fails. Cite them as the SQLite halves of R1-28 and R3-28.

8. **Four rows with a SQLite half are unnamed, and two rows have no owner.**

   - Name R5-8, the boolean deadline on every surface. SQL has no boolean, and `TRUE` is the integer 1, so it reads as 1 ms. Say it does not apply and why.
