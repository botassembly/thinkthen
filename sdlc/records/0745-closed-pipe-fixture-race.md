# Closed-output fixtures require reader-closure ordering

The configured gate run `0740/1792523048499-73469` tested candidate tree `9134147e9680f2492c7224b471cda6315c44924c`. Its retained log at `gate-runs/thinkthen/0740/m5/9134147e9680f2492c7224b471cda6315c44924c` reports `broken pipe sent 9 requests` in `annotate::scheduling::a_closed_output_pipe_stops_annotate_quietly_and_bounds_read_ahead`. Linux lint passed and the routine suite reported one failure. This is a setup failure: the fixture made every reply available after a timer while assuming the parent would close stdout before enough further ordered rows advanced the request window. The log records the excess requests; it does not record the precise process interleaving.

The class inventory contains five fixtures: annotate's bounded read-ahead case, parallel decide's reader-closure case, table decide's reader-closure case, tag's quiet reader-closure case, and filter's between-dispatches case with both batch sizes. Each prefills input and previously used a short reply delay to give the parent a chance to read one row and close its reader. A loaded machine can schedule the child repeatedly while the parent remains paused. A longer exit guard cannot establish reader closure before further ordered replies.

Commit `7b3f4cc4dfdd28873d3622373c35c8af2d5eecb7` repaired the adjacent annotate backend-failure-after-closure case with a rendezvous. For the failing bounded-read-ahead case it only raised the exit guard. The same delay assumption remained in the other four fixtures. The earlier repair addressed selected waits and hang guards without removing this whole class of assumed ordering.

The fixtures hold the second ordered request's reply with the existing `Rendezvous`. They release it only after the parent reads the first row and drops stdout. The selected identities are annotate record 2, parallel record 2, table row 1 after row 0, tag row 2 after row 1, and filter drop 2 or drop 11 according to batch size. Quoted text boundaries distinguish the table, tag and filter identities from later rows with the same numeric prefix. Arrival order does not select the held request. Every other reply remains free, so the existing request ceilings still detect continued scheduling after closure. Filter's first batch can contain several records; holding drop 2 at batch size ten would hold the first request and prevent the first output row.

`Rendezvous::wait` itself has no time limit. Its cancellation belongs to listener retirement. Each fixture therefore performs the rendezvous wait on a release thread while the parent retains its existing bounded child wait. The selected reply also announces arrival through a channel. The release thread waits for that announcement before entering the rendezvous. If that request never arrives, listener retirement drops the channel sender and the thread exits. If it arrives, listener retirement cancels its registered rendezvous when needed. The parent captures the child result and request count, retires the listener, joins the release thread, and then checks assertions. This preserves cleanup when a read, release or child-result assertion fails, without a shared helper or a new deadline. Annotate retains its original explicit exit deadline and kills and reaps the child on timeout or a status-read error.

The production closure checks in `crates/thinkthen-cli/src/cli/annotate/native.rs` and `annotate/native/rendering.rs` are unchanged. No shipped behavior or API changes. Existing request ceilings, output checks, quiet-output assertions, exit expectations and cancellation cases remain.
