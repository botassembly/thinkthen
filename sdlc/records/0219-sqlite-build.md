A separate bounded default-cache probe ran the identical five-row warm twice and then one scalar: `requests_sent=2`, `cache_answers=1`, listener `2`. This confirms the second warm reuses the **same complete packed key**, while the scalar still uses its distinct singleton key. With context, preserving the literal context does not make a two-member body equivalent to a one-member body; the two digests above differ. B0's [batching issue](../issues/2026-09-26-batching-design.md) explicitly says a member's answer depends on its neighbours and the cache key is the entire request digest. `engine/request.rs::ask_prepared` passes that digest to `recorder.prepare_checked`; the recording permit stores the complete prepared request and reply under that key. No existing native lookup can answer an ordinary singleton scalar from a packed key without an additional cohort identifier and a new result provenance rule. The scalar signature carries question, one text, deadline and optional context; it does not carry the other warm members or their ordering.

The accepted `0149` same-session warm/scalar checks established settings parity before default packing. The `0157` size/retry stage did not add an answer-transfer path. The `0222` selected warm/cache proof and B13c adapter do not change B0's full-key rule; a singleton or batch-one hit cannot prove multi-member warm-to-scalar parity. The `0219` preflight incorrectly combined the historical warm-to-scalar recipe with B0's default packed key. The previously corrected ADR 0080 budget behavior remains independent of this conflict.

The smallest safe staging choice is to keep the current settings/context/packed-warm source frozen as an **incomplete B13e slice**, retain the failing slide assertion, and have the coordinator settle an amendment before landing. One reviewed amendment could teach `thinkthen_batch(1)` for callers who require the old warm-then-scalar cache identity, while documenting that default packed warm reuses only an identical packed cohort; that narrows the accepted slide/default outcome and needs an explicit ticket/page/test correction. To retain default packing **and** consume its judged rows without a second send, the host needs a new row-result operation or explicit batch handle so later reads name the same complete request and member position. That is a new SQL/API design and source claim, not a cache alias. Silently making warm batch one would violate B0's default, and writing packed member answers under singleton digests would misstate their request provenance and may change answers. Cache ticket 0238 owns the shared request/recorder/facade paths; this lane made no edits there and recommends no cache-policy change for 0219.
