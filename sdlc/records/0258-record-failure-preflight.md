## Four original outcomes and current source

The local original register holds items 43, 65, 66 and 68. Item 43 asks for a run that can pass a poison record with one cause-bearing error row and a distinct exit. Item 66 specifically asks for scattered missing `on` pointers to leave later good records judged, with the pointer named in each miss row. Item 65 asks that a shadowing question set run under `--details` with intact input while bare record writing still refuses. Item 68 asks three-sentence-scale prose that ties same-`on` request economy to partial-answer exit 6, wholly failed group exit 4 and edit/rerun cost. They share annotate code but are not duplicates. The proposed first slice completes 65, 66 and the page criterion 68, plus only the missing-pointer subset of 43. Keep 43 open for other verbs and backend/whole-batch poison isolation.

Current `cli/annotate.rs` reads the set and resolves mode before source input, but `Judging::record` always calls `collisions`, including detailed mode. `cli/annotate/plan.rs` does the same for dry run. `QuestionSet::group_evidence` reaches `RecordError::Missed(String)` on a missing `on` member. `cli/annotate_schedule.rs` prepares every group for a record before sending that record's work. `engine/annotate_schedule.rs` currently places every preparation error in `failures`, halts, drains the ordered completed prefix and returns `Stopped`; it has no per-record error-row branch. `cli/annotate/aggregation.rs` already keeps valid answers beside failed logical markers and records a partial failure. `tests/backend/annotate/partial_failure.rs` pins two completed rows/two sends/exit 6 and a later status 401 that prints one prefix row/two sends/exit 4. `tests/backend/annotate.rs` pins bare collision exit 2 and its exact current diagnostic. `specification/{records,annotate,channels,result}.md` currently settle stop, exit 6 and the detailed carrier. `roadmap.md` holds universal `--on-error continue`; its broader hold survives a narrow shipped subset.

## Literal outside-in oracle and boundaries

Use a one-question set `{"version":1,"questions":{"urgent":{"decide":"Is this urgent?","on":"/body"}}}` and exactly these three JSONL lines:

```text
{"id":"a","body":"first"}
{"id":"b"}
{"id":"c","body":"third"}
```

The proposed error line at the second output position is exactly:

```json
{"schema":"thinkthen.record-error/1","at":2,"failure":{"kind":"usage","cause":"missing_pointer","pointer":"/body"}}
```

For good rows, pin complete expected `thinkthen.result/1` JSON templates using the exact fixed set, `first`/`third`, model `local-1`, two fixed canned yes/no replies and the test listener URL. Derive each expected digest from a **literal expected request body**, never from the captured body or emitted row. Compare each actual captured body byte-for-byte with those two literal bodies, not only a digest or send count. The request-body form to pin is `{"state":"first","model":"local-1","questions":{"q1":{"type":"noul","instructions":"Is this urgent?"}}}` and the same with `third`; confirm exact serializer spacing/order at implementation red proof before freezing fixture bytes. The two canned replies should report explicit known usage so the good rows' `meta.usage` can be asserted; the error row has no usage member. Assert entire stdout (three rows), stderr `thinkthen: 1 record skipped\n`, exit 7, exactly two sends and no request for `b`. The default command over the same input asserts the existing complete first row, `thinkthen: the record holds nothing at \`/body\`\nthinkthen: stopped at record 2; 1 record finished\n`, exit 2 and one send. Pin terminal-after-skip with one further status 401 response: it must exit 4, retain the old terminal stop line at its actual position and have the one skip-count line before it; every attempted send is counted. A partial logical answer under the flag still uses one completed detailed row with a failed marker and exit 6, or exit 7 if a separate pointer miss also occurred. Existing 401/partial fixtures provide the responses; do not copy their loose row-count assertions as a new oracle.

For name shadowing, run `{"urgent":"original","body":"first"}` with `--details`, no continuation flag: one full result row must retain `input.urgent:"original"` and put the judged `urgent` in `value`/`answers`, exit 0, empty stderr, one exact send. Bare mode on that input must retain exit 2, empty stdout, `thinkthen: the record already holds \`urgent\`, so that question cannot be appended\nthinkthen: stopped at record 1; 0 records finished\n`, and zero sends. A details dry run must complete its first plan with zero sends. Flag combinations missing `--jsonl`, `--details` or `--batch 1` must exit 2 with exact usage diagnostics before reading a deliberately missing input path; an unsupported verb must reject the flag. A pointer string and a canary API key must never appear outside the deliberately named pointer field and test backend request header, respectively. Check stdout, stderr, and relevant `Debug` formatting rather than assuming the row serializer is safe.

This proof deliberately does **not** claim a failed whole group can identify one poisoned question or preserve sibling group answers. With `--batch 1`, a failed reply costs that record and stops; group siblings may already have sent and count in actual usage. With larger batches, a wholly failed request holds several records and stops at its current range; isolating one poison would require extra sends and new request digests. No provider, stress, churn, full suite or broad host build resolves this first-slice design.

The worked shell job belongs beside the existing triage pipeline. It should make a JSONL copy of that demo's six fictional records with one `/body` omitted, run `annotate questions.json --jsonl --details --batch 1 --on-error continue` into a staged file, capture exit 7 explicitly, and route rows by `schema`: completed `thinkthen.result/1` rows to the ordinary policy, the one `thinkthen.record-error/1` row to a review queue with its position and pointer. It must reject an unknown schema, refuse publication on any other nonzero exit, and never feed the error row to the existing triage transform. Existing `demos/16-triage-pipeline/` uses TSV and a fake `thinkthen` self-test, so it is **not** already a working proof for this JSONL flag; its replay recordings must be checked for exact request identity before reusing them. A small offline new example/test under that demo is prospective implementation scope, not source touched in this preflight.

## Sources, review risks and implementation order

Prospective product files after acceptance are `cli/args.rs`, a private annotate args child, `cli/args/command.rs`, `cli/annotate.rs`, `cli/annotate/plan.rs`, `cli/annotate_schedule.rs`, `engine/annotate_schedule.rs`, a narrow error-row renderer, possibly `cli/facts.rs` only if the existing finished-record counter cannot cover skipped rows, new focused backend annotate tests, the bounded demo-16 variant and derived ratchet. The normative pages, settings inventory, named `recordError` definition in `specification/result.schema.json` and two schema-only type-corpus controls are listed in ADR 0104. The root result schema keeps validating successful detailed rows; the current failed-question definition stays backend-only. `recordError.failure.kind` is the existing `usage` kind under ADR 0082, with `missing_pointer` as its specific cause, and it does not change the six-kind host call errors. The corpus proves envelope structure, while the CLI proof and demo consumer prove actual emission and safe routing; neither an unrelated C call nor the schema alone proves those. Do not touch generic `engine/schedule.rs`, batched asking, libraries, bindings or site for this slice. First land the independent details collision exemption and grouping prose with exact existing/default tests; then introduce the annotate-only flag and missing-pointer row; finally pin mixed partial/terminal precedence and facts. Land the ticket whole after independent review, not as partially closed register items.

Risks to review: `RecordError::Missed` must be classified by variant, not by printable text; a record may have several `on` groups, so preparation must validate all groups before sending it. A pointer failure in a later group must discard that record's unprinted prepared groups without discarding completed earlier records. The engine's `Input::Failed` branch and a prepare failure have different ordinal handling; the proposed recovery must not accidentally continue past malformed or overlong input. The existing `Output` writer may itself fail, and such an error remains terminal. Prior group answers and backend attempts may consume unreported tokens; neither an error row nor `--facts` may turn that unknown into zero. `--details` is required so successful and error rows have distinct schemas; the details collision exemption must also reach dry run. The old demo 12 still teaches repairing a stopped `decide` run and remains truthful. The new demo-16 variant must not treat exit 7 as a clean published audit.
