# Usage-write cost: source preflight

Notes only, on `origin/main` `d05e85d2004a2abba3c0c151eb01cc170e18e134` (usage source unchanged from `c5293cc6`). The original criterion is [the new issue](../issues/closed/2026-09-28-usage-file-write-adds-50-ms-per-command.md): **measure the per-process usage write, then decide whether one process can skip or defer it without losing counts**. [Ticket 0141](../tickets/0141-usage-writes-stop-serializing.md), [ticket 0235](../tickets/0235-usage-compatibility-and-transient-backend-failures.md) and ADR 0097 fix the current write-behind, old-reader and final lock-wait boundaries. The issue's local fake-backend observations are 18 ms on disk versus 4 ms in memory for one-at-a-time build `02dc0b96`, 57 ms for four concurrent processes on that build, and 50 ms for four on `3b96e720`. These are whole-command medians from different builds and contention conditions, not a measured 50 ms attributable to one current `fsync`. No current-source timing was run here. The Beatles Bench and provider timing figures in the issue are background, not a durability proof or a new measurement.

## One short command, from count to exit

1. `cli/edge.rs::Environment::new` gives command counters a platform usage path; libraries without that path use memory only. Before a live send, `engine/http.rs::post_marked_with_retry` calls `Counters::prepare_attempt` (`engine/usage/attempt.rs`): it takes the in-process queue mutex, reserves space and starts the writer on first use, *before* the final stop/budget check. `PreparedAttempt::mark` then records the actual attempt and its UTC month just before transport. A refused send can have started an idle writer but publishes no delta. Each retry is another marked attempt. `engine/request.rs::ask_prepared` separately adds a successful live reply's reported tokens; a fast reply may arrive before or after the writer takes its first pending batch. A decoded cache hit adds one `cache_answers` delta only when `Recorder::counts_cache_answers` is true. Explicit replay does not; `--no-cache` does not disable usage accounting. A dry run or other no-count path starts no usage write.
2. `engine/usage.rs::add`/`PreparedAttempt::mark` merge adjacent same-month deltas under the short mutex and wake `write_behind`. The writer takes the pending vector, releases the mutex, and calls `storage::update` for each month. One short live command may therefore get one coalesced write or separate attempt/token writes depending on scheduling; coalescing is not a guaranteed one-write-per-command optimization. A longer run can amortize thread startup and combine deltas while a write is in progress, but a shell loop that starts one process per call still pays its own finalization.
3. Each `storage::update` creates or validates the private directory, opens the stable `.lock`, and obtains an exclusive lock (`usage/lock.rs::acquire`). Under that lock it verifies directory/lock identity and `scan`s **every recognized month and sidecar**. `scan` lists, sorts, opens, parses, checks file identity, rejects orphan/inconsistent/unsafe recognized state, and supplies current and all-month checked totals. This work grows with the number and size of stored months; it cannot be replaced by a current-month-only lookup while ticket 0235's all-month migration and corruption refusal remain. The writer checks the proposed current-month and aggregate additions *before* mutating any file. It then migrates every contaminated month sidecar-first and old-reader-base-second. On a previously absent current month it also syncs the lock and directory before the ordinary replacement.
4. The ordinary update writes the old-reader five-member `thinkthen.usage/1` month via `.update.tmp`, file sync, rename and directory sync, then **unconditionally** does the same for `retries-YYYY-MM.json` via `.retry.tmp` (`usage/storage.rs::update`, `replace`). Each file is mode 0600 in a verified private directory; the stable lock is never unlinked. This two-file ordering protects previously durable base totals while permitting an interrupted retry undercount. A first write or legacy migration can need more syncs; the steady clean-month path still has two file and two directory syncs per writer pass. The sidecar's retry total is unchanged when a pass contains no retries, which is a source-demonstrable redundant *replacement*, not proof that skipping it saves 50 ms.
5. After the answer and diagnostic, `cli/mod.rs` calls `Counters::finish`, which waits for pending/writing work and prints the one fixed warning on persistence failure; `--facts` follows it. `Counters::drop` sets closing and **joins** the writer. ADR 0097 gives all remaining *lock acquisitions after finalization* one shared one-second deadline, not a bound on file I/O, sync or total exit. A writer failure latches and clears later pending deltas. Removing `finish` or the join can lose counts at normal exit; omitting sync changes the previously durable-total guarantee. ADR 0049 already chose the writer over end-only flush so `status` can see a long run and a kill does not lose the whole run.

## Narrow candidate and constraints

The smallest source-supported candidate is to **avoid rewriting an unchanged retry sidecar** during an ordinary clean-month update: if the validated old retry count equals the proposed next count, leave an existing sidecar untouched, and if both are zero and no sidecar exists, keep it absent. Still write/sync the changed legacy base; still scan/validate all recognized files and perform all required migrations under the stable lock. A no-retry cache hit, a first call with no retry, or a token delta would then avoid its otherwise unconditional second temp write, file sync, rename and directory sync. A retry increment must still write the sidecar after the base. A contaminated month must still migrate even if this delta has zero retries. This is a **proposal**, not an accepted optimization: ticket 0235 explicitly says each ordinary delta writes base then sidecar, so root needs a small reviewed protocol amendment before code changes. Do not treat a sidecar's absence as zero for contaminated rows, and do not skip sidecar validation just because no retry was sent.

One coherent follow-up ticket can own `crates/thinkthen/src/engine/usage/storage.rs` and the closest `usage/tests.rs` cases. Its smallest correctness proof uses isolated 0700/0600 fixtures: (a) a clean fresh no-retry month stays old-reader five-field with no sidecar, exact current totals and a later retry creating a correct sidecar; (b) an existing sidecar with seven retries remains byte-identical through a no-retry new write and an immutable old writer's write; (c) a contaminated prior month migrates even when the current delta has no retry; (d) injected base/sidecar failures retain the accepted warning, atomic replacement and previously durable totals. Reuse the real-old-reader result and exact 100/7 → 101/7 → 102/7 snapshots from workspace `experiments/346-0235-acceptance/REPORT.md` and `experiments/347-0235-retry-preservation/transcript.json`, noting that 346's initial retry-loss claim was withdrawn. A single isolated before/after short-command observation, only after correctness, should separate first write, clean month, existing sidecar and four-process lock contention; it need not become a saturation campaign. If that bounded observation shows the base sync or history scan dominates, further latency reduction needs measured attribution or an explicit durability decision, not a skipped `fsync`, daemon, dependency or new public setting.

**Priority:** moderate, after release correctness and accepted accounting repairs. The issue's shell-per-question cost is real as an observed whole-command effect, but its exact current cause and likely gain from the narrow candidate remain unmeasured. Ordinary multi-record or long-lived invocation reuse can amortize it without satisfying the original per-command criterion. No shared user usage folder, live ledger, provider, global configuration or external artifact was changed in this preflight.
