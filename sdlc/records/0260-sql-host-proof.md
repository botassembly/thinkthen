## Host routes and observed contract

| Host | Public ordered bulk route | Public result | Five-text observation |
| --- | --- | --- | --- |
| PostgreSQL | `thinkthen_decide(question, text[])` | Five `(i, decided)` rows; no digest column. `src/array.rs` retains first-occurrence text order and original slots before calling `decide_many_with`. | Installed 0259 PG 16 package returned `0:true` through `4:true`. Its local backend counted three sends and captured the three exact fixture bodies. |
| SQLite | `thinkthen_warm(question, text)` over an explicitly ordered subquery | One distinct-count result; no per-row result or digest. `src/scalars/warm.rs` adds first-seen texts and sends them through `decide_many_with`. | Installed 0259 library on pinned SQLite 3.50 returned count 5. Its local backend counted three sends and captured the three exact fixture bodies. |
| DuckDB | `thinkthen_try_details(question, text)` over one ordered five-row vector | Five answered envelopes with `details.meta.requests`. `cpp/src/thinkthen.cpp` groups distinct texts and maps results back to slots. | A current-source extension on pinned DuckDB v1.5.5 returned five true values with digest mapping `[1,1,2,2,3]`. Its local backend counted three sends and captured the three exact fixture bodies. |

Each runner reads `specification/fixtures/batching/portable-records.json` and the three literal `portable-N.request.json` bodies. The texts are `alpha`, `café-5544`, `omega`, `line 2907`, `tail`; the body fixture establishes ordered memberships `[1,2]`, `[3,4]`, `[5]` and the accepted content/content/end cuts. The tests set Max, use the fixed question and default model, isolate the cache, use loopback only, and check the independent fixed-address fixture digests from the literal body bytes. They compare three captured complete bodies as a multiset because transport arrival can reorder concurrent requests. In DuckDB, returned row identities independently establish the logical group order at the actual listener URL. One observed DuckDB run delivered group 2 before group 1 while its five returned identities still mapped to `[1,1,2,2,3]`; a test that equates arrival order with batch order would reject valid behavior.

PostgreSQL and SQLite do not expose request identities in these public result types. Their exact bodies and counted sends prove the Max content grouping at the host boundary. The shared Rust `core/batch.rs:375` gives each request `Exchange::digest`, and `core/recording.rs:102` hashes its resolved URL and exact bytes. Applying that source rule to the fixture bodies is an inference about their unexposed digests, not a returned SQL result. A central design wording correction should accept this qualified observation for these two existing SQL routes and reserve direct `meta.requests` assertions for hosts that expose details. It should not require a new PostgreSQL array digest column or SQLite five-row warm result. Fresh review should check this equivalence against the original register 64 criterion before accepting the SQL checkpoint.
