## Trace and design correction

- `public/options/budget.rs::SendBudget::reserve` is an atomic process send count with fork reset and a pre-commit refund. `engine/http.rs::post_marked_with_retry` acquires a width permit, prepares usage, checks the final deadline, reserves the send, marks it and then sends. `engine/request.rs::ask_prepared` resolves replay/cache before the live closure and records reply usage only afterward. A retry repeats the transport loop; an oversized request can split into distinct later prepared bodies. `engine/call_facts.rs` and `engine/usage/facts.rs` preserve absent usage rather than turn it into zero. These are current source facts, not claims that 0289 has already installed a universal public cap.
- 0289 proposes `EngineBuilder::max_requests_total`, CLI `--max-requests-total`, `Engine::plan` over 0283's `core/plan_summary.rs`, and a core tally. ADR 0105 calls its 0.516/0.908 tokens-per-byte preview an **estimated band**, with planned requests before cache, retries and refusal splits. `specification/backends.md` explicitly says a token-only profile needs a tokenizer or verified byte ceiling. Therefore the 0.908 rate may be used for a **versioned estimate admission invariant**, never described as a hard provider token or money cap.
- Current process budget ownership is not globally shared across arbitrary engines merely because `SendBudget` is `Arc`: callers must pass the same owner. 0289 must make its promised owner scope real before 0299 can share it. PostgreSQL's backend/pool scope remains separate. Cache/replay may still face an independently spent request cap under an existing SQL preflight; this ticket does not silently relax that rule.
- A started failed send can have no usage; a reply can report arbitrary output after admission. Settling an estimated reservation with observed usage would mix units and create either silent undercount or a false hard cap. Keep two ledgers: admitted estimated input for this limit and optional reported input/output in existing facts. No durable status storage and no developer live-ledger reuse.

## What preparation taught us

Tracing the marked send rather than the planner exposed two hazards: planned body counts differ from live attempts after cache/retry/split, and a reservation refunded after transport would falsely make a failed billable attempt free. The review should test the body actually sent and the stop point before transport. The estimate's measured upper band is useful for admission math but is not a tokenizer upper bound; the name and proof must say so. The tiny CLI and C file headroom makes extraction part of the future scope, not an afterthought.
