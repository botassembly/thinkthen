# 0245 bounded recognition relation plan build

Status: implementation candidate `b147a98b` pushed on `ticket/0245-bound-recognition-relation-plans`; fresh independent code review is pending. The accepted design is `cbf430ab`, with its Medium review recorded [here](0245-bound-recognition-relation-plans-design-review.md). The build started from main `7e8fe1e8` and merged the unrelated marketing/main changes through `06b0803e` before the source commit. No provider, real recording or cache mutation, saturation run or broad suite was used.

`core/relation/pairs.rs` now shares first-mention, rule-side admission between the existing planner and a count-only helper. The helper counts allowed directed or `either` pairs across every rule with checked multiply, subtract and add. A repeated rule contributes another set of questions. Recognition calls it after name settlement and before `plan_pairs` or `pair_chunks`. It retains the existing `None` result for no rules and the empty relation list for a zero-pair plan, including 256 admitted names with no matching target. A nonempty plan above 255 admitted identities refuses first; a plan above 4,000 questions refuses next. The helper builds no `Question`, `Pair`, relation evidence or chunk. Standalone `relate` still calls the planner directly, and the planner's ordered output and request bytes stay the same for admitted work.

The engine's two new errors are Usage and non-retryable. CLI exit 2 and the public error envelope share numeric, path-free, content-free diagnostic constructors. A 64-name one-rule text reports 4032 prospective questions; a 256-name nonempty plan reports 256 names. An arithmetic overflow cannot wrap to an admitted plan and reports at least 4001 questions. This count is an allocation guard. Profile or byte splitting can produce more than ten requests below the limit, so it is not a request or spend cap.

What the build taught us: a name-only guard misses repeated-rule multiplication, and counting only names that participate in some pair misstates the reviewed admission rule. Reusing the planner's ordered admission keeps equal-name-and-kind identity exact while the count helper stays linear in admitted names per rule instead of constructing a quadratic question vector. The early recognition stages can be paid before this refusal, so the functional proof checks actual prior attempts and facts rather than zero total sends. Strict lint caught a test's nested loop, an indexed lookup, and an unsafe `expect` in diagnostic plumbing; they were corrected without lint suppression. Repository policy also rejected a glob test import, which was replaced with explicit names. The 255-entity standalone plan remains legal; moving the new cap into shared `plan_pairs` would have broken it.
