## What the build taught us

The accepted design's phrase “profile identity” was too strong for these public calls. The private loaders preserve the exact source and public parsing accepts the saved profile, but current public recognition and relation results expose generated stage or pair details only. They do not expose a whole-plan profile warning or a digest that contains the saved profile. No observed calibration behavior can be claimed from this test. The ticket now separates source retention from effective request model and threshold behavior. The shared-conformance issue remains open for a final criterion map and this retained limitation.

The fixed backend capture arm holds only three request bodies. Ruby therefore reads its three named-plan bodies before it starts the separate inline control calls. That synchronization proves the original request bytes without adding a mock listener or changing the product. A first existing TypeScript shape invocation lacked `THINKTHEN_TEST_BACKEND` in the author's shell and failed before product code ran; the same case passed with the pinned loopback backend path. The Ruby build initially lacked pinned Ruby headers until its toolchain environment was applied; the corrected strict Clippy and release build passed. Neither setup failure is a runtime defect.

Public documentation wording for its later owner: “Pass `{ file: path }` to TypeScript `recognize` or `relate`, or `file: path` to the Ruby verbs, to read one local version-one plan at call time. The file option is exclusive with inline plan fields. File read and validation errors are local and do not send a request. A saved model and thresholds control the call. The original saved profile text is retained by the loader; current recognition and relation results do not report plan-wide profile calibration.” Preserve the existing scalar `questionFile` and `question(file:)` descriptions and ordinary literal-string behavior.
