## What the build taught us

The C policy's unsafe-module rule applies to private children, so keeping the unsafe export in `ffi.rs` is the smaller compliant implementation. Its preexisting output validator removed the need for a new null-output branch. Removing the discarded child lowered the first candidate's C Rust count to 3324; the corrected secrecy test brings the measured tree to 3340. The shared strict arm makes C request identity observable without adding a test-only native loader. TypeScript's validated original JSON is part of the request identity: another JavaScript object serialization can change numeric key order. Ruby's question-file path must stay distinct from its question-set path. A selected case proves a boundary; it does not turn a historical full-run result into a new full gate.

## Fresh High review findings and correction

The independent High review of `1d0d8dbb` rejected two boundaries. All three file loaders forwarded `error.detail().message()` from the core parser. Its unknown-key diagnostic can include a key supplied by the file; the reviewer observed `SYNTHETIC_PRIVATE_MARKER_0244` in a Local message. Each named-file edge now uses a fixed invalid-question category. Distinct fixed read, size and UTF-8 categories remain, and inline Usage diagnostics keep their prior detail. The existing C, TypeScript and Ruby refusal tests now plant the synthetic key, require Local without the marker or path, and count zero sends. The C output sentinels remain unchanged. The corrected focused C test passed; the rebuilt TypeScript addon passed its named-file refusal and rich captured-request tests. Ruby's rebuilt extension passed its focused refusal test. Selected case 30 passed again in TypeScript and Ruby; the C case 30 and all three case 01 outcomes from the initial candidate remain valid because their inputs and paths did not change.

The reviewer also found that Ruby considered an ASCII-8BIT string valid even when its bytes were invalid UTF-8. Magnus then raised a raw `EncodingError`. The Ruby front door now duplicates a non-UTF-8-encoded path and marks the same bytes as UTF-8 before validation. Invalid bytes produce `ThinkThen::UsageError`; a valid binary-encoded path still names the original file. The focused Ruby test covers both paths and no sends. These findings show that a public parser's diagnostic must not be assumed safe for a file-origin error, and that `valid_encoding?` checks the string's current encoding rather than UTF-8 validity.
