# 0244 named question-file forms build

Status: implementation candidate for a fresh High code review. The accepted design is [ticket 0244](../tickets/0244-named-question-file-forms.md) at review `48ad825e`. The feature started from main `e70f9121`, which includes the separately reviewed Ruby and C source-counter repair. No provider request or full conformance run was made.

The C header exports `thinkthen_question_file`. Its FFI edge stays in `src/ffi.rs` beside the existing guarded exports and validates both outputs before reading. A bounded read in `src/door.rs` uses 1 MiB plus one byte and the core `Question::from_json` parser. The existing owned-string handoff writes outputs only after validation, and the caller frees the string once. TypeScript exports `questionFile(path)` from CommonJS, ESM and declarations. It returns the existing frozen question value and retains the original validated source in the branded value, so numeric description keys do not reorder. Ruby's `ThinkThen.question(file: path)` returns its existing question value through a small native read child; `ThinkThen.set(path)` still loads sets. All three map file read and content errors to non-retryable Local, while invalid caller arguments and typed inline questions retain Usage. Bare text and `@`-prefixed strings are not reinterpreted as paths.

## What the build taught us

The C policy's unsafe-module rule applies to private children, so keeping the unsafe export in `ffi.rs` is the smaller compliant implementation. Its preexisting output validator removed the need for a new null-output branch. The shared strict arm makes C request identity observable without adding a test-only native loader. TypeScript's validated original JSON is part of the request identity: another JavaScript object serialization can change numeric key order. Ruby's question-file path must stay distinct from its question-set path. A selected case proves a boundary; it does not turn a historical full-run result into a new full gate.
