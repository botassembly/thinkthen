# 0474: Recognition cache admission

Recognition now shares one writing store across the records and stages of one CLI or native call. A current-schema store validates a read snapshot without taking a migration write transaction. It checks the expected index before acquiring a writer for repair. The operation retains its SQLite connection and uses `data_version` to revalidate after another connection commits. Its own writes do not trigger another full scan. Corrupt saved answers still refuse before another request. Separate calls receive separate admissions.

The reported jobs-eight recording failure and forty-second startup were not reproduced from the admitted metadata. Owned synthetic recognition runs passed jobs one and eight with fresh and populated cache and recording folders, duplicate and distinct records, and two processes sharing a cache. A generic choose run also passed those bounded cache cases. These results do not establish the cause of the reported failures.

A new two-process synthetic test exposed a separate intermittent storage error. Before correction it failed on one of sixteen isolated runs. Failure-only diagnostic output identified SQLite `SQLITE_IOERR_RDLOCK` during initialization. The pre-send write probe opened and closed the database file outside SQLite. On POSIX, that close can release another SQLite connection's locks in the same process. The probe now opens existing files through SQLite without creation and rejects SQLite's read-only fallback. It still checks directory writability before a send. The focused two-process test passed 100 consecutive runs after correction. The read-only existing-cache test returned the storage refusal with zero new requests. A fresh High code review accepted the source at `62161ace2`.

An owned eight-record cache occupied 102,400 bytes. Five fresh admissions took 9.47 to 11.87 milliseconds. An owned valid 1,024-answer cache occupied 65,748,992 bytes, about 62.7 MiB. Its fresh admission took 873 milliseconds; unchanged reuse in the same operation took 21 microseconds. An outside corruption of one answer was refused on revalidation in 460 milliseconds. These fixtures measure this row shape and machine. One initial full scan still grows with cache content; the measurements do not establish a bound for other cache shapes or reproduce the reported startup.

The functional suite included 1,773 main tests, 339 library-only tests, 23 external consumer tests, live cases, and binding smokes. The current-source focused pre-send refusal and 100-run two-process check passed. The surface rung passed Rust and C# before it was stopped after two confirmed main findings. Its C check found a formatting error in a committed test file. Its PHP check found an accepted-request-body fixture mismatch. Both affected files match main. ## What the build taught us

A permission probe must not close a raw descriptor on a database inode while SQLite connections may hold POSIX locks. SQLite-managed opens and an explicit read-only check preserve the pre-send refusal without disturbing its locks. Read-snapshot validation and an operation-owned connection remove repeated admission work while retaining external-change detection.

## Remaining

The actual reported recognition and generic choose storage errors, and the forty-second startup, remain unconfirmed. Replay still has an initial read under concurrent writers without the writing store's retry path. A separate raw new-file creation path publishes an inode before closing its descriptor; a same-process overlap is possible but was not reproduced here. Its correction needs a short guard across every SQLite connection constructor, including replay, prune, conversion, probe, and writing stores. Cache conversion and replay contention have separate PM intake. No paid call or release workflow ran.
