# Quick Fix: Observe the named address in the missing-key case

Source base `8b0e7534`. The existing `address::a_key_that_is_unset_or_empty_is_exit_four_away_from_loopback` test asserted zero connections on a listener bound to `127.0.0.1`, while its command named `https://127.0.0.2`. That listener could not observe a connection to the destination under test. The exact exit 4, `NoKey` sentence, empty stdout, unset/empty/blank key cases and `--no-cache` command were already useful and remain unchanged.

The first fix bound `127.0.0.2` directly and passed locally. The fresh code reviewer withdrew its initial ACCEPT after the coordinator identified a portability miss in that suggested fixture: [Apple's bind path](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/netinet/in_pcb.c#L839-L852) can refuse an unassigned literal address. Local Linux binding did not prove a macOS test would run without setup. The corrected test binds an ordinary nonblocking `127.0.0.1` socket and names `https://127.1:PORT/v1`, a spelling the product's textual loopback rule does not accept. `ToSocketAddrs` must resolve that name and port to the exact bound socket before the command runs. After each command exits, `accept` must report `WouldBlock`; a queued connection to the resolved destination would instead be accepted. This is a direct assertion about the destination the command named, without a product change or shared harness API.

The [Apple resolver](https://github.com/apple-oss-distributions/Libinfo/blob/main/lookup.subproj/si_getaddrinfo.c#L3475-L3491) and [short IPv4 parser](https://github.com/apple-oss-distributions/Libc/blob/main/net/FreeBSD/inet_addr.c#L925-L1027) support this direction on macOS. Microsoft's [getaddrinfo documentation](https://learn.microsoft.com/en-us/windows/win32/api/ws2tcpip/nf-ws2tcpip-getaddrinfo) describes numeric IPv4 resolution, and its [inet_addr documentation](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-inet_addr) explicitly supports two-part IPv4 forms. Those primary sources support the Windows direction but do not prove this pinned Rust/ureq route on a Windows host. The test's runtime resolution assertion will fail visibly if a supported host maps `127.1` elsewhere; no skip or host setup is added. Linux resolution and the selected test passed here.

The selected test passed on original main, on the first direct-bind correction, and on this resolver-checked correction: `cargo test --locked --offline -p thinkthen --test backend address::a_key_that_is_unset_or_empty_is_exit_four_away_from_loopback -- --exact`, under the shared heavy lock. Focused `cargo clippy --locked --offline -p thinkthen --test backend -- -D warnings` and `cargo fmt --all -- --check` pass. The root ratchet measures `84149/84149`, up from `84139`: the test file grows from 406 to 416 nonblank lines after rustfmt. The ten lines buy a destination-matched socket observation and an explicit resolver check for all three key states. I searched the adjacent address tests and shared `Listener` helper; a socket local to this one case avoids a shared API change or duplicate test matrix. No full gate, provider call or new suite ran.

## What the build taught us

An assertion about a listener is only a send proof if the command's destination resolves to that listener. The original exact refusal stayed valuable, but its connection count observed the wrong socket. The coordinator's first literal-bind recommendation overlooked Apple's assigned-address rule. The revised fixture checks resolution and uses the ordinary loopback bind. It preserves the product's distinction between a proven loopback spelling and a short IPv4 spelling that resolves to loopback.
