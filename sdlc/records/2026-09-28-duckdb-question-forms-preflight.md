## Contract and smallest proposed form

[ADR 0013](../planning/adr/0013-the-question-file-is-the-one-direct-file.md) and the [question-file specification](../../specification/question-file.md) accept complete choose/score/tag JSON, including ordered labels or levels, descriptions, cut and saved calibration profile. A typed list, where supported beside a file, replaces the entire saved list; it must not silently merge or pretend the two questions share a digest. The same specification says SQL details keep a saved question identity and a host that cannot keep it refuses before sending. The current plain-text plus SQL-list form builds a one-member `QuestionSet` named `value` and calls `annotate_with`; it cannot represent the complete file. In particular, `QuestionSetBuilder::question` rejects a member's model and profile, so routing a parsed file into that helper would discard or refuse accepted metadata. SQLite parses a full `Question::from_json`; PostgreSQL reads a file on its backend thread and joins a supplied member array before parsing. Those are evidence that the public parser can carry the form, not an obligation to copy either host's signature or override rule.

Recommend a **complete-question overload** for each listed verb: `(question VARCHAR, text VARCHAR)` with the existing optional deadline/context pattern, while retaining the current explicit `VARCHAR[]` overload byte-for-byte. The complete-question overload takes JSON or `@file`, gets its members from that question and checks the kind; plain text without members is Usage. This leaves the existing NULL-list and empty-list behavior intact and avoids making NULL or `[]` a new sentinel. The C++ scalar owner can resolve a file under the caller's authority and pass copied text plus origin to the bridge, as decide already does. Rust can use the public `Question::from_json` and `Engine::details_many_with` over the group, map `Details::value()` to the existing listed codec and keep saved model/profile, order, descriptions, threshold and actual request identity. `details_many_with` is already used by the DuckDB scalar path and avoids a new public accessor or a copied planner. Verify the current `QuestionKind`, `Judgment` and `Details` mapping before implementing; a kind mismatch must refuse before send. A separate three-argument file-plus-list override is not required to prove this minimal SQL form, and changing that accepted plain-list overload should be a distinct explicit choice if later needed. No new grammar or ADR is indicated by the present evidence.
