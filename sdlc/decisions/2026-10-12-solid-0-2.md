# Make 0.2 solid before the candidate

Date: 2026-10-12. Ian can overturn this ruling.

Ian said: "we should add that to 0.2. I feel like all the fixes should be in 0.2. Now's the time to get this release solid."

## Context

On 2026-10-12, four fresh read-only reviews looked at the 0.2 combined branch:

- **Outside-in tests and coverage.** Which tests are not outside-in, which of those are needed, and what blocks coverage near 100% from outside-in tests alone.
- **C library size.** Hand-written C library source grew from about 2,000 to about 12,500 nonblank lines. About 8,200 of those lines are export families that no language library calls, and none of them shipped in 0.1.2.
- **Hand-written growth in language libraries.** Swift, PHP, JVM, Go and C# grew because of real 0.2 session behavior. Each language also repeats the named calls, the wait loop and the error mapping by hand.
- **Generated code.** All outputs reproduce from their generators except the Swift bridge. Only some targets have drift checks. Some outputs carry unused declarations and names derived from schema paths. Some layout and naming changes alter the public ABI and types, so they must happen before 0.2 freezes them.

## Ruling

- The fixes from these reviews belong to 0.2. Tickets 0560 to 0563 carry them, and an outside-in test ticket follows once its review returns.
- A cleanup that removes or renames public API not shipped in 0.1.2 happens now, before the candidate freezes it.
- The coverage measurement becomes a committed release-suite script with recorded results. It is not throwaway work.
- 0543 cuts the candidate after these tickets land. The other 0543 rulings still apply: one revision is tested, accepted and landed, and the full campaign runs on that revision.
