# Native package design for 0.2

This design supplies the package choices for [0517](../tickets/0517-prebuilt-native-libraries-in-every-package.md) under [the binding ruling](2026-10-09-thin-first-class-bindings.md) and [the author guide](../../libraries/BINDING-AUTHOR.md). Ian can overturn these choices. It specifies distribution targets; it certifies no platform build or publication. The release hold remains in force.

## Authority and file scope

The starting target definition is the build matrix in [release.yml](../../.github/workflows/release.yml). [release-container](../scripts/release-container) establishes the Linux native baseline. [release-pack](../scripts/release-pack), [release-workflow](../scripts/release-workflow) and [release-registry.py](../scripts/release-registry.py) distinguish native, source and registry artifacts. A route that merely checks archive names does not establish a working language package.

0517 changes this decision, the two package-design references in `libraries/BINDING-AUTHOR.md`, and `sdlc/records/0517-package-design.md`. It changes no shipping definition or loader. Migrations apply this design to the existing definitions named below and their existing README files. [0501](../tickets/0501-generated-package-manifest.md) owns the shared inventory and distribution assembly. Each migration owns its installed package check. [0383](../tickets/0383-windows-node-addon.md), [0384](../tickets/0384-windows-csharp.md) and [0385](../tickets/0385-windows-jvm.md) own Windows Node, C# and JVM qualification at an authorized candidate; their exact scope remains in their ticket records.

## Platform and dependency rules

Use these platform pairs throughout this design:

| Pair | Native target | Native runtime floor |
| --- | --- | --- |
| Linux x86-64 | `x86_64-unknown-linux-gnu` | glibc 2.28 |
| Linux arm64 | `aarch64-unknown-linux-gnu` | glibc 2.28 |
| macOS x86-64 | `x86_64-apple-darwin` | macOS 15.0 |
| macOS arm64 | `aarch64-apple-darwin` | macOS 15.0 |
| Windows x86-64 | `x86_64-pc-windows-msvc` | Windows 10 or later, MSVC native runtime |

“Four Unix pairs” below means the first four rows. A language runtime can impose a newer operating-system floor; use the higher floor. No native language package claims musl, 32-bit, Windows arm64, Android, iOS, simulators or browser targets. The Linux command's existing musl archives do not establish a musl library ABI.

The C engine builds with bundled SQLite and Rust TLS dependencies as defined in [its manifest](../../libraries/c/Cargo.toml) and [the engine manifest](../../crates/thinkthen/Cargo.toml). Consumers do not install SQLite, OpenSSL or Rust to load a prebuilt library. Linux shared assets depend on the platform C runtime and compiler support runtime. Linux static consumers inherit the existing `Libs.private` system link set from `release-pack`; package integration supplies it. Apple static consumers inherit the system libraries/frameworks reported by the actual native build; the migration records that link set in its package definition before shipping. Apple consumers also have the platform C runtime; Objective-C adds Foundation and the Apple Objective-C runtime. Windows imports must be inspected by the existing DLL check. If the DLL requires the MSVC redistributable, document that runtime prerequisite; never hide a missing dependency with PATH instructions.

Preserve the native version, source build, generated header and ABI identity across each assembled package. A host package contains the library itself or links it into its extension. A source compiler for a host facade is allowed; a consumer never compiles the Rust engine. Source-only Cargo distribution remains Cargo's normal model for Rust and Rust Polars. That exception does not excuse empty native host packages.

The [GnuCOBOL project release notice](https://sourceforge.net/p/gnucobol/news/2023/08/gnucobol-32-released/) establishes 3.2 as a released baseline.

## Artifact layout and automatic loading

### Direct Rust and native extensions

Cargo packages carry source and the normal dependency graph; the consumer compiles them with Cargo. Python wheels link the Rust engine into `thinkthen._thinkthen`; pandas and Python Polars share that extension and add no native download or second engine image. npm carries its existing four `thinkthen-<os>-<arch>.node` files plus `thinkthen-win32-x64.node` under 0383 and the loader selects by host. Native platform gems carry `lib/thinkthen/thinkthen.<extension>` and ordinary `require` loads it. The diagnostic Ruby fallback remains a clear unsupported-platform failure, never a substitute native asset. R distributes installed binary packages containing `libs/thinkthen.so` or its Mac counterpart; `library(thinkthen)` loads the engine-bearing extension. Its source package remains available for source users but cannot stand in for native binary distribution.

### C, C++, Go and constrained hosts

C archives retain `include/thinkthen.h`, `lib/libthinkthen.a`, shared-library aliases and `lib/pkgconfig/thinkthen.pc`; Windows retains its generated header, DLL and MSVC import library. Installed integration uses the package-relative static archive by default, or deploys shared libraries beside the application with platform-relative search rules. C does not need a separate runtime loader API.

C++ archives include the headers, native static/shared libraries and `lib/cmake/thinkthen-cpp/` config and target files. `find_package` and `thinkthen::cpp_static` supply native dependencies automatically; make static the recommended minimal installation. The shared target's deployment copies the library into the application's `lib/` and uses `$ORIGIN/../lib` on Linux or `@loader_path/../lib` on Mac. Imported paths derive from the package prefix. Callers may select the package through ordinary CMake discovery; they never set native library variables or a runtime path.

Go module `github.com/botassembly/thinkthen/libraries/go` carries `native/<rust-target>/include/thinkthen.h` and `native/<rust-target>/lib/libthinkthen.a`. Target-specific cgo declarations select bundled files using `${SRCDIR}` and supply the native system link set. A normal `go get` followed by `go build` needs no pkg-config installation, C archive unpacking, library environment variable or Rust compiler. The existing module path and release tag scheme stay; no new module or download hook is needed.

Zig packages carry `native/x86_64-unknown-linux-gnu/include/` and `lib/libthinkthen.a`; `linkNative` derives that directory from the dependency root and supplies LLVM/LLD and system link requirements. Remove the required `-Dnative` path. Ada archives carry their generated sources, `.gpr` and package-relative `native/include/` and `native/lib/libthinkthen.a`; the exported project supplies linking. COBOL archives carry generated copybooks, host bridge objects/source and the same bundled static engine; their package build definition links the engine and platform dependencies into the host facade. None requires `LD_LIBRARY_PATH`. Native constrained declarations remain generated from Rust under the author guide; packaging introduces no new ABI.

### .NET and JVM

NuGet retains `Botassembly.ThinkThen`, one AnyCPU managed implementation and `net8.0`. Put its reference assembly at `ref/net8.0/ThinkThen.dll`, implementation at `runtimes/any/lib/net8.0/ThinkThen.dll`, and libraries at `runtimes/{linux-x64,linux-arm64,osx-x64,osx-arm64,win-x64}/native/`. Linux includes actual `libthinkthen.so` and `libthinkthen.so.0` files, avoiding reliance on a ZIP symlink; Mac includes both matching dylib names for the install identity. Windows carries `thinkthen.dll` and any redistributable dependencies authorized for package inclusion. Resolve the logical P/Invoke name through .NET's native probing of package assets. Use portable RIDs, no distribution/version RIDs or `any/native` fallback. Unsupported pairs fail before engine creation. [Microsoft's native package guidance](https://learn.microsoft.com/en-us/nuget/create-packages/native-files-in-net-packages) defines these asset conventions. Framework, NativeAOT and single-file publication require separate adoption evidence and are not advertised by this design.

Maven retains `io.github.botassembly:thinkthen-jvm`, its Java JAR and Kotlin/Scala classifiers. Add native classifier JARs `natives-linux-x64`, `natives-linux-arm64`, `natives-osx-x64`, `natives-osx-arm64`, `natives-win-x64`, each with `META-INF/thinkthen/native/<rust-target>/` containing the actual shared library and its loader-identity alias; the Windows JAR contains `thinkthen.dll` and any authorized dependent DLLs. The main POM depends on all five same-version native JARs, so an ordinary dependency resolves everything without a caller-selected classifier. Each Kotlin/Scala facade uses the same Java loader; its documented dependency includes the appropriate standard language runtime.

Compile the Java door with `--release 22` and no preview flags; compile Kotlin/Scala output against that door. The [JDK 22 FFM API](https://docs.oracle.com/en/java/javase/22/docs/api/java.base/java/lang/foreign/package-summary.html) provides the stable foreign calls. Host process OS and architecture select exactly one bundled resource. Extract it into a private directory for this loaded package, preserve the required alias, and open its absolute path through `SymbolLookup.libraryLookup`. Never search the working directory, accept a caller library path, or fetch at first call. Keep extraction and loaded-library ownership in the shared JVM door; isolate concurrent class loaders and avoid deleting files while loaded, especially on platforms that deny deletion. Native-access permission is separate from library discovery: document `--enable-native-access=ALL-UNNAMED` for classpath applications, or the binding's named module for module-path use, following [Oracle's restricted-method guidance](https://docs.oracle.com/en/java/javase/22/core/restricted-methods.html). No `--enable-preview` or `java.library.path` is required.

### Swift and Apple Objective-C

Use a C-only static `CThinkThen.xcframework` with one macOS universal x86-64/arm64 library and the generated C header/module map. The Swift source target remains the public facade; its Apple `Package.swift` dependency becomes a binary target in the package, with `.macOS(.v15)`. A trusted versioned package contains the XCFramework; a later authorized hosted Swift package may use a versioned ZIP URL and SwiftPM checksum. No Swift facade binary or library-evolution compatibility problem is introduced. [Apple's binary package guidance](https://developer.apple.com/documentation/xcode/distributing-binary-frameworks-as-swift-packages) limits binary targets to Apple platforms.

Retain Linux Swift through bundled `native/<rust-target>/lib/libthinkthen.a` and headers in the distributed Swift package. The manifest selects the Linux C target and supplies package-relative static link settings and system dependencies; it does not declare an unsupported Linux XCFramework dependency or require a separately installed system library. Static linking eliminates native runtime search paths on both routes.

The Foundation Objective-C package uses the same C XCFramework plus its own ARC source target and generated host declarations. Package it as an Apple SwiftPM library product usable from Objective-C, with Foundation declared by the host target. The GNU libobjc facade and Linux package are replaced by 0518 under Ian's ruling. Apple native linkage and Foundation behavior need Mac qualification; a GNU/Linux check cannot establish them. No iOS, CocoaPods publication, signing commitment or Apple account change follows from this design.

### PHP, Dart and Flutter

Composer retains `botassembly/thinkthen`. Its installed package contains `libraries/php/native/<rust-target>/lib/` with the actual native shared-library filenames. Both root Composer installs and the existing PHP package resolve from `__DIR__` in the installed PHP source; host detection selects the target and FFI opens only that absolute package path. No composer install script, environment path or first-call download is needed. Keep `ext-ffi` as an explicit prerequisite; an application that disables FFI receives a clear initialization failure.

Recommend the stable native-assets route for `thinkthen_dart`: Dart 3.10 or later and Flutter 3.38 or later. Retain Linux x86-64 as the only plugin target, because the repository supplies only that host application and integration. [Dart's hook documentation](https://dart.dev/tools/hooks) establishes the released hook floor and automatic native-asset bundling; [Flutter's FFI guidance](https://docs.flutter.dev/platform-integration/legacy-ffi-plugin) names the released Flutter baseline. This raises the existing 3.3/3.24 floors in the owning migration, rather than adopting an experimental hook API or claiming unbuilt platforms.

The pub archive contains `lib/`, generated declarations, `pubspec.yaml`, `hook/build.dart` and the generated version/target/checksum asset definition from 0501. Its build hook selects the target platform from the build input, obtains the version-pinned prebuilt Linux C asset from the ordinary approved distribution, verifies its checksum, puts it in the SDK-owned hook output directory and declares a dynamic code asset. It never builds the Rust engine, contacts a model backend or downloads during a call. The installed application contains the native library; SDK code-asset resolution supplies the binding, with no manual path. Offline installed-package proof supplies the matching asset through the hook's owned cache and refuses a cache miss instead of using a development tree.

The Flutter package becomes a real Linux FFI integration over that same Dart package, with `linux: {ffiPlugin: true}`, `linux/CMakeLists.txt` and native bundled-library integration where needed by the retained plugin wrapper. Replace its parent-directory path dependency with the same released Dart version. It exposes the same generated Dart classes and session API. The plugin declares no Android, iOS, Mac, Windows or web platform. The build hook owns asset acquisition and SDK bundling; the plugin must not copy a second engine image or maintain another download list. A trusted local release package can include its matching prebuilt asset for offline installation under the same definition.

The pub route needs an explicit PM exception before implementation. [Flutter's binary-plugin guidance](https://docs.flutter.dev/platform-integration/legacy-ffi-plugin) says not to upload a plugin containing binary code to pub.dev. The recommended pub archive therefore carries a version/checksum-pinned asset reference, while the installed application carries the native binary. The required exception is: for Dart/Flutter on pub, “each package carries its prebuilt native library” permits package-managed acquisition of the same-version prebuilt library during build, followed by automatic application bundling; first-call download and consumer-built Rust remain prohibited. Do not claim this exception already exists.

The alternative is a trusted bundled Git/release plugin retaining Dart 3.3 and Flutter 3.24. It avoids build-time network access and includes the binary, but fails the ordinary pub.dev distribution outcome. Recommend the stable pub route because it preserves ordinary package installation. Its concrete costs are the higher host floors, hook dependencies and a checksum-pinned build-time asset fetch/cache; it needs no paid service or new runtime framework. Publication, download implementation and removal of `publish_to: none` wait for the exception and the existing release authorization. Independent package migrations continue under their approved designs.

## Acceptance and remaining risks

Each migration installs its final local consumer artifact into an unrelated project and makes one recorded call without native path variables, build-tree access or separately unpacked native archives. Reuse existing package checks and recordings. Inspect dependency closure, selected architecture, load identity and installed contents in those checks; do not build another release or proof framework. Package facts belong once in 0501's inventory and actual package definitions. This decision provides design choices until those definitions enforce them; language READMEs link to this design instead of maintaining another platform table.

Native qualification must run on the actual Linux, Mac and Windows hosts for the advertised pairs. Linux success supplies no Apple Foundation/XCFramework or Windows DLL evidence. R binary production must use an R-compatible package build baseline, and its dependencies may raise the floor above the bare C engine. Mac static dependencies require the native link inspection described above. COBOL 3.2 compatibility and the pub exception are explicit implementation/release risks. The runtime access flag for JVM and enabled PHP FFI are host permissions, not library-path workarounds. No paid call, hosted run, registry action, tag or workflow dispatch is authorized here.
