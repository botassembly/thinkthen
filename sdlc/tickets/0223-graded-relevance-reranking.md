## Outcome and retained behavior

`rank @relevance.json --top N` accepts a valid saved `score` question with described ordered levels, judges every record, and prints original records in descending order of `score`'s own weighted value. A plain rank question and a saved `decide` file retain their yes/no request and output contracts. Every exact tie after twelve-decimal score rounding keeps input order; a later boundary tie never displaces an earlier top-N row. Graded `--details` is a score result with numeric `value`, `answer.kind: "score"`, `question.verb: "score"`, original `input`, and null threshold. It is not a yes probability; `answer.level` may differ from the weighted position. No new schema version or public probability claim is permitted. `--facts` counts judged rows even when top drops them.

Preserve existing batch, context, request-limit, replay/cache, retry, 413 split, timeout, cancellation, warning, dry-run, record-framing and stopped-run behavior. The score question changes request identity relative to yes/no rank by design. At the same stable batch boundary it must reuse the request body and digest of `score @relevance.json` over the same records. Graded top retains ADR 0093's N-winner and `jobs` pending-window row bounds; no-top retains all rows. A failed rank run still prints no partial order and reports actual completed work. Do not promise equal speculative sends after a stop, fixed RSS, or identical pause cuts on timed input.

## Proposed implementation boundary

- `cli/asked.rs::rank` may branch on the parsed file's `Verb::Score`; resolve that branch as a score question with no threshold and with the existing file batch tier. Keep the plain/`decide` path and its errors. `cli/judge.rs::rank` keeps top validation and output selection; `cli/args.rs::RankArguments` documents file-only graded input. A score file plus `--true` or `--false` needs an explicit usage refusal; do not discard those values. Existing `cli/failure.rs::QuestionKind` wording still applies to wrong `choose`/`tag` files. Check all current refusal cases in `tests/backend/refused.rs` before changing any message.
- `cli/asking/row.rs::Judging::row_of` supplies the already computed `Value::Score` as the ordering quantity for a score question, while its graded detailed view keeps that numeric value instead of the yes/no rank's null value. Keep the score result serializer and `core/answer.rs::Distribution::position`; neither the backend-reported score nor `answer.level` is the ordering value. The earlier `cli/asking.rs` location moved to this child on current main, leaving the parent at 419 nonblank lines. `cli/schedule.rs` and the `Judged` constructors in `cli/annotate/aggregation.rs`, `cli/recognize.rs`, `cli/failure/tests.rs` and `cli/schedule/top_tests.rs` need a truthful private ordering-value name if the current `probability` field is reused for the weighted position. Preserve the end-only missing-value defect and exact top-N insertion. No engine scheduler or core batch planner rewrite is planned.
- The lane now claims `cli/args/command.rs` help. The settled `specification/{rank,score,question-file,result,records}.md`, `README.md`, executable examples and site remain on the shared documentation hold; record the exact follow-up prose before that owner edits them. Keep question-file schema and corpus unchanged because the score-file grammar does not change. The Rust/binding public `Ranked::probability()` and host APIs remain yes/no; no new surface or dependency enters this build. Measure the source ratchet in the build.

Reuse `core/answer_tests.rs`, `core/order.rs`, `tests/backend/batching/tag_score.rs` and `tests/backend/keeping/rank_top.rs`; they already pin score arithmetic, stable order, score batching, top bounds and ordinary rank. `keeping.rs` and `batching/tag_score.rs` are both at 497/500 nonblank lines, so a coherent child test file is preferable to enlarging either parent. No new persistent performance, provider or full-gate campaign is warranted.

## Deferred and routing

This design is command-only because the current public `Ranked::probability()` cannot truthfully carry a level position. A separate reviewed API design would be required if a Rust or binding caller needs graded rank. Positional levels on `rank`, custom level weights and RRF are deferred, not counted done; RRF would be a transform, not another model call. Keep the issue open for those asks or split its closure explicitly after the implemented outcome is reviewed. The coordinator owns lane claims and plan rows. Fresh independent review accepted the technical proposal without findings. Ian approved the outward shape in the work plan, and ADR 0095 records that choice. Public documentation follows the marketing hold.
