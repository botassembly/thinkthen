# 0223: Rank records by a graded question

Status: technical design ACCEPT at `aecc15f2`; pending Ian's outward-facing choice. No implementation authorized by this review alone. Owner: Codex. [ADR 0095](../planning/adr/0095-rank-graded-score-questions.md) proposes the outward command shape; the [preflight](../records/0223-reranking-preflight.md) cites current main `81b145ed`. This ticket would implement ask 1 of [the open issue](../issues/2026-09-24-rank-by-graded-relevance-for-search-reranking.md). It does not settle optional per-level weights or reciprocal rank fusion. Ian may overturn the CLI-first boundary, file-only level entry, or graded detailed value before implementation.

## Outcome and retained behavior

`rank @relevance.json --top N` accepts a valid saved `score` question with described ordered levels, judges every record, and prints original records in descending order of `score`'s own weighted value. A plain rank question and a saved `decide` file retain their yes/no request and output contracts. Every exact tie after twelve-decimal score rounding keeps input order; a later boundary tie never displaces an earlier top-N row. Graded `--details` is a score result with numeric `value`, `answer.kind: "score"`, `question.verb: "score"`, original `input`, and null threshold. It is not a yes probability; `answer.level` may differ from the weighted position. No new schema version or public probability claim is permitted. `--facts` counts judged rows even when top drops them.

Preserve existing batch, context, request-limit, replay/cache, retry, 413 split, timeout, cancellation, warning, dry-run, record-framing and stopped-run behavior. The score question changes request identity relative to yes/no rank by design. At the same stable batch boundary it must reuse the request body and digest of `score @relevance.json` over the same records. Graded top retains ADR 0093's N-winner and `jobs` pending-window row bounds; no-top retains all rows. A failed rank run still prints no partial order and reports actual completed work. Do not promise equal speculative sends after a stop, fixed RSS, or identical pause cuts on timed input.

## Proposed implementation boundary

- `cli/asked.rs::rank` may branch on the parsed file's `Verb::Score`; resolve that branch as a score question with no threshold and with the existing file batch tier. Keep the plain/`decide` path and its errors. `cli/judge.rs::rank` keeps top validation and output selection; `cli/args.rs::RankArguments` documents file-only graded input. A score file plus `--true` or `--false` needs an explicit usage refusal; do not discard those values. Existing `cli/failure.rs::QuestionKind` wording still applies to wrong `choose`/`tag` files. Check all current refusal cases in `tests/backend/refused.rs` before changing any message.
- `cli/asking.rs::Judging::row_of` must supply the already computed `Value::Score` as the ordering quantity for a score question, while its graded detailed view keeps that numeric value instead of the yes/no rank's null value. Keep the score result serializer and `core/answer.rs::Distribution::position`; neither the backend-reported score nor `answer.level` is the ordering value. This file has only seven nonblank lines of headroom at main, so place any substantial new helper in a coherent `cli/asking/` child. `cli/schedule.rs` and the `Judged` constructors in `cli/annotate/aggregation.rs`, `cli/recognize.rs`, `cli/failure/tests.rs` and `cli/schedule/top_tests.rs` need a truthful private ordering-value name if the current `probability` field is reused for the weighted position. Preserve the end-only missing-value defect and exact top-N insertion. No engine scheduler or core batch planner rewrite is planned.
- Shared `cli/args/command.rs` help belongs to accepted 0210 until that owner releases it; coordinate the exact claim before implementation. After ADR acceptance, update settled `specification/{rank,score,question-file,result,records}.md` where each currently says rank only asks yes/no or score has no dependent command. Keep question-file schema and corpus unchanged because the score-file grammar does not change. Audit `README.md`, executable rank/score pages and samples for any copy that needs an exact claim; do not edit the marketing-owned site in this ticket. The Rust/binding public `Ranked::probability()` and host APIs remain yes/no; no new surface or dependency enters this proposal. Measure the source ratchet only in the later build.

## Focused proof

Use a small compiled-command table with four distinct records and the literal three-level distributions in ADR 0095. Pin weighted order `1.5, 1, 1, 0.3`, an exact top-2 boundary tie whose detailed leaders differ, original line/JSONL bytes, and score-kind numeric details. Count all listener requests and `--facts.records`. Compare a score command's request body, digest and detailed weighted value to graded rank at explicit `--batch 1`; with described levels, check the exact ordered wire criteria and dry-run plan. Add one later failed graded request under top that pins empty stdout, exit and stopped wording. Refuse a score file with typed yes/no meanings and a wrong-kind file before any listener request. Reuse `core/answer_tests.rs`, `core/order.rs`, `tests/backend/batching/tag_score.rs` and `tests/backend/keeping/rank_top.rs`; they already pin score arithmetic, stable order, score batching, top bounds and ordinary rank. `keeping.rs` and `batching/tag_score.rs` are both at 497/500 nonblank lines, so a coherent child test file is preferable to enlarging either parent. No new persistent performance, provider or full-gate campaign is warranted.

## Deferred and routing

This design is command-only because the current public `Ranked::probability()` cannot truthfully carry a level position. A separate reviewed API design would be required if a Rust or binding caller needs graded rank. Positional levels on `rank`, custom level weights and RRF are deferred, not counted done; RRF would be a transform, not another model call. Keep the issue open for those asks or split its closure explicitly after the implemented outcome is reviewed. The coordinator owns lane claims and plan rows. Fresh independent review accepted the technical proposal without findings; ADR 0095 remains proposed until Ian chooses the outward shape. No runtime edit precedes that choice.

## What the build taught us

Preparation found that `answer.level` is a modal label while `value` is a normalized weighted position; using the label or the backend's score field would silently rank a different quantity. It also found a truthful-surface boundary: Rust and host rank results promise a yes probability, so the first proposed feature stays in the command's saved score-file route. The existing batcher dispatches from `Question::Score`, and ADR 0093 already bounds top retention. `cli/asking.rs`, `keeping.rs` and `batching/tag_score.rs` are close to the 500-line source cap. These are design findings, not build results. The builder must replace this section with actual findings and adjust the scope only after a fresh design decision.
