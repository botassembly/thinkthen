# 0226: Keep caught native panic payloads out of diagnostics

Status: proposed design only at main `cd395d3f`; fresh independent High technical and security review precedes runtime claims. Owner: Codex. The [issue](../issues/2026-09-27-panic-diagnostics-can-copy-payloads-across-host-boundaries.md) stays open. [ADR 0098](../planning/adr/0098-native-panic-diagnostics.md) proposes a private scoped hook for the three remaining named routes. No product behavior is complete from these notes.

## Outcome and retained behavior

A panic caught inside the C, SQLite, or retained DuckDB C API binding must return its existing defect kind, non-retryable flag and fixed safe diagnostic without copying the payload into a C message, SQL error, JSON failed row, stdout, or stderr. A later call must work. An unrelated host thread must still reach the hook it installed before ThinkThen's hook. No panic unwinds across a native ABI. The six error kinds, ordinary error texts, cancellation and deadline behavior, and each host's callback and C++ exception policies remain. This ticket adds no public fault switch, API or general panic framework. C shared-library residency may require one direct use of the already locked `libc` crate; High review must assess it before a runtime claim.

The landed Linux x86-64 DuckDB C++/Rust bridge already uses a once-installed delegating hook, private bridge depth and fixed defect; the engine separately scopes its own public and worker panics under ADR 0081. Preserve that checked route. The three older DuckDB release packages still use `src/errors.rs::guarded` and `src/worker.rs`. A source correction on the Linux C++ path would require its own new evidence, not follow automatically from this ticket.

## Proposed private boundary

Each affected binding installs one delegating Rust hook once before executing owned work. The hook checks a thread-local nesting depth: suppress the previous hook only while that binding owns a Rust callback or its detached worker; delegate on other threads. A drop guard restores the prior depth through normal return or unwind. Scope must enclose `catch_unwind`, fixed-error conversion and disposal of the caught payload, so a payload drop does not outlive the marker. Keep the hook's code resident for the process lifetime; never swap it per call or replace the host's unrelated diagnostics. SQLite already calls `ffi.rs::pin`, but only **after** registration; make this pin fallible and move it before installing the hook, including on a failed load. A dynamically loaded C door also needs a retained self-reference before hook installation; its static archive is part of the host image. The pinned DuckDB v1.5.5 loader opens old C API extensions with `dlopen` and its extension source has no `dlclose` path, which must be verified on each packaged target. A later host hook replacement or simultaneous competing install can bypass the wrapper; record that process-global limit rather than promise impossible ownership. The builder must inspect callback crossings and preserve any host Rust callback's own hook policy; current C pointer calls, SQLite's C `sqlite3_is_interrupted` predicate, and old DuckDB's atomic SIGINT predicate expose no Rust host callback to mask.

- **C:** `ffi.rs` routes exported work through `failures.rs::guard`, including `thinkthen_engine_new_with` around `built`. Keep one caught-panic conversion and its per-engine/per-thread last-error table. Remove `&str`/`String` payload extraction from `guard`; use a fixed `defect: a panic crossed the C door` message. `built` already returns fixed `defect: a panic built no engine` on its inner catch; the outer guard's scope must cover it. Its null-engine fallback and error-pointer lifetime remain as documented. The hook closure belongs to the shared library: a host `dlclose` after a call must not leave the global hook pointing into unloaded code. A private self-retain on dynamic load, with static-link behavior verified separately, is a prerequisite; the existing locked `libc` crate is the narrow system API candidate and needs direct C manifest/lock/dependency review.
- **SQLite:** `lib.rs::guard` is the one shared catch for scalar, settings, table callbacks and `worker.rs::spawn` on its own thread. Wrap that catch in the private scope and return one fixed `a panic crossed the SQLite boundary` defect without payload or function argument. Keep `Failure::value()` unable to turn Defect into a try-value cell. The detached worker must enter its own scope; caller thread-local state cannot cover it. `ffi.rs::sqlite3_thinkthen_init` is a distinct load entry using `extension_init2`; pinned `rusqlite` 0.40.2 does not catch a panic there. Route that exported call through the **same** `guard` after its non-panicking API pointer store, mapping an unexpected panic to `SQLITE_ERROR` and a fixed safe load diagnostic while leaving ordinary `extension_init2` errors unchanged. Install the hook before callbacks are registered; add no second catch site or public test switch. Prove the exact load mapping if the native host can expose it, and do not treat the callback child as proof of that separate path.
- **Older DuckDB C API:** `errors.rs::guarded` is the one callback catch; retain its callback name but replace payload text with fixed `thinkthen defect: the <callback> callback panicked`. `worker.rs::run_typed` starts a detached thread outside that callback's thread-local depth. Put that worker's owned closure through the same `guarded` boundary and map only its fixed caught defect to `RowError`, retaining the six-kind mapping for ordinary engine errors and existing cancellation/closed-channel results. Keep one `catch_unwind` site in `src` as `tools/source_checks.py` requires. The old `test-hooks` feature is test-only and prohibited in shipped packages; use a private unit child instead of enlarging it.

The hook scopes belong to these private binding modules. ADR 0081's engine and C++ hooks can nest through their previous-hook chain. Verify with a child process rather than assuming load order or that markers flow to workers. Do not copy the small scope implementation into a shared public crate merely to save a few lines.

## Focused proof and completion

One private child-process synthetic-marker test per affected binding exercises its actual guard and, for SQLite and old DuckDB, a worker closure on the separate thread. The child installs a prior host hook before entering the binding scope. It catches a planted string marker, checks exact fixed defect and non-retryable classification through the binding's returned error representation, makes a later successful call, and triggers an unrelated thread panic that must reach the prior hook. The parent captures the whole child stdout and stderr and asserts that the synthetic marker is absent from both and from the returned error; the unrelated host marker must be visible only in the prior-hook record. Use the existing test binary's selected child mode, as `public/options.rs` does, not a production test hook or duplicate HTTP harness. C's routine crate tests, SQLite's `cargo test --lib`, and the retained C API crate's focused unit test are the smallest executable source proofs. Keep one distinct test per binding because their error conversions and worker ownership differ; replace the current C, SQLite and old DuckDB assertions that require payload text. No loopback send or provider is needed for the synthetic fault; ordinary installed smoke paths retain their existing loopback checks.

For completion, run focused format, strict binding lint/policy/source caps and these child tests, then verify C and SQLite packaged or installed native artifacts against their current host. C's child must check a dynamically loaded library remains safe after the host releases its handle and must distinguish its static archive. SQLite's child must check both successful and failed load do not leave a dangling hook, with the load result mapped safely. A Linux x86-64 `databases/duckdb/check.sh` checks the **C++** artifact and cannot prove an old C API package. The retained C API archives target Linux ARM64 and macOS x86-64/ARM64 through `release-pack`; their actual stock v1.5.5 hosts, target toolchains, ABI metadata and installed package checks are prerequisites. If a target is unavailable, record its source child result separately and leave that package unproved. No full surfaces rung, panic campaign or paid call is part of this proof.

## Dependencies and deferred gaps

The runtime builder must refresh main and exact claims after High review, then coordinate C `failures.rs`/`ffi.rs`, its `Cargo.toml`/`Cargo.lock` if direct `libc` is necessary, SQLite `lib.rs`/`ffi.rs`, old DuckDB `errors.rs`/`worker.rs`, the three private child tests, local ratchets and any selected package checks. ADR 0081 and the landed engine worker scope are prerequisites already present on `cd395d3f`; no engine, C++ bridge or `policy.py` change is proposed. The SQLite load edit needs an exact runtime claim and a narrow host mapping check. The C residency dependency needs a second reviewer and a pinned Linux/macOS mechanism; stop that slice if no safe self-retain can be shown. The bounded other-binding scan found R `thinkthen/src/rust/src/calls.rs::on_worker` still copies a caught payload, while Python, Ruby and TypeScript return fixed defects but do not locally suppress their pre-catch hook. These are separate binding risks, not evidence that the three named issue rows are fixed or that every port is secret. Root should route them explicitly; this ticket does not quietly close them.

## Evidence

- Starts from: the open panic-diagnostics issue, current main `cd395d3f`, ADR 0081 and the landed 0201 Linux C++ bridge and engine diagnostic scopes; exact current paths and caps are in the [preflight](../records/0226-panic-preflight.md).
- Keeps: six error kinds, non-retryable Defect, fixed safe returned messages, later-call recovery, ABI containment, unrelated host-hook delivery, host callback and C++ exception policy.
- Changes: proposes private once-installed delegating hooks and scoped caught-panic conversion in C, SQLite and older DuckDB C API, with safe library residency; no public API, and one reviewed direct C `libc` dependency only if its dynamic loader needs it.
- Proof: one bounded selected child per affected binding checks synthetic payload absence from returned error/stdout/stderr, exact defect and later success, detached-worker coverage where applicable, and unrelated prior-hook delivery; target package evidence is separate.
- Defers: runtime and fresh High code review, old DuckDB target package validation, exact SQLite load-path host proof after claim, and the other-binding risks found in the bounded scan.

## What the build taught us

Design preparation only. The old issue was accurate for the three named guard payload copies, but main has since landed Linux C++ and engine diagnostic scopes. The first tempting edit, replacing error text after `catch_unwind`, would still allow the hook to print before the catch. The C++ pattern supplies a small local model; SQLite and the older DuckDB worker each need their own thread marker. An initial call-path inventory also missed the SQLite load entry and the older DuckDB worker's closure outside the callback thread. The pinned `rusqlite::Connection::extension_init2` source confirmed that load itself has no catch, so the same guard must cover it. A later teardown check found that SQLite pins only after registration and the C shared library has no self-retain; a global hook must not outlive either library's code. High review should check scope, hook chaining, payload disposal, residency and package routes before any source is claimed. Preparation saved work only if the later build and review avoid another leaked marker or a false all-platform claim.
