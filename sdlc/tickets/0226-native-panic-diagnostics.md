# 0226: Keep caught native panic payloads out of diagnostics

Status: in progress. Source correction and evidenced Linux x86-64 C/SQLite packages land after fresh independent High code review ACCEPT at `d0709b69`. Owner: Codex. The ticket and linked issue remain open for macOS C/SQLite and retained DuckDB Linux ARM64/macOS installed-package proof. [Code review](../records/0226-code-review.md) and [build record](../records/0226-build.md) distinguish source, child and package evidence. Accepted ADR 0098 preserves current loader lifetime; no all-platform completion is claimed.

Milestone: 0.1

## Outcome and retained behavior

A panic caught inside the C, SQLite, or retained DuckDB C API binding must return its existing defect kind, non-retryable flag and fixed safe diagnostic without copying the payload into a C message, SQL error, JSON failed row, stdout, or stderr. A later call must work. An unrelated host thread must still reach its prior hook. No panic unwinds across a native ABI. The six error kinds, ordinary texts, cancellation, deadline, host callback and C++ exception policies remain. No public fault switch, API or general framework is added.

The landed Linux x86-64 DuckDB C++/Rust bridge already uses a once-installed delegating hook, private bridge depth and fixed defect; the engine separately scopes its own public and worker panics under ADR 0081. Preserve that checked route. The three older DuckDB release packages still use `src/errors.rs::guarded` and `src/worker.rs`. A source correction on the Linux C++ path would require its own new evidence, not follow automatically from this ticket.

## Accepted private boundary

Each affected binding installs one delegating Rust hook once before owned work. Thread-local depth suppresses the previous hook only during binding-owned work and delegates on unrelated threads; a guard restores depth on return or unwind. Scope encloses `catch_unwind` and fixed-error conversion. Every caught `Box<dyn Any + Send>` is opaque: **forget it while scope is active**, including C's inner `built` catch, so its destructor cannot panic across the native door. This leaks one payload per caught panic, may retain private bytes in memory and accumulate under repeated defects; it does not erase them. SQLite and old DuckDB keep one catch site. The representative packaged Linux C artifact has DSO-local Rust hook state and can unload after its calling thread exits; neither C self-retention nor SQLite failed-load pinning is justified by that evidence. Keep SQLite's existing post-registration pin for detached workers. Refresh actual artifact linkage and loader behavior, especially macOS. If a supported artifact proves cross-DSO hook ownership, obtain a reviewed host-visible lifetime decision before adding a pin. The pinned DuckDB v1.5.5 loader opens old C API extensions with `dlopen` and shows no `dlclose` in its extension source; verify each package. Later host-hook replacement or simultaneous installation can bypass the wrapper. Preserve host callback policy; current C pointer calls, SQLite C interrupt predicate and old DuckDB atomic SIGINT predicate expose no Rust host callback to mask.

- **C:** `ffi.rs` routes exported work through `failures.rs::guard`, including `thinkthen_engine_new_with` around `built`. Keep one caught-panic conversion and its per-engine/per-thread last-error table. Remove payload extraction from `guard`; use fixed `defect: a panic crossed the C door`. `built` already returns fixed `defect: a panic built no engine`; both catches forget the opaque payload inside marked scope. Preserve null-engine fallback and error-pointer lifetime. Inspect the changed dynamic artifact's hook linkage and loader result; the earlier Linux artifact does not warrant a C self-retain or direct `libc` dependency.
- **SQLite:** `lib.rs::guard` is the one shared catch for scalar, settings, table callbacks and `worker.rs::spawn` on its own thread. Return fixed `a panic crossed the SQLite boundary` without payload or function argument, preserving Defect outside try-value cells. The worker enters its own marked scope. `ffi.rs::sqlite3_thinkthen_init` is a separate load entry whose pinned rusqlite 0.40.2 helper does not catch; route it through the same guard after its non-panicking API pointer store. Map only unexpected panic to fixed safe `SQLITE_ERROR` and preserve ordinary load errors. The existing successful-registration pin remains for detached workers; no failed-load pin is proposed.
- **Older DuckDB C API:** `errors.rs::guarded` remains the one callback catch and retains its callback name with fixed `thinkthen defect: the <callback> callback panicked`. Route `worker.rs::run_typed` work through that same boundary on its detached thread; map only its fixed caught defect to `RowError`, preserving ordinary six-kind mapping and cancellation/closed-channel results. Keep one `catch_unwind` site in `src` as `tools/source_checks.py` requires. The old `test-hooks` feature remains test-only and prohibited in shipped packages.

The hook scopes belong to these private binding modules. ADR 0081's engine and C++ hooks can nest through their previous-hook chain. Verify with a child process rather than assuming load order or that markers flow to workers. Do not copy the small scope implementation into a shared public crate merely to save a few lines.

## Focused proof and completion

One private child-process synthetic-marker test per binding exercises its actual guard and, for SQLite and old DuckDB, its separate worker thread. The child installs a prior host hook. It catches a string marker **and** a payload whose `Drop` panics with a distinct marker, checks exact fixed non-retryable defect through the binding's returned error, makes a later successful call, and triggers an unrelated thread panic that reaches the prior hook. The parent captures stdout and stderr and asserts neither payload marker appears there or in the returned error; the unrelated host marker appears only in the prior-hook record. Use an existing selected child mode, not a production fault switch or duplicate harness. Replace stale tests expecting payload text. No provider call is needed.

For completion, run focused format, strict binding lint/policy/source caps and these child tests, then verify packaged native artifacts. Inspect C's changed dynamic artifact hook symbol/linkage, loader flags and release result; distinguish its static archive. SQLite installed proof must check the **exact** pinned stock-host load result: successful load and later call, below-floor failed load and later host operation, plus DSO residency after both paths. Run on Linux `.so` and supported macOS `.dylib`; current `check.sh` is Linux-specific, so leave macOS installed proof open if its host/package is unavailable. Select the existing pinned `test_schema.py` failed-load assertion in the installed route rather than assuming examples/conformance invoke it. Linux x86-64 `databases/duckdb/check.sh` checks the **C++** artifact, not an old C API package. Retained C API archives target Linux ARM64 and macOS x86-64/ARM64 through `release-pack`; actual stock v1.5.5 hosts, matching toolchains, ABI metadata and installed package checks are prerequisites. Record unavailable targets as unproved. No full surfaces rung, panic campaign or paid call is part of this proof.

## Dependencies and deferred gaps

The reviewed source covers C `failures.rs` and its private test, SQLite `lib.rs`/`ffi.rs` plus the worker test module and selected installed tests, old DuckDB `errors.rs`/`worker.rs`, their private children and measured local ratchets. Later package proof must use this source and coordinate any new exact file claims. ADR 0081 and landed engine worker scope are prerequisites already present; no engine, C++ bridge, 0212 public/engine call-facts files, C `Cargo.toml`/`Cargo.lock`, or `policy.py` edit is proposed. SQLite load has exact successful and below-floor Linux host mapping proof; macOS remains open. The bounded other-binding scan found R `thinkthen/src/rust/src/calls.rs::on_worker` still copies a caught payload; main `c96f905e` separately filed [the R issue](../issues/closed/2026-09-28-r-worker-panic-can-copy-payload-text.md). Python, Ruby and TypeScript return fixed defects but do not locally suppress their pre-catch hook. These separate risks remain open.

## What the build taught us

The old issue remains accurate for the three guard payload copies, but Linux C++ and engine diagnostic scopes have landed. Replacing error text after `catch_unwind` would still let the hook print first. SQLite and older DuckDB workers need their own thread marker; SQLite load needs the same guard. The first review caught an opaque payload whose `Drop` can panic after catch, missing macOS SQLite package proof, and unverified host-visible pin choices. The changed Linux C artifact also has local Rust hook state and unloads after a joined caller thread and `dlclose`; the changed SQLite package passes separate successful and rejected load cases. These observations support the accepted no-extra-pin design only on this Linux target. Each caught payload remains allocated by design, so repeated native defects can retain memory. The later Python/Ruby/TypeScript hook risks have their own [issue](../issues/closed/2026-09-28-binding-panic-hooks-can-print-caught-payloads.md); R remains separately filed. Neither expands this build. The [build record](../records/0226-build.md) holds measured proof and platform remainders.
