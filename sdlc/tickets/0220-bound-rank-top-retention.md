## Outcome and retained contract

With `rank --top N`, retain at most N winning `Judged` payloads after each ordered output callback. An incoming row with a lower score than the current Nth row is dropped; a later exact tie at that boundary never displaces an earlier row. Keep the bounded input, worker and completed-batch pipeline independent of total file length, even when the earliest request stalls and later requests finish. On a completed finite input with stable batch boundaries, every eligible record is judged and the logical request plan, bodies, digests, count, output bytes, stable order, detailed rows and usage/facts remain identical. Concurrent transport arrival order may vary today and is not a new promise. `rank` without `--top` keeps its current all-row accumulation and scheduling mode. A single input record can still be large; this is a bound on retained *row count* across a long file, not a fixed process-byte limit or a change to recording/cache storage.

Bounded admission necessarily limits speculative work: before a failure or cancellation, held-all may have sent later requests that held-windowed has not. A timed input pause may also close a batch at another point when backpressure shifts the read. Preserve the existing failure and cancellation kinds, exit codes, accurate stopped-at/finished/replayed metadata for work actually done, empty rank stdout on stop, warning rules, and per-attempt retry/413 handling. Do not assert equal speculative sends, counters or timed batch boundaries across the two modes.

The engine's existing `held` boolean conflates two decisions: `Run::waiting(true)` counts only in-flight work, while `Outcome::Stopped.held` tells the CLI that rank printed nothing. A stalled first batch allows later completed batches to collect without bound in `Run.pending`, even if the final output vector keeps only N. Use one private three-way record-flow value: streaming, held-all (rank without top), and held-windowed (rank with top). The last reports `held=true` on stop but admits new work only while `dispatched - next < jobs`, including completed batches waiting behind an earlier one. It does not change the worker pool, batching planner or transport.

In the CLI output sink, keep the top-N rows in descending `f64::total_cmp` order and insert a later exact equal score after earlier equal rows. If N winners are already present, reject a candidate no better than the last; otherwise remove that last winner before insertion. Keep `usage.record_done()` for every completed row, including one dropped from the winners. Preserve the existing end-only missing-probability defect: remember if any ranked row lacks a probability and return the same defect at successful end before printing, even when that row was discarded. Reuse `core::order::ranking` on the at-most-N winners at the end, or prove an equivalent final order; do not introduce a second request or batch planner. Warnings remain tied to rows actually printed.

## Focused proof and limit

Use one outside-in edge table with literal expected output for `--top 1`, a boundary tie under `--top 2`, and `--top` above the input size. On completed finite input with stable batch boundaries, include unchanged line/JSONL bytes and `--details` membership, count every listener request, and compare `--jobs 1` with a parallel job setting. Reuse `keeping.rs` helpers and its existing no-top order, top membership, failure, dry-run and invalid-argument tests; do not copy their matrix. Add one failed later record after a completed prefix under `--top` that pins empty stdout and the stopped sentence with accurate metadata; do not demand the old speculative-send count. A batch-one form exercises the batched CLI route; a CSV/TSV focused row is needed only if its path is not covered by the same sink and existing table tests.

A private sink invariant must fail if a plant restores `held.push(judged)` for all rows: after every callback, retained winner count is at most N while completed-row counts still advance. A small stalled-first-batch case, using the existing loopback held reply and an acknowledged later completion, checks that the reader/transport does not keep pulling past the configured `--jobs` window before release; after release it must finish all records and print the same order. This real-boundary witness complements the source invariant: finite fixtures cannot measure peak process memory or prove every possible thread schedule. Inspect `Run::request`, `Run::pending`, the 64-record feed, batch member cap, output vector and end sort together in review. No test-only product flag, repeated saturation/churn run, broad gate or provider call is needed. Use focused formatting, Clippy/test targets and affected documentation checks after implementation under the heavy lock.

## What the build taught us

The accepted three-way flow kept the stop's `held` metadata separate from its admission window. The top sink needed a missing-probability marker: dropping a defective row to satisfy N must still return the old end-only defect before printing. Strict Clippy caught nested winner insertion and led to one small `keep_top` helper. The sink invariant reads the retained vector after every callback and checks that all five rows still enter the process facts; the loopback witness holds the first response, acknowledges the second, and sees no third request with `--jobs 2` until release. Neither finite test measures peak RSS or every thread schedule; the source invariant supplies the general row-count argument. The [build record](../records/0220-build.md) names the focused checks, measured growth and unchanged no-top evidence. Fresh code review found no blocking gap after tracing both bounds and their limits. Integration and plan closure remain with the coordinator.
