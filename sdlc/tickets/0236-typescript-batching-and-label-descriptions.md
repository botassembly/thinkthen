# 0236: Batch TypeScript calls and preserve described labels

Status: Prepared for fresh design review at main `0ad07ff4`. This ticket combines B12d and J3 in the same TypeScript source lane under accepted ADRs 0082 and 0089. It authorizes no runtime edit by itself. The [preflight](../records/0236-typescript-batching-preflight.md) records the current constructors, consumers, counters and overlap. Owner: Codex.

## Outcome and retained behavior

Every asking `Engine` method and matching module delegate returns one typed result whose `.value` is exactly the former answer and whose final `.facts` and owned ordered question detail cover that call without a second model request. Add an engine `batch` setting and per-call `batch` on eligible many-record methods. Add per-call shared-text `context` only on methods the landed Rust planner accepts. Default Max packing is already inherited through `EngineBuilder::from_env` on current bulk routes; this ticket exposes selectors, result ownership and the missing runtime-label many routes rather than building another scheduler. A no-context `batch: 1` preserves existing request bodies, digests and strict replay identity. Keep all six named error kinds, retryability, `null` for unsure or unselected, numeric score, empty successful tag list, distinct failed annotate member, UTF-16 recognition offsets, original input order and JavaScript-owned record identities.

J3 accepts ordered bare strings, readonly tuples and described label maps for `options`, `labels`, `levels` and `kinds`, with string or structured `{what, not_for, examples}` descriptions. Keep the native version-one question parser as the grammar and final validation authority. Preserve supplied label order through JavaScript normalization and the native request. Do not turn a bare score level into explicit null: a score list sends its level name, while a score map entry with `null` sends the parser's explicit no-description form. A mixed bare/described form must preserve which members were bare. Omitted and explicit null inputs must be tested separately; do not use `??` or stringify omission to silently accept a forbidden optional field. The declared TypeScript input and output types must describe the actual accepted runtime forms, including readonly tuples and the existing precise null/failure unions.

## Proposed host contract

1. `new Engine({ batch })` accepts `"max"` or a positive safe integer. Omission keeps `EngineBuilder::from_env` selection, including `THINKTHEN_BATCH`; an explicit valid engine option overrides that tier. A per-call `batch` overrides the engine and saved question setting. Reject `0`, negatives, fractions, booleans, null, nonfinite values and unsupported strings as `usage` before sending. Validate the selected setting once, after precedence is known; an overridden bad environment value must not mask a valid explicit value. `context` is a nonblank well-formed JavaScript string, sent as text rather than read as a file. It changes the request digest and not the question digest. Check host value type and lone surrogates before the native crossing; let Rust enforce content and request limits. JavaScript strings do not have Ruby's byte-encoding path, so copy no Ruby UTF-8 conversion rule.
2. Accept `batch` and `context` on `decide_many`, `filter`, `rank`, and new `choose_many`, `score_many`, `tag_many`. Accept `batch` but reject `context` on `annotate`. Reject both keys, including present `null` or an empty options object's unsupported key, on scalar `decide`, `choose`, `score`, `tag`, `details`, and on `find`, `recognize`, `relate`. `find` is one bounded selection, not the many-record planner. Preserve `signal`, `deadlineMs`, `rank.top`, `find.none`, recognition and relation options on their existing routes. `question`, `usage` and `new Engine` are not asking calls. Apply the same route table to methods and module delegates; no key may be silently ignored.
3. Add eager `choose_many`, `score_many`, `tag_many` for a question or bare question text plus its ordered runtime labels, and records. Use landed `Engine::details_many_with` and exhaust its stopping iterator before publishing final facts; compile-time Rust `Choice` cannot represent JavaScript runtime labels. Preserve `string | null` choices, numeric scores and ordered tag arrays, including an empty tag answer. A terminal failed row rejects once, with no partial success array. Existing `decide_many`, `filter` and `annotate` must likewise exhaust their lazy Rust batches before reading final `Batch::facts()`; `rank(top)` trims only `.value`, while facts and detail include every judged candidate. Retain original JavaScript strings and index mapping in `.value`, rather than substituting Rust copies.
4. On success return a `Call<T>` shaped object with immutable `.value`, `.facts` and `.details`. `Facts` has `records`, `requests_sent`, `cache_answers`, optional `input_tokens`, `output_tokens`, `seconds` and optional `model`. Omit token and model fields when the provider did not report them; never infer them from `usage()` deltas. `.details` is an ordered, owned snapshot of the existing Rust observation stream. Each completed question retains its zero-based row, optional annotate member or recognition stage/position, question digest, typed answer or failed cause, declared-order probabilities, optional confidence, model, URL, exact request digests, per-question attempt and usage shares, cache flag and failed-question count. Filtered-out and top-trimmed rows still contribute. Stop detail at the ordered terminal row; final facts include any later in-flight attempts joined by Rust. The existing `details()` value remains the `thinkthen.result/1` object inside `Call.value`, not a replacement for call detail. Do not place raw evidence, context or key in an error or debug representation.
5. A Rust failure after accounting begins retains its six-kind `ThinkThenError` and final frozen `.facts` plus `.details`, including truthful zero-send facts. Pre-accounting validation or a caught panic without retained accounting has absent facts, even if a Node worker already started. A conversion failure after a completed Rust call retains that completed account. The current `invoke` races `AbortSignal` and calls `CallHandle.detach()`, which closes the only native completion channel. Keep prompt caller rejection, listener cleanup, worker cancellation, no later admission and Node's ability to exit after an unobserved early stop. For an early caller abort whose worker was started, attach one optional completion receipt to that same error; a caller who awaits it obtains final failure identity, facts and ordered detail only after the original worker has joined, without another request. Pending receipt state must not masquerade as final zero. An already-final Rust error needs no redundant receipt. Specify the smallest Node-API lifetime and unref behavior in source review so a late callback can resolve an observed receipt without keeping an otherwise idle process alive. Preserve signal reason as the cancellation cause and the current same-tick precedence.
6. For labels, accept the existing arrays and JSON object maps, and an insertion-ordered JavaScript `Map` if the TypeScript API promises that form. Normalize `Map` before `JSON.stringify` so it does not become `{}`. Trace the native parser's order preservation rather than assuming a plain object's enumeration order for integer-like keys; use an ordered entry form or refuse an order that JSON objects cannot preserve if necessary. Keep a described `recognize.kinds` route and distinguish absent `kinds` from explicit null. Validate structured fields against the version-one schema and host types; a value such as `undefined` must not disappear during JSON serialization and turn an invalid supplied option into an omitted one. Existing output union, failed marker, error names and UTF-16 offset conversion stay intact.

## Evidence

- Starts from: Accepted ADRs 0082 and 0089, landed Rust 0212 and dynamic-details 0230, Python 0214's final facts and completion precedent, Python 0233's bare-versus-null correction, and Ruby 0234's held-batch/account-start correction. The current TypeScript boundary and exact counter headroom are in the preflight.
- Keeps: All existing ten semantic verbs and the `decide_many` surface, module delegates, bare answers inside `.value`, six error names, old one-record wire identity and host-owned input order.
- Changes: TypeScript batch/context selectors, runtime-label many calls, typed success/failure facts and detail, truthful early-abort completion, and ordered described input forms.
- Proof: Captured packed and historical request bodies, one route/refusal table, one ordered-label table, one held completion boundary, retained conformance fixture bodies and affected type consumers.
- Defers: Marketing-owned site TypeScript sample migration through the existing site issue, R's B12f/J6 work, SQL per-call facts, vendor timing/request ID and cost pricing, and measured speed/accuracy claims. This design does not close the broader batching or run-facts issues.

## What preparation taught us

Current TypeScript bulk callers already inherit `Max`; missing host options and bare result conversion are the gaps. `src/door.rs` is only 50 nonblank lines below the per-file limit, so an owned observation/result child is likely smaller than enlarging the door. `index.js` races away the sole native callback on early abort, making a completion receipt a real ownership change rather than a field on the old error. A Node worker's creation does not prove Rust accounting began. Existing held tests assert four sends but batch one is interactive; they need a separate batch-two setup, while legacy corpus bytes stay batch one. The Python score correction proves that bare level and explicit null have different request identities; the TypeScript wrapper must check both before selecting a map normalization. These are source observations and prospective checks, not completed implementation or timing gains.
