# 0236: Batch TypeScript calls and preserve described labels

Status: Implemented and accepted after fresh High code review of `b84ff2de17b8d7d8cf40483d3fe5a3f3b1bffd83`. The coordinator lands B12d and J3 with the focused proof in the [build record](../records/0236-typescript-build.md) and [code review](../records/0236-code-review.md). High design review accepted `5283cfe3`; implementation preserves ADRs 0082 and 0089. The [preflight](../records/0236-typescript-batching-preflight.md) retains source and preparation evidence. Marketing-owned site consumers remain with their existing issue. Owner: Codex.

## Outcome and retained behavior

Every asking `Engine` method and matching module delegate returns one typed result whose `.value` is exactly the former answer and whose final `.facts` and owned ordered question detail cover that call without a second model request. Add an engine `batch` setting and per-call `batch` on eligible many-record methods. Add per-call shared-text `context` only on methods the landed Rust planner accepts. Default Max packing is already inherited through `EngineBuilder::from_env` on current bulk routes; this ticket exposes selectors, result ownership and the missing runtime-label many routes rather than building another scheduler. A no-context `batch: 1` preserves existing request bodies, digests and strict replay identity. Keep all six named error kinds, retryability, `null` for unsure or unselected, numeric score, empty successful tag list, distinct failed annotate member, UTF-16 recognition offsets, original input order and JavaScript-owned record identities.

J3 accepts ordered bare string arrays and readonly tuples, plus JSON object maps for `options`, `labels`, `levels` and `kinds`. A description may be a string, object, list or null. Objects and lists may hold nested JSON values; `{what, not_for, examples}` is a common form, not a closed grammar. The order of an object map is its observable JavaScript own-property order from `Object.entries`, including integer-like keys; preserve that order through native parsing and the request. The contract does not add a JavaScript `Map` input. Keep the native version-one question parser as the grammar and final validation authority. Do not turn a bare score level into explicit null: a score list sends its level name, while a score map entry with `null` sends the parser's explicit no-description form. Omitted and explicit null inputs must be tested separately; do not use `??` or stringify omission to silently accept a forbidden optional field. The declared TypeScript input and output types must describe the actual accepted runtime forms, including readonly tuples and the existing precise null/failure unions.

## Proposed host contract

1. `new Engine({ batch })` accepts `"max"` or a positive safe integer. Omission keeps `EngineBuilder::from_env` selection, including `THINKTHEN_BATCH`; an explicit valid engine option overrides that tier. A per-call `batch` overrides the engine and saved question setting. Reject `0`, negatives, fractions, booleans, null, nonfinite values and unsupported strings as `usage` before sending. Validate the selected setting once, after precedence is known; an overridden bad environment value must not mask a valid explicit value. `context` is a nonblank well-formed JavaScript string, sent as text rather than read as a file. It changes the request digest and not the question digest. Check host value type and lone surrogates before the native crossing; let Rust enforce content and request limits. JavaScript strings do not have Ruby's byte-encoding path, so copy no Ruby UTF-8 conversion rule.
2. Accept `batch` and `context` on `decide_many`, `filter`, `rank`, and new `choose_many`, `score_many`, `tag_many`. Accept `batch` but reject `context` on `annotate`. Reject either unsupported key whenever present, including a value of `null`, on scalar `decide`, `choose`, `score`, `tag`, `details`, and on `find`, `recognize`, `relate`. `find` is one bounded selection, not the many-record planner. Preserve `signal`, `deadlineMs`, `rank.top`, `find.none`, recognition and relation options on their existing routes. `question`, `usage` and `new Engine` are not asking calls. Apply the same route table to methods and module delegates; no key may be silently ignored.
3. Add eager `choose_many`, `score_many`, `tag_many` with the existing `asked, records, lastOptions` argument order. The bare-text overloads are `choose_many(question: string, records: readonly string[], options: ChooseManyOptions)`, `score_many(question: string, records: readonly string[], options: ScoreManyOptions)` and `tag_many(question: string, records: readonly string[], options: TagManyOptions)`; each last object requires its `options`, `levels` or `labels` field respectively and may carry `batch`, `context`, `signal` and `deadlineMs`. Their question-value/spec overloads take the same first two arguments and optional `ManyCallOptions` last, refusing duplicated label input there. The existing `decide_many`, `filter` and `rank` take `ManyCallOptions` last; `annotate` takes `AnnotateCallOptions` with batch but no context. Scalar overloads retain their current argument order and `CallOptions`, with no batch/context; `find`, `recognize` and `relate` retain their own option types and refuse those keys. Every asking overload returns `Promise<Call<oldValueType>>`; `usage()` remains the direct `Usage` read. Use landed `Engine::details_many_with` and exhaust its stopping iterator before publishing final facts; compile-time Rust `Choice` cannot represent JavaScript runtime labels. Preserve `string | null` choices, numeric scores and ordered tag arrays, including an empty tag answer. A terminal failed row rejects once, with no partial success array. Existing lazy calls must likewise exhaust their Rust batches before reading final `Batch::facts()`; `rank(top)` trims only `.value`, while facts and detail include every judged candidate. Retain original JavaScript strings and index mapping in `.value`, rather than substituting Rust copies.
4. On success return a `Call<T>` object with readonly `.value: T`, `.facts: Facts` and `.details: readonly QuestionObservation[]`; the facts and observation snapshot are owned and frozen. `Facts` has `records`, `requests_sent`, `cache_answers`, optional `input_tokens`, `output_tokens`, `seconds` and optional `model`. Omit token and model fields when the provider did not report them; never infer them from `usage()` deltas. Each completed question observation retains its zero-based row, optional annotate member or recognition stage/position, question digest, typed answer or failed cause, declared-order probabilities, optional confidence, model, URL, exact request digests, per-question attempt and usage shares, cache flag and failed-question count. Filtered-out and top-trimmed rows still contribute. Stop detail at the ordered terminal row; final facts include any later in-flight attempts joined by Rust. The existing `details()` value remains the `thinkthen.result/1` object inside `Call.value`, not a replacement for call detail. Do not place raw evidence, context or key in an error or debug representation.
5. A Rust failure after accounting begins retains its six-kind `ThinkThenError` and final frozen `.facts` plus `.details`, including truthful zero-send facts. Pre-accounting validation or a caught panic without retained accounting has absent facts, even if a Node worker already started. A conversion failure after a completed Rust call retains that completed account. Keep prompt caller rejection, listener cleanup, worker cancellation, no later admission and Node's ability to exit after an unobserved early stop. An error from an early `AbortSignal` rejection has optional `.completion: Completion<unknown>`; `Completion.wait()` returns `Promise<{ok: Call<unknown>} | {err: ThinkThenError}>` from the same worker, including its final facts/detail if accounting existed. It never reports a pending report as final zero and never starts another call. An already-final Rust error carries its final account directly and has no completion receipt. Preserve signal reason as the original cancellation cause and the current same-tick precedence.
6. The concrete Node ownership route is to keep the existing `CallHandle` and worker-cloned `ThreadsafeFunction` until the worker's one envelope reaches the JavaScript callback. Add `Env` to the native call/handle methods; napi 2.16.17 exposes `ThreadsafeFunction::{unref,refer}` with `&Env`. On early abort, cancel the token and call `unref` on the mutex-held TSFN instead of `abort`; remove the signal listener and reject immediately with a receipt holding the handle and one unresolved final-report slot. An unobserved receipt leaves the TSFN unreferenced, so Node may exit while the request is held. `completion.wait()` calls a handle method that `refer`s the still-pending TSFN, keeping Node alive until the one callback stores its final envelope and resolves the wait; if completion already arrived, it returns that stored report without referring again. On final callback, release/abort the TSFN and settle the receipt exactly once; the worker's cloned TSFN and Rust-owned input remain alive until its nonblocking send, with no Node object read on the worker. The existing normal-settle path still releases the TSFN after its callback. A worker-spawn failure already schedules a local envelope on that same callback and has no invented facts. Do not use a naked Promise as the receipt: merely awaiting one does not keep Node's event loop alive.
7. Declare recursive `JsonValue = null | boolean | number | string | readonly JsonValue[] | {readonly [key: string]: JsonValue}`, then `Description = string | null | readonly JsonValue[] | {readonly [key: string]: JsonValue}` and `LabelSet = readonly string[] | {readonly [key: string]: Description}`. `QuestionText` is a nonblank string or a JSON object/list; `Meaning` for decide `true`/`false` has the same string/object/list/null top-level forms as `Description`. These declarations retain nested JSON booleans/numbers and previously valid list/object criteria while excluding a top-level numeric or boolean description. Native validation still decides blank text and label-count rules. This admits readonly tuples and JSON object maps without a `Map` API; reject a supplied JavaScript `Map` as usage before `JSON.stringify` could turn it into `{}`. Type `options`, `labels`, `levels`, `kinds` and decide meanings consistently, while keeping actual optionality and score/null output precise. For maps, `Object.entries` defines the accepted order, and `JSON.stringify` preserves that observed own-property sequence in the JSON passed to native `core::Json`, including integer-like keys in JavaScript's defined enumeration order. Keep a described `recognize.kinds` route and distinguish absent `kinds` from explicit null. At the existing `question(spec)`, `specFrom`, `recognizeSpec`, annotate-set and engine-option JSON crossings, validate supplied host values before serialization and map unsafe serialization to a safe `usage` error. Reject nested `undefined`, functions, symbols, BigInt, nonfinite numbers and cycles; otherwise `JSON.stringify` can omit an object member, turn an array member into null, or throw a bare `TypeError`. Do not add a second question parser or silently strip optional fields. Existing output union, failed marker, error names and UTF-16 offset conversion stay intact.

## What preparation taught us

Current TypeScript bulk callers already inherit `Max`; missing host options and bare result conversion are the gaps. `src/door.rs` is only 50 nonblank lines below the per-file limit, so an owned observation/result child is likely smaller than enlarging the door. `index.js` races away the sole native callback on early abort, making a completion receipt a real ownership change rather than a field on the old error. A Node worker's creation does not prove Rust accounting began. Existing held tests assert four sends but batch one is interactive; they need a separate batch-two setup, while legacy corpus bytes stay batch one. The Python score correction proves that bare level and explicit null have different request identities; the TypeScript wrapper must check both before selecting a map normalization. Fresh High design review also caught this preparation's narrower `{what, not_for, examples}` description type: `Description::of_json` accepts any JSON object/list, and `question(spec)` already passes them. The corrected recursive type and exact captured-identity table retain those accepted forms. These are source observations and prospective checks, not completed implementation or timing gains.
