## Decision proposed for review

Expose **`max_estimated_input_tokens_total`** (`--max-estimated-input-tokens-total` at the command) as an optional nonnegative whole-number limit, in *estimated input tokens admitted for live transport attempts*. There is no default limit. Zero admits cache/replay work but no live attempt, subject to the independent request-cap rules. A positive setting is active, never an inert accepted key. The estimator is `encoded-body-bytes-908-v1`: for each final encoded System One request body, charge `ceil(body.len() × 908 / 1000)` with checked integer arithmetic. Sum individually rounded attempts, not logical records or the preview's total rounded once. The coefficient is the measured high end of 0289's 0.516–0.908 planning band; **it is not a tokenizer or proven upper bound on provider input tokens**. Changing coefficient/body coverage requires a new version and compatibility review. `plan` keeps its band and no-send semantics; its planned sum can differ from actual admission after cache hits, retries and splits.

The enforceable rule is at each atomic admission: for the **effective finite limit on that attempt**, `committed_estimate + outstanding_estimate + next_body_estimate <= attempt_limit` (checked arithmetic), or the attempt is refused before transport. Outstanding reservations include in-flight attempts. Overshoot relative to that attempt’s finite limit at admission is zero. This is **not** a promise that the retained process sum stays below every caller’s setting forever: callers can select different limits. There is **no finite promised overshoot bound for reported input tokens, output tokens, provider billing or dollars**: their pre-send values are unknown, and the backend has no verified output-token limit in this source contract. Do not call this a hard token or spend cap. Do not offer an observed-usage stop under this name; post-response facts cannot prevent the send that produced them. No price lookup, output reservation or provider-specific output-bound option enters this ticket.

The scope follows 0289's shared `SendBudget` **counter owner**: one retained process count across its configured engines/threads, with the selected engine/SQL setting supplied on each attempt; PostgreSQL's backend is a separate process and a pool multiplies its independent limit. This does not create a process-wide global configuration authority. For example, A can commit 10 under limit 10, then B can commit 1 under limit 100: the retained sum is 11, B was admitted correctly, and A's next finite-limit-10 attempt is refused. A lowered limit can refuse the next attempt without a new send; a raised limit may admit later attempts; an unset limit admits while retaining checked accounting, so a later finite limit sees the prior sum. `RESET` unsets that caller's limit, not the retained count. Concurrent engines with different settings use the limit selected for **each** attempt at its linearized reservation; no lower-limit caller constrains a higher-limit caller. A forked child starts a fresh count before its first reservation; a new process starts fresh. Rebuilding an engine must not silently create a second counter in the same owner scope. It is not account-wide or durable `status` accounting. Keep `max_requests_total` and per-call `max_requests` independent; both must admit an attempt.

At the single final transport gate, after exact cache/replay lookup and before `send`, reserve the final body's estimate atomically with the request-count admission. Hold both reservations across the last cancellation/deadline and usage-store preparation; refund both if transport cannot start. Mark/commit both when the attempt is marked as started, using 0289's final-send ordering. Never refund a started attempt, including a timeout, transport error, backend failure, failed decode, absent usage, or cancellation during the response. Each retry and each refusal split child is a new final body and a new admission. A cached/replayed answer has no estimated charge and no new arrival; an independently spent request cap can still refuse according to its accepted preflight rule. Reported usage remains optional in `CallFacts`/run facts and never settles this estimated counter; missing usage is not zero. Concurrent calls must reserve against one atomic total; a pending/in-flight reservation is already counted. Checked overflow refuses before send.

Refusal is existing **Usage** kind, not Backend or a seventh kind. Give the new typed denial `InitialRequest`, `AdditionalRequest`, or `Retry { last_status: u16 }`. Initial means no request has started in this call; additional means an ordinary later batch request or refusal-split child after prior started work; retry means another attempt of the **same** exchange. The call-scoped started-attempt marker determines initial/additional; `http.rs` supplies retry context separately. Do not infer later-call context from `last_status`, which resets per exchange, or label a split child a retry. Current `engine/error.rs::retryable` retries only selected backend statuses; transport failure is terminal, so every actual retry has its own preceding numeric status. Never invent a status for an ordinary later exchange. The exact safe CLI sentences are `thinkthen usage: max_estimated_input_tokens_total={N} (encoded-body-bytes-908-v1) would be exceeded before this call's first request`, `thinkthen usage: max_estimated_input_tokens_total={N} (encoded-body-bytes-908-v1) would be exceeded before another request in this call`, `thinkthen usage: max_estimated_input_tokens_total={N} (encoded-body-bytes-908-v1) would be exceeded before retrying status {S}`. `{N}` is the attempt's effective finite limit; `{S}` exists only when the same exchange supplied a numeric retryable status. Messages print no body, key, URL or judged text. CLI exits 2; public `Error` carries the typed admission reason and final started-call facts, while pre-start settings errors have no facts. A started multi-request call retains its completed results/facts under each host's existing partial-result policy. A request cap refusal remains its own carrier/message; neither counter may be committed if the other refuses. Do not make the existing `SendBudgetDenial` falsely mean tokens.

## Smallest outside-in proof after implementation

Extend the existing loopback budget fixture (`crates/thinkthen/tests/public_env.rs`, `public_batches/native.rs`, `backend/batching/too_large.rs`) with **one bounded acceptance table** whose expected charges are calculated from independently captured final request bodies, not the implementation's estimator. Pin the versioned integer formula and exact safe denial, Usage/exit 2, final facts, and listener arrival count in each row:

| Boundary | Independent observation |
| --- | --- |
| Two held concurrent sends under the same finite limit, total sized for one actual body | Both calls reach the reservation race; exactly one backend arrival, one Usage denial, no estimated overshoot against that limit. |
| Mixed simultaneous engine settings and later change | Independently measure final body charges `a` and `b`; let A admit `a` under limit `a` and hold its reply, then B admit `b` under limit `a+b` while A is held. The retained sum is `a+b`; A's next attempt is refused with zero new arrival. Lower/unset/raise and reapply a finite limit without clearing the count; pin each selected limit and arrival. |
| Retry then limit refusal | First attempt counts; pin `Retry` with the actual last retryable status, zero extra arrivals and retained facts. A transport failure is terminal and has no retry row. |
| Ordinary next batch request and a 400 refusal-split child denied after prior work | Pin `AdditionalRequest` and its exact sentence in each route, earlier started facts/host partial results, and zero arrival for the denied body. Preserve a separate admitted split path. |
| Identical cached reply and replay, with the estimated total spent | Zero new arrivals and no new estimated charge; check independent request-cap preflight when configured. |
| Live reply with absent usage, and failed/timeout reply without usage | Each started arrival stays charged, while reported tokens remain absent and later send is refused. |
| Output much larger than input after an admitted send | The admitted estimated input is unchanged; output/reported total may exceed the number, proving wording is not a bill cap. |
| Stop between reservation and transport | Zero new arrivals and refunded charge; a later fresh-token attempt can use it. |

Reuse existing held-listener, replay and split fixtures, with no new generic harness or stress run. A small host conversion proof uses one native C/JSON settings constructor and one SQL or language typed constructor: present positive/zero, invalid negative/fraction/string/overflow, exact Usage refusal and zero send; keep missing/null semantics from each accepted host schema. Check the actual CLI flag and Rust builder separately for an active setting. Do not repeat the table in every wrapper. Focused formatting, Clippy, policy/children, relevant tests, pages/tickets and measured ratchets follow the later implementation claim; installed package and actual release runner qualification remain separate receipts.

## Separate decisions and deferred gaps

This design settles an estimated input admission bound only. The existing facts owner decides optional cost with separate caller-supplied input/output prices, missing-price and missing-usage behavior; `seconds` remains elapsed wall time, and backend server time/ID has its own issue. The status owner decides durable non-CLI product usage; the developer live ledger is not that store. Per-record cache identity remains after release under ruling 3B. No provider-specific tokenizer or output maximum is evidenced here; a future genuinely hard provider token/bill limit needs a separate verified backend contract and review. The separate audit-cost feature remains deferred. Root may recommend an ADR for this public distinction after High review; ADR 0105/0107 and their numbers are untouched by this design claim.

## What the build taught us

The 0289 `SendBudget` owner already spans Rust, CLI and C engines and resets on fork. Adding an atomic estimated sum to the same owner preserves that scope; an independent process counter would have broken mixed-engine behavior. The final `Exchange.body` is the only authoritative charge input. The process request reservation, explicit call reservation and estimated reservation all drop uncommitted when any later gate fails, and all commit only after the usage mark. The public error, CLI conversion and native batch recovery had to recognize the new typed denial separately from `SendBudgetDenial`; SQL spent-total matches remain request-only because those hosts do not yet expose this token setting.

The compiled CLI test exposed that its ordinary Usage printer would omit the ticket's `usage:` word; the dedicated typed route now prints the exact safe sentence and exit 2. The first listener proof incorrectly indexed a drained receipt list; the corrected outside-in test reads each receipt once. The bounded source proof covers selected mixed limits, held concurrent arrival, ordinary later request, status retry, cache at a spent limit, larger reported usage and refusal-split child. It does not qualify an installed archive or every later host. The core settings schema accepts only whole nonnegative values or null; the first C conversion proof rejected negative, fraction and string values while keeping null as unset; the High review correction added overflow. The C header's constructor-key list had fallen behind existing keys, so this build brought it up to the actual closed parser while documenting the new one.

Fresh High review of `b77474c01` found that the first held case was sequential and the limit table did not prove two simultaneous contenders, mixed selected limits while one call stayed in flight, or started replies without usage. The corrected one-process listener fixture uses a three-party start barrier and a held reply: two equal independently measured final bodies compete for one remaining charge, exactly one arrives, and the other gets the typed initial Usage denial before release. A subsequent held A under a smaller selected limit and live B under a larger one proves the count is shared while each limit stays local to its attempt; unset, lower, raise and finite reapply cases preserve the retained sum. The fixture separately pins one successful reply with absent token usage and one terminal 422 without usage; each actual arrival remains charged and a later attempt reaches no listener. The existing HTTP attempt seam could not stop precisely after reservation, so a narrow test-only callback at that boundary now fires cancellation; the production path rechecks stop before the usage mark and transport, and the fresh call uses both refunded slots. C now pins overflow refusal and the existing numeric Usage code 1 at a zero limit.

The review also found a cross-lane landing dependency at `3ef8c82d1`: the pending SQLite 0284 constructor used shared `validate_settings_json`, which accepted this key, while its host conversion still mapped it to Defect. SQLite 0284 has since landed an explicit Usage refusal until that host exposes active admission. The source-matched SQLite release checkpoint after the HTTP correction passed its two named settings tests, including the prior `judge-b` selection and exactly one legitimate listener arrival. Other inspected SQL hosts parse independently, and C wrappers forward JSON. This ticket still does not close the full 0299 host rollout or package qualification. The extra source/test lines measured 102,662 root and 3,858 C, up 246 and 4 from the first code candidate. I reviewed the existing held listener, HTTP pre-attempt hook, reservation guard and C settings table for reuse; no second budget, generic harness, separate estimator or copied host matrix was added.

The check now uses `remaining_without_check()` to observe cancellation without invoking a host callback under that guard; callbacks still run before the guard is acquired.
