# 0259: Accept plain PostgreSQL judgment questions and add SQLite yes probability

Status: complete after fresh independent code acceptance of `d01bc92b`. The coordinator integrated the reviewed PostgreSQL plain-question and SQLite yes-probability changes. The parent SQL usability issue retains its other criteria.

## Outcome and authority

A PostgreSQL caller can write `thinkthen_decide('Is this a complaint?', body)` and `thinkthen_choose('Which team owns this?', body, ARRAY['billing','shipping'])` under the existing signatures. Plain `score` and `tag` questions likewise use their current native `levels text[]` and `labels text[]` slots. `thinkthen_probability` reads the yes probability of a plain or saved decide question. The same question path covers the existing decide array and warm aggregate, details and `try_details`, and their final-context overloads. A SQLite caller can write `thinkthen_probability(question, text[, deadline_ms[, context]])` and receive a `REAL` yes probability without extracting JSON. An unsure decision still has a probability even though `thinkthen_decide` returns SQL `NULL`.

This implements the bare-sentence and probability promises in [the shared database plan](../planning/databases/README.md#the-sql-surface-the-same-in-all-three), [ADR 0017](../planning/adr/0017-libraries-over-one-bound-core.md) and [the settled type contract](../../specification/types.md). PostgreSQL's README prints a plain choose call that current code refuses (`databases/postgresql/README.md:51-53`). PostgreSQL and DuckDB already expose yes probability (`databases/postgresql/src/lib.rs:141-150`; `databases/duckdb/cpp/src/thinkthen.cpp:408-420`); SQLite's registration omits it (`databases/sqlite/src/scalars.rs:359-370`). No new ADR is needed for these two existing promises. The common third-slot proposal remains separate.

## PostgreSQL question boundary

Current `databases/postgresql/src/files.rs:22-33,146-180` accepts a leading `@` path or JSON starting with `{` after leading whitespace; it refuses all other text. `src/lib.rs:37-47` shares that path among judgment functions. `src/context.rs:13-179`, `src/array.rs:38-73` and `src/warm.rs:175` call the same question helper. The generic `Given::read` also serves sets and recognition/relation specs; those inputs stay JSON or `@file`. Add a question-only plain branch in the existing helper, including its non-raising `question_result` used by `try_details`. Do not make generic `Given::read` accept plain sets or specs.

Keep `@` in the first byte as the server-side file marker. After leading whitespace, `{` still starts a JSON question; malformed JSON stays `usage` and never falls back to literal text. Other nonblank text, including `names.json`, is a plain question and never a path. A literal question beginning with `@` or `{` goes in an explicit JSON question or named file (`specification/question-file.md:23-35`; compare `databases/sqlite/src/question.rs:178-187`). Preserve the file cap, `pg_read_server_files`/`thinkthen.file_directory` gate, confinement, `local` file errors, saved threshold/model/profile and existing question digest.

For plain decide, probability, details, try-details, array decide and warm, use the public decide grammar's default cut. For plain choose, score and tag, use their existing native member arrays and public question grammar in member order. Keep their `NULL`/empty array behavior and the current conflict when a JSON or file question already names the members (`files.rs:183-209`). Complete JSON/file descriptions stay intact; native arrays remain label-only. Keep `NULL` question as `usage`, `NULL` evidence as SQL `NULL` after valid question parsing, and `try_details`'s early `NULL` and answered/failed envelope. Add no signature, setting or dependency.

## SQLite probability boundary

Register the 2-, 3- and 4-argument direct-only volatile scalar beside the judgment functions in `databases/sqlite/src/scalars.rs:350-370`. Reuse `inputs` for the existing parse order: the third slot is a non-NULL deadline in milliseconds when present, and context is the final fourth slot (`scalars.rs:16-73`). Reuse `worker::run`, its connection budget, interrupt, process request total, engine settings, cache and request identity. Read `Details::probabilities()` from the same public details path that supports ordinary and banded decide questions (`scalars.rs:231-250`; `crates/thinkthen/src/public/results.rs:275-278`). Return the `Probabilities::YesNo { yes }` value as SQLite `REAL`. A choose/score/tag question is `usage` before a request rather than its named distribution being treated as yes probability, matching PostgreSQL `src/lib.rs:141-150`. A `NULL` question or text returns SQL `NULL` under the existing SQLite input order; `NULL` deadline remains its existing `usage` refusal. Keep existing integer decide, JSON details and `try_details` behavior. A probability read is its own scalar call; do not promise cache reuse with a separate decide call because the cache key is the complete request digest (`databases/sqlite/README.md:103-105`).

## What the build taught us

PostgreSQL's prior installed host refused the plain decide call before sending; SQLite's prior installed library reported no `thinkthen_probability` function. The PostgreSQL implementation adds a question-only plain branch, leaving generic set/spec parsing and file authority untouched. The new branch feeds the shared scalar, array, warm, context and non-raising `try_details` callers. SQLite's existing `only()` rejects banded questions, so probability validates decide kind directly and admits a banded decide before reading `Details::probabilities()`. Strict Clippy required one shared ordinary-details helper, which also removes duplicate details and try-details branches. The [build record](../records/0259-sql-scalar-build.md) names the exact installed SQL and request proofs, source growth, native pins and remaining limits. The original issue stays open; this candidate covers only its PostgreSQL plain-question defect and SQLite yes-probability gap.
