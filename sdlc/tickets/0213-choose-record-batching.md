# 0213: Batch choose records

Status: Design and [ADR 0090](../planning/adr/0090-choose-batches-preserve-row-options.md) accepted by fresh independent review of `02e60bc6`; command implementation and focused local proof passed fresh independent code/helper review at `b595decf`; the authorized paid measurement remains. Owner: Codex. The [preflight](../records/0213-choose-batching-preflight.md) records the source assumptions and their corrections. Ian can overturn the batching rulings in [the design issue](../issues/2026-09-26-batching-design.md); this build preserves them.

## Outcome

In record mode, `choose` fills requests with one pick-one question per record, by ADR 0048 item 7. `--batch N`, `--batch max`, `THINKTHEN_BATCH`, a choose question file's `batch`, request size and `--context FILE` use the same tiers and boundaries already built for `decide`. One document keeps today's single request and output. `choose --options POINTER` still reads each JSON record's own ordered candidate list; two records with the same selected evidence but different candidates receive separate wire questions and answers. Proposed ADR 0090 clarifies that a copied answer requires both the same selected record and the same complete question. It does not move the content cut, which remains a hash of the selected record's compact JSON.

The existing 4,096-member cap, 50 ms live pause in every mode, `--jobs` as batches in flight, profile limits and one eligible 413 halving carry over. The focused loopback proof now observes batched `choose` requests. The S1 list may drop `choose` when the reviewed implementation lands. The earlier `decide` context accuracy run does not measure choose.

The default batched form without context sends `{"records":[R1,…,RN]}` as the evidence and one `The text is R. QUESTION` pick-one question per distinct record/question pair. The list holds two equal selected records when their complete questions differ; it holds one when the pair repeats exactly. ADR 0055's fixed evidence sentence applies to `decide`, `filter` and `rank`, not `choose`. With context, the exact UTF-8 file text is the shared evidence and its raw-byte SHA-256 enters each detailed row. A batch of one without context must send today's exact request body and digest, including option order and descriptions; `--batch 1` reuses existing recordings and cache entries. A changed context changes the request digest, never the question digest. A changed per-record candidate list changes that record's question digest and request identity.

## Retained command behavior

The settled [choose contract](../../specification/choose.md) keeps two to 255 distinct, printable labels in caller order, optional descriptions, JSONL-only `--options`, and the existing field selection. The winning option's probability alone meets the optional single cut; a band is refused. An exact top-two tie is not sure even without a cut. A not sure record prints JSON `null` or an empty `--raw` line and does not stop a record run. Record-mode default output remains `{"input":RECORD,"value":ANSWER}` in input order; `--details` retains the complete answer and `--raw` remains available only for lines and JSONL. CSV/TSV still refuse raw and print JSONL. `--quiet` remains a single-document view and is refused in record mode. A single document with explicit `--batch` or `--context` is refused as those options require a stream; ambient `THINKTHEN_BATCH` alone does not change it.

An invalid per-record option list, missing field, malformed record or local size refusal first closes any earlier open batch, then stops at that record before sending it. The finished prefix stays printed, and `--facts` counts finished rows, sent attempts, cache/replay answers and optional reported usage. A whole request failure stops at its first record with the batch range. A partial reply prints the earlier usable records and stops at the first bad one. A 413 or named token-limit refusal of a batch of two or more halves once; each half retains each record's own candidate list and context. Refused attempts count as attempts, and successful halves keep their ordinary request digests and split metadata. A failed second half leaves the first half's rows printed; an unsuccessful first half sends no second half. Other retryable statuses resend the whole batch by the existing bounded retry rule. A first SIGINT/SIGTERM still stops and writes final facts after any blocking usage flush. No new exit code or cause is proposed.

The batch setting is calibration identity under ADR 0048 item 8 and ADR 0085: a threshold saved with another `batch` warns once and adds `meta.batch_warning` to detailed rows. A choose question file with a threshold but no `batch` was tuned at one. The warning leaves the request bytes, threshold decision and question digest alone. `meta.batch` is absent for a no-context batch of one; with context it is present even for one, as in reviewed 0172. `audit` and `diff` already read batch metadata and keep their own warnings.

## Small proof and validation

1. A two-row captured-wire table uses fixed options and `--options`: the dynamic case keeps `/note` identical while `/codes` differs, so a record-only duplicate bug would visibly send one question instead of two. Pin option order, descriptions, request bytes, row values and question/request digests against independent fixture bytes. A second identical record/question pair proves intentional sharing without another wire question. Compare no-context `--batch 1` directly with an old choose fixture and recording, counting listener requests rather than relying on dry-run.
2. One outside-in table covers the distinct limit and stop boundaries: default versus `--batch 1` request count and facts, context batch-one metadata and exact raw context hash, a later bad options/size row after an earlier closed batch, and 413 halves that keep differing candidate lists. A held signal/final-facts case is added only if the choose path bypasses the already proved 0170 boundary. Reuse the existing listener and schedule helpers; keep one intended failure per fixture and assert row cardinality before per-row contents.
3. The existing single-document choose tests retain cut, tie, null, raw, option and error behavior. One new batched reply table checks a tie/null and a partial invalid answer separately; neither conflates a valid null with an unusable wire answer. Review whether any existing test already covers each case before adding it. Run focused choose/batching tests, affected executable pages, settings checker, formatting, policy/file-size and strict all-feature/all-target Clippy after implementation. No broad rung, load test or paid call belongs to this design draft.
4. The shared question-file corpus must agree under `specification/fixtures/question-file/self-test` and `crates/thinkthen/tests/question_file/corpus.rs`: a choose file with a supported `batch` is valid under both schema and parser, while malformed batch values remain invalid. The existing `backend/batching/tiers.rs` choose rejection becomes a positive file-tier command case that observes the chosen batch plan; retain the typed one-document refusal as a separate command boundary. A schema-only verdict cannot prove the CLI tier was applied.

The issue's test 11 requires 200 `choose` items at default and `--batch 10`, reporting both scores against 135/200 without gating either. Experiment 262's exact 200 sampled questions form 153 distinct question-and-ordered-options groups, 147 of them singletons. Since a `choose` stream has one question text, a faithful job must group by complete question. It cannot claim a 20-request arm or infer an ungrouped batch score from that sample. The proposed [paid helper](../../probes/choose/measure.py) keeps the fixed 200 IDs, each original question, option description and input, and runs each group at the default and at batch 10. Those settings have at least 153 and 156 planned requests, respectively, before cuts or refusals. One additional context arm records the largest exact-question group of 16 records against the bench catalog. The local mixed-options listener case, not this mostly-singleton sample, proves mixed candidate batching. The helper requires input and output usage on every result, compares row shares to fresh process totals, disables retries, and stops between groups at 180,000 combined reported tokens. A 250,000-token `sdlc/scripts/live` reservation is proposed for all three arms; the reservation is a precharge, not a runtime cap. At most 600 starts per 200-item arm and 48 for the 16-item context arm are possible under one split and zero retries; the helper refuses higher reported counts. It records score against 135/200 as context only, plus actual attempts, token totals, build and answer/request identity hashes. No paid execution precedes frozen code review.

## What the build taught us

The accepted source inventory prevented a parser-only change: the closed choose schema, shared parity corpus, and old choose-batch rejection in `backend/batching/tiers.rs` changed together. The corpus CLI runner needed a two-record input only for top-level batch cases because its old one-document invocation ignores saved batch. `core/batch.rs` needed a coherent per-row-question child, and `cli/asking.rs` needed a framing child to stay under 500 nonblank lines. The first late-refusal fixture wrongly expected a 500-byte soft request-size setting to refuse a singleton. Ticket 0154's edge table and ADR 0051 retain the singleton exception; only an explicit profile limit locally refuses it. The corrected fixture uses that profile and keeps the prior soft-cut behavior. The paid preflight then found that experiment 262 contains 153 question-and-options groups, so a faithful choose stream cannot turn its 200 heterogeneous questions into 20 requests. The live helper preserves the original task and states the comparison limit. Fresh code review and paid evidence are still pending.
