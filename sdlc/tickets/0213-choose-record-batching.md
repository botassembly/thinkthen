# 0213: Batch choose records

Status: proposed B8 design for fresh independent review. Owner: Codex. This branch changes design records only. Runtime work waits for the accepted 0172 branch to land or for exact source claims to transfer. The [preflight](../records/0213-choose-batching-preflight.md) distinguishes main `0b1d4ec2`, reviewed but unlanded 0172 `43edb3dc`, and the emerging 0212 Rust library design. Ian can overturn the batching rulings in [the design issue](../issues/2026-09-26-batching-design.md); this draft preserves them.

## Outcome

In record mode, `choose` fills requests with one pick-one question per record, by ADR 0048 item 7. `--batch N`, `--batch max`, `THINKTHEN_BATCH`, a choose question file's `batch`, request size and `--context FILE` use the same tiers and boundaries already built for `decide`. One document keeps today's single request and output. `choose --options POINTER` still reads each JSON record's own ordered candidate list; two records with the same selected evidence but different candidates receive separate wire questions and answers. Proposed ADR 0090 clarifies that a copied answer requires both the same selected record and the same complete question. It does not move the content cut, which remains a hash of the selected record's compact JSON.

The default batched form without context sends `{"records":[R1,…,RN]}` as the evidence and one `The text is R. QUESTION` pick-one question per distinct record/question pair. ADR 0055's fixed evidence sentence applies to `decide`, `filter` and `rank`, not `choose`. With context, the exact UTF-8 file text is the shared evidence and its raw-byte SHA-256 enters each detailed row. A batch of one without context must send today's exact request body and digest, including option order and descriptions; `--batch 1` reuses existing recordings and cache entries. A changed context changes the request digest, never the question digest. A changed per-record candidate list changes that record's question digest and request identity.

## Retained command behavior

The settled [choose contract](../../specification/choose.md) keeps two to 255 distinct, printable labels in caller order, optional descriptions, JSONL-only `--options`, and the existing field selection. The winning option's probability alone meets the optional single cut; a band is refused. An exact top-two tie is not sure even without a cut. A not sure record prints JSON `null` or an empty `--raw` line and does not stop a record run. Record-mode default output remains `{"input":RECORD,"value":ANSWER}` in input order; `--details` retains the complete answer and `--raw` remains available only for lines and JSONL. CSV/TSV still refuse raw and print JSONL. `--quiet` remains a single-document view and is refused in record mode. A single document with explicit `--batch` or `--context` is refused as those options require a stream; ambient `THINKTHEN_BATCH` alone does not change it.

An invalid per-record option list, missing field, malformed record or local size refusal first closes any earlier open batch, then stops at that record before sending it. The finished prefix stays printed, and `--facts` counts finished rows, sent attempts, cache/replay answers and optional reported usage. A whole request failure stops at its first record with the batch range. A partial reply prints the earlier usable records and stops at the first bad one. A 413 or named token-limit refusal of a batch of two or more halves once; each half retains each record's own candidate list and context. Refused attempts count as attempts, and successful halves keep their ordinary request digests and split metadata. A failed second half leaves the first half's rows printed; an unsuccessful first half sends no second half. Other retryable statuses resend the whole batch by the existing bounded retry rule. A first SIGINT/SIGTERM still stops and writes final facts after any blocking usage flush. No new exit code or cause is proposed.

The batch setting is calibration identity under ADR 0048 item 8 and ADR 0085: a threshold saved with another `batch` warns once and adds `meta.batch_warning` to detailed rows. A choose question file with a threshold but no `batch` was tuned at one. The warning leaves the request bytes, threshold decision and question digest alone. `meta.batch` is absent for a no-context batch of one; with context it is present even for one, as in reviewed 0172. `audit` and `diff` already read batch metadata and keep their own warnings.

## Exact source path and proposed implementation boundary

Main `cli/args.rs::ChooseArguments` has no `Batching`; `cli/judge.rs::choose` sets `Asked.batch=None`; `cli/asked.rs::choose` discards `read_top`'s batch tier; `cli/asking.rs::run` therefore uses the old one-record scheduler. Add the existing `Batching` argument group, pass the choose file tier into `Tiers`, and use the existing run/context, mismatch, output and scheduler paths. `cli/args/command.rs`, `cli/mod.rs` and `cli/facts.rs` read or route `ChooseArguments`; inspect them as parent/constructor inventory and change only if compilation or the new option boundary actually requires it. Do not add a second CLI parser or a second result constructor. Review the `Run` initializer in `public/results.rs` after 0172 lands if the shared row carrier changes.

The current `cli/asking/batched.rs` accepts only `Asks::Fixed`; `Asks::FromRecord` must build its `Question::Choose` from the full record before pushing that record. Extend the core planner with a per-record question input while preserving the existing fixed-question route. Its duplicate key must compare selected record bytes and complete question, including ordered labels and descriptions. Its actual encoded body, not an estimated average option length, must govern the request-size/profile boundary. The no-context singleton plan must use that row's question. The 413 halves must reconstruct their original row questions, not the first row's list. A local refusal must not discard an earlier closed batch. `core/batch.rs` is at 496 nonblank lines on main and reviewed 0172, so plan one coherent private child extraction for the per-record question and sizing work; do not scatter code to hide growth. `cli/asking.rs` reaches 500 on 0172 and `cli/failure.rs` 499. Prefer existing typed context/refusal mapping and a private child with a reviewed exact claim over expanding those parents.

Prospective code files, pending exact claims: `crates/thinkthen/src/cli/{args,asked,judge,asking}.rs`, `cli/asking/{batched,batch_meta,context}.rs` and a coherent private batch child if needed; `core/batch.rs` and a private child, `core/question_file.rs` plus its parser tests for the choose file tier, `core/digest.rs` only if the existing per-row digest path fails, and the relevant parent exports. Inspect `cli/{args/command,mod,facts}.rs`, `result_json.rs`, `public/results.rs`, `core/records.rs`, `engine/facade.rs`, and `cli/failure/context.rs` or its current equivalent before changing them. Prospective outside-in proof belongs in `crates/thinkthen/tests/backend/batching/choose.rs`, registered by its parent; existing `backend/{choosing,asked,refusals}.rs` remain the single-document and validation proofs. Required contract pages are `specification/{choose,records,result,settings,question-file,backends}.md`, the choose row in the batching issue and its S1 list, and the affected executable page if a current one exists. Update only sentences this ticket actually makes true; read every output/failure/identity copy together before marking a row built.

## Small proof and validation

1. A two-row captured-wire table uses fixed options and `--options`: the dynamic case keeps `/note` identical while `/codes` differs, so a record-only duplicate bug would visibly send one question instead of two. Pin option order, descriptions, request bytes, row values and question/request digests against independent fixture bytes. A second identical record/question pair proves intentional sharing without another wire question. Compare no-context `--batch 1` directly with an old choose fixture and recording, counting listener requests rather than relying on dry-run.
2. One outside-in table covers the distinct limit and stop boundaries: default versus `--batch 1` request count and facts, context batch-one metadata and exact raw context hash, a later bad options/size row after an earlier closed batch, and 413 halves that keep differing candidate lists. A held signal/final-facts case is added only if the choose path bypasses the already proved 0170 boundary. Reuse the existing listener and schedule helpers; keep one intended failure per fixture and assert row cardinality before per-row contents.
3. The existing single-document choose tests retain cut, tie, null, raw, option and error behavior. One new batched reply table checks a tie/null and a partial invalid answer separately; neither conflates a valid null with an unusable wire answer. Review whether any existing test already covers each case before adding it. Run focused choose/batching tests, affected executable pages, settings checker, formatting, policy/file-size and strict all-feature/all-target Clippy after implementation. No broad rung, load test or paid call belongs to this design draft.

The issue's test 11 requires 200 `choose` items at default and `--batch 10`, reporting both scores against 135/200 without gating either. B8 also requires one recorded context run. Those are paid measurements and will receive a concrete count and `sdlc/scripts/live` reservation proposal after a reviewed build. Ian has delegated paid-testing budgets to the coordinator, but this design draft names no executable job or reservation yet. A reservation is charged before execution; it is not an in-request runtime cap. No paid execution follows from this draft alone.
