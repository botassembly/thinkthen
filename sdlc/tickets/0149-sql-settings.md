# 0149: Give SQL the engine settings and charge every send

Status: design accepted 2026-09-27 after fresh independent review of corrected `291d7532`. Owner: Codex. Retry accounting has landed; runtime work still needs 0201's final caller-session source and exact shared DuckDB claims.

## Outcome and authority

A SQL caller can select the model, timeout, retries, backend limits profile, and record or strict replay folder through its extension's existing settings style. A replay miss sends nothing. The caller cannot set a key or address in SQL. A retry consumes the SQL process request total before it sends, including when the total runs out within one call. DuckDB `thinkthen_warm` uses the calling session's settings and fills the same cache as that session's scalar calls.

Ticket 0148's section “Ticket 0149, the SQL settings” settles the spelling, JSON-text profile, cache-off and folder rules. Accepted ADR 0052 item 8 settles retry accounting; ticket 0155's backoff and retry counters have landed. Ian can overturn those settled rules. This ticket closes only the SQL portions of the two partially resolved settings and replay issues, plus register 51 after a real warm parity proof.

## Design

1. **One validated builder path.** Add `EngineBuilder::profile_json(&str) -> Result<Self, Error>` beside `profile(path)`. Parse the closed `thinkthen.backend-profile/1` object with the same `BackendProfile::parse` used for files, hold the parsed value, and apply it without reading a path. Invalid caller JSON is `Usage`; a profile-file read or parse remains `Local` under 0148. A later profile setter replaces the earlier one, as other builder setters do; no implicit file or JSON precedence enters SQL. Keep `from_env()` as the base, then apply explicit SQL values. A profile limits prepared requests before a key is used or a send starts. The public API inventory and ticket 0084 gain this one declared method. No new schema or dependency.
2. **Host spellings and retained rules.** DuckDB registers `SET thinkthen_model`, `thinkthen_timeout`, `thinkthen_max_retries`, `thinkthen_profile`, `thinkthen_record`, `thinkthen_replay` and reads them through the caller's settings handle. PostgreSQL registers the same suffixes under `thinkthen.`; timeout's GUC unit is seconds. SQLite adds `thinkthen_model(text)`, `thinkthen_timeout(n)`, `thinkthen_max_retries(n)`, `thinkthen_profile(json)`, `thinkthen_record(path)` and `thinkthen_replay(path)` before its first engine is built. Timeout is a positive whole number of seconds; retries is a whole number at least zero. All range and folder conflicts come from the builder after host type conversion. DuckDB and PostgreSQL accept `off` for their SQL cache setting, preserving unset/RESET as environment fallback; SQLite keeps `thinkthen_cache(NULL)`. DuckDB and PostgreSQL SQL cache/record/replay folders are absolute and follow their current host permissions; PostgreSQL's folder GUCs require superuser privilege. SQLite keeps its plain path rule. Address and key remain environment-only, and key text never enters SQL, logs, profile JSON or errors. A call to `record` always sends, strict `replay` never sends, and one folder may be paired as in 0148. Preserve each extension's current SQL names, NULL behavior, try-value errors, process lifetime and `thinkthen <kind>` prefix.
3. **Statement and warm reach.** Include the six new values in DuckDB's engine key; never reuse an engine made with a different profile, folder, timeout, retries or model. The caller's file system probes any SQL folder before building. DuckDB warm captures a snapshot of the *calling* session's settings through 0201's proven C++ aggregate context, then calls the same checked engine resolver as a scalar. A changed session setting yields the corresponding engine key; the same setting shares it. Neither the kept relate connection nor a process global supplies warm settings. SQLite's `thinkthen_warm`, `thinkthen_recognize` and `thinkthen_relate` gain a final deadline in milliseconds using the existing `CallOptions::deadline_millis`; `-1` clears, `0` sends nothing, positive values bound the whole call. Do not change the leading arguments or result shapes. PostgreSQL keeps native statement timeout and its existing worker cancellation.
4. **One send budget across engines, with a typed denial.** Add a small public `SendBudget` handle and `CallOptions::send_budget(&SendBudget, Option<u64>)`. Each SQL extension owns one process-scoped handle, reset on fork, and passes it on every call, including warm and a call with no current cap. The handle counts attempted live sends across all its engines, including retired DuckDB engines and retries; it counts no cache or replay answer. The current call's total is checked with one atomic reservation, so concurrent calls and later session-limit changes cannot rely on a stale counter snapshot. After backoff waiting, throttle acquisition and the gate recheck, `Client::post_observed` performs its **final** cancellation/deadline check and computes the transport timeout. Only then does it reserve one budget unit, invoke the existing nonblocking send-count hook, and start transport, with no blocking wait or second stop check between reservation and send. A passed deadline or fired cancellation during a throttle/backoff wait therefore consumes neither budget nor `requests_sent`; a denied reservation also consumes neither and opens no transport. Keep the public error kinds at six. Add the public `SendBudgetDenial` value with `BeforeFirstSend` and `BeforeRetry { last_status: u16 }`, and `Error::send_budget_denial() -> Option<SendBudgetDenial>` as the sole new discriminator. The private engine error carries those two causes through conversion: first-send denial is `Usage` with a safe fixed message; denied retry is `Backend`, retains the last retried status in its ordinary safe status message and typed `last_status`, and reports `retryable() == false` while the budget is spent. Each SQL host checks this accessor, maps either variant to its existing spent-total usage refusal after already completed rows, and never matches text, infers a denial from shared counter deltas, or swallows a different backend failure. `requests_sent` remains every actual attempt, and `retries` remains its subset under ADR 0052. The SQL process total's current pre-call row cut remains an optimization for ordered partial rows; it is no longer the enforcement boundary. Amend ticket 0084's frozen public inventory for `SendBudget`, `CallOptions::send_budget`, `SendBudgetDenial` and `Error::send_budget_denial`, and review this widened API before runtime. No command budget is added; library `max_requests` still caps records rather than sends.
The typed denial maps at the host boundary, not in the HTTP adapter: DuckDB makes the `RowError::usage` sentence already produced by `engines::within_total_typed`; SQLite makes `settings::spent(total)`; PostgreSQL makes `Call::spent()`. Each uses that call's actual configured total, leaves its existing `thinkthen usage` prefix and try-value shape intact, and emits no backend-status row in place of the spent-total refusal. The `BeforeRetry` marker retains the last status for the lower-level request result and diagnosis, while the public SQL outcome remains the spent-total usage refusal required by ADR 0052 item 8. A normal 503 without a denied reservation has no marker and follows the existing backend path.

5. **Pages and ownership.** Update the SQL cells and precedence/default notes in `specification/settings.md`, the three SQL READMEs, `conformance/settings.json` and its runner/checker for each host's applicable forms. Mark the two partial issues resolved only after all three SQL boundaries pass. Record register 51's same-session proof and ADR 0052 item 8's retry-before-send proof. Changes to 0201's migration files require an exact shared claim; 0149 owns the behavior, 0201 owns the C++ host bridge and must preserve it in its stock package. Keep calibration-profile identity (ticket 0203), request-size exposure (0157), and batching out of this ticket.

## Focused proof and order

Start with red outside-in SQL calls through the existing loopback, with no paid key. One selected setting row per host proves model in the request and timeout/retries through the public engine; a valid inline profile rejects one over-limit request before send and an invalid profile reports the host's safe usage error. A strict replay miss uses a listener counter to prove zero sends, and a paired record/replay reads the same saved exchange. A second connection checks DuckDB session isolation and a cache folder that the caller's file settings refuse. One DuckDB query sets cache and model, warms one answer, then makes a scalar call in the same session and proves no second send and one shared cache hit; a different session must not inherit the folder. A PostgreSQL non-superuser cannot set a record, replay or cache folder. SQLite's three new deadline overloads check zero and one short positive budget with the existing statement/worker boundary.

A separate short retry case sets the SQL total to one, answers the first attempt 503 with a zero or tiny retry delay, and proves the listener saw exactly one attempt, a typed `BeforeRetry { last_status: 503 }` before SQL mapping, the spent-total refusal at each SQL boundary and no retry. A direct zero-cap `SendBudget` check returns typed `BeforeFirstSend` with zero listener requests. DuckDB and PostgreSQL may also set SQL total zero. SQLite rejects total zero, so its SQL boundary spends a positive total first, then refuses the next call with zero additional sends and the same spent-total sentence. An unrelated 503 with budget available retains normal backend status and has no budget-denial marker. A second call at a raised total proves the budget counts the earlier send. One bounded held-width wait and one bounded retry-backoff wait expire their call deadline before the final stop check; both leave the listener, shared send budget and `requests_sent` unchanged. Repeat the host mapping only, not the same wait campaign on three ports. The selected `conformance/settings.json` cases and each host's small existing settings/conformance selector run. Keep full old functional cases and stress campaigns opt-in.

Implementation order from the accepted design: (a) use landed 0155 and add profile JSON plus the typed send-budget seam with a focused public consumer proof and strict core Clippy; (b) SQLite and PostgreSQL settings, focused host tests and strict lints; (c) DuckDB scalar settings, cheap policy/source-size and feature lint before packaging; (d) after 0201's stock-host aggregate-context proof, warm parity and DuckDB focused package test; (e) one reviewed batch checkpoint with the relevant specification and surface rungs. Each fix gets targeted format, schema/settings checker, file-size/policy and strict feature lint first. Do not repeat full gates per slice, run stress or paid calls, or rely on an installed extension whose source differs from the checked revision. Measure exact ratchets, record retained passes, and take fresh independent design and code reviews. Stop if the caller-session aggregate context, public budget representation, or another surface's file authority cannot be proved; amend the design before a workaround.
