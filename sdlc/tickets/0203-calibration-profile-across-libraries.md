# 0203: Preserve calibration profiles across libraries

Status: ready. Owner: Codex. Design accepted; runtime build and proof remain open.

## Outcome

A saved question's top-level `profile` has the same identity and comparison meaning on the command, Rust API, language wrappers, Polars, and SQL. Each surface either carries it to the shared result writer and compares it with an explicitly selected runtime backend profile, or refuses the call before a request when that surface cannot honor it. A runtime profile enforces its limits at the existing prepared-request boundary. No surface silently drops a saved calibration name. No profile selects a backend address or model.

## Retained behavior

Keep the closed question-file grammar, `profile` name validation, command precedence, canonical key order and digest bytes, existing profiles' limit units, pre-send check, model override, cache/recording identity and public result shapes. Keep absent-versus-present warning semantics: a warning exists only when both saved and selected runtime names exist and differ. Keep batch tuning warning separate; `batch` does not enter the question or set digest. Typed questions with no saved profile preserve current digests and request bytes. The selected limits profile does not enter the question digest. A model name is runtime metadata, not question identity.

## Design

1. Carry the saved `ProfileName` through the public parsed question value and the existing core question-set, recognize and relate values. The saved name belongs to the question or set, never to the engine. Rust and the bindings with a JSON/file reader use `Question::from_json`/`load`; no Rust programmatic profile setter is added. R needs one public file entry: `tt_question(file = PATH)`, mutually exclusive with all question keywords, reads and validates the existing single-question grammar, and returns a normal `thinkthen_question` carrying the original JSON. An unreadable or invalid file raises the existing local condition; mixed file and keywords raise usage before send. A file-backed question never drops a parsed profile while converting to `LoadedQuestion`, `ChooseQuestion<C>` or `TagQuestion<C>`.
2. Runtime profile selection belongs to the engine settings and applies to every call. Ticket 0148 supplies `EngineBuilder::profile(path)` and the six language spellings; ticket 0149 supplies SQL JSON profile settings and `profile_json`. This ticket reuses those entries and the existing `PreparedRequest(s)::with_profile` check. Do not create ambient discovery, a config tier, or a second profile schema. Invalid file/read errors are `Local`; invalid caller JSON is `Usage`. A profile limit failure is the existing usage/refusal category with a safe size-and-limit diagnostic. It happens before cache/replay/key/transport for a logical request. Batch streams can have earlier successful batches, following existing streaming failure semantics; a single request or preflighted grouped request sends none.
3. `Details::of` and its `to_json` feed the saved name and `ProfileWarning::between(saved, running)` into the existing `result_json::decision` writer. Compute the digest once and store that same value in the typed `Details`; do not hash the question separately for each field. Add `Details::profile_warning() -> Option<(&str, &str)>`, with `(tuned_for, running)` order, matching the JSON. Do not print from libraries or SQL; the command keeps its one stderr warning at the ordered output boundary. Bare value calls retain their bare shape and have no warning channel. On a mismatch, a caller seeking the warning uses `details` or a SQL details form. When only one name exists, no warning. A mismatched pair still judges normally if limits pass.
4. A loaded question's `model` continues to override engine default through the existing per-question model path. The runtime profile does not choose or change model; actual reply model stays `meta.model`. Question digest is identical for command and library given the same effective question, threshold and saved name. It may differ when the caller overrides the threshold or changes question shape. Request digests remain tied to actual wire requests, which can differ with batching. `meta.questions_sha256` follows the existing question-set canonical form with the top-level saved profile, not nested profiles. The current Rust `annotate` API returns bare values (`public/annotated.rs:47-98`), while its core set already preserves the identity; this ticket adds no second annotate digest writer. Recognize and relate return bare values in the public API; their saved profiles stay inside the parsed specs, and the command details writers remain the source of their digests. If a binding exposes their details, it must use that shared writer or refuse the details form before send; it may keep bare value calls. Do not claim a command detail row exists in an API that does not expose one.
5. Surface routing is fixed by the table below and the route rules after it. A saved calibration name without a selected runtime profile is valid and changes the question digest, as ADR 0032 says; absence of a running name is not a mismatch. A wrapper that cannot preserve the saved name must return its normal usage/local error before any send. A selected runtime profile requires the existing pre-send enforcement; a wrapper may never pretend to honor it while dropping its limits. No wrapper strips `profile` while rewriting a question object. Built programmatic questions without a saved name remain valid.
6. Integrate with 0146 batching: preserve its core batch partition and content-cut logic and 0148 settings. A profile's limits close batches at the existing limiter. `batch` mismatch metadata is separate from profile warning. For batch 1 and no context, maintain old wire/request digest. Do not add a new assembler to attach identity at wrapper level; take it from parsed public/core question and set values.

| Surface | Saved name | Runtime limits profile | Observable result |
| --- | --- | --- | --- |
| Command | Existing question/set/recognize/relate file parser | Existing `--profile FILE` | Exact digest and optional warning in `--details`; one ordered stderr warning even for a bare answer |
| Rust and Polars | `Question::from_json`/`load` through `Question`, banded and typed choice/tag conversions; core question set and recognition/relation specs | 0148 `EngineBuilder::profile(path)`; Polars uses that engine | `Details::question_sha256`, `Details::to_json`, and the new typed warning accessor for single questions. Bare collection values retain their shape |
| Python, TypeScript and Ruby | Python's JSON/file question and TypeScript's object question pass `profile` to Rust unchanged; Ruby's `ThinkThen.question(profile: ...)` passes its JSON unchanged | 0148 `profile` engine option | Existing `details` returns the command's meta fields; bare calls retain their shape |
| R | New `tt_question(file = PATH)` retains the parsed single-question JSON; keyword questions remain unprofiled | 0148 `profile` engine option | Existing `tt_details` returns the exact saved-profile digest and optional structured mismatch warning from `Details::to_json`; bare calls retain their shape |
| C | The JSON request passes `profile` through `Question::from_json`; no second C question parser | 0148 `thinkthen_engine_new_with` JSON `profile` path | Existing `details` request returns the command's meta fields; C error slot reports refusal |
| DuckDB, PostgreSQL and SQLite | Their question JSON/file adapter must preserve `profile` through public `Question` | 0149 SQL profile JSON setting and `EngineBuilder::profile_json` | Where SQL exposes details, exact digest and warning meta; bare SQL value keeps its type |

For every row, a selected limits profile is checked at the prepared request boundary. For a saved calibration name that the route cannot carry, refuse before sending with the host's existing usage/local error kind and a sentence naming the unsupported `profile`; do not reinterpret it as a runtime profile path. File syntax/read failures keep the existing local-file kind, while caller supplied JSON failures keep usage. No new per-call profile override is added. The file's `model` retains its existing precedence over the engine model, and `meta.model` is the model reported by the actual reply. Neither model nor runtime profile changes the question digest.

The public `QuestionSetBuilder::question` rejects a member whose saved `profile` is present with `Error::Usage` and the exact sentence `a question set member takes no profile; name it on the set`. It does so before adding the member; `build` cannot silently erase the name. `QuestionSet::from_json`/`load` continue to accept one top-level `profile` and refuse nested `questions.NAME.profile` under the closed grammar. A builder has no set-level profile setter in this ticket. Python's non-decide column shortcut uses the builder, so a profile-bearing `choose`, `score`, or `tag` passed with a column raises Python `UsageError` before reading or sending any rows. The caller can use a top-level-profile question set with `annotate`. R's column shortcut also uses the builder, but its existing failure branch calls `one_by_one`; a profile-bearing `tt_question(file = PATH)` must take that branch and ask each row with the original question and profile. The fallback must not swallow an unrelated invalid-question error. DuckDB's `single` builder (`databases/duckdb/src/questions.rs:166-169`) creates a fresh unprofiled question from text and members, so it has no saved name to lose; JSON/file details and annotate routes keep their parsed profile.

Ruby `rank` and `find` accept a plain question string or a built `decide` question containing only `decide`. A built question with `profile` raises `ThinkThen::UsageError` with `rank takes a decide question with no profile` or `find takes a decide question with no profile` before `crossing`; a different extra key names that key in the same sentence. This matches TypeScript's `textFrom` policy and prevents silent loss of threshold, model, or other valid fields. R's `.tt_text` takes the same pre-send refusal route for built questions, using its `thinkthen_usage` condition and the same verb-specific `takes a decide question with no KEY` sentence; a plain text question remains valid. Python's built `decide` question on rank/find must retain its existing kind refusal before send, including a saved-profile file question. These text-only ordering routes do not reinterpret a saved `profile` as a runtime profile or invent a digest-bearing details result.

## Proof before build lands

Start red with an outside-in replayed cross-surface case: one `decide` file with a fixed saved profile and a fixed expected 64-character digest taken from the specification's canonical bytes, not computed by the code under test. Cover the command, Rust, Python, TypeScript, Ruby, R, C, Polars and each SQL surface at its real entry point. R uses `tt_details(tt_question(file = PATH), evidence)` to assert that exact saved-profile digest; its bare call also succeeds under the selected runtime profile. For Polars, use the Rust engine's `Details` on the same parsed question alongside the column call; the column API itself is bare. Assert the exact digest and profile metadata wherever the surface exposes details; use one shared case, avoiding parallel expected-value assemblers. A second case with selected runtime profile of another name asserts the exact `{"tuned_for":"old","running":"new"}` pair, including in R's `tt_details` result, with command stderr once and structured detail metadata without library stderr. A same-name case asserts no warning, including in R's details result.

Use a counted loopback listener for an over-limit request and an invalid runtime profile. Assert zero sends on the live path, the exact error category and safe message, and no cache/replay/key access where the existing boundary promises it. Exercise each real loss route, not a synthetic hook: a Rust public `QuestionSet::builder().question("value", Question::from_json(...profile...))` must return the pinned usage sentence; Python `choose` with that question and a real column must raise `UsageError` with zero listener requests, even when the column has data; R `tt_score(tt_question(file = PATH), c("one", "two"))` must use its per-row fallback and produce two answers under the saved name with the runtime limit enforced; Ruby `rank` and `find`, including `none: true`, must refuse a built profiled question with their exact usage sentences and zero sends. R `tt_rank` and `tt_find` get one corresponding built-file refusal case with zero sends. A plain text ordering case keeps working. TypeScript's existing extra-key refusal is the comparison contract, not a duplicated new implementation test. The Rust builder case catches silent loss in `from_parts`; the Python case catches a column bypass of that check; the R case catches a fallback that loses the original question; the Ruby and R ordering cases catch text extraction that erases saved fields. Existing single-question digest and core set tests exercise none of these routes. All cases use public entry points and the actual loopback backend; no test-only export, flag or hook is needed.

Test a command batch whose next record exceeds one profile limit, comparing its grouping and request identity with the recorded 0146 behavior; a batch-1 no-context regression pins unchanged wire bytes. Do not demand equal request digests between a batched command and a current per-record library call. Check model override retains actual model metadata while the saved-profile digest stays fixed. Pin a question set's existing `questions_sha256` canonical form, and the command's recognize and relate digest/warning paths. Wrapper details for those verbs run the same case only if they actually expose a details form. Every test must state the credible regression it catches, why existing tests miss it and whether it needs a hook; use none.

The primary regression is today's `None` at `public/results.rs:211,228`; the shared case must fail if either one returns. Existing core digest tests prove a name changes the hash, but they never cross the public API or wrappers. The mismatch case must fail if a binding drops its runtime profile or a result writer omits the warning. The zero-send cases must fail if a rejected profile reaches the live listener. Red-green scaffold tests are removed or converted to these outside-in contract and regression cases before the build lands.

Run the five gate rungs for the eventual build and all supported surface checks. The design draft itself runs only ticket, markdown and diff checks.
