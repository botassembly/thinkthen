# 0203: Preserve calibration profiles across libraries

Status: draft. Owner: Codex. Root owns review, acceptance and landing.

## Outcome

A saved question's top-level `profile` has the same identity and comparison meaning on the command, Rust API, language wrappers, Polars, and SQL. Each surface either carries it to the shared result writer and compares it with an explicitly selected runtime backend profile, or refuses the call before a request when that surface cannot honor it. A runtime profile enforces its limits at the existing prepared-request boundary. No surface silently drops a saved calibration name. No profile selects a backend address or model.

## Evidence on current main

Experiment 284 report 24 and `sdlc/issues/2026-09-26-the-library-drops-a-question-files-calibration-profile.md` report command digest `6a0e5df25f5e...` against Python and DuckDB digest `968a10461272...`; the value without `profile` was `968a1046...`. These are recorded observations, not a new live run. The report observed these values; the builder must pin the full digest in a shared fixture rather than derive the expectation from the implementation under test.

`public/question.rs:234-239,414-446` shows that `Question::from_json` resolves a file and returns a public `Question` holding core question, threshold, model and kind, but no profile. `public/results.rs:209-229` sets `Run { tuned_for: None, warning: None }` and calls `question_sha256_with_profile(..., None)`. `public/settings.rs:228-236` sets runtime `Settings.profile` to `None` today. The command's `result_json::decision` already takes `Run.tuned_for`, and core owns the canonical digest. The accepted ADR 0032 defines the calibration name and runtime limits profile separately. ADR 0048 adds batch setting to calibration identity but leaves it outside question digest. Accepted ticket 0148, read from `origin/ticket/0148-engine-settings-everywhere`, explicitly excludes the calibration fix. Its Rust builder and six binding profile setters are prerequisites, not work for this ticket. Its “Ticket 0149, the SQL settings” section assigns SQL runtime profile JSON to 0149. Ticket 0146 is already landed. `core/question_set.rs:268-270,444-452` already keeps and hashes a set’s top-level profile. `result_json.rs:24-41` already writes a command row using the shared canonical digest. The public single-result writer is the missing caller.

## Retained behavior

Keep the closed question-file grammar, `profile` name validation, command precedence, canonical key order and digest bytes, existing profiles' limit units, pre-send check, model override, cache/recording identity and public result shapes. Keep absent-versus-present warning semantics: a warning exists only when both saved and selected runtime names exist and differ. Keep batch tuning warning separate; `batch` does not enter the question or set digest. Typed questions with no saved profile preserve current digests and request bytes. The selected limits profile does not enter the question digest. A model name is runtime metadata, not question identity.

## Design

1. Carry the saved `ProfileName` through the public parsed question value and the existing core question-set, recognize and relate values. The saved name belongs to the question or set, never to the engine. No new setter is added to programmatic question builders: the issue is a file value being dropped, and `Question::from_json`/`load` already give callers that route. A file-backed question never drops a parsed profile while converting to `LoadedQuestion`, `ChooseQuestion<C>` or `TagQuestion<C>`.
2. Runtime profile selection belongs to the engine settings and applies to every call. Ticket 0148 supplies `EngineBuilder::profile(path)` and the six language spellings; ticket 0149 supplies SQL JSON profile settings and `profile_json`. This ticket reuses those entries and the existing `PreparedRequest(s)::with_profile` check. Do not create ambient discovery, a config tier, or a second profile schema. Invalid file/read errors are `Local`; invalid caller JSON is `Usage`. A profile limit failure is the existing usage/refusal category with a safe size-and-limit diagnostic. It happens before cache/replay/key/transport for a logical request. Batch streams can have earlier successful batches, following existing streaming failure semantics; a single request or preflighted grouped request sends none.
3. `Details::of` and its `to_json` feed the saved name and `ProfileWarning::between(saved, running)` into the existing `result_json::decision` writer. Compute the digest once and store that same value in the typed `Details`; do not hash the question separately for each field. Add `Details::profile_warning() -> Option<(&str, &str)>`, with `(tuned_for, running)` order, matching the JSON. Do not print from libraries or SQL; the command keeps its one stderr warning at the ordered output boundary. Bare value calls retain their bare shape and have no warning channel. On a mismatch, a caller seeking the warning uses `details` or a SQL details form. When only one name exists, no warning. A mismatched pair still judges normally if limits pass.
4. A loaded question's `model` continues to override engine default through the existing per-question model path. The runtime profile does not choose or change model; actual reply model stays `meta.model`. Question digest is identical for command and library given the same effective question, threshold and saved name. It may differ when the caller overrides the threshold or changes question shape. Request digests remain tied to actual wire requests, which can differ with batching. `meta.questions_sha256` follows the existing question-set canonical form with the top-level saved profile, not nested profiles. The current Rust `annotate` API returns bare values (`public/annotated.rs:47-98`), while its core set already preserves the identity; this ticket adds no second annotate digest writer. Recognize and relate return bare values in the public API; their saved profiles stay inside the parsed specs, and the command details writers remain the source of their digests. If a binding exposes their details, it must use that shared writer or refuse the details form before send; it may keep bare value calls. Do not claim a command detail row exists in an API that does not expose one.
5. Surface routing is fixed by the table below. A saved calibration name without a selected runtime profile is valid and changes the question digest, as ADR 0032 says; absence of a running name is not a mismatch. A wrapper that cannot preserve the saved name must return its normal usage/local error before any send. A selected runtime profile requires the existing pre-send enforcement; a wrapper may never pretend to honor it while dropping its limits. No wrapper strips `profile` while rewriting a question object. Built programmatic questions without a saved name remain valid.
6. Integrate with 0146 batching: preserve its core batch partition and content-cut logic and 0148 settings. A profile's limits close batches at the existing limiter. `batch` mismatch metadata is separate from profile warning. For batch 1 and no context, maintain old wire/request digest. Do not add a new assembler to attach identity at wrapper level; take it from parsed public/core question and set values.

| Surface | Saved name | Runtime limits profile | Observable result |
| --- | --- | --- | --- |
| Command | Existing question/set/recognize/relate file parser | Existing `--profile FILE` | Exact digest and optional warning in `--details`; one ordered stderr warning even for a bare answer |
| Rust and Polars | `Question::from_json`/`load` through `Question`, banded and typed choice/tag conversions; core question set and recognition/relation specs | 0148 `EngineBuilder::profile(path)`; Polars uses that engine | `Details::question_sha256`, `Details::to_json`, and the new typed warning accessor for single questions. Bare collection values retain their shape |
| Python, TypeScript, Ruby and R | Their existing JSON/file readers must pass `profile` to Rust unchanged | 0148 `profile` engine option | Existing `details` returns the command's meta fields; bare calls retain their shape |
| C | The JSON request passes `profile` through `Question::from_json`; no second C question parser | 0148 `thinkthen_engine_new_with` JSON `profile` path | Existing `details` request returns the command's meta fields; C error slot reports refusal |
| DuckDB, PostgreSQL and SQLite | Their question JSON/file adapter must preserve `profile` through public `Question` | 0149 SQL profile JSON setting and `EngineBuilder::profile_json` | Where SQL exposes details, exact digest and warning meta; bare SQL value keeps its type |

For every row, a selected limits profile is checked at the prepared request boundary. For a saved calibration name that the route cannot carry, refuse before sending with the host's existing usage/local error kind and a sentence naming the unsupported `profile`; do not reinterpret it as a runtime profile path. File syntax/read failures keep the existing local-file kind, while caller supplied JSON failures keep usage. No new per-call profile override is added. The file's `model` retains its existing precedence over the engine model, and `meta.model` is the model reported by the actual reply. Neither model nor runtime profile changes the question digest.

## Proof before build lands

Start red with an outside-in replayed cross-surface case: one `decide` file with a fixed saved profile and a fixed expected 64-character digest taken from the specification's canonical bytes, not computed by the code under test. Cover the command, Rust, Python, TypeScript, Ruby, R, C, Polars and each SQL surface at its real entry point. For Polars, use the Rust engine's `Details` on the same parsed question alongside the column call; the column API itself is bare. Assert the exact digest and profile metadata wherever the surface exposes details; use one shared case, avoiding parallel expected-value assemblers. A second case with selected runtime profile of another name asserts the exact `{"tuned_for":"old","running":"new"}` pair, with command stderr once and structured detail metadata without library stderr. A same-name case asserts no warning.

Use a counted loopback listener for an over-limit request and an invalid runtime profile. Assert zero sends on the live path, the exact error category and safe message, and no cache/replay/key access where the existing boundary promises it. If any surface deliberately rejects a saved name because it cannot preserve it, add an outside-in zero-send refusal case for that actual route; never add a test-only route to manufacture a refusal. Test a command batch whose next record exceeds one profile limit, comparing its grouping and request identity with the recorded 0146 behavior; a batch-1 no-context regression pins unchanged wire bytes. Do not demand equal request digests between a batched command and a current per-record library call. Check model override retains actual model metadata while the saved-profile digest stays fixed. Pin a question set's existing `questions_sha256` canonical form, and the command's recognize and relate digest/warning paths. Wrapper details for those verbs run the same case only if they actually expose a details form. Every test must state the credible regression it catches, why existing tests miss it and whether it needs a hook; use none.

The primary regression is today's `None` at `public/results.rs:211,228`; the shared case must fail if either one returns. Existing core digest tests prove a name changes the hash, but they never cross the public API or wrappers. The mismatch case must fail if a binding drops its runtime profile or a result writer omits the warning. The zero-send case must fail if a rejected profile reaches the live listener. These use public entry points and a real loopback listener, with no test-only export or flag. Red-green scaffold tests are removed or converted to these outside-in contract and regression cases before the build lands.

Run the five gate rungs for the eventual build and all supported surface checks. The design draft itself runs only ticket, markdown and diff checks.

## Deferred gaps

No automatic profile discovery, tokenizer estimate, request reshaping beyond the existing limits, threshold recalibration, new model-version pin, new warning channel for bare values, or retroactive rewriting of cached/recorded answers. A saved profile name alone cannot prove that a backend has those limits; when no runtime profile was selected, ADR 0032 emits no mismatch warning. Document that accurately.

## What Ian can overturn

The surface-routing and refusal policy, public metadata access shape, and any further decisions recorded in this ticket. ADRs 0032 and 0048 remain accepted authority; overturning their identity or batch rules requires an ADR.

## Evidence

- Starts from: Experiment 284 report 24, the matching repository issue, current-main source cited above, ADRs 0032 and 0048, 0146's landed batching path, and accepted 0148's explicit deferral.
- Keeps: Existing file grammar, core canonical question and set digests, command warning rule, backend profile limits, model precedence, batch/request identity, replay and cache behavior.
- Changes: Carries saved calibration profile through every supported library path, compares it with the explicitly selected runtime profile that 0148/0149 supply, exposes mismatch metadata on details results, and refuses an unhonorable profile before sending.
- Proof: A pinned shared cross-surface digest case, exact warning cases, counted zero-send refusals, batch identity and model metadata regressions, then all five gates for the build.
- Defers: Profile discovery, inferred backend limits, threshold retuning, new product knobs without a demo, and record migration.
