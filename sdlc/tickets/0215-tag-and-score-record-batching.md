# 0215: Batch tag and score records

Status: Design ACCEPT at `70dc1755` by fresh independent reviewer `01a0e5f3-6946-7342-9544-34b9352902db`. B9 runtime and paid proof remain unbuilt; this acceptance grants neither. Owner: Codex.

## Outcome and authority

Build B9 of the [accepted batching issue](../issues/2026-09-26-batching-design.md): record-mode `tag` and `score` fill requests by default under ADRs [0048](../planning/adr/0048-records-batch-into-full-requests.md), [0051](../planning/adr/0051-every-address-has-a-ceiling-and-a-refused-batch-halves-once.md), [0053](../planning/adr/0053-the-pause-fires-in-every-mode-and-batches-have-a-member-cap.md) and [0055](../planning/adr/0055-decide-filter-and-rank-batches-send-each-record-once.md). `--batch 1` without context keeps each verb's exact existing request and recording identity. One paid, nongating comparison per verb at `--batch 1` and the default uses at least 200 labeled items and reports its accuracy and cost. Remove tag and score from S1's unbatched list only with a built, proved result. This ticket introduces no new public batching choice and needs no ADR 0092.

## Retained command contract

One document keeps its present request, compact JSON array for tag or JSON number for score, output and exit semantics. In record mode each input produces one ordered `{"input":RECORD,"value":ANSWER}` row, or the established detailed form. Tag keeps 1–20 unique labels in declared order, optional descriptions, an independent yes probability and one cut per label, equality passing, and `[]` as a successful answer. A band, raw or quiet view stays refused. Score keeps 2–10 ordered levels, list or described map identity, its probability-derived weighted number, and no threshold, raw or quiet view. A missing or bad answer is a Backend failure, never a tag null/empty list or score zero. Preserve six error kinds, safe diagnostic sentences, the first failed record and already printed prefix, one signal/stop outcome, replay/cache rules and final `--facts` after joins and usage flush. A question whose text is structured JSON stays one record per request; explicit context still requires quotable text.

## Proposed B9 path

1. Add the existing `Batching` argument group to tag and score and carry its typed `--batch`, `--context` and `--max-request-bytes` through `cli/judge.rs::tiers`. Let `cli/asked.rs::{tag,score}` return the already used `FileTier`, taking only a **top-level** `batch` from `core/question_file.rs::parse_top`. Keep typed call > `THINKTHEN_BATCH` > file > `max`, and the separate request-size flag/environment/default tier. A typed `--batch` or `--context` on one document is refused; ambient batch alone does not change one-document bytes. Preserve the existing calibration warning and `meta.batch_warning` behavior where a tag cut was tuned at another setting. Score has no cut or threshold to warn about.
2. Feed `Asks::Fixed` into the existing `cli/asking/batched.rs` reader and `core::Batcher`; tag already uses `fixed(&settled)`, so its current defect sentence is no evidence of an unsupported question. Keep input-order content cuts over selected record compact-JSON bytes, 4,096-member cap, 50 ms pause in every mode, `--jobs` as batches in flight, bounded output, and duplicate sharing only for equal selected evidence **and complete logical question**. That complete question includes tag labels, descriptions and order, or score levels and descriptions. Reuse 0213's final question-aware key after it lands; the fixed tag/score case has one question per run. Keep each row's original `input` even when its selected evidence shares an answer.
3. For a no-context multi-record tag or score batch, keep ADR 0048's `{"records":[…]}` evidence; ADR 0055 changes only decide/filter/rank, and the tag/score long-record comparison has not been run. Quote each distinct selected record in one logical question. `Plan::wire_question_count` expands tag into one adjacent yes/no wire question per label, while score uses one levels wire question. Use the complete encoded body and real wire count, including `q9` to `q10` name growth, for size and profile limits. A soft `--max-request-bytes` threshold closes a batch; a no-context singleton passes it as ADR 0051 item 1 requires. An explicit profile's hard `max_request_bytes`, `max_evidence_bytes` or `max_questions` can refuse even that singleton before send. Context over its one-record limit is a local Usage refusal before send.
4. The decoder already folds each adjacent tag label answer into **one logical** `Answer::Tag`; score decodes one `Answer::Score`. `Batch.questions` currently stores first **wire** offsets, but `Reply::outcomes()` indexes **logical** questions. B9 must carry or derive a distinct logical answer index for each member, repeats included, while retaining wire starts for sizing and identity. Feed that one complete `Answer` through existing `answer.read(threshold)` and `Judging::row_of`; never use only tag's first label. A missing/bad tag label fails that logical tag record. A partial reply prints the earlier usable records and stops at its first failed record. A whole-request failure stops at the batch's first record.
5. Keep the existing one eligible status 413 or named token-limit 400 halving of a batch of two or more **members**, including duplicates. Rebuild each half's same fixed logical question, selected values, context and exact body; a one-member no-context half uses old request bytes. The first half prints before the second; an unsuccessful first half sends no second half; no half splits again. Other retryable statuses resend the whole batch. `meta.requests` and cache/recording keys use each actual request digest; detailed `meta.batch` carries setting, member count, position, close reason, usage, requests sent and split marker. Even shares sum to request totals. Final `--facts` counts actual attempts including refused/retried sends and joined replies, omits unreported token totals, and does not count speculative rows past the ordered stop as finished records.
