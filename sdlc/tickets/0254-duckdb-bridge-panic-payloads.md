# 0254: Dispose of caught payloads inside the DuckDB C++ bridge scope

Status: source correction built on main `555b89ab`, awaiting fresh High code review. The independent design review accepted `6d3c90dc1be931a441db22de4659a125bf88198b`. The coordinator approved implementation under the Lanes claim. Owner: Codex. This is the current product C++/Rust bridge, not the retained DuckDB C API or `proof/0201` stand-in. The [preflight](../records/0254-duckdb-bridge-panic-preflight.md) traces the seven catch sites and package route. This ticket retains the existing panic-secrecy outcome in [the open issue](../issues/2026-09-27-panic-diagnostics-can-copy-payloads-across-host-boundaries.md); it adds no issue count.

## Outcome and retained behavior

A caught Rust panic in the product DuckDB C++ bridge must discard no opaque payload outside the bridge's marked thread scope. Keep a payload with a panicking destructor from invoking the prior host hook, writing its marker to either process stream, unwinding through `extern "C"`, or replacing the bridge's existing fixed error. A later call must work. An unrelated host thread still reaches its prior hook. Preserve the six error kinds, fixed non-retryable Defect policy, C++ exception handling, cancel/closed-channel behavior, nested engine hook scopes, and the existing seven fallback shapes: `guarded`'s fixed defect string; `reply_boundary`'s status 4 with null bytes and zero length; init's 4; query begin's null; query stopped's 1; query end's void return; and the detached worker's fixed `thinkthen defect: the engine worker panicked`. C++ currently converts a status-4 reply with no buffer to `thinkthen defect: the bridge returned no error buffer`; keep that visible mapping. Defects remain statement errors, including for try-details.

Use ADR 0098's accepted disposal rule: forget each caught `Box<dyn Any + Send>` while bridge depth is still marked. A caught panic then retains one allocation, potentially including private bytes, until process exit. This prevents its destructor from running; it does not erase the bytes or bound accumulation during repeated defects. Do not swap the process-global hook per call, add a public panic switch, claim immunity to a later host hook replacement, or change unload/pinning policy without new artifact evidence. The bridge's existing once-installed hook delegates for unrelated threads. Engine worker scopes from ADR 0081 may nest inside it. The C++ interrupt callback is `noexcept` and catches its own exceptions; C++ exceptions stay on their side of the bridge.

## Bounded source change

`databases/duckdb/bridge/src/ffi.rs` is 496 nonblank lines against the 500-line file cap. Extract its hook depth and catch/disposal logic into one private, export-free `bridge/src/ffi/panic.rs` child. Keep a small wrapper in `ffi.rs` so all seven existing call sites retain their current return shapes. The catch for owned work must execute inside `in_bridge` and forget its `Err` payload before `BridgeDepth` restores. Preserve an outer ABI containment catch for hook setup and depth-guard construction, disposing of any opaque outer payload before returning its existing fallback; a hook-install failure cannot be retroactively hidden from the hook that ran before installation. The load entry must still install the hook before `signal::install` and `signal::start_bridge`, with those latter operations inside the marked catch. The detached worker must enter its own marked scope and send its existing fixed defect rather than dropping a payload or losing the channel. `bridge/src/errors.rs` is a public-error mapper, not a second catch site; do not widen it. Do not add a shared framework or modify the old `databases/duckdb/src/errors.rs` guard.

Keep unsafe exports in files whose basename is `ffi.rs`: the 0247 review showed that policy rejects them in a differently named child even when the compiler accepts them. The new `panic.rs` should hold only safe private scope code. If a test-only C ABI symbol is unavoidable for native linkage, place it in a test `ffi.rs` path and prove that the release artifact excludes it; prefer a private child invoking the actual product `reply_boundary`, `guarded`, and `run_detached` with injected closures. Re-measure the DuckDB `src` plus `bridge/src` ratchet, inspect the root source ratchet only if root files change, and explain any growth after checking existing guard and child helpers for duplication.

## Smallest outside-in proof

One fresh child process runs against the **actual bridge module**, not a retyped guard in `proof/0201`. It installs a prior host hook, then invokes the real shared reply boundary with a string marker and an opaque payload whose `Drop` panics with a different marker. Pin the unchanged status-4/null reply in the Rust child and retain source-review evidence for the fixed C++ fallback at `cpp/src/bridge.hpp` lines 138–147; the Rust child does not execute that C++ mapping. Then assert both markers absent from the returned error, stdout and stderr. Exercise `guarded`'s fixed defect, then the actual `run_detached` worker with an opaque payload, pin its fixed worker defect, and make a later bridge/worker call succeed. An unrelated thread panic must reach the prior hook exactly once. The parent reads both captured streams and exact child exit. This child distinguishes the current source because its outer catch drops the opaque payload after depth restoration. No public test hook, provider call, repeated stress run or all-target package rebuild is needed for the source correction.

Run focused bridge test, strict bridge Clippy, formatting, policy/source caps, and the measured DuckDB ratchet before fresh code review. Existing product package checks establish the C++ static bridge route on all four targets, but they do not prove this opaque-drop behavior. Before an installed-package completion claim, check that a package contains the corrected bridge and loads on its selected stock host. A representative available Linux load can be a focused checkpoint; native Intel/macOS 15 and release-runner qualification remain with their existing owners. Do not infer a DSO hook lifetime from source alone.
