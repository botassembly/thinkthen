# 0110: Port the DuckDB surface

Status: landed 2026-09-25 on `ticket/surface-batch`, under Ian's ruling to land each surface when ready. Integration record: `sdlc/records/surface-batch-integration.md`. Owner: Claude.

## Outcome and authority

Port the core DuckDB extension from tag `surfaces-wave7-frozen-2026-09-24b` (`9df8bae9`) onto the public Rust API as the unpublished crate `thinkthen-duckdb` at `databases/duckdb`, in its own Cargo workspace. The loaded extension keeps eleven SQL names: `thinkthen_decide`, `thinkthen_probability`, `thinkthen_choose`, `thinkthen_score`, `thinkthen_tag`, `thinkthen_annotate`, `thinkthen_details`, `thinkthen_usage`, `thinkthen_warm`, `thinkthen_recognize`, and `thinkthen_relations`. `WHERE`, `ORDER BY`, and `LIMIT` stay the filter, rank, and find verbs. Every call reaches the real engine through `thinkthen`. Ticket 0118 adds `thinkthen_relate` on the caller's database on top of this crate. `sdlc/planning/one-line-plan-2026-09-25.md` ports every surface in one batch.

Draft ADR 0047 (on the 0093 branch until 0093 lands) fixes the crate's place and its checklist. Ticket 0093 sets the workspace, lint, ratchet, and surface-rung pattern. Ticket 0095 fixes the members this binding calls. Section 3.2 of `sdlc/planning/surfaces-port-guide.md` gives the port map, and its "Shared rules" bind this ticket. Accepted ticket 0105 is the template for this ticket's shape. The 2026-09-24 design review (`sdlc/records/2026-09-24-design-review-0110.md`) found ten items. This version answers all ten. Experiment 253 then contradicted decisions 5 and 10. On 2026-09-25 decisions 5 and 10 were rewritten in place for its findings, and decision 16 was added. "Changes after experiment 253" below lists what changed. Ian ruled the split into 0110 and 0118. Ian can overturn every other decision here, including each rewrite.

## Design and decisions

1. **Two tickets.** Ian ruled on 2026-09-24 that the port splits at the relate seam, as review finding 2 proposed. This ticket keeps the extension core: scalars, questions and `@file`, SIGINT and the interrupt predicate, warm, usage, details, recognize, relations, errors and the guard, `check.sh`, deny, lints, and conformance. Ticket 0118 takes relate on the caller's database: the kept connections, the registry, the identity probe, the reaper, the relate guard, relate from rows, the queue-wait message, the SIGINT bridge thread, and cases 51 and 52. Each ticket owns its rows, budget, and red-green record.
2. **Names.** The package is `thinkthen-duckdb`. Its `[lib]` is `name = "thinkthen_duckdb"` with `crate-type = ["cdylib"]`, so the build gives `libthinkthen_duckdb.so`. A crate that depends on `thinkthen` cannot keep a lib named `thinkthen`, and ADR 0047 item 6 renamed the C lib for the same reason. The extension stays `thinkthen`: `LOAD thinkthen` and the file `thinkthen.duckdb_extension`. DuckDB finds the entry symbol `thinkthen_init_c_api` from that name. The port keeps the tag's hand-written `#[unsafe(no_mangle)] extern "C" fn thinkthen_init_c_api` in `src/ffi/entry.rs`. `no_mangle` exports it from a private module. `check.sh` calls `vendor/append_extension_metadata.py -l target/release/libthinkthen_duckdb.so -o build/thinkthen.duckdb_extension -n thinkthen -dv v1.5.5 -evf <extension_version.txt> -pf <platform.txt> --abi-type C_STRUCT_UNSTABLE`. The unstable ABI stays because `duckdb-rs` needs it, as `sdlc/issues/2026-09-21-the-scalar-bind-surface-is-unusable-on-duckdbs-stable-c-api.md` records. The build therefore loads only in DuckDB v1.5.5.
3. **No C door underneath.** The extension links `thinkthen` by path and never links `thinkthen-c` (ADR 0047 item 1). Ticket 0094 serves as the reference for the FFI edge only: one panic guard, one error-kind table, and one module that holds `unsafe`.
4. **One `unsafe` module.** The tag holds 298 `unsafe` lines in seven files. The port moves every raw DuckDB C API call, the signal handler, and the entry point into `src/ffi/`, and only `mod ffi` carries `#[allow(unsafe_code, reason = "…")]` (ADR 0047 item 3). The rest of the crate is safe code over typed wrappers. A created logical type lives only inside one wrapper whose `Drop` destroys it.
5. **Engine and its settings.** LOAD registers the functions, the SIGINT handler, and four settings through `duckdb_register_config_option`, and it touches no wire. The settings are ADR 0017 section 5's, spelled the DuckDB way: `SET thinkthen_throttle = N`, `SET thinkthen_max_requests = N`, `SET thinkthen_cache = 'DIR'`, and `SET thinkthen_cache_bytes = N`. The init callback of decision 10 reads them from the caller's client context. An unset setting reads as a null value pointer, and after `RESET` it reads as a NULL value. Both mean unset (experiment 253, D1). The extension builds its engine on `EngineBuilder::from_env()` (0084, amended at `f19cf437`), so the address, key, and cache still come from the environment, and applies each setting the caller set through its setter. A setting left unset keeps the environment's value or the default. A cache folder given from SQL passes decision 10's shape check and probe on the caller's own file system at every call's init, before the engine map is read. A refused folder reads `usage` with a pinned sentence, and the engine never touches it. `THINKTHEN_CACHE` from the environment is the operator's choice and is not checked. SQL cannot name a backend or a key.
    - **Setting types.** `thinkthen_throttle`, `thinkthen_max_requests`, and `thinkthen_cache_bytes` register as `BIGINT`, and `thinkthen_cache` as `VARCHAR`, as the spike registered them. The extension reads each number as `i64` and converts it with `try_from` into the setter's type: `u8` for the throttle, `usize` for `max_requests`, and `u64` for `cache_bytes`. A failed conversion reads the setter's own sentence, so a negative or oversized value never wraps into an accepted one. Each init checks every set value against its conversion and its setter's rule before it reads the engine map, so a map hit never skips a check. It runs each setter on a fresh `EngineBuilder` it then drops, and builds only on a map miss.
    - **The throttle is process-wide.** Under 0077 and ADR 0017's amendment "one width for the process", the first explicit throttle holds for the life of the process, and a different one is `usage`. Main enforces this itself. `EngineBuilder::build` registers an explicit throttle through `Widths::select` (`engine/facade.rs:162`, `engine/mod.rs:308`), and `select` refuses a second, different one with `WidthActive`. The public error reads `throttle 8 is already active for this process; use throttle 8 or drop the throttle argument` when 8 is active (`public/error.rs:216`). Experiment 253 (D5) ran main's width tests and confirmed it. The extension keeps no throttle state of its own. Engines live in one process-wide map keyed by the session's throttle as `Option<u8>`, `max_requests`, and the cache folder, and each is built on first use. A build that fails stores nothing, so a later call with the same key builds again and reads the same error. The map holds at most 16 engines and refuses a seventeenth distinct key as `usage` with a pinned sentence. A forked child keeps the map, and main rebuilds each engine's state and throttle selection for the child's process id, so no parent throttle carries into the child. Live requests never exceed the process's active throttle, or 4 when none is set, because every attempt takes a send permit under that throttle (`engine/http.rs:125`, `engine/mod.rs:341`). Only an engine's scheduling width stays where it was built: an engine built with no throttle schedules 4 wide, or at the throttle already active when it was built (`facade.rs:162`, 295, 331). Test: a child process sets throttle 8, runs one decide, sets throttle 4, and runs a second decide on a different text, so the cache cannot answer it. The second reads `thinkthen usage: throttle 8 is already active for this process; use throttle 8 or drop the throttle argument`, and the loopback count for it reads 0. Plant: reuse the first engine the map built for every call, whatever its throttle. The second decide then answers on the throttle-8 engine, and its count reads 1. The README says the first throttle wins for the whole process, and that live requests never exceed the active throttle, or 4 when none is set.
    - **Range.** `thinkthen_throttle` takes 1 to 32, as `EngineBuilder::throttle` does in 0086 and as the command's `--jobs` does. DuckDB has no check step for a registered setting, so the `SET` succeeds. D1 accepted 33 and -5. 0, 264, and -1 pass for the same reason, since DuckDB has no check step. The refusal can only fire at the next ThinkThen call. `u8::try_from` refuses 264 and -1, and `EngineBuilder::throttle` refuses 0 and 33. Each reads `usage` with the engine's own sentence, `a throttle is a whole number from 1 through 32`, and zero counted requests. The test pins that sentence. The README says a bad value is refused at the next call and never at `SET`.
    - **The cache cap.** Main's `EngineBuilder::cache_bytes` refuses 0 and otherwise drops the value, since 0.1 keeps no cap (`public/settings.rs:213`). The extension still passes the setting through the setter, so `SET thinkthen_cache_bytes = 0` reads `thinkthen usage: a cache cap is a whole number of bytes above zero` at the next call with zero counted requests, even when an engine for that key already exists. The value stays out of the map key, since it changes no engine. `thinkthen_max_requests` applies per engine call, and one call covers one chunk of at most 2,048 rows. A per-statement limit needs statement-wide state, and the 2026-09-21 issue records the bind path that would hold it as broken. The README states the per-chunk reach and names that issue as the lever. The warm aggregate has no client-context accessor in the C API, so `thinkthen_warm` runs on the engine `EngineBuilder::from_env()` builds with no setter. The README pins a sentence that warm reads its cache folder and throttle from the environment only, and tells the reader to set `THINKTHEN_CACHE` before a warm pass. 0118's per-database connection is the lever. Ian can overturn each of these.
6. **Chunks go in bulk.** Each scalar invoke reads its chunk, drops NULL rows, dedupes texts in first-seen order, and makes one streaming call. Decide and probability use `decide_many_with`, and `thinkthen_probability` reads `Row::probability` (G4). Choose, score, and tag use `annotate_with` over a one-question set (0095, closing R2-23). Choose and tag with list members build through `Question::choose_labels` and `tag_labels` (G5). Answers map back by text, so a repeated text or a NULL never shifts a row (R1-1).
7. **Every engine call runs on a detachable worker.** Shared rule 4 makes Ctrl-C prompt for batches and single sends alike. Each engine call from a scalar, the warm aggregate, recognize, relations, and details runs on a spawned worker. The worker owns the distinct texts as `Vec<String>`, a clone of the question, and an internal `CancelToken`. It builds its own `Batch` there, since `Batch` is not `Send`, and passes the token as `CallOptions::cancel`. The DuckDB thread waits on a channel in 50 ms ticks and reads the interrupt predicate of decision 8 on each tick. On a stop it cancels the token, detaches the worker, and raises `thinkthen cancelled: ` at once. The detached worker finishes the requests already sent under 0073 and starts no retry. Until its sends end, it holds its throttle permits. Cost: one thread spawn per chunk and about 80 lines. This answers review finding 1 with its recommended fix. The fallback it names is not taken.
8. **SIGINT and the interrupt predicate.** LOAD takes SIGINT through `sigaction` and keeps the host's action for the chain, as at the tag. The install records the host's action before `sigaction` installs ours (R7-7). The handler bumps an atomic signal count, stores the signal time in an atomic, and chains. It never allocates, locks, or calls into `thinkthen`, since 0084 does not promise that `CancelToken::cancel` is async-signal-safe. The tag's rules in `current_cancel` (a signal inside this invoke, another call in flight, an active burst, a start within one burst window) become one predicate over those atomics. A query that is reading its chunk counts as in flight (R6-6). Each call builds its own token, so no token outlives a call (R1-21, R2-14). The tag's one-shot token and its re-arm logic leave. The port guide's map (section 3.1, the `Cancel` row) says DuckDB keeps its re-arm logic. This ticket departs from that line because the worker's internal token replaces it. The signal pipe and the bridge thread that interrupts relate connections move to 0118.
9. **Deadlines.** The ruled third argument stays milliseconds and goes through `CallOptions::deadline_millis` (ADR 0041). A NULL deadline gives a NULL row, as at the tag. `thinkthen_warm` takes no deadline argument.
10. **Question arguments and file access.** A question is plain text, `'@file.json'`, or the file grammar's JSON, read through `Question::from_json`. A `Usage` from a file's text maps to the `local` word, per 0095. The tag checked `@file` against every loaded database's settings through the kept connections, because its scalars could not name the caller's database. The port reads the caller's own settings instead, and the core needs no registry. Each scalar registers through the raw C API with `duckdb_scalar_function_set_init`. Its init callback reads the caller's client context through `duckdb_scalar_function_init_get_client_context`. It keeps that context and the caller's file system from `duckdb_client_context_get_file_system` in the local state until the state's destroy callback. DuckDB's own file settings then decide every access, and the binding copies none of them. The `ffi` wrappers return `Option` for the client context and the file system, so the type forces a refusal. A missing context or file system fails the init with a pinned `defect` sentence, and no file is opened another way.
    - **`@file` reads.** Each init opens each `@file` path once through `duckdb_file_system_open` on the caller's file system and reads through the same handle. The open's error type decides. A successful open reads the file. `DUCKDB_ERROR_IO` gives the tag's not-found sentence. `DUCKDB_ERROR_PERMISSION`, or any other type, refuses with the tag's refusal sentence. A missing file and a refused file keep their pinned sentences (R1-15, R2-3). The parsed file lives in the init's own state for the rest of that init, so a chunk series on one thread opens the file once (R2-18). The tag's process-wide cache keyed by path and modification time leaves. DuckDB's file handle offers no modification time, so that key would need a `std::fs` read outside the caller's file system, and a per-init open already reads the file once per thread.
    - **The cache-folder check.** A cache folder given from SQL is checked in two steps at every call's init, for the calling database, before the engine map is read. A map hit never skips the check. First, the text must be an absolute local path with no scheme: it starts with `/` and holds no `://`. Anything else, such as `~/c`, `c`, `s3://b/c`, or `file:///tmp/c`, reads `thinkthen usage: a cache folder set from SQL is an absolute local path with no scheme`. DuckDB's file system expands `~` and routes a `scheme://` path to another file system, while the engine takes the raw text, so without this step the probe and the engine would judge different folders. Second, the probe opens `<folder>/.probe` for reading through the caller's file system. The probe almost always fails, because no `.probe` file exists, so it reads DuckDB's error type. A successful open or `DUCKDB_ERROR_IO` allows the folder, since a missing `.probe` gives that type. `DUCKDB_ERROR_PERMISSION`, or any other type, refuses it. The rule fails closed. An operating-system denial that arrives as an IO error surfaces later as the engine's own `local` error. The probe creates nothing. The success branch is argued, not measured: no spike case opened `.probe`, and every allowed case came from `DUCKDB_ERROR_IO`.
    - **Why.** The tag checked `@file` against a copy of four settings: `enable_external_access`, `allowed_paths`, `allowed_directories`, and `disabled_filesystems`. Experiment 253 (D2) found that copied rule unsound. `disabled_filesystems` reads back `''` through `current_setting`, `duckdb_settings()`, and the C API while DuckDB refuses reads because LocalFileSystem is disabled. A missing path under `..` or a symlink escapes the rule, because resolving the real path fails and the rule falls back to the raw text. `allowed_paths` naming the folder itself over-allows. Over 35 cache-folder cases, the copied rule disagreed with DuckDB's own `COPY … TO` refusal in 10. The probe through the caller's file system agreed in 35 of 35 and created nothing. The spike measured no `@file` case.
    - **Test.** The spike's 35 access cases run through `SET thinkthen_cache` and one decide. Each result matches DuckDB's own `COPY … TO` refusal for a file in that folder, since the cache writes. For each refused case, `strace` shows zero creates under the folder, and the loopback count reads 0. The shape cases `~/c`, `c`, `s3://b/c`, and `file:///tmp/c` read the pinned shape sentence with zero counted requests. The same 35 settings and paths then run through `@file`. Each case reads `<case path>/q.json`. The test writes that file into every case folder that exists, so a case under a missing path such as `ok/../out/new` reads a missing file. Each `@file` result matches DuckDB's own `read_text` on the same file, case by case. The `@file` half was never measured, so it pins no count of disagreements. The cases include `disabled_filesystems = 'LocalFileSystem'`, a missing path under `..`, and a missing path under a symlink. Plant one: restore the copied four-setting rule. Ten cache cases disagree. Plant two: treat every failed probe open as allowed. The refused cache cases turn red, and their folders gain an entry. Plant three: drop the shape check. `~/c` passes the probe, and the engine creates a folder named `~` under the working folder.
    - **Two databases.** One process opens database A with default settings and database B, which runs `SET enable_external_access = false` after `LOAD`. Both run `SET thinkthen_cache = '<tmp>'`. A's decide builds the engine and answers. B's decide on the same folder then reads the probe's refusal with zero counted requests. Next, A reads `'@q.json'`, and B's `'@q.json'` then reads the refusal sentence. Plant one: run the probe only when the map builds an engine. B's decide answers. Plant two: keep one process-wide `@file` cache and read it before the open. B reads the file.
    - **Warm.** The warm aggregate has no client-context accessor in the C API, so `thinkthen_warm` refuses `@file` as `usage` with a pinned sentence that names DuckDB's `read_text`. DuckDB checks its own settings on `read_text`. Ian can overturn this narrowing.
    - **The spike ran, and no fallback is taken.** The accepted design made a spike the first build step, with a fallback for each settings path. Experiment 253 (D1) read all eight values through the scalar init context in the stock v1.5.5 CLI and in the venv's module, with no crash. A `SET` reached the next statement and a prepared statement's next run. `SET threads = 4` ran the init on 4 threads over 3,000,000 rows, and all four saw the same values. `duckdb_scalar_function_init_set_error` raised `Invalid Input Error: thinkthen usage: …`, and the next query answered. Neither fallback is needed, so the `@file`-refuses-everywhere fallback and the `thinkthen_configure` table function both leave the design. Ian can restore `thinkthen_configure`.
    - Behavior change: a database whose own settings allow a file now reads it while another database in the same process forbids files. ADR 0038 puts each call on the caller's database, and this follows it.
11. **Recognize and relations.** `thinkthen_recognize(body, kinds)` builds through `Recognize::builder` and returns a `LIST` of `(name, kind, start, end, strength)`. `start` and `end` count code points, as DuckDB's string indexing does. `thinkthen_relations(body, spec)` reads `Recognize::from_json` or the file and returns a `LIST` of `(relation, source, source_kind, target, target_kind, probability)`.
12. **Results.** `thinkthen_score` returns the position. `thinkthen_details` returns one struct from the `Details` accessors: the yes probability, the answer word, `nearest`, `model`, `question_sha256`, `requests_sent`, and `cached`. A member the verb lacks reads NULL and never 0 (R3-11). Choose and tag now fill `thinkthen_details`, because main serves them (G5). `thinkthen_annotate` returns `AnnotatedRecord::value_json`. `thinkthen_usage()` returns `requests_sent`, `cache_answers`, `input_tokens`, and `output_tokens`. Counters have no reset, and tests assert differences around a call (0095).
13. **Errors and panics.** One exhaustive `match` maps `ErrorKind::name` to the prefix `thinkthen <kind>: `. One guard function contains every callback, and the tag's three wrappers in `guard.rs` fold into it (R2-31). `thinkthen` already stops engine panics at its public methods (0086).
14. **Test hooks.** One Cargo feature, `test-hooks`, carries every test-only door: the R7-7 raise between the record and the install, the R1-10 panic trigger that replaces the tag's `test-panic` feature, and the forced reaper pass 0118 adds for R3-1. Each hook's symbol and string starts with `thinkthen_test_hook`. `default = []`. `check.sh` builds the shipped extension without the feature and fails when the shipped file holds that prefix or `ENGINE_TEST_PANIC`, or when `cargo tree -e features` shows `test-hooks` enabled in the shipped build.
15. **Site examples go to their owner.** `site/scripts/pull-examples.mjs` copies every `site/src/data/examples/*__duckdb.json` from a private deck, so a hand edit here would vanish on the next pull. The check runs every such code block (R5-24). Decision 11 changes the recognize and relations shapes, and 0118 changes relate. The builder files `sdlc/issues/2026-09-24-duckdb-site-examples-draw-the-tag-shapes.md` in this repository with both new shapes and hands the deck's owner a matching issue in the deck's repository. The check runs the ported replacement for each of the two pages and prints a divergence line that cites the in-repo issue. The divergence list is closed and lives in the check. This answers review finding 9 through its owner option.
16. **Every scalar is volatile.** Experiment 253 (D1) found that DuckDB folds a non-volatile scalar with a constant argument at plan time. Each scalar therefore registers as volatile. Test: `EXPLAIN SELECT thinkthen_decide('q', 'a constant text')` runs with a cold cache and reads the loopback count. A volatile decide is never called during planning, and the count reads 0. Plant: register decide as consistent. The planner folds the call and sends 1 request, and the count reads 1. The builder confirms that this test turns red under the plant. The test runs under `timeout` and never passes on a hang. If `EXPLAIN` stays at 0 under the plant, the builder moves the test to `SELECT thinkthen_decide('q', 't') FROM range(0)`, and if that also stays at 0, to `PREPARE` without `EXECUTE`. Each form reads the loopback count: 0 when volatile, since no row reaches the invoke, and 1 when folded. No test-only hook serves this test. The record names the form used and why. A call folded at plan time may run without the per-thread init. An invoke whose init state is null reads `defect` and never dereferences it. A folded call that fails that way before it sends counts as red when the pinned `defect` sentence shows it.
17. **A request total per process.** Ian ruled on 2026-09-25 that every SQL surface caps the requests one process sends (`sdlc/planning/one-line-plan-2026-09-25.md`, `f78421be`). A SQL row is its own engine call, so `max_requests` alone caps nothing on a large query. LOAD registers `SET thinkthen_max_requests_total = N` as `BIGINT`, unset by default, and the extension converts it with `try_from`. Before each engine call the extension sums `requests_sent` over every engine it keeps. A spent total refuses as `usage` with zero sends: `this process has spent its request total of N; raise SET thinkthen_max_requests_total or RESET it`. Main has no per-call request limit, and the extension builds no extra engine. A call with more texts than remain sends only the first ones that fit, then refuses with the same sentence. Calls running at the same time can each spend what remains, so the total can be passed by one call per thread in flight, plus retries. A forked child starts from zero, as main's counters do. `thinkthen_warm` reads no session setting, so the total does not bind it. Test: on the generic loopback arm, a total of 3 and a decide over 10 distinct rows sends exactly 3 requests and reads the sentence, and the next call reads it too with no send. Plant: check the total only when an engine is built. The ten rows send 10 requests.

## Shared rules

This ticket follows the seven shared rules of `sdlc/planning/surfaces-port-guide.md` on main (`446a4d6b`, with the builder wording of `6eb1303e` and the paid-backend rule of `d783ab6b`).

1. **No Docker.** The check runs offline on Linux with the pinned toolchains and no container. See the gate section.
2. **Toolchains under `~/.cache/thinkthen-toolchains/`.** The DuckDB v1.5.5 CLI and the test venv live under `~/.cache/thinkthen-toolchains/duckdb/v1.5.5/`. The one download is setup with a sha256 pinned in `tools/version.env` and a refusal on mismatch. Gates then run offline.
3. **One cache and one backend per test.** Each test sets its own temporary cache folder through `SET thinkthen_cache`, or through `THINKTHEN_CACHE` for warm, and starts its own loopback backend. The held reply that can hold again and one backend per test come from ticket 0117. Main writes its usage counter under `XDG_CACHE_HOME/thinkthen-usage/` even while `THINKTHEN_CACHE` is set (experiment 253, S3). Each test child therefore also gets a fresh `XDG_CACHE_HOME` and `XDG_CONFIG_HOME`, as 0109 decision 14 does. `check.sh` refuses to start a suite when either is unset or points at the user's home folders. Plant: drop the guard. The guard's test starts a suite with `XDG_CACHE_HOME` unset and turns red.
4. **Prompt Ctrl-C.** Decision 7 runs every engine call on a detachable worker. R4-22, R5-23, and case 23 meet 100 ms.
5. **A deny plant that reaches deny offline.** The plant removes one license exception. See the gate section.
6. **No test or plant reaches a paid backend.** `check.sh` unsets `THINKTHEN_API_KEY` and sets a fake key only beside a `THINKTHEN_BASE_URL` on `127.0.0.1`. It refuses to start a suite when the address is anything else. Plant: a non-loopback `THINKTHEN_BASE_URL` still starts the suites. The guard's test turns red. The seeding plant below points `XDG_CACHE_HOME` at a temporary folder, and the builder confirms that the default cache resolves under it before running that plant. The secrecy test's base URL with credentials is a loopback address. Environment seeding is proved through the cache folder, never through a request. No plant here changes the address the engine is built with.
7. **Public engine settings.** Decision 5 exposes the throttle, `max_requests`, cache, and `cache_bytes` as DuckDB settings on an engine built on `EngineBuilder::from_env()`. Each test that needs requests in flight runs `SET thinkthen_throttle = 8` first in its own child process and never uses a hidden hook or the default. The first throttle holds for that process.
