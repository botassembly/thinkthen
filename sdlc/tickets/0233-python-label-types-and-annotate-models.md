# 0233: Type Python labels and annotate rows

Status: Design accepted at `3d44d4dd` by the same independent Sol reviewer; coordinator approved implementation under ADR 0082 and main `f261fd11` granted the runtime claims. Fresh code review of `f88e3162` found two required product corrections; the corrected candidate awaits the same reviewer. Owner: Codex. This is the existing Batch J5 item, not a new Every-item outcome.

## Outcome and authority

Python accepts ordered standard-library `Enum` classes and direct `Literal[...]` forms wherever it accepts label sets. Its stub names finite question and error kinds and the real annotate row values, including a distinct failure marker. An optional `thinkthen[pydantic]` extra reads Pydantic model/`Field` metadata and provides `thinkthen.pydantic.row_model(question_set)` for validating rows. Ordinary `import thinkthen` and all core calls keep no Pydantic dependency. ADR 0082 and the [type-contract issue](../issues/2026-09-27-one-type-contract-for-every-surface.md) approved this outcome; the public spellings below are routine design choices for review, not another Ian decision.

## Starts from and keeps

- J1 ticket 0204 and ADR 0082 settled the question/result grammar; J2 ticket 0209 landed typed pandas/Polars answer columns and the separate `failed` column. High-reviewed 0214 landed `Call.value/facts/details`, six exception classes, prompt cancellation receipts, module delegates, eager lists and batch-one request identity. Use these implementations, not a second result carrier, parser or scheduler.
- `thinkthen/__init__.py::question` serializes parts into the existing native question-file parser; `_asked` handles scalar/many/column calls, and `_spec` handles annotate. Lists and insertion-ordered maps already work, including string, object, list and null descriptions under the question-file grammar. Keep them byte-for-byte unchanged. `src/asked.rs` does not need a new public Rust question type.
- Keep `score` numeric, `choose`/`decide` unresolved as `None`, successful empty `tag` as `[]`, and a failed annotate member as the existing `{"failed":{"kind","cause"}}` dictionary. Frame columns, pandas index, Arrow ownership, final facts, ordered details, error metadata, cancellation and the receipt are unchanged. Python offsets remain code points. A model validates a returned row; it does not replace the row inside `Call.value`.

## Public input choices

1. `tt.question(..., options=SET, labels=SET, levels=SET, descriptions=MAP)` and `Engine.choose/choose_many(..., options=SET, descriptions=MAP)`, `score/score_many(..., levels=SET, descriptions=MAP)`, `tag/tag_many(..., labels=SET, descriptions=MAP)` accept the new sets. Matching module functions pass the same keyword unchanged. `Engine.recognize(..., kinds=SET, descriptions=MAP)` and its module delegate use the same normalization for kind names. The existing `options`/`labels`/`levels`/`kinds` spellings remain; `descriptions=` is the one new per-label override keyword. It is allowed with Enum or Literal forms, not beside a built `Question`, file question, or an already described map. Its keys must belong to the selected set; an unknown key is `UsageError` before any worker/send. A map value replaces only that label's default, never the whole set. The existing native question and recognize JSON parsers remain the final grammar checks.
2. An Enum **class**, rather than one member or instance, supplies labels in canonical declaration order. A string-valued member supplies its string `.value`; a nonstring-valued member supplies `.name`, so ordinary `Enum` and `StrEnum` both work without sending an integer label. Refuse duplicate resulting label strings, including aliases visible in `__members__` and collisions that would make identity ambiguous. A member's `description` attribute wins over its own distinct docstring; inherited class/module docstrings do not become descriptions. A description may use any accepted question-file description shape. `descriptions=` overrides either metadata source for one label. `Literal["a", "b"]` supplies its direct string arguments in order, with no metadata; refuse nonstrings, duplicates still present in `typing.get_args()`, and nested unions whose argument order is not a reliable contract. Python can collapse `Literal["a", "a"]` to one argument before inspection, so that original repetition cannot be diagnosed; the native choose label-count rule then refuses the resulting one-label set. The existing parsers enforce each verb's label count and validity.
3. For `recognize` keyword calls, lower the ordered kind names and descriptions to the existing closed `{"version":1,"recognize":{"kinds":{...},"relations":[...]},"threshold":...,"relation_threshold":...}` object and pass its JSON to `_Recognize._from_json`. Emit each existing keyword relation as `name`, `source`, `target`, and `either`, in `_rules` order; let the parser retain the current default `reads` (underscores become spaces), wildcard normalization, thresholds and default `ENTITY` for no kinds. Omit optional cuts when absent, leaving their current `0.5` defaults. Preserve `ask=` file/dict handling and the existing `on=` frame-column eligibility, including its relation refusal; do not put Python's frame-column `on` into the recognition question JSON. This reuses `Recognize::from_json` and `Description::of_json` for string/object/list/null kinds. `_Recognize._build` remains the narrow text-only legacy constructor, not a second structured-description parser; `relate` keeps its separate keyword builder.
4. The optional extra declares `pydantic>=2.11,<3` in `pyproject.toml`; a hash-pinned tested 2.x version and its transitive dependencies enter the development requirements only for the focused optional proof. No import is added to `thinkthen/__init__.py` on ordinary use. A `BaseModel` **class** used as a label set supplies ordered `model_fields` names and each field's `Field(description=...)` as a default; a field with no description is bare. A tuple of `Annotated[Literal["one"], Field(description=...)]` entries gives distinct described labels in tuple order. A direct `Annotated[Literal["one", "two"], Field(description=...)]` gives that one description to both labels, since the question grammar has no set-level description slot. Structured meanings use an explicit description map. All forms lower to the same list/map JSON and native parser for their verb; missing extra on a Pydantic-only form gets one actionable usage message, not a top-level import failure. Pydantic v1 and arbitrary model instances are outside this contract.
5. A Pydantic question-set model has one field per question. `bool | None` denotes decide, `Literal["a", ...] | None` choose, `float` score, and `list[Literal["a", ...]]` tag. Each field's `Field(description="question text")` supplies the question; `Field(json_schema_extra={...})` may hold existing question-file settings such as score `levels`, `threshold` or `on`. The adapter copies only accepted question-file keys and sends the resulting version-one set through the existing parser. The model is a schema, not input evidence or an annotated output instance. `Annotated[..., Field(...)]` on a field uses the same `model_fields` inspection. A root Field description on a whole model is refused, since the question-set grammar has no place for it and discarding it would change the question. Keep file/dict question sets fully supported; Pydantic is an additional authoring form.

## Public result types and optional model

- In `__init__.pyi`, define `QuestionKind = Literal["decide", "choose", "tag", "score", "rank", "find"]` for `Question.kind` and `ErrorKind = Literal["usage", "backend", "deadline", "local", "cancelled", "defect"]` for `ThinkThenError.kind` and `Completion.kind | None`. `RecognizedEntity.kind` remains `str`: it is a caller-defined entity label. Define typed `Failed` as a `TypedDict` with nested `kind` and `cause`, matching the current dictionary marker, and `AnnotatedValue = bool | str | float | list[str] | None | Failed`; `AnnotatedRow = dict[str, AnnotatedValue]`. `Engine.annotate` and the module delegate return `Call[list[AnnotatedRow] | Frame]`. The stub retains `Call` around all methods and delegates; no type alias turns a failed field into `None` or turns a numeric score into a level name. Narrow the label input aliases where Python's public typing forms permit; the runtime check remains authoritative for a `Literal[...]` type object.
- `thinkthen.pydantic.row_model(question_set) -> type[BaseModel]` accepts the same version-one dict/file form as `annotate` or the question-set model above. It produces a Pydantic v2 model with one required field per question and an optional distinct `Failed` branch: `bool | None | Failed`, `Literal[...] | None | Failed`, `float | Failed`, or `list[Literal[...]] | Failed`. It reads validated question kinds and ordered labels from the supplied set; it does not inspect an answer to invent its expected type. Use Pydantic's documented `create_model` and strict validation so a string cannot silently become a score or boolean, and forbid extra row keys. For a file, read once and validate the same bytes with the existing native set parser before deriving the model; preserve file-local versus usage errors. The generated model is used explicitly as `Row.model_validate(call.value[0])`, and the native `Call` and frame values stay unchanged.

## What the build taught us

The accepted design's two corrections held in the build: recognition needed the existing JSON parser for structured kinds, and a collapsed duplicate Literal had to reach the native label-count rule. The new listener proof captured equal request bodies and returned digests for old and typed forms, including relation and default recognition settings; invalid override and alias paths sent nothing. The optional adapter stayed lazy under an import blocker, and its strict row model kept answered, unresolved and failed fields distinct. `LabelSet` remains `Any` in the stub because Python typing has no portable annotation for a direct `Literal[...]` object; concrete `Call`, annotation row, question-kind and error-kind outputs have strict mypy proof. The first fresh code review of `f88e3162` found that a mixed score Enum's bare member became map `null`, changing its criterion from its name to `{}`, and that nullable score/tag model fields could be accepted despite a nonnullable row model. Both are corrected with exact captured score bytes/digest and four-form Pydantic refusal proof. The [build record](../records/0233-python-types-build.md) names those cases, retained installed-wheel proof, the measured 3,431 Python / 6,353 Rust ceilings, and one unrelated existing frame-listener failure requiring its owner's route. Library examples changed; marketing's separate site migration issue remains open. Fresh code/API review of the correction is required before landing. Its [review record](../records/0233-code-review.md) retains the two findings and pending status. For the next TypeScript/Ruby briefs, absence and explicit null must be checked separately under each native verb, and host optionality must match the returned row type exactly.
