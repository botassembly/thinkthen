# 0233: Type Python labels and annotate rows

Status: Proposed J5 design on clean main `95070787`; implementation files are not claimed. Fresh independent design review precedes source work. Owner: Codex. This is the existing Batch J5 item, not a new Every-item outcome.

## Outcome and authority

Python accepts ordered standard-library `Enum` classes and direct `Literal[...]` forms wherever it accepts label sets. Its stub names finite question and error kinds and the real annotate row values, including a distinct failure marker. An optional `thinkthen[pydantic]` extra reads Pydantic model/`Field` metadata and provides `thinkthen.pydantic.row_model(question_set)` for validating rows. Ordinary `import thinkthen` and all core calls keep no Pydantic dependency. ADR 0082 and the [type-contract issue](../issues/2026-09-27-one-type-contract-for-every-surface.md) approved this outcome; the public spellings below are routine design choices for review, not another Ian decision.

## Starts from and keeps

- J1 ticket 0204 and ADR 0082 settled the question/result grammar; J2 ticket 0209 landed typed pandas/Polars answer columns and the separate `failed` column. High-reviewed 0214 landed `Call.value/facts/details`, six exception classes, prompt cancellation receipts, module delegates, eager lists and batch-one request identity. Use these implementations, not a second result carrier, parser or scheduler.
- `thinkthen/__init__.py::question` serializes parts into the existing native question-file parser; `_asked` handles scalar/many/column calls, and `_spec` handles annotate. Lists and insertion-ordered maps already work, including string, object, list and null descriptions under the question-file grammar. Keep them byte-for-byte unchanged. `src/asked.rs` does not need a new public Rust question type.
- Keep `score` numeric, `choose`/`decide` unresolved as `None`, successful empty `tag` as `[]`, and a failed annotate member as the existing `{"failed":{"kind","cause"}}` dictionary. Frame columns, pandas index, Arrow ownership, final facts, ordered details, error metadata, cancellation and the receipt are unchanged. Python offsets remain code points. A model validates a returned row; it does not replace the row inside `Call.value`.

## Public input choices

1. `tt.question(..., options=SET, labels=SET, levels=SET, descriptions=MAP)` and `Engine.choose/choose_many(..., options=SET, descriptions=MAP)`, `score/score_many(..., levels=SET, descriptions=MAP)`, `tag/tag_many(..., labels=SET, descriptions=MAP)` accept the new sets. Matching module functions pass the same keyword unchanged. `Engine.recognize(..., kinds=SET, descriptions=MAP)` and its module delegate use the same normalization for kind names. The existing `options`/`labels`/`levels`/`kinds` spellings remain; `descriptions=` is the one new per-label override keyword. It is allowed with Enum or Literal forms, not beside a built `Question`, file question, or an already described map. Its keys must belong to the selected set; an unknown key is `UsageError` before any worker/send. A map value replaces only that label's default, never the whole set. The native question parser remains the final grammar check.
2. An Enum **class**, rather than one member or instance, supplies labels in canonical declaration order. A string-valued member supplies its string `.value`; a nonstring-valued member supplies `.name`, so ordinary `Enum` and `StrEnum` both work without sending an integer label. Refuse duplicate resulting label strings, including an alias/collision that would make identity ambiguous. A member's `description` attribute wins over its own distinct docstring; inherited class/module docstrings do not become descriptions. A description may use any accepted question-file description shape. `descriptions=` overrides either metadata source for one label. `Literal["a", "b"]` supplies its direct string arguments in order, with no metadata; refuse nonstrings, repeated labels, and nested unions whose argument order is not a reliable contract. The existing parser enforces each verb's label count and validity.
3. The optional extra declares `pydantic>=2.11,<3` in `pyproject.toml`; a hash-pinned tested 2.x version and its transitive dependencies enter the development requirements only for the focused optional proof. No import is added to `thinkthen/__init__.py` on ordinary use. A `BaseModel` **class** used as a label set supplies ordered `model_fields` names and each field's `Field(description=...)` as a default; a field with no description is bare. A tuple of `Annotated[Literal["one"], Field(description=...)]` entries gives distinct described labels in tuple order. A direct `Annotated[Literal["one", "two"], Field(description=...)]` gives that one description to both labels, since the question grammar has no set-level description slot. Structured meanings use an explicit description map. All forms lower to the same list/map JSON and native parser; missing extra on a Pydantic-only form gets one actionable usage message, not a top-level import failure. Pydantic v1 and arbitrary model instances are outside this contract.
4. A Pydantic question-set model has one field per question. `bool | None` denotes decide, `Literal["a", ...] | None` choose, `float` score, and `list[Literal["a", ...]]` tag. Each field's `Field(description="question text")` supplies the question; `Field(json_schema_extra={...})` may hold existing question-file settings such as score `levels`, `threshold` or `on`. The adapter copies only accepted question-file keys and sends the resulting version-one set through the existing parser. The model is a schema, not input evidence or an annotated output instance. `Annotated[..., Field(...)]` on a field uses the same `model_fields` inspection. A root Field description on a whole model is refused, since the question-set grammar has no place for it and discarding it would change the question. Keep file/dict question sets fully supported; Pydantic is an additional authoring form.

## Public result types and optional model

- In `__init__.pyi`, define `QuestionKind = Literal["decide", "choose", "tag", "score", "rank", "find"]` for `Question.kind` and `ErrorKind = Literal["usage", "backend", "deadline", "local", "cancelled", "defect"]` for `ThinkThenError.kind` and `Completion.kind | None`. `RecognizedEntity.kind` remains `str`: it is a caller-defined entity label. Define typed `Failed` as a `TypedDict` with nested `kind` and `cause`, matching the current dictionary marker, and `AnnotatedValue = bool | str | float | list[str] | None | Failed`; `AnnotatedRow = dict[str, AnnotatedValue]`. `Engine.annotate` and the module delegate return `Call[list[AnnotatedRow] | Frame]`. The stub retains `Call` around all methods and delegates; no type alias turns a failed field into `None` or turns a numeric score into a level name. Narrow the label input aliases where Python's public typing forms permit; the runtime check remains authoritative for a `Literal[...]` type object.
- `thinkthen.pydantic.row_model(question_set) -> type[BaseModel]` accepts the same version-one dict/file form as `annotate` or the question-set model above. It produces a Pydantic v2 model with one required field per question and an optional distinct `Failed` branch: `bool | None | Failed`, `Literal[...] | None | Failed`, `float | Failed`, or `list[Literal[...]] | Failed`. It reads validated question kinds and ordered labels from the supplied set; it does not inspect an answer to invent its expected type. Use Pydantic's documented `create_model` and strict validation so a string cannot silently become a score or boolean, and forbid extra row keys. For a file, read once and validate the same bytes with the existing native set parser before deriving the model; preserve file-local versus usage errors. The generated model is used explicitly as `Row.model_validate(call.value[0])`, and the native `Call` and frame values stay unchanged.

## Proof and implementation boundary

It checks declaration order, one-label explicit override, structured description retention, and unknown override with **zero listener sends**. Exercise an engine method, its module delegate and one many route in that table; keep one historical `batch=1` body/digest assertion. A separate partial annotate row checks answered value, `None` and exact failed marker, plus the already stable frame dtype/`failed` column without repeating the 0214 matrix. One optional case checks a model field and an `Annotated[..., Field]` label route, then `row_model(...).model_validate` accepts answered/unresolved/failed rows and rejects a wrong kind; one isolated plain import without Pydantic proves the base wheel remains optional. A bounded strict static-type fixture checks the six-kind and question-kind literals, `Call` wrappers, and annotate row union. Pin `mypy` as a development-only requirement with hashes and invoke `tests/type_contract.py` from the Python check rung so it cannot rot; no test-only product hook or paid call is needed.
