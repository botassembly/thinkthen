# 0344: A both-ways relation edge says so

Status: in progress. Lane claude-2. Branch `ticket/0342-s2-both-ways-edges`. Plan: `sdlc/planning/cleanup-2026-09-30.md`. Carries the both-ways edge shape that ticket 0342 deferred to "its own relate ticket after 0314 slice 4", issue priorities rank 9, and the second half of `sdlc/issues/2026-09-30-relate-pair-planner-loses-precision-on-the-beatles-bench.md`. Amends ADR 0057 item 6. The shape is a coordinator default Ian can overturn.

## Outcome

An edge of an `either` rule carries `"either":true` as its last member, after `probability`. Its `source` and `target` stay in input order, and each unordered pair still appears once. A directed edge writes no `either` member, so every directed edge keeps its bytes. That is the one documented edge shape, on:

- `relate` bare output and the `value` of `relate --details`;
- `recognize` relations, bare and in `--details`, because recognize and relate share the edge type;
- the Rust library, where `Edge::either()` and recognize's `Relation::either()` return the flag;
- the C door and every library that reads relate or recognize results as JSON, with no hand code, because each passes the engine's JSON through;
- the libraries that build typed edges by hand (listed under Changes), which gain an `either` attribute;
- the SQLite, DuckDB and PostgreSQL `thinkthen_relate` tables, which gain a last visible column `either`, false or 0 for a directed edge.

Question keys, request bodies, cached answers and plans stay the same.

- Defers: a `pair` array in place of `source` and `target`. Ian can overturn this choice before 0.1. `single` with `either` stays refused, as ticket 0342 left it.
