# 0262: Pack C# and JVM binaries with one matching C archive

Status: corrected design accepted by fresh independent review at `da2ed94a`; coordinator approved implementation and pushed the exact claim at main `16e77459`. No package, backend, workflow or registry action had run at design acceptance. Owner: Codex.

## Outcome and retained behavior

One local Linux x86-64 invocation builds the existing versioned C header/shared/static archive and packages the current C# NuGet wrapper and Java/Kotlin/Scala JARs from the same clean committed source. It records a checksum beside each versioned outer archive. Each managed archive names the exact C archive SHA-256 that its installed consumer must use. Fresh isolated consumers load only the unpacked managed files and unpacked C library, make successful counted loopback calls, and refuse a missing, changed, mismatched or extra file before either managed consumer starts. Keep `libraries/csharp/check.sh` and `libraries/jvm/check.sh` source mode, their 30-arrival C# and three 60-arrival JVM matrices, 55-schema/29-applicable J1 checks, ABI export checks, cancellation and package-member plants. This ticket does not publish NuGet/Maven packages or close the original consumer issues.

The [preflight](../records/0262-csharp-jvm-release-preflight.md) traces the current hardcoded debug-native and checkout-source paths. Use the 0261 packer's clean-commit fresh-C rule, adjacent SHA files, private pair preflight and `installed.sh` scratch/unpack contract. No runtime ABI identity handshake, generic language packaging framework, second validator, or new ADR is needed.

## File and identity contract

`release-pack x86_64-unknown-linux-gnu OUT c csharp jvm` is the explicit pilot route. It must start from a clean commit, build `part_c` once in non-reuse release mode, and require that freshly built C part earlier in the same invocation. `--reuse`, a preexisting C file in OUT, and a wrapper-only invocation refuse. The default part list and established `--reuse` behavior remain unchanged. Record the exact source SHA, host/target, tool versions, build command, C member hashes, each managed inner artifact hash and all three outer hashes. The C archive's engine dependency tree makes a header-only source comparison inadequate.

The versioned outer files are `thinkthen-csharp-$V-$TARGET.tar.gz` and `thinkthen-jvm-$V-$TARGET.tar.gz` beside `thinkthen-c-$V-$TARGET.tar.gz`, each with the existing adjacent `.sha256` format. The C# outer archive has exactly `Botassembly.ThinkThen.$V.nupkg` and `THINKTHEN-PACKAGE-INPUTS`. The nupkg is built by `dotnet pack libraries/csharp/ThinkThen.csproj` from `src/ThinkThen.cs`, `LICENSE` and `README.md`, with an isolated local restore source; it contains no native library. The JVM outer archive has exactly `thinkthen-door.jar`, `thinkthen-kotlin.jar`, `thinkthen-scala.jar`, `pom.xml`, `LICENSE`, `README.md` and `THINKTHEN-PACKAGE-INPUTS`. The POM preserves the integrated `io.github.botassembly:thinkthen-jvm:0.0.1` coordinates without a Maven publication claim. The native C archive remains separate and supplies `include/thinkthen.h`, `lib/libthinkthen.so`, soname link, `lib/libthinkthen.a` and pkg-config metadata.

`libraries/jvm/build.sh` currently writes classes and JARs into persistent `libraries/jvm/target`; its `package_check.py` compares JAR members to that same directory. A leftover class in both places could pass that self-consistent check while entering a release file. For release mode, pass a new absolute `THINKTHEN_JVM_OUT` pointing to an empty directory made by the packer's existing `scratch_dir` in this invocation. `build.sh` refuses a missing, symlinked or nonempty release output before invoking any compiler, writes all three class trees and JARs only below that directory, and never removes a caller-owned path. Without the variable, it retains the current source-mode `target` behavior. Let `tests/package_check.py` read that same explicit fresh output in release mode, while preserving its source default; its class/JAR comparison then starts from an observed empty tree. Copy only those newly built JARs into the wrapper stage. An inner-JAR inventory and the clean source build receipt still supply the release claim; the persistent source tree is never a release input.

Both managed wrappers carry the same strict five-line fixed-data manifest introduced by 0261: `source_commit`, `target`, `version`, `c_archive`, `c_sha256`. The packer calculates the C SHA after the fresh C pack; no caller supplies it. Extend the private `sdlc/scripts/release-go-cpp-pair` with one literal `csharp-jvm` mode while leaving its existing one-argument Go/C++ behavior intact. The historical filename stays private; the mode selects only the fixed C#/JVM/C basenames and adjacent sidecars, rejects any other C#/JVM/C family archive or sidecar for another version/target, verifies all outer SHA lines, requires one manifest in each managed tar and compares the exact manifest bytes to the actual C archive digest. It treats manifests as data, never shell input. The two modes each validate their selected pair and one C archive, so a full bundle containing both pairs can call both without treating the other pair as an extra. Source SHA equality is a bundle-consistency check. The clean non-reuse command and build receipt establish provenance; neither mode demands manifest SHA equal a later checkout HEAD or claims authenticity against a malicious rewrite of archives and checksums.

`release-smoke` calls that same preflight in `csharp-jvm` mode if either managed family appears, before its backend starts or archive loop. It routes the two exact patterns before the broad command pattern and passes the selected wrapper plus the validated C path to each installed selector. Go/C++ routing and the nine legacy required families remain unchanged. C#/JVM are conditional until a later workflow ticket makes them required. A three-file OUT is a passing pair-preflight baseline, not a passing full-bundle smoke.

## Installed consumers and smallest proof

In installed-file mode only, each managed `check.sh` unpacks its wrapper and the passed C archive into separate fresh scratch folders with `installed.sh`. It does not build debug C, read `libraries/c/target`, read managed `target/` artifacts or copy product source from the checkout. Preserve the existing source mode exactly. Run `check-c-exports.py` against the unpacked C header and shared library, then compare the separately installed shared-library bytes actually loaded by each consumer to that archive member; C# also extracts the archive header and static member into its prefix and compares those copies. Inspect decompressed nupkg/JAR members for the accepted package inventory, matching `0.0.1` inner metadata, missing native bits in the nupkg and private build path/probe bytes. Parse the nupkg's internal nuspec and the unpacked JVM POM as data and compare their versions with the selected root `$V`; never evaluate them as shell. An inner hash in the build receipt identifies each managed file, while the checked outer tar SHA protects it in the local bundle.

For C#, adapt `tests/isolated_consumer.py` to accept explicit nupkg and C archive paths from the installed selector instead of its current fixed `target/scratch/managed` and debug-native tar. Run its existing `tests/source/Installed.cs` consumer once in a fresh unrelated bwrap root, with a local NuGet feed and no product source, Rust compiler or checkout build tree exposed; the .NET SDK remains available to compile that consumer. Its two public calls must print `INSTALLED_JSON_ENVELOPE_PASS` and `INSTALLED_CSHARP_CONSUMER_PASS`, produce exactly two independently counted complete request bodies for `consumer-csharp` and `consumer-json`, and keep the spent-token zero-send check. The checkout supplies only test-authored consumer source and backend code; the binding and native bytes come only from the unpacked files.

For JVM, retain `tests/installed.py` and `tests/consumer-run.py` as the bwrap/backend route but add a bounded artifact selector. It copies only the three unpacked product JARs and C shared library into each isolated consumer root, not `kotlin/KotlinCaller.kt`, `scala/ScalaCaller.scala`, `target/native` or compiled checkout classes. Three small test-authored consumers compile against those JARs: Java calls `thinkthen.Door`, Kotlin calls its packaged `KotlinFacade`, and Scala calls its packaged `ScalaFacade`. Run one `decide("Is it?", ...)` per language under JDK 21 preview/native-access flags, assert exact output and one complete body each for distinct `release-java`, `release-kotlin` and `release-scala` states, and assert three total backend attempts/connections. This proves each packaged facade plus native load without repeating the three 60-arrival matrices. The existing source mode keeps those matrices and its cancellation, one-MiB and J1 plants. Report the actual JAR classpath and absolute native path. Do not copy product source from the checkout into an installed root; test-authored consumer source is allowed.

The passing baseline is `release-pack ... c csharp jvm`, then `sh sdlc/scripts/release-go-cpp-pair OUT csharp-jvm` returning 0 on exactly the three expected files and sidecars, then the two installed selectors returning 0. A focused build-boundary plant puts `classes/door/Stale.class` into a fresh test-owned output directory and invokes `build.sh` with `THINKTHEN_JVM_OUT` set to that directory. It must refuse the nonempty output before javac starts, without deleting the plant; the normal release invocation starts with an empty scratch output and its three JAR member lists contain no `Stale.class`. This catches the stale-class path that a comparison against persistent classes would miss. On copies of the passing package baseline, remove JVM and its sidecar; alter one C# archive byte without updating its sidecar; replace C by a separately valid, differently hashed C archive and update its sidecar; and add a second C# family archive/sidecar for another version. Each plant runs the same preflight before either selector and must exit nonzero with a named missing/checksum/C-identity/extra-family diagnostic, zero consumer starts and zero loopback sends. Pass one missing-file plant through the actual `release-smoke` entry to prove it calls preflight before backend startup. Preserve the full-bundle smoke's nine-family presence check. Record exact source and artifact hashes, commands, process exits, output, backend bodies/counts and missing-tool/exit-77 behavior. No paid call, stress run, registry or workflow dispatch is part of this local proof.
