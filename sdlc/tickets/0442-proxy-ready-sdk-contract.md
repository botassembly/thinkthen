## Design notes

### Outbound identity and provenance

Use `User-Agent: thinkthen/<engine-version> (<surface>)`, `X-ThinkThen-Call-Id` and `X-ThinkThen-Request-Id`. The version is the Rust engine crate's compiled semantic version, so independently packaged wrappers do not claim the wrong engine version. The exact surface tokens are `cli`, `rust`, `c`, `python`, `pandas`, `python-polars`, `rust-polars`, `javascript`, `ruby`, `r`, `cpp`, `go`, `csharp`, `java`, `kotlin`, `scala`, `swift`, `zig`, `php`, `dart`, `objective-c`, `ada`, `cobol`, `flutter`, `duckdb`, `sqlite` and `postgresql`. TypeScript and JavaScript both truthfully use `javascript` at runtime; each outer JVM and dataframe wrapper supplies its own token, with no stack/source guessing. The C door validates this closed token list. Each call ID is unique across concurrent calls and a new invocation; each request ID is unique within and across calls to practical collision resistance. Add the same `call_id` to the existing `facts` object on success and started failure, including a no-send call; repeated SQL rows of one call have the same ID and facts. IDs contain no caller text, key, address or model. They are absent from cache keys, recording bodies, usage files and key-bearing diagnostics. The proxy scopes deduplication to the authenticated caller plus request ID, and must compare request bodies before treating a retry as duplicate. A different body with the same ID is a conflict, not a hit. A status retry retains its ID; a split child does not. The SDK still counts each transport attempt as sent and retry even if a future proxy deduplicates billing. A transport failure is not retried under the existing rule. The existing `x-typesafe-request-id` is a backend reply observation and cannot stand in for the outbound request ID. The contract does not choose an ID generator; implementation review must establish practical uniqueness, including concurrent calls and forked processes, without hashing caller data or adding a dependency.

Add `meta.origin` with emitted values `live`, `cache` and `replay`. It describes this result's retrieval: `live` if any question required a live reply, `cache` if all questions came from ordinary cache lookup, and `replay` for explicit offline replay. Reserve `proxy` and `memory` in the schema for a later source that can attest those meanings; a proxy response over today's model wire is `live` at the SDK boundary. For every result, add `meta.question_sources`, an ordered array aligned one-to-one with `meta.requests`; each entry carries exactly `origin` (`live`, `cache` or `replay`) and the concrete `answered_by`. This shows mixed cache/live provenance without changing `meta.requests` or the existing question observations. Add scalar `meta.answered_by` when every constituent question agrees; omit it when the models differ. Retain `meta.model` and its historical scalar behavior for compatibility; it is not a new proof that mixed answers agree. Add optional `meta.proxy` as a reserved object whose initial recognized member is `decision_id`; omit it in 0.2 unless an actual, validated proxy decision ID exists. A plain model reply or unknown header must not fabricate that ID. Existing mixed-model refusal rules for live filter/rank/annotate stay.

Treat a successful reply's `Cache-Control: no-store` as a prohibition on writing its answer to the platform cache or an explicit recording folder. A preexisting held cache answer must not be returned during refresh. If the fresh reply says no-store, evict the previous working-cache answer under the existing transaction so a later call cannot serve stale content. Explicit `--record` cannot promise replay of a no-store reply, so return a clear local recording failure after that reply, with started-call facts, without storing it or retrying a paid request. Ordinary cache-mode calls may return the good answer without persisting it. On `--refresh-cache`, send `Cache-Control: no-cache` on every actual request, including retries and split children. Existing explicit replay stays offline, reads no header and sends nothing. The no-store rule covers the reply's entire packed response. An invalid/multiple cache-control header should fail closed for storage when it contains an unambiguous `no-store` token; define parser limits in the contract and avoid treating arbitrary unknown headers as instructions. Unknown reply body fields and unrelated headers remain tolerated; malformed known model, answer or usage fields retain their existing failure behavior.

### V2 cache identity and compatibility

Define v2 question identity exactly as SHA-256 over ASCII `thinkthen.question-key/2` followed by a zero byte, then six length-prefixed byte strings in this order: adapter name, canonical final posting URL, requested model as compact JSON string, concrete answered model as compact JSON string, canonical shared state JSON, and canonical wire question JSON. Each length is an unsigned 64-bit big-endian byte count. The version tag and lengths prevent cross-version and component-boundary ambiguity. Both model names belong in the preimage: the concrete model prevents a group move from finding the old answer, and the requested selector keeps two distinct proxy setups from sharing an answer merely because they routed to the same concrete model. The decisive safety property is that a group selector is never indexed for online cache hits to a prior concrete version. Every saved entry must have enough data to recompute and verify its own v2 key without an HTTP call: address, adapter, requested model, answered model, state and question. Current question rows contain all but an explicit key version and adapter column; the built-in adapter is known from the current store schema. Add `key_version: 2` and the adapter to each v2 saved answer. During migration first verify the v1 key from the **original stored URL bytes** and other v1 fields, then validate the stored state digest and answer against its saved question, then normalize the URL and compute v2. Normalizing before v1 verification would falsely reject or misidentify old rows. Reject unknown adapters, missing address or invalid fields locally. Legacy request-level `thinkthen.recording/1` entries retain their existing converter; never infer a missing address.

Online lookup can only know the model it asks for. It may use a v2 entry whose answered model equals that explicitly requested model. A selector such as a proxy group whose replies name another concrete model therefore goes live on every online call and writes under the actual model. It must never look up a prior group-to-model mapping as if it proved today's target. A proxy group reply must name the concrete model version, not echo the group selector. If the proxy cannot promise that, it must require a no-cache/no-store route or a future versioned target proof; merely changing the key formula cannot solve stale group hits. The known `jev-latest` forced-refresh rule remains, including any reply that happens to echo the alias. This restriction also affects an existing local alias whose requested name differs from the reported model. Document the loss of online local reuse and warn the CLI before it sends when a held answer is excluded for this reason. A first call with no held answer remains an ordinary cache miss. Do not add a discovery request or guess which unknown names are pinned. Explicit replay resolves the saved requested selector without a send. If exactly one validated historical answer matches, return it; if distinct concrete versions match, refuse locally as ambiguous with zero sends and ask for a recording with only one version. Never choose by SQLite order, lexical key or timestamp. `--record` still sends. Cache hits preserve the recorded answer's actual model and usage share. URL normalization runs before key calculation on every source, including `THINKTHEN_BASE_URL`; trailing slash and host case variants of the same final endpoint share v2 identity, while distinct paths remain distinct. Check the effective key against both the raw resolved input/posting URL and canonical URL before hashing, lookup, storage or send. Keep the existing user-information, query and fragment refusals.

This is a deliberate pre-0.2 storage compatibility change. It need not preserve byte-for-byte v1 digests, but it must preserve no-send explicit replay of committed fixtures and provide deterministic conversion for user stores. On writable SQLite, verified conversion occurs in one transaction before an answer lookup; it is idempotent and keeps original rows until the new index is committed. If conversion fails, refuse locally before a send. Read-only replay builds the verified index in memory only. Old installed writers cannot read or maintain v2 keys: do not promise concurrent old/new writers in one shared folder or a supported downgrade on the migrated store. Keep an original backup outside the migration transaction only if the existing store's backup practice already provides one; otherwise the ticket must state that users who need an old writer use an unmigrated copy made before upgrade. No automatic network probe or migration command. `meta.requests` changes to v2 keys only for answers under the new identity, so examples and fixtures that pin those keys require one controlled update. Usage state remains count-only and is never migrated through answer records.
