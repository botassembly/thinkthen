# 0224: Find one best unit from an ordered SQL group

Status: **Linux SQLite, PostgreSQL and DuckDB slices complete; remaining target work stays open.** Fresh High reviews accepted SQLite `d482ed6a` and PostgreSQL `f59bd3d5`, and Linux DuckDB `fb9009aa`, each with independent installed cases 18/19 and host edge checks. Their product source merged unchanged. Ian already approved ADR 0096. See [SQLite review](../records/0224-sqlite-code-review.md), [PostgreSQL review](../records/0224-postgresql-code-review.md) and [current DuckDB preflight](../records/0224-duckdb-find-preflight.md). This is not whole-ticket or new-platform completion.

Milestone: 0.1

## Outcome and retained behavior

Make [shared cases 18 and 19](../../conformance/cases.json) executable through each installed SQLite, PostgreSQL and DuckDB extension. The function takes one complete, ordered set, sends the one existing public `find` request, and returns the selected **original** value or an explicit none choice with its probability. Generated `u001`…`u255` IDs, the strict none lead or tie rule, first-unit real tie rule, 2–255/254 bounds, one-request identity and request body remain the settled [find contract](../../specification/find.md). A duplicate string retains its own index and probability. Scalar `ORDER BY thinkthen_probability(...) LIMIT 1` and B13 packed per-row calls are different operations and remain so. Existing SQL scalars, arrays, warm aggregates, settings, error kinds and cancellation remain unchanged.

## Approved SQL boundary

ADR 0096 recommends host-native ordered inputs: SQLite JSON string array, PostgreSQL `text[]`, DuckDB `VARCHAR[]`. Each takes plain question text and an explicit optional `none` flag; SQLite and DuckDB may take their established optional deadline after that flag. PostgreSQL returns `jsonb`, SQLite JSON text, and DuckDB a typed `STRUCT`. Each non-null result has zero-based `index` or null, selected original `value` or null, selected `probability`, and ordered candidate `{index, probability}` entries with null index for offered none. A SQL NULL top-level argument and a valid empty set return SQL NULL without a send; model-selected none is a non-null result with null index/value. A one-unit set, too many units, NULL element, wrong element type, malformed collection, invalid flag, blank question or total text over 16 MiB is Usage without a send. Built-in type binding handles PostgreSQL/DuckDB wrong SQL types. SQL group construction must name an ordering key; no aggregate encounter-order promise is inferred.

Use `Question::find` and optionally `offering_none`, then `Engine::find_with` on private index-bearing `Evidence` values. The current return is `Call<Found<Indexed>>`: access the completed `Found` through `Call::value` or `into_value`. `Found::selected` returns the original index/value through that wrapper and `Found::candidates` returns the full distribution. No public Rust accessor, copied planner, new request format or request-level batching is needed. `Question::from_json` cannot parse find: it accepts only decide/choose/tag/score question files today. Therefore the new SQL question argument is plain text, not `@file` or a serialized find question; `@` is literal text. Per-question model/profile/file precedence is not silently invented. Each host's existing engine environment, model/profile settings, cache/replay/recording permissions, process attempt total and query deadline apply at the same caller boundary. The omitted file form is part of the approved SQL spelling.

## Host placement and proof

- **SQLite:** register the 2, 3 and 4 argument direct-only volatile scalar beside `scalars.rs`; keep dynamic type checks at the edge and call `worker::run` once with its existing connection budget, interrupt and process `SendBudget`. Current `scalars.rs` is 379 nonblank lines; a private child keeps the ordered-set parser and result mapping separate from judgments. The pinned 3.50.0 host returned `["first","second","second"]` for `json_group_array(unit ORDER BY ordinal)`. Do not reuse `warm`'s distinct-pair state, failed-step finalizer or per-chunk deadline.
- **PostgreSQL:** add one parallel-restricted scalar family in a private child registered through `lib.rs`/pgrx generated SQL. Read `Array<'_, &str>` in order and refuse NULL members; call `call::read` on the backend thread and `call::run` once on its detachable worker. Use existing file-independent plain `Question::find` and the backend's settings, SQLSTATE table, statement timeout and send budget. The function reads no table or file. `array_agg(unit ORDER BY ordinal)` is the caller's ordering tool; an empty aggregate yields SQL NULL. Include the generated overloads in the packaged SQL and installed `check.sh` proof.
- **DuckDB:** Linux x86-64 C++ registers a volatile `VARCHAR[]` scalar with 2/3/4 argument forms in a private source child. Copy the list and settings before its Rust bridge's detached worker. Read `StatementOwner::Remaining` and the optional scalar deadline once for that call; use `StopFor`, `engines::options` and the existing folder probes before transport. The bridge returns an owned bounded frame that C++ decodes into the typed struct and frees. First verify the pinned v1.5.5 `list(unit ORDER BY ordinal)` spelling. Linux ARM64 and both macOS packages still retain the C API after 0201/0149/0157; a separate implementation through `src/{scalars,ffi,worker}.rs` with the same SQL shape and host proof is required before claiming all three DuckDB platforms. No platform is labeled externally blocked.

The smallest outside-in proof runs only cases `18-find-second` and `19-find-none` on each installed host's `/case/ID/capture/v1` loopback arm. Extend the shared backend's existing bounded capture selector from relation cases 42–50 to these two find cases; its three-body, 96,000-byte-per-body limit already covers each one-request fixture. SQLite's conformance runner already reads `Backend.capture()`. PostgreSQL's `check.sh` can read the existing backend `capture` command beside `bcount()` and pass it to a selected `runner.py` verifier. DuckDB needs a small `Backend.capture()` method in `tools/harness.py`, using its existing backend stdin/stdout, and a check in the installed `tools/conformance.py` path. Each runner must compare the **observed complete body** byte-for-byte with the independent corpus request, derive a digest from that observed body and actual served URL, and compare it with the expected digest independently recomputed from the pinned corpus body and that URL; also pin exactly one listener request, selected original index/value, selected probability and ordered candidate probabilities. SQL results contain no request digest and cannot substitute for capture. Remove exactly the find skip paths once these checks run. Keep the corpus's `question.find/none/units` fields as runner inputs, not a false `Question::from_json` fixture. One compact edge table checks duplicate strings with the second duplicate selected, a real top tie, a none tie, empty input and one-unit/NULL-member/invalid-type refusals. The invalid cases count zero loopback sends; no separate planner matrix or paid call. Test one held cancel and one expired query budget using each host's existing worker/budget harness; SQLite's `thinkthen_budget_ms(0)` is an accepted expired connection budget with an existing no-send regression, distinct from refused `thinkthen_max_requests_total(0)`. No sleep, broad timing or stress is needed. For DuckDB, the installed `check.sh` path currently invokes conformance only, which covers the two shared cases; any additional selected edge case must run from an invoked suite against that same installed binary. Reuse existing settings/folder/cancellation proofs where unchanged.

## What the build taught us

The initial issue correctly distinguished set-level find from scalar ranking, but preparation had to expose two traps: public `Question::from_json` cannot parse find, and public `Found` has no selected-index accessor. A plain question plus an explicit none argument reaches `Question::find`; private index-bearing `Evidence` preserves the chosen duplicate's position without widening Rust. The existing SQLite slot-aware deadline grammar needed only a parameterized slot, so the fourth argument uses the same parser. The bounded conformance capture already held complete relation bodies; extending only its case selector let the installed SQLite runner compare actual bytes and digests with independent corpus expectations. A generic backend always favors its first option, so a fixed-reply use of the existing counted proxy was necessary to prove second-duplicate and tie mapping at the host boundary. No new listener or product test hook was added. SQLite's `thinkthen_budget_ms(0)` remains an expired connection budget; the separate process request total is checked before an ordinary scalar call. The installed package passed these boundaries and pinned host load/refusal. No scaffold test was deleted or consolidated: the new cases protect distinct capture, original-index/tie, zero-send and held-interrupt boundaries. The initial SQLite policy scan exposed shared size/seam violations; the independently reviewed policy cleanup has since landed and the integrated scan passes. SQLite and PostgreSQL native reviews accepted their lifetimes and result mapping. PostgreSQL preparation avoided reusing the decision array's deduplication and proved generated overloads and grants in the actual installed host.
