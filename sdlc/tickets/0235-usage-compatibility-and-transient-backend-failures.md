# 0235: Keep old usage readers working and retry transient backend failures

Status: design proposed on main `faa9e7b8`, awaiting fresh independent High design review before runtime work. Owner: Codex. This is one pre-0.1 batch for the severity 2 usage compatibility defect and the severity 3 backend retry and timeout-advice defect. Ian's release priority and routine design delegation are recorded in the [work plan](../planning/work-plan-2026-09-27.md). Neither issue is closed by this design.

## Outcome and compatibility boundary

A current command must keep accurate count-only monthly totals, including retries, while an immutable pre-0155 binary can still parse and update its monthly file. A current build must read both old four-field files and the already written five-field files. It must recover all recognized five-field months before its first later durable usage update, so an older binary's `status` no longer fails on an old contaminated month. `status` remains read-only. A pinned older binary cannot acquire a new parser or diagnostic from this ticket: until recovery runs, it still fails on a five-field month. Users can immediately recover by replacing that executable with the compatible build. A user who must keep the old executable also needs a completed compatible-build usage write to migrate every contaminated month first. A current `status` alone cannot perform that migration, and no provider request is prescribed merely to repair advisory statistics. The release and bench owners should upgrade their pinned consumers separately; ticket 0160's current `check` fix is another reason to do so.

The existing `YYYY-MM.json` wire shape returns to exactly `schema: "thinkthen.usage/1"`, `requests_sent`, `input_tokens`, `output_tokens`, and `cache_answers`. No `retries`, extra marker, alternate schema, or unknown member enters this file again. An old writer may continue to update it under `.lock`; it cannot update a retry counter it never knew. A new private `retries-YYYY-MM.json` sidecar in the same usage directory holds `schema: "thinkthen.usage.retries/1"`, an absolute `retries` total, and an optional `last_transaction` identifier for recovery. Its name does not pass `recognized_month`, so old readers ignore it. New readers sum the four legacy counters and the sidecar retry count for each month. A missing sidecar means zero retries only for a clean legacy month. A still contaminated five-field month supplies its own retry total; if a sidecar also exists, both must agree and are never added together. `status` retains its current public fields, including `usage.path` and `retries`.

This is advisory local accounting, not the paid live ledger. A crash can interrupt an already asynchronous write and lose pending deltas today. The protocol below preserves every **previously durable** count and never silently resolves an ambiguous two-file update. It does not promise an atomic transaction across the legacy file and sidecar or exact statistics after process death at an arbitrary instruction. Do not touch or migrate the live ledger.

## Migration and ordinary writes

All inspection and mutation use the existing verified private directory, 0600 regular files, stable `.lock`, and its exclusive lock. Keep the current one-second finalization lock-acquisition bound, writer failure latch, single warning and atomic temp-write, file sync, rename and directory sync rules. A new writer first lists **all** `YYYY-MM.json` names accepted by `recognized_month`, validates every monthly row and its optional sidecar, and refuses the whole write before changing anything if it sees malformed JSON, an unrecognized field, a foreign or future schema, unsafe object, invalid count, overflow, or inconsistent retry totals. Do not infer a schema from the presence of `retries`. The new reader uses the same strict input rules under the existing shared lock. It ignores unrelated names; it never deletes them.

For each five-field month with no sidecar, publish a synced sidecar containing exactly that month's retry total, then atomically replace the monthly file with the four-field projection. Do this under one exclusive lock. If the process dies after the sidecar rename and before the legacy rename, a later new reader accepts the matching sidecar and five-field month without double counting, and the next writer finishes the projection. If it dies earlier, the five-field month remains authoritative. If both exist and disagree, refuse with the generated month filename and leave both untouched. Scan every month, not only the current one; otherwise an old `status` still fails while summing total usage. An old binary cannot interleave during a held lock. Once a month is four-field, an old writer can safely add its deltas, and a later new writer rereads the latest value under the same lock.

For a new current-month delta, update the four-field file and sidecar under the exclusive lock, with checked addition and a private synced intent file that records the prior and proposed four-field values, prior and proposed retry totals, and one transaction identifier. Its dot-prefixed name is ignored by old readers. Publish the intent before either replacement, then the sidecar with that transaction identifier, then the legacy file; sync each atomic rename and the directory, and remove and sync the intent only after both are durable. Recover an intent before scanning or mutating any month on the next writer invocation. A read-only `status` inspects an intent under the shared lock and reports a fixed recovery-needed local error; it never writes or prints the intent's contents.

| State under the lock after an interrupted new update | Writer recovery |
| --- | --- |
| Prior legacy and prior sidecar, intent present | Complete the proposed sidecar and legacy replacements, then remove the intent. |
| Prior legacy and proposed sidecar carrying the intent identifier | Complete the proposed legacy replacement, then remove the intent. |
| Proposed legacy and proposed sidecar carrying the intent identifier | Remove the completed intent. |
| Any changed legacy value after an old writer could have run, or a sidecar not matching either recorded value | Refuse; retain all files and name the generated month. The same observed legacy delta may have come from the old writer or the interrupted new update. |

An old writer may advance the legacy counters after a crash because it ignores the intent. Never replay a base delta on a guess or erase an already durable retry total. The implementation review must check the table against actual old-writer ordering, including equal deltas that mimic the proposed value. A proposed value **without** its matching proposed sidecar identifier is ambiguous and must not be accepted merely because the numbers match. If the table cannot distinguish an interleaved old writer, refuse rather than silently count twice. An unresolved intent requires an explicit inspected recovery path; it is not silently discarded.

A successful `finish()` means both files have completed their syncs and the intent is gone. A failed update keeps the existing command answer and exit, reports the single usage warning, and stops later persistence in that process. In-memory request and retry facts remain the actual attempts observed before transport. A cancelled or expired call sends nothing after its stop check, and an attempt already sent keeps its existing count. No migration runs through `status`, replay-only lookup, `--dry-run`, or any path that currently writes no usage. The ordinary first usage write is the recovery trigger; a user retaining an old binary may instead upgrade that binary and keep running without an extra paid call.

Diagnostics must distinguish cache inspection from usage inspection at the CLI edge and name only a generated month filename such as `2026-09.json` or the fixed usage directory label. A writer warning may name the same generated file. Do not print raw JSON, parser or operating-system text, user-selected path bytes, a key, a backend URL, or judged evidence. Preserve exit 5 for local `status` failures and the existing warning-only outcome of a usage write failure. The old executable's generic messages cannot change.

## Backend and timeout correction

Add 520, 521, 522, 523 and 524 to the structured retried-status classification and fixed exhausted-attempt message table. [Cloudflare's 2026 structured-error notice](https://developers.cloudflare.com/changelog/post/2026-04-27-structured-responses-for-5xx-errors/) labels 520–524 retryable and says those responses carry `Retry-After`; its [5xx reference](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/) describes their origin and gateway causes. A persistent 520 can still be an origin defect, so only the caller's existing `--max-retries` bound applies. Keep the exact-URL process gate, exponential wait, header floor, deadline and cancellation precedence, response-body withholding, refusal exit 4, and actual-attempt retry and request counts. Keep 429, 500, 502–504 and 529 behavior. Transport errors, including timeouts after a possibly billed send, remain single-attempt. `--max-retries 0` reports the first 520 with the fixed phrase and one send.

A multi-record attempt timeout should name its failed record range and advise `increase --timeout or try again`, as the singleton timeout already does. Do not suggest a smaller request from elapsed time alone. Keep size guidance for 400 `max_tokens_exceeded`, 413 and the 422 refusal. Do not infer that a 520 or a timeout proves size. Preserve safe fixed phrases and the public six-kind error model; SQL surfaces still give their bare status line.

The prior register 53/D18 correction is **partly reopened by new evidence**: Quick Fix `da606611` correctly fixed the 429 exhausted-attempt sentence, which remains done, but its multi-record timeout sentence gives size advice that the live 30-second timeout cannot justify. This ticket replaces that one sentence and its exact listener expectation. Register 13/D19 and ticket 0160 concern `thinkthen.result/1`, not the usage file schema; leave them done and separate.

- Changes: current durable retries move to an old-reader-ignored sidecar; a new writer migrates all recognized contaminated months under the stable lock; new readers understand clean and transitional files; 520–524 gain bounded retries; multi-record timeout advice names time alone.

- Defers: repair of an immutable old binary before a compatible writer runs, an atomic all-fields transaction under arbitrary process death and old-writer interleaving, status lock or filesystem I/O bounds, paid-ledger changes, provider behavior guarantees, and release/package pin upgrades owned by their consumers.

## What the build taught us

Pending implementation and independent code review. Preparation found that the old parser rejects an added field under an unchanged schema, that `status` scans every recognized month, and that an older writer still uses the stable lock and four-field shape. It also found that the prior D18 Quick Fix created the multi-record size hint; its accepted 429 correction remains valid. The builder must check the proposed two-file recovery table against real pinned executable behavior before implementing it, and record any narrower compatibility guarantee explicitly rather than treating a current-reader unit test as old-reader proof.
