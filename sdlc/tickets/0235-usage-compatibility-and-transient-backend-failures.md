# 0235: Keep old usage readers working and retry transient backend failures

Status: design accepted by fresh High review at `55137d08`; runtime implementation is in progress for fresh independent code review. Owner: Codex. This is one pre-0.1 batch for the severity 2 usage compatibility defect and the severity 3 backend retry and timeout-advice defect. Ian's release priority and routine design delegation are recorded in the [work plan](../planning/work-plan-2026-09-27.md). Neither issue is closed before verified landing.

## Outcome and compatibility boundary

A normally completed current command must keep accurate count-only monthly totals, including retries, while an immutable pre-0155 binary can still parse and update its monthly file. A current build must read both old four-counter files and the already written retry-extended files. It must recover all recognized retry-extended months before its first later durable usage update, so an older binary's `status` no longer fails on an old contaminated month. `status` remains read-only. A pinned older binary cannot acquire a new parser or diagnostic from this ticket: until recovery runs, it still fails on a retry-extended month. Users can immediately recover by replacing that executable with the compatible build. A user who must keep the old executable also needs a completed compatible-build usage write to migrate every contaminated month first. A current `status` alone cannot perform that migration, and no provider request is prescribed merely to repair advisory statistics. The release and bench owners should upgrade their pinned consumers separately; ticket 0160's current `check` fix is another reason to do so.

The existing `YYYY-MM.json` wire shape returns to exactly five JSON members: `schema: "thinkthen.usage/1"`, `requests_sent`, `input_tokens`, `output_tokens`, and `cache_answers`. No `retries`, extra marker, alternate schema, or unknown member enters this file again. An old writer may continue to update it under `.lock`; it cannot update a retry counter it never knew. A new private `retries-YYYY-MM.json` sidecar in the same usage directory holds only `schema: "thinkthen.usage.retries/1"` and an absolute `retries` total. Its name does not pass `recognized_month`, so old readers ignore it. New readers sum the four legacy counters and the sidecar retry count for each month. A missing sidecar means zero retries only for a clean legacy month. A still contaminated retry-extended month supplies its own retry total; if a sidecar also exists, both must agree and are never added together. `status` retains its current public fields, including `usage.path` and `retries`.

This is advisory local accounting, not the paid live ledger. A crash can interrupt an already asynchronous write and lose pending deltas today. The protocol below preserves every **previously durable legacy-base** total. A crash between the ordinary base and sidecar writes can leave retries lower than actual retry sends. A returned error from the sidecar write keeps the existing warning and failure latch. There is no atomic transaction across the two files or exact statistics after process death at an arbitrary instruction. Do not touch or migrate the live ledger.

## Migration and ordinary writes

All inspection and mutation use the existing verified private directory, 0600 regular files, stable `.lock`, and its exclusive lock. Keep the current one-second finalization lock-acquisition bound, writer failure latch, single warning and atomic temp-write, file sync, rename and directory sync rules. A new writer lists **all** `YYYY-MM.json` names accepted by `recognized_month` and all matching retry sidecar names. It validates every monthly row and sidecar, and refuses the whole write before changing anything if it sees malformed JSON, an unrecognized field, a foreign or future schema, unsafe object, invalid count, overflow, inconsistent retry totals for a still contaminated row, or a sidecar with no matching month. Do not infer a schema from the presence of `retries`. The new reader uses the same strict input rules under the existing shared lock. It ignores unrelated names; it never deletes them.

For each retry-extended month with no sidecar, write and file-sync a sidecar containing exactly that month's retry total, rename it and sync the directory, then write and file-sync the four-counter projection, rename it and sync the directory. Do this under one exclusive lock. If the process dies after the sidecar's rename **and directory sync** but before the legacy projection, a later new reader accepts the matching sidecar and retry-extended month without double counting, and the next writer finishes the projection. A crash before that directory sync may leave either the prior state or the matching sidecar; the retry-extended month remains authoritative in both cases. If both exist and disagree, refuse with the generated month filename and leave both untouched. Scan every month, not only the current one; otherwise an old `status` still fails while summing total usage. An old binary cannot interleave during a held lock. Once a month is four-counter, an old writer can safely add its deltas, and a later new writer rereads the latest value under the same lock.

For each ordinary new current-month delta, read the latest legacy-base and sidecar values under the same exclusive lock, checked-add, **file-sync, rename and directory-sync the four-counter legacy replacement first**, then do the same for the retry sidecar. A sidecar failure after the base directory sync does not roll back that durable base or replay its delta. It reports the existing single warning, latches writer failure and drops later queued persistence in that process. If the process dies at that point, the next current reader sees the preserved base and the last durable retry count. It may undercount retries, but does not guess missing retries from the base counters. An immutable old writer can interleave only after the lock is released; it rereads and advances the four-counter base, while leaving the sidecar alone. A later new writer rereads both durable values before adding only its own delta.

| Interrupted point | Durable state and next action |
| --- | --- |
| Migration before sidecar directory sync, including after its rename | The retry-extended month remains authoritative. The sidecar may be absent or matching; the next new writer completes the projection. |
| Migration after sidecar directory sync, before base directory sync, including after base rename | The synced sidecar and retry-extended month are safe together. A crash may retain the retry-extended month or expose its four-counter projection; the next writer completes migration if needed. |
| Ordinary write before base directory sync, including after base rename | The prior base remains durable; a crash may retain it or expose the new base. The sidecar remains at its prior durable value. |
| Ordinary write after base directory sync, before sidecar directory sync, including after sidecar rename | The new base remains durable; the sidecar may retain its prior value or its new value. Retries may undercount. The next writer adds only its own delta to observed values. |
| Ordinary write after both directory syncs | Both totals are durable; an old writer may then advance only the base. |

A successful `finish()` means both files have completed their syncs. A failed update keeps the existing command answer and exit, reports the single usage warning, and stops later persistence in that process. In-memory request and retry facts remain the actual attempts observed before transport. A cancelled or expired call sends nothing after its stop check, and an attempt already sent keeps its existing count. No migration runs through `status`, replay-only lookup, `--dry-run`, or any path that currently writes no usage. The ordinary first usage write is the migration trigger; a user retaining an old binary may instead upgrade that binary and keep running without an extra paid call.

Diagnostics must distinguish cache inspection from usage inspection at the CLI edge and name only a generated month filename such as `2026-09.json` or the fixed usage directory label. A writer warning may name the same generated file. An existing zero-byte canonical month is malformed input: both paths refuse it, name its generated filename and fixed category, and preserve its bytes rather than guessing lost totals or resetting it. A new first write must publish either a complete valid month or no canonical month; it never creates an empty canonical placeholder. The observed zero-byte file's origin is unverified. Do not print raw JSON, parser or operating-system text, user-selected path bytes, a key, a backend URL, or judged evidence. Preserve exit 5 for local `status` failures and the existing warning-only outcome of a usage write failure. The old executable's generic messages cannot change.

## Backend and timeout correction

Add 520, 521, 522, 523 and 524 to the structured retried-status classification and fixed exhausted-attempt message table. [Cloudflare's 2026 structured-error notice](https://developers.cloudflare.com/changelog/post/2026-04-27-structured-responses-for-5xx-errors/) labels 520–524 retryable and says those responses carry `Retry-After`; its [5xx reference](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/) describes their origin and gateway causes. A persistent 520 can still be an origin defect, so only the caller's existing `--max-retries` bound applies. Keep the exact-URL process gate, exponential wait, header floor, deadline and cancellation precedence, response-body withholding, refusal exit 4, and actual-attempt retry and request counts. Keep 429, 500, 502–504 and 529 behavior. Transport errors, including timeouts after a possibly billed send, remain single-attempt. `--max-retries 0` reports the first 520 with the fixed phrase and one send.

A multi-record attempt timeout should name its failed record range and advise `increase --timeout or try again`, as the singleton timeout already does. Do not suggest a smaller request from elapsed time alone. Keep size guidance for 400 `max_tokens_exceeded`, 413 and the 422 refusal. Do not infer that a 520 or a timeout proves size. Preserve safe fixed phrases and the public six-kind error model; SQL surfaces still give their bare status line.

The prior register 53/D18 correction is **partly reopened by new evidence**: Quick Fix `da606611` correctly fixed the 429 exhausted-attempt sentence, which remains done, but its multi-record timeout sentence gives size advice that the live 30-second timeout cannot justify. This ticket replaces that one sentence and its exact listener expectation. Register 13/D19 and ticket 0160 concern `thinkthen.result/1`, not the usage file schema; leave them done and separate.

## What the build taught us

Fresh High design review accepted the corrected protocol at `55137d08`; independent code review remains pending. Preparation found that the old parser rejects an added field under an unchanged schema, that `status` scans every recognized month, and that an older writer still uses the stable lock and four-counter shape. The first High design review found that a tagged retry sidecar cannot prove who wrote an equal four-counter legacy delta after a crash. The corrected ordinary write commits the base first and accepts a documented retry undercount on interruption; it has no intent journal or manual recovery dependency. The prior D18 Quick Fix created the multi-record size hint; its accepted 429 correction remains valid. The pinned binary source and current source only create or truncate `.update.tmp` before atomic replacement, so neither explains the observed zero-byte canonical file. The build refuses it and proves the canonical file remains absent when a first write fails before rename. The real pinned executable interoperability proof is recorded in the build record.
