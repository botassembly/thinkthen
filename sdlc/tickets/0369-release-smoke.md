# 0369: The release workflow's four smoke jobs pass

Status: in progress. Lane claude-2. Branch `ticket/0369-release-smoke`. Plan: `sdlc/planning/cleanup-2026-09-30.md`. Parent: ticket 0128, phase 3b.

## Outcome

Each `smoke` job of `release.yml` gets past the four failures of rehearsal run 36853575250, and no surface reports "not run" for a missing host tool, toolchain or pin:

1. The x86 Linux language tools step loads an AppArmor profile that lets the pinned `/usr/bin/bwrap` make user and network namespaces, when the runner's kernel restricts them and the plain probe fails. The probe still runs `--unshare-net`, so the installed consumers' "no network" sandbox stays the same.
2. On every target the installed Python, PostgreSQL and SQLite checks find what they need: uv's cache holds the pins for the Python the check picks, both Linux jobs fetch the pinned PostgreSQL server package for their CPU and the SQLite amalgamation, and the macOS check accepts the version line of the pinned Homebrew bottle.
3. On both Macs the SQLite check runs under Homebrew's Python, whose `sqlite3` module can load extensions. No test is skipped.
4. `smoke-bundle` reads the DuckDB archive's member list once, so `tar` no longer writes into a closed pipe.

## Evidence

- Starts from: rehearsal run 36853575250 on main `d2cf57b26`, the first run in which every build, wheel, gem, npm-pack, crate and registries job passed. All four smoke jobs failed:
  - x86 Linux (job 110353213856), step "Select installed language tools": `/usr/bin/bwrap: bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted`. The step's last check probes `bwrap --unshare-user --unshare-pid --unshare-net ... /bin/true` (`release-language-tools.py` `check_smoke_tools`). ubuntu-24.04 sets `kernel.apparmor_restrict_unprivileged_userns=1`. A process with no AppArmor profile may then create a user namespace but holds no capability in it, so bwrap cannot configure the new namespace's loopback. Locally, on Ubuntu 24.04 with the same setting, `/usr/bin/bwrap` passes the probe because this host loads Ubuntu's `bwrap-userns-restrict` profile. A copy of the same binary at another path has no profile and fails with the runner's exact message. The `--share-net` form that the PHP, Swift, Zig and C# consumers use fails the same way, with `setting up uid map: Permission denied`. Bubblewrap entered the smoke job's pins with ticket 0273. Quick fix `d18a5adb2` removed it from the build job only.
  - ARM Linux (job 110353213791), macOS ARM (110353213815) and macOS Intel (110353213967): `libraries/python` not run, `uv's cache lacks a pin of requirements-dev.txt`. `host-setup` seeds uv's cache by installing the pins under `python3.12`. `libraries/python/check.sh` picks the first of `python3.14`, `python3.13`, uv's 3.13, `python3.12`. The runners have `python3.13` (setup-python) and, on macOS, Homebrew's `python3.14`. numpy, pandas, pyarrow, polars and pydantic-core ship one wheel per Python version, so the 3.12 seed holds none of the wheels the check asks for.
  - ARM Linux: `databases/postgresql` not run, `cargo-pgrx is missing`. Linux `host-setup` installs neither cargo-pgrx nor the pinned server package. `runtime.sha256` pins only the amd64 package. Past that, the header check would compare `/usr/bin/pg_config`, which the runner image installs from apt.postgresql.org (16.15-1.pgdg), with Ubuntu's 16.15-0ubuntu0.24.04.1 server, and report "not run". The installed-file mode builds nothing, so it needs neither cargo-pgrx nor the header check.
  - Both Macs: `databases/postgresql` not run, `pg_config is not PostgreSQL 16.15`. The job installs the pinned 16.15 bottle. The bottle's `pg_config --version` prints `PostgreSQL 16.15 (Homebrew)`, and `runtime.sh` compares the whole line with `PostgreSQL 16.15`. The M5's zerobrew pour of the same formula, at 16.14, prints `PostgreSQL 16.14 (Homebrew)`.
  - ARM Linux: `databases/sqlite` not run, no SQLite 3.50.0 amalgamation. Linux `host-setup` never runs `databases/sqlite/setup.sh`. macOS does.
  - Both Macs: `databases/sqlite` failed `test_every_example_answers_as_written` with `'sqlite3.Connection' object has no attribute 'enable_load_extension'`. The check runs `THINKTHEN_PYTHON`, else `python3`, which is setup-python's 3.12. That macOS build has no loadable SQLite extensions. Homebrew's `python@3.14` is built with them. setup-python's Linux build is configured with `--enable-loadable-sqlite-extensions`, per `actions/python-versions`' Ubuntu builder.
  - ARM Linux: three `tar: stdout: write error` lines at the start of the smoke step. `smoke-bundle` runs `tar -tzf "$duckdb" | grep -Fxq "$needed"` for four member names. `grep -q` exits at its first match. The runner's shell ignores SIGPIPE, so `tar` gets a write error instead of a quiet signal. The fourth name, `./DEPENDENCIES.txt`, is the archive's last member (296 of 296 in the x86 file), so its `tar` had finished before `grep` matched. The step's verdict came from `grep`, so the lines were harmless, and a `tar` failure was hidden the same way.
- Keeps: the probe's `--unshare-user --unshare-pid --unshare-net` arguments, so a broken network sandbox still fails the step; the bubblewrap package pin and owner checks; every image file (the profile goes into the kernel only, with `apparmor_parser --replace`, for this job's virtual machine); every consumer's bwrap arguments; `not run` as a release failure; every surface check's routine and full modes; the amd64 server pin and its Launchpad file; the macOS bottle pins and the Homebrew keg checks; the SQLite tests that the installed-file mode runs; the build jobs' host setup.
- Changes:
  - `sdlc/scripts/release-language-tools.py`: `check_smoke_tools` runs the probe. When it fails and `/proc/sys/kernel/apparmor_restrict_unprivileged_userns` reads `1`, it writes a profile to the job folder that attaches to the pinned bwrap path with `flags=(unconfined) { userns, }`, loads it with `sudo apparmor_parser --replace`, and runs the same probe again. Any other failure, or a second failure, fails the step. The selection record names whether the profile was loaded. This is the form Ubuntu 24.04 ships for each program that needs user namespaces, such as `/etc/apparmor.d/brave`. Coordinator decision, which Ian can overturn: the profile over the per-job alternative `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`. The profile lets only the pinned bwrap make namespaces and leaves the restriction on for every other program in the job. Both last only for the job's virtual machine, and neither removes runner software.
  - `libraries/python/host.sh`, new: one function, sourced by `check.sh` and `host-setup`, that prints the Python the check runs. `host-setup` seeds uv's cache for that Python in place of `python3.12`.
  - `databases/postgresql/runtime.sha256` and `runtime.url` gain the arm64 package (`postgresql-16_16.15-0ubuntu0.24.04.1_arm64.deb`, SHA256 `177e88b1…56479`, from Launchpad's published file metadata, which also gives the existing amd64 pin). `runtime.sh` picks the line for the machine's CPU. New `databases/postgresql/setup.sh` fetches the pinned package for this CPU into the toolchain folder and checks its SHA256. `runtime.sh`'s "not run" hint names it.
  - `runtime.sh`: on Linux, the installed-file mode skips the cargo-pgrx check and the header check, which guard a build. On macOS, the version check accepts the bottle's `PostgreSQL 16.15 (Homebrew)`.
  - `sdlc/scripts/release-workflow host-setup`, smoke only: Linux also runs `databases/sqlite/setup.sh` and `databases/postgresql/setup.sh`. macOS installs `python@3.14`, checks that its `sqlite3` can enable extension loading, and hands it to later steps as `THINKTHEN_PYTHON` through `GITHUB_ENV`.
  - `release-workflow smoke-bundle`: lists the DuckDB archive once into a variable and matches each member name with `case`. A failed `tar` now fails the step.
  - The `workflows` self-test's host-setup table and `release-language-tools-self-test.py` follow the changes.
