## Outcome

DuckDB accepts a complete `choose`, `score` or `tag` question as inline JSON or `@file` in a new two-argument SQL form: `thinkthen_choose(question, text)`, `thinkthen_score(question, text)` and `thinkthen_tag(question, text)`. The saved question supplies its ordered options, levels or labels, descriptions, threshold, model and calibration profile. The result keeps the verb's existing SQL type. The current three-argument `question, text, list` forms, including their deadline and context extensions, keep their current interpretation and request identity.

## SQL and parsing contract

| Call | Interpretation | Result or refusal |
| --- | --- | --- |
| `thinkthen_choose('{"choose":"Which?","options":["a","b"]}', text)` | Complete typed question | `VARCHAR` choice or typed SQL NULL for an unsure choice. |
| `thinkthen_score('@score.json', text)` | Complete file question under the calling `ClientContext` | `DOUBLE` score. |
| `thinkthen_tag('@tag.json', text)` | Complete file question under the calling `ClientContext` | `VARCHAR[]` tags. |
| Any existing `(plain question, text, VARCHAR[] members)` call | Original list-built question, including empty, NULL and null-child behavior | Existing result and request bytes; `@file` or JSON with the list remains Usage. |
| Complete form with plain text, invalid inline JSON, or a valid question of another verb | No implicit options or coercion | Usage; zero sends. A wrong verb is Usage even when the question came from a valid file. |
| Complete form with unreadable, malformed, oversized or non-UTF-8 file | Caller-local input failed | Local; zero sends. A parser error does not repeat file-supplied keys or payload bytes. |
| Complete form with NULL question or NULL text | No question to ask | Typed SQL NULL of the verb's result type; zero sends. |

The two-argument form takes only JSON text starting with `{` or a named `@file`; plain text has no member list to supply and is Usage. `Question::from_json` is the single parser. It already refuses a library question whose `on` selects part of a record; this SQL form passes each entire text as evidence. It rejects `LoadedQuestion::Banded` and every nonmatching `QuestionKind` before send. Parsing validates complete ordered lists and metadata; no JSON-to-list conversion, description loss or question reconstruction is allowed. A saved `batch` setting follows the existing public engine selection rule for this one-document call. The configured DuckDB model/profile remain defaults or run settings where the saved question allows them; the public engine resolves the effective model and profile, so the new route must not replace them with a list-built question. The body and `question_sha256` are compared with independently fixed canonical bytes during proof.

The existing `cpp/src/scalar_owner.cpp::ResolveQuestion` reads through `FileSystem::GetFileSystem(context)` in 64 KiB blocks. It accepts at most 1 MiB of content and rejects a larger file after appending the block that crosses the limit. A rejected stream can therefore reach 1 MiB plus 64 KiB of accumulated content before refusal; the existing `/dev/zero` case proves refusal, not a one-byte-over read limit. It then checks UTF-8. `StatementOwner::Resolve` caches a named file only until `QueryEnd`; the next statement reopens it under that caller's current directory and permissions. Bind-time validation of a foldable file cannot authorize a later execution or freeze its bytes across statements. The new execution branch must resolve and validate the whole non-NULL chunk before its first live send, as the current scalar and listed branches do. It must use `Settings(*context)`, `StatementOwner::Remaining`, `StopFor(*context)` and the bridge's existing `engines::options_for`; the `thinkthen_query_budget_ms` setting and interruption therefore still apply. It adds no per-call deadline or context argument. An optional three-argument complete form with a `BIGINT` deadline would compete with the legacy `VARCHAR[]` form when SQL supplies untyped `NULL` as argument three. Keeping just the disjoint two-argument arity preserves existing overload resolution and typed NULL behavior. A later explicit overload needs its own host-resolution proof.

The file-origin parser boundary maps malformed file content to a fixed, useful Local category without forwarding `error.detail().message()`: a foreign key can contain file-supplied secret bytes. Inline JSON parser failures remain Usage under the existing SQL prefix. Existing `ResolveQuestion` path diagnostics identify the named local file; they must not add file contents, evidence, URL, API key or parser key. Wrong-kind refusal is a fixed Usage category. Runtime settings and backend failures retain their existing mapping, actual attempt accounting and retryability; this ticket does not convert a paid or cancelled call into a local validation error.

## Implementation boundary

`cpp/src/thinkthen.cpp::BindDecide` currently reads `arguments[2]` for every listed verb and `Listed` reads `args.data[2]`. Registering a two-argument overload without a separate mode would be out of bounds. Record a complete-question mode in `ScalarBind` and its `Copy`/`Equals`, branch bind validation on that mode, and dispatch to a complete executor. Keep the original list callback and its three-, four- and five-argument registration unchanged. The new executor can live in a coherent private `cpp/src/listed_complete.cpp` and header because `thinkthen.cpp` is already 417 nonblank lines against the 500-line cap; add it to `cpp/CMakeLists.txt`. Reuse `StatementOwner`, `ResolvedQuestion`, `Settings`, `StopFor`, `RustReply`, `Checked` and `DecodeListed` rather than copying the file reader or result decoder. C++ grouping must preserve first-seen texts and row mapping, validate each distinct question before sending, and carry `from_file` across the new bridge call.

The Rust bridge needs a new complete-question validation/group export in `bridge/src/ffi.rs`, `cpp/src/bridge.hpp` and a coherent private child. The final child is `bridge/src/ffi/complete_listed/ffi.rs`: binding policy requires unsafe exports in a file named `ffi.rs`, while the parent is already 494 nonblank lines. That child parses `Question::from_json`, applies origin-aware safe categories and kind validation, passes the original `Question` to `Engine::details_many_with`, then encodes `Judgment::Choice`, `Score` or `Tags` in the existing listed codec. It preserves `Choice(None)` as codec tag 0 and refuses an impossible judgment kind as Defect. It reuses `asked`, `batch`, `engines::engine_for`, `engines::options_for`, `run_detached` and the existing call-error conversion. The original `bridge/src/ffi/listed.rs::set` and list route remain intact. `tools/verbs_suite.py` registers a focused private `tools/verbs_complete.py` test child. `cpp/src/scalar_owner.{cpp,hpp}` and `cpp/src/listed_result.{cpp,hpp}` are reused without edits. The public engine, question grammar and SQL result schema need no edit.

After design acceptance, coordinate concise DuckDB README wording with the documentation owner: “With two arguments, choose, score and tag accept a complete JSON question or `@file`; with a third `VARCHAR[]`, they keep the plain-question/list form. Files use the calling database session's access settings.” Do not overwrite the current public page during this notes-only pass.

## What the build taught us

The two-argument mode must be copied with `ScalarBind`: adding only SQL registration would have read a nonexistent member argument at bind. The new executor reuses the caller's `StatementOwner`, file resolution and listed result decoder while leaving the original list construction intact. The complete path needs the public detail call because the set builder would reject a saved model or profile. A file-origin parse error can contain a synthetic file-supplied key, so the new bridge maps it to a fixed Local category before it reaches SQL. The installed Linux proof observed all three described request bodies, exact independent question digests, typed results, zero-send refusals, a later prepared permission denial and a spent statement budget. The first loopback backend binary was older than the current capture arm and reported an empty capture despite three counted sends; rebuilding the unchanged conformance-backend source in this lane restored the real captured-body proof. Shared binding policy then caught unsafe exports in a private file not named `ffi.rs`; placing the coherent child at `ffi/complete_listed/ffi.rs` kept that boundary explicit and passed policy without a new exception. Source/file caps required a coherent Rust child, C++ executor and Python proof child. The build record gives measured growth, duplication checked and exact package hashes. Other targets have not run this changed package.
