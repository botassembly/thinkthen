# 0222: Batch DuckDB record vectors and warm groups

Status: B13c technical design accepted at `e103c36f`; Ian approved all ten implementation choices, including the public recoverable Rust carrier, in the work plan. Owner: Codex. Linux x86-64 implementation and selected installed-package proof are complete and accepted by fresh High code review at `e7d57bc0`; no other-platform completion is claimed. The [preflight](../records/0222-duckdb-batching-preflight.md) preserves its historical source audit. Rust 0212, dynamic details 0230 and offline 0216 are now on main.

## Accepted outcome and retained behavior

Build B13c under the [accepted batching issue](../issues/2026-09-26-batching-design.md) and ADRs [0048](../planning/adr/0048-records-batch-into-full-requests.md), [0051](../planning/adr/0051-every-address-has-a-ceiling-and-a-refused-batch-halves-once.md), [0053](../planning/adr/0053-the-pause-fires-in-every-mode-and-batches-have-a-member-cap.md), [0055](../planning/adr/0055-decide-filter-and-rank-batches-send-each-record-once.md) and [0087](../planning/adr/0087-a-shared-context-stops-at-the-record-that-overflows.md). Accepted [ADR 0094](../planning/adr/0094-recoverable-batch-outcomes.md) defines the cross-crate recoverable carrier for review. Default `max` fills requests from compatible rows in one DuckDB vector or one warm aggregate group. `SET thinkthen_batch = 1` restores each distinct record's old no-context body and digest. A final literal context text sends once per request, changes request identity and stays out of question identity. The caller-session settings, typed/environment/question/default precedence, calibration warning and SQL process usage rules stay with B0 and their owners. No SQL per-call facts are added.

Preserve DuckDB's native result types and row positions: decide `BOOLEAN` with `NULL` unsure, probability and score `DOUBLE`, choose `VARCHAR`, tag `LIST<VARCHAR>`, details/try-details/annotate JSON `VARCHAR`, and warm `BIGINT` distinct count. Current vector adapters group compatible rows and deduplicate repeated texts in first-seen order; `NULL` input rows return `NULL` and send nothing. `thinkthen_try_details` converts recoverable per-row Usage, Local or Backend failure to a safe failed JSON value and continues later rows; Cancelled, Deadline and Defect remain fatal. Keep bound-question and member validation, one-question warm refusal, `@file` reads and folder probes through the caller database, read-only file controls, 16-plan engine registry, same-session warm/scalar cache parity, signal/cancellation worker and C++ reply ownership. `thinkthen_recognize`, `thinkthen_relations` and table-valued `thinkthen_relate` keep their separate operation contracts. Annotate-over-records follows B10/0216's separate named-`on` outcome; no B13c claim silently settles its pending metadata choice.

## Proposed Linux C++ boundary

1. Register `SET thinkthen_batch = 'max'` or a positive decimal member cap in the existing caller-session extension settings. Unset or `RESET` falls back to `THINKTHEN_BATCH`, then a loaded question's batch, then `max`; reject zero, signs, fractions and other text before transport. The SQL setting is the accepted environment tier, not a per-row typed value. Add it to `SessionSettings`, the C++/Rust settings ABI and the engine key or per-call options as final B12a requires. Sample the executing session, including warm finalization; never resolve a key, address or file from SQL. Keep staged 0149/0157 throttle, positive request size, retries, profile, cache, record, replay and total domains. No engine plan may reuse a stale batch value.
2. Keep every old registration. Add final `context VARCHAR` to `thinkthen_decide`, `thinkthen_probability`, `thinkthen_details`, `thinkthen_try_details` as `(question VARCHAR, text VARCHAR, deadline BIGINT, context VARCHAR)`; to `thinkthen_choose`, `thinkthen_score`, `thinkthen_tag` as `(question VARCHAR, text VARCHAR, members LIST<VARCHAR>, deadline BIGINT, context VARCHAR)`; and to aggregate `thinkthen_warm` as `(question VARCHAR, text VARCHAR, context VARCHAR)`. The caller uses deadline `-1` when selecting context without a time limit. Do not add a same-arity `(question,text,context)` scalar: it would compete with the existing deadline overload for untyped `NULL` and risk changing current SQL. `NULL` context means absent identity; non-NULL blank context is Usage before a send. For other arguments, preserve each old `NULL` rule, especially try-details' optional `NULL` deadline and failed-value contract. Context is literal UTF-8 text, never an `@file` lookup. A context-bearing singleton uses B0's quoted-record form rather than the old bare request. `annotate` and document/relation operations remain under their separate contracts.
3. In one scalar `DataChunk`, keep first-seen compatible groups, duplicate-to-original-slot mapping and pre-send validation for ordinary verbs. A group key includes resolved question or exact question text, complete ordered member list where present, per-row deadline and context. Ordinary foldable question/member validation at bind and row-dependent validation at execution retain prepared-query behavior; **exempt `thinkthen_try_details` from ordinary bind-time question validation**, as current `BindDecide` does. Even an invalid foldable prepared question must produce a failed JSON row beside a good answer. Do not freeze session settings at prepare. The pure core planner receives first-seen distinct records from each group, fills by fully encoded bytes/profile ceiling, content cuts and member cap, then closes at that vector's edge (at most 2,048 input rows). One eligible 413 or named `max_tokens_exceeded` halves once; retries and halves use their actual request digests. Reassemble typed outputs in DuckDB row order only after the group's answer is decoded; input/output order does not imply which concurrent request arrives first. `details` must obtain full per-row detail from B12a's bounded observation or typed result without a second model call. Its member constructor must preserve the saved question's calibration profile, runtime profile warning and profile-aware digest from the landed shared writer. Listed choose/score/tag retain their complete option order and typed list/float/text codec.

   `try_details` also participates in the accepted `max` vector outcome. Proposed ADR 0094 names the reachable boundary: a reviewed, doc-hidden **public** `thinkthen::Engine::details_many_recoverable_with` returns `Call<Vec<RecoverableDetails>>` to the separate DuckDB bridge crate. Inside `thinkthen`, its private adapter reuses `core::Batcher`, a **to-be-implemented** shared `facade::Engine::ask_record_batch_with_one_split` around the current single-send `ask_batch`, and `workers::ordered`. Only recoverable Usage, Local or Backend request errors travel inside the worker's successful envelope. Fatal Cancelled (including interruption), Deadline and Defect return outer `Err` as soon as that worker finishes, halting further admission even if an older request remains held; already in-flight work joins and ordered delivery remains. This is a real Rust surface addition, not access to private core from the bridge; the paired native `thinkthen_cpp_try_details_group` C ABI frames one JSON value per input slot. Hold at most one DuckDB vector (2,048 rows) plus the bounded worker window. Preserve duplicate-to-logical-outcome mapping: a partially answered **one** packed reply can yield answered, safe failed, answered SQL slots, while a later independent request still answers. A recoverable whole-request Usage, Local or Backend error fails that request's members only; a bad question or file row fails its own slot before packing. Never re-ask members to isolate a failure. Fatal Cancelled, Deadline or Defect aborts and joins the vector. Keep first-seen identity, size/member limits, one eligible 413/`max_tokens_exceeded` split using `halves_with_questions`, actual attempts and output order. B12a must supply and prove that shared split-aware private adapter before B13c uses it; if its final build does not, B13c implements it under fresh exact claims. The adapter takes a private `after_left(&Batch, &Result<Answered, Error>) -> SplitDecision` callback **before** sending right. B12a returns `Stop` for a failed left request or any failed logical left member, keeping its valid ordered prefix and leaving right unsent under ADR 0051. Native `try_details` returns `SendRight` for recoverable left request/member failures and maps those left slots to safe failed JSON; fatal kinds bypass the callback and halt both callers. ADR 0094 walks original, left and right outcomes separately. Only attempts actually begun enter facts; the original refusal and both halves count when all three send, with no member-isolation resend. The accepted B12a `Batch<T>` remains a stopping stream; the new eager native carrier owns final call facts without unbounded history. If the carrier is staged later, B13c remains unfinished. Annotate's separate B10 route remains outside this vector claim.
4. Warm currently stores a sorted `std::set` of unique texts and accepts one question per aggregate group. Replace the order source with first-seen distinct texts and a lookup index; keep the one-question refusal, merge semantics, `NULL` skipping, cache fill and distinct count. With a context argument, distinctness is `(question, context, text)`: different contexts form separate first-seen internal plans without relaxing one question per SQL aggregate group. Keep memory owned by the aggregate until finalization and freed by its destructor. DuckDB's `memory_limit` remains its existing aggregate memory bound; do not invent a fixed row cap. Parallel aggregate combination and vector delivery can change visit order; exact replay requires a fixed input order and `SET threads = 1` where applicable. The warm caller session supplies settings, file permission and `StatementOwner` query budget at finalization. A failed aggregate returns no completed count through `fetchall()`, though earlier requests/cache writes may survive.
5. `StatementOwner::QueryBegin` establishes one absolute `thinkthen_query_budget_ms` expiry for the statement; later vectors and warm finalizations use its remaining time. At warm `Finish`, call `StatementOwner::Remaining` on the executing caller context before transport, then add a signed remaining-milliseconds argument (`-1` means no query budget) to the paired `thinkthen_cpp_warm` declarations in `cpp/src/bridge.hpp` and `bridge/src/warm/ffi.rs`. Pass it to `engines::options` for the entire warm plan instead of today's hardcoded `-1`; zero/expired time returns the existing Deadline error before any send. A scalar's optional deadline belongs to its own vector/group invocation and must not restart for each internal packed request. Preserve held-send cancellation through `run_detached` and the caller's `StopFor`. Remove `engines::within_total`'s pre-send row truncation from newly packed paths: a row is not an attempt. The landed 0149 `SendBudget` reserves at the actual transport boundary for first sends, failed sends, retries and 413 halves, across sessions and engine plans; cache/replay hits consume none. `thinkthen_max_requests_total = 0` still refuses before a send. An internal denial maps to the existing spent-total Usage sentence. Earlier DuckDB chunks may have reached a streaming consumer before a later chunk errors, so the proof speaks only about the one evaluated vector or aggregate, not a transactional rollback of prior output or sends.

## What the build taught us

The first Linux package compiled but failed stock 1.5.5 initialization because DuckDB cannot alter a previously registered aggregate when the three-input warm overload arrives. Registering both warm arities in one `AggregateFunctionSet` fixed installed load; the corrected package also passed stock 1.5.4 and changed-footer refusal. Focused installed cases proved mixed good/failed/good `try_details` members, prepared invalid-row recovery, first-seen warm context order, a zero-budget no-send, and five shared conformance IDs. The intermediate exact context and batch-one witness exposed a scalar detail seam: `details_many_with` is a record API and writes `input` into SQL scalar JSON. Its request bodies and profile/batch metadata were correct; the scalar JSON assertion remains red until the existing writer's optional-input path can be retained on `Details`. That requires an exact claim on `public/results.rs`; the [build record](../records/0222-duckdb-batching-build.md) pins this artifact and each pass/failure. No other platform result follows from this Linux package.

Main `32e544a7` granted the missing file. The scalar correction retains a second view from the existing writer at member construction, so record consumers keep full `input` while SQL sees no `input`; the bridge reads that view without JSON field surgery. The intermediate installed package also exposed DuckDB default NULL propagation around `try_details`' optional NULL deadline and older tests that treated every row as an attempt. Special null handling for this one function and explicit batch-one baselines keep those contracts separate from the new packed total-one proof. The final Linux x86-64 package passed the selected 12 verbs, two settings and five conformance cases, stock 1.5.5 load, old-version/footer refusals and held/late signal boundaries. A bounded Rust worker witness also proves fatal second-result admission stops before a third request. The [build record](../records/0222-duckdb-batching-build.md) pins hashes, invocation, counts and historical red artifacts. Fresh High review subsequently accepted `e7d57bc0`; the other platform builds remain open.

The first fresh High review found one missed host-validation boundary: C++ rejected blank literal context before `try_details` could create a recoverable row, so a mixed vector raised an exception and lost good siblings. The correction lets only `try_details` carry that context to canonical Rust validation and returns its recoverable Usage error through the existing safe row path. A bounded installed case now pins good/failed/good/NULL, one exact good-row request, the safe fixed message, no private evidence, and the unchanged ordinary scalar throw. The first version of that case failed against the `b8106d51` package with the reviewer's exception; the corrected `8546ad51` package passed it and seven adjacent installed cases. The [build record](../records/0222-duckdb-batching-build.md) pins that package's exact hashes. This lesson applies to every validation performed before grouping: `try_details` must convert recoverable row errors before C++ can abort the vector.

The follow-up High review found that the broad outer Usage catch also swallowed tagged send-budget denials. A new installed total-one `try_details` case first observed four completed safe Usage rows after one real send; it now requires the exact spent-total exception, one send and no completed vector, sharing the ordinary packed case's exact body set. The bridge checks `send_budget_denial()` before converting recoverable kinds, so first-send and retry denials remain fatal even though their public kind is Usage. Cancellation, deadline and defect remain fatal by kind; a selected zero-deadline `try_details` call returned a fatal deadline with no send. Returning safe row values must preserve typed fatal metadata; a broad kind-only catch loses it. The corrected `0541e6b0` package passed four affected installed verbs and the held/late signal boundary. The same High reviewer accepted final candidate `e7d57bc0` and independently passed the three affected installed try-details cases. Its exact hashes and review are in the build record.

The following is the historical design preparation. DuckDB differs from both earlier SQL briefs: normal vectors already deduplicate but their Rust bridge still sends per text, while warm sorts distinct evidence and receives session settings only at finalization. The first review exposed three preparation misses: B12a's stopping stream cannot by itself preserve packed `try_details` failed/good siblings; warm has no remaining-budget bridge despite owning a statement timer; and two source verifiers named as proof are not run by `check.sh`. The first correction still placed a private carrier beyond the reach of the separate bridge crate and tested only whole-request failures. Proposed ADR 0094 now pins the public Rust/native C boundary, per-member reply mapping, and installed-artifact selected-suite routing; the paired warm ABI stays explicit. The latest boundary review found two further source mistakes: wrapping fatal worker errors delays admission halt, and `ask_batch` sends once while the CLI owns the one-time split. The correction makes the fatal outer-error path and shared split-aware prerequisite explicit. The final technical review then caught a shared-helper policy miss: ADR 0051 stops before the right half on a failed left, while native `try_details` must continue after recoverable left failures. The private `after_left` decision now separates those callers before transport, with request/member and facts cases for each. The same independent reviewer accepted this technical design at `e103c36f`; that acceptance confirms the boundary and proof proposal, not Ian's public-shape choice or a runtime result. Main `5261cb93` also changed `Details::of` to preserve a saved calibration profile and shared writer digest; the member constructor must follow that current source. The old row-cut helper and several listener assertions encode one row per attempt. The implementation review should compare this inventory with actual source and measure whether the proposed carrier avoids duplicated planner work. No product result is inferred from the staged Linux package or the pending B12a API.
