# 0222: Batch DuckDB record vectors and warm groups

Status: B13c design proposed for independent review. Owner: Codex. No runtime, installed-package or other-platform completion is claimed. The [preflight](../records/0222-duckdb-batching-preflight.md) pins executable main `e99da4a1`, accepted unbuilt Rust B12a `14cbd4b5` and the staged 0201/0149/0157 platform split.

## Accepted outcome and retained behavior

Build B13c under the [accepted batching issue](../issues/2026-09-26-batching-design.md) and ADRs [0048](../planning/adr/0048-records-batch-into-full-requests.md), [0051](../planning/adr/0051-every-address-has-a-ceiling-and-a-refused-batch-halves-once.md), [0053](../planning/adr/0053-the-pause-fires-in-every-mode-and-batches-have-a-member-cap.md), [0055](../planning/adr/0055-decide-filter-and-rank-batches-send-each-record-once.md) and [0087](../planning/adr/0087-a-shared-context-stops-at-the-record-that-overflows.md). Default `max` fills requests from compatible rows in one DuckDB vector or one warm aggregate group. `SET thinkthen_batch = 1` restores each distinct record's old no-context body and digest. A final literal context text sends once per request, changes request identity and stays out of question identity. The caller-session settings, typed/environment/question/default precedence, calibration warning and SQL process usage rules stay with B0 and their owners. No SQL per-call facts are added.

Preserve DuckDB's native result types and row positions: decide `BOOLEAN` with `NULL` unsure, probability and score `DOUBLE`, choose `VARCHAR`, tag `LIST<VARCHAR>`, details/try-details/annotate JSON `VARCHAR`, and warm `BIGINT` distinct count. Current vector adapters group compatible rows and deduplicate repeated texts in first-seen order; `NULL` input rows return `NULL` and send nothing. `thinkthen_try_details` converts recoverable per-row Usage, Local or Backend failure to a safe failed JSON value and continues later rows; Cancelled, Deadline and Defect remain fatal. Keep bound-question and member validation, one-question warm refusal, `@file` reads and folder probes through the caller database, read-only file controls, 16-plan engine registry, same-session warm/scalar cache parity, signal/cancellation worker and C++ reply ownership. `thinkthen_recognize`, `thinkthen_relations` and table-valued `thinkthen_relate` keep their separate operation contracts. Annotate-over-records follows B10/0216's separate named-`on` outcome; no B13c claim silently settles its pending metadata choice.

## Proposed Linux C++ boundary

1. Register `SET thinkthen_batch = 'max'` or a positive decimal member cap in the existing caller-session extension settings. Unset or `RESET` falls back to `THINKTHEN_BATCH`, then a loaded question's batch, then `max`; reject zero, signs, fractions and other text before transport. The SQL setting is the accepted environment tier, not a per-row typed value. Add it to `SessionSettings`, the C++/Rust settings ABI and the engine key or per-call options as final B12a requires. Sample the executing session, including warm finalization; never resolve a key, address or file from SQL. Keep staged 0149/0157 throttle, positive request size, retries, profile, cache, record, replay and total domains. No engine plan may reuse a stale batch value.
2. Keep every old registration. Add final `context VARCHAR` to `thinkthen_decide`, `thinkthen_probability`, `thinkthen_details`, `thinkthen_try_details` as `(question VARCHAR, text VARCHAR, deadline BIGINT, context VARCHAR)`; to `thinkthen_choose`, `thinkthen_score`, `thinkthen_tag` as `(question VARCHAR, text VARCHAR, members LIST<VARCHAR>, deadline BIGINT, context VARCHAR)`; and to aggregate `thinkthen_warm` as `(question VARCHAR, text VARCHAR, context VARCHAR)`. The caller uses deadline `-1` when selecting context without a time limit. Do not add a same-arity `(question,text,context)` scalar: it would compete with the existing deadline overload for untyped `NULL` and risk changing current SQL. `NULL` context means absent identity; non-NULL blank context is Usage before a send. For other arguments, preserve each old `NULL` rule, especially try-details' optional `NULL` deadline and failed-value contract. Context is literal UTF-8 text, never an `@file` lookup. A context-bearing singleton uses B0's quoted-record form rather than the old bare request. `annotate` and document/relation operations remain under their separate contracts.
3. In one scalar `DataChunk`, keep first-seen compatible groups, duplicate-to-original-slot mapping and pre-send validation for ordinary verbs. A group key includes resolved question or exact question text, complete ordered member list where present, per-row deadline and context. Ordinary foldable question/member validation at bind and row-dependent validation at execution retain prepared-query behavior; **exempt `thinkthen_try_details` from ordinary bind-time question validation**, as current `BindDecide` does. Even an invalid foldable prepared question must produce a failed JSON row beside a good answer. Do not freeze session settings at prepare. The pure core planner receives first-seen distinct records from each group, fills by fully encoded bytes/profile ceiling, content cuts and member cap, then closes at that vector's edge (at most 2,048 input rows). One eligible 413 or named `max_tokens_exceeded` halves once; retries and halves use their actual request digests. Reassemble typed outputs in DuckDB row order only after the group's answer is decoded; input/output order does not imply which concurrent request arrives first. `details` must obtain full per-row detail from B12a's bounded observation or typed result without a second model call. Listed choose/score/tag retain their complete option order and typed list/float/text codec.

   `try_details` also participates in the accepted `max` vector outcome. Its private native batch carrier holds at most one DuckDB vector of input slots, classified before planning as SQL `NULL`, recoverable safe failed JSON, or eligible record; it owns only the rows and outcomes needed until that vector returns. Map each planned request to its original slots, including deduplicated siblings. Drive the same core planner with a bounded per-planned-request outcome adapter: successful replies supply each member's details; a recoverable Usage, Local or Backend failure supplies safe failed JSON for the affected request's members and does not suppress later independent requests. A bad question or file row fails only its own slot before packing; a failed packed request does not trigger extra model calls to isolate a member. Fatal Cancelled, Deadline or Defect still aborts the vector. Preserve first-seen grouping, size/member limits, one eligible split, retries, attempt accounting and output order. This private carrier needs a per-request outcome seam below B12a's success-only stopping `Batch<T>` stream; it neither changes public `Call<T>` nor retains unbounded history. The extra vector-sized result frame is the cost of keeping both maximal packing and row-isolated recoverable values. If the needed internal scheduler seam is absent when B12a lands, stage other verbs first and leave `try_details` packing explicitly unfinished: B13c is not complete until the carrier and its outside-in proof pass. Annotate's separate B10 route remains outside this vector claim.
4. Warm currently stores a sorted `std::set` of unique texts and accepts one question per aggregate group. Replace the order source with first-seen distinct texts and a lookup index; keep the one-question refusal, merge semantics, `NULL` skipping, cache fill and distinct count. With a context argument, distinctness is `(question, context, text)`: different contexts form separate first-seen internal plans without relaxing one question per SQL aggregate group. Keep memory owned by the aggregate until finalization and freed by its destructor. DuckDB's `memory_limit` remains its existing aggregate memory bound; do not invent a fixed row cap. Parallel aggregate combination and vector delivery can change visit order; exact replay requires a fixed input order and `SET threads = 1` where applicable. The warm caller session supplies settings, file permission and `StatementOwner` query budget at finalization. A failed aggregate returns no completed count through `fetchall()`, though earlier requests/cache writes may survive.
5. `StatementOwner::QueryBegin` establishes one absolute `thinkthen_query_budget_ms` expiry for the statement; later vectors and warm finalizations use its remaining time. At warm `Finish`, call `StatementOwner::Remaining` on the executing caller context before transport, then add a signed remaining-milliseconds argument (`-1` means no query budget) to the paired `thinkthen_cpp_warm` declarations in `cpp/src/bridge.hpp` and `bridge/src/warm/ffi.rs`. Pass it to `engines::options` for the entire warm plan instead of today's hardcoded `-1`; zero/expired time returns the existing Deadline error before any send. A scalar's optional deadline belongs to its own vector/group invocation and must not restart for each internal packed request. Preserve held-send cancellation through `run_detached` and the caller's `StopFor`. Remove `engines::within_total`'s pre-send row truncation from newly packed paths: a row is not an attempt. The landed 0149 `SendBudget` reserves at the actual transport boundary for first sends, failed sends, retries and 413 halves, across sessions and engine plans; cache/replay hits consume none. `thinkthen_max_requests_total = 0` still refuses before a send. An internal denial maps to the existing spent-total Usage sentence. Earlier DuckDB chunks may have reached a streaming consumer before a later chunk errors, so the proof speaks only about the one evaluated vector or aggregate, not a transactional rollback of prior output or sends.

## Small installed-host proof and routing

After B12a lands and exact runtime claims are refreshed, build the changed Linux x86-64 C++ extension and load that artifact into the pinned stock DuckDB v1.5.5 CLI/Python host. Put new assertions in `tools/verbs_suite.py`, `tools/settings_suite.py` and selected `tools/conformance.py` cases, which `check.sh` invokes; reuse `tools/harness.py` and the historical `cpp/verify_decide.py`/`cpp/verify_tables.py` cases as inputs, not as an unrun gate. A selected short vector with duplicates, `NULL`, one listed member-order variant and one context pins independently expected full bodies/digests, native typed values, row order and listener attempts at `batch 1` and default. One warm group pins first-seen rather than sorted body order and cache reuse, including context identity and a mixed-context count. An invoked verbs case prepares an invalid foldable `try_details` question beside a good row, plus a failed packed request followed by an independent good request, proving safe per-row JSON and no extra isolation sends. A forced two-packed-request case with total one first pins both two-member bodies in an unlimited run; the limited run permits either as the sole transport arrival, requires exactly one attempt and the existing spent-total Usage error, with no completed result from that vector or aggregate. Keep an independent 503 denied-retry case and a true cross-vector statement-budget boundary. In the invoked settings suite, set the warm query budget to zero and require the exact Deadline error and zero listener sends; held cancellation remains a separate regression. A single eligible 413 identity can reuse the shared Rust fixture. `SET threads = 1` and fixed input order make byte comparisons meaningful. Verify a prepared statement with bound question/context and changed session setting, one caller-permitted `@file` and one denied folder with zero sends. Use the installed artifact's version/ABI proof; an unchanged old binary cannot prove changed C++ or Rust bridge source. No paid call, stress campaign or all-port gate follows from this design.

Prospective Linux runtime scope: `databases/duckdb/cpp/src/{thinkthen,warm,scalar_settings}.cpp`, their relevant headers and `bridge.hpp`; `databases/duckdb/bridge/src/{ffi,ffi/settings,ffi/scalar/ffi,ffi/listed,warm/ffi}.rs`; `databases/duckdb/src/engines.rs` and the B12a core planner/scheduler adapter needed for bounded per-request outcomes; selected stock-host `tools/{verbs_suite,settings_suite,settings_cases,conformance,signal_suite}.py`, `check.sh` only if selected routing changes, executable examples and `README.md`; shared `conformance/`, `specification/settings.md`, batching issue B13c row and measured ratchets. `cpp/src/thinkthen.cpp` is 408 nonblank lines at main `e99da4a1`, leaving 92 under the 500-file cap; `bridge/src/ffi.rs` is 439, leaving 61. Extract a coherent vector adapter rather than adding registration/grouping logic beyond either cap. The preflight gives the other relevant headroom and old-test dispositions. Shared pages merge second. No runtime file is claimed in this design branch.

Stage Linux x86-64 C++ first because it is the installed path with caller-session warm and settings proof on main. Linux ARM64 and both macOS packages still use the retained C API and lack the 0201/0149/0157 C++ migration; the later three builds must use their migrated C++ source and receive their own ABI/host checks before B13c can claim all-platform completion. This is unfinished in-repo work, not an external blocker. Main's staged 0149/0157 behavior is real for Linux C++; 0203's question-identity work is in progress and must be refreshed at integration. B12a `Call<T>` and many-record batching are accepted design at `14cbd4b5`, not current runtime.

## Evidence

- Starts from: Main `e99da4a1`, accepted batching B0/B13c and ADRs 0048/0051/0053/0055/0087, accepted unbuilt Rust B12a `14cbd4b5`, landed Linux stage of 0201/0149/0157, shared SQL preflight and prior 0217/0219 design lessons.
- Keeps: Caller-session settings and file authority, one-question warm rule, row-to-result types and `NULL`, recoverable try-details values including invalid prepared questions beside good rows, one absolute statement budget, six error kinds, prompt worker cancellation, C++/Rust owned-reply boundary and accurate platform scope.
- Changes: Proposed `thinkthen_batch` setting, record packing including a bounded private `try_details` outcome carrier, first-seen warm order, final context overloads, paired warm deadline ABI and attempt-based total admission for packed calls.
- Proof: Pinned stock-host installed artifact; invoked suite cases for exact full bodies/digests/listener counts at batch `1` and default, recoverable failed/good `try_details` siblings, prepared/session/permission behavior, total-one forced two-request denial, separate retry denial, cross-vector budget and warm zero-budget zero-send.
- Defers: B12a runtime, 0203 integration refresh, three retained C API platform migrations and their host proof, B10 annotate metadata, SQL per-call facts and paid performance results. Any staged `try_details` omission leaves B13c open. Design acceptance alone closes nothing.

## What the build taught us

Design preparation only. DuckDB differs from both earlier SQL briefs: normal vectors already deduplicate but their Rust bridge still sends per text, while warm sorts distinct evidence and receives session settings only at finalization. The first review exposed three preparation misses: B12a's stopping stream cannot by itself preserve packed `try_details` failed/good siblings; warm has no remaining-budget bridge despite owning a statement timer; and two source verifiers named as proof are not run by `check.sh`. The bounded private carrier and paired warm ABI are now explicit proposals, with cases routed to invoked suites. The old row-cut helper and several listener assertions encode one row per attempt. The implementation review should compare this inventory with actual source and measure whether the proposed carrier avoids duplicated planner work. No product result is inferred from the staged Linux package or the pending B12a API.
