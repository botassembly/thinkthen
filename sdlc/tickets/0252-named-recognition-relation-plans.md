## Outcome

A TypeScript or Ruby caller can pass an explicit local file containing the settled version-one recognition or relation plan to the existing public verb. The binding reads and validates it under that process's file authority before sending. The original plan source retains ordered kinds, descriptions, relation reads, thresholds, model and saved profile. The effective model and thresholds affect the public call. Invalid local content produces a safe, non-retryable Local error and zero sends. Ordinary inline options retain their meanings and invalid inline input remains Usage.

## Public spelling and validation

TypeScript accepts `tt.recognize(text, { file: path, signal?, deadlineMs? })` and `tt.relate(entities, { file: path, signal?, deadlineMs? })`, with the same forms on `Engine`. The existing last-object splitter distinguishes call controls from question inputs; `file` is a question input. A file call cannot also name `kinds`, `relations`, `either`, `threshold` or `relationThreshold`, even if one is present with `undefined`. Preserve the current non-file options contract and reject unknown keys as before. The `file` value is a nonempty well-formed JavaScript string without NUL. The Node boundary encodes that value as UTF-8 for an ordinary `File::open`; invalid path type/text is Usage before reading. Bare strings, including `@` prefixes elsewhere, are never reinterpreted as plan paths.

Ruby accepts `engine.recognize(text, file: path, cancel:, deadline:)` and `engine.relate(entities, file: path, cancel:, deadline:)`; module-level verbs retain their existing delegation. Change `relations:` from required to optional on `relate`, but keep the existing missing-relations Usage refusal when `file:` is absent. A file is exclusive with non-nil inline `kinds`, `relations`, `either`, `threshold` and `relation_threshold`; `batch` and `context` retain their current separate call-option rules. An invalid type, blank path, NUL or invalid UTF-8 path is Usage. Follow `ThinkThen.question(file:)`'s normalization: valid UTF-8 bytes from a binary-encoded Ruby string can name a file, but invalid bytes are refused as Usage before Magnus. Neither host expands `~`, searches a configuration directory, caches the file contents across calls or grants authority beyond the calling process.

For both hosts, the native seam opens the path at the call, reads at most 1,048,577 bytes and rejects content beyond 1 MiB. It validates UTF-8 and calls **the appropriate** public `Recognize::from_json` or `Relate::from_json` on the unchanged source. A fixed Local category reports unreadable, too-large, non-UTF-8 or invalid plan content. Do not forward `error.detail().message()` from file-origin parsing: an unknown JSON key can contain private file bytes. The message and any Debug/envelope omit the path, JSON key, file content, evidence, backend URL and credential. The validation result is returned through each host's existing error envelope; both native calls subsequently use the original validated source and existing parser. Inline malformed plans remain Usage. A wrong-verb named file is invalid Local because the file, rather than an inline argument, supplied the verb. File admission precedes any engine send, cache lookup or recording write.

The file must obey existing whole-document restrictions: recognition rejects nonempty `on`; relation rejects fields other than `/name` and `/kind`. A saved `model` affects the effective backend model. The loader retains the saved `profile` in the unchanged source, but current public recognition and relation calls do not expose a plan-wide profile warning or calibrated identity. Their detail digests describe generated stage and pair questions. Thresholds affect which answers survive. Ordered descriptions and relation reads affect generated requests. The host's normal call deadline and cancellation still apply after local validation. An empty or malformed entity set keeps its existing Usage boundary.

## What preparation taught us

The 0244 scalar-file loaders cannot parse a recognition or relation plan, even though both hosts already carry a validated scalar file value. The public core `Recognize::load` and `Relate::load` do parse plans but read without a byte limit and forward parser details into Local messages; they are unsuitable as these host boundaries. The final design must preserve provenance while using `from_json` for grammar, as 0244's unknown-key and Ruby path-encoding findings showed. The original Q5 prose is historical after accepted 0247; it is not a reason to widen this ticket into DuckDB. Host-idiomatic TypeScript options and Ruby keywords can supply the missing plan-file form without changing the settled question grammar or the existing C, R and SQL APIs.
