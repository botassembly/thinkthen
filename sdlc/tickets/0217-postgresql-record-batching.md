# 0217: Batch PostgreSQL records and expose context

Status: COMPLETE.

Opened as: 2026-10-11. for B13d.** Fresh independent High code review accepted `3a73b7e413b1d9ef575e4461cc2b195940fe9229` after the settings documentation correction. The coordinator integrated unchanged PostgreSQL runtime/tests and verified the settings table with a current binary. Installed Linux proof is in the [build record](../records/0217-postgresql-batching-build.md); scalar register 73, SQL per-call facts and broader platform/release proof remain separate.

## Accepted outcome and retained behavior

Build B13d of the [accepted batching issue](../issues/closed/2026-09-26-batching-design.md) under ADRs [0048](../planning/adr/0048-records-batch-into-full-requests.md), [0051](../planning/adr/0051-every-address-has-a-ceiling-and-a-refused-batch-halves-once.md), [0053](../planning/adr/0053-the-pause-fires-in-every-mode-and-batches-have-a-member-cap.md), [0055](../planning/adr/0055-decide-filter-and-rank-batches-send-each-record-once.md), [0087](../planning/adr/0087-a-shared-context-stops-at-the-record-that-overflows.md) and B0. One PostgreSQL array call and one `thinkthen_warm` aggregate group can fill requests from their records. `SET thinkthen.batch = 'max'` is the default spelling and `SET thinkthen.batch = '1'` restores each distinct record's historical request bytes. A final context argument sends one nonblank reference text per request, enters the request digest, and stays out of the question digest. The typed-call, environment/session, question-file, default tiers and calibration warning remain the accepted B0 rule. SQL per-call facts remain deferred; `thinkthen_usage()` retains backend process totals.

Keep the SQL value and error contracts: `thinkthen_decide(question, text)` returns `boolean` or `NULL` for not sure; `thinkthen_decide(question, text[])` returns `(i integer, decided boolean)` for each array slot; `thinkthen_warm(question, text)` returns the count of distinct pairs judged and fills the answer cache. A failed call raises one of the same six kinds and SQLSTATEs. A scalar receives one text and remains one call, so an ordinary `WHERE thinkthen_decide(question, column)` still waits per SQL row. B13d packs explicit arrays and warm groups and adds context to eligible one-text judgments. Those scalar overloads still make one request per SQL row; they do **not** close register 73's scalar throughput or make a million-row scalar scan concurrent. The equivalence page must report that remaining gap after build.

## Accepted PostgreSQL boundary

1. Register `thinkthen.batch` as a user-settable string GUC: unset or empty leaves `EngineBuilder::from_env()`'s environment value, `'max'` selects maximal packing, and a decimal whole number of at least 1 selects a member cap. Reject `0`, signs, fractions and other strings as Usage before a send. The SQL session value overrides the process environment at the same accepted tier; the loaded decide question's `batch` follows it. Do not add a key, address, file path or second context source in SQL. Keep `thinkthen.max_requests`, `thinkthen.max_requests_total`, `thinkthen.deadline_ms`, throttle, profile, cache, record and strict replay with their current owners and domains. A selected question-file batch is calibration identity, not a new question digest.
2. Keep every existing overload and add B0's final context argument to each eligible judgment form. Exact new SQL signatures and retained result types are:

   | New overload | Result |
   | --- | --- |
   | `thinkthen_decide(question text, evidence text, context text)` | `boolean`, including SQL `NULL` for not sure |
   | `thinkthen_decide(question text, evidences text[], context text)` | table `(i integer, decided boolean)` |
   | `thinkthen_probability(question text, evidence text, context text)` | `double precision` |
   | `thinkthen_choose(question text, evidence text, options text[], context text)` | `text` or SQL `NULL` for not sure |
   | `thinkthen_score(question text, evidence text, levels text[], context text)` | `double precision` |
   | `thinkthen_tag(question text, evidence text, labels text[], context text)` | `text[]` |
   | `thinkthen_details(question text, evidence text, context text)` | `jsonb` details |
   | `thinkthen_try_details(question text, evidence text, context text)` | `jsonb` answered/failed envelope, or SQL `NULL` for a `NULL` question/evidence |
   | aggregate `thinkthen_warm(question text, evidence text, context text)` | `bigint` count |

   This is the B0/B13d accepted final-argument reach, not a new setting or a new public choice. `NULL` context means absent context and keeps the corresponding old request identity; non-NULL blank or whitespace-only context is Usage before a send. Context is literal SQL text, never an `@file` name. A non-NULL context makes even a one-text judgment use the accepted quoted record and shared-evidence form, so that request has a new digest and cannot hit the old no-context entry. Reuse the many-record planner with one member and B12a's typed details/borrowed observation where a scalar's probability or JSON detail needs its original output shape; make no second model call. Preserve the existing validation order: ordinary scalars parse their question before returning SQL `NULL` for `NULL` evidence; `thinkthen_try_details` returns SQL `NULL` for a `NULL` question or evidence before settings/file/context validation. A `NULL` options/levels/labels array still means “read members from the question,” and a present empty members array keeps its current Usage refusal. Existing two-argument and three-argument member-array overloads stay byte-compatible when no context is selected. `thinkthen_annotate` uses named `on` evidence and B10's separate grouped contract; `recognize` and relations are document/relation calls, and `thinkthen_usage()` is not a judgment. They gain no context overload in B13d. PostgreSQL has no trailing scalar deadline argument: `thinkthen.deadline_ms` remains a GUC, so context is last without moving another argument.

3. Parse and validate a question and the selected settings on PostgreSQL's backend thread, then own the array values and optional context before a worker starts. A SQL `NULL` evidence element retains its original zero-based `i` and a `NULL` decided value, and consumes no question or send. A `NULL` array or empty array yields zero rows, with the current question/settings validation order and no send. Duplicate non-NULL evidence asks once within that logical call but occupies each original output slot. Preserve **first occurrence** order of distinct evidence; the current array implementation sorts it, which is unsuitable for accepted consecutive-record batch identity. The new packed bodies follow the core planner's content cut, member cap including repeats, exact fully encoded request size, hard profile limit and end-of-call close. A finite PostgreSQL array has no input-pause close. A structured JSON question text stays a historical singleton. A batch of one distinct record without context preserves its exact old body/digest. One eligible 413 or named `max_tokens_exceeded` refusal halves once in member order; other retries repeat the same body. Return ordered `(i, decided)` rows only after the call has completed in the existing materialized table-iterator style. SQL errors abort that result, even when earlier sends filled the cache; do not promise a visible prefix from the current adapter.
4. The warm aggregate keeps its 20,000-input-row and 2 MiB escaped-state caps. It ignores rows whose question or evidence is SQL `NULL`; the third argument, when present, is part of the distinct group key so two different contexts never share an answer. A present blank context refuses before a send. Group by the exact question argument and context, retain first-seen group order and first-seen evidence order, and count each distinct `(question, context, evidence)` once. The PostgreSQL aggregate's input visit order is not a query-order guarantee: callers who need reproducible batch digests give the aggregate an explicit `ORDER BY`. No sort or dedupe by a context-blind pair may silently reorder the batch. Warm still accepts decide and banded-decide questions only, with its existing cache identity, named-file security and errors. A later scalar without that context does not hit a context-bearing warm entry; an ordinary warm/scalar pair retains its current cache hit.
5. Treat one array invocation and one warm aggregate finalization as their respective deadline lifetimes. Capture the backend's `thinkthen.deadline_ms` and validated setting snapshot once for that operation; any internal group or batch has the same absolute due time, not a reset per chunk. Keep `max_requests` admission over the array's distinct records and, for warm, over each distinct question/context group as today; a later warm group may encounter its own refusal after earlier groups have filled cache entries. Keep the native `statement_timeout`/cancel polling on the backend thread and the masked detachable worker. Move no `pgrx` value, borrowed `Array`, memory-context reference or GUC read into that worker; it owns strings and returns owned values, which PostgreSQL materializes after joining or detaching under the current cancellation rule. Bound held work by the existing warm caps or array length, the core 4,096-member planner cap and the process throttle. Do not create one worker per member or an unbounded completed-detail history. `max_requests` keeps its current distinct-record admission meaning for an array and refuses over-limit input before any send; warm's existing row/state caps remain. A request total is **attempts**, not rows: remove the old `remaining sends -> truncate distinct rows` shortcut for batched paths. Reserve each actual live attempt through 0149's `SendBudget` after the final stop check, including retry and refused-whole/half attempts. A spent total yields the existing SQL Usage sentence; a strict replay miss sends nothing and remains Local. Earlier successful sends can leave cache entries before PostgreSQL raises, but the table result and aggregate count do not partially return. The process throttle and total belong to one backend process, not a SQL statement or a connection pool.
6. Reuse B12a's public `EngineBuilder::batch`, `CallOptions::batch/context`, `Batch<T>`, `Call<T>` and borrowed ordered observation contract after **its final source lands**. These names and final per-call facts are accepted design at `14cbd4b5`, not main code. Use the existing pure core planner and one Rust many-record call for each compatible question group; unwrap `Call<T>` at this native boundary without adding SQL per-call facts. After 0157 lands, pass its selected request size through the same engine plan; keep the 96,000-byte default and smaller profile ceiling. Do not infer attempt totals by subtracting process counters or alter 0149's typed budget-denial mapping.

## Proof, scope and routing

The first outside-in listener case uses an array with repeated evidence, one `NULL` slot and a content-cut-free short cohort. It pins exact ordered `(i, decided)` values, full request bodies and recording digests against the same Rust/CLI fixture, and counts **requests** at `batch 1`, `max`, and one shared context. A compact scalar table covers a context-bearing decide, choose, score and tag value, probability and both details shapes while preserving each native type, `NULL` rule and old-form fallback; it needs only the distinct adapter boundaries, not a copy of every scalar conformance case. A separate empty/`NULL` array and malformed batch/context table pins validation and zero sends. Replace `check.sh::the_total_holds_across_rows`'s old four-row/three-send array expectation: with cache disabled, four distinct short records, `thinkthen.batch = '2'`, `max_retries = 0` and `thinkthen.max_requests_total = 1`, exactly one of the two packed requests reaches the listener and the other is denied before transport; the listener sees exactly **one attempt**, and PostgreSQL raises the existing spent-total Usage sentence without returning partial table rows. In a separate unlimited-total run on those same four records, pin both two-member request bodies and digests. In the total-one run, require its sole captured body and digest to equal **either one** of those two pinned requests, with neither singleton nor a second attempt accepted. Input and output order do not fix which request starts transport first. Keep `sql_settings_and_retry_total`'s 503 then denied-retry listener check: one row can consume one attempt without an answer. Retain the existing array deadline/cancel, warm-to-scalar cache and strict replay checks; add one distinct held-reply or short-deadline case proving that a second internal batch cannot restart the statement clock. A replay miss under a changed context counts zero listener requests and preserves Local. One warm case pins first-seen grouping, duplicate suppression, explicit aggregate order and its count; a different context must miss the plain entry. Pin one eligible half identity only if the shared Rust fixture does not already cover it through the host. No timing campaign, full-port gate or paid call belongs to this design.

The runtime claim covers PostgreSQL `src/{lib,call,warm}.rs`, `src/call/settings.rs`, private `src/array.rs` and `src/context.rs`, selected installed tests and helpers, `check.sh`, `examples.json`, `README.md`, the PostgreSQL settings cell and measured PostgreSQL ratchets. Shared Rust and canonical conformance are unchanged. The generated pgrx SQL and ordinary package were checked from the merged source; no site page was edited because ticket 0241 owns shared documentation. Register 73 remains a scalar throughput gap.

## What the build taught us

The design preparation began with this finding. The preliminary SQL map found the existing array and warm entrypoints, but did not inspect `decide_distinct`'s sorting or its assumption that one remaining send equals one remaining record. Both affect batch identity and budget admission. Inspecting the generated pgrx signatures exposed that PostgreSQL has no scalar deadline argument to move, while `thinkthen.deadline_ms` must cover a whole array or warm finalization. The warm state already owns its values under 20,000-row and 2 MiB caps; the new design keeps those bounds and records that SQL aggregate visit order needs an explicit caller order for stable replay. The existing suite proves cancellation, warm cache reuse and the old total, but none proves new packed bodies or a second internal chunk under one deadline. Review of `0328141f` found two preparation misses: B0 already grants the final context argument to eligible singleton judgments, and the old four-row/three-send request-total assertion becomes false when rows pack. The correction inventories all output-preserving overloads and makes the total proof force two packed requests while preserving the separate retry-denial case. Follow-up review found a repeated harness and preparation assumption: ordered SQL output does not imply transport arrival order when batches dispatch concurrently. The total-one proof therefore accepts either independently pinned two-member body as its one actual send, without serializing product dispatch. The build then confirmed that the transport budget, not row truncation, must count packed attempts. It also found that batch one admits interactively: the retained eight-held-request cancellation tests needed batch two to exercise concurrency. Raw recording request text, rather than parsed JSON, is the digest input. PostgreSQL did not run the warm finalizer after the tested blank-context step error. One warm worker across groups preserved the deadline, while packed warm entries remained exact cohort cache entries. The independent High code review remains to assess this candidate before landing.
