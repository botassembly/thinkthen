# 0217: Batch PostgreSQL array and warm records

Status: proposed B13d design for independent review. Owner: Codex. No runtime, installed extension, paid result or register 73 closure is claimed. The [preflight](../records/0217-postgresql-batching-preflight.md) pins main `0da697c3`, accepted but unbuilt B12a `14cbd4b5`, and building 0157 `92eac8ea` separately.

## Accepted outcome and retained behavior

Build B13d of the [accepted batching issue](../issues/2026-09-26-batching-design.md) under ADRs [0048](../planning/adr/0048-records-batch-into-full-requests.md), [0051](../planning/adr/0051-every-address-has-a-ceiling-and-a-refused-batch-halves-once.md), [0053](../planning/adr/0053-the-pause-fires-in-every-mode-and-batches-have-a-member-cap.md), [0055](../planning/adr/0055-decide-filter-and-rank-batches-send-each-record-once.md), [0087](../planning/adr/0087-a-shared-context-stops-at-the-record-that-overflows.md) and B0. One PostgreSQL array call and one `thinkthen_warm` aggregate group can fill requests from their records. `SET thinkthen.batch = 'max'` is the default spelling and `SET thinkthen.batch = '1'` restores each distinct record's historical request bytes. A final context argument sends one nonblank reference text per request, enters the request digest, and stays out of the question digest. The typed-call, environment/session, question-file, default tiers and calibration warning remain the accepted B0 rule. SQL per-call facts remain deferred; `thinkthen_usage()` retains backend process totals.

Keep the SQL value and error contracts: `thinkthen_decide(question, text)` returns `boolean` or `NULL` for not sure; `thinkthen_decide(question, text[])` returns `(i integer, decided boolean)` for each array slot; `thinkthen_warm(question, text)` returns the count of distinct pairs judged and fills the answer cache. A failed call raises one of the same six kinds and SQLSTATEs. A scalar receives one text and remains one call, so an ordinary `WHERE thinkthen_decide(question, column)` still waits per SQL row. B13d improves explicit arrays and warm groups; it does **not** by itself close register 73's scalar throughput or make a million-row scalar scan concurrent. The equivalence page must report that remaining gap after build.

## Proposed PostgreSQL boundary

1. Register `thinkthen.batch` as a user-settable string GUC: unset or empty leaves `EngineBuilder::from_env()`'s environment value, `'max'` selects maximal packing, and a decimal whole number of at least 1 selects a member cap. Reject `0`, signs, fractions and other strings as Usage before a send. The SQL session value overrides the process environment at the same accepted tier; the loaded decide question's `batch` follows it. Do not add a key, address, file path or second context source in SQL. Keep `thinkthen.max_requests`, `thinkthen.max_requests_total`, `thinkthen.deadline_ms`, throttle, profile, cache, record and strict replay with their current owners and domains. A selected question-file batch is calibration identity, not a new question digest.
2. Preserve existing two-argument SQL forms and add only the accepted final context overloads for the B13d multi-record entries: `thinkthen_decide(question text, evidences text[], context text) RETURNS TABLE(i integer, decided boolean)` and `thinkthen_warm(question text, evidence text, context text) RETURNS bigint` as an aggregate. The ordinary array overload remains `thinkthen_decide(question text, evidences text[])`; ordinary warm remains `thinkthen_warm(question text, evidence text)`. `NULL` context means no shared context and retains their old request form; explicitly empty or whitespace-only context is Usage before send. Context is SQL text, not a server file spelling. Existing scalar, choose, score, tag, probability, details, try-details, annotate, recognize and relate signatures stay as they are in this B13d slice. The accepted issue says “a final context argument” but does not enumerate singleton scalar overloads. Adding `thinkthen_decide(question text, evidence text, context text)` would also change one-row request identity; the [review handoff](../records/0217-design-review.md) names that public reach question rather than treating this narrow reading as an Ian ruling. PostgreSQL has no trailing deadline argument: `thinkthen.deadline_ms` remains a session GUC, so these new context arguments are last without moving a native argument.
3. Parse and validate a question and the selected settings on PostgreSQL's backend thread, then own the array values and optional context before a worker starts. A SQL `NULL` evidence element retains its original zero-based `i` and a `NULL` decided value, and consumes no question or send. A `NULL` array or empty array yields zero rows, with the current question/settings validation order and no send. Duplicate non-NULL evidence asks once within that logical call but occupies each original output slot. Preserve **first occurrence** order of distinct evidence; the current array implementation sorts it, which is unsuitable for accepted consecutive-record batch identity. The new packed bodies follow the core planner's content cut, member cap including repeats, exact fully encoded request size, hard profile limit and end-of-call close. A finite PostgreSQL array has no input-pause close. A structured JSON question text stays a historical singleton. A batch of one distinct record without context preserves its exact old body/digest. One eligible 413 or named `max_tokens_exceeded` refusal halves once in member order; other retries repeat the same body. Return ordered `(i, decided)` rows only after the call has completed in the existing materialized table-iterator style. SQL errors abort that result, even when earlier sends filled the cache; do not promise a visible prefix from the current adapter.
4. The warm aggregate keeps its 20,000-input-row and 2 MiB escaped-state caps. It ignores rows whose question or evidence is SQL `NULL`; the third argument, when present, is part of the distinct group key so two different contexts never share an answer. A present blank context refuses before a send. Group by the exact question argument and context, retain first-seen group order and first-seen evidence order, and count each distinct `(question, context, evidence)` once. The PostgreSQL aggregate's input visit order is not a query-order guarantee: callers who need reproducible batch digests give the aggregate an explicit `ORDER BY`. No sort or dedupe by a context-blind pair may silently reorder the batch. Warm still accepts decide and banded-decide questions only, with its existing cache identity, named-file security and errors. A later scalar without that context does not hit a context-bearing warm entry; an ordinary warm/scalar pair retains its current cache hit.
5. Treat one array invocation and one warm aggregate finalization as their respective deadline lifetimes. Capture the backend's `thinkthen.deadline_ms` and validated setting snapshot once for that operation; any internal group or batch has the same absolute due time, not a reset per chunk. Keep `max_requests` admission over the array's distinct records and, for warm, over each distinct question/context group as today; a later warm group may encounter its own refusal after earlier groups have filled cache entries. Keep the native `statement_timeout`/cancel polling on the backend thread and the masked detachable worker. Move no `pgrx` value, borrowed `Array`, memory-context reference or GUC read into that worker; it owns strings and returns owned values, which PostgreSQL materializes after joining or detaching under the current cancellation rule. Bound held work by the existing warm caps or array length, the core 4,096-member planner cap and the process throttle. Do not create one worker per member or an unbounded completed-detail history. `max_requests` keeps its current distinct-record admission meaning for an array and refuses over-limit input before any send; warm's existing row/state caps remain. A request total is **attempts**, not rows: remove the old `remaining sends -> truncate distinct rows` shortcut for batched paths. Reserve each actual live attempt through 0149's `SendBudget` after the final stop check, including retry and refused-whole/half attempts. A spent total yields the existing SQL Usage sentence; a strict replay miss sends nothing and remains Local. Earlier successful sends can leave cache entries before PostgreSQL raises, but the table result and aggregate count do not partially return. The process throttle and total belong to one backend process, not a SQL statement or a connection pool.
6. Reuse B12a's public `EngineBuilder::batch`, `CallOptions::batch/context`, `Batch<T>`, `Call<T>` and borrowed ordered observation contract after **its final source lands**. These names and final per-call facts are accepted design at `14cbd4b5`, not main code. Use the existing pure core planner and one Rust many-record call for each compatible question group; unwrap `Call<T>` at this native boundary without adding SQL per-call facts. After 0157 lands, pass its selected request size through the same engine plan; keep the 96,000-byte default and smaller profile ceiling. Do not infer attempt totals by subtracting process counters or alter 0149's typed budget-denial mapping.

## Proof, scope and routing

The first outside-in listener case uses an array with repeated evidence, one `NULL` slot and a content-cut-free short cohort. It pins exact ordered `(i, decided)` values, full request bodies and recording digests against the same Rust/CLI fixture, and counts sends at `batch 1`, `max`, and one shared context. A separate empty/`NULL` array and malformed batch/context table pins validation and zero sends. Reuse the existing array deadline/cancel, warm-to-scalar cache, request-total and strict replay checks; add one distinct held-reply or short-deadline case proving that a second internal batch cannot restart the statement clock. A replay miss under a changed context counts zero listener requests and preserves Local. One warm case pins first-seen grouping, duplicate suppression, explicit aggregate order and its count; a different context must miss the plain entry. Pin one eligible half identity only if the shared Rust fixture does not already cover it through the host. No timing campaign, full-port gate or paid call belongs to this design.

Prospective runtime claim after B12a, 0157 and ownership refresh: `databases/postgresql/src/{lib,call,warm}.rs`, `src/call/settings.rs`, a coherent private child if `lib.rs` needs extraction, `tests/runner.py`, selected `check.sh` cases, the generated SQL registration/package evidence, `examples.json`, `README.md`, shared `conformance/` and `specification/settings.md`, the batching issue's B13d row, and measured `sdlc/ratchet.json`. `files.rs` remains a read-only dependency unless final source shows a need. `src/lib.rs` has only 56 nonblank lines below the 500 cap at main `0da697c3`; plan one private array adapter, not a second planner. Shared pages merge second. No runtime file is claimed by this design branch. Review exact ownership with B12a, 0157 and 0149 before editing.

## Evidence

- Starts from: Main `0da697c3`, local experiment 284 register 73 as a historical finding, accepted batching issue B0/B13d, ADRs 0048/0051/0053/0055/0087, staged 0149, building 0157 `92eac8ea`, and accepted unbuilt B12a/ADR 0089 `14cbd4b5`.
- Keeps: Current PostgreSQL SQL names and types, zero-based array positions and `NULL`, six kinds/SQLSTATEs, banded warm cache parity, named-file authority, one backend process throttle/total, statement interruption and no SQL per-call facts.
- Changes: Proposed `thinkthen.batch` session setting, record packing for array and warm, final context overloads on those multi-record entries, first-seen batch order, and transport-attempt rather than row-count total admission.
- Proof: Existing loopback, array/warm/deadline/replay cases plus one exact body/digest/order/listener table, one context shape and one true cross-chunk deadline boundary; selected PostgreSQL and shared cases after runtime only.
- Defers: Register 73's one-text scalar throughput, other SQL hosts B13c/e, SQL per-call facts, public singleton-context reach decision, B12a and 0157 implementation, installed-package proof and any paid comparison.

## What the build taught us

Design only. The preliminary SQL map found the existing array and warm entrypoints, but did not inspect `decide_distinct`'s sorting or its assumption that one remaining send equals one remaining record. Both affect batch identity and budget admission. Inspecting the generated pgrx signatures exposed that PostgreSQL has no scalar deadline argument to move, while `thinkthen.deadline_ms` must cover a whole array or warm finalization. The warm state already owns its values under 20,000-row and 2 MiB caps; the new design keeps those bounds and records that SQL aggregate visit order needs an explicit caller order for stable replay. The existing suite proves cancellation, warm cache reuse and the old total, but none proves new packed bodies or a second internal chunk under one deadline. Compare these observations with the eventual builder's lessons and independent review before landing.
