# 0111: Port the PostgreSQL surface

Status: landed 2026-09-25 in the surface batch, at batch head `03580733` on `ticket/surface-batch`. Integration record: `sdlc/records/surface-batch-integration.md`. Owner: Claude.

## Outcome and authority

Port the PostgreSQL extension from tag `surfaces-wave7-frozen-2026-09-24b` (`9df8bae9`) onto the public Rust API as the unpublished crate `thinkthen-postgresql` at `databases/postgresql`, in its own Cargo workspace. `CREATE EXTENSION thinkthen` keeps its SQL names: `thinkthen_decide` (scalar and array), `thinkthen_probability`, `thinkthen_choose`, `thinkthen_score`, `thinkthen_tag`, `thinkthen_annotate`, `thinkthen_details`, `thinkthen_usage`, `thinkthen_warm`, `thinkthen_recognize`, `thinkthen_relations`, and `thinkthen_relate`. `WHERE` and `ORDER BY` stay the filter, rank, and find verbs. Every call reaches the real engine through `thinkthen`. Queue item 3 of `sdlc/planning/one-line-plan-2026-09-24.md` lists PostgreSQL among the remaining surfaces.

Draft ADR 0047 (on the 0093 branch until 0093 lands) fixes the crate's place and its checklist. Ticket 0093 sets the workspace, lint, ratchet, and surface-rung pattern. Ticket 0095 fixes the members this binding calls. Section 3.2 of `sdlc/planning/surfaces-port-guide.md` gives the port map, and its "Shared rules" section (main at `bced9c4d`) sets six rules every surface ticket follows. ADR 0043 on main makes this ticket its owner. Accepted ticket 0105 is the template, and ticket 0110 (DuckDB) makes the same relate and deny choices. The 2026-09-24 design review (`sdlc/records/2026-09-24-design-review-0111.md`) found ten items, and this version answers all ten. Ian can overturn every decision below.

## Design and decisions

1. **Shared rules.** This ticket follows the six rules in the port guide's "Shared rules" section. Claude set them on 2026-09-24 from the design reviews of 0105 to 0112, and this ticket records how it meets each.
   - No Docker. The check runs a local PostgreSQL 16.15 from Ubuntu's package (the gate section). The tag's cached-Docker path is dropped.
   - Toolchains outside the answer cache. The package and its extracted tree live under `~/.cache/thinkthen-toolchains/postgresql/`. The product's answer cache stays at ADR 0017's XDG folder or a folder the test names. The fetch is one-time setup with a SHA256 pinned in the repo, and `runtime.sh` refuses a mismatch.
   - Each test gets its own product cache folder and its own loopback backend. The server's environment carries `THINKTHEN_CACHE` and `THINKTHEN_BASE_URL`, so the check restarts the server for each test with a fresh `mktemp` cache folder and that test's backend. One backend per test comes from ticket 0117, and this ticket depends on it. This ticket uses neither 0117's fixed delay nor its held reply that holds again.
   - Ctrl-C is prompt for single calls and batches alike (decision 7).
   - Deny plants reach deny while offline (the gate section).
   - Tests that need parallel requests set the throttle they need through the public `thinkthen.throttle` setting of decision 3. No hidden hook sets it. The rule as corrected on main at `446a4d6b` asks for this. Throttle is process-wide under 0077, and each PostgreSQL backend is its own process. Each test also restarts the server, so no two tests share a throttle.
2. **No C door underneath.** The extension links `thinkthen` by path through pgrx and never links `thinkthen-c` (ADR 0047 item 1). A C hop would add JSON text per call and a second FFI edge. From 0094 it takes only the pattern: one `unsafe` module tree, one error table, and the output-name collision check behind R2-26.
3. **Engine and settings.** Each backend builds one engine on the first call's worker (decision 7) and keeps it for the backend's life. `_PG_init` registers settings and touches no engine. It starts from `EngineBuilder::from_env()`. 0084's amendment at `f19cf437` adds that member. That call reads the key, the address, and the cache folder from `THINKTHEN_API_KEY`, `THINKTHEN_BASE_URL`, and `THINKTHEN_CACHE` exactly as `Engine::from_env` does. The binding then applies each of the four public settings below that is set, and `build()` makes the backend's engine. A setting left at its default calls no setter, so the seed's value stands. `default_engine()` goes unused. The key and the address come from the server's environment alone. ADR 0017 section 5 gives databases "the engine value's setting, then the same variable" for the address. Leaving out an address setting at 0.1 is this ticket's decision, and it answers open question 4 of `postgres.md`. Two reasons: the key setting leaks into `pg_stat_statements` on PostgreSQL 15 to 17 (`postgres.md`), and a failing `SET` writes its value to the server log (decision 12). An address setting would carry any credentials in the address the same way. `thinkthen.api_key` stays registered (`Suset`, hidden) so a stray `SET` has a defined answer. The `SET` succeeds, and the next call refuses (decision 12).
   - Engine settings. ADR 0017 section 5 puts throttle, `max_requests`, `cache`, and `cache_bytes` on the engine value. The shared rule corrected at `446a4d6b` has every surface expose them publicly. The extension registers them in `_PG_init` beside `deadline_ms` and `file_directory`, with PostgreSQL's own range checks and units:
     - `thinkthen.throttle`, integer -1 or 1 to 32, default -1. -1 means unset: the binding calls no setter, and the engine's default throttle of 4 applies (ADR 0017 section 5). This is the owner's decision, 2026-09-24. It follows the port guide's rule that an omitted throttle stays omitted (0077), and it keeps the four settings to one rule. Any other value maps to `EngineBuilder::throttle`, and 0095 keeps the range 1 to 32. PostgreSQL's range check cannot exclude one value, so 0 reaches `throttle(0)`. The builder refuses it as `usage` (0086, R4-12), and every call in that backend refuses with 22023 and sends nothing. Ian can overturn this.
     - `thinkthen.max_requests`, integer -1 to 2,147,483,647, default -1. -1 means unset: the binding calls no setter, and the seed's value stands. `from_env` reads no request limit, so an unset setting means no limit. Any other value N maps to `max_requests(Some(N))`. A call whose input holds more than N records refuses before its first request with 22023, as ADR 0017 describes. So `max_requests = 0` refuses every call that holds one record or more, with 22023 and zero sends. 0084's setter takes `Option<usize>`, and `None` alone means no limit. It states no floor. If 0086 makes the setter refuse `Some(0)`, the first call raises that `usage` refusal as 22023 instead, and it still sends nothing. The README states the 0 case.
     - `thinkthen.cache`, a folder path, empty by default. Empty means unset: the binding calls no setter, and `from_env`'s choice stands (`THINKTHEN_CACHE`, then the configuration file's switch and ADR 0017's XDG folder). A path maps to `cache_at`.
     - `thinkthen.cache_bytes`, an integer with PostgreSQL's byte unit, default -1. -1 means unset: the binding calls no setter, and `from_env` keeps the configuration file's `cache_bytes`, or the ruled 100,000,000 bytes (`DEFAULT_CACHE_BYTES` in `cli/config.rs`). A default of `100MB` would override that file. It would also mean 104,857,600 bytes, because PostgreSQL's `MB` is 1,048,576 bytes. PostgreSQL spells sizes with units (`shared_buffers = '128MB'`), so the setting takes `'500MB'` as well as a bare byte count, and it maps to `cache_bytes`. The binding itself refuses `cache_bytes = 0`. The plan refuses it before `build` with 22023 and the sentence "thinkthen.cache_bytes must be -1 or at least 1", and nothing is sent. Neither 0084 nor 0086 says whether `cache_bytes(0)` is an error, and 0062's rule covers the command's configuration file only. This is the owner's decision, 2026-09-24, and Ian can overturn it. The README states the 0 case. A PostgreSQL integer setting stops at 2,147,483,647, so the ceiling is about 2 GB, and the README says so. Lever: a text setting if a reader needs a larger cache.
   - The 2026-09-24 amendment below replaces this bullet and the restart bullet: the four settings use `Suset`, and a changed plan rebuilds the engine.
   - Their context is `SuBackend`. A superuser sets them in the server's configuration, per role, or at connection start. Nobody changes them once the session runs, so the engine a backend built never disagrees with what `SHOW` prints. Superuser only, because the four move spend and the folder the server writes. The tag's `Suset` settings follow the same privilege rule.
   - `max_requests` is superuser-only at 0.1. An ordinary role therefore cannot tighten its own spend guard. `ALTER ROLE … SET` gives an administrator a limit per role. A later option lets users only lower it: a user-settable value that the binding checks per call against the superuser's limit. Ian can overturn this.
   - Restart. PostgreSQL ignores a `SuBackend` value that `pg_reload_conf()` changes after a library loaded lazily. The README tells an administrator that a changed setting needs a server restart, unless `shared_preload_libraries` preloads the library. The tests restart the server for each test, so they are unaffected.
   - The throttle test. With `thinkthen.throttle = 8` in the server's configuration, a held 64-row array batch holds 8 counted sends. Plant: ignore the setting. The count reads the engine's default of 4. A `max_requests = 3` test refuses a 4-row array batch with zero counted sends. A `thinkthen.cache` test warms two pairs and finds entries in that folder and none in `THINKTHEN_CACHE`. A `max_requests = 0` test refuses a scalar decide with 22023 and zero counted sends. A unit test checks that `cache_bytes = '1MB'` reaches the builder as 1,048,576 bytes. A throttle test also proves the environment survives the setters: with `thinkthen.throttle = 8` and `THINKTHEN_BASE_URL` at the test's loopback backend, a decide answers and the backend counts exactly one send. Change 15 replaces that test's plant.
   - The unset test. The binding turns the four raw values into a small plan of setter calls, and one function applies the plan to the seeded builder. The apply function is generic over a four-method setter trait, and the binding implements that trait for `EngineBuilder`. A Rust unit test feeds the plan the four registered defaults. `_PG_init` and the test read the same default constants. The plan holds no setter call. The test then applies that empty plan to a counting stand-in for the builder, and the stand-in counts zero calls. A plan with all four set counts one call to each setter with its value. Plant: register `cache_bytes` with a default of `100MB` and always apply it. The plan holds `cache_bytes(104857600)`, and the test turns red. A second plant makes the apply function always call `cache_bytes`. The stand-in counts one call for the empty plan, and the test turns red. A second unit test builds the plan with `cache_bytes = 0` and gets the 22023 refusal with its pinned sentence, and the stand-in counts zero calls. Plant: drop the zero check. The plan holds `cache_bytes(0)`, and the test turns red. The test sits at the plan because the public API has no getter for the prune target, and no request prunes (0062). The end-to-end path is the environment-seed test of change 15.
   - The panic probe of R1-10 builds only under the test feature `panic-probe`. It is a function, and it moves no engine setting. A package check proves the shipped tree lacks it.
   - Lever: Ian can drop any of the four settings. The engine then keeps the environment's or the built-in value for it.
4. **Saved answers move to the engine cache.** The per-backend answer map, `thinkthen.saved_answer_kb`, and the binding's hit counter leave. `thinkthen_warm` fills the engine's disk cache at ADR 0017's default folder for the server's operating-system user, or `THINKTHEN_CACHE`. A decide after a warm pass reads that cache and sends nothing, in the same session and in the next. `thinkthen_usage` reads `Counters` alone. Cost: a cached answer costs one file read, a 5.7 µs median by ADR 0017 section 5.
   - Warm cap. One `thinkthen_warm` call takes at most 20,000 rows. The 20,001st refuses with 22023 and the sentence "thinkthen_warm takes at most 20,000 rows per call". The aggregate holds every row's text in backend memory until the finalizer, and the cap bounds that memory and one statement's spend. The tag holds the same cap as `WARM_ROW_CAP`, so its test carries over.
   - Cache size. The engine cache keeps its ruled default of 100,000,000 bytes unless the configuration file or `thinkthen.cache_bytes` sets another. The README tells a reader to raise `thinkthen.cache_bytes` before a warm pass over more than about 25,000 answers. `thinkthen cache prune` frees space in the same folder.
5. **Deadlines.** `thinkthen.deadline_ms` stays `Userset` with the range -1 to 2,147,483,647, so PostgreSQL itself refuses -2. Every call passes it through `CallOptions::deadline_millis` (ADR 0041, ADR 0043). `-1` is none, and `0` returns 57014 with nothing sent. The backend thread also checks the deadline's instant on each tick of decision 7. On a passed deadline it cancels, detaches, and raises `thinkthen deadline` with 57014.
6. **Settings and files are read on the backend thread.** pgrx `GucSetting::get` panics off the backend thread, as the tag's comment at `lib.rs` near line 220 records. So the backend thread reads `deadline_ms`, `file_directory`, the key check, and the four engine settings, reads any named file, and runs every SPI query before the spawn. The worker receives owned values only and never calls into PostgreSQL.
7. **Every call runs on a detachable worker under a full signal mask.** This amends ADR 0043, and the section below gives the amendment's text.
   - Which calls. All of them: `decide` (scalar and array), `probability`, `choose`, `score`, `tag`, `annotate`, `details`, `recognize`, `relations`, the `thinkthen_warm` finalizer, and `thinkthen_relate`. The first engine build in a backend happens inside a worker too.
   - The worker. It owns a clone of the question, the texts as `String` values, and a clone of an internal `CancelToken`. It builds its own `CallOptions` with that token and the deadline. It sends its result over a channel. It ignores a closed channel and never panics on one.
   - The mask. The backend thread blocks every signal with `pthread_sigmask` before the spawn and restores its own mask right after. The worker and every thread the engine spawns from it inherit the full mask. PostgreSQL's handlers therefore run only on the backend thread. This rule covers batches and the first engine build as well as single rows. A test reads the mask of every thread (acceptance, "Signal mask").
   - The wait. The backend thread waits on the channel in 50 ms ticks. A finished call returns at once. On each tick it reads `QueryCancelPending` and `ProcDiePending` with volatile reads in the FFI module and checks the deadline instant. It never runs `check_for_interrupts!` inside the wait, because that jumps across Rust frames. Any other pending interrupt, such as a memory-context request, leaves the wait alone and is serviced after the call.
   - On a cancel. The backend thread cancels the internal token, detaches the worker, and runs `check_for_interrupts!()`. That raises PostgreSQL's own error for a user cancel, a terminate, or a statement timeout. If it returns, the binding raises `thinkthen cancelled` with 57014. A single row and a batch both return within one tick. The engine starts no new send and no retry once the token is cancelled. The detached worker finishes the requests already sent under 0073 and drops the result.
   - Cost. About 60 lines and one thread spawn per call, cache hits included. The record measures a 20,000-row scalar decide over cached answers and stops the ticket above 100 µs a row. The tag's `run_batch` thread and its poll loop leave, and `CallOptions::interrupt` goes unused.
   - Ian can overturn this and keep ADR 0043's deadline-only rule.
8. **Question arguments.** A question, set, or spec is `'@file.json'` or the file grammar's JSON text. Bare text refuses with the tag's sentence naming the `@` form (R2-4). The binding reads a named file itself under the privilege gate, the 1 MiB cap, the regular-file rule, and `open_beneath` confinement. It then calls `Question::from_json`, `QuestionSet::from_json`, `Recognize::from_json`, or `Relate::from_json`. A `Usage` from a file's text maps to `local` (0095). The members array of `choose`, `score`, and `tag` joins the question's JSON object as `options`, `levels`, or `labels` before `from_json`. A question that already carries its members and also gets an array refuses with `usage`. The tag's `with_members` rebuild and its lifting of the `recognize` section leave.
9. **Results.** `decide` returns true, false, or NULL. `probability` reads `Probabilities::YesNo` from `details`. Scalar `choose` and `tag` call `details` and read `value()` with no added send, as 0095 G5 and 0105 decision 8 do. `score` returns the position. `tag` returns `text[]`. Scalar `annotate` returns `AnnotatedRecord::value_json` as `jsonb`, and `details` returns `Details::to_json`. `thinkthen_usage()` returns `requests_sent`, `cache_answers`, `input_tokens`, and `output_tokens`. Tests assert differences around a call (0095). `thinkthen_recognize` returns `(name, kind, start, end, strength)`, main's shape (port guide 4.3), and the `text` column becomes `name`. Offsets count Unicode scalar values. PostgreSQL counts characters the same way in a UTF-8 database. `thinkthen_relations` returns `(relation, source_name, source_kind, target_name, target_kind, probability)`.
10. **Relate from rows.** `thinkthen_relate(query, rules)` reads a query whose columns are id, name, and kind. A two-column query of id and name reads kind `*` and takes only bare rules, as 0110 does. `rules` is a `text[]` of the command's inline rule strings, or `text` holding `'@file.json'` or a version-one relate file. Per ADR 0047 item 9, the binding dedupes rows by name and kind in first-seen order, calls `relate_with` once, and returns one row `(relation, source, target, probability)` per matching id pair. Ids stay `bigint`, as at the tag. SPI reads under `LIMIT 256`, and a 256th row refuses with 22023 naming the cap (R3-12's shape). This row cap is stricter than the unique-pair cap of ADR 0047 item 9 and 0095 Q14, and the README says so. It counts rows before the dedupe, so a reader can predict the refusal from the query alone.
11. **Errors and panics.** One exhaustive `match` maps each `ErrorKind` to its SQLSTATE: `usage` 22023, `backend` 38000, `local` 58030, `cancelled` and `deadline` 57014, `defect` XX000. The message keeps the tag's shape, `thinkthen <kind>: <message> (retryable: yes|no)`, with the kind from `ErrorKind::name`. pgrx's `#[pg_extern]` guard turns a Rust panic into an error, and the binding writes no second guard. A worker that dies closes its channel, and the backend thread raises `defect`. `thinkthen` stops engine panics at its public methods (0086).
12. **The key setting refuses on the next call.** The 2026-09-24 amendment below registers the key as `Userset`. A `SET thinkthen.api_key = '…'` succeeds. Its check hook accepts every value and sets no `GUC_check_errmsg`. The next thinkthen call refuses with 22023, naming `thinkthen.api_key` and `THINKTHEN_API_KEY`, and never echoing the value. A refusal inside the `SET` would fail that statement. PostgreSQL would then log `STATEMENT: SET thinkthen.api_key = '…'` under the default `log_min_error_statement`, and the key would sit in the server log. This is the tag's call-time rule (`unwired_key_refusal`), kept for that reason.
13. **Authority.** The install block that revokes PUBLIC, the scoped event trigger, the narrowed grant in the README, `thinkthen.file_directory` (`Suset`), and the `pg_read_server_files` gate move unchanged.
14. **Two engine images (G9).** A backend that also loads the Python wheel through PL/Python holds two engines. The README states whichever answer Ian gives to ADR 0047 item 5.
15. **No test or plant can reach a paid backend (amendment of 2026-09-24).** The port guide's shared rule on main at `d783ab6b` forbids it. Decision 3's plant broke it. Under `Engine::builder()` the backend ignores `THINKTHEN_BASE_URL` and sends to the built-in address, the paid vendor's endpoint. That plant leaves, following 0105 change 13 at `c294ca9c`.
   - The real key. PostgreSQL backends inherit the postmaster's environment, and the postmaster inherits `pg_ctl`'s. So `check.sh` runs `unset THINKTHEN_API_KEY` at its top, before any `cargo`, `initdb`, or `pg_ctl` step. Each server start runs `env -u THINKTHEN_API_KEY THINKTHEN_API_KEY=tt-loopback-fake THINKTHEN_BASE_URL=<loopback> THINKTHEN_CACHE=<folder> pg_ctl start`. The fake key appears only beside a loopback address. The start function refuses any `THINKTHEN_BASE_URL` whose host is not `127.0.0.1`. A check step reads `/proc/<postmaster pid>/environ` after each start and fails unless the key reads `tt-loopback-fake`. Plant: drop the top `unset`, and start the server with plain `pg_ctl start` under the same address and cache. The gate runs with a sentinel `THINKTHEN_API_KEY` exported. The environ step reads the sentinel and turns red before any test sends.
   - The environment-seed test. The server starts with `THINKTHEN_CACHE` at folder A and with `HOME` and `XDG_CACHE_HOME` at a scratch folder. `thinkthen.cache` stays empty. One session decides the same pair twice. The loopback backend counts exactly one send, and A holds a cache entry. Plant: after `EngineBuilder::from_env()`, the binding calls `cache_at` with ADR 0017's XDG folder whenever `thinkthen.cache` is empty. The entry lands in the scratch folder, A stays empty, and the test turns red. The address still comes from `from_env`, so the plant run also counts its one send on the loopback listener. Both runs differ only in which folder gets the entry.
   - Every other plant keeps `EngineBuilder::from_env()` and the server's loopback environment. The throttle, preload, and mask plants change a setting or a thread. None of them changes the engine's address.

## Amended 2026-09-24 after experiment 254

Experiment 254 ran the accepted design's settings, key, lint, and start rules on Beelink against the pinned PostgreSQL 16.15 package. Its logs are in `~/workspace/experiments/254-thinkthen-postgresql-spike/logs/`, and the "Spike finding" section below summarizes them. This amendment overrides decisions 3, 12, and 15, the lint paragraph of the gate section, and R5-17's test wherever they disagree. The spike used the old name `thinkthen.width`. Here the setting is `thinkthen.throttle`, as ADR 0017's rename amendment asks. Ian can overturn each decision below.

1. **The four engine settings use `Suset`.** Under `SuBackend` with lazy loading, any `pg_reload_conf()` made every new session drop every `thinkthen.*` value from the server's configuration, with no warning. `ALTER ROLE … SET` and `ALTER DATABASE … SET` failed with 55P02 under preload, and under lazy loading each session warned and ignored the value. So decision 3's per-role spend limit did not work. Under `Suset` the spike saw the configuration file, a reload, `ALTER ROLE`, and `ALTER DATABASE` all reach the session (log 14, S1 and S2). An ordinary role still gets 42501 through `PGOPTIONS`, a `SET` before load, and a `SET` after load (S3).
   - Rebuild. A superuser can change a setting mid-session, and a reload changes it in running sessions. So each call compares the setter plan it reads on the backend thread (decision 6) with the plan its engine was built from. When they differ, the call builds a new engine from `EngineBuilder::from_env()` and the new plan before its worker starts, and it keeps that engine. Detached workers hold clones of the old engine, so the old engine ends when its last worker ends. `Counters` is a process total (0084), so `thinkthen_usage` carries across a rebuild.
   - The throttle under a rebuild. 0077 allows one explicit throttle per process, and a later different explicit throttle fails. A rebuild therefore passes the plan's throttle only while no explicit throttle is active in the backend. Once one is active, the rebuild omits the throttle, and the engine follows the active cap. A changed `thinkthen.throttle` reaches new sessions only, and the README says so.
   - Tests. A superuser session sets `thinkthen.max_requests = 3`, answers a 3-row array batch, sets it to 2, and gets 22023 with zero counted sends on the next 3-row batch. Plant: build once and never compare plans. The second batch answers. A second test sets the throttle to 8, calls, sets it to 6, and calls again. The call answers, and a held 64-row batch holds 8 counted sends. Plant: pass the new throttle on the rebuild. The call fails with 0077's conflict. A per-role test runs `ALTER ROLE` with `thinkthen.max_requests = 2` for an ordinary role, and that role's 3-row batch refuses with 22023 and zero counted sends.
   - This replaces decision 3's `SuBackend` context and its restart rule. The README drops the restart sentence and states the rebuild and the throttle rule. `max_requests` stays superuser-only, and `ALTER ROLE` now gives the per-role limit.
2. **The key setting uses `Userset`.** Under `Suset`, an ordinary role's `SET thinkthen.api_key = '…'` failed PostgreSQL's privilege check, and the log recorded `STATEMENT:` with the value. The 2026-09-24 review's rule stands: no failing statement the extension causes may write the key to the log. So `thinkthen.api_key` is `Userset`, with `NO_SHOW_ALL`, `SUPERUSER_ONLY`, and `DISALLOW_IN_AUTO_FILE`. Its check hook accepts every value. An ordinary role's `SET` after the library loads then succeeds, the next call refuses with 22023 (decision 12), and the log holds no line with the value. `SHOW` by an ordinary role still refuses with 42501 (log 14, S5). The spike ran no `SET` before load, no `PGOPTIONS` value, and no `ALTER ROLE` for the key. The secrecy test below proves the first two. If either leaks, the builder stops and re-scores.
   - The limit. PostgreSQL logs the text of any statement it refuses for its own reasons, whatever the setting's context. Examples are a `SET` inside an aborted transaction, an `ALTER ROLE` on another role without the privilege, and `ALTER SYSTEM`. `DISALLOW_IN_AUTO_FILE` refuses `ALTER SYSTEM`. `ALTER ROLE … SET thinkthen.api_key` by an ordinary role for itself joins this list. In a session that has not loaded the library, the name is a placeholder, and PostgreSQL 16 may refuse a non-superuser's placeholder without `USER SET`. No context choice keeps a key typed into such a statement out of the log. The README tells readers never to type a key into SQL, and to set `THINKTHEN_API_KEY` in the server's environment. Builder note: the README gives a second reason beside the log. A successful `ALTER ROLE … SET` or `ALTER DATABASE … SET` of the key stores it in the `pg_db_role_setting` catalog. Every role can read that catalog, and `\drds` shows it, whatever the setting's flags.
   - The test. The server runs with PostgreSQL's default `log_min_error_statement = error` and `log_statement = 'none'`. An ordinary role and a superuser each run `SET thinkthen.api_key = '<value>'` twice: once in a fresh session before the library loads, and once after a call has loaded it. Each then makes a call. The ordinary role also connects with the value in `PGOPTIONS`. Each call gives 22023. The test then reads the whole server log, and no line carries the value. Plant: register the key as `Suset`. The ordinary role's `SET` fails, the log carries its `STATEMENT:` line, and the test turns red.
3. **The embed shim allows `unsafe`.** `cargo check --lib --bins` passed under `unsafe_code = "deny"`, but `cargo pgrx package` failed with six errors. The package step injects generated `unsafe extern` blocks into the embed binary. So `src/bin/pgrx_embed.rs` carries `#![allow(unsafe_code, reason = "cargo pgrx package injects unsafe extern blocks here")]`, and nothing else. `policy.py` accepts `unsafe_code` in that file and under `src/ffi/`, and it refuses it anywhere else. The package step runs in `check.sh`, so a broken shim fails the check. The ADR 0047 PostgreSQL section records the shim.
4. **The `unexpected_cfgs` policy covers every door.** Under `deny`, the spike compiled a hand-written `allow`, an `expect`, a `cfg_attr` form, a multi-line `allow`, and a `build.rs` that widens `check-cfg` (log 08). ## The ADR 0043 amendment

The builder appends this amendment to ADR 0043 and changes its status line to read: "Status: accepted 2026-09-23. Amended 2026-09-24 by ticket 0111: a cancel now stops single-row calls and batches within one 50 ms tick, and the deadline stays the budget." The title and the original decision stay as history. ADR 0043 does not record its rule as Ian's (record 0070 names no ruling by him), and its text says Ian can overturn it. So the owner amends it, and Ian can overturn the amendment.

The amendment says:

- `pg_cancel_backend`, `pg_terminate_backend`, and `statement_timeout` stop a single-row call or a batch within one 50 ms tick. Every call runs on a detachable worker (0111 decision 7). The backend thread waits in ticks, reads `QueryCancelPending` and `ProcDiePending`, and on either cancels the call's token and detaches the worker. `thinkthen.deadline_ms` stays the budget, and conformance case 27 still runs through it.
- Signals. The backend thread blocks every signal before it spawns a worker and restores its mask after. Every engine thread descends from a worker and inherits the full mask. PostgreSQL's cancel, alarm, and procsignal handlers therefore run only on the backend thread. This holds for batches and for the first engine build. The check's signal-mask test reads each thread's `SigBlk` line and covers the rule.
- Settings. The backend thread reads every setting and every named file before the spawn, because pgrx `GucSetting::get` panics off the backend thread.
- What a cancel does not stop. A cancel returns control to the session. A send already on the wire still completes and is billed, and its answer lands in the cache. Each detached send holds one throttle permit until it ends, and the engine's 30-second request timeout bounds that. Repeated cancels can hold at most the throttle's permits at once. A later call then waits at the throttle gate for at most 30 seconds, and its own deadline still bounds it.

Contradictions with the accepted design:

1. `SuBackend` does not do what decision 3 says. With lazy loading, any `pg_reload_conf()` makes each new session drop every `thinkthen.*` value from the server's configuration, even when nothing changed. PostgreSQL logs no warning. `ALTER ROLE … SET` and `ALTER DATABASE … SET` fail with 55P02 when the library is preloaded. When it loads lazily, each session warns and ignores the role's value. The per-role spend limit of decision 3 does not work. Decision: the four settings use `Suset`. Under `Suset` the configuration file, a reload, and `ALTER ROLE` all work, and an ordinary role still gets 42501 through `PGOPTIONS`, `SET` before load, and `SET` after load. A superuser can `SET` a value mid-session. So each call compares the plan it reads (decision 6) with the plan its engine was built from, and rebuilds the engine when they differ. The README drops the restart rule. Ian can overturn this.
2. The key setting leaks under `Suset`. An ordinary role's `SET thinkthen.api_key = '…'` fails in PostgreSQL's privilege check, and the log records `STATEMENT:` with the value. Decision: register `thinkthen.api_key` as `Userset`, keeping `NO_SHOW_ALL`, `SUPERUSER_ONLY`, and `DISALLOW_IN_AUTO_FILE`. Any role's `SET` then succeeds, the next call refuses with 22023, the log holds no line with the value, and `SHOW` by an ordinary role still refuses with 42501. The secrecy test runs its `SET` as an ordinary role as well as a superuser. Ian can overturn this.
3. `unsafe_code = "deny"` breaks `cargo pgrx package`. The design probe ran `cargo check --lib --bins`. That check passes. The package step injects generated `unsafe extern` blocks into the embed binary, and the build fails with six errors. Decision: `src/bin/pgrx_embed.rs` carries `#![allow(unsafe_code, reason = "…")]`, and `policy.py` accepts `unsafe_code` in that file and in `src/ffi/`. The ADR 0047 section records it.
