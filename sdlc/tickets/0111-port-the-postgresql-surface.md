# 0111: Port the PostgreSQL surface

Status: revised after review; confirmation pending. Owner: Claude.

## Outcome and authority

Port the PostgreSQL extension from tag `surfaces-wave7-frozen-2026-09-24b` (`9df8bae9`) onto the public Rust API as the unpublished crate `thinkthen-postgresql` at `databases/postgresql`, in its own Cargo workspace. `CREATE EXTENSION thinkthen` keeps its SQL names: `thinkthen_decide` (scalar and array), `thinkthen_probability`, `thinkthen_choose`, `thinkthen_score`, `thinkthen_tag`, `thinkthen_annotate`, `thinkthen_details`, `thinkthen_usage`, `thinkthen_warm`, `thinkthen_recognize`, `thinkthen_relations`, and `thinkthen_relate`. `WHERE` and `ORDER BY` stay the filter, rank, and find verbs. Every call reaches the real engine through `thinkthen`. Queue item 3 of `sdlc/planning/one-line-plan-2026-09-24.md` lists PostgreSQL among the remaining surfaces.

Draft ADR 0047 (on the 0093 branch until 0093 lands) fixes the crate's place and its checklist. Ticket 0093 sets the workspace, lint, ratchet, and surface-rung pattern. Ticket 0095 fixes the members this binding calls. Section 3.2 of `sdlc/planning/surfaces-port-guide.md` gives the port map, and its "Shared rules" section (main at `bced9c4d`) sets six rules every surface ticket follows. ADR 0043 on main makes this ticket its owner. Accepted ticket 0105 is the template, and ticket 0110 (DuckDB) makes the same relate and deny choices. The 2026-09-24 design review (`sdlc/records/2026-09-24-design-review-0111.md`) found ten items, and this version answers all ten. Ian can overturn every decision below.

## Design and decisions

1. **Shared rules.** This ticket follows the six rules in the port guide's "Shared rules" section. Claude set them on 2026-09-24 from the design reviews of 0105 to 0112, and this ticket records how it meets each.
   - No Docker. The check runs a local PostgreSQL 16.15 from Ubuntu's package (the gate section). The tag's cached-Docker path is dropped.
   - Toolchains outside the answer cache. The package and its extracted tree live under `~/.cache/thinkthen-toolchains/postgresql/`. The product's answer cache stays at ADR 0017's XDG folder or a folder the test names. The fetch is one-time setup with a SHA256 pinned in the repo, and `runtime.sh` refuses a mismatch.
   - Each test gets its own product cache folder and its own loopback backend. The server's environment carries `THINKTHEN_CACHE` and `THINKTHEN_BASE_URL`, so the check restarts the server for each test with a fresh `mktemp` cache folder and that test's backend. One backend per test comes from ticket 0117, and this ticket depends on it. This ticket uses neither 0117's fixed delay nor its held reply that holds again.
   - Ctrl-C is prompt for single calls and batches alike (decision 7).
   - Deny plants reach deny while offline (the gate section).
   - Tests that need parallel requests set the width they need (decision 3).
2. **No C door underneath.** The extension links `thinkthen` by path through pgrx and never links `thinkthen-c` (ADR 0047 item 1). A C hop would add JSON text per call and a second FFI edge. From 0094 it takes only the pattern: one `unsafe` module tree, one error table, and the output-name collision check behind R2-26.
3. **Engine and settings.** Every call uses `thinkthen::default_engine()`, built lazily in each backend on the worker of decision 7. `_PG_init` registers settings and touches no engine. The key, the address, and the cache folder come from the server's environment alone (`THINKTHEN_API_KEY`, `THINKTHEN_BASE_URL`, `THINKTHEN_CACHE`). ADR 0017 section 5 gives databases "the engine value's setting, then the same variable". Reading the environment alone at 0.1 is this ticket's decision, and it answers open question 4 of `postgres.md`. Three reasons: the key setting leaks into `pg_stat_statements` on PostgreSQL 15 to 17 (`postgres.md`), a failing `SET` writes its value to the server log (decision 12), and no public builder starts from the environment. `thinkthen.api_key` stays registered (`Suset`, hidden) so a stray `SET` has a defined answer. The `SET` succeeds, and the next call refuses (decision 12). The extension adds no width or address setting, and the width stays the engine default. Lever: an `EngineBuilder` member that starts from the environment, as a 0095 amendment.
   - Test width. A test-only Cargo feature `test-hooks` adds `thinkthen.test_width` (`Suset`, 1 to 32, unset by default) and the panic probe of R1-10. When the setting is unset, the backend uses `default_engine()`. When a test sets it in the server's configuration, the first call builds the backend's engine with `Engine::builder()`, `base_url` and `cache_at` from the same two variables, and `width`. Tests that need parallel requests set width 8. Every other test leaves the setting unset and runs `default_engine()`. A package check proves the shipped tree lacks both hooks.
4. **Saved answers move to the engine cache.** The per-backend answer map, `thinkthen.saved_answer_kb`, and the binding's hit counter leave. `thinkthen_warm` fills the engine's disk cache at ADR 0017's default folder for the server's operating-system user, or `THINKTHEN_CACHE`. A decide after a warm pass reads that cache and sends nothing, in the same session and in the next. `thinkthen_usage` reads `Counters` alone. Cost: a cached answer costs one file read, a 5.7 µs median by ADR 0017 section 5.
   - Warm cap. One `thinkthen_warm` call takes at most 20,000 rows. The 20,001st refuses with 22023 and the sentence "thinkthen_warm takes at most 20,000 rows per call". The aggregate holds every row's text in backend memory until the finalizer, and the cap bounds that memory and one statement's spend. The tag holds the same cap as `WARM_ROW_CAP`, so its test carries over.
   - Cache size. The engine cache keeps its 100 MB default. The README tells a reader to raise the limit before a warm pass over more than about 25,000 answers. The binding has no setting for it. The reader raises it in the configuration file of the server's operating-system user (ADR 0017 section 5), or frees space with `thinkthen cache prune`.
5. **Deadlines.** `thinkthen.deadline_ms` stays `Userset` with the range -1 to 2,147,483,647, so PostgreSQL itself refuses -2. Every call passes it through `CallOptions::deadline_millis` (ADR 0041, ADR 0043). `-1` is none, and `0` returns 57014 with nothing sent. The backend thread also checks the deadline's instant on each tick of decision 7. On a passed deadline it cancels, detaches, and raises `thinkthen deadline` with 57014.
6. **Settings and files are read on the backend thread.** pgrx `GucSetting::get` panics off the backend thread, as the tag's comment at `lib.rs` near line 220 records. So the backend thread reads `deadline_ms`, `file_directory`, the key check, and `test_width`, reads any named file, and runs every SPI query before the spawn. The worker receives owned values only and never calls into PostgreSQL.
7. **Every call runs on a detachable worker under a full signal mask.** This amends ADR 0043, and the section below gives the amendment's text.
   - Which calls. All of them: `decide` (scalar and array), `probability`, `choose`, `score`, `tag`, `annotate`, `details`, `recognize`, `relations`, the `thinkthen_warm` finalizer, and `thinkthen_relate`. The first engine build in a backend happens inside a worker too.
   - The worker. It owns a clone of the question, the texts as `String` values, and a clone of an internal `CancelToken`. It builds its own `CallOptions` with that token and the deadline. It sends its result over a channel. It ignores a closed channel and never panics on one.
   - The mask. The backend thread blocks every signal with `pthread_sigmask` before the spawn and restores its own mask right after. The worker and every thread the engine spawns from it inherit the full mask. PostgreSQL's handlers therefore run only on the backend thread. This rule covers batches and the first `default_engine()` build as well as single rows. A test reads the mask of every thread (acceptance, "Signal mask").
   - The wait. The backend thread waits on the channel in 50 ms ticks. A finished call returns at once. On each tick it reads `QueryCancelPending` and `ProcDiePending` with volatile reads in the FFI module and checks the deadline instant. It never runs `check_for_interrupts!` inside the wait, because that jumps across Rust frames. Any other pending interrupt, such as a memory-context request, leaves the wait alone and is serviced after the call.
   - On a cancel. The backend thread cancels the internal token, detaches the worker, and runs `check_for_interrupts!()`. That raises PostgreSQL's own error for a user cancel, a terminate, or a statement timeout. If it returns, the binding raises `thinkthen cancelled` with 57014. A single row and a batch both return within one tick. The engine starts no new send and no retry once the token is cancelled. The detached worker finishes the requests already sent under 0073 and drops the result.
   - Cost. About 60 lines and one thread spawn per call, cache hits included. The record measures a 20,000-row scalar decide over cached answers and stops the ticket above 100 µs a row. The tag's `run_batch` thread and its poll loop leave, and `CallOptions::interrupt` goes unused.
   - Ian can overturn this and keep ADR 0043's deadline-only rule.
8. **Question arguments.** A question, set, or spec is `'@file.json'` or the file grammar's JSON text. Bare text refuses with the tag's sentence naming the `@` form (R2-4). The binding reads a named file itself under the privilege gate, the 1 MiB cap, the regular-file rule, and `open_beneath` confinement. It then calls `Question::from_json`, `QuestionSet::from_json`, `Recognize::from_json`, or `Relate::from_json`. A `Usage` from a file's text maps to `local` (0095). The members array of `choose`, `score`, and `tag` joins the question's JSON object as `options`, `levels`, or `labels` before `from_json`. A question that already carries its members and also gets an array refuses with `usage`. The tag's `with_members` rebuild and its lifting of the `recognize` section leave.
9. **Results.** `decide` returns true, false, or NULL. `probability` reads `Probabilities::YesNo` from `details`. Scalar `choose` and `tag` call `details` and read `value()` with no added send, as 0095 G5 and 0105 decision 8 do. `score` returns the position. `tag` returns `text[]`. Scalar `annotate` returns `AnnotatedRecord::value_json` as `jsonb`, and `details` returns `Details::to_json`. `thinkthen_usage()` returns `requests_sent`, `cache_answers`, `input_tokens`, and `output_tokens`. Tests assert differences around a call (0095). `thinkthen_recognize` returns `(name, kind, start, end, strength)`, main's shape (port guide 4.3), and the `text` column becomes `name`. Offsets count Unicode scalar values. PostgreSQL counts characters the same way in a UTF-8 database. `thinkthen_relations` returns `(relation, source_name, source_kind, target_name, target_kind, probability)`.
10. **Relate from rows.** `thinkthen_relate(query, rules)` reads a query whose columns are id, name, and kind. A two-column query of id and name reads kind `*` and takes only bare rules, as 0110 does. `rules` is a `text[]` of the command's inline rule strings, or `text` holding `'@file.json'` or a version-one relate file. Per ADR 0047 item 9, the binding dedupes rows by name and kind in first-seen order, calls `relate_with` once, and returns one row `(relation, source, target, probability)` per matching id pair. Ids stay `bigint`, as at the tag. SPI reads under `LIMIT 256`, and a 256th row refuses with 22023 naming the cap (R3-12's shape). This row cap is stricter than the unique-pair cap of ADR 0047 item 9 and 0095 Q14, and the README says so. It counts rows before the dedupe, so a reader can predict the refusal from the query alone.
11. **Errors and panics.** One exhaustive `match` maps each `ErrorKind` to its SQLSTATE: `usage` 22023, `backend` 38000, `local` 58030, `cancelled` and `deadline` 57014, `defect` XX000. The message keeps the tag's shape, `thinkthen <kind>: <message> (retryable: yes|no)`, with the kind from `ErrorKind::name`. pgrx's `#[pg_extern]` guard turns a Rust panic into an error, and the binding writes no second guard. A worker that dies closes its channel, and the backend thread raises `defect`. `thinkthen` stops engine panics at its public methods (0086).
12. **The key setting refuses on the next call.** A `SET thinkthen.api_key = '…'` succeeds. Its check hook accepts every value and sets no `GUC_check_errmsg`. The next thinkthen call refuses with 22023, naming `thinkthen.api_key` and `THINKTHEN_API_KEY`, and never echoing the value. A refusal inside the `SET` would fail that statement. PostgreSQL would then log `STATEMENT: SET thinkthen.api_key = '…'` under the default `log_min_error_statement`, and the key would sit in the server log. This is the tag's call-time rule (`unwired_key_refusal`), kept for that reason.
13. **Authority.** The install block that revokes PUBLIC, the scoped event trigger, the narrowed grant in the README, `thinkthen.file_directory` (`Suset`), and the `pg_read_server_files` gate move unchanged.
14. **Two engine images (G9).** A backend that also loads the Python wheel through PL/Python holds two engines. The README states whichever answer Ian gives to ADR 0047 item 5.

## The ADR 0043 amendment

The builder appends this amendment to ADR 0043 and changes its status line to read: "Status: accepted 2026-09-23. Amended 2026-09-24 by ticket 0111: a cancel now stops single-row calls and batches within one 50 ms tick, and the deadline stays the budget." The title and the original decision stay as history. ADR 0043 does not record its rule as Ian's (record 0070 names no ruling by him), and its text says Ian can overturn it. So the owner amends it, and Ian can overturn the amendment.

The amendment says:

- `pg_cancel_backend`, `pg_terminate_backend`, and `statement_timeout` stop a single-row call or a batch within one 50 ms tick. Every call runs on a detachable worker (0111 decision 7). The backend thread waits in ticks, reads `QueryCancelPending` and `ProcDiePending`, and on either cancels the call's token and detaches the worker. `thinkthen.deadline_ms` stays the budget, and conformance case 27 still runs through it.
- Signals. The backend thread blocks every signal before it spawns a worker and restores its mask after. Every engine thread descends from a worker and inherits the full mask. PostgreSQL's cancel, alarm, and procsignal handlers therefore run only on the backend thread. This holds for batches and for the first engine build. The check's signal-mask test reads each thread's `SigBlk` line and covers the rule.
- Settings. The backend thread reads every setting and every named file before the spawn, because pgrx `GucSetting::get` panics off the backend thread.
- What a cancel does not stop. A cancel returns control to the session. A send already on the wire still completes and is billed, and its answer lands in the cache. Each detached send holds one width permit until it ends, and the engine's 30-second request timeout bounds that. Repeated cancels can hold at most the width's permits at once. A later call then waits at the width gate for at most 30 seconds, and its own deadline still bounds it.
