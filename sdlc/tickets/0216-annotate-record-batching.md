# 0216: Batch annotate records within each on group

Status: Proposed B10 design for fresh independent review. No runtime, paid result or B10 completion is claimed. ADR 0092 proposes one additive metadata choice; it is not accepted. Owner: Codex.

## Accepted outcome and retained behavior

Build B10 of the [accepted batching issue](../issues/2026-09-26-batching-design.md) under ADRs [0048](../planning/adr/0048-records-batch-into-full-requests.md), [0051](../planning/adr/0051-every-address-has-a-ceiling-and-a-refused-batch-halves-once.md), [0053](../planning/adr/0053-the-pause-fires-in-every-mode-and-batches-have-a-member-cap.md) and [0055](../planning/adr/0055-decide-filter-and-rank-batches-send-each-record-once.md). In record mode, each normalized `on` group fills requests with consecutive records, subject to the settled close rules. A recorded question set of yes/no and pick-one questions measures the result and cost without an accuracy gate. Remove only annotate's B10 exception from S1 after implementation and proof; retain its function workload. B8 choose code at `e5419ef9` passed helper review and completed its paid proof, but completion review and landing remain pending. B9 ticket 0215 has accepted design only. Both source outcomes must be refreshed before B10 runtime claims.

Keep the current one-document route, request bytes, profile chunking, cache/recording identity, output shape and exit codes. `--batch 1` in record mode sends each record's grouped chunks byte for byte as today. Each named question keeps its `on` pointers, question order, complete option/label descriptions, own threshold, `null` for not sure and a distinct failed marker. A reply with a failed logical question beside a good answer prints both and a completed run exits 6; a record with no usable group result or a whole request failure stops under its existing six-kind cause. Earlier complete rows remain an ordered prefix. A group never sees another group's selected evidence or answers. The existing grouped scheduler can run different groups concurrently under the global `--jobs` width; record order does not imply serial transport.

## Concrete B10 route

1. Add `Batching` to `AnnotateArguments` and resolve typed `--batch`, `THINKTHEN_BATCH`, the one **top-level** question-set `batch`, then `max`. The existing `--max-request-bytes` typed/environment/default tier closes batched requests; an explicit profile remains a hard limit. A typed `--batch` on one document is Usage exit 2; an ambient or file batch leaves that document unchanged. `QuestionSet::parse` admits only the top-level key and keeps every `questions.NAME.batch` rejection (ADR 0048 item 4). Reject a selected malformed set value at the file boundary without adding it to the resolved question-set digest. The set's named questions and canonical SHA-256 remain unchanged. This does not add `--context`: each group's `on` selection is its evidence, and shared context belongs only to commands that already expose it.
2. Parse a record and validate collisions, base selection and **all** group selections before sending work for that record, as `annotate_schedule::prepare` currently does. Keep group order by first appearance of normalized `on` pointers. A bounded coordinator holds an input-ordered record window and one open batch per group; each batch refers to row indices and selected `BatchRecord` values rather than copying a new harness or opening a worker per question. Within a group, derive stable contiguous question slices with the existing `facade::split` profile logic for each singleton; only compatible slices share a batched request. If a record changes that slice layout, close the affected open slice before it and retain its own legacy chunks. No explicit profile is the ordinary one-slice-per-group case. This preserves every `--batch 1` chunk and permits a hard profile to split a group without treating a soft request-byte threshold as a singleton refusal.
3. Reuse the B3/B8 pure batch close/count code for each compatible group slice: content cut on the group's **selected** compact JSON bytes, 4,096 record members including repeats, number, exact fully encoded body size, 50 ms pause in every mode, and end. A multi-record slice sends `{"records":[…]}` of selected evidence and one quoted copy of each slice question per distinct record, in record-major then question-set order. Do not apply ADR 0055's decide/filter/rank fixed sentence to annotate. Share an answer only when selected evidence **and the complete ordered slice of logical questions** match; a copy retains its original input row and named slots. Count expanded tag labels in wire limits and names, while mapping each decoded logical outcome back to `(record,group,question place)`. Do not use a first-wire offset as a logical outcome index, the B9 seam. Use actual serialized bytes/digest for profile, cache, replay and recording; `--jobs` changes scheduling, not batch identity.
4. Turn each returned request into bounded per-record group fragments. Preserve the existing `facade/annotate.rs::take_answers` behavior: good sibling values survive a failed logical question, failures carry their own `question` and `request`, `meta.failed_questions` counts them, and a group with no usable answer still fails. A row prints only after its required group slices finish and every earlier row has printed. On a later parse, selection, profile or send error, flush earlier closed work, join in-flight work, then stop at the first affected record with the already printed prefix. A failed request names its member range; a partial reply stops at the first record with no usable answer. Keep queue, in-flight request and retained row windows bounded by `--jobs`, group count and the 4,096-member cap, with backpressure rather than unbounded result history. Keep one finished-record count per fully assembled input row.
5. Reuse one eligible 413 or named `max_tokens_exceeded` 400 halving by **record members**, first ceiling half then second, with no recursive split. Rebuild the same group slice and exact selected values for each half; a singleton half uses its historical prepared chunk. The first half's rows may complete before a second-half stop, while a row still waits for its other groups. Other retryable statuses resend the whole request. A missing whole replay may find recorded halves in order; a failed whole stores no entry. Divide each actual request's usage and attempt count over its member rows with the existing earliest-remainder rule, then sum each row's group/chunk shares. Preserve ordered `meta.requests` positions even when two groups have equal digests and cache coalesces their send. `cached` requires every contributing chunk to be stored. `--facts` ends after joined work and usage flush; it counts actual attempts, retries, cache answers and only fully finished rows, omitting token fields when reported usage is incomplete. Exit 6 is a finished partial result, not a stopped run.

## One proposed public metadata choice

A row may ride different batches for two `on` groups and several profile chunks. ADR 0048 item 9 and ADR 0083 describe singular `meta.batch`; `AnnotateMeta` currently has no batch field. [Proposed ADR 0092](../planning/adr/0092-annotate-group-batch-metadata.md) recommends additive `meta.batches` entries in `meta.requests` order, one per contributing request when any chunk of that row was batched or split. Each entry names its stable group ordinal and request digest and reuses the accepted batch fields. `meta.batch` stays singular on one-question verbs. At `--batch 1`, omit `meta.batches` and keep old detailed bytes. This is the sole new outward choice found; independent review and a recorded owner ruling are required before implementation. No accepted B10 outcome is made conditional on a particular spelling without that ruling.

Design only. The 0215 design exposed why wire offsets cannot index logical tag outcomes here either.
