# 0216: Batch annotate records within each on group

Status: B10 code and its recorded 182-case comparison passed independent reviews at `efa2cd9e` and `c61654d4`. The accepted evidence removes only annotate's S1 list exception; the function workload and wider S1 live measurements remain. Pending coordinator landing. Owner: Codex.

## Accepted outcome and retained behavior

Build B10 of the [accepted batching issue](../issues/closed/2026-09-26-batching-design.md) under ADRs [0048](../planning/adr/0048-records-batch-into-full-requests.md), [0051](../planning/adr/0051-every-address-has-a-ceiling-and-a-refused-batch-halves-once.md), [0053](../planning/adr/0053-the-pause-fires-in-every-mode-and-batches-have-a-member-cap.md) and [0055](../planning/adr/0055-decide-filter-and-rank-batches-send-each-record-once.md). In record mode, each normalized `on` group fills requests with consecutive records, subject to the settled close rules. A recorded question set of yes/no and pick-one questions measures the result and cost without an accuracy gate. Remove only annotate's B10 exception from S1 after implementation and proof; retain its function workload. B8 choose completed review and landed on main at `78eea61c` after the paid result at `e5419ef9`. Main was checked at `374f8396`; B9 ticket 0215 still has accepted design only and is building separately. Refresh B9 final source before B10 runtime claims.

Keep the current one-document route, request bytes, profile chunking, cache/recording identity, output shape and exit codes. `--batch 1` in record mode sends each record's grouped chunks byte for byte as today. Each named question keeps its `on` pointers, question order, complete option/label descriptions, own threshold, `null` for not sure and a distinct failed marker. A reply with a failed logical question beside a good answer prints both and a completed run exits 6; a record with no usable group result or a whole request failure stops under its existing six-kind cause. Earlier complete rows remain an ordered prefix. A group never sees another group's selected evidence or answers. The existing grouped scheduler can run different groups concurrently under the global `--jobs` width; record order does not imply serial transport.

## Concrete B10 route

1. Add `Batching` to `AnnotateArguments` and resolve typed `--batch`, `THINKTHEN_BATCH`, the one **top-level** question-set `batch`, then `max`. The existing `--max-request-bytes` typed/environment/default tier closes batched requests; an explicit profile remains a hard limit. A typed `--batch` on one document is Usage exit 2; an ambient or file batch leaves that document unchanged. `QuestionSet::parse` admits only the top-level key and keeps every `questions.NAME.batch` rejection (ADR 0048 item 4). Reject a selected malformed set value at the file boundary without adding it to the resolved question-set digest. The set's named questions and canonical SHA-256 remain unchanged. This does not add `--context`: each group's `on` selection is its evidence, and shared context belongs only to commands that already expose it.
2. Parse a record and validate collisions, base selection and **all** group selections before sending work for that record, as `annotate_schedule::prepare` currently does. Keep group order by first appearance of normalized `on` pointers. A bounded coordinator holds an input-ordered record window and one open batch per compatible `(group, question slice)`; a batch refers to row indices and selected `BatchRecord` values rather than copying records or opening a worker per question. Within a group, derive stable contiguous question slices with the existing `facade::split` profile logic for each singleton; only compatible slices share a batched request. If a record changes that slice layout, close the affected open slice before it and retain its own legacy chunks. No explicit profile is the ordinary one-slice-per-group case. A slice containing any JSON object or list question text is ineligible for quotation and uses its historical singleton chunk, even at `max` (ADR 0048 item 7). This preserves every `--batch 1` chunk and permits a hard profile to split a group without treating a soft request-byte threshold as a singleton refusal.
3. Reuse the B3/B8 pure batch close/count code for each compatible group slice: content cut on the group's **selected** compact JSON bytes, 4,096 record members including repeats, number, exact fully encoded body size, 50 ms pause in every mode, and end. Only a slice whose every question has quotable text can hold multiple records. It sends `{"records":[…]}` of selected evidence and one quoted copy of each slice question per distinct record, in record-major then question-set order. A structured-text slice closes as a singleton with the original unquoted questions and exact prepared body/digest; it never enters this multi-record encoding. Do not apply ADR 0055's decide/filter/rank fixed sentence to annotate. Share an answer only when selected evidence **and the complete ordered slice of logical questions** match; a copy retains its original input row and named slots. Count expanded tag labels in wire limits and names, while mapping each decoded logical outcome back to `(record,group,question place)`. Do not use a first-wire offset as a logical outcome index, the B9 seam. Use actual serialized bytes/digest for profile, cache, replay and recording; `--jobs` changes scheduling, not batch identity.
4. Turn each returned request into bounded per-record group fragments. Preserve the existing `facade/annotate.rs::take_answers` behavior: good sibling values survive a failed logical question, failures carry their own `question` and `request`, `meta.failed_questions` counts them, and a group with no usable answer still fails. A row prints only after its required group slices finish and every earlier row has printed. On a later parse, selection, profile or send error, flush earlier closed work, join in-flight work, then stop at the first affected record with the already printed prefix. A failed request names its member range; a partial reply stops at the first record with no usable answer. Let `Q` be the finite number of named questions in the validated set; every compatible slice holds at least one. Retain at most 4,096 admitted row seeds plus one candidate being classified, at most 4,096 × `Q` row/slice references or closed fragment descriptors, and at most `--jobs` in-flight requests. Descriptors refer to those rows rather than copying their bodies. The fixed row bound never scales with `--jobs`. Before backpressure, read through the accepted close event needed by the oldest unfinished row: content, number, exact byte/profile limit, incompatible slice layout, genuine input pause, end, or the 4,096-member cap. A stable slice containing that oldest row must close by the cap; a changed layout or structured question closes earlier. Dispatch its closed slices first under the global width, join their workers, assemble the row, and advance the oldest-row frontier before admitting a new window. If the window fills, the cap has closed each still-compatible oldest-row slice; window fullness itself is **never** a close reason. A 50 ms pause measures missing upstream input only while the reader may poll; worker waits and internal backpressure neither create a pause nor alter request identity. Thus changing `--jobs` changes dispatch speed, not file/fast-pipe batch boundaries or digests. Keep one finished-record count per fully assembled input row.
5. Reuse one eligible 413 or named `max_tokens_exceeded` 400 halving by **record members**, first ceiling half then second, with no recursive split. Rebuild the same group slice and exact selected values for each half; a singleton half uses its historical prepared chunk. The first half's rows may complete before a second-half stop, while a row still waits for its other groups. Other retryable statuses resend the whole request. A missing whole replay may find recorded halves in order; a failed whole stores no entry. Divide each actual request's usage and attempt count over its member rows with the existing earliest-remainder rule, then sum each row's group/chunk shares. Preserve ordered `meta.requests` positions even when two groups have equal digests and cache coalesces their send. `cached` requires every contributing chunk to be stored. `--facts` ends after joined work and usage flush; it counts actual attempts, retries, cache answers and only fully finished rows, omitting token fields when reported usage is incomplete. Exit 6 is a finished partial result, not a stopped run.

## Settled public metadata choice

A row may ride different batches for two `on` groups and several profile chunks. ADR 0048 item 9 and ADR 0083 describe singular `meta.batch`. Ian accepted [ADR 0092](../planning/adr/0092-annotate-group-batch-metadata.md): detailed annotate rows add `meta.batches` entries in `meta.requests` order, one per contributing request when any chunk of that row was batched or split. Each entry names its stable group ordinal and request digest and reuses the accepted batch fields. `meta.batch` stays singular on one-question verbs. At `--batch 1`, omit `meta.batches` and keep old detailed bytes.

## What the build taught us

The design phase identified the group scheduler and nested refusal, then expanded its inventory to `AnnotateMeta`, the profile chunk adapter, schema and type corpus. The 0215 design exposed why wire offsets cannot index logical tag outcomes here either. The existing 182-case annotate suite is keyed but has no decide question; a new pinned set is needed to meet B10's exact yes/no and pick-one proof. Fresh design review of `8121c171` found that the first brief named backpressure without proving progress, quoted structured question text in its general rule, and omitted the hand-maintained result schema and type corpus. The corrected design named the oldest-row invariant and singleton exception. Ian later approved ADR 0092.

The [offline build](../records/0216-batching-build.md) reused the shared group packer and scheduler. Its first feeder silently ended with a later closed row still waiting behind the oldest row; a profile listener printed only row one of two with a successful exit. The fix waits for the frontier and drains closed work before ending. A split-stop proof corrected the stopped row for a failed second half. Old singleton stream fixtures now say `--batch 1` explicitly, preserving their original assertions. A controlled 4,096-member listener proves cap progress while the first group's reply is held. These findings reduced duplicate scheduler work and exposed data loss before review. Independent High review accepted the offline code at `efa2cd9e`. The later named comparison used the same 182 ordered cases and independently reviewed answer, request, recording, usage and facts identities. Its default arm sent one decide and two album requests versus 182 of each at batch one. It reported 300,925 combined tokens over both arms and retained the historical price caveat. Fresh evidence review accepted `c61654d4`; the only S1 gate change removes annotate's exception while retaining its workload. The large wall-time difference belongs to this one run and does not establish a stable ratio.

The focused speed test also exposed an inherited fault plant that still targeted choose's removed list entry. Pointing that plant at recognize's still-listed entry kept the landed-ticket refusal assertion and let the unchanged annotate workload pass the offline gate.
