## Outcome

A C, TypeScript or Ruby caller can name a local file holding exactly one `decide`, `choose`, `score` or `tag` question. The binding validates it through the existing Rust question parser before a request. A bad named file produces a non-retryable Local failure with zero sends; a bad caller-built question remains Usage. Existing bare strings, inline JSON, objects and keywords retain their meanings, including strings beginning with `@`.

## Public forms and failure contract

| Host | Explicit form | Success and ownership | Failure |
| --- | --- | --- | --- |
| C | `int thinkthen_question_file(const thinkthen_engine *engine, const char *path, char **out, size_t *out_len)` | Return a NUL-terminated owned copy of the validated source JSON and its byte length. The caller passes it to a typed verb such as `thinkthen_decide` or constructs its JSON-door call, then frees it once with `thinkthen_free_string`. No new C struct or changed symbol. | Null engine retains the existing Usage behavior. Null path/output and invalid path text are Usage. Read, UTF-8, size and file-question failures are `THINKTHEN_ELOCAL`, `retryable=0`, no facts, with both outputs untouched. The normal per-engine, per-thread error accessors report the refusal. |
| TypeScript | `questionFile(path: string): Question` | A synchronous, frozen question value accepted wherever `question(spec)` is accepted. Native Node reads and validates once, then the existing error envelope and `ThinkThenError` handle failures. Export it from CommonJS, ESM and the declaration file. | A non-string, ill-formed or NUL path is Usage. A named-file read or content failure is non-retryable Local. No native exception or path/content text leaks through the envelope. |
| Ruby | `ThinkThen.question(file: path)` | Return the existing `Question` object, holding the validated original JSON. `file:` is exclusive with the existing grammar keywords. `ThinkThen.set(path)` remains a question-set loader. | Missing/ambiguous/invalid path arguments are Usage. A named-file read or content failure is non-retryable Local through the existing Ruby error class. |

Read at most 1,048,577 bytes and reject a file larger than 1 MiB. Bound the actual read rather than trusting metadata: a file can change while it is read. Decode UTF-8 and pass the text to `Question::from_json`; do not use the current unbounded `Question::load` as the host read. File-origin parser failures become Local, while the same typed JSON content remains Usage. The error text uses a fixed category and the core parser's safe grammar diagnostic. It does not print the path, file bytes, evidence, URL or key. File construction is local and synchronous; it has no engine send or cache effect. A later verb still enforces its own kind and inputs. A `choose` file passed to `decide` remains that verb's existing Usage refusal.

For TypeScript, keep the validated file's original source in the branded `Question.__spec`. `specFrom` should pass an already branded question's `__spec` directly to the native call after checking incompatible last-object members. Parsing and serializing it again could reorder numeric member keys in a rich description. Keep `specOf` for ordinary object and text conversion and the existing text-only `rank`/`find` checks. For Ruby, the native file edge returns the current `QuestionValue`; do not route `file:` through the set loader or parse it into a keyword hash in Ruby. For C, the caller receives no success buffer until full validation has finished, and the existing guarded failure slot remains authoritative. The C loader returns a validated question JSON value, not a whole `thinkthen_call` request.

| Boundary | Required observation |
| --- | --- |
| Literal `@question` or inline object/JSON | Existing literal/typed interpretation and Usage failures; no implicit disk access. |
| Valid named decide file | Same captured request body, digest and answer as the canonical inline question; one intended send. |
| Named blank decide, malformed JSON, invalid UTF-8 or unreadable file | Local, non-retryable, zero sends; neither path nor file content in the message. |
| Named file of 1 MiB plus one byte | Local before parser or send; no unbounded allocation. |
| Wrong verb after successful load | Existing verb-level Usage refusal; no send. |
| C output pointer or length on loader failure | Both retain their prior values; no allocation escapes. |

## Routing and limits

The equivalence study's E4 paragraph also mentions recognize and relate file forms and Q5. This ticket proves the three named single-question boundaries and does not relabel that whole paragraph complete. The original shared issue asks for equivalent host-boundary evidence, not identical API spelling or zero skips. A public loader is the recommended choice here because it makes Local origin observable without inventing a caller-specific error adapter; a caller-owned loader would need the same real consumer and failure proof before replacing this design. No new ADR is needed: the current question-file, error and host ownership contracts govern these additions. The accepted design governs runtime claims; fresh code review must verify the resulting implementation.

## What the build taught us

The C loader fits the existing owned-string ABI when it validates before assigning either output. Reusing the current output validator kept the exported unsafe edge in `ffi.rs`, inside its line cap and binding policy. TypeScript's branded file question must retain its original JSON source: parsing and serializing it again changes numeric object-key order and therefore the request digest. Ruby's question-file path belongs to the question loader; the existing set loader remains separate. Selected case 01 and case 30 runs establish the public host boundary, while the broader shared issue still needs its remaining DuckDB and equivalence mapping work.
