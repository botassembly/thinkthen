# 0219: Batch SQLite warm records and expose context

Status: B13e design accepted by independent reviewer session `01a0e63f-e8d5-7db1-9c02-81da1d161d55` at `6456ab23bc5bae7c0198e27f7cd264c4332984c3`; source and selected Linux x86-64 installed package proof are ready for fresh High code review after the [coordinator's ADR 0048 clarification](../records/2026-09-28-sql-warm-cache-identity.md). Owner: Codex. This is not yet code-review acceptance or register 73 closure. The [build record](../records/0219-sqlite-build.md) separates the WIP library from the exact archive.

## Accepted outcome and retained behavior

Build B13e of the [accepted batching issue](../issues/2026-09-26-batching-design.md) under ADRs [0048](../planning/adr/0048-records-batch-into-full-requests.md), [0051](../planning/adr/0051-every-address-has-a-ceiling-and-a-refused-batch-halves-once.md), [0053](../planning/adr/0053-the-pause-fires-in-every-mode-and-batches-have-a-member-cap.md), [0055](../planning/adr/0055-decide-filter-and-rank-batches-send-each-record-once.md), [0087](../planning/adr/0087-a-shared-context-stops-at-the-record-that-overflows.md) and B0. `thinkthen_warm` packs distinct decide records into full requests and caches each complete request by its digest. A new `thinkthen_batch(value)` settings call before the process engine's first build selects `max` or a positive whole member cap; unset resolves `THINKTHEN_BATCH`, then the question file, then `max`. `1` retains old single-record request bytes without context and lets later singleton scalars reuse those same keys. A default packed warm can be reused by repeating the identical ordered cohort; later singleton calls have different requests. A final nonblank context text argument sends reference evidence once per request, changes the request digest and leaves the question digest alone. SQL per-call facts remain deferred; `thinkthen_usage()` keeps process totals.

Keep current SQLite value shapes: decide returns integer `1`, `0` or SQL `NULL` for unsure; choose and tag return text (tag's existing JSON text), score returns real, details and annotate return JSON text, try-details returns its answered/failed JSON text or SQL `NULL`, and warm returns one integer count of distinct `(question, evidence)` pairs judged without context. Current warm accepts decide and banded decide questions, skips `NULL` question/evidence rows, deduplicates within the aggregate, groups by first-seen question, flushes at 256 pending texts, and caches answers. Preserve six failure kinds and SQLite result codes, named-file authority, direct-only volatile registration, connection budget and process throttle/total. The existing `thinkthen_recognize` and `thinkthen_relate` table-valued functions retain their hidden arguments and result schemas; they are not warm or B13e record-batch entrypoints.

A scalar receives one row and waits for its worker. B13e improves explicit warm aggregation, not ordinary `WHERE thinkthen_decide(question, column)` throughput. Register 73's scalar path and the equivalence page remain open after B13e. The old warm-then-scalar cache recipe explicitly sets batch one before the engine builds; default packed warm does not populate singleton request keys.

## Accepted SQLite boundary

1. Register `thinkthen_batch(value)` with the existing direct-only setting functions. SQL text `'max'` selects maximal packing; a positive whole SQLite INTEGER selects a cap. `NULL` clears an explicit setting back to the environment/question/default chain before engine build. Reject zero, negatives, REALs and other text before a send. Like `thinkthen_throttle`, the call applies only before the process engine is built and belongs to the environment tier, below a typed per-call value and above a loaded question file. Do not add key, address or context settings. Retain the existing max-requests, total, request-size, retry, timeout, profile, cache, recording and replay owners and value domains. A question file's batch is calibration identity and stays outside the question digest.
2. Preserve two- and three-argument forms. SQLite's **third** judgment/aggregate argument already means deadline milliseconds; therefore context is final in a **four**-argument overload, `function(question, evidence, deadline_ms, context)`. Use `-1` for no call deadline; `NULL` in the deadline slot retains today's Usage refusal. `NULL` context means absent and preserves the corresponding old request identity; a non-NULL blank context is Usage before a send. Context is literal SQL UTF-8 text, never an `@file` lookup. The new four-argument forms are `thinkthen_decide`, `thinkthen_choose`, `thinkthen_score`, `thinkthen_tag`, `thinkthen_details`, `thinkthen_try_details`, and aggregate `thinkthen_warm`; each keeps its existing result type. These are the eligible one-text judgments and warm group covered by B0's final-context rule. SQLite has no `thinkthen_probability` scalar. `thinkthen_annotate` has a named question set and B10's separate `on` grouping; document/relation functions and usage gain no B13e context form. Keep existing scalar validation order, including `thinkthen_try_details`'s early SQL `NULL` result, deadline parsing before ordinary inputs, and warm's one deadline per aggregate group. For warm, context joins the distinct group key: two values never share a request or answer; count distinct `(question, context, evidence)` triples in the four-argument form. Apply each group's context to every packed request and singleton in that group.
3. Keep the warm aggregate's first-seen `(question, context)` grouping and 256-distinct-text flush boundary per group. Each flush uses the existing pure batch planner through B12a's many-record Rust API: maximal filling, content cuts, full encoded request size and profile minimum, 4,096-member cap, and at most one eligible 413/`max_tokens_exceeded` halving. Preserve duplicate suppression and the count of distinct grouped records, including cached records. A SQL `NULL` question/evidence row adds no record or request; an empty input yields count `0` and no send. Without a context and with batch `1`, old one-record bodies, cache keys and recording digests remain byte-identical. For stable recording/replay the caller supplies a stable aggregate visit order; SQL does not promise row visitation order without one. Different questions and contexts remain separate plans. Do not copy the planner into the extension or let a page imply it batches an ordinary scalar scan.
4. Capture the warm call's absolute deadline once at its first step and pass it through every chunk worker and finalization; keep the connection's independent absolute `thinkthen_budget_ms` bound. A scalar's deadline still covers only that scalar call. Retain interruption and detached-worker behavior. A `thinkthen_max_requests_total` reservation is per **actual transport attempt**, not per input row or planned batch: first sends, failed sends, retries and eligible 413 halves spend it; cache/replay hits do not. Remove the old `settings::remaining` row truncation in `flush`, which equates a row to an attempt. The engine's 0149 `SendBudget` guards each attempt at the final send boundary. With total one and two planned requests, one can send and the next returns the existing spent-total Usage failure; an allowed 503 first attempt can likewise deny its retry. Do not reset the absolute deadline or total at a chunk boundary, and do not infer per-call facts by subtracting process usage.
5. A failed warm statement returns no aggregate count through normal `fetchall()`; earlier sends and cache entries may still exist, including a completed 256-row flush before a later error. SQLite scalar rows can be stepped and observed before a later row fails, so make no PostgreSQL-wide no-partial-result claim. Within a single warm aggregate, no partial count is returned on failure. A strict replay miss with changed context stays Local and sends nothing. Preserve normal failed-value behavior of `thinkthen_try_details` and fatal Deadline/Cancelled/Defect errors.

## What the build taught us

The first runtime slice exposed an overbroad preparation claim: default packing makes one five-row request, then the old slide's five singleton calls make different requests, yielding six sends. B0 already specified complete-request cache keys and batch-one compatibility. The coordinator recorded that interpretation at `fcf7bbef`; the library-owned slide and README now choose batch one visibly, preserving their five sends and zero later sends. A separate default-Max proof repeats the identical packed cohort for a cache hit, then shows the singleton has another key. Same context does not merge those requests. The WIP record's original failed slide result remains as historical evidence; no cache alias or new API was built. The coordinator also corrected a copied DuckDB budget rule: ADR 0080 requires SQLite `try_details` to return a safe Usage value for a spent total; `worker::run` keeps the old scalar before-call refusal while warm's `run_until` uses actual-attempt transport admission.

The design preflight found two SQLite-specific boundaries: the third argument is already the deadline, and `thinkthen_warm` can send during a 256-row `step` before `finalize`. The old `flush` truncated rows by remaining attempts, which would underfill a packed request; the new path relies on actual transport admission and one absolute warm deadline. The Python helper's `fetchall()` returns one error string for a failed aggregate, while scalar row stepping can expose earlier values, so the no-partial-count claim applies only to one aggregate result. Early review of `c2c5b0f4` also found retained tests implicitly counting one send per row. The final source assigns those tests to explicit batch one, unchanged singleton/group behavior or independently pinned packed requests. The subsequent slide failure showed that a test inventory can still miss a cache-identity assumption; the corrected public recipe and separate packed proof now pin both forms. B12a and 0157 landed before this runtime build; their original preflight status remains historical evidence in the linked record.
