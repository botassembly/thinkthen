# 0210: Refuse a backend address that contains the configured key

Status: proposed design on `ticket/0210-protect-known-keys-in-backend-paths`. No runtime file is claimed or changed. Owner: Codex. Register 106 remains open until a reviewed, proven implementation lands. Ian must rule on the dry-run contract change below.

## Evidence

- Starts from: Register 106 in `experiments/284-issue-register/106-token-in-base-path-in-recordings.md` and the independent review recorded in [the preflight](../records/0210-path-secrecy-preflight.md). Main `a09ceb8f` preserves arbitrary base-path bytes. A configured key appearing verbatim in those bytes therefore enters the resolved URL, every successful recording entry for it, plan and status output, and some `Debug` lines. Existing secrecy proofs use a key different from the address and miss the collision.
- Keeps: Legitimate gateway path routing, the complete URL's request digest and folder identity, exact replay checks, `THINKTHEN_API_KEY` as the key channel, and keyless loopback. Do not strip, rewrite, or redact the transport URL or stored entries. Existing recordings made with a collided key remain sensitive; this ticket cannot erase them.
- Changes: when a nonblank configured key occurs as exact contiguous bytes anywhere in the resolved endpoint URL, refuse with one fixed usage sentence before a plan, status line, result, digest, recording access, key send, or network request. Suggested text: `the backend address contains the configured API key; put the key only in THINKTHEN_API_KEY`. Do not include URL or key in the error or its `Debug`. Compare bytes exactly; no shape, length, prefix, percent-decoding, or path-segment heuristic. Checking the entire URL also covers the same known-key collision in a host or port spelling. A short key may match an otherwise innocent address; that conservative refusal is part of the proposed public rule. An absent or blank key does not cause this refusal and keeps existing no-key behavior.
- Pure `Backend::resolve` keeps validating an address without reading the environment. The host edge supplies the known key to one pure URL/key collision check. Every command path performs the check after resolving the final URL and before constructing output or planning a request. Rust `EngineBuilder` checks the final base, model, and explicit or environment-captured key at `build`; other language and database doors that use it inherit the guard. The command's send-time key read must also reject a collision if the value differs from the early read, before transport; the early check protects plans, status, recording setup, and digest work. Confirm the exact host adapter inventory before code.
- A `Debug` value formed before the key is known cannot promise safety by comparison. Withhold the full base URL from `Debug` for raw URL holders (`Url`, CLI arguments/configuration/environment, and the public builder), while retaining explicit public result URL fields after validation. Do not expose a rejected address through a wrapped error. This is separate from changing the transport address.
- Proof: Use a synthetic key/address collision at the compiled command and public builder boundaries. Check no printed sentinel, listener request, recording file or marker; retain exact safe gateway plan, digest, recording and replay behavior. The focused proof is detailed below.
- Defers: Arbitrary token-like path segments not equal to the configured key remain a documented hygiene risk. Old files containing a collided key require separate operator handling; no automatic migration or fixture scan belongs to this design.

## The dry-run decision for Ian

Today `--dry-run` reads no key and emits the exact resolved URL and request digest. A key-free process cannot determine whether independently supplied URL bytes equal its configured key. With arbitrary gateway paths and exact URL plans, it cannot simultaneously keep that rule and guarantee that the configured key is never printed or hashed. **Recommend allowing dry-run to read `THINKTHEN_API_KEY` only for this comparison**, without requiring a key, constructing an Authorization header, making a call, or changing a safe plan's bytes. A collision receives the same fixed refusal before the plan or digest; a safe or keyless plan remains byte-for-byte the same. This amends the sentence “`--dry-run` ... reads no key” in `specification/backends.md`; it must say the key may be inspected solely to prevent disclosure, never printed or sent. Ian can instead retain no-key dry runs, but then must accept either path-blind disclosure risk or a larger change that withholds paths and path-derived digests from all dry-run formats, reducing plan fidelity. No implementation starts until he chooses.

`status` already reads key presence through `Environment::api_key_set`; the proposed guard may inspect its value only for the comparison before either human or JSON status output. The live commands already read it at send time; early comparison adds a read, not a send. Replay/cache-only runs also need the check before URL-bearing output or storage identity work when the key is configured, although they may send nothing. The absolute no-key-output promise in `AGENTS.md` and `specification/backends.md` governs these paths.

## Proof and bounds

Use a synthetic configured key such as `sk-test-path-0210` on a local loopback base `http://127.0.0.1:PORT/v1/sk-test-path-0210`. One compiled-command edge table covers normal `--record`/`--cache`, `--replay`, `--dry-run` for the ordinary and recognize/relate plan shapes, `check --dry-run`, and `status` human/JSON: exact fixed refusal, no sentinel in stdout/stderr/Debug, no listener request, and no new recording file or marker. Use existing loopback and scratch helpers. A Rust public-builder case with an explicit key and that URL proves the library path; the existing secrecy contract test can extend its key/address pair instead of adding another framework. A valid gateway prefix that does not contain the key keeps its exact planned URL, request digest, entry URL, replay, and result output. Keyless dry-run and keyless loopback remain accepted. Pin whether a short key's exact byte collision is refused. Focused tests and strict relevant lint, format, policy, and measured ratchet suffice; no paid or broad stress run.

The preflight names prospective source, test, spec, and documentation claims plus file-size headroom. Claim them on main after design review and Ian's ruling. Register 106's arbitrary path-token hygiene remains separate: the code cannot infer other secrets, and `specification/backends.md` and `specification/recording.md` already warn about that limit. The work plan's “strip the token before a recording is written” is not this ticket's behavior and requires correction by the queue owner after review.
