# 0319: Build and prove the command-line release on this host

Status: landed. Plan: `sdlc/planning/cleanup-2026-09-30.md`, step 8. Issue: `sdlc/issues/2026-09-25-release-and-install-for-0-1.md`, items 1, 2, 11 and 13.

## Outcome

Two offline commands build this host's command-line release files and prove them the way a user meets them. The files are the static command archive, the first-run sample, and a `.sha256` beside each. The proof checks each checksum and the version line. It installs through `install.sh` from a loopback server into a clean prefix. It runs the README's no-key replay block against the unpacked release binary and sends nothing to any backend. Nothing is tagged, released, or published.

It refuses an extra, linked or missing file by name, then checks both checksums before the loopback backend starts. It scans the unpacked binary, runs the command check, and runs `release-workflow installer-smoke DIR`. ## What the build taught us

- The replay entry name covers the backend address. A loopback `THINKTHEN_BASE_URL` makes the demo 27 replay miss with exit 5, so the count cannot come from moving the address. The proxy variables send any `https://` request, the default backend included, to the loopback backend as a `CONNECT`, which it counts.
- With no key, the real binary refuses before any send, and a replay miss sends nothing. The count guards the block's other lines and a future binary that sends without a key.
- A planted network line must not start with `curl `, or the sample-line rule catches it first.
- This host still lacks `x86_64-linux-musl-gcc`. `ring` builds with `CC_x86_64_unknown_linux_musl=clang`, as 0267 recorded. `release.yml` on a GitHub runner is unaffected.
- The nine-family `release-smoke` has not run since this change. It shares `command_check`, so the next `surfaces` run proves its new block finder against today's README.
