# 0207: Give SQLite the full recognize relation result

Status: revised design proposed for fresh review; no product API is authorized by ticket 0206. Owner: Codex. Ian can overturn the SQL spelling and argument behavior before implementation.

## Outcome

An SQLite caller must be able to ask one recognize question with relation rules over the original text and receive the complete entity and relation result. Keep the existing entity-only `thinkthen_recognize` table and row-based `thinkthen_relate` behavior. The new route must use the same public recognize engine call and request bodies as the settled `specification/recognize.md`, including offsets, strengths, full source and target entities, relation thresholds, and no-edge results. Do not emulate recognition with two unrelated model judgments.

- Starts from: Ticket 0206's bounded case-42 comparison and `sdlc/records/2026-09-27-shared-case-gap-audit.md`. `databases/sqlite/src/tables.rs::Recognizer::ask` explicitly rejects relation specs. The standalone `Relater` reads only row ID, name, and kind. On the pre-0167 code checked by 0206, a generic-arm run over case-42 entities produced two relation requests whose states had `entities` and `relation` but no original text; neither body matched the captured case-42 relation request. Its two 0.9 generic edges were not case-42 answers. A direct case-arm attempt with a stripped recognize spec failed after three requests with backend 500; it did not prove an equivalent composition. Pending 0167 replaces the standalone pair planner and its request shape, but still gives it no original text; see the [build preflight](../records/0207-build-preflight.md).
- Keeps: The existing two table-valued functions, their input and error behavior, all nine named relation skips until their shared arms pass, and the 54-case corpus as the only expected-answer source.
- Changes: Add the `thinkthen_recognize_document(body, spec)` scalar defined below. It calls `Engine::recognize_with` once and returns the complete public `Recognized::to_json()` value, including relations when rules were given. Keep both existing table-valued functions and their behavior.
- Proof: Run shared cases `42` through `50` through the installed extension against their own captured arms. Each has one captured request in each of recognition's three dependent phases. Compare the listener's observed three exact bodies in phase order and its count, then the complete JSON result with entity offsets and strengths and directed full-entity edges and probabilities. This does not impose a network-arrival order on requests within a phase when a larger case sends them concurrently. Remove each skip only after its own arm passes. A separate small boundary proves a nondefault relation threshold and an entirely empty relation result, because the nine captured final outputs do not prove those variants. One malformed spec refusal counts zero listener sends. Keep the full-functional route separate from stress.

## Proposed SQL contract for review

`thinkthen_recognize_document(body, spec)` is a volatile, direct-only scalar with exactly two arguments. `body` is the original UTF-8 text. `spec` is either a full version-one JSON question file with a `recognize` member, a bare JSON recognize section wrapped as version one, or an `@file` naming either JSON form under the SQLite process's existing file authority. It does not take comma kinds or another SQL shorthand. Parse the spec with `Recognize::from_json`, preserving its validation and the existing file-versus-inline error mapping. A spec without relation rules is valid and returns the public entity-only object. A spec with rules returns `relations`, including `[]` if no edge passes.

If `body` is SQL NULL, return SQL NULL with zero sends, without parsing `spec`. If a non-NULL `body` has the wrong SQL type, a NUL byte, or invalid UTF-8, return `usage` before any send. Apply the same rules to `spec` after validating `body`: SQL NULL returns SQL NULL; a number, BLOB, NUL byte, or invalid UTF-8 returns `usage`. An empty or malformed JSON spec returns the existing JSON `usage` message. A valid JSON spec with an invalid recognize rule retains `Recognize::from_json`'s `usage` error inline or the existing file `local` mapping. File open and read failures retain existing `local` behavior. No parser or worker begins after a NULL or invalid argument.

One SQL call makes one public `Engine::recognize_with` call. Recognition may send multiple ordered backend requests for names, kinds and relation pairs. The scalar returns exactly `Recognized::to_json()` as SQL TEXT, without an envelope or SQL projection. `relations` is absent when no rule was supplied and is `[]` when rules were supplied but none passed, as `specification/recognize.md` states. SQL callers may use `json_extract` on that text.
