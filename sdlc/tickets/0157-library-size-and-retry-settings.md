# 0157: Expose request size and retry counts through the libraries

Status: design accepted 2026-09-27 after fresh independent review at `5f3b943e`. Owner: Codex. Implementation waits for corrected 0149, 0154 and 0155 to land and needs exact runtime claims.

## Outcome and authority

A Rust, Python, TypeScript, Ruby, R or C caller can set the request-byte ceiling that the command calls `--max-request-bytes` and read how many of its actual sends were retries. Each SQL host can set the byte ceiling in its existing settings style where it affects a relation or other split plan. The size limits requests and never changes a single unsplittable question into a smaller request. `requests_sent` continues to count first sends and retries together; `retries` is its subset.

Ticket 0154 and ADR 0051 settle the 96,000-byte default, positive integer rule, smaller-of profile limit and one halving rule. Ticket 0155 and ADR 0052 settle the default of three retries, per-address backoff, `requests_sent` meaning and separate retry count. Ticket 0148 supplies the existing builder and binding settings maps. Ticket 0149 supplies the SQL settings maps and their send budget. This ticket propagates the two settled values; it does not reopen batching, backoff or budget semantics. Ian can overturn the accepted defaults and shape through the owning ADRs.

## Design

1. **One Rust size setter.** Add `EngineBuilder::max_request_bytes(usize) -> Result<Self, Error>`; zero is `Usage` with the same whole-number rule as the command. `EngineBuilder::from_env()` reads `THINKTHEN_MAX_REQUEST_BYTES` with the command's spelling and validation, then explicit setter values override it. A bare builder uses 96,000. The builder passes the resolved value to 0154's `Backend::with_request_size`; a runtime profile's `max_request_bytes` lowers it and cannot raise it. `record`, `replay` and the cache use the resulting request bodies and digests unchanged. A request that cannot split still goes alone; the setting acts on the existing batch/relation plan limit and the later B12 library batching paths, not on arbitrary single-document length. Declare the setter in ticket 0084 and check it through the built public inventory.
2. **One row per binding.** Python `tt.Engine(max_request_bytes=)`, TypeScript `new tt.Engine({ maxRequestBytes })`, Ruby `Engine.new(max_request_bytes:)`, R `tt_engine(max_request_bytes = )`, and C `thinkthen_engine_new_with` key `"max_request_bytes"` call the Rust setter from each binding's 0148 settings map. Their module-level convenience calls keep their one environment-built engine; an explicit engine value overrides the environment. Host code checks integer representation only and never implements a second byte limit, splitter or profile precedence. Rust's normal builder setter and `Engine::from_env()` cover the Rust library and Polars adapter. The C settings JSON remains closed and rejects a duplicate or unknown key. This row is not a new key channel or a new function argument on every judgment.
3. **SQL size where it acts.** Add `SET thinkthen_max_request_bytes` in DuckDB, `thinkthen.max_request_bytes` in PostgreSQL, and `thinkthen_max_request_bytes(n)` before first use in SQLite, using the same validated builder setter after 0149's existing SQL values. DuckDB's engine key includes the size, so two sessions with different sizes cannot share the wrong engine; warm captures the caller's size with the other settings through 0201's proved aggregate context. PostgreSQL's plan key includes it; SQLite's process engine stores it before construction. `RESET` or an unset SQL value falls back to `EngineBuilder::from_env()` and then 96,000. These SQL forms do not add an address/key option and do not change their current process request-total setting. The SQL setting affects relation and any other operation whose engine plan splits under request bytes; a lone scalar call still sends its one request. A profile's smaller ceiling wins on SQL too.
4. **Expose one retry count, do not recompute it.** Add `Counters::retries() -> u64` from 0155's engine counter snapshot. Keep `requests_sent` counting every attempt, including retries, and preserve old usage-file reads as zero retries under ADR 0052. Extend each library's existing usage result with one `retries` member in its native shape: Python dictionary, TypeScript object/type, Ruby hash, R named usage value and C usage JSON. Rust reads the accessor directly. No wrapper subtracts first sends to guess retries, and no row's `Details` or bare answer grows a retry field. The SQL usage result remains as already ruled; exposing retries there would need a separate SQL contract and is deferred.
5. **Pages and ratchets.** Add the library and SQL Request size cells and the library retry-count usage note to `specification/settings.md`, its checked source `sdlc/scripts/settings`, the six library READMEs and three SQL READMEs. Keep the accepted 0154 default and profile precedence. Add one `conformance/settings.json` row whose fixed request text and recorded loopback send count distinguish a lowered byte size from the 96,000-byte default, and route it through the existing settings runners. Do not duplicate the generated request-body count in host unit tests. Update the public API inventory, exact ratchets and source-size report only for touched files. No new dependency or test-only export.

## Small outside-in proof and build order

First run a Rust consumer or loopback relation with a fixed input whose expected request count and body digests were recorded independently of the new setter. At a small positive size it splits; at the default it does not. A profile lower than the setting still wins. `0` and malformed `THINKTHEN_MAX_REQUEST_BYTES` fail before a send. One shared settings case exercises the same behavior through each host's settings parser, with each runner reporting an unsupported form honestly. The host-focused checks verify that the value reaches Rust; they do not reimplement the relation planner or repeat a load campaign.

For retry visibility, a loopback first answers 503 once and then 200 with `max_retries=1`; the public `Counters` reports `requests_sent=2`, `retries=1`. A no-retry answer reports `1/0`, and replay reports `0/0`. One focused native usage assertion per binding proves field shape and value; there is no repeated timed backoff campaign. SQL focused checks confirm their size spelling and one changed relation request count, with DuckDB's installed C++ artifact version pinned by 0201. Use the accepted 0149 same-session warm proof rather than rerunning it solely for this size row unless the changed key makes it fail.

Build from landed 0155, 0154 and 0149 in that order. Add the public setter and counter accessor first, with focused Rust format, strict feature Clippy, policy and source-size checks. Add binding rows in the existing maps and run each touched port's small settings/usage proof. Then add SQL size entries and the one shared selected case. Run the settings checker and focused SQL package/check only where source changed. Preserve unrelated 0205 routine-gate results while their inputs are unchanged; take one integration checkpoint for the related settings batch after review. Do not run full old conformance, stress, repeated saturation or paid calls per slice. Stop and amend the design if 0154 or 0155 land a different public shape, if the size does not act on a named SQL verb, or if 0149's aggregate caller settings remain unproved.
