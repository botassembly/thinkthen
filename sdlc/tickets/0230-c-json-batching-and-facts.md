# 0230: Batch the C JSON door and return call facts

Status: technical design ACCEPT at `23f905ad` from independent native review; public choices below remain pending coordinator/Ian decision. Owner: Codex. Preparation pins main `cbaa5fbd` and accepted, unlanded Rust design ADR 0089 at `a713e462`; the unreviewed 0212 source at `e306674f` is a prerequisite, not a completed product. No 0230 runtime work or register closure is claimed.

## Outcome and retained contract

B12b in [the batching issue](../issues/2026-09-26-batching-design.md) gives the C JSON door the Rust library's default maximal batching, explicit batch size, context and per-call facts. Reuse Rust's planner, limits, one eligible 413 split, ordered stop, cache/replay identity, exact one-record bytes, question descriptions and declared option order. Keep the ABI as JSON strings. Do not add C result structs or description arrays. The typed C entry points, the `thinkthen_answer` layout, six error codes, process `{"usage":true}` response and ordinary `NULL` failure signal stay as they are. The C door's `decide`/`choose` null is a successful value; a malformed or missing answer is a failure. Tag `[]` is a valid answer; annotate's failed member retains its explicit marker.

ADR 0089 §Proposed decision 4 is inherited: `Error::facts()` holds a frozen report on **started eager failures**, including a zero-send cancellation, and is absent before a call starts. For lazy batches, the terminal error and `Batch::facts()` hold the same report after workers join. B12b must expose these facts rather than discard them while converting to C. This includes failed sends and joined replies; `thinkthen_usage()` process totals cannot stand in for one call's facts. The [preflight](../records/0230-c-batching-preflight.md) maps the current door and the [design handoff](../records/0230-design-review.md) names the public choice.

## Recommended C JSON contract for review

Technical review accepted this coherent route, not its publication. The pending outward choices are the successful C `{value,facts}` migration from bare JSON, the request's `call` spelling, and the additive borrowed failure-facts accessor. The proposed public Rust `details_many_with` stopping bridge and record-detail conversion also need their own public-surface approval and implementation. Root will present a concrete C/API migration choice; do not begin runtime or treat the proposed fields as shipped before that decision and the reviewed 0212 landing.

1. Keep the current request's question-file fields. Add a distinct `"call":{"batch":10,"context":"..."}` object for eligible many-record operations, with `"batch":"max"` as the explicit maximal spelling. A top-level question-file `batch` is already calibration identity and must not be stolen as the call override. Closed parsing refuses unknown or ill-typed call keys before sending. The call override outranks the engine constructor/environment default, which outranks the saved question's batch, then maximal default. `context` is nonblank shared evidence for supported text-record planners; it changes request digest, not question digest, and is refused for single-document, structured, find, recognize and relate routes that cannot use it. `thinkthen_engine_new_with({"batch":...})` captures the engine default, overriding `THINKTHEN_BATCH`; an environment-only engine uses the environment. Review the exact JSON spelling before publishing it. For decide/choose/score/tag, retain `"evidence":"..."` for one document and add `"records":["...",...]` for a many-record call; exactly one of these inputs is present. The many-record value is an ordered array of the corresponding single-document values, including successful nulls and empty tag arrays. All rows in one C call share the complete question, options, descriptions and order. This does not add the command's dynamic per-row question grammar. **Do not route dynamic C choose/tag through 0212's typed `choose_many`/`tag_many`: their `Choice` labels are compile-time types.** Use the stopping dynamic-details bridge in point 5 for all four new record arrays.
2. On a **successful asking call**, return `{"value":<the current bare JSON answer>,"facts":<one call's facts>}`. The existing `"details":true` object becomes `value`; do not flatten or regenerate its fields. Facts contain `records`, `requests_sent`, `cache_answers`, `seconds`, optional `input_tokens`, `output_tokens` and `model`, using ADR 0089's absence rules. No provider request retrieves facts. Keep `{"usage":true}` as its existing direct process-counter object because it is not an asking call. This changes the successful C JSON body. Existing callers that parse a bare answer must update; the schema, corpus, header, examples and direct C consumers must change together. Do not claim wire compatibility for those callers.
3. On **failure**, retain `NULL` and the current code, message and retryability accessors. Add `thinkthen_error_facts_json(engine) -> const char *`, returning the last failure's JSON facts on the calling thread and engine, or `NULL` when that failure has no started-call facts or none exists. It is a borrowed pointer with the same replacement, engine-free and null-engine build-slot lifetime as `thinkthen_error_message`; callers do not free it. Preserve `Error::facts()` in `Failure`/`Last` when converting an engine error. Parser and constructor refusals have no facts. This is an additive symbol, not a new model call. A successful call still does not clear the last failure, so callers read it only after a `NULL` return, as with the current code accessor. The alternative of returning a non-NULL `{error,facts}` object would make existing `if (answer == NULL)` callers treat a failure as success and would discard the current failure signal. Reject that alternative unless Ian expressly changes the ABI contract.
4. Materialized `records` and `units` arrays stay owned by the C parser. Exhaust Rust stopping `Batch` iterators before reading final facts. The four new decide/choose/score/tag record arrays use the bridge below; existing filter/rank/annotate use their existing or 0212-adjusted routes. Return one ordered result array on success. A stopped or failed call still returns `NULL`; no partial success array escapes. Retain the inherited started-failure facts through the accessor. Recognize's multi-step planner and find/relate's candidate planners remain theirs; their `Call<T>` facts still wrap the successful JSON reply. `batch 1` without context must preserve each old request body/digest and replay identity.
5. **New reviewed Rust prerequisite, not part of accepted 0212.** Propose `Engine::details_many_with<'a, I, Q: DetailQuestion + ?Sized>(&'a self, question: &'a Q, records: I, options: CallOptions<'a>) -> Batch<'a, Row<I::Item, Details>>` where `I: IntoIterator + 'a` and `I::Item: Evidence`, plus a no-options sibling only if the public API review warrants it. The source must validate decide/banded/choose/tag/score kinds, accept a runtime `Question` from `Question::from_json`, and use the same private `decisions` planner, one-split adapter, stop, joined workers and call-scoped facts as 0212; do not loop over `details_with`. Each successful logical row owns its **whole original input**, not only the evidence selected from it, and a complete record `Details`. Its serialized `thinkthen.result/1` object includes `input`, exact request digest, per-row attempt/usage share, declared-order probabilities, question digest and `meta.batch` when the row rode in a multi-record batch, a split half or a contextual batch. `meta.batch` carries setting, member count, one-based position, closure reason, whole-batch usage and attempts, and split flag where applicable. Applicable `meta.profile_warning`, `meta.batch_warning` and `meta.context_sha256` follow [the existing record-details contract](../../specification/result.md); their absence follows that contract too. The current `Details::of` writes a **single-document** row with no input, batch warning or context digest, so merely calling it on each member is insufficient. `public/batch/planned.rs::Packet.detail` is populated only when an observer is installed; the new conversion must retain bounded answered-member data and construct the record payload even with no user observer. Share the existing `result_json::decision_with_batch` writer and its profile-aware digest instead of a C-only serializer. Convert the raw dynamic `Judgment` to bare JSON for `records` without details, avoiding any `Choice` conversion. With `"records"` and `"details":true` on these four verbs, `value` is an ordered array of full `thinkthen.result/1` record-detail objects, each with its normal `value`; absent details yields an array of bare values. A failed logical row yields the earlier successful iterator rows then one terminal error with frozen facts; the C door returns `NULL`, not a partial array. The bridge must not inherit 0222's continue-after-row-error rule. Use one shared `Details::of_member` conversion for the answered member; inspect proposed ADR 0094 at `fb58010a` for reuse, but its proposed constructor alone does not specify this C record shape and it is unimplemented and pending Ian's separate SQL/public API decision. Review this **new public Rust method** and any shared private constructor as a distinct prerequisite before 0230 code; do not silently widen the accepted 0212 candidate or disturb its annotation work.

## Small proof and integration

Use one listener table through `thinkthen_call[_opts]`: a three-record default/max call versus `batch 1` checks exact bodies, digest, request count and returned facts; runtime choose labels/descriptions and tag order check the dynamic route; a profile hard limit versus the soft singleton exception and one 413 split check retained planner boundaries. One success-null row, tag-empty row and failed-answer row distinguish values from failure. For `records` plus `details:true`, the same captured multi-record reply checks each `value[i].input` against the **whole original** array element, `value[i].value`, question digest, exact captured request digest, `meta.batch` member count/position/whole-batch counts, and outer call facts. A selected mismatched saved profile/batch with shared context checks the applicable profile and batch warnings and the SHA-256 of exact context bytes; a no-context `batch 1` row checks those fields are absent when the record-details contract says so. The shared result-schema/type corpus accepts the full record-detail shape and rejects an object missing `input` or carrying malformed batch/context metadata. A failed middle row yields `NULL` and **no** partial JSON despite earlier good rows. One later-record refusal after an earlier sent batch must return `NULL`, unchanged code/message/retryability and nonempty failure facts; a first-record local refusal sends nothing and has the appropriate started-call facts only if Rust marks the call started. Another engine/thread's last failure must not replace the accessor pointer. Compare the previous single-document bare value under `value`, including `details:true`, with the shared C/CLI fixture; test the wrapper and failure accessor separately. Keep the existing `{"usage":true}` byte contract. Replace any old choose-batch rejection assertion only if it exists in the C route. One packaged C driver proves the shipped header/symbol and JSON ownership. Do not repeat B12a's full planner matrix or 0226's native panic campaign.

0212 must land and compile first. The dynamic stopping-details bridge above also needs independent public API review and implementation before the C records route can be built. ADR 0094's recoverable SQL outcome cannot substitute for it. ADR 0089 fixes facts, but its pending caller-owned `Max` iterator pause is a separate Rust choice. The C parser already materializes JSON arrays before calling the iterator, so the C design does not need a second host iterator rule; the implementation must still follow the final 0212 planner. The exact source and test inventory is in the preflight. No paid call or broad surface gate is part of this design draft.

## Evidence

- Starts from: B12b, ADR 0089's successful and started-failure facts, current C JSON/error ABI at main `cbaa5fbd`, and the unlanded 0212 source at `e306674f`.
- Keeps: ten verb values and null/error distinctions, `NULL` failure and existing accessors, process usage, typed C functions, loader/error lifetimes and exact `batch 1` identity.
- Changes: proposed call options, automatic success facts wrapper, additive failure-facts accessor, a separately reviewed dynamic stopping-details Rust bridge, batch planning through Rust and corresponding shared schema/corpus/docs.
- Proof: one outside-in listener table, exact one-record bytes, success/null/failure facts, unchanged old error handling, closed JSON shapes and one installed C driver.
- Defers: other language doors and SQL per-call facts to their B12c–B13e owners; 0212 implementation, the new dynamic bridge review/build and the separate iterator choice remain prerequisites. No product gap closes from preparation.

## What preparation taught us

The existing C `NULL` signal and thread-scoped `Last` table can carry started-failure facts without changing error control flow. A second C accessor is not a second model call. The current door's bare-success contract still makes automatic success facts an outward JSON change; review its exact spelling and migration evidence. A top-level `batch` belongs to the saved question, so a separate call-options object avoids changing calibration identity. The first review found that dynamic native labels cannot route through compile-time `Choice` and that typed bulk rows do not supply `Details`; a shared dynamic stopping bridge and an explicit records-detail schema are required. The second review found that naming `Details` was still insufficient: its current serializer is a single-document shape, and the bulk packet's detail exists only for observers. Preparation must trace every applicable grammar combination and the complete serialized metadata from its producer, not just the outer carrier and request identity. This section records reviewed preparation, not a completed build.
