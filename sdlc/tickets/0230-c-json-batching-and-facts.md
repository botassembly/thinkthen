# 0230: Batch the C JSON door and return call facts

Status: proposed design for independent review. Owner: Codex. Preparation pins main `cbaa5fbd` and accepted, unlanded Rust design ADR 0089 at `a713e462`; the unreviewed 0212 source at `e306674f` is a prerequisite, not a completed product. No 0230 runtime work or register closure is claimed.

## Outcome and retained contract

B12b in [the batching issue](../issues/2026-09-26-batching-design.md) gives the C JSON door the Rust library's default maximal batching, explicit batch size, context and per-call facts. Reuse Rust's planner, limits, one eligible 413 split, ordered stop, cache/replay identity, exact one-record bytes, question descriptions and declared option order. Keep the ABI as JSON strings. Do not add C result structs or description arrays. The typed C entry points, the `thinkthen_answer` layout, six error codes, process `{"usage":true}` response and ordinary `NULL` failure signal stay as they are. The C door's `decide`/`choose` null is a successful value; a malformed or missing answer is a failure. Tag `[]` is a valid answer; annotate's failed member retains its explicit marker.

ADR 0089 §Proposed decision 4 is inherited: `Error::facts()` holds a frozen report on **started eager failures**, including a zero-send cancellation, and is absent before a call starts. For lazy batches, the terminal error and `Batch::facts()` hold the same report after workers join. B12b must expose these facts rather than discard them while converting to C. This includes failed sends and joined replies; `thinkthen_usage()` process totals cannot stand in for one call's facts. The [preflight](../records/0230-c-batching-preflight.md) maps the current door and the [design handoff](../records/0230-design-review.md) names the public choice.

## Recommended C JSON contract for review

1. Keep the current request's question-file fields. Add a distinct `"call":{"batch":10,"context":"..."}` object for eligible many-record operations, with `"batch":"max"` as the explicit maximal spelling. A top-level question-file `batch` is already calibration identity and must not be stolen as the call override. Closed parsing refuses unknown or ill-typed call keys before sending. The call override outranks the engine constructor/environment default, which outranks the saved question's batch, then maximal default. `context` is nonblank shared evidence for supported text-record planners; it changes request digest, not question digest, and is refused for single-document, structured, find, recognize and relate routes that cannot use it. `thinkthen_engine_new_with({"batch":...})` captures the engine default, overriding `THINKTHEN_BATCH`; an environment-only engine uses the environment. Review the exact JSON spelling before publishing it. For decide/choose/score/tag, retain `"evidence":"..."` for one document and add `"records":["...",...]` for a many-record call; exactly one of these inputs is present. The many-record value is an ordered array of the corresponding single-document values, including successful nulls and empty tag arrays. Use 0212's typed bulk methods, so all rows in one C call share the complete question, options, descriptions and order. This does not add the command's dynamic per-row question grammar.
2. On a **successful asking call**, return `{"value":<the current bare JSON answer>,"facts":<one call's facts>}`. The existing `"details":true` object becomes `value`; do not flatten or regenerate its fields. Facts contain `records`, `requests_sent`, `cache_answers`, `seconds`, optional `input_tokens`, `output_tokens` and `model`, using ADR 0089's absence rules. No provider request retrieves facts. Keep `{"usage":true}` as its existing direct process-counter object because it is not an asking call. This changes the successful C JSON body. Existing callers that parse a bare answer must update; the schema, corpus, header, examples and direct C consumers must change together. Do not claim wire compatibility for those callers.
3. On **failure**, retain `NULL` and the current code, message and retryability accessors. Add `thinkthen_error_facts_json(engine) -> const char *`, returning the last failure's JSON facts on the calling thread and engine, or `NULL` when that failure has no started-call facts or none exists. It is a borrowed pointer with the same replacement, engine-free and null-engine build-slot lifetime as `thinkthen_error_message`; callers do not free it. Preserve `Error::facts()` in `Failure`/`Last` when converting an engine error. Parser and constructor refusals have no facts. This is an additive symbol, not a new model call. A successful call still does not clear the last failure, so callers read it only after a `NULL` return, as with the current code accessor. The alternative of returning a non-NULL `{error,facts}` object would make existing `if (answer == NULL)` callers treat a failure as success and would discard the current failure signal. Reject that alternative unless Ian expressly changes the ABI contract.
4. Materialized `records` and `units` arrays stay owned by the C parser. Use the Rust bulk methods and exhaust their `Batch` iterators before reading final facts. This includes the four newly exposed decide/choose/score/tag record arrays alongside filter/rank/annotate. Return one ordered result array on success. A stopped or failed call still returns `NULL`; no partial success array escapes. Retain the inherited started-failure facts through the accessor. Recognize's multi-step planner and find/relate's candidate planners remain theirs; their `Call<T>` facts still wrap the successful JSON reply. `batch 1` without context must preserve each old request body/digest and replay identity.

## Small proof and integration

Use one listener table through `thinkthen_call[_opts]`: a three-record default/max call versus `batch 1` checks exact bodies, digest, request count and returned facts; mixed choose labels/descriptions and tag order check no question fusion; a profile hard limit versus the soft singleton exception and one 413 split check retained planner boundaries. One success-null row, tag-empty row and failed-answer row distinguish values from failure. One later-record refusal after an earlier sent batch must return `NULL`, unchanged code/message/retryability and nonempty failure facts; a first-record local refusal sends nothing and has the appropriate started-call facts only if Rust marks the call started. Another engine/thread's last failure must not replace the accessor pointer. Compare the previous bare value under `value`, including `details:true`, with the shared C/CLI fixture; test the wrapper and failure accessor separately. Keep the existing `{"usage":true}` byte contract. Use the shared valid/invalid question-file and result-schema corpus; replace any old choose-batch rejection assertion only if it exists in the C route. One packaged C driver proves the shipped header/symbol and JSON ownership. Do not repeat B12a's full planner matrix or 0226's native panic campaign.

0212 must land and compile first. Its accepted ADR fixes facts, but its pending caller-owned `Max` iterator pause is a separate Rust choice. The C parser already materializes JSON arrays before calling the iterator, so the C design does not need a second host iterator rule; the implementation must still follow the final 0212 planner. The exact source and test inventory is in the preflight. No paid call or broad surface gate is part of this design draft.

## Evidence

- Starts from: B12b, ADR 0089's successful and started-failure facts, current C JSON/error ABI at main `cbaa5fbd`, and the unlanded 0212 source at `e306674f`.
- Keeps: ten verb values and null/error distinctions, `NULL` failure and existing accessors, process usage, typed C functions, loader/error lifetimes and exact `batch 1` identity.
- Changes: proposed call options, automatic success facts wrapper, additive failure-facts accessor, batch planning through Rust and corresponding shared schema/corpus/docs.
- Proof: one outside-in listener table, exact one-record bytes, success/null/failure facts, unchanged old error handling, closed JSON shapes and one installed C driver.
- Defers: other language doors and SQL per-call facts to their B12c–B13e owners; 0212 implementation and its separate iterator choice remain prerequisites. No product gap closes from preparation.

## What preparation taught us

The existing C `NULL` signal and thread-scoped `Last` table can carry started-failure facts without changing error control flow. A second C accessor is not a second model call. The current door's bare-success contract still makes automatic success facts an outward JSON change; review its exact spelling and migration evidence. A top-level `batch` belongs to the saved question, so a separate call-options object avoids changing calibration identity. This section records preparation, not a completed build.
