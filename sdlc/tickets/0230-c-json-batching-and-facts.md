# 0230: Batch the C JSON door and return call facts

Status: technical design ACCEPT at `23f905ad` from independent native review. Ian approved the recommended C `{value,facts}` success JSON, `NULL` failure plus facts accessor, `call` options, and public dynamic stopping-details Rust bridge on 2026-09-28, as recorded in the work plan. Owner: Codex. Rust 0212 landed at `737a762e`; 0230 remains a separate build and does not close B12b until reviewed and landed.

## Outcome and retained contract

B12b in [the batching issue](../issues/2026-09-26-batching-design.md) gives the C JSON door the Rust library's default maximal batching, explicit batch size, context and per-call facts. Reuse Rust's planner, limits, one eligible 413 split, ordered stop, cache/replay identity, exact one-record bytes, question descriptions and declared option order. Keep the ABI as JSON strings. Do not add C result structs or description arrays. The typed C entry points, the `thinkthen_answer` layout, six error codes, process `{"usage":true}` response and ordinary `NULL` failure signal stay as they are. The C door's `decide`/`choose` null is a successful value; a malformed or missing answer is a failure. Tag `[]` is a valid answer; annotate's failed member retains its explicit marker.

ADR 0089 §Proposed decision 4 is inherited: `Error::facts()` holds a frozen report on **started eager failures**, including a zero-send cancellation, and is absent before a call starts. For lazy batches, the terminal error and `Batch::facts()` hold the same report after workers join. B12b must expose these facts rather than discard them while converting to C. This includes failed sends and joined replies; `thinkthen_usage()` process totals cannot stand in for one call's facts. The [preflight](../records/0230-c-batching-preflight.md) maps the current door and the [design handoff](../records/0230-design-review.md) names the public choice.

## Approved C JSON contract

Technical review accepted this coherent route, and Ian approved its outward choices. The successful C `{value,facts}` migration, request `call` spelling, borrowed failure-facts accessor, and public Rust `details_many_with` stopping bridge are authorized for implementation. Their approval is not a claim that the API has shipped.

1. Keep the current request's question-file fields. Add a distinct `"call":{"batch":10,"context":"..."}` object for eligible many-record operations, with `"batch":"max"` as the explicit maximal spelling. A top-level question-file `batch` is already calibration identity and must not be stolen as the call override. Closed parsing refuses unknown or ill-typed call keys before sending. The call override outranks the engine constructor/environment default, which outranks the saved question's batch, then maximal default. `context` is nonblank shared evidence for supported text-record planners; it changes request digest, not question digest, and is refused for single-document, structured, find, recognize and relate routes that cannot use it. `thinkthen_engine_new_with({"batch":...})` captures the engine default, overriding `THINKTHEN_BATCH`; an environment-only engine uses the environment. Ian approved this JSON spelling for the 0230 build. For decide/choose/score/tag, retain `"evidence":"..."` for one document and add `"records":["...",...]` for a many-record call; exactly one of these inputs is present. The many-record value is an ordered array of the corresponding single-document values, including successful nulls and empty tag arrays. All rows in one C call share the complete question, options, descriptions and order. This does not add the command's dynamic per-row question grammar. **Do not route dynamic C choose/tag through 0212's typed `choose_many`/`tag_many`: their `Choice` labels are compile-time types.** Use the stopping dynamic-details bridge in point 5 for all four new record arrays.
2. On a **successful asking call**, return `{"value":<the current bare JSON answer>,"facts":<one call's facts>}`. The existing `"details":true` object becomes `value`; do not flatten or regenerate its fields. Facts contain `records`, `requests_sent`, `cache_answers`, `seconds`, optional `input_tokens`, `output_tokens` and `model`, using ADR 0089's absence rules. No provider request retrieves facts. Keep `{"usage":true}` as its existing direct process-counter object because it is not an asking call. This changes the successful C JSON body. Existing callers that parse a bare answer must update; the schema, corpus, header, library C example and C test consumers change in this ticket. Seven marketing-owned site C examples still parse the bare answer and remain a release-priority migration in [the site C examples issue](../issues/2026-09-28-site-c-examples-need-json-value-wrapper.md). Do not claim all direct consumers or public release compatibility until that issue closes.
3. On **failure**, retain `NULL` and the current code, message and retryability accessors. Add `thinkthen_error_facts_json(engine) -> const char *`, returning the last failure's JSON facts on the calling thread and engine, or `NULL` when that failure has no started-call facts or none exists. It is a borrowed pointer with the same replacement, engine-free and null-engine build-slot lifetime as `thinkthen_error_message`; callers do not free it. Preserve `Error::facts()` in `Failure`/`Last` when converting an engine error. Parser and constructor refusals have no facts. This is an additive symbol, not a new model call. A successful call still does not clear the last failure, so callers read it only after a `NULL` return, as with the current code accessor. The alternative of returning a non-NULL `{error,facts}` object would make existing `if (answer == NULL)` callers treat a failure as success and would discard the current failure signal. Reject that alternative unless Ian expressly changes the ABI contract.
4. Materialized `records` and `units` arrays stay owned by the C parser. Exhaust Rust stopping `Batch` iterators before reading final facts. The four new decide/choose/score/tag record arrays use the bridge below; existing filter/rank/annotate use their existing or 0212-adjusted routes. Return one ordered result array on success. A stopped or failed call still returns `NULL`; no partial success array escapes. Retain the inherited started-failure facts through the accessor. Recognize's multi-step planner and find/relate's candidate planners remain theirs; their `Call<T>` facts still wrap the successful JSON reply. `batch 1` without context must preserve each old request body/digest and replay identity.
5. **Approved Rust prerequisite, separate from accepted 0212.** Implement `Engine::details_many_with<'a, I, Q: DetailQuestion + ?Sized>(&'a self, question: &'a Q, records: I, options: CallOptions<'a>) -> Batch<'a, Row<I::Item, Details>>` where `I: IntoIterator + 'a` and `I::Item: Evidence + Serialize`, with an additive no-options sibling. The coordinator accepted this whole-input serialization bound as a necessary refinement for fresh code/API review. The source must validate decide/banded/choose/tag/score kinds, accept a runtime `Question` from `Question::from_json`, and use the same private `decisions` planner, one-split adapter, stop, joined workers and call-scoped facts as 0212; do not loop over `details_with`. Each successful logical row owns its **whole original input**, not only the evidence selected from it, and a complete record `Details`. Its serialized `thinkthen.result/1` object includes `input`, exact request digest, per-row attempt/usage share, declared-order probabilities, question digest and `meta.batch` when the row rode in a multi-record batch, a split half or a contextual batch. `meta.batch` carries setting, member count, one-based position, closure reason, whole-batch usage and attempts, and split flag where applicable. Applicable `meta.profile_warning`, `meta.batch_warning` and `meta.context_sha256` follow [the existing record-details contract](../../specification/result.md); their absence follows that contract too. The current `Details::of` writes a **single-document** row with no input, batch warning or context digest, so merely calling it on each member is insufficient. `public/batch/planned.rs::Packet.detail` is populated only when an observer is installed; the new conversion must retain bounded answered-member data and construct the record payload even with no user observer. Share the existing `result_json` writer and its profile-aware digest, adding an explicit request-list entry point for split parent plus half metadata instead of a C-only serializer. Convert the raw dynamic `Judgment` to bare JSON for `records` without details, avoiding any `Choice` conversion. With `"records"` and `"details":true` on these four verbs, `value` is an ordered array of full `thinkthen.result/1` record-detail objects, each with its normal `value`; absent details yields an array of bare values. A failed logical row yields the earlier successful iterator rows then one terminal error with frozen facts; the C door returns `NULL`, not a partial array. The bridge must not inherit 0222's continue-after-row-error rule. Use one shared `Details::of_member` conversion for the answered member; inspect proposed ADR 0094 at `fb58010a` for reuse, but its proposed constructor alone does not specify this C record shape and it is unimplemented and pending Ian's separate SQL/public API decision. The fresh 0230 code/API review must inspect this new public Rust method and its shared private conversion; the accepted 0212 annotation work remains intact.

## Small proof and integration

Use one listener table through `thinkthen_call[_opts]`: a three-record default/max call versus `batch 1` checks exact bodies, digest, request count and returned facts; runtime choose labels/descriptions and tag order check the dynamic route; a profile hard limit versus the soft singleton exception and one 413 split check retained planner boundaries. One success-null row, tag-empty row and failed-answer row distinguish values from failure. For `records` plus `details:true`, the same captured multi-record reply checks each `value[i].input` against the **whole original** array element, `value[i].value`, question digest, exact captured request digest, `meta.batch` member count/position/whole-batch counts, and outer call facts. A selected mismatched saved profile/batch with shared context checks the applicable profile and batch warnings and the SHA-256 of exact context bytes; a no-context `batch 1` row checks those fields are absent when the record-details contract says so. The shared result-schema/type corpus accepts the full record-detail shape and rejects an object missing `input` or carrying malformed batch/context metadata. A failed middle row yields `NULL` and **no** partial JSON despite earlier good rows. One later-record refusal after an earlier sent batch must return `NULL`, unchanged code/message/retryability and nonempty failure facts; a first-record local refusal sends nothing and has the appropriate started-call facts only if Rust marks the call started. Another engine/thread's last failure must not replace the accessor pointer. Compare the previous single-document bare value under `value`, including `details:true`, with the shared C/CLI fixture; test the wrapper and failure accessor separately. Keep the existing `{"usage":true}` byte contract. Replace any old choose-batch rejection assertion only if it exists in the C route. One packaged C driver proves the shipped header/symbol and JSON ownership. Do not repeat B12a's full planner matrix or 0226's native panic campaign.

0212 landed and compiled first. The approved dynamic stopping-details bridge and C records route are built together in 0230; both await fresh code/API review. ADR 0094's recoverable SQL outcome cannot substitute for it. ADR 0089 fixes facts, but its pending caller-owned `Max` iterator pause is a separate Rust choice. The C parser already materializes JSON arrays before calling the iterator, so the C design does not need a second host iterator rule; the implementation must still follow the final 0212 planner. The exact source and test inventory is in the preflight. No paid call or broad surface gate is part of this build.

## What preparation taught us

The existing C `NULL` signal and thread-scoped `Last` table carry started-failure facts without changing error control flow. A second C accessor is not a second model call. The current door's bare-success contract still makes automatic success facts an outward JSON change; review its exact spelling and migration evidence. A top-level `batch` belongs to the saved question, so a separate call-options object avoids changing calibration identity. The first review found that dynamic native labels cannot route through compile-time `Choice` and that typed bulk rows do not supply `Details`; a shared dynamic stopping bridge and an explicit records-detail schema are required. The second review found that naming `Details` was still insufficient: its current serializer is a single-document shape, and the bulk packet's detail exists only for observers. Preparation must trace every applicable grammar combination and the complete serialized metadata from its producer, not just the outer carrier and request identity. This section records reviewed preparation, not a completed build.

## What the build taught us

The Rust details bridge must retain the answered member independently of an observer: the old packet detail was observer-only. Serializing an `Evidence` item alone loses fields when evidence selects a part of a structured input, so the public item bound includes `Serialize` and the result writer stores the whole original input. A refused parent 413 digest must be passed explicitly to that shared writer with the answering half; the first split proof found that the typed accessor had both while JSON kept only the half. The focused split regression turned green after the writer accepted the full request list.

The C error slot already had the required engine/thread lifetime, so failure facts extend that slot without a second response channel. C success wraps the old value, while the process usage request remains direct. The preexisting C/CLI byte and type fixtures described one-record requests; selecting `batch 1` in those fixtures preserves their recorded identities while separate C listener proof checks maximal packing, explicit one-record calls, context metadata, failure facts and zero-send refusal. No test was deleted or consolidated. The held-input settings test now checks that a batch-one caller waits for a held request; it no longer claims two requests are concurrently issued by one synchronous iterator.

Fresh High review of source `360f4e7a` found two correction points. A 413 split creates new half requests whose planner closure reads `end`; the detail row must retain the refused whole batch's `closed` reason while keeping half-local counts, position and `split:true`. The corrected split regression pins `closed:size` for explicit batch two. The C parser checked `call` eligibility only while iterating option keys, allowing an empty object on unsupported routes. Eligibility is now checked for the container before any send; the corpus and installed C listener pin empty-object refusals, and the schema rejects `annotate` context while continuing to allow its batch option.

High review also found seven marketing-owned site C examples that still expect a bare `thinkthen_call` result: `site/examples/functions/{filter,choose,annotate,find,rank,tag}/c.c` and `site/examples/install/c/first-call.c`. The latter's numeric parse yields zero on the wrapper. Their migration belongs to [the release-priority site issue](../issues/2026-09-28-site-c-examples-need-json-value-wrapper.md), owned by the coordinator and marketing. This ticket's library, header, C example and test consumers are updated; the site consumers are outstanding. Public release must not close that issue by landing 0230 alone.

The root Rust counter rises from 89290 to 89801 in `sdlc/ratchet.json` for the dynamic bridge, member metadata, shared writer and two outside-in regressions. The C counter rises from 2824 to 3193 in `libraries/c/ratchet.json` for the JSON controls, facts accessor and installed-header driver proof. The bridge reuses the existing planner, stop/join loop and result writer; the C route reuses the Rust bridge rather than another batch scheduler. Fresh High review must check both raised ceilings, the public `Evidence + Serialize` bound and the ABI/JSON migration.
