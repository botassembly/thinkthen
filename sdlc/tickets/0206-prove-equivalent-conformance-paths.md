## SQLite relation decision and separate feature work

Before claiming equivalence for `42` through `50`, compare the request and result of `thinkthen_recognize` followed by `thinkthen_relate` with the captured shared relation arm. `databases/sqlite/src/tables.rs` rejects a recognize spec containing relations. Its relate table reads `id`, `name`, and `kind` from rows; recognized offsets and strengths can be joined back into output, but the relate request has no original evidence text. `specification/recognize.md` requires a relation question about what the whole text states. The request identity therefore appears different even if a SQL join can reconstruct the visible entities. This is a source-based inference, not a passing experiment. Make one bounded case-42 request-digest and output comparison through existing SQL facilities after design approval. If either differs, retain all nine skips and open a reviewed SQLite recognize-relations feature ticket under the existing proof issue; do not label a standalone relate test equivalent. If both match, prove case 42 and the eight full-only variants through the same existing runner before removing their skips. No relation product change belongs in 0206.

The already filed `sdlc/issues/2026-09-27-sql-find-is-missing-from-three-databases.md` owns cases `18` and `19` for DuckDB, SQLite and PostgreSQL. Ticket 0150 deferred SQL find; B13 batching does not supply its grouped selection and none result. Do not duplicate that issue here. Full-only `30-local-question-file` in C, TypeScript, Ruby and R needs a separate reviewed host-file-form decision under the existing proof issue. A keyword constructor or annotate-only loader is not proof of decide's file form. Keep those skips until that decision and boundary check. A failed PostgreSQL or SQLite filter/rank equivalence also becomes a named follow-on feature ticket, with the mismatched result/request recorded, rather than a silent new API in this batch.
