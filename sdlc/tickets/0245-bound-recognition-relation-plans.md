## Outcome

After recognition has settled its names and before it constructs any relation question, a relation-enabled text refuses a nonempty plan with more than 255 distinct rule-side-admitted names, or more than 4,000 allowed pair questions across its rules. The local refusal names the applicable count and how to reduce it. It sends no relation request. Already completed boundary and kind requests retain their actual usage and attempt accounting. Standalone `relate` keeps its current 255-entity admission and shared planner semantics.

- Starts from: Local experiment `284-issue-register/111-recognize-has-no-entity-cap.md` asks for a local entity-count refusal and remedy before a dense relation plan expands or spends; the open [scale-and-shape issue](../issues/2026-09-25-recognize-and-relate-scale-and-shape.md) has distinct standalone-relate criteria. [ADR 0056](../planning/adr/0056-recognize-is-three-steps.md) fixes recognition's three stages and pair semantics.
- Keeps: Step-1 BILOU and step-2 kind/edge requests, equal-name-and-kind deduplication, rule and pair order, directed/either matching, whole-text stated-relation wording, 400-question and byte splitting, cuts, details, cancellation, and standalone `relate`'s 254/255/256 boundary. No new option, wire identity, saved format or result field is proposed.
- Changes: Recognition alone counts its distinct rule-side-admitted names and all allowed pairs with checked arithmetic before `plan_pairs` allocates questions or `pair_chunks` prepares requests. It returns an exit-2 Usage refusal above 255 admitted names in a nonempty plan or 4,000 questions. No-rule and zero-pair texts retain `relations: null` and `relations: []` respectively, even with many irrelevant names.
- Proof: A small pure count table compares the preflight count with the existing planner for directed, either, overlapping kinds, duplicate names and duplicate rules. A bounded loopback table observes a 64-name wildcard rule's 4,032 prospective questions, a 256-name case, and zero-pair/no-rule cases. It pins the numeric remedy, no relation send, no completed refused row, and exactly the earlier stage attempts and usage. Existing standalone-relate 254/255/256 checks stay green.
- Defers: A user-selectable cap, a total request or spend ceiling, relation-window or distance changes, SQL edge identity, many-record recognition batching, and the separate source/proof gaps recorded in the [recognition remainder preparation](../records/2026-09-28-recognition-batching-remainder-preparation.md). This ticket does not close the wider scale-and-shape issue.

## Bound and placement

`engine/facade/recognize.rs::relations` already returns `None` for no rules and calls `core/relation/pairs.rs::plan_pairs` only after names settle. Add a recognize-only preflight at that point. Reuse the planner's first `(name, kind)` identity and rule-side admission, including `*`. Count distinct admitted identities without constructing a `Question`, `Pair`, evidence string or chunk. A linear set of references to existing name/kind strings is acceptable; it cannot grow faster than the settled entity list already held in memory. The preflight must examine the full admitted set before applying the name limit because a 256-name input with irrelevant kinds, or one with no possible cross-kind or non-self pair, has no relation work to refuse. If the allowed-pair total is zero, return the existing empty relation list without calling the planner. If positive, check the 255-name limit first, then the 4,000-question limit. A no-rule text takes the existing early return and never runs this count.

For each rule let `A` be admitted names matching its source, `B` matching its target, and `I` matching both. A directed rule contributes `A × B − I`; the subtraction excludes self-pairs. An `either` rule contributes `A × B − I − I × (I − 1) / 2`, because the intersection's reverse orientation is the only duplicate after the self-pairs are removed. Sum each rule separately: repeated rules intentionally ask repeated questions, so they must count twice. Use checked multiply, subtract and add, or a proven saturating count that reports only “at least 4,001” after crossing the limit. An overflow must refuse locally; it may not wrap to an apparently safe plan. Counting mirrors the planner rather than changing its rule order or question wording. The selected limit bounds the whole recognition relation plan to at most 4,000 `Question` and `Pair` elements before per-request splitting; it does not establish a maximum of ten requests or a cost ceiling because profile and byte splitting can make smaller chunks.

The 255-name ceiling matches the accepted standalone `relate` admission but applies only to recognition's distinct rule-side-admitted identities when the whole plan has at least one allowed pair. An admitted identity counts even if that particular identity contributes no pair. The separate 4,000-question ceiling closes the multiplication hole when a smaller set meets many or repeated rules. It is below the first 64-name `*:*` directed plan of 4,032 questions. The recorded relation key has at most four names per sentence and its replay uses four rules. The recorded 65-name long text is replayed without relations. Thus both existing recorded replay forms remain below these ceilings; future dense relation work must be split or use a narrower rule set. The fixed limits are a conservative pre-0.1 safety policy, not a claim that every request or spend is otherwise bounded.

The CLI refusal should say `thinkthen: recognize: 256 distinct relation-eligible names exceed the limit of 255; reduce names or split the input` for the name case, and `thinkthen: recognize: 64 distinct relation-eligible names would ask 4032 relation questions, over the limit of 4000; reduce names or relation rules, or split the input` for the question case. If checked arithmetic overflows, say `at least 4001 relation questions` instead of an exact larger count. Public callers receive the same safe count/remedy through the existing Usage error envelope. Neither error includes name text, evidence, path, URL, key or rule wording. No `Recognition` value or final JSONL row is emitted for the refused text; earlier completed records and observed stage-1/2 calls remain untouched. The existing run facts and advisory usage count only actual attempts; do not manufacture relation usage or erase earlier sends. A cancellation or earlier stage failure still follows its existing path and precedence.

| Boundary | Required observation |
| --- | --- |
| No relation rules; many names | Existing `relations: null`; no new refusal or relation send. |
| Rules with no eligible kind or no possible non-self pair; more than 255 names | Existing `relations: []`; no unnecessary refusal or relation send. |
| Duplicate `(name, kind)` mentions and duplicate rules | First mention is retained; repeated mentions do not inflate the count, while each rule contributes its own questions. |
| 255 rule-side-admitted names but more than 4,000 allowed pairs | Question-count Usage refusal before any relation question is materialized or sent. |
| 256 rule-side-admitted names in a nonempty plan | Name-count Usage refusal before relation materialization or send, regardless of whether the prospective question total also exceeds 4,000. |
| Directed or `either` overlap | Checked count matches the existing planner's small actual pair list and includes no self-pair or double-counted unordered pair. |

## Review boundary and build lesson

This design adds a local refusal only to the relation stage of `recognize`; it does not revise ADR 0056's detection or standalone relate policy. The preflight's count must use the exact current planner's deduplication and rule semantics. A simple entity cap would leave rule multiplication unbounded, while a shared `plan_pairs` cap would reject currently valid standalone relate work. A per-request ceiling protects the send size after planning and therefore cannot protect the preceding allocation. Fresh code review must confirm arithmetic, zero-pair exemption, accounting and safe host error mapping before closure of register 111.

## What the build taught us

The shared first-mention admission function gives the preflight and planner the same `(name, kind)` identity and ordered names. All rule-side-admitted names count in a nonempty plan, even if one name cannot form a pair; the pure zero-pair and compiled source-only cases protect the exemption. A public failure after eight real boundary/kind requests carries those eight requests and 80/16 reported tokens in its facts while it sends no relation request. Standalone `relate` still plans its accepted 255-entity, 64,770-question case. The [build record](../records/0245-bound-recognition-relation-plans-build.md) gives exact checks, measured growth, strict-lint corrections and the held specification sentence.
