# 0212: Batch Rust library records and return run facts

Status: proposed B12a design for fresh independent review. Owner: Codex. This branch changes notes only. Runtime work needs the final 0172 context source and exact claims for files overlapping 0149/0157; those settings tickets are coordination dependencies, not new semantic prerequisites to the batch rule. [Proposed ADR 0089](../planning/adr/0089-rust-calls-carry-facts.md) narrows the needed ADR 0017 amendment to the Rust public return shape; no ADR or runtime contract is approved by this draft.

## Outcome and authority

Batch G's B12a gives the Rust library the same content-cut, fill-to-limit requests as the command. A caller can select `batch` and one shared `context` for a many-record call. Every Rust call returns facts without a second request, and bulk choose, score and tag answer many texts. This is the Rust portion of register 19 and 78 and pins register 64's byte spelling. The remaining C, Python, TypeScript, Ruby, R, frames and SQL rows keep their own B12b–B13e work; do not mark cross-surface parity complete merely because Rust is built. Ian's automatic maximal batching, speed-over-accuracy, `batch 1` compatibility and library-facts rulings in [the batching issue](../issues/2026-09-26-batching-design.md) stay. ADRs 0048, 0053, 0055 and 0083 own batch and command facts; ADR 0056 owns recognize's separate three-step method. The [preflight](../records/0212-rust-batching-preflight.md) pins source and branch distinctions.

## Proposed Rust contract for review

1. **One batch selector.** `BatchSetting::{Max, Records(NonZeroUsize)}` names the existing core `Setting`, with `Max` as the default. `EngineBuilder::batch(setting)` captures an engine default; `CallOptions::batch(setting)` overrides it on a call. On `Engine::from_env`, `THINKTHEN_BATCH` overrides the default. A loaded question's existing `batch` value is the next tier, below the typed call and engine environment setting; a bare builder reads no environment. Keep the typed-call > engine/environment > question-file > max order and question-file calibration warning. The public spelling is proposed, not an added setting in 0149/0157. One shared `CallOptions::context(&str)` supplies nonblank UTF-8 text for eligible many-record text questions; it is evidence, enters the request digest, and stays out of the question digest. It is refused for a structured question, a single-document call, and a call whose planner cannot use it. The named context is borrowed for the call and is not silently read from a file or environment. No context is applied to standalone `relate` or the one-document `recognize` method.
2. **Batch the existing streaming path.** `filter`, `decide_many` and `rank` feed `core::Batcher`, then `facade::Engine::ask_batch`, preserving input order, lazy pulling for iterator returns, the throttle, bounded in-flight work, duplicate record sharing, first failed record and worker joining. `rank` remains a whole-input result and keeps stable ties. A one-record batch with no context has today's exact body and digest. `annotate` keeps its grouped `on` pointer and partial-failure rules; its multi-record packing needs the same planner semantics without flattening distinct evidence groups. `find` already sends its whole candidate set; recognize and relate keep their existing request planners. The first implementation slice should prove `decide_many` and `filter` before widening the other adapters. Do not copy the command's CLI parser or build a second batch planner.
3. **Three missing bulk verbs.** Add `choose_many`, `score_many` and `tag_many`, with `_with` variants, using the corresponding typed question and `Evidence` iterator. Keep `Option<C>` for a choose null, `f64` for score, and declared-order `Vec<C>` for tag. Each row owns its input and value; a missing or invalid logical answer is a Backend failure, not a null, zero or empty list. The stream stops at the first failed record after yielding earlier rows, as `decide_many` does. Distinct null/failed-answer cases are part of the outside-in proof. The root free functions delegate to the same engine methods and preserve failed-default-engine-as-first-row behavior.
4. **Facts and public return shape.** Proposed `Call<T>` holds one private value and immutable facts for eager single, rank, find, recognize and relate results; `value()`, `into_value()` and `facts()` expose them. Existing `Batch<T>` remains an iterator and gains `facts() -> Option<&Facts>` once exhausted or after its terminal error; before that it returns `None`, never a misleading final total. `Facts` has read-only `records()`, `requests_sent()`, `cache_answers()`, `input_tokens() -> Option<u64>`, `output_tokens() -> Option<u64>`, `seconds()` and `model() -> Option<&str>` accessors. A single successful call has `records=1`; a batch counts all finished records, including filtered-out and partially annotated ones, and all attempts, including retries and a failed attempt. A cache or replay-only run omits token fields rather than claiming zero provider usage. Timing is wall time, excluded from byte identity. These facts belong to one call, not a before/after subtraction of process `Counters`, which concurrent calls can change. Per-row probabilities, request digests and confidence need a bounded typed path for each verb; `Details` already has the single-call forms, while bulk and filtered-away rows do not. Before implementation, review must settle whether the same `Call<T>`/`Batch<T>` family can carry that full detail without retaining an unbounded stream. An additive `details()` call is not sufficient under Ian's no-second-call ruling.
5. **Failure and stop.** Keep the six exhaustive public `ErrorKind` variants. An eager `Err(Error)` cannot contain a successful `Call<T>`; propose `Error::facts() -> Option<&Facts>` for an attempted call and `None` for pre-call construction/validation errors. A batch's terminal error freezes its final facts after joined workers; dropping early still cancels and joins, but no final result is returned after the batch value is dropped. Cancellation, deadline, replay miss, profile limit and provider failure keep their existing kinds and precedence. A planner refusal after earlier batches have completed preserves those rows and their facts; a first-record refusal sends nothing. No raw evidence or context enters a fact, diagnostic or `Debug` line. Review must decide whether this error/facts shape fulfills the accepted outcome before runtime claims.
6. **Identity and reuse.** Define the content-cut input as the exact UTF-8 bytes of `core::render::json_line` for the `core::Json` value produced by the record adapter: compact JSON, current escaping and numeric spelling, no trailing newline. Hash SHA-256, use the first eight bytes in big-endian order, cut at remainder zero modulo 4096. No host language reserializes those bytes; the later C door and wrappers call the Rust adapter or compare against one pinned fixture. Profile limits, 4096-member cap, 50 ms live pause, one eligible 413 halving, and context-overflow-at-the-record rule remain those of the existing engine and landed 0172. An inserted record changes batches only up to the next content cut; it does not redefine the cut for another record.

## Small outside-in proof

Use the existing Rust public consumer and loopback listener with the pinned `batch-duplicate`, `batch-context` and single-record fixtures. One `decide_many` call checks exact request bodies/digests and listener count at default and `batch 1`, including one duplicate that adds no question. A copied non-Rust digest fixture pins register 64's spelling without asking each wrapper to hash separately. A three-record table checks choose null, score and ordered tag labels in a full batch; one deliberately invalid answer checks the first-error boundary and preceding row count. A filtered-out row plus a 503/200 retry checks that final `facts.records`, `requests_sent` and optional tokens are per-call, not just emitted-row shares or process deltas. A replay-only `batch 1` call proves old entry reuse and zero sends; a changed context misses that identity and sends nothing under strict replay. One early context overflow and one later-record overflow preserve the already completed rows. Preserve the existing public cancellation, deadline and worker-join tests; add only a distinct row when the new batching path would evade them. Verify exact error kinds, safe `Debug`, no listener request on local refusal and no key/evidence leak. Use focused format, feature lint, selected public/conformance and executable-page checks after implementation; no paid, load or full gate is authorized by this note.

## What preparation taught us

The current public `Batch` streams per record through `facade::records`; `core::Batcher` already owns request shape, so a Rust batching implementation must bridge those layers rather than rebuild the parser. The command's run snapshot is process-wide and cannot supply exact facts for concurrent library calls. `Question::from_json` currently drops the parsed batch setting, while `Engine::with_model` re-resolves the backend and can lose a later nondefault request size until 0157 fixes it. The 0172 branch edits the batch parent and public results; this design needs one narrow post-landing refresh and exact file claims. Measuring headroom now exposed `core/batch.rs` at 496 and `engine/usage.rs` at 483 nonblank lines, so routing new state into either parent without extraction would fail lint.
