# 0212: Batch Rust library records and return run facts

Status: corrected B12a design for the same independent reviewer after findings on `8541ca52`. Owner: Codex. Notes only. Runtime work needs final 0172 context source and exact claims for files overlapping 0149/0157; those settings tickets are coordination dependencies, not new semantic prerequisites to the batch rule. [Proposed ADR 0089](../planning/adr/0089-rust-calls-carry-facts.md) makes the Rust public return choice explicit; design acceptance and runtime claims remain pending.

## Outcome and authority

Batch G's B12a gives the Rust library the same content-cut, fill-to-limit requests as the command. A caller can select `batch` and one shared `context` for a many-record call. Every Rust call returns facts without a second request, and bulk choose, score and tag answer many texts. This is the Rust portion of register 19 and 78 and pins register 64's byte spelling. The remaining C, Python, TypeScript, Ruby, R, frames and SQL rows keep their own B12b–B13e work; do not mark cross-surface parity complete merely because Rust is built. Ian's automatic maximal batching, speed-over-accuracy, `batch 1` compatibility and library-facts rulings in [the batching issue](../issues/2026-09-26-batching-design.md) stay. ADRs 0048, 0053, 0055 and 0083 own batch and command facts; ADR 0056 owns recognize's separate three-step method. The [preflight](../records/0212-rust-batching-preflight.md) pins source and branch distinctions.

## Proposed Rust contract for review

1. **One batch selector.** `BatchSetting::{Max, Records(NonZeroUsize)}` names the existing core `Setting`, with `Max` as the default. `EngineBuilder::batch(setting)` captures an engine default; `CallOptions::batch(setting)` overrides it on a call. On `Engine::from_env`, `THINKTHEN_BATCH` overrides the default. A loaded question's existing `batch` value is the next tier, below the typed call and engine environment setting; a bare builder reads no environment. Keep the typed-call > engine/environment > question-file > max order and question-file calibration warning. The public spelling is proposed, not an added setting in 0149/0157. One shared `CallOptions::context(&str)` supplies nonblank UTF-8 text for eligible many-record text questions; it is evidence, enters the request digest, and stays out of the question digest. It is refused for a structured question, a single-document call, and a call whose planner cannot use it. The named context is borrowed for the call and is not silently read from a file or environment. No context is applied to standalone `relate` or the one-document `recognize` method.
2. **Batch the existing streaming path.** `filter`, `decide_many` and `rank` feed `core::Batcher`, then `facade::Engine::ask_batch`, preserving input order, lazy pulling for iterator returns, the throttle, bounded in-flight work, duplicate record sharing, first failed record and worker joining. Keep already closed batches when a later planner push refuses a record; a partial reply emits every valid ordered prefix row, then one error. `rank` remains a whole-input result and keeps stable ties. A one-record batch with no context has today's exact body and digest. `annotate` keeps its grouped `on` pointer and partial-failure rules; its multi-record packing needs the same planner semantics without flattening distinct evidence groups. `find` already sends its whole candidate set; recognize and relate keep their existing request planners. The first implementation slice should prove `decide_many` and `filter` before widening the other adapters. Do not copy the command's CLI parser or build a second batch planner. Pending 0213/ADR 0090 at `7c97e2f8` identifies a distinct dynamic-choose boundary: rows sharing selected evidence but differing in complete ordered question, options or descriptions cannot share an answer. B12a's typed fixed-question `choose_many` may reuse the current planner; a future per-row-question extension must dedupe by evidence **and complete question**, while content cuts still hash selected record bytes. Coordinate that shared core file with codex-3 without claiming its proposed ADR is accepted.
3. **Three missing bulk verbs.** Add `choose_many`, `score_many` and `tag_many`, with `_with` variants, using the corresponding typed question and `Evidence` iterator. Keep `Option<C>` for a choose null, `f64` for score, and declared-order `Vec<C>` for tag. Each row owns its input and value; a missing or invalid logical answer is a Backend failure, not a null, zero or empty list. The stream stops at the first failed record after yielding earlier rows, as `decide_many` does. Distinct null/failed-answer cases are part of the outside-in proof. The root free functions delegate to the same engine methods and preserve failed-default-engine-as-first-row behavior.
4. **Facts and public return shape.** Recommend the uniform `Call<T>` proposal in ADR 0089 for every eager single, rank, find, recognize and relate result; `value()`, `into_value()` and `facts()` expose its value and immutable facts. Existing `Batch<T>` remains an iterator and gains `facts() -> Option<&Facts>` only after exhaustion or its terminal error; before completion it returns `None`. `Facts` has read-only `records()`, `requests_sent()`, `cache_answers()`, optional `input_tokens()`/`output_tokens()`, `seconds()` and optional `model()` accessors. These are scoped to one call, never computed as a delta of shared process `Counters`. A cache or replay-only call omits provider token fields rather than claiming zero reported usage. Timing is wall time, excluded from byte identity. Uniform wrapping breaks Rust signatures and requires the consumer migration below; its consistent access across primitive, `Vec` and structured results earns that cost. Extending only existing structured results still needs wrappers for primitives and `Vec`, two retrieval rules and equivalent consumer changes. Additive `*_call` siblings could preserve old signatures, but leaving old bare calls callable without facts fails Ian's **every** library call ruling; it is not the proposed outcome.
5. **Bounded full detail.** `CallOptions::observe(&dyn Fn(RecordObservation) + Send + Sync)` registers an optional caller-owned observer. An owned `RecordObservation` has a zero-based input index, typed value or failed-answer cause where available, probabilities in declared order, confidence if reported, model and the exact request-digest list. It carries no evidence or key. The public adapter invokes it on the caller thread once per **finished** logical input in input order as results are consumed, including `filter` rows it does not yield; duplicates receive separate observations pointing at the shared request digest. A partially answered batch observes its valid prefix, then stops at its first failed record. Rows beyond an ordered stop are not presented as completed rows, even if their in-flight request replied before join. The callback may keep selected observations, but the library retains at most the bounded scheduler window and one batch of detail at a time. Eager single `Call<T>` also exposes its one `RecordObservation` directly; eager many-record calls invoke the observer before returning and do not retain a second vector beside their already-held values. A caller wanting full rank/annotate/find detail registers the observer on that call; this is one request path, not a second `details()` call. The observer is an ordinary public feature, never a test-only hook. Its callback cannot alter answers; callback panic follows the existing caller-check unwind-after-join policy. Review this representation as part of ADR 0089 before widening the API.
6. **Failure, stop and exact accounting.** Keep six exhaustive public `ErrorKind` variants. `Error::facts() -> Option<&Facts>` is `None` for failure before a call starts and `Some` for a started eager call that fails, including zero-send cancellation; no seventh kind. A lazy batch emits ordered successes, then exactly one error and ends. Both that error and `Batch::facts()` expose the same frozen final facts **after** every in-flight worker joins. `records` counts finished ordered input rows, including filtered-out and partially annotated rows, but excludes the failing row and later speculative rows. Attempts/retries count every actual transport start in this call, including a failed request and attempts for later in-flight batches joined after the ordered stop. Cache answers and optional token/model presence count every reply received for this call through that join, including replies whose rows were suppressed by the stop; an absent provider usage report makes tokens absent for a mixed live run. Hook a call-scoped observer into the final send boundary after stop/budget checks and below the success-only `Answered` return, and into cache/replay/live reply receipt. It sees a failed transport attempt and 413/retry sends that never yield `Answered`. `Completed` and ordered emission supply finished-row counts, not the HTTP hook. Freeze only after join and `Stop::finish`, so cancellation precedence and caller-check unwind stay intact. A first-record local refusal sends nothing; earlier closed batches still complete before a later planner refusal. Dropping a lazy batch cancels and joins but cannot return facts after its value is gone. No raw evidence or context enters facts, observations, diagnostics or `Debug`.
7. **Identity and reuse.** Define the content-cut input as the exact UTF-8 bytes of `core::render::json_line` for the `core::Json` value produced by the record adapter: compact JSON, current escaping and numeric spelling, no trailing newline. Hash SHA-256, use the first eight bytes in big-endian order, cut at remainder zero modulo 4096. No host language reserializes those bytes; the later C door and wrappers call the Rust adapter or compare against one pinned fixture. Profile limits, 4096-member cap, 50 ms live pause, one eligible 413 halving, and context-overflow-at-the-record rule remain those of the existing engine and reviewed 0172, pending its landing. An inserted record changes batches only up to the next content cut; it does not redefine the cut for another record.

## Small outside-in proof

Use the existing Rust public consumer and loopback listener with the pinned `batch-duplicate`, `batch-context` and single-record fixtures. One `decide_many` call checks exact request bodies/digests and listener count at default and `batch 1`, including one duplicate that adds no question. A copied non-Rust digest fixture pins register 64's spelling without asking each wrapper to hash separately. A three-record table checks choose null, score and ordered tag labels in a full batch; one deliberately invalid answer checks the first-error boundary and preceding row count. A filtered-out row plus a 503/200 retry checks that the observer reports all finished rows in order while the normal iterator omits the filtered value; final `facts.records`, `requests_sent` and optional tokens must be per-call, not emitted-row shares or process deltas. A failing eager `rank` request checks `Error::facts()`, and a failing lazy batch checks its one terminal error and identical frozen `Batch::facts()` after a later in-flight reply joins; count that late attempt and reply, but no later row. A replay-only `batch 1` call proves old entry reuse and zero sends; a changed context misses that identity and sends nothing under strict replay. One early context overflow and one later-record overflow preserve the already completed rows. Preserve the existing public cancellation, deadline and worker-join tests; add only a distinct row when the new batching path would evade them. Verify exact error kinds, safe `Debug`, no listener request on local refusal and no key/evidence leak. Use focused format, feature lint, selected public/conformance and executable-page checks after implementation; no paid, load or full gate is authorized by this note.

## What preparation taught us

The current public `Batch` streams per record through `facade::records`; `core::Batcher` already owns request shape, so a Rust batching implementation must bridge those layers rather than rebuild the parser. The command's run snapshot is process-wide and cannot supply exact facts for concurrent library calls. Fresh review caught that `Batch::facts()` alone hides filtered-out row detail and that success-only `Answered` misses failed attempts and joined replies; the corrected proposal adds ordered bounded observation and a call-scoped hook below that return. It also caught that the public shape needed a recommendation and a complete compile migration, not a reviewer-invented alternative. `Question::from_json` currently drops the parsed batch setting, while `Engine::with_model` re-resolves the backend and can lose a later nondefault request size until 0157 fixes it. The 0172 branch edits the batch parent and public results; this design needs one narrow post-landing refresh and exact file claims. Measuring headroom now exposed `core/batch.rs` at 496 and `engine/usage.rs` at 483 nonblank lines, so routing new state into either parent without extraction would fail lint.
