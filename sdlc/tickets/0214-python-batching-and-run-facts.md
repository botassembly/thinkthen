Status: landed. High code/API review accepted source `82e359af`. The branch integrates main `e97d0342` with focused Python consumer proof and received independent integration ACCEPT at `dfc1b5fb` and landed on main. ## Outcome and authority

Deliver Batch G B12c after B12a: automatic maximal batching where the Rust planner permits it, a Python `batch` selector and shared `context` on eligible multi-record calls, and per-call facts on every Python verb without a second provider call. A one-record request with no context keeps its exact existing body and digest. Preserve the six Python error classes, stop precedence, `None` for an unsure answer, failed annotate markers, ordered partial results, and the existing pandas/Polars value schema and index. Ian's [batching](../issues/closed/2026-09-26-batching-design.md) and [run-facts](../issues/closed/2026-09-26-every-surface-should-give-back-run-facts.md) rulings govern the outcome. Accepted ADR 0089 governs the Rust carrier and bounded observer. [Accepted ADR 0091](../planning/adr/0091-python-call-facts-after-an-early-stop.md) isolates Python's approved early-stop receipt. J5's Enum, Literal, typed annotate and optional Pydantic work is later.

## Approved Python contract

1. `tt.Engine(batch=...)` supplies the engine/environment tier, and each eligible call accepts `batch=`. Accept `"max"` or a positive non-bool integer, including 1; reject zero, negatives, floats and unknown strings as `UsageError` before a send. The typed call overrides the engine/environment tier, then a loaded decide question's batch, then `max`, exactly as `specification/settings.md` and 0212 define. `context=` is nonblank text supplied on one eligible many-record text call; it enters request digest as shared evidence, not question digest. A Series or frame is eligible when its Rust question path actually supports shared context; do not infer eligibility from the Python container alone. Refuse context on a single document, `recognize` or `relate`, or any other path the accepted Rust API refuses. Do not silently read a context file or apply it to an unsupported method. `batch=1` with no context preserves old recordings.
2. A Python `Call[T]` exposes `.value`, `.facts`, `.details` for **every** successful `Engine` method and matching module function except `question()` (a local constructor) and `usage()` (a process counter read). `.value` holds exactly the old return value: bool/None, choice/None, score, tags, list, rank/find dictionary, recognized object, edges, Series or frame. `details()` returns `Call[dict]` whose inner dictionary keeps the existing `thinkthen.result/1` shape. `decide_many`, `filter`, list `annotate`, and new `choose_many`, `score_many`, `tag_many` remain eager in Python; no new public iterator is needed merely because Rust internally yields `Batch<T>`. A Python caller can read the final Rust `Batch::facts()` only after consuming it fully or its terminal error. No Python `Call` pretends that a partial iterator is final.
3. `.facts` has `records`, `requests_sent`, `cache_answers`, optional `input_tokens` and `output_tokens`, `seconds`, and optional `model`. It is scoped to the one call, including filtered rows and in-flight attempts/replies joined at stop. Missing usage or model stays absent, never zero or guessed. `.details` is an ordered tuple of recursively immutable mappings and sequences copied from ADR 0089's completed logical `Question` observations. Every entry has `index`, `question_sha256`, `requests`, `requests_sent`, `cached`, `failed_questions`, `url`, `request_digests`, and either typed `answer` or typed `failed` cause; optional `member`, `stage`, `position`, `probabilities`, `confidence`, `usage`, and `model` appear only when the corresponding observation supplies them. `index` is zero-based input position, including a suppressed `filter` row. Annotate member and recognize stage/position distinguish multiple questions of one row. The sequence has no entries after an ordered stop, but `.facts` still includes actual later in-flight sends/replies through the join. Frame results carry these observations on `Call`, not as new frame columns; 0209's typed answer and separate `failed` column remain unchanged. The Python adapter may own a details collection proportional to the eager input; Rust keeps only bounded observer state.
4. A started ordinary failure raises the same `ThinkThenError` subclass and carries final `.facts` plus completed `.details` after Rust joins. A refusal before worker start has neither facts nor receipt; a returned started zero-send failure has final facts. A genuinely unaccounted worker panic has a safe Defect terminal outcome with `facts=None` and `details=None`; no partial or invented zero is final. A post-call conversion error carries an already frozen account as a returned error; a caught worker panic still loses it. ADR 0089's returned Error/Batch guarantees do not cover unwind. Python's outer fast cancellation is distinct: accepted ADR 0091 gives `Cancelled.completion`, whose final facts/details become available after the detached worker exits on normal success or returned error. It retains the under-100-ms held-call stop and releases imported Arrow batches later. Do not claim final accounting at the early raise. A signal handler's `SystemExit` retains its type and exit code, receives the same completion receipt after worker start, and is not converted to `Cancelled`. Error `kind`, `retryable` and messages stay as today.
5. Adapt `Engine` and every module free function together. `rank(top=)` trims only `.value`; the call facts and details cover all judged candidates. `find(None)` remains a valid inner value, not an absent `Call`. `_column` rebuilds the Series **inside** `.value` and preserves pandas index/name and Polars dtype. `annotate`/`recognize` frame constructors likewise rebuild inside `.value`; the pandas `failed` column stays the fixed 0209 type. Where an eager Python invocation currently makes several Rust calls, particularly frame `each_named`, combine their **call-scoped** facts without a process-counter delta: sum records/sends/cache, sum tokens only when every relevant live reply reports usage, keep model only when one model is known for the whole invocation, and time the whole invocation. Include completed earlier calls and the failing Rust call's facts if a later row fails. Preserve final ordered detail and only one Python error. All Python and Rust extension constructors return the same wrapper, including `details` and error paths. Update the stub and README in the same build. No new Python runtime dependency; J5 adds optional Pydantic later.

### Missing list and completion boundaries

Add eager `Engine.choose_many(question, records, *, options=None, batch=None, context=None, deadline=None, token=None) -> Call[list[str | None]]`, `score_many(question, records, *, levels=None, batch=None, context=None, deadline=None, token=None) -> Call[list[float]]`, and `tag_many(question, records, *, labels=None, batch=None, context=None, deadline=None, token=None) -> Call[list[list[str]]]`, plus matching module delegates and stub signatures. Preserve typed-question acceptance, option order/descriptions, null and failed semantics. Their extension route must consume the accepted Rust many planner; current scalar `src/engine.rs::ask` calls `text()` and refuses lists. A Series still uses its existing column path, with `Call.value` holding the rebuilt Series. The new list methods accept iterable text records; existing scalar choose/score/tag retain their column overloads. The stub exposes both the new list signatures and old column overloads.

Use a private completion carrier containing the Rust result or stop plus **final** facts and owned ordered observations after the batch is exhausted/joined. Keep that carrier through `frame::on_worker`, `answered` JSON and failure-cell parsing, `Stop::Said`, Arrow output, `ask_column`, frame and column helpers, and Python `_column`, `_on` and pandas/Polars reconstruction. The carrier preserves an account frozen before a later conversion error returned normally; current `worker::run` sends only `None` on any caught worker panic, so the receipt does not promise facts for panic even if freeze happened earlier. `Stop::Said` after an engine result remains UsageError with completed facts; pre-engine refusals have no facts. A post-call conversion failure uses the existing applicable six-kind exception with final facts/details and source in `__cause__`; pandas/Polars reconstruction failure becomes LocalError with cause rather than escaping bare. Never infer completion from process `usage()` deltas. For `each_named`, aggregate already completed per-text facts with a failing call's final facts, keeping ordered detail and one final exception. An eager Python call may own detail proportional to its input; no process-wide or Rust-engine unbounded history is added.

## What the build taught us

The design review found three missing eager list verbs, mutable dictionaries in the proposed detail shape, lost accounts through frame reconstruction, and an impossible panic-facts promise. The build uses the landed 0230 dynamic-question bridge for runtime labels, copies Rust question observations into immutable Python detail, and carries one owned account through worker, Arrow, frame and Python reconstruction. A caught worker panic remains unaccounted. The approved receipt keeps prompt cancellation while the same detached worker finishes and releases its imported input.

The existing held tests assumed that throttle 8 had eight requests in flight before the first reply. The landed Rust planner now waits on the first held request, even with explicit `batch=1`. The updated focused tests pin one held send, no later send after cancellation, and all rows after release. Historical per-row body/count fixtures use explicit `batch=1`; a separate new listener test pins the default three-row packing into one request. No test-only hook was added. The Python result carrier also changed direct consumer syntax: library tests and examples now read `.value`, while marketing-owned `site/` Python copies remain the open [site migration issue](../issues/closed/2026-09-28-site-python-examples-need-call-values.md).
