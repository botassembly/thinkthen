# 0339: An `ollama` built-in backend, and descriptions each backend accepts

Status: ready. Design: ADR 0115, which amends ADR 0114. Ian asked for it on 2026-09-30. Build after 0304 slice 4 lands, because the dialect reaches `cli/asking/judged.rs`, `engine/facade/recognize.rs` and `engine/prepared_request.rs`, which slice 4 edits.

## Outcome

`--backend ollama` reaches Ollama 0.35 at `http://localhost:11434/v1` with model `nimble` and no key. `thinkthen check --backend ollama` against a server that refuses object descriptions reports no critical finding. Each built-in and each configured backend names how its criteria descriptions travel: `typesafe`, `liquid`, configured entries by default and the unnamed path send them as written, and `ollama` sends each as text. With no backend named, every command's bytes stay today's.

## Evidence

- Starts from: ADR 0114 and ticket 0334 (landed). `core/adapters/systemone/backends.rs` holds the two built-ins. `core/backend/named.rs::Choice::guard` compares the final host with every other built-in's base host. `engine/facade.rs` sends no `Authorization` header when the key is missing and the address is loopback. `core/adapters/systemone/request.rs` writes each description as authored, omits a null `noul` side (ADR 0110) and writes `{}` for a null `score` level. `core/pack.rs::asks` keys each question on the bytes `built_in::parts` writes (ADR 0111). Workspace experiment 415 found Ollama's 400 on object descriptions. The 2026-09-30 hosted Liquid recheck passed on today's bytes. The TypeSafe OpenAPI schema accepts every form.
- Keeps: with no backend named, or with `typesafe` or `liquid`, every request body, question key, recording digest, `--plan` document and check fixture (`specification/fixtures/check/requests.jsonl`) is byte for byte today's. The 0334 keep also stands: every surface check passes with no backend named. Other keeps: ADR 0110's null `noul` omission; ADR 0114's selection order, key rules and refusals, including section 5 for `TYPESAFE_API_KEY` and `LIQUIDAI_API_KEY`; the loopback-without-key rule; the clear-text rule; the configuration file's closed shape except the new optional field; the replay decoder.
- Changes: the `ollama` row in `backends.rs`, with a `descriptions` column on every row (ADR 0115 section 1). `Named` and the resolved backend carry the dialect. The plan carries it beside the model, so the request body, the question key and the `--plan` document all read one rendering. `request.rs` renders descriptions under `text` before it builds each question (ADR 0115 section 3). `guard` leaves loopback built-in bases out of the "other" side (section 2). There is an optional `descriptions` field on a `backends` entry, with its exit-5 refusal (section 5). There are the check note line and the `--plan` note sentence (section 4). The new unknown-name sentence lists three built-ins. Spec and doc pages: `specification/types.md` (a backend's dialect decides how descriptions travel; `ollama` sends the `what` text), `specification/backends.md`, `specification/check.md`, `specification/settings.md` (the `OLLAMA_API_KEY` row), `specification/recording.md` (the entry field), the README's backend list, and the CHANGELOG. ADR 0115 moves to accepted when this ticket lands.
- Proof: loopback servers that mimic each dialect's refusals, with no network and no real Ollama. The Ollama mimic answers 400 to any object description. The Liquid mimic answers 422 to a null `noul` side. The TypeSafe mimic accepts every form. `check --backend ollama --url MIMIC` reports `critical 0` and prints the note line, and `check` against the same mimic on the unnamed path still reports its criticals. Exact request bodies are pinned per dialect for the four check probes and for `decide`, `choose`, `tag` and `score`, with string, object (`what` with `not_for` and `examples`), object without `what`, list, empty object, null and absent descriptions. The `text` dialect's check bodies go in a fixture beside `requests.jsonl`. `--backend ollama` with `OLLAMA_API_KEY` unset sends N requests to a loopback server, and none carries `Authorization`. At a non-loopback address the same run exits 4 naming `OLLAMA_API_KEY` and sends nothing, counted by a loopback proxy. There is an edge table for the guard: `OLLAMA_API_KEY` at the TypeSafe and Liquid hosts is refused at exit 2. `--backend liquid --url http://localhost:PORT/v1` sends the Liquid marker. `--backend typesafe --url http://localhost:PORT/v1` passes. Cache proof: `L` is the TypeSafe mimic, which accepts every form, so both runs store answers. One question with an object description, asked under `--backend ollama --url L` and then under a configured `authored` backend at `L` with the same model, sends one request each time. A string-only question asked both ways sends one request and then none. The recording digests differ in the first case. Secrecy markers in `OLLAMA_API_KEY` and each 0334 key variable never appear in output, the store, recordings, usage files, `--plan`, `status` or `Debug`. A configured `descriptions` refusal repeats no value. `policy.py`, `sdlc/scripts/{test,spec,settings,tickets}`, workspace clippy with `-D warnings`, the C door and Polars tests, every surface check with no backend named, and `lint` in a clean checkout pass. A manual `thinkthen check --backend ollama` against a real local Ollama is optional, and only if one already runs. The mimic assumes Ollama accepts an object `state` (the mixed probe); only a real check or a user run shows it.
- Defers: the gaps ADR 0115 lists. These are structured question text on Ollama, Ollama's hosted host in the key guard, refreshing a re-pulled Ollama tag, the dialect in bindings and SQL (ADR 0114 slice 2), and `status` naming the dialect. A per-backend longer timeout is also deferred, as 0334 deferred per-backend limits. The site's providers page belongs to marketing.
