## Part two: the hard questions

**Ian** marks the few that need his product direction. The rest are recommendations the thinkthen PM can carry into tickets, and Ian can overturn any of them.

### What went wrong, and the rules it teaches

**Q1. What actually failed in DuckDB PR #2936?**
Four things, each a process gap, not a coding gap. First, the words: the PR body runs five paragraphs of qualification jargon ("bounded inspection of official Rust 1.95 standard libraries meets the macOS 11 baseline"), and the descriptor links to `databases/duckdb/README.md`, which opens "Unsigned loadable extensions for DuckDB v1.5.5 and v1.5.4 that put the `thinkthen` engine behind SQL". The maintainer called both "AI-generated and borderline incomprehensible". Second, the price: nothing said who pays for what. Third, the build: community CI stopped on Linux ARM64 at `vcpkg.json: No such file or directory`, because the repository root lacks the file DuckDB's CI expects, and the offline rehearsal in 0415 never ran the vcpkg toolchain. Fourth, the watch: ticket 0415 says Ian's 2026-10-05 authorization covered the listing and that "the approved outside pull request needs no second permission request", then marked itself complete. Nobody looked at the PR for seven days, and Ian learned of it from a marketing report. Recommendation: the four rules in Q2 to Q5. Ticket 0577 already carries the repair for 0.2.

**Q2. Who may put words or code on someone else's repository or registry? (Ian)**
The launch plan already says "Agents open nothing on outside repositories", and the workspace rules require authorization for visible external changes. 0415 read a general listing authorization as permission to post any text. Options: Ian posts everything himself; an agent posts only exact text Ian approved; an agent posts within a standing authorization. Ian's account carries his name, so his reputation is what a maintainer judges. Recommendation: authorization covers exact words and an exact commit. An agent drafts the PR body, the README page and the descriptor. Ian reads them in chat. After his yes, the PM posts exactly those bytes, or Ian posts them himself. Any later change to the words, or a new commit pin, returns to Ian, with one exception in Q11 for routine version bumps. Replies to a maintainer are Ian's own; an agent drafts them.

**Q3. What does "done" mean for outside work?**
0415 closed when the PR opened. The thing a user gets, a listed extension, did not exist. Recommendation: a ticket with outside work closes only when the outside item closes: merged and the package installs, or closed with a recorded reason. Submitting is progress, not completion. The check Ian added on 2026-10-13 to `sdlc/checks.md` ("Does every outside pull request or issue have an owner checking it...") enforces this for the PM.

**Q4. Who watches an outside PR until it closes, and how does the tracker show it?**
The repo's PM owns every outside PR or issue its tickets open, from submission to close. The project's tracker cannot show outside items today; it has no command for them. Under the workspace rule, status must not live in a Markdown file. Recommendation: ask for the tracker to show open outside items in its daily report, read from the ticket's linked URL through `gh`: state, CI result, last maintainer comment and its age. Until the tracker shows it, the PM reads each linked PR with `gh pr view` at every daily report. A maintainer comment reaches Ian in chat the same day, with a drafted reply.

**Q5. How do we keep machine-written prose out of public text?**
Outside readers now say so in their rules: Hacker News says "Don't post generated text or AI-edited text", and sindresorhus/awesome refuses fully AI-generated pull requests. The pattern is visible on three live ThinkThen channels, not only DuckDB. PyPI's page for `thinkthen` opens "The binding is the unpublished crate `thinkthen-python` in its own Cargo workspace (ADR 0047). The design page is `sdlc/planning/libraries/python.md`." npm shows no README at all. The DuckDB README speaks of "admission", "qualified" and "routes". The cause is one file serving two readers: each package README is both the builders' internal note and the registry's front page. Options: rewrite each README by hand; split public from internal text; add a lint. Recommendation: three layers. First, split: each package gets a short public README for its registry page, and internal notes move to a file the package does not publish, which follows the workspace decision that "README is public, AGENTS.md is for agents". Second, write every public README from one listing source in the thinkthen repo: the one-line description, the price sentence, the install line, a ten-line example, links. Each README is that source in its language's idiom, and the house copy and writing rules apply. Third, a check that fails a published README containing `ADR`, `ticket`, `sdlc/`, `0.1.2`-style stale versions, or words from a short internal list ("surface", "admission", "qualified", "engine route"). A lint cannot judge clarity, so the last gate is a reader test in Q6.

**Q6. What review step proves a text reads well before Ian sees it?**
Ian is the final reader, and his time is the scarcest input. Recommendation: a cold read. A fresh reviewer with no repository context gets only the listing text and answers three questions in writing: what is it, what does it cost me, and how do I install it. If any answer is wrong or hedged, the text goes back. Then Ian approves. The reviewer also runs the install line from the text alone, which matches the strategy's 0.2 exit test that "a fresh agent with no repo context installs from the docs alone".

**Q7. What does every listing say about price?**
The maintainer's third point. ThinkThen is MIT and free, and it calls a model the user picks. Recommendation: one sentence, the same on every registry, from the listing source: "ThinkThen is free and MIT licensed. It calls the model you choose: hosted models bill you per token through your own key, and local models cost nothing. Nothing is sent to us." The last sentence holds until the hosted service exists. Ticket 0577 carries the same three facts for DuckDB.

### Which channels matter

**Q8. Which channels matter for the 0.3 builder, and which are vanity? (Ian)**
The 0.3 customer is one builder who wants control of models and data (0.3 README). Ian measures traction by GitHub stars and YouTube views. A registry listing produces installs, not stars. Stars come from people who reach the GitHub page: Hacker News, YouTube, blog posts, awesome lists and the DuckDB extension directory send them there. Downloads so far are small: crates.io counts 45. Every channel costs one build job, one install check and one README to keep current per release. Recommendation, three tiers. The fifteen front-door and listed channels are the 0.2 release's registries; nothing new joins them in 0.3 except the MCP Registry and a container image.
- **Front door (six):** the GitHub release with `install.sh`, the Homebrew tap, crates.io, PyPI, npm and the DuckDB community extensions. Each gets a reviewed README, the install check and a fix before any release ships. These are where builders and agents start: the shell, Python, TypeScript and Rust programs, and the database where the data talk sends people (the 0.2 marketing plan).
- **Listed (nine):** R-universe, RubyGems, NuGet, Maven Central, pub.dev, Packagist, the Go module proxy, and the PostgreSQL and SQLite archives. They publish from the same workflow with the shared listing text and the install check, and they get no hand-tuned copy.
- **Archive only (six):** C++, Swift, Zig, Ada, COBOL and Objective-C ship as release archives with a README in the archive. Their reach comes from posts, not registries: the strategy says each language is "a post that could reach the front page of Hacker News".
- **Not in 0.3:** CRAN, homebrew-core, PGXN, PGDG, the Swift Package Index, vcpkg, Conan, Alire, CocoaPods and Bioconductor, for the reasons in Q9 to Q15.

**Q9. CRAN, or R-universe only?**
CRAN reviews every submission by hand and requires Rust packages to vendor every crate and build offline on its machines (the marketing libraries notes, §8; `sdlc/planning/libraries/r.md`). Each release faces the same review, on CRAN's schedule. R-universe publishes from GitHub with no review and already serves 0.1.2. R is graded C- in 0576, so a CRAN reviewer would also meet the weakest library. CRAN's Rust policy adds vendored crates, a check with a cargo at least two years old, one or two build jobs, Rust authors in DESCRIPTION and a 10 MB tarball limit. Recommendation: R-universe only through 0.3. Revisit CRAN when R users ask for it in issues and the R library reaches B.

**Q10. Homebrew core, or the tap?**
Homebrew's acceptance policy asks for at least 30 forks, 30 watchers or 75 stars, and a formula submitted by the project's own owner needs 90 forks, 90 watchers or 225 stars. It also says a third-party tap "does not imply Homebrew endorsement". With 8 stars ThinkThen does not qualify. The tap already works and `brew install botassembly/thinkthen/thinkthen` is one line. Recommendation: keep the tap. Submit to homebrew-core only once someone else does it, at 75 stars, or Ian does it at 225; either way Ian approves the words. A rejected core submission is a public mark against the project.

**Q11. How does the DuckDB listing stay current without asking Ian each time?**
The listing pins one commit in `description.yml`. Each ThinkThen release needs a PR that moves `ref`, and each DuckDB release triggers DuckDB's own rebuild. If every bump needs Ian's reading, releases stall; if none does, Q2's rule breaks. Recommendation: Ian approves the full listing once. A version bump PR then changes only `version` and `ref` (and `ref_next`), with a fixed one-line body Ian approves once: "Update thinkthen to 0.2.1." Any other change to the descriptor or text returns to Ian. The same rule fits the tap and any later listing that pins a version.

**Q12. Which DuckDB versions do we support? (Ian)**
DuckDB's newest release is 1.5.6. 2.0 has been in alpha since 2026-09-02, and DuckDB's release calendar lists 2.0.0 for 2026-10-21, tentatively. DuckDB's rules say `ref` must work with the latest stable release and the optional `ref_next` with the next one, and that community extensions "aim to be built … only for the latest stable DuckDB release". Every extension is rebuilt when DuckDB releases. So within days of 2.0.0, CI builds the plain `ref` against 2.0, and a `ref` that only compiles on 1.5 drops off the listing. Community CI also runs a job against 1.4, the long-term support line ("Community Extension with DuckDB on Andium" on PR #2936, skipped there), and DuckDB gives each long-term release a year of community support. Every DuckDB binary is "tied both to a specific DuckDB version and a platform". DuckDB's C extension API has a stable part meant to load across versions, but its C template is marked experimental, and its Rust template still lists community-extension support as "coming soon". Options: keep the C++ extension and track stable plus next; port to the C API; add 1.4. Recommendation: for 0.2, keep C++ and make both `ref` and `ref_next` compile: 1.5.6 and 2.0 now, then 2.0 and DuckDB's main once 2.0.0 ships. Since the 0.2 listing will likely land after 2.0.0, 2.0 is the version that must pass. For 0.3, a prototype ports a few scalar functions to the C API's stable part and tests whether one build loads on 1.4, 1.5 and 2.0. If it does, the long-term line comes free. If not, support stable and next only, and skip 1.4.

**Q13. Do the standalone unsigned DuckDB archives stay?**
They exist for DuckDB 1.5.4 and 1.5.5 only, while the newest is 1.5.6, and they need `allow_unsigned_extensions`, which dbt v2 refuses (`databases/duckdb/README.md`). They are already stale and they teach users to disable a safety setting. Recommendation: once the community listing serves a version, remove the unsigned archives from the next release and point every DuckDB install line at `INSTALL thinkthen FROM community`.

**Q14. Which PostgreSQL versions, and through which channel?**
0.2 builds only PostgreSQL 16 (`databases/postgresql/Cargo.toml`, `default = ["pg16"]`), as a tarball an administrator copies by hand. A builder on 17 or 18 gets nothing. pgrx builds each major from a feature flag. PGXN ships source and needs Rust and pgrx on the installing machine; Trunk and pgxman are gone; PGDG and Pigsty are the live binary channels (`sdlc/planning/databases/postgres.md` §6). Recommendation: for 0.3, build every PostgreSQL major that the PostgreSQL project still supports and pgrx supports, on Linux x86-64 and ARM64, test the oldest and newest each release, and ship them as release archives. Publish one container image with PostgreSQL and ThinkThen installed, the quickest way for a builder to try SQL, using the same image pipeline the proxy needs (PRD 05 Q21). Ask Pigsty to carry the extension once the archives are stable; that request is an outside submission under Q2. No PGXN and no PGDG in 0.3.

**Q15. How do SQLite users get the extension?**
Today: download a release archive, rename `libthinkthen0.so` to `thinkthen.so`, and `.load` it with a named entry point (`databases/sqlite/README.md`). Most SQLite users load extensions from Python or Node. SQLite has no central registry: sqlpkg was archived on 2026-02-04, and `sqlite-dist`, which packs one extension for pip, npm and gem, calls itself a work in progress. The working pattern is sqlite-vec's: the extension ships inside ordinary pip, npm, gem, cargo and Go packages with a `load(connection)` helper. Recommendation: keep the archive for 0.3, and fix its file name so no rename is needed. A pip and npm route for the SQLite extension is a later candidate if SQLite users ask; it adds packages to keep in step.

**Q16. Swift Package Index and Go?**
SwiftPM resolves a dependency from a Git URL whose root holds `Package.swift`; ThinkThen's manifest sits in `libraries/swift/`, and the root has none. The Swift Package Index requires `Package.swift` at the root, a semantic version tag, and that the package "must all compile", Linux included, and a package with only an XCFramework fails its Linux build. Options: a root `Package.swift` with a binary target pointing at the release's XCFramework, which makes every Swift user clone the whole repository; a small mirror repository published by the release; or archive only. Recommendation: archive only in 0.3, with a later mirror if Swift users ask. Go already publishes as `libraries/go/v*` tags and the proxy serves v0.1.2. Go module zips skip symbolic links and nested modules, so each prebuilt native library must be a real file inside the tagged tree; the install check already proves this. Go stays Listed.

### The release itself

**Q17. What must the 0.2 release do for channels, and what waits for 0.3?**
0.2 already ships through every Listed and Front-door registry from one workflow (`release-process.md` §4 to §7). The gaps are words, the DuckDB build and the watch. Recommendation for 0.2, all inside existing tickets: 0577 fixes the DuckDB build and words; a new ticket splits public package READMEs from internal notes for the six Front-door channels and RubyGems (whose page still shows a placeholder), and adds the price sentence; the PM runs Q4's watch by hand. The release coordinator also confirms the Maven Central namespace: Maven sets up `io.github.<user>` names automatically but not organization names, and `io.github.botassembly` is an organization. Everything else in this PRD is 0.3: the tiers as policy, the listing source and its check, the PostgreSQL majors, the DuckDB C API experiment, MCP registries, the container image, the CLI inside the Python and npm packages, and dropping the unsigned DuckDB archives.

**Q18. How do 21 channels stay in step each release without a proof spiral?**
The release process already says to reuse passing checks, not to repeat full matrices, and it retired per-language receipts (`release-process.md` §2, §7). The risk is that each new channel adds hand steps. Recommendation: one version, one workflow, one listing source. Each channel has exactly one proof: Front door and Listed channels pass `install-check.yml` from the public registry after publication; Archive channels pass the release smoke on their archive. No per-channel write-up, no second campaign. A channel that fails its one proof is fixed in the next release, unless it is Front door, which holds the announcement.

**Q19. Signing, provenance and reproducible builds: what do we promise?**
Today npm publishes with `--provenance`, Maven artifacts are GPG-signed, `install.sh` refuses a missing or wrong checksum, and crates.io, PyPI, RubyGems, NuGet and pub.dev use trusted publishing. GitHub release archives carry checksums but no signature, and a checksum served beside the file proves only that the download was not corrupted. Bit-for-bit reproducible Rust builds across machines need path trimming (`trim-paths` or `--remap-path-prefix`) and a pinned toolchain, and split debug information and linker settings still vary. Recommendation: promise provenance, not reproducibility. Add GitHub artifact attestations (`actions/attest`) to every release archive, so `gh attestation verify` ties each file to the workflow run and commit; GitHub documents this as SLSA Build Level 2, or Level 3 from a reusable workflow. Turn on PyPI attestations, which the publish action uploads by default with trusted publishing. Maven Central keeps PGP signatures, which it requires. The DuckDB community build is signed by DuckDB. Do not claim reproducible builds in 0.3; one experiment may measure how far two clean builds differ, and the claim waits for its result.

**Q20. Which language and platform versions do we support?**
0.2 states floors per package (2026-10-09 native package design): Python 3.10 by abi3, Node 22, Ruby 3.4, R 4.2, JDK 22, .NET 8, PostgreSQL 16, DuckDB 1.5.4 and 1.5.5. The macOS wheels are tagged `macosx_15_0`, so a Mac on macOS 14 cannot install them. Python 3.10 reaches its end of life in October 2026. Recommendation: one rule. Support each language version and database major its own project still supports on the release day, and build once where a stable binary interface allows it (Python's abi3, Node-API, DuckDB's C API if Q12's experiment wins). Lower the macOS deployment target to the oldest macOS Apple still patches, unless a dependency forbids it. Raise floors only in a minor release, with a line in the changelog.

### Discovery

**Q21. MCP registries: when, and what do they list?**
Ian ruled that MCP is not marketed until 0.3 ships its one-tool redesign (`mcp.md`, the 0.2 marketing plan). The official MCP Registry, still in preview, holds metadata that points at a package in npm, PyPI, NuGet, crates.io, a container registry or an MCPB bundle, and checks ownership by an `mcpName` field in npm or a visible `mcp-name:` line in a PyPI, NuGet or crates.io README. Its moderation removes spam and broken servers and leaves "low-quality or buggy servers". ThinkThen's MCP server lives inside the command, which reaches users through `install.sh`, Homebrew and crates.io. A crates.io entry is valid, but an MCP client then needs Rust to install it. Recommendation: no MCP listing for 0.2. In 0.3, after the one-tool MCP passes its agent experiment, list it in the official registry and the largest directories. That needs the command reachable through a registry the MCP Registry accepts, which Q22 provides.

**Q22. Should `uvx thinkthen` and `npx thinkthen` run the command? (Ian)**
Agents install tools through `uvx` and `npx` far more than through Homebrew or Cargo, and MCP clients configure servers that way. ruff and biome ship their command-line executables inside ordinary PyPI and npm packages. The command's archive is about 3.7 MB and a wheel about 4 MB (0.1.2 release). PRD 05 Q21 builds the proxy into the command and keeps it out of the libraries. Options: ship the command as a separate file inside the existing `thinkthen` wheel and npm package; publish a second package such as `thinkthen-cli`; or leave it to `install.sh`. Recommendation: ship the executable as a separate file inside the existing packages, as ruff does, so `pip install thinkthen` gives both the library and the command, and `uvx thinkthen mcp` is the MCP Registry entry. The library still links only the engine, which keeps PRD 05's rule. The cost is one more file per wheel and per npm platform package, and package size roughly doubles.

**Q23. Awesome lists, Hacker News and YouTube: who submits, and when?**
The launch plan orders the launch: the repository's README, the site, the talk on YouTube, the blog post, Show HN, then X and LinkedIn, and then Ian opens pull requests to community lists himself. The marketing playbook lists fifteen awesome lists checked on 2026-10-06. Each list has its own entry rules. awesome-rust wants more than 50 stars or 2,000 crates.io downloads. awesome-go wants 80% test coverage and five months of history. awesome-python's editors go by PyPI downloads. awesome-duckdb asks contributors to "avoid promotional claims" and disclose their affiliation. sindresorhus/awesome does not accept "fully AI-generated pull requests". Hacker News asks that a Show HN be something people can try "without barriers such as signups", and its guidelines say "Don't post generated text or AI-edited text". Recommendation: Ian submits every awesome-list PR and every Hacker News post himself, under Q2's rule, drafted from the listing source. Order the awesome lists by fit and by entry bar: the DuckDB, PostgreSQL and SQLite lists after the DuckDB listing is live; awesome-rust and awesome-python only once their thresholds are met. Every YouTube description carries the install line and the repository link, because a viewer who becomes a star must reach GitHub in one click.

**Q24. How do we learn which channels earn their keep?**
Without numbers, tiers stay opinions. Each registry publishes download counts, and GitHub's traffic API reports the top referring sites to the repository for the last 14 days. Recommendation: a small script, run by the PM at each release, prints downloads per channel and the top GitHub referrers. Ian reads the numbers in the release summary. A Listed or Archive channel whose numbers stay near zero across two releases is a candidate to drop; a channel that sends stars moves up. The script prints, and writes no file.

**Q25. What does a builder see about where their copy came from?**
Bug reports need the version and the install route. `install.sh` already writes `thinkthen.install.json` beside the binary. Recommendation: `thinkthen status` reports the version and, when it knows, the channel it came from (install script, Homebrew, Cargo, PyPI, npm). It never checks the network for updates. The issue template asks for `thinkthen status` output. This adds no command and fits PRD 00's growing `status`.
