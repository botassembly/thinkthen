### Why the DuckDB items wait

**The scalar-bind issue.** DuckDB v1.5.5 offers a bind callback for scalar functions, and it fires at plan time. Its accessors are broken. `duckdb_bind_get_parameter_count` returns `-7`. `duckdb_bind_get_parameter` and `duckdb_bind_set_error` crash the process. A callback that returns with no bind data crashes it at cleanup with a double free. Experiment 207 isolated each step. The extension wants the bind step for two jobs. It would refuse a bad question when the query is planned, and it would hold state for a whole statement, such as a request cap per statement.

The landed extension (ticket 0110) works around both. It checks the question at the first row, before anything is sent, so a bad threshold costs zero requests. It caps requests per call, one chunk of up to 2,048 rows, and Ian's 2026-09-25 ruling adds a total per process (`databases/duckdb/README.md` lines 37 and 40). The user sees the error at the first row, which is later than plan time, and pays nothing for it. Batching ticket B13c batches inside one chunk and needs no bind step.

A real fix takes one of two paths. DuckDB could fix the accessors upstream. Ian decides whether anyone reports it. Or the extension could move to DuckDB's C++ API, which gains plan-time checks, the Secret Manager and parallel controls. That move rewrites a landed surface, adds C++ to a Rust build, and needs one binary for each DuckDB version. Neither path serves a 0.1 goal, and the workaround is tested. The extension already loads only in DuckDB v1.5.5 (ticket 0110 decision 2).

The issue's status line still says "Owner: ticket 0110 (DuckDB), not landed". Ticket 0110 landed on 2026-09-25. The line should say the issue waits past 0.1 for one of the two paths.

**The query-hook issue.** Ticket 0110 already registers every scalar through the C API with an init callback and a destroy callback, so each execution has its own state. The handler still decides by timing. A signal counts when it lands inside a running call, or within 10 ms before one starts while the same query runs. No token outlives a call, so a late signal never stops the next query (`databases/duckdb/src/signal.rs` lines 5 to 7). The gap is narrow. A Ctrl-C that lands after a query's last engine call does nothing. That query has no more requests to stop, and it ends on its own. A Ctrl-C during a call still stops it within 100 ms. The fix ties each signal to the execution state that is alive. It changes signal code that the rearm suite guards, and it adds a test for a late signal.

The issue's own trigger says to schedule it "before the surface leaves beta". Ian ruled that every surface ships together in 0.1 with no beta label. Under that ruling, the trigger reads as "before 0.1". This page still leaves it out, because the gap stops no request and bills nothing. Ian can pull it in as a medium ticket.
