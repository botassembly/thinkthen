# 0081: DuckDB uses its C++ extension API

Status: accepted 2026-09-27 by the Codex queue owner after fresh review for ticket 0201. Ian directed the C++ migration. He can overturn the bridge and packaging choices below. Runtime work follows a separate file claim.

## Decision

Build the DuckDB extension against DuckDB v1.5.5's C++ extension API. DuckDB owns registration, bind, vectors, client settings, file access, and query lifecycle. Rust keeps the public `thinkthen` engine, engine registry, throttle, cancellation token, cache, and counters. One narrow `extern "C"` bridge connects them. No Rust or C++ exception unwinds across that bridge: Rust catches panic and returns a tagged error, C++ catches its exceptions before it calls Rust or returns to DuckDB. Each side frees only memory it allocated.

The bridge never copies a panic payload into a returned defect or diagnostic. Catching a Rust unwind alone does not stop the process panic hook from writing the payload to stderr. Install one delegating bridge hook at load and use thread-local bridge depth to suppress diagnostics only for that call. Preserve the prior hook for unrelated host threads. Do not swap the process-global hook around individual calls. The host can replace a process-global hook after extension load, and simultaneous hook registration by another library cannot be ordered by this extension; the bounded proof records this coexistence limit. Engine worker threads do not inherit the caller's marker. The public engine door returns a fixed defect, but the first worker panic can invoke the hook before that catch. The product migration must prove the worker boundary separately before claiming panic payload secrecy.

The accepted internal amendment at `3d368d59` adds one private engine diagnostic scope and delegating hook in `crates/thinkthen/src/engine/workers.rs`. `public/options.rs::guarded` enters it around the existing public catch, while each `on_worker` and `scoped_observed` closure enters it on its own thread before engine work. A drop guard restores nesting depth through unwind and worker teardown. The existing fixed defect remains non-retryable. Host interrupt callbacks temporarily leave the engine diagnostic scope so direct public-engine callers retain prior-hook behavior; this touches `Stop::interrupted` and the single direct check invocation in `engine/mod.rs::Cancel::checked`. Ticket 0155 has landed, and the direct check invocation is in the 0201 branch. A check reached through DuckDB remains inside the outer bridge marker, which may suppress its diagnostic while preserving panic propagation and worker teardown. `engine/mod.rs` already exposes `workers` within the crate, so the amendment needs no module declaration or public API. The DuckDB bridge still guards bind and FFI operations before the first engine call. These two once-installed hooks may nest. An unrelated host thread reaches the previous host hook; a host that replaces a hook later can bypass either guard, which is a distinct coexistence limit rather than permission for ThinkThen to print its own panic payload.

A private child-process proof panics with distinct synthetic markers. An `on_worker` panic through the public catch and a separate `scoped_observed` worker panic leak no marker through stdout, stderr, or the returned fixed, non-retryable defect; a later call succeeds. Direct public-engine host-interrupt panics through both `Stop::interrupted` and `Cancel::checked` must reach the prior host hook and resume their original payloads after workers join. An unrelated host thread must also reach the prior hook. An in-bridge host callback may remain suppressed by DuckDB's outer marker. No test-only public fault hook or paid call is added. The design passed fresh High review at `3d368d59`. Its source still needs independent code review, and full 0201 acceptance depends on the product boundary proof.

The bridge passes one chunk's typed rows and returns typed results and a structured error. It may use a bounded serialized representation for nested `LIST` and `STRUCT` values; the first build proof must fix its exact encoding and ownership before any verb moves. The bridge contains no DuckDB object or Rust layout. The C++ side never calls the old DuckDB C extension API. The Rust side reaches `thinkthen` only through its public API. This supersedes ADR 0047's DuckDB-specific raw C API choice while keeping its public-engine boundary and unpublished Rust crate.

The first target remains v1.5.5, the repository's CLI, Python package, and `tools/version.env` pin. The C++ source and template are pinned to that release. The package builds one binary per DuckDB version and platform, and its metadata names both. The gate loads the packaged binary in the matching stock CLI and Python module with no Rust toolchain in the load process, and checks that a different DuckDB version refuses it. A successful in-tree DuckDB shell run alone is insufficient. DuckDB states that C++ extensions use internal APIs and may change between versions, and that extension binaries are version and platform bound: [C++ API](https://duckdb.org/docs/current/clients/cpp), [extension distribution](https://duckdb.org/docs/lts/extensions/extension_distribution), [C++ template](https://github.com/duckdb/extension-template).

## Bind and execution

Register the existing SQL names and overloads plus ADR 0080's tenth scalar, `thinkthen_try_details`, as volatile C++ functions. A bind callback reads constant question, question-set, member-list, relation-rule, and deadline arguments when DuckDB can fold them. For the nine ordinary scalars it parses and validates them before any engine call, and keeps validated data in `FunctionData`. `FunctionData::Copy` and `Equals` preserve prepared statements and parallel plans. A nonconstant argument remains legal. An ordinary invoke validates all rows in its chunk before sending that chunk's first request. Bind does not read a row-dependent value or send a request. A bad constant on an ordinary scalar raises a DuckDB bind error with the same `thinkthen <kind>: ` classification and the stub counts zero requests.

`thinkthen_try_details` is the explicit exception to fatal bind and whole-chunk validation. Its bind records a foldable bad question as typed usage or local failure data instead of raising; execution emits ADR 0080's safe failed JSON value for each non-`NULL` row using that argument. A nonconstant question is read and parsed per distinct row, and one row's usage, local, or backend failure does not prevent a later good row from answering. A SQL `NULL` input returns SQL `NULL` before argument read or parse. Host interrupt, cancellation, deadline, and defect remain statement errors. The try path never copies raw exception text, question text, evidence, key, file path, cache path, or backend address into a failed value. The ten output types and NULL handling follow `databases/duckdb/README.md` and ADR 0080; `thinkthen_annotate` remains JSON text.

Use one `ClientContextState` per connection as the statement owner. Its `QueryBegin` captures a monotonic start, the I2 query expiry, and the current SIGINT sequence. Every scalar expression and chunk on that connection reads the same state. `QueryEnd`, on success or failure, ends it and spends a signal that arrived after the last engine call. The next query snapshots a new signal sequence. A state first created while a query is binding missed that query's `QueryBegin`; it initializes once from that active query before its first call. That first-use fallback starts the time budget late and does not claim to bound earlier SQL work. Prepared execution and a state already registered use `QueryBegin`. The proof must show both paths, including two scalar expressions in one statement. An `init_local_state` is per expression and cannot by itself own a statement. The official v1.5.5 headers define [scalar bind and local state](https://raw.githubusercontent.com/duckdb/duckdb/v1.5.5/src/include/duckdb/function/scalar_function.hpp) and [ClientContextState query callbacks](https://raw.githubusercontent.com/duckdb/duckdb/v1.5.5/src/include/duckdb/main/client_context_state.hpp); [ClientContext dispatch](https://raw.githubusercontent.com/duckdb/duckdb/v1.5.5/src/main/client_context.cpp) calls them at query start and end.

Ticket 0200 and ADR 0080 own the SQL time-budget contract. Ticket 0201 implements its DuckDB hook once 0200 is accepted. `SET thinkthen_query_budget_ms = n` takes `-1` for none, `0` for spent, and a positive representable millisecond limit; other negative or unrepresentable values are usage errors. The owner passes `min(remaining query time, per-call deadline)` to the existing Rust `CallOptions` before each send and refuses an expired query before a send. The existing per-call `thinkthen_max_requests` and process `thinkthen_max_requests_total` remain count limits; this ADR adds no query count setting. Rust retains I2's engine residency and historical counters. A query deadline or host cancellation stays a statement error, including for an I2 try-value function.

The C++ migration changes no key channel. `THINKTHEN_API_KEY` remains the key, and the extension never writes it to SQL, a log, a recording, or a DuckDB secret. A DuckDB secret type would change user configuration and persistent-secret risk, so it requires its own ticket. The prior C++ comparison makes it possible, but the two issues this ticket closes require bind and query lifecycle, not a new credential surface. `@file`, SQL cache folders, and `thinkthen_relate` continue to obey the caller's current file and database rules.

## Build and proof boundary

First link a tiny C++ extension to a Rust static library and load it in the stock v1.5.5 CLI. Then prove ordinary bind-time validation, try-value recovery from a bad foldable constant in a prepared statement with a later good row, and query begin/end, including first use, prepared execution, parallel chunks, a failed statement, and late SIGINT. Only then port all ten scalars, `thinkthen_usage`, `thinkthen_warm`, and `thinkthen_relate`; remove the raw DuckDB C API dependency and entry point in the same landing change. Existing loopback and conformance suites prove the SQL contract, secrecy, cancellation, settings, file access, and saved answers. The package check proves the shipped artifact.

The build records source and artifact digests, runs offline after the pinned toolchain is installed, and never makes a paid call. Ticket 0201 owns the full proof and the changes to the extension, package scripts, policy check, pages, and issue disposition. This ADR does not authorize an upstream report. Ian retained that choice in `2026-09-21-the-scalar-bind-surface-is-unusable-on-duckdbs-stable-c-api.md`.
