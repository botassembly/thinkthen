# ADR 0094: Recoverable batch outcomes for a native details vector

- Status: Proposed for fresh independent design review. No Rust method, C ABI, or B13c runtime is built. Ian may overturn this proposal.
- Date: 2026-09-28

## Context

B0/B13c requires DuckDB vectors to pack at `max`; `thinkthen_try_details` already returns safe failed JSON for a recoverable row while later good rows continue. A packed backend reply can answer some logical questions and fail others. `core::reply::Reply::outcomes()` retains those individual outcomes, but `core` and `engine` are private to the `thinkthen` crate. DuckDB's `thinkthen-duckdb-bridge` is a separate Rust crate and cannot call them. Accepted ADR 0089's public `Batch<T>` stops at the first failed record and cannot serve this SQL contract directly. A permanent row-isolated exception would leave B13c incomplete.

## Proposed boundary

1. Add one documented but `#[doc(hidden)]` native-adapter method on the **public** `thinkthen::Engine`, implemented in a private `public/native_batch.rs` child: `details_many_recoverable_with<Q: DetailQuestion + ?Sized>(&self, question: &Q, rows: &[String], options: CallOptions<'_>) -> Result<Call<Vec<RecoverableDetails>>, Error>`. Register that child in `public/mod.rs` and re-export the public, non-exhaustive `RecoverableDetails` enum there: `Answered(Details)` or `Failed { kind: ErrorKind, retryable: bool, cause: Option<FailureCause> }`. Only Usage, Local and Backend can inhabit `Failed`; `cause` is `Some` for a failed logical answer and `None` for a failed whole request or local preparation. The `Call` owns final per-call facts under ADR 0089. A started fatal Cancelled, Deadline or Defect is an outer `Error` with final facts after worker join; a pre-start refusal has none. Per-row failed members do not pretend to hold final call facts. `Details` retains full answered detail, including request identity, without a second model call. This is an intentionally widened Rust surface despite `#[doc(hidden)]`; it requires fresh public-surface review and a same-candidate compile check. The separate bridge must match a non-exhaustive enum with a fatal Defect fallback for an unknown future variant. It does not change the existing `Batch<T>` iterator, ordinary `details_with`, or the six error kinds.
2. Inside `thinkthen`, adapt the fixed typed question and each input text to the existing `core::BatchRecord`; use **one** `core::Batcher` with the accepted batch/context/profile/size controls. Its `Batch::{questions,outcomes,row_questions,plan,body,digest}` already maps duplicate slots to logical outcomes and exact wire requests. `engine::facade::Engine::ask_batch` currently sends the closed body **once** through replay, cache, retry, budget and transport; it performs no 413 split. The CLI alone wraps it with one halving in `cli/asking/batched.rs::split_answered`. Require a real, shared private `facade::Engine::ask_record_batch_with_one_split` adapter as a B12a implementation prerequisite, available to both B12a's stopping stream and this native method. If B12a lands without it, B13c must implement and review that same private adapter before claiming DuckDB packing. It calls `ask_batch` for the original; only an eligible 413 or named `max_tokens_exceeded` on a batch of at least two members invokes the existing `core::batch::halves_with_questions` with retained original `(BatchRecord, Question)` pairs, profile and context, then calls `ask_batch` for each half once. It never recursively halves or re-asks individual members. Its ordered per-half results retain the original refused attempt and both half attempts in call-scoped transport facts and preserve each half's exact digest. A recoverable failed half marks that half's members and still permits the other half; a fatal half stops admission. Strict replay and cache identity stay governed by their existing contracts; this proposal does not infer splitting from a replay miss.

   Add a `pub(crate)` facade adapter `Engine::ask_batches_recoverable` in a private `engine/facade/native_batch.rs` child that sends at most the engine width of closed batches using `engine::workers::ordered` and the implemented split-aware method. Its worker returns `Ok((batch, result))` **only** for success or recoverable Usage, Local or Backend results. It returns outer `Err` immediately for `engine::error::Kind::{Cancelled,Deadline,Defect}` (the public Interrupted path is Cancelled), including a fatal half. `workers::ordered` sets `halted` on that received outer error before admitting another request, even when an earlier request is held; it then delivers the earlier result before the fatal in order and joins already in-flight work. Do not put a fatal result inside an `Ok` envelope. This reuses the planner, request machinery, half-builder and scheduler rather than copying them into DuckDB. On a local per-row planning refusal, retain already closed batches, mark only that input row failed, and continue with the existing `Batcher` state; its `push_with_question` already retains closed prefixes and clears a refused singleton. The implementation must verify that continuation at the actual boundary. It never re-sends a request to find which member failed. It closes the batch at the caller's vector edge and retains at most that vector's results plus the bounded worker window; the DuckDB caller supplies at most 2,048 input rows.
3. For an `Answered` reply, require the logical outcome count to match the batch mapping. Map each `AnswerOutcome::Answered` through a `pub(crate)` `Details::of_member` constructor using the original question, per-member answer and one request's metadata. Extract its shared implementation to a results child because `public/results.rs` is already at 474 nonblank lines on main `5261cb93`. The constructor must take the saved public `Question` and runtime `BackendProfile` as current `Details::of` does, compute `ProfileWarning::between`, and use the shared `result_json::decision` writer that returns both JSON and the profile-aware question digest; map each `AnswerOutcome::Failed` to only its logical member and its duplicates with Backend and the existing `FailureCause` (make the current `public/annotated.rs` cause mapper `pub(crate)` for this shared conversion). A recoverable whole-request Usage, Local or Backend error maps to **all** members of that request, preserving kind and retryability, while a later independent request may still answer. The current decoder treats an all-failed reply as a request error; it therefore maps to the whole batch without fabricating good values. A missing/bad member in a partially answered reply must not discard good siblings. Freeze call facts only after all workers join, including the refused original attempt, both half attempts when sent, and any retries; deliver any ADR 0089 borrowed observation on the caller thread in ordered logical-row order, including failed questions, without keeping run-length history.
4. Add one DuckDB C ABI function beside `thinkthen_cpp_try_details_row`: `thinkthen_cpp_try_details_group(question, question_len, texts, count, deadline_ms, settings, from_file, stop) -> ThinkThenReply`. Its Rust bridge parses one compatible resolved question, copies the at-most-2,048 texts before `run_detached`, calls the public method above, then frames exactly `count` answered or safe failed JSON values as length-prefixed bytes. `reply.status != 0` is reserved for fatal errors. C++ `Decide` keeps the existing `BindDecide` exemption for `try_details`, SQL `NULL` slots and per-row `@file`/invalid-question failures; it groups only eligible rows by the complete question, context, deadline and session settings, maps returned frames to original slots, and preserves good siblings. It does not parse a second copy of the batching rule. The C ABI is native and owned by this extension; the Rust method is the cross-crate boundary. Both require ABI/public review. A temporary use of the existing row function may stage other verbs, but cannot close B13c.

## Rejected shortcuts and proof

- Exposing `core` or `engine` modules to the bridge spreads private transport and planner types across crates. Copying `Batcher` or decoding the backend reply in the bridge forks request identity and failure policy. Returning only the existing stopping `Batch<T>` loses later good SQL rows. Re-asking individual members would spend extra attempts and change answers. This narrow method and C ABI have a real surface cost, but preserve both settled outcomes.
- Reuse the canonical loopback case machinery to pin one exact packed request/reply with three logical members: good, failed (missing or wrong-kind answer), good. A fourth good member belongs to a **later independent request**. Require the first three SQL slots to be answered, safe Backend failed with `{"kind":"backend","message":"the backend did not answer; retry if allowed","retryable":false}`, answered, and the later slot answered; pin both independent request bodies/digests and exactly two transport attempts. The prospective `tools/verbs_suite.py::b13c_try_details_members` case asserts the four SQL slots against that case; a separate whole-request 503 case checks all affected slots failed while a later request succeeds, with no member-isolation resend. A separate `b13c_try_details_prepared` case proves a prepared invalid foldable question and good sibling retain safe Usage JSON and one good answer. Choose four fixed records whose content hashes do not cut before the cap of three; pin the request bytes and digests independently. A bounded internal worker witness uses the existing acknowledgement/barrier pattern with width two: hold request one, return outer fatal Deadline or Defect from request two, observe that request three is never admitted before releasing one, then assert ordered completion and joined workers. It does not need a production test hook or a stress loop. A separate one-eligible-413 case pins three actual attempts (refused original, left half, right half), exact half bodies/digests and no member-isolation resend. The prospective `tools/settings_suite.py::b13c_warm_zero_budget` case pins Deadline and zero sends. The installed branch of `check.sh` exports the unpacked `THINKTHEN_DUCKDB_EXTENSION` and invokes these three named cases after its conformance case. `harness.main` must reject an unknown selected name; its current named-case filter would otherwise report success after running zero cases. The routine branch also invokes the owning suites. These tests must run against the just-built or newly installed extension, not only a source verifier.

## Scope and authority

This proposal changes only the native recoverable details carrier. B0 owns maximal packing and first-seen request identity; ADR 0089 owns ordinary Rust stopping streams and final per-call facts; the existing DuckDB `try_details` contract owns row-isolated safe failures. The warm deadline ABI, caller-session authority, other vector types, total attempt admission and staged three-platform migration remain in ticket 0222. No new package dependency or public SQL overload is needed for this carrier. The only new outward-facing choice after technical review is Ian's approval of the additive public Rust method and enum; `#[doc(hidden)]` does not make either private. Review must verify that choice, the native C ABI, immediate fatal admission halt, implemented one-time split, saved-profile details, exact safe diagnostics and measured file caps before implementation claims.
