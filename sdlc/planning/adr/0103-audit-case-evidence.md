# ADR 0103: Show saved audit evidence one case at a time

- Status: Proposed for fresh Medium design review. The coordinator may approve this API within Ian's recorded per-case audit outcome; Ian can overturn it.

## Decision

Add `thinkthen audit RESULTS KEY --cases` as a **case-only JSONL** view. Without `--cases`, every aggregate JSONL or table byte, exit, refusal, tuning decision and `--write` or `--write-to` publication remains as it is. The case view runs the existing aggregate validation and refusal path before rendering anything; it prints no partial cases when that path refuses input. A case is one parsed answer identity, in saved result-line order, then `answers` member order, then `tag` label order. Its stable join identity is record `id` plus answer `name`, question text and `label` when present. The one-based result `line` is provenance, not a substitute for that identity. The existing `Answer::read(..., Identity::Question)`, `Key::want`, rule, duplicate refusal and set-item matching decide every grade; the view does not invent another scorer.

`--cases` accepts `--id`, `--threshold` and `--match`, which can change case identity or grade. It requires the current `KEY`; an empty key may show unlabeled rows, while a nonempty key with no labeled unfailed answer keeps audit's current refusal. It explicitly conflicts with aggregate-only `--by`, `--seed`, `--target`, `--optimize`, `--curve`, `--pooled`, `--table`, `--write` and `--write-to`; an explicitly supplied conflict exits 2 before reading either file, using the CLI's ordinary usage diagnostic. This separates read-only case inspection from publication and avoids accepting flags whose effects would be hidden. The defaults of those flags do not conflict. `--cases --threshold` still obeys each verb's current rescore limits and refusal. No existing invocation without `--cases` changes.

Each case object carries `case: true`, `line`, `id`, nullable `name`, `question` text and `label`, `verb`, raw saved `input` when present, `options` in the saved question's order when that carrier exists, `said`, `truth`, `key_value`, `outcome`, `probability`, `probabilities`, nullable `top_two`, `item_counts`, `usage` and `usage_scope`. The implementation may choose a compact stable field order, but the named types and absence rules are normative. `said` is the answer under the selected rule, not merely the raw `value`. For scalar graded answers, `truth` is the normalized `Key::want`; for sets it is the saved keyed items. `key_value` is the raw value of the matching key member, or null when absent. It remains visible on a failed answer without claiming that the key was valid for grading. `outcome` is exactly `right`, `wrong`, `unsure`, `tied`, `unlabeled`, `failed`, or `items`. Failed takes precedence, keeps the original identity/input and raw key value, and has `said: null` and `truth: null`; it is never graded. An unlabeled answer has `truth: null`, never `wrong`. `tied` and `unsure` stay separate from `wrong`. For a labeled `recognize` or `relate` answer, `outcome: "items"` carries the filtered said items and saved key items with `item_counts: {matched, extra, missed}` from the existing item tally. It must not turn a partly matched set into a single right/wrong count. Ordinary scalar rows have `item_counts: null`.

The row's `input` comes only from the saved result line. `options` comes only from the entry's saved `question.options` for `choose`, `question.labels` for `tag`, or `question.levels` for `score`, in array or object member order as applicable; it is null when that carrier is absent. `probability` and `probabilities` copy valid saved answer fields rather than deriving a missing distribution. `top_two` is present only for a `choose` distribution that has two options with saved sent order and valid numeric probabilities; rank by probability, breaking a tie by that sent order. It is null for other verbs, missing or incompatible options, or fewer than two options. The full distribution remains available, so a tie among three is not reduced to two holders. No top-two promise is made for every verb.

`usage` copies the valid saved `meta.usage` token pair, otherwise it is null. When present, `usage_scope` is `"result_line"`; otherwise it is null. On an `annotate` line, several criterion rows refer to the **same** root usage object, which is not a per-criterion charge and must not be summed across those rows. A packed saved row may already contain an upstream apportioned usage value; audit neither redivides nor recomputes it. Missing, null or unusable usage means unknown, never zero or an allocation from whole-run `--facts`. The view does no cost calculation.

## Why this shape

A case-only stream lets a proposer consume every line without filtering out unrelated aggregate schemas. The alternative was to append marked case rows after the groups, keeping every aggregate flag combinable, but that would mix two row types and make aggregation controls easy to mistake for case controls. The explicit conflict list is smaller and clearer than silently ignoring flags. Aggregate audit remains one command without `--cases`; a caller can run it separately over the same saved files. The view is opt-in because input and key values may contain user data already present in those files.

## Normative and implementation boundary

The implementation must amend settled `specification/audit.md` with the command option, row schema, source/absence rules, set counts, conflicts, unchanged default and no-send statement; update audit command help in the same landing. `specification/settings.md` needs no new setting row because this flag adds no setting or environment source. Existing `site/` ownership remains separate. The [ticket](../../tickets/0257-audit-case-evidence.md) and [preflight](../../records/0257-audit-case-preflight.md) name the exact file claim and proof. This decision does not design uncertain-case selection, repeated runs, per-case costs, a top-two representation for other verbs, or reconstruction of absent result metadata.
