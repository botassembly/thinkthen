# ADR 0103: Show saved audit evidence one case at a time

- Status: Proposed for fresh Medium design review. The coordinator may approve this API within Ian's recorded per-case audit outcome; Ian can overturn it.

## Decision

Add `thinkthen audit RESULTS KEY --cases` as a **case-only JSONL** view. Without `--cases`, every aggregate JSONL or table byte, exit, refusal, tuning decision and `--write` or `--write-to` publication remains as it is. The case view runs the existing aggregate validation and refusal path before rendering anything; it prints no partial cases when that path refuses input. A case is one parsed answer identity, in saved result-line order, then `answers` member order. A `tag` entry expands in saved `answer.probabilities` member order when present, otherwise in `question.labels` order, exactly as the current parser does. Its stable join identity is record `id` plus answer `name`, question text and `label` when present. The one-based result `line` is provenance, not a substitute for that identity. The existing `Answer::read(..., Identity::Question)`, `Key::want`, rule, duplicate refusal and set-item matching decide every grade; the view does not invent another scorer.

`--cases` accepts `--id`, `--threshold` and `--match`, which can change case identity or grade. It requires the current `KEY`; an empty key may show unlabeled rows, while a nonempty key with no labeled unfailed answer keeps audit's current refusal. It explicitly conflicts with aggregate-only `--by`, `--seed`, `--target`, `--optimize`, `--curve`, `--pooled`, `--table`, `--write` and `--write-to`; an explicitly supplied conflict exits 2 before reading either file, using the CLI's ordinary usage diagnostic. This separates read-only case inspection from publication and avoids accepting flags whose effects would be hidden. The defaults of those flags do not conflict. `--cases --threshold` still obeys each verb's current rescore limits and refusal. No existing invocation without `--cases` changes.

Every row has `case: true`, one-based integer `line`, string `id` and `verb`, nullable strings `name`, `question` and `label`, and `input` as the saved JSON value or null when absent. `options` is a string array or null. `said` and `truth` are booleans for a graded yes/no or `tag` label, strings for an option/level/unit, or null when unresolved, tied, failed or unlabeled as applicable. `said` is `Answer::said` under the selected rule: `Yes` and `No` become true and false; `Option` becomes its text; `Unresolved` and `Tied` become null, distinguished by `outcome`. `truth` maps scalar `Key::want` the same way, and is null for failed or unlabeled rows. A failed row alone may add `key_value`, the raw saved JSON key member if one exists; this is unvalidated evidence, not duplicated normalized truth. Nonfailed rows omit `key_value`.

`outcome` is exactly `right`, `wrong`, `unsure`, `tied`, `unlabeled`, `failed`, or `items`. Failed takes precedence and has `said: null` and `truth: null`; no new validation of a failed answer's keyed value occurs. An unlabeled answer has `truth: null`, never `wrong`. For a labeled `recognize` or `relate` answer, `outcome: "items"`, `said` is the saved item-list shape filtered to `Items::kept(rule)` in that reader's strongest-first item order, and `truth` is the matching saved key item's original JSON shape and order. A recognize value keeps its `{ "entities": [...] }` shape and a relate value stays an array; these are JSON objects/lists, not the internal `Said::Items` or `Want::Items` enums. `item_counts` is `{matched, extra, missed}` with three nonnegative integers from the existing `items::tally`; every other row has `item_counts: null`. A partly matched set is not a single right/wrong case. [The preflight](../../records/0257-audit-case-preflight.md) pins complete example rows for these distinct shapes.

The row's `input` comes only from the saved result line. `options` comes only from the entry's saved `question.options` for `choose`, `question.labels` for `tag`, or `question.levels` for `score`, in array or object member order as applicable; it is null when that carrier is absent. `options` shows the question's sent order even when a tag's **row order** follows a different saved distribution order. `probability` is the parsed saved `Answer.probability` number in [0, 1] for a yes/no, `rank` or `choose` answer, or the parsed tag-label probability; otherwise it is null. `probabilities` is the saved answer object mapping option names to finite numbers in [0, 1] when valid, else null; neither field is synthesized from the other. `top_two` is an array of exactly two `{option: string, probability: number}` objects only for a `choose` distribution with at least two saved sent options and valid probabilities for all options; rank by probability, breaking a tie by the saved question option order. It is null for other verbs, missing or incompatible options, or fewer than two options. The full distribution remains available, so a tie among three is not reduced to two holders. No top-two promise is made for every verb.

`usage` copies the valid saved `meta.usage` pair of nonnegative integer `input_tokens` and `output_tokens`, otherwise it is null. When present, `usage_scope` is `"result_line"`; otherwise it is null. On an `annotate` line, several criterion rows refer to the **same** root usage object, which is not a per-criterion charge and must not be summed across those rows. A packed saved row may already contain an upstream apportioned usage value; audit neither redivides nor recomputes it. Missing, null or unusable usage means unknown, never zero or an allocation from whole-run `--facts`. The view does no cost calculation.

## Why this shape

A case-only stream lets a proposer consume every line without filtering out unrelated aggregate schemas. The alternative was to append marked case rows after the groups, keeping every aggregate flag combinable, but that would mix two row types and make aggregation controls easy to mistake for case controls. The explicit conflict list is smaller and clearer than silently ignoring flags. Aggregate audit remains one command without `--cases`; a caller can run it separately over the same saved files. The view is opt-in because input and key values may contain user data already present in those files.

## Normative and implementation boundary

The implementation must amend settled `specification/audit.md` with the command option, row schema, source/absence rules, set counts, conflicts, unchanged default and no-send statement; update audit command help in the same landing. `specification/settings.md` needs no new setting row because this flag adds no setting or environment source. Existing `site/` ownership remains separate. The [ticket](../../tickets/0257-audit-case-evidence.md) and [preflight](../../records/0257-audit-case-preflight.md) name the exact file claim and proof. This decision does not design uncertain-case selection, repeated runs, per-case costs, a top-two representation for other verbs, or reconstruction of absent result metadata.
