# ADR 0126: Add recognition stage context and boundary proposals

Accepted by the queue owner after fresh design review for tickets 0478 and 0479 on 2026-10-08. Implementation remains required in 0.2. ADR 0125 supplies the typed Request and shared admission path. Ticket 0489 separately supplies per-record context. Ian can overturn the spellings, precedence and proposal contract below.

## Evidence

At main `eb023f4bc077a73f8abe6a86b946d6594c776d42`, `engine/facade/recognize.rs` runs boundary questions, groups kind and edge questions into step-2 requests, and then plans relation questions. `core/recognize/bilou.rs` already decodes valid BILOU paths and computes P(span). `core/recognize_file.rs` owns saved declarations and their canonical description. `core/recognition_result.rs` represents classified entities, and `public/complete/recognize.rs` reports actual staged observations. The contracts are `specification/recognize.md`, `records.md`, `cache.md` and accepted ADRs 0124 and 0125. These decisions extend those contracts for 0.2. `engine/store.rs::lookup` and `engine/store/fixture.rs::Replayed::get` load individual question answers, not complete recognition values. `result_json/complete/recognize.rs::recognition` builds the aggregate identity from the resolved spec and actual stage trace. `core/identity/trace.rs::LogicalTrace::identity` includes that resolved reading, and `core/identity/answer.rs::ResultIdentity::of` hashes the reading with scope and accepted observations. This existing separation permits boundary answer reuse while keeping recognition modes distinct.

## Stage context

Define one typed `RecognitionStageContext` with optional string members `boundary`, `kind_edge` and `relation`. The second member serves both questions sharing a step-2 request. The canonical Request recognize options member is `stage_context`. Saved version-one questions place the same object under `recognize.stage_context`. Native Rust uses the same edge type and typed `boundary`, `kind_edge` and `relation` setters. Generate binding types and schema from Request; add no parallel carrier grammar.

CLI adds `--boundary-context TEXT`, `--kind-edge-context TEXT` and `--relation-context TEXT`. These are literal strings. Existing `--context FILE` retains its file behavior. Each flag may appear once. No environment or engine configuration setting supplies stage context.

Resolve each stage independently. A supplied call member replaces the corresponding saved member; omitted call members retain saved members. A resolved stage member then replaces the record context selected by 0489. An omitted stage member uses that record context; an absent record context uses the existing whole-call context. A present empty string clears that stage's context. An empty per-record string clears fallback for all stages without a stage override; an explicit stage override still applies. Context strings are never concatenated. Unselected stages receive none of another stage's override.

Stage context accepts exact strings, including empty and multiline strings. Null, other types, unknown members and duplicate members refuse. A present empty object has the same behavior and canonical identity as omission. Validate selected per-record context under 0489 even if all stages override it. Stage context remains plain caller text and does not change that ticket's pointer or object-declaration rules.

Complete output retains the resolved nonempty stage-control object in `question.stage_context`, including explicit empty member strings. Bare output receives no context member. Debug withholds context. Canonical question description omits an empty object. The question reading digest excludes stage context, just as existing call context stays outside the saved question digest; effective context enters each affected stage's ordinary state/question identity. Complete answer identity includes the resolved control declaration and actual observations. Rebuilding the saved declaration uses the retained strings.

## Boundary mode

Define typed `RecognitionMode::{Whole, BoundaryOnly}` with wire values `whole` and `boundary_only`. Request recognize options uses `mode`; saved questions use `recognize.mode`; Rust uses the same enum; CLI uses `--mode whole|boundary_only`. An explicit call mode replaces saved mode. An omitted call mode retains the saved mode. Absence from both resolves to whole. Canonical descriptions omit whole, including explicitly supplied whole, preserving default bytes.

Boundary mode uses the existing tokenization, windows, BILOU probabilities, valid-path decode and caller kinds, descriptions, instructions and entity definition. Its boundary wording, options and request bodies remain identical to whole recognition with the same effective boundary context. Reuse those individual boundary answers through the ordinary cache and replay paths. Encode boundary_only in the resolved recognition spec passed to the existing aggregate identity calculation; omit whole as today. Even when whole recognition asks no later questions, its complete answer ID differs from boundary_only because the resolved reading differs. Each invocation rebuilds its typed value from its selected mode and accepted boundary observations. A whole entity value is never loaded or relabeled as proposals. This settles ticket 0479's mode-isolation requirement at the aggregate/result boundary and introduces no extra model wording, cache domain or replay format.

[Ticket 0479](../../tickets/0479-recognize-boundary-only.md) and [ADR 0125](0125-one-request-contract-and-native-admission.md) distinguish reusable boundary question answers from mode-specific aggregate answer IDs and typed recognition values.

After decoding, return the found stretches directly. Create no kind questions, edge questions, settled entities or relation plans. Caller kinds guide boundary questions; they assign no proposal kind. Boundary proposals preserve the decoded spans and punctuation, even where whole recognition would adjust edges or decline a kind.

Return a distinct typed value variant. Its bare JSON is:

```json
{"mode":"boundary_only","proposals":[{"text":"Ada","start":0,"end":3,"length":3,"probability":0.9876}]}
```

An empty successful value is `{"mode":"boundary_only","proposals":[]}`. Proposals contain no `kind`, `strength`, `entities` or `relations`. Their text and offsets follow the existing host-specific offset rules. Order proposals by start, then end. Keep original record positions and locations. Own the value and detail variants in the existing typed recognition result module, `core/recognition_result.rs`. The canonical serializer in `core/result/complete/recognize.rs` emits the selected variant through the existing result/2 carrier; `result_json/complete/recognize.rs` continues to assemble its actual trace, reading and usage. Native complete readers and generated host readers expose the proposal variant explicitly rather than manufacturing classified entities. Derive both result schemas through `schema_tests.rs` and `schema_tests/complete.rs` from those serializer types; add no hand-written result schema or independent host JSON shape. Whole selects its existing serializer without a mode member or union wrapper, preserving exact bare and complete bytes and existing answer IDs.

`probability` is existing P(span), computed over valid paths with the existing probability floor. Round it to four decimal places. `--threshold` keeps proposals whose printed probability meets the cut, with the existing default 0.5 and valid single-cut range above zero through one. Cutting changes no boundary questions, decode or request count. Complete boundary details contain `pieces` and `proposals`; the latter lists every decoded proposal with its probability before the cut. They contain no fabricated kind, edge or pair distributions. Complete output and saved questions retain mode so rebuilding and rescoring select proposal probability.

## Relations and admission

Boundary mode refuses any supplied relation declaration, including an empty saved array, any explicit relation threshold, and any `relation` or `kind_edge` stage-context member. Empty strings still count as supplied members. This check applies after saved/call mode and stage overrides resolve, and accounts for explicitly supplied controls before defaults are inserted. The whole serializer's implicit default relation threshold is not an authored control. Boundary canonical descriptions omit that inapplicable default, enabling valid output to rebuild. Reject conflicting saved controls rather than silently ignoring them.

The native RequestDefinition authored-grammar encoder must preserve that distinction during a wire round trip: omit an implicit relation threshold and retain an explicitly authored one. The previous encoder emitted the whole default as if supplied, causing a native whole definition with a boundary_only call override to refuse its own serialized form. This narrow repair changes RequestDefinition's default wire encoding. Whole complete output, saved canonical question descriptions, reading digests, request bodies and result identities retain their existing bytes and meaning. The code review checks both the native-to-wire admission regression and default whole identity preservation.

Use one safe diagnostic: `boundary_only recognition takes no relations, relation threshold, kind_edge context or relation context`. Invalid modes and malformed stage context receive usage errors without echoing caller text. CLI argument faults exit 2; invalid saved definitions retain the existing saved-definition exit convention. ADR 0125 header admission catches available controls before question reads or source enumeration. Loaded-definition admission precedes evidence reads. Validate inline records together before any send; bounded feeds retain the existing admitted-prefix behavior.

Prepare exact boundary bodies with their effective context and existing resolved size/profile caps. For whole mode, admit all available static context/question feasibility checks using the appropriate stage context before any send; do not probe a skipped kind stage in boundary mode. Unknown future edge and relation bodies retain runtime size checks before their own sends. Earlier stages may already have completed when such a derived body cannot fit. The new controls create no truncation, automatic tuning or request-size exemption. Context counts toward ordinary body limits and budget planning. Boundary plans report exact boundary requests and zero later-stage bounds.

## Identity and acceptance

Preserve exact request bodies, wire questions, question keys, request digests and default canonical declaration bytes when mode is omitted or whole and stage context is omitted or empty. A changed stage context changes only that stage's direct state/question identity. Changed earlier answers can naturally change later generated questions. Explicit context equal to fallback reuses the same effective request identity. An empty string clears fallback using the existing no-context encoding. A changed threshold filters the same answered boundaries locally.

Generic offline cases run through native typed calls, canonical Request, valid CLI, saved readers and generated bindings. Pin outgoing bodies and ordinary key derivation, rather than introducing a second fingerprint. Use two records with distinct context, a shared fallback, an explicit empty record context and one override at a time. Assert every stage receives its intended text, unaffected direct stage keys stay equal, and jobs eight preserves separation. Pin omitted and explicit-default bodies against existing recordings.

Boundary cases assert exact proposal spans and pre-cut probabilities, rounding at the threshold, caller wording in every token question, and only boundary observations. Count loopback requests to prove zero kind, edge and relation sends, including a saved boundary_only declaration with no call mode override. Assert equal boundary request bodies and question keys across modes with the same effective boundary context. A whole recording may answer boundary_only with zero sends; assert a proposal value and its mode-specific complete answer ID. A boundary-only recording may answer whole boundary questions, but missing kind, edge or relation answers retain ordinary replay-miss behavior. Include a one-piece no-kind case where whole asks no later questions and a no-proposal case; both modes must still have distinct aggregate answer IDs. Assert actual per-question observation identities remain reusable, and no whole entity value appears as a proposal value. For malformed modes/context, forbidden controls, invalid pointers and statically impossible bodies, count source enumeration, evidence reads and loopback requests at the appropriate admission boundary; assert zero sends. Loaded-question tests permit only the necessary definition read. Do not use plan output as no-send proof.

Implement 0489 first, then shared typed controls and admission, then staged execution and typed proposal results, then generated surface adoption and shared fixtures. Define each rule once and compare generated schema decoding with real admission to avoid duplicated truth. Use generic fixtures and existing offline gates; these changes make no accuracy claim.
