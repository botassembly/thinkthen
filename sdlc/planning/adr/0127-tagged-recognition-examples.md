## Input forms

Define one typed `RecognitionExample` input enum with two JSON forms. A string holds one inline bracket example. An object holds `text`, `entities` and optional `kinds`. Each entity is a closed object containing `start`, `end` and `kind`. Offsets are nonnegative Unicode-scalar positions in the decoded original text, with inclusive start and exclusive end. No byte or UTF-16 interpretation is accepted at this interchange boundary. The typed native constructor receives the same fields directly.

```json
"[[PERSON|Ada]] works at [[ORG|Orbit]]."
```

```json
{"text":"Ada works at Orbit.","entities":[{"start":0,"end":3,"kind":"PERSON"},{"start":13,"end":18,"kind":"ORG"}]}
```

Bracket notation uses `[[KIND|TEXT]]`. Remove its delimiters and label to obtain original text and spans. Backslash escapes backslash, square brackets and the vertical bar. Other escapes, unclosed delimiters, nested entities, empty kind labels and empty entities refuse. Strings outside entities retain their exact decoded text. Users who need arbitrary multiline text or complex punctuation may use the structured form.

`--examples FILE` reads UTF-8 once at the edge. Ignore empty lines. If the first nonempty line starts with `{` or a JSON string quote, read JSON Lines of the two forms above; otherwise each nonempty physical line is one bracket example. Do not infer forms from a filename extension. A JSON Lines file may mix the string and object forms. Malformed rows refuse the whole file; do not fall back to a second parser after choosing the form. An empty file means an empty example list. Files contain no mandatory bundle wrapper, saved question definition or executable instruction.

`--examples-field POINTER` selects an array of the same example values from each original JSON record. An absent pointer member uses the shared list. A present empty array clears that list. A present null or non-array value refuses. A missing pointer through an invalid container follows the existing pointer-selection errors. Header admission checks pointer syntax and incompatible non-record framing before source enumeration. Plain line and located text inputs may use shared examples but cannot select an examples field.

The canonical Request recognize options add `examples`, an optional array of `RecognitionExample`, and `examples_field`, an optional validated JSON Pointer. Record descriptors add optional typed `examples` for explicit per-item values. Explicit item examples conflict with an examples projection pointer, as explicit item context conflicts with its pointer under ADR 0125. Shared examples and a projection pointer may coexist because selection replaces fallback. Absence retains fallback; an explicit empty array suppresses it. Null refuses. Unknown and duplicate control members refuse under canonical Request. No general CallOptions field permits examples on other functions. Generate the schema and binding types from these edge types once in the Request owner lane.

Examples remain call inputs. Add no saved-question, environment, configuration or metadata-schema spelling. Family migration tickets expose the settled typed examples and projection through their Request adoption rather than inventing another host grammar.

## Vocabulary and spans

The two requirements to reject undeclared kinds and render other entities OUT need separate meanings for declaration and selection. Default each example's allowed vocabulary to the resolved recognition kinds. When recognition has no kinds, its default vocabulary is the existing generic `ENTITY`. A structured example may supply its own nonempty, unique ordered `kinds` array to declare a broader vocabulary. Every span label must occur in that example's effective vocabulary. An unknown label refuses before any sends. This optional declaration permits retrieved examples to contain types outside the current recognition selection without weakening typo detection.

The current pass is the resolved recognition's own kind set, or `ENTITY` when that set is empty. This change adds no loop, separate pass selector or automatic routing. A valid example entity outside that set produces OUT for all its pieces. It remains a validated entity, so invalid edges and overlaps still refuse. Bracket examples use the default vocabulary; a broader-vocabulary example uses the structured form. A mandatory global bundle vocabulary would complicate both simple file forms, while rejecting every kind outside the current selection would make the PM's OUT rule unreachable. The optional per-example declaration is the smallest distinction that supports both rules.

An example must have nonblank decoded text and at least one recognition piece. Its entity list may be empty to teach OUT. Check integer ranges, start before end, end within text, duplicate and overlapping spans, and both edges against recognition's existing pieces. A span must start at one piece's start and end at one piece's end; whitespace outside those pieces is not an entity edge. Interior whitespace remains allowed. Adjacent spans remain separate. Sort valid entities by start for canonical rendering without changing their text or edges. Combining marks and punctuation obey the existing piecer. Do not round an invalid edge, repair a span or reinterpret its units. Unknown members and duplicate structured members refuse. Diagnostics identify the example or record ordinal and fault category without echoing text, labels or paths. Debug withholds example contents.

## Boundary rendering and context

Pure core code parses brackets, validates the typed spans against the existing piecer and renders examples. For each example, keep its snippet text and generate every piece question in original order through `step_one_questions`, using the resolved caller instructions, definition, descriptions and current kind selection. Follow each question's actual text with its answered boundary label. A one-piece selected entity answers SINGLE; longer selected entities answer BEGIN, INSIDE and END. Include its declared kind beside answers inside a selected entity. All remaining pieces answer OUT without a kind. JSON-quote answer values and piece text in the rendering so embedded newlines and punctuation remain unambiguous. Do not reproduce question wording or tokenization in a second renderer.

Carry the ordered rendered examples once in each boundary request's state, beside the existing evidence, rather than repeating the examples in every live piece question. Extend the typed State transformation with an examples wrapper containing `examples` and `evidence`; its examples value is the ordered rendered text list. Then apply the existing context wrapper without changing the selected 0489 context value. With examples and context, the logical state is `{"context":C,"evidence":{"examples":[R],"evidence":E}}`; without context it is `{"examples":[R],"evidence":E}`. With no examples, use the current state bytes directly. Apply the same transformation before boundary admission, planning and live execution; recompute ordinary keys through State and Asks. Do not hand-build adapter bodies.

Context remains independently selected and validated under 0489. Empty per-record context clears context fallback without clearing examples, and empty per-record examples clears examples without clearing context. Future boundary stage context under ADR 0126 replaces only context. Examples never replace, concatenate with or enter that context value. The kind feasibility probe, kind/edge questions and relation requests receive their normal context and no examples. Later questions can naturally change when boundary answers change; their direct request identity gains no example-only field.

## Admission, identity and plans

Validate the shared examples after resolving the question but before reading evidence. Validate all explicit inline records, all selected per-record examples and each exact initial body before any sends. The CLI examples-field path admits its collected records together, as its context-field path already does; the new Request inline-record path uses shared admission. Bounded feeds validate each available record before that record's sends and retain ADR 0125's admitted-prefix behavior. A bad later feed record cannot promise zero earlier sends. The only file reads allowed before definition admission are those needed to load that definition; shared example and evidence files wait until then.

Use ordinary profile, request-byte, request-budget and route admission after rendering. Admit a single boundary question including all selected examples and effective context; refuse if it cannot fit alone. Preserve request splitting for groups without dropping examples. Add no truncation, automatic example count, special size exemption, token estimator or retrieval cap. Future derived stages keep their existing runtime checks. An empty input record does not bypass example validation.

Changed rendered examples change the boundary state and ordinary per-question keys, request digests and aggregate trace identity. Equal rendered examples reuse those identities across bracket and structured inputs. Empty selected examples and absence preserve current exact request bytes and keys. Keep examples outside the saved question reading digest and context digest. Complete result identity already includes actual boundary observations, so add no example fingerprint or duplicate cache namespace. A negative example is nonempty rendering and changes identity even when every piece is OUT. Ordinary replay from matching boundary recordings works unchanged; a different rendered example produces an ordinary miss. Kind/edge/relation recordings may still be reused when their actual states and questions match.

`--plan` prints the actual rendered boundary bodies already prepared for execution, including examples, and uses the existing shared token accounting on those bodies. Preserve the existing first-record request display and all-record aggregate totals; document that distinction. Do not print original span input as a substitute for rendered questions. The separate 0461 slice B owns largest-request reporting and model-window admission; 0490 must preserve its integration points and does not build another estimator or facts field.

## Implementation and acceptance

First settle the shared Request types with the 0491 owner. Add the pure parser, validation and rendering beside recognition. Add the narrow State and Asks transformations through the coordinator because those files are shared. Connect selected typed examples to boundary admission and execution, then CLI file/projection reading and plan rendering, then shared generic fixtures and the recognition specification. Native entry points call the same admission and renderer; adapters only serialize their admitted values. No dependency is needed.

Use one outside-in owner for each behavior. Compare bracket and structured forms using the exact same synthetic software text, including non-ASCII and combining marks. Assert full piece order, labels, current-kind answers, OUT for a declared broader kind and unchanged context. Two records with different examples, a shared fallback and empty record overrides establish isolation at jobs eight. Count loopback requests to establish zero sends for undeclared kinds, inside-piece edges, overlap, null, incompatible pointers and a statically oversized boundary request. Exercise inline-all-record admission separately from bounded-feed prefix behavior. Pin outgoing bodies for boundary and later stages, compare plan bodies with those sends, and assert cache/replay reuse or misses through the existing public typed entry points. Pin unchanged default requests and keys with examples absent and empty. Shared Request schema cases cover exact decoding and null/duplicate/unknown-member refusal. Existing fixtures own secrecy, cancellation and request-limit regressions; extend them only where examples introduce a distinct fault path.

The structural risks are duplicated grammar, duplicated question wording and state leakage across records. One typed example contract, one pure renderer, derived schema and immutable per-record selection address those risks. The agreed stopping rule is the focused offline checks, policy check and one source review after implementation. No paid call, workflow, release or model-quality claim follows from this ADR.
