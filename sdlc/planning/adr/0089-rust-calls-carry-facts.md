# ADR 0089: Rust calls carry their own run facts

- Status: Accepted design after the same independent Sol review of `a713e462`. The coordinator approved the routine `Call<T>` choice under Ian's facts-on-every-call outcome. No implementation or public API change has landed; Ian can overturn the choice.
- Date: 2026-09-27

## Context

ADR 0017's Rust API and ticket 0084 return bare single values, `Result<Vec<_>, Error>` for eager bulk operations, and lazy `Batch<T>` iterators. Ian later ruled in `sdlc/issues/2026-09-26-every-surface-should-give-back-run-facts.md` that every library result carries facts with no second call. The batching issue fixes the fact names and per-call meaning. ADR 0083 fixes the command's final stop facts and explicitly leaves the library return shape to B12a. A process `Counters` snapshot cannot isolate one Rust call while another call uses the same engine.

## Options and recommendation

| Shape | Caller effect | Decision |
| --- | --- | --- |
| Uniform `Call<T>` around every eager value, final facts on existing lazy `Batch<T>` | One `facts()` rule for primitives, vectors and structured results; breaking Rust signatures and a same-candidate compile migration across adapters | **Recommend.** The migration is broad but mechanical, and no bare call escapes Ian's every-call rule. |
| Add facts to `Ranked`, `Found`, `Recognized`, `Details` and other existing structs, wrap primitives and vectors | Fewer edits to already structured values, but several result-specific facts rules and the same primitive/vector signature breaks; bulk vectors cannot naturally hold whole-call facts on each element | Decline. It does not materially reduce adapter work or resolve filtered-out detail. |
| Add `*_call` siblings and keep old bare methods | Old callers compile; new callers opt in to facts | Decline without a separate Ian ruling. Old methods would still be library calls without facts, contrary to the accepted outcome. |

The recommended public choice amends ADR 0017 and ticket 0084 only after review acceptance. Its breadth needs exact file claims and all-current-consumer compile proof in B12a. Native port facts behavior remains with B12b–B13e, but those adapters must unwrap the changed Rust value or use the approved compatibility route in the same Rust candidate.

## Proposed decision

1. Eager Rust methods and matching root free functions return `Result<Call<T>, Error>`. `Call<T>` owns one value and one immutable `Facts`, with `value()`, `into_value()` and `facts()` accessors. This is an intentional source-breaking public signature change. All currently compiling native, SQL, frame, root, example and conformance Rust consumers must adapt in the same candidate; their own outward result shape stays until later port tickets. It does not change the bare command output or SQL scalar shape.
2. Lazy methods keep `Batch<T>: Iterator<Item = Result<T, Error>>`. After exhaustion or a terminal error, `Batch::facts() -> Option<&Facts>` returns final facts; before completion it returns `None`. Reading facts sends nothing. Dropping an unfinished batch cancels and joins its work as before, but a dropped value cannot return a final report. A first-error row still appears once and then the iterator ends.
3. `Facts` exposes `records()`, `requests_sent()`, `cache_answers()`, optional `input_tokens()` and `output_tokens()`, `seconds()`, and optional `model()`. The names and presence rules come from the batching design and run-facts issue. `records` is the finished ordered prefix, including filtered-out rows; it excludes a failed row and later speculative rows. Attempts and retries count every actual transport start of the call, including a failed request and starts from later in-flight work joined after an ordered stop. Cache/replay answers and live usage/model presence include replies received through that join. One missing usage report in a mixed live run makes token totals absent. These facts are collected in call-scoped state at the send, reply and ordered-completion boundaries, not by subtracting process counters or reading only success-only `Answered`. No price, server duration or vendor request ID is guessed.
4. Keep six public `ErrorKind` variants and the exhaustive public `Error` variants. Store optional facts in the private `ErrorDetail` payload; add `Error::facts() -> Option<&Facts>`. It returns a frozen report for a started eager failure, including zero-send cancellation, and `None` before a call starts. The lazy iterator emits one terminal error; both it and `Batch::facts()` expose the same final report after every in-flight worker joins. `Stop::finish` fixes cancellation and callback-panic precedence before that freeze. Dropping a lazy iterator still joins but returns no later object. Existing failure kinds, retryability and stop order remain. Facts never carry raw evidence, context, key or backend reply text.
5. `CallOptions::observe(&'a (dyn for<'r> Fn(RecordObservation<'r>) + Send + Sync))` borrows a caller-owned callback for the call or lazy iterator lifetime. The callback receives ordered events on the caller thread. A `Question` event names its zero-based input index, optional `annotate` member name, optional `recognize` question kind (`boundary`, `kind`, `edge`, `relation`) and within-kind question position. It borrows a `QuestionDetail<'r>` with the complete question digest, typed answered judgment or `FailureCause`, probabilities in declared order when supplied, optional confidence, answer model, URL, exact request digests, that question's per-row usage share, requests-sent share, cache/replay flag and failed-question count. Absent answer fields stay absent for a failed logical question; failure does not become null or an invented zero. A `Row` event names the same input index and its final typed value, after its question events; it is emitted even when `filter` suppresses the row from the iterator. An `annotate` row emits one named `Question` event per set member in set order, including `Annotated::Failed`, then one `Row` event; its failed-question count equals the number of failed members, not the number asked. `recognize` emits question events for each completed request chunk of each step in step/question order, then the final `Recognized` row. `find` and `relate` emit their actual candidate/relation question events, not a made-up single decide detail. A partially answered batch observes its valid ordered prefix and stops at the first failed record; a failed question may have an event, but the terminal record has no finished `Row` event. No events are delivered for rows after that ordered stop even if their in-flight requests later reply; those attempts and replies still enter final `Facts`.
6. Reuse `Details` rather than creating a partial second detail model. Its current public fields already cover one decide/choose/tag/score judgment's value, probabilities, confidence, question digest, model, URL, request digests, usage, requests sent and cache flag; `Details::failed_questions()` is currently always zero. It has no named `annotate` member, failed-question variant, find/relate candidate question or multi-step `recognize` representation. The implementation extracts their common private metadata/answer carrier and lets both existing `Details` accessors and the borrowed `QuestionDetail` view read it. Add only the typed name/stage/failure fields the current `Details` cannot express. Do not fabricate a `Details` for a failed member or a whole multi-step call. The borrowed view is valid only during its callback; a caller may copy selected fields into its own storage. The library retains at most the bounded scheduler window and one request chunk's details, not a run-length history. Eager calls deliver all question/row events before returning; a simple one-question `Call<T>` may also retain its ordinary `Details`, while multi-question calls use the observer. An observer panic unwinds on the caller after workers join, matching the existing callback path; eager paths must prove that join order. This is a public user path, not a test-only hook, and it makes full detail available without another model request.

## Existing decisions retained

ADRs 0048, 0053 and 0055 continue to fix batch shape, limits and shares. ADR 0056 continues to fix recognize's separate three-step planner. ADR 0083 remains the command's stop and count contract. ADR 0017's blocking engine, shared throttle, fork rebuild, six error kinds and cancellation rules remain. This proposal amends only the public Rust return shape and call-scoped facts access once reviewed and accepted.

## Accepted 0212 source-boundary clarification

Status: Ian approved the ADR 0053 caller-owned iterator amendment on 2026-09-28. It does not change the accepted `Call<T>` or facts decision. A synchronous Rust `Batch::next()` may remain in a caller-owned `Iterator::next()` until a record or end arrives. No send or row observation can be promised while that call blocks. A `Max` batch closes only on an actual batch boundary for this input type; explicit `BatchSetting::Records(1)` preserves one-record interactive progress without pulling the next caller item first. Once a batch closes, the accepted ordered stop, worker join, final facts and caller-thread observation rules above still apply. The 50 ms command pause is unchanged.
