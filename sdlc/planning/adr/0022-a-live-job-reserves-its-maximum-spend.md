# ADR 0022: A live job spends its reservation before it starts

- Status: Decided by the agent on 2026-09-20. Ian can overturn any line
- Date: 2026-09-20

The live script guards paid development calls with one repository ledger. It currently checks only whether earlier spend has reached the limit. It neither reserves room for the next job nor prevents two jobs from reading and replacing the ledger together. Its later file scan is not authoritative: a repeated request can be paid and leave an immutable recording unchanged, and the plan already holds 3,207 tokens that had to be added by hand after a job wrote no usage record.

## Decision

- The invocation is `sdlc/scripts/live --max-tokens N JOB [ARG...]`. `N` is a positive canonical decimal no greater than 999,999,999. It is the most input-token budget the job is authorized to consume. After key validation, a relative `JOB` is resolved against the repository once, before job-path validation, charging, and execution.
- The ledger accepts exactly one positive `limit_tokens` and one `spent_tokens`, each a canonical decimal no greater than 999,999,999, with spend no greater than limit. Blank lines and comment lines are allowed. Other data, duplicate fields, leading zeroes, and out-of-range values are refused.
- One atomic lock directory at `sdlc/live-tokens.lock` is held from the ledger read until the job ends. Another invocation refuses before building or running anything.
- The script refuses when `N` is greater than the remaining budget. An exact fit is allowed. Before any paid child starts, it atomically adds the whole reservation to `spent_tokens`, atomically records the charged owner, and runs POSIX `sync`. The wrapper creates the FIFO and opens it read/write before it spawns a keyless local gate. That open does not wait for another endpoint on the supported Linux platform; the behavior is verified with dash, Bash, and Zsh. The gate closes its inherited descriptor and polls the lock until its PID is atomically recorded and synced. The wrapper then marks delivery, writes the key through its already-open descriptor, waits for receipt, checks for a pending signal, and only then creates the release marker. There is no helper or later blocking wrapper open. The release marker remains until cleanup, so the gate cannot miss it. A failed sync leaves the lock and starts no user job. The charge is never refunded automatically. A crash, signal, missing recording, repeated immutable entry, deleted file, or accounting failure therefore cannot reopen spent authority.
- The newer-JSON scan remains an informational measurement. It prints what it found and warns when that number exceeds the reservation. It never reduces or increases the durable charge. A failed job retains its own nonzero status. A successful job whose measured use exceeds its reservation exits 1.
- The lock contains a small owner file with the wrapper PID, child PID, hexadecimal absolute job path, reservation, prior spend, charged total, and state. `child_pid 0` means no child has been recorded. It holds no key. The script never repeats its contents in a diagnostic.
- The wrapper validates and copies the key into a non-exported shell variable, then unsets `THINKTHEN_API_KEY` before repository resolution or any external command. A key with no non-whitespace byte is blank. A key containing LF is refused with one fixed diagnostic at that same early boundary because POSIX line input cannot preserve LF. The FIFO preserves leading and trailing spaces, backslashes, tabs, carriage returns, and every other accepted environment byte. Only the recorded gate receives the key through process input, and only the released job shell receives it in its environment.
- Signal traps remain installed from before lock acquisition through measurement and cleanup. The first HUP, INT, or TERM fixes status 129, 130, or 143; later signals are still forwarded while the child lives and never replace that status. POSIX asynchronous shells may ignore INT, so the wrapper translates INT into TERM for the child while retaining status 130. It forwards HUP and TERM unchanged. A signal before paid work reaches a safe checkpoint and starts no user job. Every trapped wait loops until the child is truly gone, including handoff and failure cleanup. A later signal can interrupt a wait but cannot clear the child state or remove the lock. After the child starts, the wrapper reports any measurement it can make and cleans up. If the child remains alive, the wrapper keeps waiting and the lock stays held.
- An uncatchable stop can leave the lock. Recovery first reads the owner file and verifies that the ledger's `spent_tokens` is at least its `charged_total` when the state is `charged`. If the state is earlier or the ledger is lower, recovery leaves the lock and repairs the ledger to the recorded charged total. `child_pid 0` can coexist briefly with an unrecorded keyless gate. That gate polls the lock and exits after recovery removes it; it has no key and cannot start paid work. A nonzero child PID requires a separate `ps` check because a gate holding the key or a running job may outlive the wrapper. The permanent charge keeps the budget closed even if such an orphan remains. The lock stays while either recorded process remains. Once neither remains and the ledger is safe, the person removes the named temporary files, the owner, and the exact empty directory. The charge remains.

## Failure order

Key refusal happens before repository resolution and every external command. Other input, resolved job-path, and ledger refusals happen before a build or job. A held lock also refuses before either. Initial owner creation failure removes the uncharged lock when it can and otherwise leaves it fail-closed. Build failure releases an uncharged lock. Failure to prepare, install, or sync the conservative charge leaves the lock when the ledger state is uncertain and starts no user job. Failure to record or sync the keyless gate's PID stops and waits for that process before returning. After the precharge succeeds, no later bookkeeping failure can understate authorized spend.

The job's nonzero status wins over an over-reservation warning or informational scan failure. An otherwise successful job returns 1 for either condition. Signal status wins after the child stops. Every path keeps the conservative charge.

## Limit of the guarantee

The ledger now limits the sum of maxima authorized through this script. It does not know the vendor's token count before a response and cannot stop one job that violates its declared maximum. Such a breach is reported after the irreversible call. Job authors choose a conservative maximum, and no automatic refund depends on recordings or job-controlled files.

The fixed numeric ceiling keeps every subtraction and addition inside signed 32-bit shell arithmetic while exceeding the current 476,000,000-token project limit. Raising the project limit beyond that ceiling requires changing this decision and its boundary tests.

## Amendment: one local authority and a bounded supervisor

Accepted for ticket 0034 on 2026-09-20 after independent design review rejected and then accepted a full rewrite. The agent chose these changes; Ian can overturn them. The original decision remains above because ticket 0028 implemented it. This amendment replaces its storage, handoff, indefinite signal wait, recovery, build, and scan. Permanent precharge remains.

### Supported boundary

This is a supervisor for cooperative repository jobs on one authorized Linux installation. It cannot constrain an operator who restores retired code or an old authority backup, copies a grant, launches directly with the key, or detaches a job from its session. Those actions are outside the authorized workflow. Every registered worktree must retire its legacy launcher before activation. Old scripts are tested for refusal against the new checkpoint; a note or an unrecognized marker alone is insufficient.

The live tool requires Linux, readable `/proc` process identity/group fields and boot ID, `/etc/machine-id`, `/usr/bin/python3` version 3.12 or newer, `/usr/bin/git` with absolute `--git-common-dir` and NUL-delimited worktree enumeration, Unix socket pairs, `flock`, `waitid(WNOWAIT)`, atomic same-directory replacement, and file/directory `fsync`. The install rung checks the live prerequisites on Linux, and the live tool refuses unsupported prerequisites before charging. This changes no platform promise of the judgment binary. Tests exercise the exact interpreter with `-I -S`, not an environment-selected substitute.

### Authority and checkpoint

The calling checkout supplies the job, working directory, and prebuilt `target/debug/thinkthen`. Resolve Git's common directory with `/usr/bin/git -C CHECKOUT rev-parse --path-format=absolute --git-common-dir`, then `realpath`. Its private `thinkthen-live/` directory holds a permanent `lock` file and `state.json`. Keep the exclusive nonblocking OS lock until settlement; never replace or remove its inode. The execed gate receives no lock descriptor. A second launch refuses if the lock is held or a pending run exists.

State has a version, authority UUID, `active` or `retired` status, limit, total charged, and an optional pending run. Bind it to the exact validated 32-hex machine ID from `/etc/machine-id` and the hexadecimal filesystem bytes of the common directory's canonical absolute path. A process identity is the boot UUID from `/proc/sys/kernel/random/boot_id`, PID, and start ticks from field 22 of `/proc/PID/stat`; the gate must also have PGID and SID equal to its PID. Parse the stat command field correctly when it contains spaces or parentheses. Store identities privately; never print or commit them. Unknown/duplicate state keys, invalid numbers, symlinks at authority files, and inconsistent totals refuse. Numeric bounds from the original decision remain. Directory/file modes are 0700/0600.

A pending run contains wrapper and gate identities, its original charge, reservation, resulting charge, and `pending` or `unresolved` phase. Its arithmetic must agree with the total. `pending` means the job might have been released; it never implies permission to refund. A moved repository, changed machine identity, or copied authority refuses. Neither recovery nor status rewrites the binding or creates authority.

The tracked `sdlc/live-tokens` is an audit checkpoint with `checkpoint_limit_tokens`, `checkpoint_charged_tokens`, and `checkpoint_authority_id`. It contains no legacy `limit_tokens`/`spent_tokens` rows. Both historical launchers must therefore refuse it before build/job execution. Runtime state never reads this checkpoint after migration. The coordinator records `--status` into the checkpoint after paid work, retaining the maximum observed charged total and the authority ID; a stale checkpoint grants nothing.

### Audited migration and transfer

The coordinator owns migration after this ticket lands. No live call occurs during migration. Record its evidence in the ticket record. The script page must provide the exact keyless commands and expected results for these steps:

1. Enumerate every registered tree with `git worktree list --porcelain -z`. Record each HEAD and branch using `git -C TREE rev-parse HEAD` and `git -C TREE symbolic-ref -q HEAD`. `git -C TREE status --porcelain=v1 -z` must be empty; locked/prunable trees, an active worker, any live wrapper/job, and any `sdlc/live-tokens.lock` stop migration. Inspect owner identities rather than deleting a lock. Every tree must be reachable.
2. Audit each old ledger and every charged run since the last checkpoint. The known baseline is 476,000,000 authorized and 429,118 charged; use it only if all inspected evidence still agrees. Divergent ledgers require reconciliation from run records; taking their maximum can omit independent reservations and is forbidden. Unexplained spend or missing records stops migration. Do not increase the allowance.
3. Preserve every worktree directory and branch reference. For each clean, idle legacy tree, record its old revision, then `git -C TREE switch --detach LANDED_0034_SHA`. Leave the primary main tree and already-current ticket trees on their branches. This replaces the executable and checkpoint without deleting worktrees or moving old branch tips. Re-enumerate and verify every launcher/checkpoint is the landed guarded version and every tree remains clean. Dirty or active trees are never reset.
4. With all old launchers retired, create the private authority exactly once from the audited total using temporary-file sync, atomic installation, and directory sync. Refuse an existing state file; a missing file after an earlier activation is lost authority, not first use. Record the new authority UUID and activation in SDLC, without machine/path identities. A local `--status` must agree; no job is part of migration. A failure before completion leaves live work disabled.

New worktrees use the landed guarded revision or a descendant. A historical revision is inspected with `git show`, or in a specifically read-only worktree with no key and no authority to launch paid work. Before paid activity resumes, such a registered historical tree is upgraded by the same clean/idle retirement step. The current launcher checks all registered launchers/checkpoints before admitting a paid job and refuses an unretired tree. Git operations that restore old live code are forbidden while a live job runs. This is cooperative enforcement, not a defense against deliberately running historical code with a credential.

A move or another machine requires a later authorized transfer owned by the coordinator: quiesce, recover/settle, obtain the source lock, durably mark source state `retired`, record its final UUID/charge, then initialize the destination binding with exactly that charge and limit. Source retirement must finish before destination activation. On uncertainty, both remain disabled. Missing or unreachable source state is never replaced from the Git checkpoint. No automatic transfer, distributed operation, or generic initialization command is added by this ticket.

### Keyless gate and durable release

Use `#!/usr/bin/python3 -IS` for the supervisor and explicit `-I -S` for its separately execed gate. The supervisor is the initial credential owner; unsetting Python's environment does not erase its inherited `/proc/PID/environ`. Never claim that it does. Read the key as bytes, retain it only in supervisor memory, and remove it from the environment mapping before any child starts. Keep blank/LF refusals and other accepted bytes.

Every Git helper and gate receives an explicitly constructed environment: `PATH=/usr/bin:/bin` and `LC_ALL=C`, with no inherited key, Python startup variables, shell hooks, or Git configuration environment. The job receives the caller's intended environment after gate release, with its key added then and its worktree binary first on PATH. Transfer that environment through the private channel; never put it or the key in argv or state. Gate startup uses only its clean environment and Python's standard library. Tests inspect `/proc/PID/environ` of a blocked helper and a ready gate for absence of the marker, not just a subsequently read `os.environ` mapping.

Create an anonymous Unix socket pair. Spawn a fresh gate interpreter with `close_fds=True`, only its socket endpoint inherited, and `start_new_session=True`. The gate closes no unrelated inherited descriptor because none is passed; specifically, it cannot inherit the lock. After interpreter startup and session creation it sends readiness. The parent verifies PID, PGID, SID, boot ID, and start ticks from `/proc`, confirms the child is still its own unreaped child, and only then can charge. A failed spawn, socket, setsid, readiness timeout, or identity check gives no key, no charge, and no job. Close the channel and stop/wait for the owned child; never send a group signal before the group identity is verified.

Durably replace state with the increased charge and pending identities: write private temporary file, fsync file, replace, fsync directory. Only then deliver the key and job environment on the socket. The gate acknowledges receipt but still waits for a separate release byte. After checking pending signals, the parent releases it. The gate execs `/bin/sh -- JOB ARG...` with the job environment. Any EOF or protocol failure before release starts no job. Parent death closes its only socket endpoint. Fork/exec failures, a dead gate, partial delivery, and post-charge channel failure retain any installed charge; pending state is settled only after absence is proved. Job exec failure retains the charge and returns a fixed safe failure without echoing environment values.

The supervisor does not build binaries. It refuses a missing/non-executable worktree binary before charging; the caller builds first with the key removed. It also removes the newer-JSON scan and explicitly retires its measured-over-reservation warning and success-to-exit-1 rule. No replacement scan claims to detect a job exceeding its maximum. Job records may report observed usage separately. Output says charged authority, never measured spend. An ordinary job returns its status unless local settlement fails.

### Interruption and recovery

Child/channel waits use polling against a monotonic deadline. A normal paid job has no new wall-clock limit. Readiness and each unreleased handoff phase have a five-second deadline. The first HUP, INT, or TERM starts a five-second cancellation grace and fixes status 129, 130, or 143. Forward HUP/TERM to the verified group and INT as TERM. Later signals do not extend the grace. Before release, closing the socket prevents job execution. Keep the direct child unreaped with `waitid(WNOWAIT)` until signaling is finished; never let `Popen.poll()` release its PID early.

When cancellation grace ends, stop waiting for the child, preserve the charge, durably mark `unresolved`, and return the first signal status. Final synchronization and diagnostics follow the grace, so this is a bound on child waiting, not a five-second hard bound on total wrapper runtime. Tests use functioning local storage and allow scheduler margin. Kernel/storage hangs remain outside the guarantee. If the unresolved update fails, the earlier pending state still blocks launches. A normally exited leader with running descendants gets the same bounded TERM stop; leftover members mean unresolved failure. Inspect the entire recorded session so a child changing process group within it is not missed. Approved jobs do not detach into another session.

`--recover` takes the same lock, sends no signal, and creates no authority. A still-live matching wrapper, any running member of the recorded session, unreadable identity, malformed state, mismatched binding, retired authority, or inconsistent charge refuses. A different boot on the same machine proves old processes gone. On the same boot, inspect start ticks as well as PIDs; a reused PID is not the old process and is never signaled, but an ambiguous matching session leaves recovery closed. If no old process remains, clear pending state with synced replacement and retain the full charge. No pending run is a no-op. `--status` reports only the safe authority ID, allowance, charge, activation status, and pending/unresolved presence.

Crash proof uses real SIGKILL/restart at these boundaries: before readiness; after readiness before charge; after temporary-file sync; after replacement before directory sync; after durable charge before key; after key receipt before release; after release while the job lives; and after job exit before settlement. Pre-release kills start zero jobs; any released job has a durable charge. Restart never refunds, double-charges, clears an active session, or initializes missing authority. Injected sync failure complements SIGKILL tests; a process kill alone does not prove power-loss ordering.

### Cost and retained limits

The design removes filesystem FIFO markers, automatic builds, and file scanning. It adds no package dependency and makes no claim yet that the implementation is smaller. Report raw/nonblank counts for every production script/helper and every proof file, including Python outside the Rust ratchet, against the old 449/426 production and 1,158/1,090 proof baselines. The review must explain any growth and identify removed duplication. The authority directory remains essential operational state; Git cannot restore its latest charge. Refunds, recovery signals, and distributed locks remain excluded. A declared maximum limits authorized spending and does not mechanically cap a job's actual bill.
