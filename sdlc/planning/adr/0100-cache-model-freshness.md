# ADR 0100: Refresh mutable model aliases through requested cache work

Status: **Proposed for fresh design review.** Ticket [0238](../../tickets/0238-cache-model-freshness-and-refresh.md) owns implementation. This decision amends ADR 0020 only for answer-cache replacement. It does not amend strict recording or replay.

## Decision

The built-in default remains pinned to `jev-1.13.0`. The known mutable alias `jev-latest`, when selected as the effective request model through a command option, question file, or configuration for a write-capable answer cache, makes **each planned exchange a live refresh**. A valid cache hit is not returned. The ordinary request goes through the existing key, cancellation, deadline, per-address gate, retry, send-budget and usage path. There is no synthetic probe or extra question. Before the first possible send, the CLI states in fixed safe words that a mutable model alias refreshes cached answers and may incur a request for each planned exchange. Actual sends and retries retain their normal accounting. An explicitly requested `--refresh-cache` flag gives a pinned or other model the same behavior for this run; it is valid only with an active answer cache (named or platform default), and conflicts with `--record`, `--replay` and `--no-cache`. A configured disabled cache makes the flag invalid unless `--cache DIR` selects one. The flag applies to every CLI call carrying shared cache options, including annotate, find, recognize and relate, rather than being silently ignored by another verb. Library and SQL force-refresh controls are deferred; the known-alias cache rule belongs in the shared engine so those callers cannot silently serve an old alias hit.

Refresh acquires the existing per-digest lock under the shared folder gate before inspecting the entry and holds both through the live answer and installation. A complete decoded answer atomically replaces the valid version-one cache entry at the same digest, then syncs the directory; a failure before rename, a refused answer or an incomplete answer leaves the prior valid entry byte-for-byte intact. The replacement path reuses the private temporary file and final validation. A crash before replacement leaves the old complete entry; after rename and directory sync, the new complete entry is durable. Between rename and directory sync, either complete version can survive, including after a returned sync error. Concurrent refresh callers serialize by digest but each sends its own requested exchange after acquiring the lock; the last completed replacement wins. A cooperating ordinary cache miss waits on the same lock and then sees a complete entry. A pinned ordinary hit can be read before a refresher takes that lock, so concurrent runs do not get a global snapshot.

The `thinkthen.recording/1` envelope, request bytes, digest name, backend marker and lock names do not change. The response's existing `model` remains the evidence of which version answered. The strict marker schema cannot gain fields: the pinned `02dc0b96` and `72d60786` readers use `deny_unknown_fields`, and their writers publish the marker before entries. Existing readers can read either complete entry; older binaries do not inherit this freshness policy and can still serve a stale alias hit. An older cache writer may install or read an entry under its own policy, so a new process makes a live request on every alias-cache use rather than trusting shared-folder history. Explicit `--record` still sends and compares with an immutable first answer; a different answer remains a conflict. `--replay` remains read-only, keyless and offline, returning exact historical bytes with no claim about the alias's present target. `--no-cache` remains live and stores nothing. No migration, extra marker member or re-key is needed.

For `annotate`, all groups under a mutable alias cache are actual requested live calls. An old cached group plus a newly added group therefore no longer produces an artificial old/new mixture. The existing per-record `ModelsDiffer` refusal remains for genuinely different live reply versions, including an alias move during one run. No rejected group is silently substituted by an old cache answer. A completed earlier record may already have been emitted by a streaming command, and actual requests already sent still count.

`filter` and `rank` compare the actual reply model carried by **each answered row**, including a row that will be filtered out. The first answered row in input order establishes the run model. Check every later row in the ordered output path before printing or ranking it. One ordinary batch has one reply model, but `cli/asking/batched.rs::split_answered` may send a refused parent and two halves, then merge both halves into one `Completed<Vec<Judged>>`. A single model field on that completion would miss a difference between the halves. Carry each half reply's model into its own rows through `row_of`; the left rows precede the right rows. A 413 parent contributes an actual attempt but no answering model. If the right reply differs, `filter` retains only left rows it already printed and prints no right row; `rank` prints no ranking. Both half requests may already have been sent before the ordered callback sees their rows, so all three attempts count when the parent and both halves each send once. A partial first half retains its existing stop behavior and need not send the right half. The shared `decide`/`choose` row path may inherit this guard when it uses the same scheduler, but no claim about separate annotate/recognize/relate output modes follows from that reuse. A different model stops with exit 4 and fixed safe advice to pin `--model` and rerun. Do not print untrusted model names in the diagnostic. A later in-flight request may already have reached transport; cancellation cannot retract it, and usage reports actual attempts. A complete reply may also have refreshed its cache entry before the ordered-output check refuses the run; that entry remains valid evidence of the exchange, not a successful run result. Existing partial-answer, stopped-run and `--top` behavior otherwise remains. The existing per-record check for several `annotate` groups is retained, not replaced by the run check.

## Why this policy

An offline comparison between a stored `meta.model` and literal `jev-latest` cannot identify today's target. Refusing every alias cache hit would reveal the uncertainty but not satisfy the requested refresh workflow. One live first exchange followed by model-matched hits would save calls, but requires a run-wide alias epoch, coordination across concurrent requests, and a claim that the alias stays fixed after that one observation. Refreshing each requested exchange is bounded by the existing request plan and exposes exactly which work can cost money. A new standalone probe would add an otherwise unrequested paid request and would not guarantee later requests use the same model. Manual prune or `--no-cache` remains available, but neither updates a held cache entry. The cache-only exception to ADR 0020 is deliberate: an answer cache is reusable working state, while an explicit recording remains immutable evidence.

## Limits and separate findings

This policy observes only the model reported by actual responses. Select automatic alias refresh from **each prepared exchange's effective model**, not a recorder-wide boolean captured when an engine is built. `public/engine.rs::for_model` can override the built engine for one question while `facade::with_model` shares its recorder: a pinned engine asking an alias question must refresh, and an alias engine asking a pinned question must use an ordinary pinned cache hit. It cannot know the alias target before a live request, guarantee the provider holds an alias fixed across a run, validate a backend's truthfulness, or make a pinned model immutable at the provider. Explicit force refresh has the same bounded actual-request cost. A changed model in any run still causes the applicable refusal; already emitted streaming output and spent attempts are retained. It does not add vintage metadata or a fixture-refresh cadence (register 105), a trust warning for a named shared writable folder (register 40), or a tuned-profile contract beyond ticket 0159. No production folder is migrated by this design.
