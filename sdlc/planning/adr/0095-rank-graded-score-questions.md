# ADR 0095: Rank records by a saved graded question

Status: proposed for fresh design review with [ticket 0223](../../tickets/0223-graded-relevance-reranking.md). Date: 2026-09-28. This would amend the settled rank, score, result and question-file reference pages. No contract changes until acceptance and implementation. Ian may choose a wider public API or typed level list instead.

## Problem

The command's `score` computes a probability-weighted position on two to ten named levels, but prints records in input order. The command's `rank` sorts and supports `--top`, but currently accepts only a yes/no question. A person reranking search results with described relevance levels must run `score`, sort its result rows with `jq`, and recover the original records. The existing Rust and binding rank results instead promise a *yes probability* through `Ranked::probability()` and their corresponding host shapes. Reusing that field for a weighted level position would misstate its unit.

## Proposed decision

Accept a saved `score` question file in the **command** form `thinkthen rank @FILE [--top N]` over records. The file keeps the existing `score` grammar: two to ten levels in order, optionally an ordered map with descriptions, and existing `on`, model, profile and batch settings. A plain question argument and a saved `decide` file keep today's yes/no rank. Do not add positional rank levels, a new flag, a new file key or a second batch planner in this first slice. This file-only route supplies the described-level case that raised the issue. `rank` still refuses `--threshold`, `--quiet` and `--raw`; `--true` and `--false` beside a graded file must be refused as typed usage instead of silently ignored. A `choose` or `tag` file remains a wrong-kind usage refusal. A malformed or invalid score file remains a local-file refusal.

For a graded run, sort descending by the same normalized, twelve-decimal weighted position that `score` prints under `value`. Use `f64::total_cmp` and input order for exact ties **after that rounding**, including at a top-N boundary. Do not sort by the detailed `answer.level`, any single level's probability, or the backend's reported score field. The default view still prints the original records in ranked order; `--details` prints the existing `thinkthen.result/1` score shape for those records in that order: `question.verb: "score"`, `answer.kind: "score"`, numeric weighted `value`, original `input`, and `threshold: null`. It names the actual question and sorting quantity, so no rank-specific invented probability field or schema version is needed. `--facts` counts every completed record, including rows omitted by `--top`.

Use the existing score question, answer decoder, batch planner and request identity. A graded rank request has the same body and digest as `score @FILE` on the same records with the same framing, model, context and batch boundaries; its output order and record view differ. Ordinary yes/no rank retains its request, digest, result shape, tie rule and failure wording. Graded rank retains rank's no-partial-stdout stop, accurate actual-work metadata, and the 0220 top-N winner and pending-batch bounds. A stopped or timed input may send different speculative work or close a pause batch differently, as ADR 0093 already limits. Uncut rank still holds all scored rows; a top-N bound is on retained row count, not RSS.

Leave `Question::rank`, `Engine::rank`, public `Ranked::probability()` and the existing Python, TypeScript, Ruby, R and C rank shapes as yes/no operations in this slice. SQL probability queries also stay unchanged. The command issue can be solved without making a weighted position masquerade as a probability or designing a new cross-language result carrier. If graded library rank becomes an accepted need, design a separate truthful value type and binding parity. This is an outward choice: the alternative is to broaden Rust and each host now, which grows the contract and proof before there is an example that needs those APIs. Ian may overturn the CLI-first scope. Optional per-level weights have no demonstrated need beyond the current index weights, and RRF is a separate arithmetic transform over named ranked lists; retain both asks as open rather than declaring the entire issue closed.

## Proof boundary

Use the accepted `score` parser, arithmetic and request tests, plus one compiled-command edge table. Three-level distributions `(0.1, 0.3, 0.6)`, `(0.5, 0, 0.5)`, `(0, 1, 0)` and `(0.8, 0.1, 0.1)` have weighted positions `1.5`, `1`, `1` and `0.3`. The middle two tie on the printed value despite naming different leading levels; top two keeps the earlier of them. Check literal original-record output and graded details, counted sends and facts, a score-command body/digest comparison at stable `--batch 1`, unchanged yes/no rank, and a later failed graded row with empty stdout and the existing stop sentence. Use one wrong-kind/meaning refusal table and a dry-run plan; do not add a provider run, test-only product hook or broad gate. Read the affected settled pages and executable rank/score samples together before build, preserving ADR 0093's retention and timed-input limits.
