# ADR 0098: Scope caught native panic diagnostics to the owning binding

- Status: Proposed after the first independent High design review (session `01a0e6ac-7239-7b31-a3b0-bc2290d75158`); its payload-disposal, package-proof and loader-lifetime findings are corrected here for follow-up review. No runtime source is accepted or built.
- Context: [ticket 0226](../../tickets/0226-native-panic-diagnostics.md), the [panic-diagnostics issue](../../issues/2026-09-27-panic-diagnostics-can-copy-payloads-across-host-boundaries.md), and accepted ADR 0081's engine and Linux C++ bridge scopes.

## Proposed decision

For the remaining C, SQLite and older DuckDB C API routes, install one private delegating Rust panic hook per binding before owned work can panic. It calls the previous hook for unrelated threads and suppresses that hook only while thread-local binding depth is nonzero. An RAII depth guard restores the prior value through nesting, return and unwind. Scope encloses `catch_unwind` and fixed Defect mapping. Workers enter their own scope; caller thread-local state is not inherited. No global hook is taken or set for each call, and no public fault switch or shared framework is introduced.

The caught `Box<dyn Any + Send>` is opaque. Its destructor may itself panic, so each `Err(payload)` arm must deliberately `std::mem::forget(payload)` **inside the marked scope** before returning the fixed defect. C's nested `built` catch must do the same even though its message is already fixed. This uses the existing catch site in SQLite and old DuckDB: a second catch around Drop would violate their source check and could itself recurse. The cost is one unreclaimed payload per caught panic, potentially retaining sensitive bytes in process memory until exit and accumulating on repeated defects. It never writes those bytes to diagnostics or claims to erase them. A private child case with a marker-bearing payload whose `Drop` panics checks that the native door still returns a fixed defect, emits neither marker and permits a later call.

C `failures::guard`, SQLite `lib::guard`, and old DuckDB `errors::guarded` stop extracting a string from the caught payload. Each returns its existing Defect classification and a fixed safe message. C's nested `built` catch already has fixed text and remains inside the outer scope. SQLite's `worker::spawn` already calls its shared guard on the worker thread. Its exported `sqlite3_thinkthen_init` also needs to invoke that **same** guard around `Connection::extension_init2`: pinned rusqlite 0.40.2 does not catch there. Only an unexpected load panic maps to fixed safe `SQLITE_ERROR`; ordinary load errors retain their existing mapping. The old DuckDB `worker::run_typed` must use `errors::guarded` around its work on that thread, then convert the fixed caught defect to `RowError` without changing ordinary engine errors. This preserves its source check's one-catch rule. No edit to the accepted root engine hook or Linux C++ bridge hook is proposed.

The hook chain is cooperative, not exclusive. ADR 0081's root and bridge hooks may nest with these local hooks; a marked binding-owned panic must not leak to a previous hook, while an unrelated host thread still reaches it. A host that replaces the global hook after installation or races another installation can bypass this wrapper. Rust gives this binding no ownership over later host hook operations. The design makes no absolute claim under that condition. Current C calls accept pointers rather than Rust callbacks, SQLite's interrupt predicate is a C API function, and the old DuckDB SIGINT predicate is atomic. If implementation finds a Rust host callback inside a marked region, it must leave the binding depth for that callback and retain its own panic policy, as ADR 0081 does for direct engine host checks. C++ exceptions remain on the C++ side.

Do not infer that a Rust hook installed by one DSO is a host-wide pointer into that DSO. A representative packaged Linux C shared library at source `22f36d00` has a **local** `std::panicking::HOOK` BSS symbol, no `NODELETE` flag and no separately linked Rust runtime. In the bounded local workspace experiment `298-thinkthen-native-hook-loader-probe`, `dlclose` after a joined calling thread unmapped that exact artifact. Its hook state and hook code thus leave together on that observed route; a C self-reference is neither established as necessary nor proposed. The C static archive resides in the host image. SQLite's existing `ffi.rs::pin` remains **after successful registration** for its detached workers; do not retain a failed load merely for an unproved cross-DSO hook theory. These artifact observations are historical, not a proof of a newly compiled hook or of macOS linkage. Before any installed completion claim, inspect the changed artifact's Rust hook symbol/linkage, loader flags and actual load/unload result. If a supported package actually has hook state outside unloadable hook code, stop and propose the exact host-visible pin and failed-load lifetime choice to Ian after technical review. Pinned DuckDB v1.5.5 `extension_load.cpp` uses `dlopen` for the old C API package and has no `dlclose` call in its extension source tree; verify each target host and archive instead of inferring lifetime from Linux C++ tests.

A private child-process synthetic-marker case for each affected binding checks the exact fixed non-retryable Defect, absence of both string and panic-on-Drop payload markers from returned error and both streams, later-call recovery, and previous-hook delivery for an unrelated host thread. SQLite and old DuckDB each add their distinct detached-worker entry in that same selected child. Replace stale unit tests that expected payload text. The installed SQLite route must check the **exact load result** on the pinned stock host, including the supported macOS `.dylib` package: successful load and later call, below-floor failed load and subsequent host operation, and whether each path retains or unloads the DSO. The Linux `.so` check alone cannot close macOS. Installed C artifact linkage and loader checks and actual old DuckDB target-package checks remain separate. Source inspection or a Linux C++ package run cannot close an old C API route.

## Alternatives and limits

Changing only the caught error string leaves the default hook's earlier stderr print. Taking and restoring the process hook around each call can erase a host or another extension's hook and races concurrent calls. A public test-only panic switch would expose a new product path merely for proof. The proposed private scope follows the reviewed ADR 0081 pattern with one bounded child per binding. It does not settle the separately observed R payload copy or the other binding hook paths; those need their own routing and evidence before any repository-wide secrecy claim.
