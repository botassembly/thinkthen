# SQL find is missing from three databases

Filed 2026-09-27. Status: open. Source: `conformance/cases.json` cases `18-find-second` and `19-find-none`; `databases/duckdb/tools/conformance.py:29-35`, `databases/sqlite/tests/conformance.py:26-44`, and `databases/postgresql/tests/runner.py:52-58` skip them. Ticket 0150 explicitly deferred SQL find in `sdlc/tickets/0150-find-none-and-annotate-parts.md:109-110`. The equivalence study names the missing function F7 and proposes an aggregate in E3 (`sdlc/planning/library-equivalence-2026-09-26.md:79-83,202-208`).

All three SQL extensions lack a function that judges a bounded set of units together and can select none. Their scalar decision or probability calls do not implement `find`: they ask separate questions of separate rows, while `specification/find.md` fixes one bounded unit set. DuckDB and PostgreSQL have probability scalars; SQLite has neither a probability scalar nor a rank form. B13 batching changes request scheduling and does not supply the selection contract.

Retain the existing SQL scalar and table behaviors. Design one SQL group form per database that passes a complete ordered unit set to the existing public find operation, retains stable input indexes, represents a selected unit or none without ambiguity, and applies the same bounds and question settings. Reconcile its shape with the SQL mapping retained by ticket 0201 and the settled `find` contract before adding an API. Ian can overturn the SQL spelling after seeing that design; this issue authorizes no feature work.

Closure proof: run `18-find-second` and `19-find-none` through each installed extension against the shared case arm, compare the selected original unit or none and probability to the corpus, and remove both from all three skip lists. Include a small empty-set and tied-candidate boundary check if the SQL representation introduces a distinct edge. Keep this work after the current lightweight functional-gate cleanup. A feature ticket and independent review own the design and implementation.
