# SQL find is missing from three databases

Filed 2026-09-27. Status: open. Source: `conformance/cases.json` cases `18-find-second` and `19-find-none`; `databases/duckdb/tools/conformance.py:29-35`, `databases/sqlite/tests/conformance.py:26-44`, and `databases/postgresql/tests/runner.py:52-58` skip them. Ticket 0150 explicitly deferred SQL find in `sdlc/tickets/0150-find-none-and-annotate-parts.md:109-110`. The equivalence study names the missing function F7 and proposes an aggregate in E3 (`sdlc/planning/library-equivalence-2026-09-26.md:79-83,202-208`).

All three SQL extensions lack a function that judges a bounded set of units together and can select none. Their scalar decision or probability calls do not implement `find`: they ask separate questions of separate rows, while `specification/find.md` fixes one bounded unit set. DuckDB and PostgreSQL have probability scalars. SQLite exposes the probability through `thinkthen_details`; ticket 0206 proved its equivalent rank query against shared cases 15, 16 and 31. That query still does not supply grouped `find`. B13 batching changes request scheduling and does not supply the selection contract.

Retain the existing SQL scalar and table behaviors. Design one SQL group form per database that passes a complete ordered unit set to the existing public find operation, retains stable input indexes, represents a selected unit or none without ambiguity, and applies the same bounds and question settings. Reconcile its shape with the SQL mapping retained by ticket 0201 and the settled `find` contract before adding an API. Ian can overturn the SQL spelling after seeing that design; this issue authorizes no feature work.

Closure proof: run `18-find-second` and `19-find-none` through each installed extension against the shared case arm, compare the selected original unit or none and probability to the corpus, and remove both from all three skip lists. Include a small empty-set and tied-candidate boundary check if the SQL representation introduces a distinct edge. Keep this work after the current lightweight functional-gate cleanup. A feature ticket and independent review own the design and implementation.

Investigation at main `30bf6e81`: `databases/duckdb/tools/conformance.py`, `databases/sqlite/tests/conformance.py` and `databases/postgresql/tests/runner.py` still skip both IDs. Main's older 0201 ticket sentence calls `LIMIT` a find form, but the active 0201 ticket at `04ba4a10` corrects it and keeps this issue open. Use the active accepted design for pending 0201 scope and main for executable behavior. `specification/find.md` fixes one ordered bounded set, its original indexes and the none choice. An `ORDER BY thinkthen_probability(...) LIMIT 1` query cannot share that one set-level request or express the same none judgment. The accepted B13 design explicitly batches only rows one call sees; it cannot supply the missing selection contract.

The next design ticket should first compare an ordered array argument, an aggregate over rows, and each host's existing public find call against the exact result shape needed by SQL callers. Decide how a selected original unit, duplicate unit text, an empty set, ties and none appear without losing indexes. Name NULL and wrong-type handling, host file authority if a question file is accepted, and which host can preserve order before selecting a spelling. Reuse the captured request bodies and expected answers for cases 18 and 19; then add one listener-backed no-send invalid-input boundary if the chosen form introduces it. This investigation makes no API decision and authorizes no runtime change.
