# 0201 C++ product candidate

This is the in-progress replacement extension, not the shipped DuckDB surface. It calls the real public `thinkthen` engine through `bridge/` and now registers all ten retained scalars, `thinkthen_usage()`, and `thinkthen_warm`. The old C API extension and its tests remain active until every retained function and host behavior moves and the final candidate passes review.

The source is DuckDB v1.5.5 at `d8cdaa33fda8df955cc76ef58a280f68f4cd43fa`. The official [v1.5.5 Linux static release ZIP](https://github.com/duckdb/duckdb/releases/download/v1.5.5/static-libs-linux-amd64.zip) has SHA-256 `deb47c5300f3c99725e84cdb14d214c3b12bbd748b613b1698b938c894cb68eb`. `archive-sha256.txt` fixes every extracted `.a`; CMake rejects a changed source commit, missing archive, added archive, or hash mismatch. The source and archives are DuckDB MIT inputs. The Rust bridge depends on the repository's public engine and its pinned Cargo lock. The C++ file follows the separately accepted 0201 proof; no template code is copied into it.

With the verified source checkout and extracted archives in `DUCKDB_SOURCE` and `DUCKDB_STATIC`, build offline from the repository root under the canonical heavy lock:

```sh
export THINKTHEN_HEAVY_LOCK=/run/user/1000/thinkthen-heavy.lock
flock -o "$THINKTHEN_HEAVY_LOCK" cargo build --locked --offline --release --manifest-path databases/duckdb/bridge/Cargo.toml
flock -o "$THINKTHEN_HEAVY_LOCK" cmake -S "$DUCKDB_SOURCE" -B target/duckdb-cpp -G 'Unix Makefiles' -DCMAKE_BUILD_TYPE=Release -DBUILD_UNITTESTS=OFF -DBUILD_SHELL=OFF -DEXTENSION_STATIC_BUILD=OFF -DDUCKDB_EXTENSION_CONFIGS="$PWD/databases/duckdb/cpp/extension_config.cmake" -DTHINKTHEN_RUST_STATICLIB="$PWD/databases/duckdb/bridge/target/release/libthinkthen_duckdb_bridge.a" -DTHINKTHEN_DUCKDB_STATIC_DIR="$DUCKDB_STATIC"
flock -o "$THINKTHEN_HEAVY_LOCK" cmake --build target/duckdb-cpp --target thinkthen_loadable_extension -j 2
```

`verify_decide.py --extension PATH` uses the surface's loopback backend and isolated child process. Set `THINKTHEN_BACKEND_BIN` to the local `conformance-backend` binary, and use the pinned v1.5.5 Python environment. It asserts bad foldable and row-dependent questions send zero requests, NULL sends none, a valid question sends one, and SQL exposes `BOOLEAN`. Repeated evidence in each decision or probability chunk sends once, and probability returns `DOUBLE`, and details returns parseable JSON text as `VARCHAR`. It never uses a real key or paid service.

This slice groups and deduplicates one decision or probability chunk by question, deadline, and first-seen evidence. The `thinkthen_query_budget_ms` setting now starts one monotonic statement clock. The focused stock-host check proves zero-budget refusal with no send, recovery in the next query, and one live call after a 2,049-row vector boundary. It also checks the numeric throttle, per-call request, and process request-total settings refuse invalid or spent values before a send and recover after reset. The `thinkthen_cache` setting passes an absolute local folder to the existing engine registry after a caller-file-system permission probe. The stock-host check covers one allowed folder, invalid relative path, and a folder refused after external access is disabled. The listed `choose`, `score`, and `tag` scalars share whole-chunk validation, first-seen deduplication, and a checked result codec. Their focused cases cover returned types and values, repeated evidence, a later invalid list stopping sends, foldable bind refusal, and NULL propagation. `thinkthen_annotate` reuses the grouped text path with question-set validation and length-framed JSON output. Its focused case checks the value and zero-send failures for bad bind and later bad row. A parameterized NULL-row table binds the current distinct signatures without backend sends. The two nested-output scalars share an owned byte codec and reconstruct typed DuckDB lists and structs. Their family verifier checks complete entity offsets, relation endpoints, bad foldable and later-row arguments with zero sends, NULL rows, and an allowed and refused relation file. The try-details path preserves a bad foldable question as a safe failed row and lets later good rows answer; it converts a caller-refused or malformed `@file` to a safe local failure. The caller file system now reads ordinary question files and enforces the 1 MiB cap. The usage table returns four process counters; a focused stock-host check observes one request increment after a decision and no request from the table itself. The warm aggregate asks each distinct text once on the environment engine, keeps NULL rows out, refuses mixed questions, and reads allowed absolute files while refusing `@~` and caller-denied files. Its focused witness crosses one 2,049-row vector boundary with one live row and confirms that warm ignores the SQL request-total setting. This slice still needs the full file-permission matrix, SIGINT, relate, or final package checks. It must not replace the shipped extension until those behaviors and the shared worker panic boundary pass. A loadable binary from this folder is a build artifact for the ticket, not a release file.
