# Recording and replay

Status: **Settled** for version one, by an agent under ADR 0005. Ian has not read it, and he can overturn it cheaply until demos depend on it. Every token count and probability in an example here is illustrative. [ADR 0120](../sdlc/planning/adr/0120-sdk-result-and-cache-contract.md) settles the 0.2 storage/timing target below; its implementation remains in 0443–0445/0450.

A recording is a folder of stored answers, one for each question a backend answered. It lets a command run again with no network, no required key, and the same answer. A replay inspects an optional configured key to reject a collision with the resolved address before it reads the folder. Demos and tests replay recordings, so no gate ever reaches a backend.

## The options

| Option | Meaning |
| --- | --- |
| `--record DIR` | Send every question, even one already held in `DIR`, then store each answer, replacing a held one. `DIR` is created when absent |
| `--replay DIR` | Answer from `DIR` alone. Open no connection and require no key. Inspect an optional key for an address collision before opening `DIR`. A question that `DIR` lacks is a local failure, exit code 5, and the message names the missing question key and says what forms it |
| Both, with the same `DIR` | A cache. A held answer is replayed for a pinned model. A request naming `jev-latest` instead refreshes it. A question with no held answer goes to the backend, and its good answer is stored |
| `--cache DIR` | The row above, written once. It stands beside neither `--record` nor `--replay`, because one run keeps one folder |
| `--refresh-cache` | With an enabled answer cache, send every planned question live and replace each held answer. The flag stands beside neither `--record`, `--replay` nor `--no-cache` |

Giving both options with two different folders is a usage error. So is giving either option beside `--plan`, because a plan sends nothing and reads no recording folder. It only inspects the optional configured key for an address collision.

`--record` alone does not reuse a held answer. Recording the same question into a used folder sends it to the backend again and may incur another charge, and the new answer replaces the old one. For a pinned model, use `--cache DIR` or both `--record DIR --replay DIR` to reuse held answers. For a deliberate new measurement, copy the old folder for safekeeping, then direct the new run to another empty folder. In this example, neither destination exists yet:

```sh
cp -a runs/first runs/first-backup
thinkthen decide 'Does this need review?' --record runs/second < case.txt
```

The command creates `runs/second`.

A request naming the mutable `jev-latest` model refreshes automatically in a write-capable answer cache, including an explicit same-folder record/replay pair. Before a CLI run can send, a fixed warning says each planned cache question may incur a charge. No extra probe is sent. `--refresh-cache` applies the same live replacement to another model in an enabled named or default answer cache. A disabled default cache requires `--cache DIR` for this flag. A good live answer replaces the held one in the same transaction that stores it. A refused or failed answer leaves the held answer untouched, and that run never serves it silently. `--replay` remains keyless, read-only history and never checks where an alias points today.

With none of these options, normal commands use the platform answer cache: `$XDG_CACHE_HOME/thinkthen`, then `$HOME/.cache/thinkthen` on Linux, and `$HOME/Library/Caches/thinkthen` on macOS. On Windows it is `%LOCALAPPDATA%\thinkthen\cache`. `THINKTHEN_CACHE` selects another folder. The SQL extensions never use the platform folder; they cache only in a folder `THINKTHEN_CACHE` or their own cache setting names. `--no-cache` disables answer-cache lookup and writing for one run. Explicit `--record` or `--replay` suppresses the default cache. Plan previews, help, version, `status`, `backends check`, and `cache prune` create no default cache.

`thinkthen status` is read-only and opens no connection. It reports the version, resolved configuration with provenance, key presence, the answer count of the cache's `thinkthen.sqlite` as `cache_entries`, that file's allocated bytes as `cache_bytes`, the count of old digest-named entries beside it as `cache_old_entries`, the prune target as `cache_prune_target_bytes` with its source as `cache_prune_target_source`, and local usage for the current UTC month and all months. `status --json` emits the same facts as one closed `thinkthen.status/2` object. `status --backend NAME` reports that backend. The human form prints `backend NAME` or `backend none` and `key_variable NAME`, the first variable the key would be read from; `api_key_set` reports that variable. The JSON `backend` object carries `name` (a string or null) and `key_variable`, and `url_source` and `model_source` read `backend` when a named backend supplied the value (ADR 0114). JSON names the three cache counts `cache.entries`, `cache.bytes` and `cache.old_entries`, and an absent cache path makes each null. Version 2 moves no field: `.usage.total.requests_sent`, `.usage.total.input_tokens`, and every other kept version-1 path stay where they were. It drops `cache.binding`, `cache.bad_entries`, `cache.temporary_entries` and `cache.temporary_bytes`, because ADR 0111 section 10 retires the folder marker, bad entries and temporary entry files they counted. Status opens `thinkthen.sqlite` read-only and exits 5 when it is not a question store. No line holds a key. It shows one combined total of what every surface sent (ADR 0113). The command and every engine built from the environment, which covers each library, the C door, the data frames and the three SQL extensions, add their counts to the same files. `EngineBuilder::new()` keeps its counts in memory. A SQL extension writes its counts when its process exits; a crash loses the last ones. A PostgreSQL backend writes to the usage folder of the server's operating-system user, so `status` run as that user sums every backend. Each SQL extension's request total is per process: PostgreSQL counts it per connection, so a pool of N connections can spend N times it. Every attempt, a retry included, reserves its unit atomically, so calls running at the same time cannot pass the total together. Status accepts no judgment overrides.

Usage is state. Clearing the cache never resets it (ticket 0360). It lives at `$XDG_STATE_HOME/thinkthen`, then `$HOME/.local/state/thinkthen` on Linux, and `$HOME/Library/Application Support/thinkthen/usage` on macOS. On Windows it is `%LOCALAPPDATA%\thinkthen\usage`. macOS has no state folder, and the system may purge `Library/Caches`. `THINKTHEN_CACHE` never moves it, and `--no-cache` never disables it. One private `YYYY-MM.json` file per month holds checked aggregates for requests sent, retries, input tokens, output tokens, and cache answers in the `thinkthen.usage/1` shape. A month file without `retries` reads as zero retries. Any other name in the folder, such as a `retries-YYYY-MM.json` file an older build wrote, is not a month and is ignored. A stable private `.lock` serializes writes across processes. The writer makes `.lock` before any month file and installs a month only by renaming a complete file, so a folder without `.lock` holds no month thinkthen wrote. Its month files are read without the lock: a valid month counts, and a malformed one refuses as it would under the lock. A read that fails after another process made `.lock` reads again under it (ticket 0367). Every replacement syncs its temporary file, renames it, then syncs the directory. `status` reads the files without changing them, and waits at most one second for another process's lock. The files contain no request, response, address, model, price, or key. Nothing reads the older `thinkthen-usage` folder under the cache home; its counts are not carried over.

On Windows, the usage folder, `.lock`, `.update.tmp` and recognized month files must be owned by your user. Their access permissions may grant access only to your user and Windows SYSTEM. Read-only access for another user also refuses usage. ThinkThen creates missing objects with protected private permissions and never repairs existing permissions. It refuses leaf reparse points, the wrong object type, unreadable security information and a changed native file identity. It checks the existing temporary file before truncation. Windows does not sync the directory after replacement. These checks cover the named objects and do not impose a whole-drive ancestor policy. Unsafe-state advice says `Make it owned by your user and restrict its Windows access permissions to your user and Windows SYSTEM, or move it aside.` A generated filename instead ends with `or move it out of the usage folder that thinkthen status names.`

Every HTTP attempt counts immediately before it is sent, including a retry or failed attempt. `retries` counts the retry subset of `requests_sent`. `status` reports monthly and total retries. Validated provider token counts count once for each successful live response, including a response whose answer is later refused. Replayed response bytes add no tokens. A decoded hit in the platform cache, `THINKTHEN_CACHE`, or `--cache` counts as a cache answer. Explicit replay and an explicit record/replay pair do not. Packed `annotate` groups count as their actual exchanges.

Before a process's first send, its counters read the usage totals once. This covers the command and every engine built from the environment. If the usage folder exists and cannot be read, that send and every later send in the process are refused, and nothing is sent. A month file of zero bytes is malformed, as is any file that is not one `thinkthen.usage/1` object. The command exits 5, and a library or SQL call returns a local error. The sentence names only the generated file name, or the usage folder, and the fix. One example is `cannot read the usage totals: 2026-09.json has invalid contents. Move it out of the usage folder that thinkthen status names, and counting starts again.` A lock another process holds for more than one second passes the check, so the first send can wait up to one second. Plans, dry runs, replay and runs answered only from the cache send nothing and are never refused. `status` on an unreadable count prints the rest of its report, shows the month and total counts as `unavailable` (JSON `null`), writes the same sentence with the full path on standard error, and exits 0.

A write that fails after a good start is best effort. Its first failure disables later updates in that process. The command prints one fixed warning after ordered results; it never changes a judgment, output order, or exit meaning. The libraries and SQL extensions still drop such a failure without a word, as [the debt issue](../sdlc/issues/closed/2026-09-30-a-usage-write-that-fails-after-a-good-start-is-silent-on-the-libraries.md) records. The command waits for its usage writer after its result. From that finish point, the writer allows one second in total for any remaining attempts to acquire another process's usage lock. If the lock stays held, the writer abandons unwritten counts and prints the same fixed warning before final `--facts`. Other filesystem operations can still delay exit. ADR 0097 amends ADR 0049 item 3's unlimited lock wait. A crash can undercount the requests and tokens counted after the last write that finished. These totals describe local observations and are not a provider bill. A missing month stays absent until a complete replacement is installed. The writer refuses a zero-byte or otherwise malformed recognized month; it never silently resets it or guesses its lost totals. The writer's warning names only the generated filename and a fixed error category.

An XDG home, `HOME`, or a Windows `APPDATA` or `LOCALAPPDATA` home participates in these paths only when it is absolute. A relative or blank home is unusable and never resolves below the working directory.

The default cache folder is created only when a run first opens its store or checks it before a send. A rejected record or invalid `find` set creates nothing. Before a call's first send, a writing store checks that it can keep the answer (ticket 0367). It makes the folder as a write would, opens an existing `thinkthen.sqlite` for writing, and creates and removes one file of its own in the folder, where SQLite writes its journal. It makes no store file. A folder that fails refuses that send and every later send of the call, and nothing is sent. The command exits 5 with the default cache or recording folder sentence; a library call returns the same local error. This covers the platform default cache, `THINKTHEN_CACHE`, `--cache` and `--record`. The check runs after the key and usage checks, and before a send total or token cap is charged, so an unwritable folder outranks a cap refusal. A run refused by such a cap, or whose send then fails, can therefore leave the empty folder the check made, with no store file. Replay and a run that sends nothing make no check. Replay of a missing explicit directory reports the question's normal replay miss and creates no directory. Replay of an existing read-only directory changes no file or directory metadata.

The optional read-only configuration file is `$XDG_CONFIG_HOME/thinkthen/config.json`, then `$HOME/.config/thinkthen/config.json` on Linux, and `$HOME/Library/Application Support/thinkthen/config.json` on macOS. On Windows it is `%APPDATA%\thinkthen\config.json`. It has schema `thinkthen.config/1` and optional `url`, `model`, `cache`, positive `cache_bytes`, `usd_per_million_input` and `usd_per_million_output`, `backend`, and `backends` fields. `backend` names the default backend and `backends` adds named backends, each with `url`, `key_env`, `model`, and optional `path`, `requests_per_minute`, `both_sides`, atomic `usd_per_million_input` and `usd_per_million_output`, and inline `profile`. A built-in accepts any nonempty subset of rate, atomic prices and profile. That rate holds within one process, and separate processes each get the full rate, as [backends.md](backends.md#named-backends) says. The file names key variables and never a key ([backends.md](backends.md#named-backends)). Unknown fields are refused. Each refusal names the field, never a value, and exits 5. The default is cache enabled, and `cache_bytes` defaults to 100,000,000 allocated bytes. `cache_bytes` is the target `cache prune` trims to. Nothing trims the cache on its own. It grows, and keeps the judged text, until the user runs `cache prune`. The tool never creates or edits this file.

A recording directory argument that names a regular file is a local failure at exit 5. The diagnostic says to choose another path or remove the file. It repeats neither the path nor an operating-system error.

Answers from two addresses never mix, because the address is part of every question key. A cache pointed at a new address misses and sends again, and the folder then holds both addresses' answers. ADR 0111 section 3 retired the backend marker `.thinkthen-backend.json`, the `.locks` folder and the folder gate. A marker or lock a former version left is ignored and kept.

Both options on one folder are also the resume for a record run. A resumed run asks again only the questions whose answer failed, because a store keeps no failed answer. [records.md](records.md) shows it.

## What replay changes in a result

For landed result/1, `meta.cached` is `true` when every answer came from the store and `false` when a backend answered. It is always present. `meta.requests` lists the row's question keys, the same keys that name its stored answers. Replay and live execution therefore report one identity. Everything else in the result is what the stored answers yield, their usage shares included. A later token ledger counts only answers that a backend gave.

Result/2 adds actual source/observation identity and uses v2 question keys under [result.md](result.md#metadata-and-empty-aggregates) and [cache.md](cache.md). A result with zero observations has null origin, no answered model and `cached:false`; an empty actionable value after stored answers still reports their provenance. Refresh changes observation identity, cache/replay retain it, and rereading changes answer identity only when the normalized reading changes.

A store installs no failed answer, so a replay of a question the backend failed is a miss at exit 5, and a cached run asks it again. ADR 0111 section 6 rules it. To retry a failed question, run the same command again under a cache. This includes `relate` edges.

## A recording holds the evidence

The request body carries the evidence. A recording is as private as the input it was made from. Record only what may be kept, and keep a recording of private input out of version control.

## Pruning a cache

`thinkthen cache prune DIR` is the only answer removal surface, and `DIR` is always explicit. It trims `DIR/thinkthen.sqlite` and never touches a fixture, an old digest-named entry or any other file. A folder with no `thinkthen.sqlite` has nothing to prune. Bare prune commits immediately; `--dry-run` opens the file read-only and previews the same selection without changing a byte. Both forms take the same selectors. `--older-than Nd|Nh|Nm|Ns` and `--answered-by-other-than MODEL` select a union. `--older-than` compares each answer's `taken_at` second with the current time. MODEL is matched byte for byte against the model each reply names. When some answer asked for MODEL and no reply names it, MODEL is the alias, and prune exits 2 before it deletes anything with ``--answered-by-other-than names the model the requests asked for, and no reply names it, so prune removed nothing; name the version a result's meta.model shows, not the alias passed to --model``. When the store holds an answer and no reply names MODEL, as with a typo or a newer version that has not answered yet, prune exits 2 before it deletes anything with ``--answered-by-other-than names a model no reply in the folder names, so prune removed nothing; name the version a result's meta.model shows, or delete the folder to remove every answer``. The alias sentence above wins when some answer asked for MODEL. A newer version that has answered at least once removes every older answer.

`--max-size BYTES` sets a separate target; without it, the configuration target applies. Selected answers leave first. Then the oldest `taken_at` leaves, equal times sorted by question key, until the kept answers fit the target. Prune reckons an answer's share of the file by the length of its stored text: the kept share is the file's allocated bytes times the kept answers' text over all answers' text. A cache hit does not refresh `taken_at`, so a frequently read old answer can leave before a newer one that was never read. Commit deletes the chosen answers and every stored state no answer uses in one transaction. Then it runs `PRAGMA incremental_vacuum`, which gives the freed pages back to the file system. The file's fixed pages stay, so a small target can leave the file above it. Committed prune prints `removed N answers and B bytes; K answers and C bytes remain`. B is how much the file shrank, and C is its allocated bytes afterwards. Preview prints `selected N answers and B bytes; K answers and C bytes unselected`, followed by `selected KEY` in deletion order for each chosen answer. There C is the kept share, and B is the rest of the file. A preview is a snapshot, not a promise that a later commit will remove the same answers. Prune waits up to 30 seconds for another process's write, as a run does.

`thinkthen cache unused DIR --used KEYS` reads an existing explicit folder. It reports the question keys the folder holds that a caller-supplied complete list lacks. KEYS is a UTF-8 file with one lowercase 64-character question key per nonblank line. Duplicates and blank lines are ignored, and an empty file reports every answer as unused from the supplied list. An invalid line is refused before DIR opens. The command reads `thinkthen.jsonl` as a replay reads it, and otherwise opens `thinkthen.sqlite` read-only. A folder holding both files is refused as a replay refuses it. A fixture line that does not parse refuses the whole report without partial output. The report prints `unused from supplied keys: N`, then `unused KEY` in lexical order. A replay's `meta.requests` lists the keys a run used. The command creates no cache, usage state or answer. It neither proves the supplied list covers a suite nor removes answers.

## Converting a folder to the question fixture

`thinkthen cache convert DIR [--quote]` writes `DIR/thinkthen.jsonl`, the question fixture of ADR 0111, from the union of what `DIR` holds: an existing `thinkthen.jsonl`, a `thinkthen.sqlite`, and every old `DIGEST.json` entry of schema `thinkthen.recording/1`. It reads them in that order, and the old entries in name order. When two sources hold one question key, the newer `taken_at` wins, and a tie keeps the entry read first, so a fixture keeps its own entries. It opens `thinkthen.sqlite` read-only.

Each old entry is decoded against its own request. The request's state, model and each question are written again as compact JSON. They must join back into the recorded body byte for byte, and each key hashes those bytes. An entry that does not rejoin is skipped with ``thinkthen: cache convert: skipped `NAME`; its request does not rejoin byte for byte from its parts``, and an entry whose reply holds no answer that decodes is skipped the same way. Only good answers are written. A failed answer is left out, so the next run asks it again. Each written answer keeps the reply's model as `answered_by` and its even share of the reply's usage, the remainder to the earliest question. Every converted answer takes `taken_at` 0 and `origin` `converted`. An entry whose envelope carries `"quoted": true` gets `origin` `quoted`. A `{"records":[…]}` exchange is written under the state `Each question quotes the text it asks about.`, because its questions already quote their records. With `--quote`, a single-record exchange is also written in the quoted form: the state becomes that sentence, each string instruction becomes `The text is `, the record's compact JSON, `. ` and the instruction, and `origin` is `quoted`. An exchange with a JSON instruction is not quoted. An exchange whose instructions already quote a record is not quoted again: such an instruction begins `The text is `, one complete JSON value, and `. `, and the value is the state's own JSON or a string, list or object, as a context exchange quotes its records. A question in the user's own words that begins `The text is the title`, or `The text is true. `, is quoted. No old entry tells two rare cases apart from a quoted record: a question that opens with a quoted word, such as `The text is "urgent". `, is left unquoted, and a context exchange over bare number or `true` records is quoted a second time.

The fixture is written through a temporary file in `DIR` and renamed into place. Then `thinkthen.sqlite` is removed, because `--replay` refuses a folder holding both files. The command waits for the file's write lock and holds it from its read to its removal. Run it only when no live writer has the folder open: a process that holds the file open keeps writing to the removed file, and those answers are lost. Old entries stay in place, so the command can run again, and converting the same folder twice writes the same bytes. It prints `thinkthen: cache convert: wrote N answers to thinkthen.jsonl, M from old entries, U left unquoted; skipped K entries` on standard error and exits 0. U counts the answers from old entries written only in the old form: a single-record exchange without `--quote`, or one with a JSON instruction. A replay on this version misses them, because each request quotes its record in its question (ADR 0111). A missing `DIR` exits 5 with `cache convert takes an existing folder, and the one named is missing or not a folder`. A digest-named file that cannot be read or is no recording entry, a fixture that does not parse, or a live file that cannot be read exits 5 before anything is written.

## Optional timing history for 0.2

Status: **Settled** target by ADR 0120, implemented by 0445. Native `CallOptions::attempts(true)` with explicit recording and CLI `--details --record DIR` opt into timing history. Ordinary recording, cache and refresh calls keep no sidecar. An opt-in `thinkthen.timing.jsonl` sidecar is separate from header-free answer bodies. Each line has saved question `key` and timing-only attempt fields `ordinal,wall_ms,outcome,status?,server_ms?`, using the types and meanings in [result.md](result.md#call-facts-transport-and-attempts). A packed attempt may be attributed to multiple saved keys. No raw headers, provider/SDK IDs, address, evidence or request/response bodies enter this file.

Bound the whole sidecar to 8 MiB and 65,536 line entries. Overflow is a local recording failure (CLI exit 5), not silent truncation or a reason to retry a send. Replay never re-emits historical entries as current attempts; requested current replay attempts remain []. `--record` with a nonstorable reply fails with the exact [Cache-Control refusal](cache.md#response-cache-control), storing none of that reply's answers or sidecar entries. Transient call/request IDs remain absent from all recording artifacts. Persistent observation IDs are answer metadata under cache/2, not transport headers.

Timing writers hold one folder lock through bounded history validation, the existing atomic answer/original-body transaction and sidecar replacement. Invalid or full existing history fails before inserting the new answers and leaves the old history unchanged. The sidecar is written through a private temporary file and renamed; it is not in the SQLite transaction. A filesystem failure after that transaction commits returns a local error and can leave the accepted answers recorded without the new timing history. It never retries the send. Replay ignores the sidecar and changes none of its bytes.
