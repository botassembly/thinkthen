# Resource observations

Read these limits before installing or making paid calls. The resource observations below come from the pre-release qualification campaign. They do not prove that any surface is free of leaks. Later observations cover only their measured intervals. The earlier PostgreSQL System One descriptor failure remains a historical failure.

The extended Java and TypeScript observations used Linux x86_64 with glibc 2.28 and a local backend stub, without forced collection. Each completed 60 rounds of 100,000 records. Their figures measure the change in RSS across owned processes from the completed-round 41 checkpoint to the round 60 checkpoint, over 1,900,000 subsequent verified records. Both intervals met the extended-soak floor of less than 1 byte per verified record and are recorded as finite-window warm-up or allocator retention. Their storage owners and behavior after round 60 remain unproven.

The resource soaks ran on Linux only. Memory over long runs on Windows and macOS is unmeasured.

An Excel workbook's whole shared-string table loads into memory, and that table may hold up to 512 MiB. One record of plain text, lines, CSV, TSV or JSON Lines input, or one Excel row, may hold up to 64 MiB.

| R memory (System One client path, local stub) | A later observation with R 4.3.3 on Linux x86_64 and glibc 2.28 used a local backend stub and completed 60 rounds, 6,000,000 correct rows and 187,500 requests. Between checkpoints 41 and 60, over 1,900,000 subsequent verified records, group RSS rose from 804,405,248 to 805,421,056 bytes: 1,015,808 bytes, or 0.5346357895 bytes per record. R process RSS rose from 800,493,568 to 801,509,376 bytes. The allocator arena remainder fell from 735,384,379 to 729,055,293 bytes: -6,329,086 bytes, or -3.3310978947 bytes per record. Allocator mmap storage stayed at 7,421,952 bytes. This interval is accepted as finite-window allocator retention under the qualification rule. The arena remainder includes tcache and allocator overhead; allocator quantities are not resident memory or measurements of live objects. Capture adds overhead and the snapshots are not atomic. Natural level-2 collection figures are rounded to 0.1 MiB and are not aligned to checkpoints. Allocation owners, allocation sites and future growth remain unproven. Earlier failures remain failures. |
| Ruby memory (System One and OpenAI client paths, local stub) | On Linux x86_64 with glibc 2.28, Ruby 3.3.8 and FFI 1.17.4, RSS changed by 0.065 bytes per verified record on System One, a PASS for every measured resource criterion, and by 1.261 on OpenAI over rounds 41 to 60. The OpenAI figure is above the 1 byte floor and is attributed to glibc allocator retention: in separate diagnostic runs on another Linux machine's own glibc, glibc's bytes in use and Ruby's live objects stayed flat while the free storage glibc kept grew; the run that measured 1.261 did not record those series. The release check accepts the figure only while glibc's bytes in use, counting the blocks glibc maps on their own, Ruby's live object heap, and RSS outside the storage glibc has mapped all stay under the same floor over the same rounds. That last check cannot see growth outside glibc that is offset by pages glibc still counts but has returned to the system. That room was about 0.31 bytes per verified record over rounds 41 to 60 of one diagnostic run, and far more in another, and the release soak does not measure it. So a leak up to the 1 byte floor plus that room could be hidden and cannot be ruled out. The installed Ruby library returns freed allocator storage once per call, which cannot release storage fragmented within pages. A user may set `GLIBC_TUNABLES=glibc.malloc.mmap_threshold=65536` before Ruby starts: in a 15-round trial on another Linux machine it kept glibc's arena nearly flat and cut RSS growth by about a third, but it was not measured over rounds 41 to 60, and the library does not set it. Allocation owners, future growth and absence of leaks remain unproven. |

The earlier qualification campaign covered 34 surface/backend pairs. Seven PASS observations cover C#, SQLite and PostgreSQL on both the System One and OpenAI client paths and Ruby on the System One client path. One attributed allocator-retention observation covers Ruby on the OpenAI client path. Six new installed-package observations and one saved historical PostgreSQL/OpenAI observation meet the extended-soak memory criterion and all other measured resource criteria. Each completed 60 rounds of 100,000 correct records against local backend stubs, with 187,500 requests and zero failed rows. Their RSS figures compare completed checkpoints 41 to 60 over 1,900,000 subsequent verified records. Three separate retention observations cover TypeScript and Java on the OpenAI client path and R on the System One client path. These three windows met the extended-soak floor and are accepted as finite-window warm-up or allocator retention under the qualification rule. Their storage owners remain unproven. These observations do not replace earlier results or establish behavior on other platforms. This is not an all-pass qualification of the new release. Use bounded workloads and monitor process resources for long-running applications.
