# Java and Kotlin packaging proposal

Use Maven with one parent project under `sdk/java`, a Java artifact `io.github.botassembly:thinkthen-java`, and a Kotlin artifact `io.github.botassembly:thinkthen-kotlin` sourced from `sdk/kotlin`. Keep the repo's current package version until the release milestone sets the next publication version. Java callers depend only on the Java artifact. Kotlin callers depend on the Kotlin artifact, which brings Java transitively. Both Maven and Gradle consumers use these ordinary coordinates. Publishing is outside this ticket.

The Java artifact contains the hand-written Java classes and the engine's shared library as resources selected by operating system and architecture. A build stages native assets from that same revision; the wrapper never searches the system library path or downloads a native library at runtime. The package ships Linux amd64 and macOS arm64 assets. Each platform gate tests a fresh installed consumer with its matching asset; package assembly combines those assets from the same revision. No bootstrap version check or compatibility negotiation exists.

The loader opens unpacked file resources directly. For JAR resources it retains one SHA-256 keyed copy under the platform user cache: `Library/Caches` on macOS, `LocalAppData` on Windows, or absolute `XDG_CACHE_HOME` with `~/.cache` as the Linux default. These follow [`os.UserCacheDir`](https://pkg.go.dev/os#UserCacheDir) and the [XDG specification](https://specifications.freedesktop.org/basedir/latest/). It publishes complete files atomically and verifies existing copies before reuse. Cache entries persist across processes and can be removed while no caller uses them. The system temporary directory is never used for the engine. Java's built-in foreign function and memory API keeps the lookup alive through a global arena for process lifetime. Missing assets fail with a useful Java loader error. There is no user-configured native path. Calls never unload the library because native workers may still be finishing after call cleanup.

Runtime dependencies have distinct purposes:

- Jackson databind provides normal JSON parsing, serialization and JSON trees. Java's standard library has no general JSON facility; a private JSON parser would add unrelated code. Core and annotations arrive transitively.
- JSpecify supplies nullable API annotations so the Kotlin facade reuses Java rows without duplicating them. It introduces no engine validation or runtime framework.
- The Kotlin artifact uses Kotlin's standard library and `kotlinx-coroutines-core` for suspending methods, cancellation and `Flow`. Java users do not acquire coroutine dependencies.

Use pinned dependency and compiler plugin versions in the implementation. Maven supplies dependency resolution and packaging; it introduces no application framework. The JDK compiler uses release 22. Both published artifacts require Java 22 at runtime; a lower Kotlin bytecode target would not lower that requirement. Kotlin compilation targets a JVM level compatible with Java 22 and treats JSpecify nullability strictly. No generated source is committed. The Java artifact uses the classpath, so its documented native access flag is `--enable-native-access=ALL-UNNAMED`.

Dependency preparation runs separately before offline package tests. Gate builds reuse the same native output for Java and Kotlin. The consumer gate installs built JARs and their ordinary dependencies into an isolated local repository and runs offline, away from the source classes. It exercises the resources extracted from those JARs, so a missing engine resource cannot pass by finding a development build.

The platform facilities used here are documented by [Java 22 SymbolLookup](https://docs.oracle.com/en/java/javase/22/docs/api/java.base/java/lang/foreign/SymbolLookup.html), [Java 22 Arena](https://docs.oracle.com/en/java/javase/22/docs/api/java.base/java/lang/foreign/Arena.html), [Kotlin Flow](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines.flow/flow.html), and [cancellable continuations](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines/suspend-cancellable-coroutine.html).
