## Corrections after the adversarial review, 2026-09-21

The three-lens review found one interrupt defect, confirmed by probe, and several overstatements in the records. Corrected here and in `experiments/211-thinkthen-blocking-engine/FINDINGS.md`:

- **The interrupt promise.** The poll ran only on idle waits, so a fast backend starved it: SIGINT one second into a three-million-record null batch surfaced at 8.48 s, after the batch drained. The fix wave (`f9db281`) runs the poll from the answer arms too, gated by one tick since the last poll; the same probe through the Python shim surfaces in about 0.8 s (0.772 s in the lane's recorded run), and `libraries/python/tests/test_cancel_fast.py` holds the regression — the Rust test fails in 2.87 s with the busy-arm ticks dropped and passes in 0.24 s with them. The promise now pinned: an interrupt or a spent deadline surfaces within one poll tick, however fast the backend answers; the `AbortSignal` shape holds it. Every binding's interrupt reaches the engine through the one poll: SQLite's progress handler, PostgreSQL's interrupt check, and DuckDB's chained SIGINT-at-LOAD handler — proven inside a Python process at 0.11 s with the wire frozen — as that surface's channel, alongside the deadline in the call options. This is the shape ADR 0017 copies.
- **PostgreSQL's cancel physics, corrected 2026-09-22.** The earlier claim that the same promise held for `pg_cancel_backend` and `statement_timeout` was wrong and is removed. The deadline is the tool on this surface: a single-row call is one blocking network round, so `pg_cancel_backend` and `statement_timeout` arrive only when the round returns, and the batch shapes stop at the engine's next tick after the signal (measured: the array overload 0.30 s past the signal, `statement_timeout` 1.23 s for a 1 s timeout). The setting `thinkthen.deadline_ms` is resolved before any request is sent and ends a mid-batch call at the engine's tick — measured: a spent budget sends nothing, a 50 ms budget ended a 300k-record batch in 0.37 s on the null backend and a 64-record wire batch in 0.28 s against the 300 ms stub. `databases/postgresql/NOTES.md` carries the pre-fix and post-fix commands.
- **"Three passes each by builder and orchestrator"** was an overstatement in the 211 findings: the builder ran three null-backend passes and the orchestrator one. Corrected there.
- **"The findings, all pinned and filed"** was an overstatement on this page; the paragraph above now names where each finding is recorded.
- **The derived numbers** are labeled as derived in the 211 findings: the thread-count halving from the resolver fix, and the single-batch retention note.
- **The missing relations finding is filed**: `the deck repository's issue` (`7a1bbdb`).
